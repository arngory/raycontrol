# 06. Требования к клиенту (для следующей фазы)

Статус: **требования**. Клиент в этой фазе не реализуется. Документ фиксирует, что серверная часть должна
дать клиенту, и ограничения, которые клиент накладывает на сервер.

## Назначение

Один кроссплатформенный клиент с двумя режимами:

- **Пользователь**: подключение к одной или нескольким нодам всеми доступными способами, с автоматическим выбором и переключением.
- **Администратор**: управление нодой через её API — то, что сейчас делает `rayctl`.

Режим определяется ролью устройства (`devices.role`) и его областями доступа (scopes), а не настройкой в интерфейсе.
Одно устройство может быть администратором одной ноды и пользователем другой.

## Платформы

Android, iOS, Windows, macOS, Linux. Опционально: OpenWrt (роутер) как отдельная сборка без интерфейса.

## Режим пользователя

**Подключение к ноде**
- Регистрация устройства по одноразовой ссылке или QR от администратора: клиент генерирует ключи (SPA, mTLS),
  нода выдаёт сертификат устройства и набор профилей.
- Импорт сторонних ссылок и подписок (vless://, hysteria2://, qwdtt:// и т.п.) — для совместимости.
- Получение и обновление профилей через API ноды (подписка с подписью ноды).

**Работа с профилями**
- Профили всех классов входа: direct, relayed, rendezvous, dns ([05-transports-research.md](05-transports-research.md)).
- Приоритеты и автоматическое переключение: проверка доступности, переход на следующий профиль при блокировке,
  возврат на лучший при восстановлении.
- Встроенные knock + SPA (библиотека `rayknock`) для gated-сервисов, продление доступа до истечения TTL,
  повтор SPA при смене IP (Wi-Fi ↔ мобильная сеть).
- Для движков без пользователей — вторая ступень аутентификации к `ray-core` внутри туннеля.

**Сеть на устройстве**
- Режимы TUN (системный VPN) и локальный SOCKS5/HTTP-прокси.
- Раздельное туннелирование: по приложениям (Android, Windows, macOS по возможности), по доменам и адресам.
- Kill switch и защита от утечек DNS.
- Свой DNS (DoH/DoT) внутри туннеля.

**Учётные данные третьих сторон на клиенте**
- Для relayed и rendezvous клиенту могут понадобиться данные платформы (хэши звонков, комнаты, доступ к бакету).
  Нода выдаёт их в профиле; клиент хранит их как секреты.
- Обработка капчи платформ во встроенном WebView.

## Режим администратора

- Пользователи: создание, срок, лимит, блокировка, выдача профилей и QR.
- Устройства: регистрация, роли, отзыв, ротация ключей.
- Сервисы: включение и выключение движков, профиль public/gated, порты, статус и здоровье.
- Учётные данные третьих сторон: добавление, проверка, ротация.
- Периметр: активные доступы SPA, баны knock, аварийный доступ.
- Статистика и журнал аудита.
- Обновление движков и ноды, бэкап и восстановление.
- Подтверждение опасных операций (удаление, отзыв всех ключей, отключение периметра) повторной аутентификацией.

## Безопасность клиента

- Ключи устройства — в аппаратном хранилище: Android Keystore, iOS/macOS Keychain (Secure Enclave), Windows TPM/DPAPI,
  Linux Secret Service или файл с правами пользователя.
- Проверка идентичности ноды по закреплённому ключу (pinning), полученному при регистрации.
- Ключ администратора не хранится на устройствах с ролью пользователя.
- Никаких секретов в логах; экспорт логов для поддержки — с вычищенными секретами.

## Ограничения, которые клиент накладывает на сервер

| Ограничение | Что значит для сервера |
|---|---|
| Память Network Extension на iOS ограничена (порядка десятков МБ) | Ядра для iOS выбираются по потреблению памяти; профиль должен работать с одним ядром в процессе. |
| Мобильный IP меняется | SPA-доступы с коротким TTL и быстрым повтором; соединения переживают смену IP там, где протокол это позволяет (QUIC). |
| Сторонние клиенты не умеют knock/SPA | Профиль public для части сервисов (см. 02-security-model). |
| Встраивание движков в клиент | Лицензии движков (GPL-3.0, MPL-2.0, PolyForm) определяют лицензию клиента; вопрос M-2 в 07-questions. |
| Совместимость версий протоколов | API отдаёт версию движка и протокола в профиле; клиент отказывается от несовместимых профилей. |

## Что сервер должен предоставить клиенту (API)

- Регистрация устройства (enrollment) и выдача сертификата.
- Подписанный список профилей подключения с приоритетами, версиями и требованиями (gated, класс входа, платформы).
- Ротация своих учётных данных пользователем.
- Проверка состояния ноды без раскрытия лишнего (для автоматического переключения).
- Все административные операции — под областью доступа `admin`.
- Стабильное версионирование API: клиент старой версии продолжает работать с новой нодой.

## Варианты стека (для решения в следующей фазе)

- Ядро клиента на Go (как `rayknock` и большинство движков), встраивание через gomobile и c-shared — так сделаны olcRTC и OpenFlux.
- Интерфейс: Kotlin Multiplatform / Compose Multiplatform, Flutter или Tauri.
