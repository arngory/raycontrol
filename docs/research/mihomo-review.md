# mihomo: что взять для маршрутизации на клиенте и на ноде

Статус: исследование на 2026-11-14. Прочитан код mihomo, ветка `Alpha`, коммит `184857ce21a3e4ef48c6829265c00aedfd87792b`
(2026-11-14 23:28 +0800), и вики https://wiki.metacubex.one/. Для сравнения — форк ядра клиента `arngory/sing-box`
(`34eaa8c`, версия `1.14.4-neko-1`) и код Niko (`bb322e1`, только чтение). Из наших документов — 04, 08, 15, 17, 18,
спеки подписки, политики выхода, замера канала, relay, LAN, пределов соединений и трафика, `handoff/`.
**Ничего не запускалось**: ни mihomo, ни замеров. Ссылки `путь:строка` без префикса — код mihomo этого коммита;
`sing-box:` — форк ядра; `niko:` — `app/src/main/java/io/niko/` клиента. «Вики» — прочитано только в документации.
Размеры — как в [18](platforms-and-hosts.md): S — до двух дней, M — около недели, L — две–четыре недели.

Решения владельца от 2026-11-14 — в конце §10.

Одна поправка к вводным. Маршрутизация в Niko уже не «всё через профиль и пара обходов»: в нём правила пользователя
с наборами правил (`.srs`), пресет для России, правила по приложениям, группы selector и urltest, FakeIP и сниффинг
(§3.1). Поэтому почти всё, что mihomo умеет на клиенте, у нас уже есть в другом виде.

## 1. Итог в одной странице

| № | Что | Где | Размер | Подписка |
|---|---|---|---|---|
| 1 | Наборы правил через ноду: нода держит копии тех `.srs`, что Niko сейчас качает с GitHub, и пишет их SHA-256 в подписку; клиент берёт файлы с порта подписки | оба | M (нода S–M, клиент S) | да: новое необязательное поле |
| 2 | Выходы ноды: второй хоп (WARP, вышестоящий прокси, другой адрес ноды) для класса назначений — по IP в ядре, по имени в процессах | нода | L | нет |
| 3 | Выход на пользователя: администратор назначает пользователю выход из п. 2; при нескольких адресах ноды — закреп пользователя за адресом | нода | M после п. 2 | нет (необязательно — строка для показа) |
| 4 | Одна DNS-политика ноды: все процессы data plane резолвят через `rayd`, кеш общий, имена класса п. 2 — через его выход | нода | M | нет |
| 5 | Watchdog просыпается от отказов соединений в ядре, а не только по таймеру раз в 10 минут | клиент | S | нет |
| 6 | Блокировка по наборам правил на ноде (реклама, вредоносное), выключена по умолчанию | нода | S–M после п. 1 и 4 | нет |
| 7 | Живые соединения пользователя в API: список, байты, закрыть — для администратора с телефона | нода и Niko | M | нет, меняется `api-v1` |
| 8 | Замер цены TCP keepalive на Android: mihomo там его выключает, sing-box шлёт раз в 5 минут | клиент | S | нет |

Главный вывод: брать из mihomo код не нужно. Полезны три идеи модели — «набор правил как файл, который приносит
источник» (п. 1), «пользователь и назначение → выход» (п. 2–3), «у каждого резолвера своя дорога» (п. 4). Остальное
на клиенте у sing-box есть, часто новее (§9).

## 2. Как устроен mihomo — коротко, что нужно дальше

- **Правила** идут списком сверху вниз до первого совпадения (`tunnel/tunnel.go:654-711`). Типы — `rules/parser.go:12-104`:
  DOMAIN, -SUFFIX, -KEYWORD, -REGEX, -WILDCARD, GEOSITE, GEOIP, IP-ASN, IP-CIDR, IP-SUFFIX, SRC-* и DST-PORT, IN-PORT,
  DSCP, PROCESS-* (имя, путь, regex, wildcard), NETWORK, UID, IN-TYPE, IN-USER, IN-NAME, REMATCH-NAME, SUB-RULE, AND,
  OR, NOT, RULE-SET, MATCH.
- **Неявный резолв.** IP-правило без `no-resolve` само резолвит имя назначения через DNS клиента
  (`rules/common/ipcidr.go:38-40`, `geoip.go:35-37`, помощник — `tunnel/tunnel.go:336-350`). Резолв один на
  соединение, но он есть и у соединений, которые потом уйдут в прокси.
- **Pass и Rematch.** Особые «исходящие»: Pass продолжает список правил дальше, Rematch меняет метку и набор подправил и
  проходит правила заново, с защитой от цикла (`tunnel/tunnel.go:670-700`, `adapter/outbound/rematch.go:10-56`).
  SUB-RULE — именованные списки правил; listener может начать с такого списка (`tunnel/tunnel.go:713-721`).
- **Наборы правил** (`rule-providers`): поведение `domain`, `ipcidr` или `classical`, формат `yaml`, `text` или
  `mrs` (вики, https://wiki.metacubex.one/en/config/rule-providers/).
  - `domain` — сжатое префиксное дерево (succinct, из openacid/succinct; `component/trie/domain_set.go:1-5`), проверка
    одним проходом по имени (`rules/provider/domain_strategy.go:26-28`).
  - `ipcidr` — отсортированные слитые диапазоны (`component/cidr/ipcidr_set.go:11-14`, слияние —
    `rules/provider/ipcidr_strategy.go:54-56`).
  - `classical` — обычный список правил, проверяется по одному (`rules/provider/classical_strategy.go:22-30`):
    большой classical-набор стоит как столько же правил подряд.
  - `mrs` — заголовок `MRS\x01`, поведение, число, затем готовое дерево или диапазоны, всё под zstd
    (`rules/provider/mrs_reader.go:13-70`). Только для `domain` и `ipcidr`: `FromMrs` есть лишь у них
    (`domain_strategy.go:57`, `ipcidr_strategy.go:58`).
  - Обновление: по интервалу, файл пишется, если изменился хеш; ETag по выбору (`component/resource/fetcher.go:116-160`,
    `vehicle.go:127`). Встроенный `payload` служит запасом, пока файла нет (`rules/provider/provider.go:139-141`).
    Подписи или пина нет: источник — любой HTTPS.
- **Горячая перезагрузка** конфига без перезапуска процесса (`hub/executor/executor.go:84-123`). Пока она идёт,
  туннель в состоянии «suspend», и новые соединения закрываются сразу (`tunnel/tunnel.go:270-273`, `503-506`).
- **Группы** (`adapter/outboundgroup/`, далее файлы этого каталога; `parser.go:26-45`, `188-218`): `select`, `url-test`, `fallback`, `load-balance`;
  `relay` удалён в пользу `dialer-proxy` у исходящего (`parser.go:216-217`, `adapter/outbound/base.go:199`).
  - Проверка — запрос HEAD через исходящий; задержка — от dial до ответа. `unified-delay` делает второй запрос по тому же
    соединению и берёт его время (`adapter/adapter.go:166-282`). `expected-status` — какие коды считаются успехом.
  - `lazy` (по умолчанию включён, `parser.go:52`): плановая проверка пропускается, если группой не пользовались весь
    интервал (`adapter/provider/healthcheck.go:44-60`).
  - **Пассивная проверка.** Отказ dial через группу считается; 5 отказов за 5 секунд (умолчания `groupbase.go:96-99`)
    или «connection refused» сразу запускают проверку всей группы (`groupbase.go:265-300`).
  - `url-test` держит текущий, пока он жив и не хуже лучшего больше чем на `tolerance` (`urltest.go:103-149`).
    `fallback` — первый живой по порядку (`fallback.go:105-124`).
  - `load-balance`: `consistent-hashing` (ключ — eTLD+1 назначения, jump hash), `round-robin`, `sticky-sessions`
    (источник + назначение, LRU на 10 минут) (`loadbalance.go:43-60`, `196-250`). Ключ `hash-key: in-user` закрепляет
    по пользователю входа (`loadbalance.go:76-107`).
- **TUN** — та же библиотека sing-tun, что у sing-box (свой форк `metacubex/sing-tun`), с теми же опциями: стеки,
  `auto-route`, `auto-redirect`, `strict-route`, `route-address(-set)`, исключения, UID, пакеты Android, MAC,
  endpoint-independent NAT, GSO (`listener/inbound/tun.go:15-71`). Новое — свой стек `mips`; он стоит по умолчанию
  (`config/config.go:548`, `docs/config.yaml:131-196`). Как он себя ведёт, не проверялось.
- **Listener'ы (сервер)**: десятки протоколов с пользователями, у каждого `rule` (начальный SUB-RULE), `proxy`
  (сразу в этот исходящий) и `routing-mark` (`listener/inbound/base.go:92-121`). Имя пользователя попадает в
  метаданные (`adapter/inbound/addition.go:23-25`, `listener/sing/context.go:31`) и проверяется правилом IN-USER.
  `tunnels` — пересылка порта на адрес через правила (`listener/inbound/tunnel.go:15-16`).
- **Исходящие** знают `interface-name`, `routing-mark`, `ip-version`, `dialer-proxy`, TFO и MPTCP
  (`adapter/outbound/base.go:193-199`). Двойной стек — запас 300 мс до второго семейства, `tcp-concurrent` — все адреса
  разом (`component/dialer/dialer.go:25`, `40-75`).

## 3. Маршрутизация на клиенте

### 3.1. Что в Niko сейчас (по коду, `bb322e1`)

- **Правила пользователя** (`niko:fmt/ConfigBuilder.kt:1010-1165`): домены, адреса, порты, сеть, протокол, источник,
  пакеты приложений; выход — прокси, прямо, блок или другой профиль (`niko:database/RuleEntity.kt:19-27`).
- **Наборы правил** — бинарные `.srs` sing-box. Приложение само качает их по HTTPS через прокси и подкладывает ядру;
  набор, которого ещё нет, не попадает в конфиг, а не роняет старт (`niko:RuleSetFiles.kt:23-37`). Причина записана там
  же: через DNS-туннель список в 500 КБ идёт минуту (`RuleSetFiles.kt:27`). Проверка — только «https»
  (`RuleSetFiles.kt:58`), предел 32 МиБ (`:37`).
- **Пресет «Россия»**: заблокированное — через прокси, российское — прямо, списки runetfreedom (обновляются раз в
  6 часов); прямое правило ждёт, пока скачаны списки заблокированного (`niko:RoutePresets.kt:11-55`).
- **По приложениям** — `VpnService` с разрешёнными или запрещёнными пакетами (`niko:bg/VpnService.kt:132-177`), плюс
  `package_name` в правилах.
- **Группы**: selector или urltest (раз в 3 минуты, допуск 50 мс) для групп профилей
  (`niko:fmt/ConfigBuilder.kt:957-983`).
- **Watchdog** для профилей ноды: тест через профиль через 20 с после старта, через 15 с после смены сети, раз в
  10 минут; два провала — перезапрос подписки, затем вторая учётная запись, затем замер других профилей и переход на
  лучший (`niko:raycontrol/RayWatchdog.kt:18-34`, `RayChannel.kt:637`). Замер — скачивание (успех, время до первого
  байта, скорость, на каком объёме встало) и UDP (потери, RTT); результаты по сетям, `hints` ноды — только начальный
  порядок (`niko:raycontrol/RayChannel.kt:29-31`, `151-153`).
- **DNS**: FakeIP по умолчанию включён, удалённый DNS — DoH ноды, прямой — для прямых доменов, сниффинг включён,
  `resolve` выключен (`niko:database/DataStore.kt:142-162`, `ConfigBuilder.kt:1209-1229`, `1282-1286`, `1330-1344`).

### 3.2. Что из mihomo имеет смысл и как это выглядит у нас

> Дальше: спека [rules-v1](../spec/rules-v1.md) (R4-44, 2026-11-16) — списки по приложениям в `arngory/niko-routes`,
> зеркало на ноде, поле `rules`. Владелец решил дать администратору и правила, которые меняют выход (`enforce`,
> включая `direct`): абзац ниже о том, что нода таких правил не присылает, этим пересмотрен.

**Наборы правил через ноду (п. 1).** У mihomo набор правил — это файл, который приносит «провайдер», с запасом на
время, пока файла нет. У Niko то же самое уже есть, кроме источника: сейчас это GitHub через туннель. Предложение:

- нода держит копии нужных файлов (сначала — четыре списка пресета) и обновляет их сама, как зеркало APK
  ([app-update-v1](../spec/app-update-v1.md));
- подписка несёт новое необязательное поле, например
  `"rules": {"v": 1, "sets": [{"tag": "ru-blocked-domains", "kind": "domain", "sha256": "…", "size": 412345, "path": "/rules/v1/<sha256>.srs", "updated": 1767225600}]}`;
- клиент берёт файл с того же порта и пина, что подписка, сверяет SHA-256 из подписанного payload и только тогда
  подкладывает ядру. Если порт подписки недоступен — как сейчас, по старому URL через прокси.

Что это даёт: файл не идёт минуту через DNS-туннель; GitHub не нужен в сети клиента; файл нельзя подменить — хеш
подписан двумя ключами ноды. В `subscription-v1` это укладывается: v1 заморожена только для несовместимых изменений, а
необязательные поля добавлялись много раз (`name`, `note`, `traffic`, `lan`, `app`, `dnsauth`, `dns_probe` —
[subscription-v1](../spec/subscription-v1.md) §3). Сами файлы в подписку не кладутся: сотни килобайт и срок жизни
ответа 72 часа.

Что остаётся выбором пользователя: включать ли пресет вообще; что идёт прямо, а что через прокси; порядок правил и свои
правила выше пресета. Нода только поставляет списки. Правил, которые сами меняют выход, нода не присылает: иначе
подписанный ответ ноды начинает решать, что идёт мимо туннеля, и ошибка или злой администратор ноды тихо выводит
трафик пользователя в открытую сеть. Можно добавить подсказку `"preset": "ru"` (нода знает страну клиента по AS из
`hints`), но включает пресет только пользователь, по кнопке.

Формат — `.srs` sing-box, не `mrs`: ядро клиента его читает, а `mrs` умеет только домены и адреса (§2) и в sing-box не
читается. Структуры данных внутри одинаковые: у sing-box тот же succinct из openacid
(`sagernet/sing` v0.9.7, `common/domain/set.go:11`, сжатие zlib — `sing-box:common/srs/binary.go:23`, `71`).

**Watchdog против групп с проверками (п. 5).** Сравнение:

| | mihomo `url-test`/`fallback` | sing-box `urltest` | Watchdog Niko |
|---|---|---|---|
| Что меряет | HEAD, время до ответа | тест URL, задержка | скачивание: первый байт, скорость, где встало; UDP |
| Когда | по интервалу, ленивая; после 5 отказов за 5 с | по интервалу; после смены интерфейса (`sing-box:protocol/group/urltest.go:151-167`) | 20 с после старта, 15 с после смены сети, раз в 10 мин |
| Отказ соединения | считается, запускает проверку (`adapter/outboundgroup/groupbase.go:265-300`) | удаляет историю этого исходящего (`sing-box:protocol/group/urltest.go:190-191`) | не видит |
| Выбор | самый быстрый с допуском / первый живой | самый быстрый с допуском, TCP и UDP отдельно (`sing-box:protocol/group/urltest.go:310-352`) | рабочий в этой сети по своим замерам и `hints`, с подпиской и `next` |

Watchdog сильнее там, где важно нам: «быстрый по RTT» и «работает под DPI» — разные вещи. Профиль, который отвечает
на HEAD за 80 мс и встаёт после 16 КБ, url-test выберет первым; замер Niko его отбракует. Слабее он в одном: между
проверками пройти может до 10 минут, а поломку раньше всех видят сами соединения. Взять у mihomo только пассивный
счёт: ядро считает отказы dial и сбросы до первого ответа через профиль ноды; N отказов за T секунд — внеочередной
тест watchdog. В sing-box это место — `URLTest.DialContext` и исходящие профилей; Niko и сейчас строит свой
конфиг, ядро — свой форк. Значения N и T — по полевым данным, не из mihomo.

**По приложениям, сниффинг, TUN** — брать нечего. Пакеты и UID на Android у обоих ядер идут через одну и ту же
sing-tun и `VpnService`; сниффинг TLS, HTTP и QUIC есть у обоих. У mihomo одна удобная мелочь: адрес, на котором
сниффинг не удался больше 5 раз, 10 минут не сниффится (`component/sniffer/dispatcher.go:141`, `329`), — это экономит
до секунды ожидания первого байта (`dispatcher.go:224-227`) на протоколах, где первым говорит сервер. В sing-box у
`sniff` есть `timeout`; если появятся жалобы на задержку SMTP или IMAP через Niko — смотреть сюда.

## 4. Маршрутизация на ноде

### 4.1. Что есть сейчас

- Выход пользователей — только из процессов с UID 9100–9179; частные сети и сама нода закрыты; политика выхода
  (BitTorrent, SMTP) — в ядре, одна на ноду, потому что ядро не знает пользователя
  ([egress-policy-v1](../spec/egress-policy-v1.md) §1, §2).
- Xray (`inner`, REALITY) умеет правила по пользователю (`xray:app/router/condition.go:158`) и исходящие с меткой
  или интерфейсом (`xray:infra/conf/transport_sockopt.go:46`, `60`). Сейчас из них используется запрет частных сетей.
- Hysteria2 в niko-server соединяется сам, мимо маршрутизатора sing-box (egress-policy-v1 §4). naive — свой код в
  `rayd`.
- Резолверов три: Xray — DoH 1.1.1.1 и 9.9.9.9, naive — публичные, Hysteria2 и Yggdrasil — `/etc/resolv.conf`
  ([traffic](../design/traffic.md) §3).

### 4.2. Что предлагает серверная сторона mihomo

Модель у mihomo простая и полная: вход знает пользователя → правила видят IN-USER, IN-NAME, назначение → выход —
исходящий с интерфейсом, меткой, семейством адресов или цепочкой через другой прокси (§2). Пользователя можно закрепить
за одним из нескольких выходов хешем (`hash-key: in-user`).

Лучше того, что у нас есть, сам код ничем не стал бы: протоколы у нас уже обслуживают Xray, niko-server и `rayd`, у
каждого свои пределы, счёт трафика и разрыв соединений при отзыве. mihomo был бы четвёртым процессом с теми же
задачами. Берём модель, не код.

### 4.3. Выходы ноды (п. 2 и 3), как это выглядело бы у нас

Выход — именованный путь в интернет: `direct` (как сейчас); `wg:<имя>` (WireGuard-интерфейс на ноде, например WARP);
`socks:<адрес>` или `http:<адрес>` (вышестоящий прокси); `addr:<адрес>` (другой IPv4 или IPv6 самой ноды).

Решать, куда идёт соединение, можно в двух местах, как и в политике выхода:

1. **По адресу назначения — в ядре, для всех профилей сразу.** Набор `ipcidr` (из `.srs` п. 1 или свой) становится
   набором nftables. Цепочка `type route hook output` для UID data plane ставит метку по набору; правило `ip rule
   fwmark` уводит помеченное в таблицу маршрутов выхода. В цепочке типа route смена метки ведёт к повторному выбору
   маршрута (документация nftables; здесь не проверялось). Тот же приём у обоих ядер клиента —
   `route-address-set` (`docs/config.yaml:154-159`) и `route_address_set` в sing-box. Процессы не меняются, как не
   менялись для egress-policy-v1.
2. **По имени и по пользователю — в процессах.** Ядро не знает ни пользователя, ни имени. Значит:
   - Xray — правило `user`/`domain` → исходящий `freedom` с `sockopt.mark` (умеет уже);
   - naive (`rayd`) — имя из CONNECT и пользователь известны, метка на сокет dial — правка в нашем коде;
   - Hysteria2 — метка на dial в niko-server, новое поле конфига, по правилу закрепления версий (сначала релиз
     niko-server, потом поле, egress-policy-v1 §4).
   Метку дальше разводит то же `ip rule`, что и в п. 1: выбор пути один, в ядре.

Пользователь → выход (п. 3) — решение администратора: `rayctl user egress NAME <выход>`. Закреп хешем, как
`hash-key: in-user` у mihomo, нужен только когда у одного выхода несколько адресов: пользователь получает
постоянный адрес выхода (сайты, которые следят за адресом сессии, не разлогинивают), а пользователи
распределяются по адресам.

Что не меняется: запрет частных сетей и `to_node` действуют и на пути через WARP (те же UID и юниты); политика выхода
остаётся цепочкой `egress`; пределы соединений и счёт трафика — в процессах и не зависят от выхода. Что надо
продумать: что делать, когда выход упал (переходить на `direct` или отказывать — это решение владельца, вопрос 4);
DNS для выхода (§5.3); куда ставить WireGuard-клиент (это ещё один процесс data plane со своим UID).

Выход в стране пользователя — не здесь, а на relay: [relay-entry-v1](../spec/relay-entry-v1.md) (R4-45, 2026-11-16).
Выход `relay:<имя>`, которым решала бы нода, не нужен: путь выбирает клиент, relay выпускает только внутреннее.

**Блокировка по наборам правил (п. 6)** ложится туда же: IP-наборы — `reject` в цепочке `egress`, доменные — правило
в процессах или ответ `NXDOMAIN` в DNS ноды (§5.3). Выключено по умолчанию, как всё новое.

## 5. DNS

### 5.1. Как у mihomo

- Режимы `fake-ip` и `redir-host` (в коде — mapping: настоящий ответ, но адрес запоминается за именем до конца TTL;
  `dns/middleware.go:99-141`, FakeIP — `:149-190`). Фильтр FakeIP — список имён, белый или чёрный, или правила с ответом
  `fake-ip`/`real-ip` (`component/fakeip/skipper.go:19-35`). Пул FakeIP можно хранить между запусками
  (`store-fake-ip`, `config/config.go:365`).
- Резолверы: `nameserver`, `nameserver-policy` по имени или набору правил, `fallback` с `fallback-filter`
  (ответ основного с адресом не той страны — берётся ответ запасного; `dns/resolver.go:299-343`),
  `proxy-server-nameserver` — для имён самих серверов, `direct-nameserver` — для прямых соединений
  (`dns/resolver.go:526-636`).
- У каждого резолвера может быть своя дорога: `…#ИмяПрокси` в адресе (`config/config.go:1213-1223`) или
  `respect-rules` — соединения к резолверам идут по правилам; тогда обязателен `proxy-server-nameserver`
  (`config/config.go:1421-1422`). ECS — параметр `ecs` у резолвера (`dns/util.go:260-274`). Схемы — UDP, TCP, DoT,
  DoH (с HTTP/3), DoQ, системный (`config/config.go:1226-1262`).
- Правила видят имя из сниффинга отдельно от имени из DNS: `SniffHost` идёт в правила, а назначение заменяется только
  с `override-destination` (`component/sniffer/dispatcher.go:169-180`, `constant/metadata.go:270-276`).

### 5.2. Утечки и что из этого нужно Niko

- **Неявный резолв — источник утечки у mihomo.** IP-правило резолвит имя через DNS клиента и для соединения, которое
  уйдёт в прокси (§2). Без `no-resolve` в правиле или `respect-rules` имя видит DNS провайдера. В sing-box, на котором
  стоит Niko, резолв делает только явное действие `resolve` (`sing-box:docs/configuration/route/rule_action.md:305-320`),
  а в Niko оно по умолчанию выключено. Здесь sing-box лучше, менять нечего.
- **Fallback и fallback-filter** в sing-box 1.14 покрывает общее средство: действие `evaluate` и правила по ответу
  (`match_response`), плюс `race` (`sing-box:docs/configuration/dns/rule_action.md:5-14`, `147-172`). Per-domain
  резолверы и ECS у sing-box тоже есть (`dns/rule_action.md:79`, `131`).
- **FakeIP с DoH ноды** — правильная схема для телефона: имена прокси-трафика не резолвятся на устройстве вовсе, их
  резолвит нода; DoH ноды нужен только самому устройству и прямым именам. У mihomo это та же схема, без выигрыша.
- Что остаётся открытым и не связано с mihomo: IP-списки пресета (`geoip-ru`) при FakeIP и выключенном `resolve`
  совпадают только с соединениями на голый адрес. Это поведение sing-box; решение (оставить или резолвить
  прямые имена через DoH ноды) — за клиентом.

Итог по DNS для клиента: брать из mihomo нечего.

### 5.3. DNS-политика ноды (п. 4)

Идея mihomo, которая полезна именно на ноде, — «у каждого резолвера своя дорога». Сейчас у ноды три разных резолвера
(§4.1), и Hysteria2 с пирами Yggdrasil зависят от `/etc/resolv.conf` хоста. Предложение:

- `rayd` поднимает резолвер для data plane (сокет unix или loopback только для UID 9100–9179) с общим кешем;
- по умолчанию — DoH к тем же 1.1.1.1 и 9.9.9.9; ECS не шлётся;
- имена класса выхода п. 2 резолвятся через этот выход: CDN отвечает адресом рядом с выходом, а не с нодой
  (`nameserver-policy` + `#прокси` у mihomo);
- блок-лист п. 6 — ответ `NXDOMAIN` или пустой;
- Xray, naive и niko-server получают этот адрес в конфиге.

Цена: `rayd` становится частью пути каждого соединения по имени. Нужны запасной путь (процесс резолвит сам, если
сокет молчит) и предел очередей. Плюс: одно место для счётчиков DNS и для `rayctl check`.

## 6. Другие находки

- **Сервер VLESS encryption (ML-KEM-768) есть в mihomo** (`listener/inbound/vless.go:15`,
  `transport/vless/encryption/server.go`). R1-2 говорит «вернуться, если появится» — появилось, но в mihomo, не в
  sing-box. Менять `inner` с Xray на что-то ещё сейчас незачем: Xray уже форк с правками отзыва и пределов.
- **Горячая перезагрузка** у mihomo закрывает новые соединения на время применения (§2). У нас `rayd` и так меняет
  пользователей без перезапуска (API Xray, файлы niko-server и naive) — подход лучше. Niko перезапускает ядро; это
  его выбор, mihomo тут не образец.
- **Живые соединения** (п. 7): у mihomo `/connections` — список с правилом, цепочкой, байтами и закрытие по ID
  (`hub/route/connections.go:18-20`, `tunnel/statistic/tracker.go:24-34`). У Niko тот же Clash API из sing-box. На
  ноде такого нет: есть счётчики (`rayctl metrics`) и пределы. Список «соединения пользователя, кто, куда, сколько,
  закрыть» помог бы администратору с телефона при жалобе. Данные есть у каждого процесса, сборка — в `rayd`. Нарушает
  ли это D-12 («access-логи выключены»), решает владелец: это не журнал, а снимок в памяти, но адреса назначения
  администратор увидит.
- **TCP keepalive на Android** mihomo выключает принудительно (`component/keepalive/tcp_keepalive.go:33-39`);
  sing-box шлёт первый через 5 минут, дальше раз в 75 с (`sing-box:constant/timeout.go:6-7`). Причина у mihomo в коде не
  написана; обычно это расход батареи на пробуждение радио. Не брать вслепую: без keepalive мёртвое соединение к ноде
  живёт до тайм-аута приложения. Замерить (п. 8).
- **IP-ASN** — правило по номеру AS из mmdb (`rules/parser.go:35-39`). В sing-box такого нет. Для ноды это способ
  задать класс выхода «вся сеть такого-то CDN» без ручных списков; источник ASN уже выбран в
  [asn-sources](asn-sources.md). Позже, если п. 2 будет.
- **Пакет наборов `BundleMRS.7z`** — все списки одним архивом, из которого провайдер берёт файл, пока не скачал свой
  (вики, rule-providers). Для п. 1 то же самое даёт хеш в подписке; архив не нужен.
- **Двойной стек и `tcp-concurrent`** — запас 300 мс (`component/dialer/dialer.go:25`); у sing-box то же
  (`fallback_delay`, `sing-box:option/outbound.go:108`). Разницы нет.
- **smux с Brutal, ECH, NTP, `store-selected`, `store-fake-ip`** — есть у обоих ядер. naive у нас ECH не может по
  причине фронта ([naive-default](naive-default.md) §2.1), mihomo это не меняет.
- **geodata**: mihomo держит `.dat` и mmdb, загрузчик по умолчанию — «memconservative»
  (`component/geodata/utils.go:15`). sing-box geosite и geoip убрал в 1.12 в пользу наборов правил
  (`sing-box:docs/configuration/route/geoip.md:5-7`). Для нас наборы правил лучше: файл на список, а не база на всё.
- **Тесты** mihomo: интеграционные через Docker (`test/`) и юнит-тесты разборщиков. Нового для нас нет.

## 7. Чего брать не стоит

1. **Полный язык правил на телефоне** (YAML с AND/OR/NOT, SUB-RULE, Rematch, Pass). Niko уже даёт правила с
   наборами, пакетами и выходом — это покрывает раздельное туннелирование из [06](client-requirements.md). Каждое
   новое средство — ещё один способ тихо пустить трафик мимо туннеля; ошибку пользователь не видит, а нода её
   проверить не может. Поддержка «почему сайт не открывается» растёт быстрее пользы.
2. **mihomo как ядро** клиента или ноды, или его listener'ы на ноде. Клиент: форк sing-box уже несёт наши протоколы
   (dnstt, masterdns, Yggdrasil, naive через cronet); переезд — всё заново ради того, что у sing-box есть. Нода:
   четвёртый процесс с теми же протоколами, без наших пределов, счёта и разрыва по отзыву.
3. **Группы `url-test`/`fallback`/`load-balance` вместо watchdog.** Они меряют задержку, а нам нужна работа под DPI
   (§3.2). Балансировка по профилям одной ноды ничего не даёт: узкое место одно — путь до ноды.
4. **Неявный резолв для IP-правил и модель `fallback-filter`.** Первое — утечка (§5.2); второе в sing-box 1.14 есть в
   общем виде.
5. **Формат `mrs` и `.dat`.** Клиент читает `.srs`; `mrs` уже по возможностям. Два формата для одних списков — лишняя
   работа для зеркала п. 1.
6. **Нода, которая ставит правила за пользователя.** Даже подписанная подписка не должна сама менять, что идёт прямо
   (§3.2). Нода приносит списки, решает пользователь. *Пересмотрено владельцем 2026-11-16 (R4-44,
   [rules-v1](../spec/rules-v1.md) §6): у администратора есть и `direct`, цена сказана прямо.*
7. **Свой стек `mips`.** Новый, по умолчанию у mihomo, его поведения никто у нас не мерил; у Niko — gVisor, system или
   mixed sing-tun, проблем с ними в `handoff/` нет.

## 9. mihomo и sing-box: где есть разница

Прежний вывод «большой разницы нет» в целом верен. Где он не верен — в таблице.

| Область | Разница | Комментарий |
|---|---|---|
| Порядок и цена правил | нет | у обоих список сверху вниз до первого совпадения |
| Типы правил | есть, нам не важна | у mihomo IP-ASN, DSCP, wildcard, SUB-RULE, Pass/Rematch, IN-PORT; у sing-box Wi-Fi SSID, тип сети, правила по ответу DNS, `preferred_by`, AdGuard. Niko пользуется общей частью |
| Наборы правил: структура | нет | одно и то же дерево succinct; IP — диапазоны |
| Наборы правил: формат | есть, в пользу sing-box | `.srs` — любые headless-правила; `mrs` — только домены и адреса; classical у mihomo — линейный |
| Обновление наборов | нет | интервал, хеш, запасной файл (`initial_path` у sing-box 1.14) |
| Группы | есть, нам не важна | у sing-box только selector и urltest (`sing-box:constant/proxy.go:52-53`); fallback и load-balance заменяет watchdog |
| Пассивная проверка группы | небольшая | mihomo считает отказы и запускает проверку; sing-box стирает историю исходящего. Берём идею в watchdog (п. 5) |
| Неявный резолв | есть, в пользу sing-box | у sing-box только явный `resolve` |
| DNS | есть, в пользу sing-box 1.14 | `evaluate`, `match_response`, `race` шире, чем `fallback-filter`; политики по имени и ECS — у обоих |
| FakeIP и его сохранение | нет | у обоих |
| Сниффинг | нет | TLS, HTTP, QUIC у обоих; у mihomo кеш неудачных адресов |
| TUN, по приложениям, `auto-redirect` | нет | одна библиотека sing-tun; у mihomo ещё стек `mips` |
| Сервер, пользователи, правило по пользователю | нет | IN-USER у mihomo, `auth_user` у sing-box |
| Исходящие: интерфейс, метка, цепочка | нет | `interface-name`/`routing-mark`/`dialer-proxy` и `bind_interface`/`routing_mark`/`detour` |
| API соединений | нет | Clash API у обоих |
| Перезагрузка без перезапуска | есть | у mihomo в процессе, но с паузой для новых соединений; Niko перезапускает ядро |
| TCP keepalive на Android | есть | mihomo выключает, sing-box — 5 мин и 75 с; замерить (п. 8) |
| VLESS encryption, сервер | есть | у mihomo есть, у sing-box нет; нам не нужен (`inner` на Xray) |

## 10. Вопросы владельцу

1. Наборы правил через ноду (п. 1) — делаем?

10. Пассивный триггер watchdog (п. 5) и замер keepalive (п. 8) — передать клиенту как предложения?

### Решения владельца (2026-11-14)

1. **Наборы правил через ноду — делаем** (п. 1 таблицы). Какие списки нода держит и отдаёт, выбирает администратор
   ноды; пресет «Россия» — один из вариантов, не единственный. Ответ на вопросы 1 и 2.
2. **Выходы ноды — делаем** (п. 2). Минимум — вышестоящий прокси по HTTP и SOCKS5; остальные виды (WARP, второй адрес
   ноды) — по итогам изучения. Ответ на вопрос 4.
3. **Выход недоступен — отказывать**, на `direct` не переводить. Ответ на вопрос 5.
4. **Блокировка рекламы и вредоносного на ноде — по желанию администратора** (п. 6), выключена по умолчанию. Ответ на
   вопрос 8.
5. **Список живых соединений для администратора — по желанию администратора** (п. 7), выключен по умолчанию. До

6. **Остальные кандидаты** (п. 3, 4, 5, 8) — изучаем, что и как можно сделать; решений по ним пока нет. Вопросы 3, 6,
   7 и 10 остаются открытыми до этого изучения; клиентские пункты (5, 8 и клиентская часть п. 1 и 7) переданы сессии
