# raycontrol → Niko: серверная часть R2/R3 и что нужно от клиента

Заметка для сессии клиента Niko, после [niko-r4-note.md](niko-r4-note.md). Сессия Niko отдала серверную часть R2
и R3 сюда, потому что фронт niko-server на 443 отложен. Ниже — что сделано на сервере, в каком виде это приходит
клиенту и что нужно от клиента. Формат подписки v1 и пакет `rcdev1` **совместимы**: добавились только профили и
необязательные поля.

## 1. Что работает на сервере сейчас

Пока нет фронта niko-server, протоколы работают на движках, которые уже есть на ноде. Для клиента ссылки от этого не
зависят. Таблица «сейчас / с фронтом» — в [08-decisions.md](../08-decisions.md), раздел «Решения R3».

| Протокол | Где | Решение |
|---|---|---|
| REALITY + Vision (ML-DSA-65, VLESS ML-KEM-768) | Xray, TCP 443 | R2a, R4-7 |
| Hysteria2 `hy2-masq` | Xray, UDP 443, сертификат сайта, masquerade — пустой `404` | R3-1 |
| Hysteria2 `hy2-obfs` | Xray, свой UDP-порт, salamander, самоподписанный сертификат с пином | R3-1 |
| DoH | `rayd`, TCP 443 через сайт | R3-2 |
| naive (h2) | `rayd naive`, TCP 443 через сайт | R2-14 |
| Удалённый API, регистрация по приглашению | `rayd`, свой TCP-порт за SPA, mTLS | R3-3 |

TCP 443 общий у REALITY, DoH и naive. REALITY отдаёт сайту всё, что не его клиент, а сайт по SNI передаёт имена DoH и
naive, не расшифровывая, в их сокеты (R2-13). Всё за SPA. Для всех TLS — только `X25519MLKEM768`.

## 2. Профили в подписке

Форматы — в [spec/subscription-v1.md](../spec/subscription-v1.md) §4. У всех пароль или токен — учётные данные
пользователя с ротацией: новый приходит в `next` за 3 дня, старый работает ещё 2 дня после `from` (R4-1).

```
hysteria2://<пароль>@<host>:443/?sni=<имя>&insecure=0&niko-node=…&niko-svc=…#hy2-masq
hysteria2://<пароль>@<host>:<порт>/?sni=<hex>.invalid&insecure=0&obfs=salamander&obfs-password=…
  &niko-pin=<SPKI SHA-256, base64url>&pinSHA256=<hex>&niko-node=…&niko-svc=…#hy2-obfs
https://<имя>/dns-query/<токен>?niko-node=…&niko-svc=…#doh
naive+https://niko:<пароль>@<имя>:443?niko-node=…&niko-svc=…#naive
```

Что важно клиенту:

1. **hy2-obfs**: имени нет в DNS, сертификат самоподписанный. Niko пинит ключ по `niko-pin` и не проверяет цепочку.
   `pinSHA256` — для сторонних клиентов.
2. **DoH**: перед запросом отбросить параметры `niko-*`. Запрос — `https://<имя>/dns-query/<токен>`, RFC 8484,
   GET `?dns=` или POST `application/dns-message`, по h2. `<имя>` резолвится на ноду через wildcard; соединяться
   стоит на адрес, для которого прошёл SPA.
3. **naive**: CONNECT по HTTP/2, `Proxy-Authorization: Basic niko:<пароль>`, заголовок `Padding` и паддинг первых
   8 кадров в каждую сторону — как у NaiveProxy. Неверный пароль или запрос без паддинга получают пустой `404`, а не
   `407`: «404 на CONNECT» значит «не авторизован». Обычно это устаревший пароль, и тогда нужно перезапросить
   подписку.
4. **Порты UDP** у `hy2-masq` и `hy2-obfs` ротируются по расписанию: `services[].port_key` в пакете, `spa-v2.md` §11.

## 3. Регистрация устройства по приглашению (новое)

Спецификация — [spec/api-v1.md](../spec/api-v1.md). Коротко:

- Администратор делает `rayctl device invite USER NAME [-role user|admin]` и отдаёт строку `rcinv1:…` или QR
  (около 600 символов). Приглашение одноразовое и живёт сутки, если не задано иное (максимум неделя).
- `rcinv1:` — тот же JSON, что `rcdev1:` (`spa-v2.md` §8), но ключ SPA в нём одноразовый и открывает только порт
  API. Ещё в нём есть `api {port, pin}` и `expires`, а `node_keys` и `sub` нет.
- Клиент:
  1. Создаёт ключ клиентского сертификата (ECDSA P-256, в Keystore) и самоподписанный сертификат.
  2. Проходит SPA ключом приглашения.
  3. Открывает TLS с пином `api.pin` и своим сертификатом.
  4. Вызывает `DeviceService.Register` с HMAC приглашения, привязанным к минуте и к пину своего сертификата.
  5. Получает обычный `rcdev1:` с новым ключом и дальше работает как раньше.
- Любой отказ `Register` — `not_found`. Если отказали свежему приглашению, его мог использовать кто-то другой: стоит
  попросить пользователя сообщить администратору.

Что нужно от клиента:

1. **Импорт `rcinv1:`** (строка, QR, ссылка) рядом с импортом `rcdev1:`.
2. **Регистрация по §4 спецификации.** Эталон — `rayctl remote enroll` в
   [`cmd/rayctl/remote.go`](../../cmd/rayctl/remote.go); на сервере его прогоняет установочный тест на пяти
   системах.
3. **Режим администратора** (если он нужен в Niko): устройству с ролью `admin` доступен весь `NodeService` по mTLS
   (`api/proto/raycontrol/node/v1/node.proto`), кроме `Backup`. Порт API и его пин — в поле `api` пакета.
4. **Смена клиентского ключа**: `DeviceService.RotateCertificate` раз в 90 дней (§6 спецификации).

## 4. Что проверить в CI Niko

Здесь нет клиента NaiveProxy (форк `arngory/naiveproxy` вне доступа этой сессии), поэтому совместимость naive
проверена клиентом на Go с тем же протоколом, что у NaiveProxy и inbound sing-box: CONNECT, `Padding`, 8 кадров.
Просьба — добавить в совместимость Niko:

1. naive-плагин Niko ↔ `rayd naive` за REALITY. Бинарник `rayd` есть в релизе; конфиг рисует `rayctl service add
   naive naive`. Для стенда без ACME подойдёт тест `TestRealitySelfStealWithXray` в
   [`internal/xrayapi/xray_test.go`](../../internal/xrayapi/xray_test.go): он поднимает REALITY, сайт, DoH и naive.
2. Hysteria2 `hy2-obfs` с `niko-pin` против Xray-сервера.
3. Регистрация по `rcinv1:` с устройства.

## 5. Что ещё не сделано и почему

| Пункт | Состояние |
|---|---|
| naive-quic, DoH3 | ждут udpmux: UDP 443 занят `hy2-masq` |
| tcpmux / udpmux, Xray на unix-сокете | за фронтом niko-server; сейчас — REALITY на 443 и маршруты сайта (R2-13) |
| Yggdrasil | бэкенд niko-server (R1-3: линк TLS 1.3 с `X25519MLKEM768`, трафик в `inner`). Может пойти тем же путём, что naive (SNI через сайт), если фронт задержится; вид сервиса `yggdrasil` в базе есть |
| `export` (P-10) | закрыт подпиской v1: формат ссылок задаёт сервер и описывает в `spec/subscription-v1.md` |
| Доступ к API изнутри туннеля (H-2) | не сделан: хватает порта за SPA |
