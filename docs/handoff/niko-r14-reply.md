## 1. Ответы на §14.2

1. **`link` во время замера — можно.**
   - `link` не занимает слот «один замер на устройство». Его можно звать, пока идёт `down`, `up` или открыта сессия
     UDP.
   - Ограничение одно: не чаще раза в 5 с на устройство.
   - В `probe-v1.md` §4.1 это теперь сказано явно.
2. **Своя сессия Hysteria2 — сделано иначе, чем вы предложили, и точнее** (R4-20).
   - Пары (`rate_bps`, `ack_rate`) всех сессий адреса выдают темп чужих сессий за CGNAT. Поэтому нода отдаёт по одной
     только сессии **того же пользователя**, что и устройство, которое спрашивает.
   - Сессию нода знает по паролю Hysteria2, с которым та авторизовалась, а устройство — по `RC1`.
   - Новое поле — `own` в объекте сервиса внутри `hysteria2`:

     ```json
     "own": [{"rtt_us": 52000, "min_rtt_us": 48000, "packets_sent": 9100, "packets_lost": 210,
              "brutal": {"rate_bps": 20000000, "ack_rate": 0.97}}]
     ```

   - `brutal` нет, если клиент не задал темп.
   - Несколько своих сессий бывает, если два устройства одного пользователя стоят за одним адресом или клиент
     переподключился. Их различает `rate_bps`, который вы объявили сами.
   - Суммы по адресу остаются как были.
   - Нужен niko-server v0.7.0 ([#10](https://github.com/arngory/niko-server/pull/10)): он уже закреплён в ветке
     raycontrol и выйдет со следующим релизом. Со старым бэкендом поля нет, остаются суммы.
3. **HTTP.**
   - Эндпоинт объявляет в ALPN `h2` и `http/1.1`.
   - `down` объявляет trailer заранее (`Trailer: Probe-Result`). Поэтому trailer приходит и по h2, и в chunked
     HTTP/1.1 — читайте его в обоих случаях, как и собирались.
   - Через туннель TLS сквозной, всё то же самое.
4. **Через туннель — верно.**
   - Адрес `probe.raycontrol.invalid` на любом порту, 443 подходит.
   - SNI эндпоинт не проверяет, решает пин `sub.pin`. Имя `probe.raycontrol.invalid` в SNI — правильный выбор.
   - Авторизация `RC1` — та же.

## 2. Сводка от клиентов (§14.3): позиция сервера

Предложение принимаем как основу: согласие, отчёт только о текущей сети и только из неё, раз в сутки на сеть, без
идентификаторов, корзины. Правки сервера:

1. **ASN и страну нода определяет по адресу запроса в момент приёма.** Адрес не пишется никуда.
2. **«Раз в сутки на сеть» без хранения устройств.**
   - `X-Raycontrol-Device` нужен для `RC1`.
   - Для `429` нода держит в памяти на текущие сутки UTC набор `HMAC(ключ суток, устройство ‖ ASN)`. Ключ суток
     случайный, в конце суток ключ и набор выбрасываются.
   - С данными устройство не связывается и на диск не попадает.
3. **Лишнее из тела убрать:**
   - `kind` — нода знает вид по `svc`;
   - `mcc_mnc` — подсказка всё равно по ASN адреса запроса, а сочетание MCC/MNC с ASN только сужает группы.
     Если MVNO на чужом ASN окажутся важны, вернём это поле отдельным решением.
4. **Хранение.**
   - Только счётчики по ключу (сутки, ASN, `svc`):
     - `works`, `degraded`, `fails`;
     - корзины `udp` и `mbps`;
     - гистограмма `tcp_stall_kib`.
   - Сырые отчёты не пишутся.
   - Счётчики живут 30 дней, подсказка считается по последним 7.
5. **k-анонимность.** Группа (ASN, `svc`) участвует в подсказке, только если в ней не меньше k отчётов. Предлагаем
   k = 10. Меньше — подсказки для этого ASN нет совсем, как вы и просили.
6. **Отравление.**
   - Лимит — один отчёт на устройство и сеть в сутки.
   - Устройства заводит администратор, поэтому их число у одного пользователя ограничено.
   - `avoid` и `udp_blocked` — только при явном большинстве: доля ≥ 60 % при числе отчётов ≥ k.
7. **Формат ответа** — как у вас: `204`, `429` при повторе. Кроме них: `400` на неизвестную версию или поля вне
   корзин, `404`, если нода сводок не принимает (выключено администратором).

## 3. Подсказка о порядке (§14.4): позиция сервера

- Принимаем ваш вид: необязательное поле подписки `hints`, посчитанное для ASN адреса запроса подписки. Подписка и
  так подписывается на каждый запрос, поэтому разные сети получают разные `hints`, и подпись это покрывает.
- Поля:
  - `order`, `avoid`;
  - `devices` — у нас это число отчётов, различать устройства между сутками нода не умеет;
  - `days`;
  - `udp_blocked` (bool);
  - `tcp_stall_kib` — самый частый порог, если на него пришлась доля ≥ 60 %.
- Вашу политику применения поддерживаем: подсказка — только начальный порядок для сети без своих результатов.
- Малые ноды подсказок почти не увидят: у них мало отчётов на ASN. Это ожидаемо.

## 4. Решения владельца (2026-11-04)

1. **Делаем — как необязательную метрику.**
   - Сводка нужна для понимания статистики, как `rayctl metrics`.
   - Нода принимает отчёты, только если администратор включил приём. Выключено — `404`.
   - Клиент отправляет только с согласия пользователя.
2. **Источник ASN — IPinfo Lite** (R4-21, разбор источников — [11-asn-sources.md](../11-asn-sources.md)).
   - База приходит в релизе raycontrol под его подписью. Лицензия CC BY-SA 4.0, атрибуция в архиве.
   - Оператор может заменить её своей базой MMDB.
   - Запрос к API ipinfo — только если администратор включил его явно, и только по сети адреса (/24 и /48), не по
     самому адресу. Поддержка других API — позже.
   - Скачивание по расписанию на ноде по-прежнему отвергаем (R4-5).
3. **k = 10, хранение 30 дней.**

**Сделано** (raycontrol v0.5.0, когда выйдет): `POST /probe/v1/report` и `hints` по §2–3. Формат — `probe-v1.md`
§6, поле `hints` — `subscription-v1.md` §3. Проверить отправку с ноды можно командой
`rayctl probe -report '{…}' @bundle`. Пока релиза нет, отправку в клиенте держите выключенной; после — включайте
только с согласия пользователя.
