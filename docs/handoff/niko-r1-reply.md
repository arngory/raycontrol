## 2. TCP-носитель SPA: что изменилось против предложения

Нормативный текст — [`spec/spa-v2.md`](../spec/spa-v2.md) §10.

- **На ноде — обычный слушающий сокет в `rayspa`**, а не `synproxy` + NFLOG первого сегмента. Причина: ваш клиент
  режет записи против DPI (anti-dpi.md §2–§3), и пакет SPA тоже может прийти в нескольких сегментах. NFLOG увидел бы
  только первый, сокет собирает весь поток. Снаружи разницы нет: порт слота отвечает на SYN, пока слот активен.
- **Для клиента ничего не меняется**: тот же порт слота, пакет первыми данными, закрыть соединение, ответа не ждать.
  Сервер читает до EOF (не больше `len_max + 1` байт, не дольше 3 с) и сбрасывает соединение.
- **Порядок в клиенте** (§7 спецификации): UDP → повтор UDP → TCP; запоминать носитель для сети.
- **Проверено**: интеграционный тест в network namespace с настоящими nftables, NFLOG и TCP — `internal/perimeter/netns_test.go`
  (UDP-SPA открывает порт сервиса, повтор отклоняется, отзыв устройства закрывает порт, TCP-носитель с разрезанной
  записью открывает порт, мусор отклоняется). Доступ выдаётся примерно за 10 мс после пакета.

## 3. Замечания к CONFIG.md и IPC.md

Ни одно не меняет схему 1; это уточнения перед заморозкой.

1. **Файл пользователей.** raycontrol пишет отдельный `users_file` для каждого бэкенда и кладёт туда учётные данные
   только этого `kind` (минимум прав). Формат ваш не меняется; просьба прямо записать в CONFIG.md, что бэкенд не должен
   рассчитывать на поля других видов.
2. **`check` для машины.** raycontrol вызывает `niko-server check` перед каждым применением и показывает ошибку
   администратору. Нужен стабильный код выхода (0 — ок, 1 — ошибка конфига, 2 — ошибка запуска/окружения) и флаг
   `--json` с массивом `{"path": "tcp.routes[2].backend", "error": "…"}`.
3. **UID.** raycontrol раздаёт UID из диапазона 9100–9199 (решение R1-6): `niko-front` 9100, бэкенды и Xray
   9110–9179. Значения в примерах CONFIG.md попадают в диапазон — можно оставить их как есть.
4. **Окно ACME.** `rayspa` ставит перенаправление `tcp dport 443` → `acme_listen` для адресов, которых нет в allow-наборах,
   только на время выпуска (R2). На стороне фронта всё как в CONFIG.md.
5. **Ротация портов UDP** (anti-dpi.md §5, п. 6). Предлагаем сделать её целиком в `rayspa`: порты слотов сервиса
   перенаправляются nftables на 443 только для авторизованных адресов, conntrack сам возвращает ответы с порта слота.
   niko-server ничего менять не нужно: фронт видит пакет на 443, поле `local` в IPC остаётся корректным. Если согласны —
   берём в R3–R4; клиенту понадобится только вычислять порт сервиса так же, как порт SPA (отдельный ключ расписания).
6. **Окно TCP на фронте** (anti-dpi.md §5, п. 7) — на вашей стороне: флаг в конфиге фронта, например
   `tcp.window_clamp` (байты). raycontrol будет выставлять его из настроек ноды.
7. **Переподключение `fd`/`packet`.** Уточните в IPC.md, что фронт переподключается к бэкенду с задержкой (backoff) и что
   датаграммы, пришедшие пока соединения нет, отбрасываются. raycontrol на это опирается при `SIGHUP`/перезапуске бэкенда.

## 4. Что raycontrol делает в R1 дальше

- генерация конфигов фронта, `dnstt`, `masterdns` и `inner` (Xray) по CONFIG.md;
- учётные данные пользователей по сервисам, аллокатор UID и сокетов;
- systemd-юниты по IPC.md (группы, `RuntimeDirectory`, `LoadCredential=`);
- ключи ноды (Ed25519 + ML-DSA-65), эндпоинт подписки, поле `node_keys` в `rcdev1`;
- установщик и релиз с подписью.

Для интеграционного теста R1 «клиент Niko ↔ нода» нужны бинарники `niko-server front` и `backend` (dnstt, masterdns)
из вашего релиза. Сообщите тег, когда будет.

## 5. Уточнения после реализации R1

raycontrol уже генерирует конфиги по CONFIG.md схемы 1 — код в `internal/render`, примеры в его тестах. Что мы
сделали и что из этого нужно учесть на вашей стороне:

1. **Пути ключей** (изменено после теста установки, решение R2-9). Ключи бэкендов лежат не в
   `/run/credentials/<unit>/`, а в каталоге сервиса: `/run/niko/<сервис>/<файл>`, например `/run/niko/dns/noise.key`
   (`0400`, владелец — пользователь сервиса; копирует systemd перед стартом). Путь задаётся в конфиге бэкенда, niko-server
   менять не нужно; в примерах CONFIG.md стоит показать этот вариант: `LoadCredential=` не работает в контейнерах.
2. **Секции фронта необязательны.** Если маршрутов TCP или UDP нет (в R1 есть только DNS-туннели), raycontrol не пишет
   секции `tcp` и `udp`, и фронт не должен слушать 443. Просьба прямо записать это в CONFIG.md.
3. **MasterDnsVPN — `encryption_method: 5`** (AES-256-GCM). Метод 2 в MasterDnsVPN — ChaCha20 без аутентификации,
   а нода разрешает только AEAD (решение R1-8). В SPEC §3.3 у вас по умолчанию 2 — поменяйте на 5. Ключ — файл
   с 32 hex-символами (как генерирует сам MasterDnsVPN).
4. **Ключ dnstt** — файл с hex закрытого ключа X25519 (64 символа и перевод строки), как `dnstt-server -gen-key`.
   Публичный ключ клиент получает в ссылке (`niko-dns`).
5. **Имена.** Бэкенд, сокет и юнит называются по имени сервиса в raycontrol, а не по виду: сервис `dns` вида
   `dnstt` → `/run/niko/dns/packet.sock`, юнит `niko-dns.service`, пользователь `niko-dns`. Вид — поле `kind`.
6. **Каталоги.** `RuntimeDirectory=niko/<имя>` (0710, группа сервиса) создаёт systemd; сокет внутри создаёт процесс
   с правами 0660 (`UMask=0007` в юните). DNS-бэкенды запускаются с `PrivateNetwork=yes` и только `AF_UNIX`:
   им нужны лишь сокеты фронта и `inner`.
7. **`inner`.** Xray слушает `/run/niko/<inner>/vless.sock` (0660), API — в отдельном каталоге
   `/run/niko/<inner>-api/` (доступ только у `rayd`). Поле `inner` бэкенда — путь `vless.sock`. Проверено
   на Xray из `arngory/xray-core` a4a3dff: конфиг, пользователи через API, трафик через VLESS с ML-KEM-768.
8. **Ссылки DNS-туннелей** для клиента — [`spec/subscription-v1.md`](../spec/subscription-v1.md) §4: VLESS к `inner`
   с `encryption` ML-KEM-768 и параметром `niko-dns`.
9. **Порядок запуска.** Юниты: `niko-inner` → бэкенды → `niko-front`; фронт должен переживать отсутствие бэкенда
   при старте (переподключение, §3 п. 7 выше).

## 6. Ответ на открытые вопросы из `docs/server/README.md` (niko, 337bddf)

1. **`services[].port_key`, `port_base`, `port_range`** — есть в `rcdev1` для сервисов с ротацией UDP-порта
   (сейчас `hy2-masq`, `hy2-obfs`, `naive`, `doh`). Формула — [`spa-v2.md`](../spec/spa-v2.md) §11: та же, что §3,
   с ключом и диапазоном сервиса; длина слота — `spa.slot_len_s` ноды. Нода перенаправляет порты слотов `s−1..s+1`
   на UDP-порт сервиса (443); без SPA-доступа к UDP-порту сервиса пакеты отбрасываются. Проверено на nftables
   в network namespace (`internal/perimeter/netns_test.go`).
2. **Подписка v1 заморожена** вместе с `/sub/v1` (решение R1-17), включая поле `time`. Несовместимые изменения — только
   v2 с новым путём.

## 7. После теста установки на разных системах (R2-1…R2-5)

raycontrol теперь ставится в CI через `bootstrap.sh` на Debian 12/13, Ubuntu 24.04 и Rocky Linux 9/10 с бинарником
`niko-server-v0.1.1` из релиза (проверка по `SHA256SUMS`) и проверяется снаружи как клиент. Что важно для niko-server:

1. **Хосты без IPv6** (`ipv6.disable=1`, бывает у провайдеров): `listen` на `[::]:53` там не открывается
   (`address family not supported by protocol`), и фронт падает целиком. raycontrol на таких хостах пишет только
   `0.0.0.0:53`. Просьба: фронту пропускать адрес, семейство которого ядро не поддерживает, с предупреждением,
   а не завершаться — тогда конфиг остаётся переносимым.
2. **Порядок запуска** держит raycontrol: `rayd` отрисовывает файлы бэкендов до их старта (раньше `rayctl apply` мог
   запустить бэкенд до появления файла credentials). Требование к фронту из §3 п. 7 (переподключение к бэкенду) остаётся.
3. **Файрволы хоста** (firewalld, ufw, `flush ruleset` при перезапуске nftables) — целиком на стороне raycontrol,
   niko-server ничего менять не нужно.
4. **REALITY (R2a) уже в подписке** — формат ссылки: [`spec/subscription-v1.md`](../spec/subscription-v1.md) §4,
   «Профиль REALITY». Клиенту нужны: VLESS + REALITY + Vision, `pqv` (проверка ML-DSA-65 обязательна), второй слой
   VLESS encryption (`encryption`), только `X25519MLKEM768`. Пока у фронта нет tcpmux, Xray с REALITY слушает 443 сам
   (решение R2-7); когда tcpmux появится, raycontrol переведёт его на `proxy-v2`-сокет по CONFIG.md, ссылки не меняются.
   Цель REALITY должна отдавать цепочку сертификатов не короче ~3,5 КБ (решение R2-8) — учтите в своих тестах interop.
5. **Ключи бэкендов** — см. §5 п. 1 (R2-9): `/run/niko/<сервис>/<файл>` вместо `/run/credentials/...`. Тест установки
   в CI теперь поднимает весь data plane (Xray `inner`, dnstt, MasterDnsVPN, фронт) на каждой системе из `niko-server-v0.1.1`.
6. **Сайт и ACME до вашего R2** (решения R2-11, R2-12). Пока у niko-server нет бэкенда `site` и tcpmux, raycontrol сам
   обслуживает сайт-приманку (`rayd site` на `/run/niko/site/tls.sock` — тот же путь, что в SPEC) и выпускает
   сертификаты через HTTP-01 с окном на TCP 80. Когда появятся ваш `site` и окно TLS-ALPN-01 через фронт, raycontrol
   перейдёт на них: содержимое сайта (`root`) и сертификат он уже готовит. Для interop-тестов: цепочка цели REALITY
   должна быть не короче ~3,5 КБ (с ML-DSA-65), поэтому сайт досылает корневой сертификат.
