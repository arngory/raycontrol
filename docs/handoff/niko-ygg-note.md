# raycontrol → Niko: Yggdrasil на ноде (R4-15)

Заметка для сессии клиента Niko после [niko-mux-note.md](niko-mux-note.md). Yggdrasil теперь — бэкенд niko-server
[`v0.4.0`](https://github.com/arngory/niko-server/releases/tag/v0.4.0) за tcpmux. raycontrol отдаёт его в подписке
новым видом профиля. Подписка v1 и её эндпоинт не меняются: добавились вид профиля и параметр `niko-ygg`. Формат —
[`subscription-v1.md`](../spec/subscription-v1.md) §4, «Профиль Yggdrasil».

## 1. Профиль

```
vless://<uuid>@[<адрес ноды в Yggdrasil>]:<порт выхода>?type=raw&encryption=mlkem768x25519plus.native.0rtt.<ключ>
  &niko-node=<node_id>&niko-svc=<id>&niko-ygg=<пир>%3B<seed>#ygg
```

- **`niko-ygg` = `<пир>;<seed>`**:
  - пир — `tls://<имя>:443?key=<ключ ноды, hex>&sni=<имя>`, сама нода (P-14);
  - `<seed>` — закрытый ключ узла клиента: seed ed25519, 64 hex-символа. Endpoint `yggdrasil` форка принимает
    его как `private_key` (`parsePrivateKey` берёт и seed 32 байта, и ключ 64 байта).
- **Адрес и порт VLESS.** Адрес ноды в сети Yggdrasil (`200::/7`) выводится из `key` и совпадает с хостом ссылки.
  Порт выхода случаен для каждой ноды. VLESS идёт с тем же `encryption`, что у DNS-туннелей, — в `inner`.
- **Конфиг ядра.** Endpoint `yggdrasil`:
  - `private_key` = `<seed>`, `peers` = [`<пир>`];
  - `tls_fingerprint` — `chrome`, по умолчанию. ClientHello uTLS Chrome 133 предлагает `X25519MLKEM768`, а нода
    принимает только эту группу.

  Исходящий `vless` на `[<адрес>]:<порт>` с `detour` на этот endpoint. Endpoint и так пускает исходящие только в
  `200::/7`.
- **Что делает нода.**
  - Принимает TLS 1.3 только с `X25519MLKEM768`, сертификат — сайта ноды; Yggdrasil его не проверяет.
  - Пускает линк, если ключ из рукопожатия есть среди пользователей и подпись верна.
  - TCP на порт выхода передаёт в `inner`; на другие порты отвечает сбросом, UDP не принимает.
  - Всё, что не линк Yggdrasil, получает от этого имени пустой `404` (h2 или HTTP/1.1).
- **SPA.** TCP 443, как у REALITY, naive и DoH; `svc` — ID сервиса Yggdrasil.

## 1а. Публичные пиры (R4-18)

Если у ноды включены публичные пиры (`rayctl service set ygg peers=...`, по умолчанию их нет), нода подключается к
ним и становится доступна через общую сеть Yggdrasil. Профиль тогда несёт их повторяемым параметром:

```
...&niko-ygg=<пир>%3B<seed>&niko-ygg-via=tls%3A%2F%2Fygg.example.net%3A443&niko-ygg-via=quic%3A%2F%2F203.0.113.9%3A443#ygg
```

- **Порядок.** Сначала прямой пир из `niko-ygg`, как раньше. Пиры из `niko-ygg-via` — запасной путь, когда прямой
  не подключается: клиент добавляет их в `peers` endpoint и идёт к тому же адресу и порту через mesh. Когда прямой
  снова доступен, лучше вернуться на него: путь короче, и публичные пиры не видят клиента.
- **Что меняется для клиента.**
  - Владельцы публичных пиров видят адрес клиента и то, что он говорит по Yggdrasil.
  - Узел клиента становится виден в сети: принимать входящие нельзя, endpoint только исходящий.
  - Постквант на линке к публичному пиру не гарантирован (его TLS — не нашей ноды). Полезный трафик всё равно
    идёт VLESS с ML-KEM-768 в `inner`, и `encryption` из ссылки подтверждает, что ответила наша нода, а не узел
    по пути.
  - Схемы: `tls`, `quic`, `wss`, `ws`, `tcp` — как их принимает yggdrasil-go; `quic` — только с IP-адресом. `key` в URI пира, если есть, —
    закреплённый ключ этого пира. Для `tls`, `wss` — ClientHello uTLS, как для прямого пира.
- **Если параметра нет** — у ноды публичных пиров нет, путь только прямой.

## 2. Ротация

Ключ клиента выводится из UUID в той же ссылке (с v0.20.1 — ещё и из SPA-ключа устройства: у каждого устройства свой), поэтому он сменяется вместе с UUID `inner` (R4-1).
- `next` профиля несёт новую пару: UUID и seed.
- Нода принимает новую пару с момента публикации, а прежнюю — ещё 2 дня после `from`, как UUID в `inner`.

Ключ ноды и порт выхода не ротируются: они задаются при создании сервиса.

## 3. Проверено на сервере

- Тест niko-server: настоящий узел yggdrasil-go подключается через tcpmux.
  - Через mesh доходит до `inner`.
  - Ключ не из списка линка не получает.
  - Новый пользователь пускается без перезапуска, линк удалённого рвётся.
  - На имени без линка — `404` по h2 и HTTP/1.1; TLS без `X25519MLKEM768` отвергается.
- Тест raycontrol на настоящем niko-server: ключ из ссылки подписки получает в ответ рукопожатие ноды с её ключом
  из `key`, а чужой ключ — ничего.
- Установка на пяти системах: юнит без сети, в группе `inner`; фронт достаёт сокет бэкенда.

Клиентом Niko (endpoint форка с uTLS) профиль на сервере не проверялся. Предлагаем добавить Yggdrasil в
`niko-server-interop.yml`, если в ядре есть `with_yggdrasil`. Схема та же, что для DNS-туннелей:
- Xray `inner`;
- `niko-server backend` вида `yggdrasil` с `exit_ports`;
- фронт с маршрутом `tcp` по имени;
- ядро клиента с endpoint `yggdrasil` и исходящим `vless`.

Пример конфига бэкенда — в `docs/CONFIG.md` niko-server.
