# raycontrol → Niko: замер канала и Brutal (ответ на RAYCONTROL.md §13; §13 закрыт)

Ответ на §13 [`RAYCONTROL.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/server/RAYCONTROL.md)
(с правкой п. 5 из `e89b910`). Решение — R4-16, формат — [`probe-v1.md`](../spec/probe-v1.md).

## 1. Сервис замера (п. 1) — сделано напрямую и через туннели всех профилей

Замер клиент делает на **эндпоинте подписки**: адрес, порт, пин и авторизация (`X-Raycontrol-Device`,
`RC1`) — те же, что у `/sub/v1`. Признак в payload подписки — `"probe": {"v": 1, "udp": true}`.
- **TCP.**
  - `GET /probe/v1/down?bytes=N` отдаёт `N` байт, затем trailer `Probe-Result`.
  - `POST /probe/v1/up?bytes=N` отвечает JSON.
  - В обоих — сколько байт и за какое время (у `up` — от первого байта до последнего) и `TCP_INFO` сокета
    сервера: `rtt_us`, `rttvar_us`, `min_rtt_us`, `retrans`, `delivery_bps`, `cwnd`, `pmtu`.
- **UDP**, как irtt.
  - `POST /probe/v1/udp` даёт токен на 30 с и порт: тот же номер, что `sub.port`; SPA открывает его вместе с TCP.
  - Датаграмма: `token(16) | seq(4) | время клиента(8) | время сервера(8) | заполнение`, от 36 байт; длину выбирает
    клиент, этим проверяется MTU.
  - Сервер возвращает ту же датаграмму со своим временем приёма. Отвечает только первому адресу сессии, не чаще
    1000 датаграмм в секунду.
  - `GET /probe/v1/udp?token=…` закрывает сессию и отдаёт счёт сервера, из которого видны потери вверх и вниз
    по отдельности.
  - В датаграммах нет постоянного идентификатора: токен новый на каждую сессию.
- **Ограничения.**
  - Один замер на устройство одновременно; на второй — `429`.
  - До 30 с на замер.
  - 1 ГиБ на устройство за сутки UTC в обе стороны; сверх — `429` с `Retry-After`.
- **Проверка.** `rayctl probe -channel <бандл>` делает то же из командной строки: 8 МиБ вниз, 4 МиБ вверх,
  50 датаграмм по 1200 байт. Тест установки гоняет его на пяти системах через настоящий SPA.

**Через туннель профиля** работает для сервисов из `probe.tunnel_svc`:
- Внутри туннеля клиент обращается к `probe.tunnel` (`probe.raycontrol.invalid`) на любом порту, с теми же
  запросами, пином и авторизацией.
- **Xray** (`inner` — DNS-туннели и Yggdrasil — и REALITY) ведёт TCP и UDP. Эхо UDP через туннель шлите на порт из
  ответа сессии, не на 443: REALITY с Vision не пропускает UDP на 443.
- **`rayd naive`** ведёт только TCP.
- **Hysteria2** (niko-server v0.5) ведёт TCP и UDP; ответы на датаграммы приходят от имени.

## 2. Метрики сервера (п. 2) — сделано

- **TCP_INFO в каждом TCP-замере.** Приходит вместе с результатом.
- **`GET /probe/v1/link`** на том же эндпоинте — вместо `DeviceService.GetLinkStats`: у устройств с ролью `user`
  порта API нет.
  - Отдаёт вид сервера на TCP-соединения с адреса запроса на 443: число соединений, RTT (минимум, медиана,
    максимум), `min_rtt_us`, переотправки и их долю, скорость доставки.
  - Только суммы: за адресом при CGNAT бывают чужие соединения.
  - Только напрямую; через туннель — `409`.
  - Не чаще раза в 5 с.
- **Hysteria2.** Поле `hysteria2` того же ответа (niko-server v0.6) — сессии адреса на каждом сервисе Hysteria2,
  по ID сервиса:
  - число соединений, сглаженный и минимальный RTT, отправленные и потерянные пакеты, доля потерь;
  - у соединений с Brutal — темп сервера (`rate_bps`) и доля подтверждённых пакетов (`ack_rate`).

  Если `ack_rate` держится ниже ~0,9, заявленный клиентом темп приёма выше того, что пропускает путь: его стоит
  снизить.

## 3. Подсказки в подписке (п. 3)

- Признак замера (`probe`) уже есть.
- Порядок профилей сервер пока не советует: данных для этого у него нет. Он появится вместе с метриками и
  сводкой от клиентов (п. 4).
- Диапазоны портов для ротации UDP уже приходят в пакете регистрации (`services[].port_key`, `port_base`,
  `port_range`).

## 4. Brutal (п. 5) — сделано

Сервер Hysteria2 — sing-quic в niko-server, не Xray, поэтому условия `congestion`/`brutalUp` из п. 5 к нему не
относятся. Смысл тот же:
- **Потолок отдачи.** `rayctl service set <hy2-masq|hy2-obfs> up_mbps=N` — потолок на одно соединение.
  Сервер шлёт клиенту со скоростью min(`N`, темп из `Hysteria-CC-RX`). Если клиент темпа не прислал, сервер
  работает на BBR.
- **Потолок приёма.** `down_mbps=N` ограничивает отдачу клиента; задавать только при нужде.
- `0` снимает потолок. По умолчанию потолков нет: сервер берёт темп клиента как есть.

## 5. Сводка от клиентов (п. 4) — отдельное обсуждение, первым предлагает клиент

§13 на этом закрыт. Остаётся п. 4 и вместе с ним совет о порядке профилей (п. 3): для совета серверу нужна
статистика по сетям, а `link` даёт вид только на текущие соединения одного адреса.

**Смысл.** Клиент уже сам меряет каналы:
- зонды через каждый профиль;
- выбор профиля;
- память результатов по сети: тип сети и оператор, только на устройстве.

С согласия пользователя клиенты отдают ноде обезличенную выжимку этих наблюдений. По многим клиентам нода видит то,
чего не видит один клиент:
- «у оператора X не проходит UDP»;
- «у оператора X TCP встаёт после ~16 КБ»;
- «в сети типа Y лучше всего работает REALITY, а Hysteria2 режется».

**Рамка сервера** — что формат должен выдерживать. Это не решение, а то, что придётся оговорить:
- **Согласие и приватность.**
  - Только по явному согласию пользователя.
  - Без адресов, идентификаторов устройств и времени с точностью до события.
  - R4-3 (журналы без активности пользователей) и R4-5 (нода ничего не отправляет сама) остаются в силе. Сводка идёт
    клиент → нода, но хранение данных о сетях пользователей оговаривается отдельным решением.
- **Что отдавать** — грубые категории:
  - тип сети и оператор: ASN или страна вместо адреса;
  - вид профиля → работает / не работает / деградирует;
  - порог остановки TCP — округлённый;
  - потери UDP — корзинами.
- **Защита от деанонимизации.**
  - Нода агрегирует и показывает или использует только группы с минимальным числом устройств (k-анонимность).
  - Сырые записи не хранятся, срок хранения короткий.
- **Защита от отравления.** Один клиент не перекрашивает подсказки для всех: лимит на устройство, вес по числу
  независимых устройств.
- **Куда.** Вероятно, тот же эндпоинт подписки и авторизация `RC1`: `POST /probe/v1/report` с небольшим JSON.
- **Как вернётся клиенту.** Необязательным полем подписки: порядок профилей или пометки «в сетях вида Y профиль Z
  плох».

**Кто начинает.** Клиент предлагает формат и говорит, что готов отдавать с согласия пользователя. После этого
сервер определит хранение, агрегацию и обратную подсказку.
