## 1. Что решено и касается Niko

- **Роли.** niko-server — data plane и «наше ядро». raycontrol — control plane: хранит пользователей и ключи,
  генерирует конфиги niko-server и Xray, ведёт nftables и SPA, ротирует ключи, отдаёт подписку и API.
  `niko-server.yaml` перестаёт быть источником правды: его (и остальные конфиги) генерирует raycontrol.
- **Процессы.** Мультиплексоры (TCP 443, UDP 443, UDP 53) — отдельный процесс `niko-front` без ключей пользователей.
  Каждый протокол — отдельный процесс-бэкенд со своим системным пользователем.
- **Периметр.** Все порты ноды закрыты (nftables, policy drop). Доступ — только после SPA v2 и только к разрешённым
  портам на TTL. Для всех открыты только UDP 53 (DNS-туннели) и, на время выпуска сертификата, TCP 443 для ACME.
  Port-knocking не используется. Неавторизованный адрес получает drop, а не приманку.
- **SPA v2 вместо Niko SPA v1.** Ключи по эпохам, порт по слотам, scope и время внутри шифрованного пакета.
  Пакеты обрабатывает `rayspa` через NFLOG, а не udpmux.
- **Постквант обязателен** везде, где протокол его поддерживает. DNS-туннели, olcRTC и OpenFlux идут во внутреннюю
  ступень `inner` (VLESS с ML-KEM-768).
- **Ротация:** ключи и порт SPA (клиент вычисляет сам), учётные данные пользователей, ключи REALITY, shortId и SNI —
  через подписку с окном перекрытия. Порты сервисов не ротируются. Параметры каждой установки случайны.
- **Белые списки в v1:** dnstt, MasterDnsVPN, olcRTC, OpenFlux. Аккаунты платформ — режим `node` (выделенные аккаунты
  на ноде) или `client` (пользователь входит своим аккаунтом в клиенте).
- **Целевые сети:** Россия, Китай, Казахстан, Кыргызстан, Узбекистан.
- **Правила работы** из SPEC (свои форки, закреплённые версии, release notes EN + RU, релиз после каждого блока)
  действуют в обоих репозиториях.

## 2. Правки в `docs/server/SPEC.md`

| Раздел SPEC | Было | Стало |
|---|---|---|
| §1 Цель | один процесс `niko-server` | `niko-front` + процессы-бэкенды (§3 ниже); Xray — как было, отдельно |
| §1 Порты | TCP 443, UDP 443, UDP 53 открыты | все порты закрыты до SPA v2; для всех — только UDP 53 и TCP 443 на время ACME; TCP 80 и 853 не открываются |
| §2.2 Домены | фиксированные поддомены `r.`, `n.`, `h.`, `y.` | поддомены выбираются случайно при установке и ротируются; DNS — wildcard `*.example.com A` + NS-делегирование зон туннелей |
| §3.1 tcpmux | неавторизованный SPA-клиент получает приманку | неавторизованных до фронта не пропускает nftables; приманка остаётся для прошедших SPA (защита от соседей по CGNAT) |
| §3.2 udpmux, шаг 3 | SPA v1 в udpmux | шаг удалить: SPA v2 обрабатывает `rayspa` на отдельном ротируемом порту |
| §3.5 SPA | Niko SPA v1 | заменить ссылкой на `docs/spec/spa-v2.md` в raycontrol; v1 остаётся в клиенте только для сторонних серверов |
| §3.6 REALITY | Xray на `127.0.0.1:8443` | Xray на unix-сокете с `acceptProxyProtocol`; `mldsa65Seed` обязателен; ключи и shortId ротируются через raycontrol |
| §3.2, §3.7, §3.8 TLS | группы по умолчанию | только `X25519MLKEM768` для Hysteria2, naive, DoH; классические группы отклоняются |
| §4 Конфиг и команды | `init`, `export` в niko-server | ключи и конфиги генерирует raycontrol; niko-server читает сгенерированные файлы, `check` остаётся; `export` и подписку отдаёт raycontrol |
| §4 Деплой | один юнит | юниты на каждый процесс, с отдельными пользователями; ставит их raycontrol |
| новый раздел | — | внутренняя ступень `inner` (§3.5 ниже) |
| новый раздел | — | olcRTC и OpenFlux как движки ноды (§3.6 ниже) |

## 3. Что нужно от niko-server (контракт с raycontrol)

### 3.1. Роли одного бинарника

- `niko-server front -c <файл>` — tcpmux, udpmux, dnsmux. Знает только таблицу маршрутов, пароль salamander
  (для классификации) и пути сокетов бэкендов. Ключей пользователей не знает. Права: только `CAP_NET_BIND_SERVICE`.
- `niko-server backend -c <файл>` — один протокол: `hy2-masq`, `hy2-obfs`, `naive`, `doh`, `dnstt`, `masterdns`,
  `yggdrasil`, `inner`, `site` (сайт-приманка, цель REALITY). Без capabilities, слушает только свой unix-сокет.
- `niko-server check -c <файл>` — проверка конфига без запуска; ненулевой код и понятная ошибка при проблеме.
  raycontrol вызывает её перед каждым применением.

### 3.2. Связь фронта с бэкендами

- **TCP:** фронт передаёт принятый сокет бэкенду через unix-сокет (`SCM_RIGHTS`) вместе с метаданными: адрес клиента,
  уже прочитанные байты, маршрут. Для Xray — поток через unix-сокет с заголовком PROXY v2.
- **UDP:** фронт пересылает датаграммы в `SOCK_DGRAM`-сокет бэкенда с заголовком «адрес клиента»; бэкенд видит
  виртуальный `net.PacketConn` (тот же хук, что SPEC §3.2 требует для inbound hysteria2 и naive-quic). Ответы — обратно
  через фронт.
- Сокет бэкенда доступен только UID фронта; бэкенд проверяет `SO_PEERCRED`.
- Формат метаданных и заголовка UDP определяет niko-server (обе стороны у вас) и описывает в своей документации.
- Нагрузочный тест SPEC §6.4 — с разделёнными процессами. Если копия UDP через фронт окажется узким местом,
  сообщите: запасной путь — `SO_REUSEPORT` + eBPF.

### 3.3. Конфиги

- Опубликуйте схему конфигов фронта и бэкендов (например, `docs/server/CONFIG.md` + JSON Schema).
  raycontrol будет генерировать их по этой схеме; версия схемы — поле в конфиге.
- Секреты (ключи, пароли, сертификаты) — через пути к файлам, которые systemd передаёт `LoadCredential=`,
  а не строками в конфиге.
- **`SIGHUP`:** перечитать пользователей и ключи без разрыва установленных соединений. Смена портов и доменов —
  через перезапуск.

### 3.4. Постквант в TLS

- Hysteria2 (оба инстанса), naive (h2 и QUIC), DoH: `CurvePreferences = [X25519MLKEM768]`, без отката.
- REALITY в Xray: гибридный ключ (по умолчанию с Xray 26.9.8) + `mldsa65Seed`.
- Тест в CI: клиент без `X25519MLKEM768` не подключается.

### 3.5. Внутренняя ступень `inner`

- Бэкенд с VLESS-сервером и `decryption` ML-KEM-768 (`mlkem768x25519plus`), пользователи — от raycontrol.
- **Проверить:** умеет ли форк sing-box серверную часть VLESS encryption. Если нет — `inner` поднимается на Xray,
  сообщите об этом.
- dnstt и MasterDnsVPN (режим `TCP` + фиксированный upstream) отдают соединения в `inner`, а не в shadowsocks,
  как в SPEC §3.3.

### 3.6. olcRTC и OpenFlux

- Форки: `arngory/olcrtc` (upstream — движок Ghostlane), `arngory/OpenFlux`.
- На ноде это отдельные процессы под управлением raycontrol; входящих портов нет.
- Нужен режим **фиксированного upstream**: серверная сторона не открывает соединения к произвольным адресам,
  а отдаёт каждый поток в `inner` (unix-сокет). Клиент поднимает VLESS к `inner` внутри туннеля.
- OpenFlux: шифрование обязательно, выход L4, без root.

## 4. Что нужно в клиенте Niko

### 4.1. SPA v2

- Реализовать по [`spa-v2.md`](https://github.com/arngory/raycontrol/blob/claude/clever-feynman-w0e2v1/docs/spec/spa-v2.md)
  §2–§5 и §7: ключ эпохи, порт слота, пакет случайной длины, продление до истечения TTL со случайным смещением,
  повтор после смены сети и после неудачного подключения.
- Тест на векторы: скопировать `vectors.json` в тесты клиента и проверять порты, ключи эпох и пакеты побайтно
  (как `TestSPAVector` для v1).
- Существующий стук и SPA v1 оставить для сторонних серверов; для нод raycontrol используется только v2.

### 4.2. Импорт устройства

- Импорт строки `rcdev1:…` (вставка и QR) по `spa-v2.md` §8: создаёт «ноду» с параметрами SPA, ключом устройства
  и картой сервисов (ID → kind, name).
- `device_key` хранить в Android Keystore; в логи и экспорт профилей не попадает.
- Профили подключения этой ноды автоматически получают шаг SPA v2.

### 4.3. Подписка с ротацией (этап R1/R4)

- Подписка: HTTPS к `rayd` после SPA, TLS только с `X25519MLKEM768`, ответ подписан ключом ноды
  (гибрид Ed25519 + ML-DSA-65; точный формат фиксируется в R1 вместе с вами).
- Учётные данные приходят парами «текущие + следующие» со временем переключения; клиент держит обе и переключается
  без разрыва.
- Ссылки в подписке привязываются к импортированной ноде (например, параметр `niko-node=<node_id>`), а не несут
  ключ устройства. Формат ссылок задаёт `export` raycontrol (решение P-10); согласуем на R1.

### 4.4. Постквант

- Убедиться, что во всех TLS к ноде клиент предлагает `X25519MLKEM768`: отпечаток uTLS `chrome`, Go TLS
  у Hysteria2, Chromium у naive. Отката на классические группы для нод raycontrol нет.

### 4.5. Белые списки

- olcRTC и OpenFlux как исходящие в ядре (Go, gomobile — как у этих проектов).
- Вторая ступень: исходящий VLESS с ML-KEM-768 к `inner` через detour — для dnstt, MasterDnsVPN, olcRTC, OpenFlux.
- Режим аккаунта `client`: вход в платформу и капча — во встроенном WebView.

## 5. Синхронизация этапов

| Этап raycontrol | niko-server | Клиент Niko |
|---|---|---|
| R0 — база (готово: SPA v2, хранилище, `rayd`, `rayctl`, пакет регистрации) | — | SPA v2 + векторы, импорт `rcdev1:` |
| R1 — периметр и DNS-туннели | SPEC §7 шаги 1–2 + разделение на фронт и бэкенды + схема конфигов | подписка (формат согласуем) |
| R2 — TCP 443 | SPEC §7 шаг 3, Xray на unix-сокете | PQ-проверка REALITY с ML-DSA-65 |
| R3 — UDP 443 и API | SPEC §7 шаг 4 без SPA в udpmux | регистрация через API |
| R4 — ротация и эксплуатация | SPEC §7 шаг 5 | переключение учётных данных с перекрытием |
| R5 — белые списки | `inner`, olcRTC и OpenFlux с фиксированным upstream | olcRTC, OpenFlux, вторая ступень |

## 6. Что ждём обратно от сессии Niko

1. Ответ: есть ли серверная часть VLESS encryption в форке sing-box.
2. Схема конфигов фронта и бэкендов (`CONFIG.md` или аналог) с версией.
3. Описание IPC фронт ↔ бэкенд (метаданные TCP, заголовок UDP).
4. Результат нагрузочного теста с разделёнными процессами.
5. Возможен ли постквант для Yggdrasil.
6. Предложение по формату ссылок и подписи подписки (совместно, к R1).
