# 02. Модель безопасности: периметр и zero trust

Статус: **черновик для согласования**.

## Угрозы, от которых защищаемся

| Противник | Что делает | Чем закрываемся |
|---|---|---|
| Массовые сканеры | Сканируют порты, подбирают пароли SSH. | Закрытые по умолчанию порты, knock + SPA для служебного доступа, SSH только по ключам. |
| Цензор (DPI, активные проверки) | Классифицирует трафик, повторяет соединения клиента со своих адресов, проверяет, что отвечает сервер. | Протоколы, которые выглядят как обычный сайт и корректно отвечают на проверки (self-steal); gated-сервисы не отвечают вовсе. |
| Пользователь прокси | Пытается через прокси попасть в локальные сервисы, метаданные облака, админку. | Запрет приватных адресов в движках и в nftables по UID процесса. |
| Взломанный компонент | Пытается расширить доступ (прочитать базу, чужие ключи, управлять файрволом). | Разделение пользователей, минимальные права, отдельные учётные данные. |
| Утечка бэкапа или лога | Секреты попадают к посторонним. | Шифрованные бэкапы, никаких секретов в логах и argv. |

Вне модели: компрометация root на хосте и злоумышленник с доступом к консоли хостера.

## Три эшелона

```
пакет из интернета
  │
  ├─ Эшелон 0: nftables, policy drop. Открыто только то, что в профиле public.
  │
  ├─ Эшелон 1: port-knocking. Дешёвый фильтр в ядре: без правильной последовательности
  │            SPA-порт для этого IP не существует.
  │
  ├─ Эшелон 2: SPA. Один криптографически подписанный пакет → временный доступ
  │            для конкретного IP к конкретным сервисам (scope) на TTL.
  │
  └─ Эшелон 3: сервис. Своя аутентификация по своим учётным данным
               (UUID VLESS, пароль Hysteria-инстанса, mTLS + токен API, ключ SSH).
```

Ни один эшелон не доверяет предыдущему: доступ на уровне сети не заменяет аутентификацию в сервисе.

### Профили: public и gated

Это главное противоречие, которое нужно решить до реализации.

- Сервисы с маскировкой под сайт (VLESS REALITY с self-steal на TCP 443, Hysteria2 masquerade на UDP 443)
  должны отвечать **всем**: если 443 «чёрная дыра», то домен, сертификат и сайт-приманка теряют смысл,
  а сторонние клиенты (v2rayN, Hiddify, sing-box) не умеют стучать.
- Сервисы без маскировки (SSH, удалённый API, Hysteria salamander, всё экспериментальное) лучше прятать за knock + SPA.

Предлагается задавать профиль на уровне инстанса (`instances.profile`):

| Инстанс | Профиль по умолчанию | Почему |
|---|---|---|
| SSH | gated (+ аварийный доступ, см. ниже) | Не должен быть виден сканерам. |
| API `rayd` (удалённый) | gated + mTLS | Управление. |
| VLESS REALITY (TCP 443) | public | Маскировка под сайт; на проверки отвечает сайт-приманка. |
| Hysteria2 masquerade (UDP 443) | public | Маскировка под HTTP/3 того же сайта. |
| Hysteria2 salamander | gated | Случайный UDP без маскировки; лишний раз светить его не нужно. |
| XHTTP, Naive и другие | решается при добавлении | По свойствам протокола. |
| dnstt | public (вынужденно) | Рекурсивные DNS-резолверы стучать не будут. |

Любой инстанс можно перевести в другой профиль; для своего клиента можно держать всё в gated.

### Эшелон 1: port-knocking (исправленная схема)

Что меняется по сравнению с v0 (L-30…L-33):

- **Ограничения на каждый IP**, а не глобальные: dynamic set с `limit rate over … per saddr`.
  Флуд одного адреса не мешает остальным.
- **Устойчивость к ретрансмитам:** повторный пакет на порт текущей стадии не считается ошибкой.
- **Бан не с первого промаха:** счётчик ошибок на IP, бан после N ошибок, срок короче суток.
- **Один L4-протокол для стука** (UDP или TCP SYN), чтобы не удваивать правила.
- **IPv4 и IPv6** равноправно: парные наборы и правила на каждой стадии.
- **Результат стука — не доступ к сервисам,** а только право отправить SPA-пакет: IP попадает в
  `spa_open` на ~30 секунд.

Вариант на обсуждение: **последовательность портов из TOTP**. Порты стука вычисляются из общего секрета
и текущего временного окна (окно 30–60 с, принимаем текущее и предыдущее). `rayspa` перестраивает правила
на каждом окне. Перехваченная последовательность устаревает сама.

Что стук не даёт: криптографической защиты. Последовательность видна на пути и повторяема в пределах окна.
Его задача — убрать SPA-порт из видимости и дёшево отсечь флуд до проверки криптографии.

### Эшелон 2: SPA

Схема (черновик):

- **Доставка:** правило `ip saddr @spa_open udp dport $SPA_PORT log group N drop`. Ядро копирует пакет
  в NFLOG и отбрасывает его. `rayspa` читает NFLOG и сокет не открывает. Для сканера порт закрыт,
  ответа никогда нет.
- **Ключи:** у каждого устройства своя пара X25519. Сервер хранит только публичные ключи устройств.
  Общий ключ = X25519(устройство, сервер) → HKDF.
- **Пакет:** `версия | key_id | nonce(24) | XChaCha20-Poly1305(ts, scope, ttl, client_nonce) | padding`.
  Длина случайная в диапазоне, чтобы не было фиксированного размера.
- **Защита от повтора:** окно времени ±60 с и кэш nonce на это окно.
- **Привязка к IP:** доступ выдаётся на адрес-источник пакета (адрес после NAT). Заявленный клиентом IP не используется.
- **Scope:** клиент запрашивает конкретные сервисы. `rayspa` выдаёт пересечение запрошенного и разрешённого
  устройству. Каждый сервис — свой allow-набор, на TTL.
- **Продление:** клиент повторяет SPA до истечения TTL. Установленные соединения держит conntrack.
- **Отзыв:** отзыв устройства в `rayd` → `rayspa` удаляет ключ и его активные доступы.

Почему не fwknop: клиент свой, а fwknop тянет свой формат пакета, свою конфигурацию и устаревшие мобильные
клиенты. Его модель (SPA + HMAC + окно времени) берём как образец.

Открыто: стоит ли маскировать SPA-пакет под что-то правдоподобное (DNS-запрос, QUIC Initial)
вместо случайного UDP.

### Аварийный доступ

Чтобы не повторить L-33 (сбой стука = только консоль хостера):

- при установке выпускается аварийный ключ устройства с правом только на SSH, хранится офлайн;
- опционально: allowlist статических адресов администратора в обход knock;
- `rayctl perimeter disable` с консоли возвращает обычный SSH.

## Zero trust между компонентами

### Кто кому доверяет

| Вызов | Канал | Аутентификация |
|---|---|---|
| `rayctl` → `rayd` | unix socket `0660 root:raycontrol` | `SO_PEERCRED` (UID и группа) |
| Клиент → удалённый API `rayd` | HTTPS, gated | mTLS-сертификат устройства от внутреннего CA + scope устройства |
| `rayd` → `rayspa` | unix socket | `SO_PEERCRED`: принимается только UID `rayd` |
| `rayd` → Xray API | `127.0.0.1:порт` | nftables `meta skuid rayd`: остальные UID отбрасываются |
| Hysteria → колбэк авторизации `rayd` | `127.0.0.1:порт` (http auth не умеет unix socket) | nftables по `skuid` инстанса + отдельный секрет в URL для каждого инстанса |
| `rayd` → Traffic Stats Hysteria | `127.0.0.1:порт` | секрет `trafficStats.secret` на инстанс + `skuid rayd` |
| Xray → caddy (fallback REALITY) | loopback или unix socket | только UID xray |

### Учётные данные

- У каждого инстанса движка свои ключи и секреты: REALITY private key, пароль salamander, секрет Traffic Stats,
  секрет колбэка. Ничего общего между инстансами.
- У каждого пользователя отдельные учётные данные на каждый инстанс.
- TLS-ключи сайта отдаются движкам через `LoadCredential=` и не лежат в общем каталоге с групповыми правами.
- Внутренний CA для mTLS API — отдельный от публичных сертификатов, ключ CA только у `rayd`.

### Изоляция процессов

- Отдельный системный пользователь на каждый компонент и инстанс.
  Фиксированные UID, а не `DynamicUser`, потому что на них опираются правила nftables по `skuid`.
- Systemd hardening: `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`,
  `CapabilityBoundingSet` минимальный, `RestrictAddressFamilies`, `SystemCallFilter=@system-service`,
  `SocketBindAllow` только на свои порты.
- **Исходящий трафик прокси:** запрет приватных и служебных сетей в двух местах — в маршрутизации движка
  (`geoip:private` в Xray, ACL в Hysteria) и в nftables `output` по `skuid` процессов-прокси
  (127.0.0.0/8, 10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10, fc00::/7, fe80::/10). Исключения точечные
  (Xray → caddy для fallback).

### Логи и секреты

- Никаких секретов в логах, argv и переменных окружения дочерних процессов.
- Журнал аудита API (кто, что, когда, результат) — в базе `rayd`.
- Access-логи движков выключены по умолчанию; если включены — через journald с ограничением срока хранения.

## Что проверяем тестами

- Правила nftables: сценарии knock (правильный порядок, ретрансмит, флуд с другого IP, IPv6) в network namespace.
- SPA: повтор пакета, просроченный ts, чужой ключ, scope шире разрешённого.
- Изоляция: процесс-прокси не может открыть соединение на 127.0.0.1:5432, на API Xray и на колбэк авторизации.
