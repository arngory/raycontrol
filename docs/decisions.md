## Ключевые решения

| № | Решение | Как принято |
|---|---|---|

## Следствия, которые нужно учесть

1. **Ротация SNI и сертификаты.** Каждый новый поддомен получает свой сертификат, а все сертификаты публикуются
   в журналах Certificate Transparency: домен, выпускающий много случайных поддоменов, сам становится отпечатком.
   Wildcard-сертификат этого избегает, но требует DNS-01 через API DNS-провайдера. Решение по умолчанию:
   wildcard-запись `*.example.com A`; если у провайдера есть API — wildcard-сертификат через DNS-01;
   если нет — поддомены из коротко-оконного ACME и редкая ротация SNI.
2. **Общий IP (CGNAT).** SPA открывает доступ для адреса, за которым может быть много людей, включая проверяющего.
   Поэтому сервисы остаются устойчивыми к активному зондированию сами по себе: REALITY с self-steal, naive без `407`,
   Hysteria2 masquerade — как в SPEC, только за SPA.
3. **SPEC niko-server нужно обновить** (она в `arngory/niko`, отсюда её не правим):
   - неавторизованный IP получает drop, а не приманку (§3.1, §3.5);
   - SPA обрабатывает `rayspa` через NFLOG на ротируемом порту, а не udpmux (§3.2, §3.5);
   - формат SPA v2 вместо v1 (§3.5);
   - фронт и бэкенды — отдельные процессы (§2, §3);
   - конфиги генерирует raycontrol, `init` и `export` вызываются через него (§4);
   - обязательный PQ в TLS (`X25519MLKEM768`) для Hysteria2, naive и DoH.
4. **Доработки клиента Niko:** SPA v2 с эпохами и ротируемым портом; автообновление подписки с перекрытием
   учётных данных; olcRTC и OpenFlux как исходящие; вторая ступень с VLESS encryption внутри DNS-туннелей,
   olcRTC и OpenFlux; ACME-окно не затрагивает клиент.
5. **Внутренняя ступень с PQ.** Для DNS-туннелей, olcRTC и OpenFlux внутренняя ступень — VLESS с `decryption`
   ML-KEM-768. Нужно проверить, умеет ли серверную часть VLESS encryption форк sing-box; если нет — ступень на Xray.
6. **Китай.** Выбранные транспорты белых списков работают через российские платформы (Телемост, Яндекс Документы,
   WB Stream); для Китая нужны свои платформы — отдельное исследование после v1. Hysteria2/QUIC в Китае часто
   ограничивают — основной там REALITY.

| № | Решение |
|---|---|
| R1-1 | **SPA v2 по TCP — принят** как второй носитель на тех же портах слотов ([`spec/spa-v2.md`](spec/spa-v2.md) §10). Реализация на ноде — обычный слушающий сокет в `rayspa`, а не `synproxy` + NFLOG: сокет собирает пакет из любого числа сегментов (клиент режет записи против DPI), NFLOG видит только первый. Снаружи разницы нет: порт слота отвечает на SYN, пока слот активен. Включён по умолчанию (`rayd serve -spa-tcp`). |
| R1-2 | **`inner` — на Xray** (`arngory/xray-core`), пока в форке sing-box нет серверной части VLESS encryption. |
| R1-3 | **Постквант Yggdrasil**: линк TLS 1.3 только с `X25519MLKEM768`; сквозное шифрование Yggdrasil классическое, полезный трафик идёт в `inner`. Публичные пиры — флагом, по умолчанию выключены (P-14). |
| R1-4 | **Ссылки и подписка** — предложение Niko принято как основа: параметры `niko-node`, `niko-svc`, `niko-pin`, `niko-dns`, `niko-dnskey`, `niko-inner`; подписка — JSON-конверт с двумя подписями (Ed25519 и ML-DSA-65, обе обязательны), `seq` против отката, `next` для ротации. Дополнительно в payload — поле `time` (время сервера) для проверки часов клиента. Ключи ноды — необязательное поле `node_keys` пакета `rcdev1` (§8 спецификации SPA). Формат замораживается вместе с эндпоинтом подписки в R1. |
| R1-5 | **CONFIG.md и IPC.md (схема 1, IPC 1)** приняты как основа; замечания — в [`handoff/niko-r1-reply.md`](handoff/niko-r1-reply.md). raycontrol генерирует конфиги по ним. |
| R1-6 | **UID процессов ноды** — фиксированный диапазон 9100–9199: `niko-front` 9100, бэкенды и Xray 9110–9179, `rayd` 9190, `rayspa` 9191. Таблицу ведёт аллокатор `rayd`; niko-server получает UID только из конфигов. |
| R1-7 | **Периметр закрыт при сбое**: таблица nftables остаётся, если `rayspa` остановлен. Восстановление с консоли — `rayspa teardown`. |
| R1-8 | **MasterDnsVPN — метод 5 (AES-256-GCM)**, а не 2: метод 2 у MasterDnsVPN — ChaCha20 без аутентификации, а нода разрешает только AEAD. Ключ — 32 hex-символа, как его генерирует сам MasterDnsVPN. |
| R1-9 | **Кто что пишет.** `rayd` (без привилегий) сам генерирует конфиги и секреты data plane в `/var/lib/raycontrol/rendered/<сервис>/`, синхронизирует пользователей `inner` через gRPC API Xray и перезапускает изменённые процессы (правило polkit разрешает ему только `niko-*.service`). root (`rayctl apply`) ставит системных пользователей, юниты и системные файлы — только при добавлении или удалении сервисов. План root строит сам из проверенных входов `rayd`, а не берёт у него (R4-33). Поэтому `rayd` входит в группы сервисов: ему нужно выставлять группу на их файлы. |
| R1-10 | **API ноды**: сокет `rayd.sock` открыт всем локальным пользователям (0666); кто что может, решает проверка `SO_PEERCRED` (root, сам `rayd`, группа `raycontrol`). `rayspa` к API управления не допускается, ему доступна только лента периметра. |
| R1-11 | **API Xray `inner`** — unix-сокет в отдельном каталоге `/run/niko/<inner>-api` (setgid, группа `rayd`): DNS-туннели, которые ходят в `inner` по VLESS, до API не дотягиваются. |
| R1-12 | **`inner` резолвит через DoH** (1.1.1.1, 9.9.9.9): резолвер хоста может быть в приватном диапазоне, который `inner` блокирует. Приватные сети закрыты дважды: правилом маршрутизации и собственной защитой `freedom` в Xray 26. |
| R1-13 | **Подписка в R1** — собственный порт `rayd` за SPA, TLS 1.3 только с `X25519MLKEM768`, самоподписанный сертификат с пином в `rcdev1` ([`spec/subscription-v1.md`](spec/subscription-v1.md)). В R2 переезжает за tcpmux на 443. |
| R1-14 | **Изоляция DNS-бэкендов**: `PrivateNetwork=yes`, только `AF_UNIX`, без capabilities — сети у них нет вовсе, пакеты приносит фронт, потоки уходят в `inner`. |
| R1-15 | **Лицензия** — GPL-3.0 (M-1), файл `LICENSE`. |
| R1-16 | **Ротация UDP-портов сервисов** ([`spec/spa-v2.md`](spec/spa-v2.md) §11): у сервисов на UDP 443 своё расписание порта (ключ, диапазон), формула как у SPA. `rayspa` перенаправляет порты слотов на порт сервиса через NAT; доступ — тот же SPA-доступ к UDP-порту сервиса. Параметры уходят клиенту в `services[]` пакета `rcdev1`. niko-server ничего не меняет. |
| R1-17 | **Подписка v1 заморожена** вместе с эндпоинтом `/sub/v1`; несовместимые изменения — только подписка v2 с новым путём. |
| R1-18 | **Релиз raycontrol** запускается из GitHub (workflow `Release`, ручной запуск с тегом): из сессий пушить теги нельзя. |

## Решения R2

| ID | Решение |
|---|---|
| R2-1 | **Целевые системы** (заменяет B-6): последние релизы Debian и Rocky Linux как минимум, и любой современный Linux с systemd. Проверяются в CI полной установкой: Debian 12/13, Ubuntu 24.04, Rocky Linux 9/10 (amd64; arm64 — сборка). На остальных `rayctl install` не отказывает по названию системы, а проверяет то, что нужно ноде: systemd ≥ 247 и шина D-Bus, polkit, `nft` и ядро, которые загружают таблицу периметра (пробная загрузка `nft -c`), команды `useradd`/`groupadd`/`usermod`/`runuser`/`systemd-tmpfiles`/`sysctl`; непроверенная система — только предупреждение. `bootstrap.sh` ставит зависимости через apt, dnf, zypper или pacman и проверяет подпись через openssl, без minisign. |
| R2-2 | **Файрвол хоста.** Таблица `inet raycontrol` решает, кому какой порт открыт, но пакет проходит, только если его принимают все базовые цепочки хука. Поэтому `rayctl apply` сам открывает порты ноды (диапазон SPA по UDP и TCP, порты включённых сервисов) в firewalld (сервис `raycontrol` в зоне по умолчанию и активных зонах) и в ufw (профиль приложения `raycontrol`); перенаправленные порты ротации в этом не нуждаются — NAT срабатывает раньше. Про другие таблицы nftables с `policy drop` на входе выводится предупреждение со списком портов. |
| R2-3 | **Таблица переживает чужой `flush ruleset`**: `rayspa` раз в секунду проверяет, что таблица на месте, и восстанавливает её вместе с выданными доступами (с оставшимся временем). Перезапуск nftables.service на Debian, перезагрузка firewalld или ufw открывают ноду не дольше чем на секунду. Юнит `rayspa` стартует после `nftables`, `firewalld` и `ufw`. |
| R2-4 | **Порядок `rayctl apply`**: юниты по порядку плана, `rayd` первым. Если юнит `rayd` изменился (новые группы сервисов), он перезапускается, отрисовывает файлы сервисов до открытия сокета, и только потом стартуют юниты data plane, которые эти файлы читают. Сервис, файлы которого записать нельзя, пропускается, остальные отрисовываются. |
| R2-5 | **Хост без IPv6** (`ipv6.disable=1`): фронт слушает только `0.0.0.0:53`, иначе он не стартует вовсе. |
| R2-6 | **`rayctl probe`** проверяет ноду снаружи по пакету `rcdev1`, как клиент: SPA по UDP (затем TCP), подписка с пином и обеими подписями. Им же пользуется установочный тест. |
| R2-7 | **REALITY до tcpmux слушает TCP 443 сам.** В niko-server v0.1.1 нет TCP-фронта (`check` отклоняет секцию `tcp`), поэтому Xray с REALITY получает `CAP_NET_BIND_SERVICE` и слушает порт сервиса напрямую; SPA-доступ к нему выдаёт `rayspa`, как к любому сервису. Когда у фронта появится tcpmux, Xray переезжает на unix-сокет с PROXY v2 (маршрут по SNI, CONFIG.md); код отрисовки обоих вариантов уже есть (`render.Model.FrontTCP`). Ссылки при переезде не меняются: порт 443. |
| R2-8 | **REALITY: постквант и цель.** Обмен ключами — `X25519MLKEM768`, подпись сертификата — ML-DSA-65 (`mldsa65Seed`), второй слой — VLESS encryption с ML-KEM-768, Vision. У сервиса 4 shortId случайной длины, пользователи распределены по ним. Цель пока задаётся явно (вариант B; self-steal на своём сайте-приманке — R2b, нужен сертификат). При создании `rayd` проверяет цель с ноды: TLS 1.3, `X25519MLKEM768`, HTTP/2, валидный сертификат для `sni` и **длина цепочки сертификатов не меньше сертификата REALITY с подписью ML-DSA-65** (~3,5 КБ): REALITY подгоняет свои сообщения под длины цели и с короткой цепочкой не работает (многие сайты с ECDSA-цепочками не подходят). |
| R2-9 | **Ключи бэкендов — копия в каталоге сервиса, а не `LoadCredential=`.** В контейнерах (Docker, LXC — частый вариант VPS) systemd 257 не создаёт каталог credentials сервиса, и бэкенды не стартуют. Поэтому перед стартом systemd от root копирует отрисованный ключ в `RuntimeDirectory` сервиса: `ExecStartPre=+rayd credential` (до v0.21.0 — `install -m 0400 -o niko-<сервис>`, R4-33), путь в конфиге — `/run/niko/<сервис>/<файл>`. Изоляция та же: читает только пользователь сервиса (фронт — нет: в группы сервисов он не входит, R4-28), исходный файл — `0600 rayd`, копия исчезает с остановкой сервиса. Работает везде, где есть systemd. |
| R2-10 | **Перерисовка чинит права.** Файл, отрисованный до появления группы сервиса, получает её при следующем проходе `rayd`, даже если содержимое не изменилось, и процесс перезапускается. Юниты без ограничения частоты запусков (`StartLimitIntervalSec=0`): процесс, которому ещё нечего читать, пробует снова каждые 2 с, а не останавливается навсегда. |
| R2-11 | **Сертификаты — ACME HTTP-01 в коротком окне.** По умолчанию Let's Encrypt. На время заказа (не дольше 3 мин) `rayspa` перенаправляет TCP 80 от любых адресов на ответчик `rayd` (порт случайный для установки и входит в порты для firewalld/ufw, потому что после перенаправления хост видит его), который отдаёт только токены этого заказа; элементы nftables живут с таймаутом и закрываются сами, даже если `rayd` или `rayspa` упадут. Перед заказом `rayd` проверяет, что имя резолвится в адрес ноды. Порт 443 при этом не открывается (TLS-ALPN-01 через tcpmux — когда он будет у niko-server; DNS-01 — если у провайдера есть API). Продление — когда осталась треть срока. |
| R2-12 | **Сайт-приманка и self-steal.** С доменом REALITY по умолчанию берёт целью свой сайт: при первом сервисе REALITY без `target` создаётся сервис `site` со случайным поддоменом. Содержимое генерируется из seed установки (небольшой сайт мастерской с журналом; у каждой установки своё), сертификат — ACME (R2-11), RSA: цепочка Let's Encrypt с корнем, который сайт досылает, длиннее сертификата REALITY с ML-DSA-65. Пока у niko-server нет бэкенда `site`, сайт обслуживает `rayd site` отдельным юнитом и пользователем, только unix-сокет `/run/niko/site/tls.sock` (`PrivateNetwork=yes`), TLS 1.3, X25519MLKEM768, h2. Сайт и REALITY ждут сертификата: юниты с `ConditionPathExists=` на свои файлы, и `rayd` запускает их, когда файлы впервые появляются. |

## Решения R3

Серверная часть R2 и R3 (мультиплексоры на 443, naive, DoH, Hysteria2) перешла из сессии Niko сюда: фронт
niko-server на 443 отложен. Пока его нет, протоколы работают на тех движках, что уже есть на ноде, каждый на своём
порту; ссылки и подписка от этого не зависят.

| Пункт SPEC | Сейчас (до фронта niko-server) | С фронтом |
|---|---|---|
| tcpmux на TCP 443 | **сделано**: фронт niko-server v0.2 делит 443 по SNI (R2-15) | — |
| Xray на unix-сокете | **сделано**: REALITY на сокете за фронтом, PROXY v2 (R2-15) | — |
| `site` | `rayd site` на unix-сокете (R2-12, R4-8); бэкенд `site` в niko-server не нужен | — |
| naive (h2) | `rayd naive` за фронтом, сокеты передаёт фронт (R2-14, R2-15) | — |
| DoH | в `rayd` за фронтом, сокеты передаёт фронт (R3-2, R2-15) | — |
| udpmux на UDP 443 | **сделано**: фронт niko-server v0.3 делит UDP 443 по имени в QUIC Initial и по salamander (R3-4) | — |
| naive-quic, DoH3 | **сделано**: HTTP/3 в `rayd naive` и `rayd` за udpmux (R3-5) | — |

| ID | Решение |
|---|---|
| R3-1 | *Движок и порты заменены R3-4.* **Hysteria2 ×2 на Xray.** `hy2-masq` — UDP 443, TLS 1.3 только с `X25519MLKEM768`, сертификат сайта ноды под своим случайным поддоменом (wildcard через DNS-01 или имя в сертификате сайта), без пароля — `masquerade` с пустым `404`, как у сайта (R4-8). `hy2-obfs` — внутри salamander, на своём случайном UDP-порту (443 занят `hy2-masq`, пока нет udpmux), с самоподписанным сертификатом: клиент пинит его ключ (`niko-pin`), имени нет ни в DNS, ни в CT. Пароли пользователей — учётные данные с ротацией и перекрытием (R4-1); Xray получает их через API без перезапуска. Оба за SPA и с ротацией UDP-портов. Переход на udpmux niko-server ссылки не меняет. |
| R3-4 | **Hysteria2 — бэкенды niko-server за udpmux (v0.3).** Фронт слушает UDP 443 и закрепляет поток (адрес клиента и локальный) первой датаграммой, которая классифицируется. Это QUIC Initial (v1 или v2), чей ClientHello называет `hy2-masq`: фронт расшифровывает его открытыми ключами Initial и собирает ClientHello из нескольких пакетов. Или пакет salamander, который открывается паролем `hy2-obfs`. Фейки, чужие имена и мусор отбрасываются, поток не закрепляя. Поэтому `hy2-obfs` тоже на UDP 443, и у обоих сервисов ротация портов ведёт на 443. Бэкенды — sing-quic, тот же код, что в клиенте Niko. Пароли берутся из `users.json`, который `rayd` переписывает при ротации, а бэкенд перечитывает сам, без перезапуска и обрыва сессий. TLS 1.3 только с `X25519MLKEM768`, неавторизованным — пустой `404`. Выход только на публичные адреса: в коде и `IPAddressDeny`. Пароль salamander есть у бэкенда и копией у фронта (`ExecStartPre`, только пользователь фронта). Xray для Hysteria2 больше не нужен; совместимость с другой реализацией проверяет тест с клиентом Xray. Потолок серверного Brutal на соединение — `up_mbps` бэкенда: сервер шлёт со скоростью min(потолок, темп клиента), без темпа клиента — BBR (сейчас не задан; см. задачу об адаптивности). |
| R3-5 | **naive-quic и DoH3 — те же имена по QUIC за udpmux.** У сервисов `naive` и `doh` порты TCP 443 и UDP 443. Фронт отдаёт им датаграммы потоков с их именем в QUIC Initial (режим `packet`): `rayd naive` и `rayd` поднимают на них HTTP/3 (quic-go), TLS 1.3 только с `X25519MLKEM768`, ALPN `h3`. Обработчики те же, что для HTTP/2: naive — CONNECT с паддингом, неавторизованным ответ сайта; DoH — `/dns-query/<токен>`. Ссылки и учётные данные не меняются: клиент сам выбирает h2 или h3 по одному и тому же имени и порту 443. Как у всего на UDP, у них есть расписание портов. |
| R3-2 | **DoH в `rayd` за REALITY.** `https://<имя>/dns-query/<токен>` (RFC 8484, GET и POST, h2), TLS 1.3 только с `X25519MLKEM768`, сертификат сайта. Токен — учётные данные пользователя с ротацией (с v0.27.0 — свой у каждого устройства, R4-37); без верного токена — ответ сайта, как у naive (R2-14): пустой `404` по умолчанию, `403` или `silent`, у сайта со страницами — `404` (до волны 2 — всегда пустой `404`). Запросы уходят к DoH-резолверам (1.1.1.1, 9.9.9.9), в журналы не пишутся (P3). TCP 443 общий с REALITY (фронт, R2-15), поэтому DoH ставится после REALITY с self-steal. DoH3 (UDP 443) ждёт udpmux. |
| R3-3 | **Удалённый API: свой порт за SPA, mTLS по ключу устройства, регистрация по приглашению** ([spec/api-v1.md](spec/api-v1.md)). Сервис `api` включается явно (`rayctl service add api api`), случайный TCP-порт, TLS 1.3 только с `X25519MLKEM768`, самоподписанный сертификат с пином, как у подписки. Через SPA порт открывают только устройства-администраторы, зарегистрированные через API, и действующие приглашения; пользовательским устройствам он не нужен. Клиентский сертификат обязателен; устройство — это пин его ключа, CA на ноде нет: выпускать нечего и некому украсть, отзыв сразу (`device revoke`), смена ключа — `RotateCertificate` с подписью новым ключом. Приглашение `rcinv1:` — пакет регистрации с одноразовым ключом SPA только к API и сроком (сутки по умолчанию, неделя максимум); `Register` берёт его HMAC, привязанный к минуте и к ключу клиентского сертификата, и возвращает обычный `rcdev1:` с новым ключом. Ключ устройства не показывается администратору и не попадает в QR. `admin` получает весь `NodeService`, кроме `Backup` (в базе все закрытые ключи), `GetDeployment` и `GetDeployInputs` (ключей в них нет, но план ставит только root на ноде, R4-33); то, что меняет хост (`apply`, `update`, `uninstall`), остаётся за `rayctl` на ноде. Аудит пишет `<пользователь>/<устройство> (remote)`. `rayctl` сам служит клиентом: `remote enroll`, затем `rayctl -remote FILE <команда>`. Доступ к API изнутри туннеля (H-2) пока не сделан: порта за SPA хватает. |
| R2-13 | *Заменено R2-15.* **TCP 443 делится через сайт, пока нет tcpmux.** REALITY отдаёт всё, что не его клиент, процессу сайта. Сайт читает ClientHello, не завершая TLS, и по SNI передаёт поток, ещё зашифрованный, в сокет службы (`routes.json`; сейчас — DoH в `rayd`). Остальное сайт обслуживает сам (R4-8), не TLS закрывает без ответа. У сайта по-прежнему нет сети: только unix-сокеты. |
| R2-14 | **naive (h2) — свой процесс `rayd naive` за сайтом.** Inbound naive из форка sing-box отвечает неавторизованным `407` и рвёт соединение, а SPEC §3.7 требует сайт, поэтому сервер свой, на Go. HTTP/2 CONNECT с `Proxy-Authorization: Basic` (имя любое, пароль — учётные данные пользователя с ротацией, R4-1) и паддингом naive: заголовок `Padding`, первые 8 кадров в каждую сторону — как у NaiveProxy и inbound sing-box. Всё остальное получает ответ сайта, без `407`: не CONNECT, без паддинга, без пароля или с неверным, HTTP/1. Это пустой `404` по умолчанию, `403` или `silent`; в режиме `pages` — `404`, страницы только у сайта. TCP 443 общий с REALITY: фронт передаёт соединения с именем naive его процессу (R2-15), TLS 1.3 только с `X25519MLKEM768` с сертификатом сайта завершает сам процесс. У процесса свой пользователь и нет capabilities; выходит он только в интернет: адреса самой ноды, loopback, частные, link-local, CGNAT и multicast отклоняются в коде (по адресу после резолва) и через `IPAddressDeny` systemd. Пароли лежат в файле хешами SHA-256. При ротации rayd переписывает файл, процесс перечитывает его сам — без перезапуска и обрыва соединений. naive-quic (UDP 443) ждёт udpmux, как DoH3. |
| R2-15 | **TCP 443 — за фронтом niko-server (tcpmux, v0.2).** Фронт слушает 443 и по SNI из ClientHello выбирает бэкенд, поток не трогает. REALITY (Xray) слушает unix-сокет с `acceptProxyProtocol`, и фронт пишет туда заголовок PROXY v2: Xray видит адрес клиента, а `CAP_NET_BIND_SERVICE` остаётся только у фронта. DoH (`rayd`) и naive (`rayd naive`) получают от фронта сам принятый сокет: `SCM_RIGHTS` по `SOCK_SEQPACKET`, вместе с уже прочитанным ClientHello (IPC.md, режим `fd`). Их сокеты лежат в каталогах с группой фронта, и обе стороны сверяют `SO_PEERCRED`. Неизвестное имя и ClientHello без имени идут в REALITY, а тот отдаёт чужих сайту (R4-8). Не TLS и тишина дольше 5 с — закрыть без ответа. Маршрутизация через сайт (R2-13) убрана: у сайта снова только свой сокет. Без фронта (`FrontTCP` выключен — только тесты) REALITY слушает свой порт сам, а DoH и naive не обслуживаются. Включается вместе с закреплением niko-server v0.2: со старым фронтом нода с REALITY не поднимет 443. |

## Решения R4

| ID | Решение |
|---|---|
| R4-1 | **Ротация учётных данных пользователей с перекрытием.** Каждые 30 дней у пары «пользователь — сервис» (UUID для REALITY и `inner`) появляется следующий секрет: за 3 дня до перехода он попадает в подписку как `next` с моментом `from`, и сервер уже принимает его; в момент перехода он становится текущим, а прежний принимается ещё 2 дня. Сервер (Xray) получает действующие секреты через API, без перезапуска. С v0.23.0 у каждого секрета своё имя на всю жизнь (`u<id>-<отпечаток>`, traffic-limit-v1 §2.6): переход не меняет пользователей Xray и users-файлы и не рвёт соединений. Следующий круг отсчитывается от перехода; после долгого простоя ноды переход не раньше чем через полный срок публикации. Сроки — флаги `rayd serve` (`-cred-period`, `-cred-lead`, `-cred-grace`). Внеплановая ротация с тем же перекрытием — при отзыве устройства с `-overlap` (R4-43, v0.31.0). |
| R4-2 | **Удаление без следа.** Перед каждым изменением системы `rayctl install`/`apply` записывают его в журнал установки (`/var/lib/raycontrol-install`, только root): какие файлы созданы, а какие заменены (оригинал сохраняется), созданные каталоги, пользователи, группы, включённые юниты, прежние значения sysctl, прежняя цель `/etc/resolv.conf`, файлы зон firewalld и правил ufw до изменения, установленные бинарники и пакеты bootstrap. `rayctl uninstall` возвращает всё в обратном порядке и удаляет журнал; `-keep-state` оставляет базу, `-purge-packages` удаляет пакеты, поставленные bootstrap (по умолчанию остаются: ими могли начать пользоваться). Без журнала (старые установки) удаляется то, что raycontrol заведомо создаёт. Тест установки на каждой системе сравнивает снимок системы до установки и после удаления: пользователи, группы, хеши всех файлов `/etc`, ссылки, включённые юниты, правила nftables, sysctl, файрволы. |
| R4-3 | **Журналы без активности пользователей**: на обычном уровне нет адресов клиентов и устройств; подробности — только в режиме отладки на время разбора ([observability.md](design/observability.md)). |
| R4-4 | **Отчёт для issue** — `rayctl report`: только открытые данные и очищенные журналы, случайный ID на отчёт, ничего не отправляет сам. |
| R4-5 | **Телеметрии нет.** Нода ничего не отправляет по своей инициативе. |
| R4-6 | **Обезличенные пользователи**: без имени пользователь получает непрозрачный номер `u-xxxx-xxxx`; нода не хранит персональных данных. |
| R4-7 | *Перекрытие ключей — R4-19.* **Ротация REALITY эпохами, только self-steal для имён.** У Xray один закрытый ключ на inbound, поэтому ключи не перекрываются: раз в 90 дней (`-reality-period`) нода заводит следующий набор — ключи X25519 и ML-DSA-65, зерно ML-KEM-768 второго слоя, shortId и, если REALITY ворует у своего сайта, новое имя — и за срок публикации (`-cred-lead`, 3 дня) до перехода кладёт его в подписку как `next`. В момент `from` (с точностью до минуты) нода переключается и перезапускает REALITY; прежний набор после перехода не работает, клиент, не успевший обновить подписку, обновляет её (подписка от REALITY не зависит). Имя меняется только на случайный поддомен собственного домена ноды: чужие сайты не ищутся и не сканируются, соседние адреса тоже. Новое имя берётся, только если оно уже указывает на ноду (wildcard `*.<domain>`), и публикуется, когда сертификат сайта покрывает оба имени (менеджер сертификатов просит оба; если новое не выходит, старое всё равно продлевается); не успел за сутки (`-reality-prepare`) — меняются только ключи. Сайт переезжает на новое имя вместе с REALITY; старое имя остаётся в сертификате до продления. `rayctl service rotate NAME` переносит переход на «через срок публикации», `-now` — немедленно (утечка ключей, блокировка имени). Если в одном профиле ждут и смена UUID (R4-1), и смена ключей, `next` описывает ближайшую; следующий UUID в ссылке со сменой ключей ставится сразу, сервер принимает его с момента публикации. **С v0.29.0 (R4-42, п. 4)** имя при плановой смене меняется по умолчанию только под wildcard-сертификатом (сертификат сайта — `*.<домен>` или токен Cloudflare, DNS-01): при HTTP-01 новое имя попадало в журналы CT при заказе, за 3–4 дня до перехода, в одном списке с постоянными именами naive, DoH и `hy2-masq`. По ревью: заказ по команде идёт сразу и мимо выдержки после неудач; настройки и секреты подписка читает одной транзакцией; перезапуск после смены ключа не теряется — он записан долгом на диск до `systemctl`, повторяется каждым `apply` и виден ошибкой в `rayctl status`, а `rayd naive` и `rayd site` через 30 с с цепочкой на чужой ключ выходят сами, чтобы юнит поднял их с новым; `rayctl restore` сразу ведёт `seq` подписки от часов. Свой сертификат оператора (R4-23) и нода без ACME пинов не получают: нода не может обещать ключ следующего сертификата; импорт — только root; поверх пинов с другим ключом он отрезает клиентов до новой подписки и потому требует `-force`. У выпущенного клиента кода под ошибку пина нет: новую подписку приносит сторож рабочего профиля, на ближайшей проверке соединения (до ~10 минут) и только когда отказал рабочий профиль. `hy2-obfs` не меняется. Новый ключ процессам приходит только с перезапуском (копия при старте, R2-9). Бэкенды niko-server под тем же сертификатом (`hy2-masq`, Yggdrasil) при продлении по-прежнему перезапускаются, хотя закреплённый niko-server v0.17.0 берёт новую цепочку сам (`TestRenewedChainWithNikoServer`): `apply` их пока не щадит, это следующий шаг (spec §12). Остальные устройства переходят со следующей подпиской без разрыва; данные отозванного действуют lead + grace (5 дней). **Почему так:** украденный телефон должен быть отрезан за секунды, и разрыв остальных устройств до их подписки — приемлемая цена; при плановой замене разрыв ничего не даёт (устройство отдано сознательно или не работает), а перекрытие держит остальные устройства пользователя в работе. **Уже идущая ротация:** `next`, опубликованный до отзыва с `-overlap` (планом или прежним таким отзывом), отозванное могло взять — он заменяется свежим, lead начинается заново; клиент, уже перешедший на прежний `next`, возвращается к `link`. **Отзывы с `-overlap` подряд** каждый раз заменяют `next` и перезапускают lead, но переход не позже чем через 2·lead после первого отзыва, который пережил текущий секрет (отзыв без перекрытия меняет данные в свою же секунду и в цепочку не входит, а отзыв в секунду перехода, после него, входит: новый текущий он знал как `next`; переход никогда не раньше заменённого `next`): что знало любое отозванное так устройство, принимается не дольше 2·lead + grace после его отзыва (8 дней по умолчанию), после последнего в цепочке — не дольше lead + grace. Граница держится, пока rayd работает с теми же флагами: пока он остановлен, ничего не переходит (плоскость данных принимает то, что у неё есть), а меньший `-cred-lead` после перезапуска переносит переход раньше заменённого `next`; переход ротации, начатой таким отзывом (есть устройство пользователя, отозванное после того, как текущий секрет стал текущим), запоздавший из-за простоя, принимает прежний секрет grace после своего времени (`next_from`), а не после хода цикла; плановый переход (R4-1) — как прежде, grace от хода цикла: клиенты, не взявшие подписку, пока rayd стоял, ещё на прежнем. И ещё предел: отзыв в ту самую секунду перехода, после него (цикл прошёл в эту секунду), считается в цепочке, пока есть `prev`; после grace цикл его снимает, и такой отзыв уже не отличить от отзыва без перекрытия в его собственной секунде — для него граница 3·lead + grace; поздний отзыв цепочки даёт остальным меньше lead (не успевшее устройство идёт по `link`, это `prev` на весь grace, и берёт подписку). **В обоих режимах:** ключи самого устройства уходят сразу (SPA, сертификат API, метка dnsauth, ключ Yggdrasil устройства, токен DoH); секрет DoH не трогается (R4-37); ключ LAN новый сразу (у пароля multicast перекрытия нет, а отозванное может быть в той же Wi-Fi), с `-overlap` `lan.next` — для свежего UUID; повторный отзыв ничего не меняет; пользователь без данных — ничего. `-overlap` доступен и admin-устройствам через `-remote`: он не шире отзыва без него — устройство отзывается так же, а данные отозванного уже у того, кто его держит. `rayctl` предупреждает, если устройство было последним активным у пользователя (перекрытие тогда только продлевает отозванному время), а повторный отзыв говорит, до какого времени то, что оно знало, ещё принимается. **`-cred-period 0`:** плановой ротации нет, но `-overlap` ротирует так же — цикл rayd теперь работает и без периода (только переходы и сроки), `-cred-grace` меньше 12 ч там поднимается до 12 ч, `-cred-lead` меньше нуля или от 30 дней становится 3 днями; lead и grace rayd задаёт хранилищу при каждом старте (отзыв берёт их из памяти) и пишет в базу вместе с периодом (`settings.cred_rotation`: для хранилища без rayd; откат и обновление назад читают оттуда период), так что отзыв и цикл идут по одним значениям. **API и аудит:** `RevokeDeviceRequest.overlap`, `RevokeDeviceResponse.switch_at` — только при `overlap`, `until` — при `overlap` и у повторного отзыва, пока то, что знало устройство, ещё принимается (node.v1, добавления); Поэтому везде, где на ноду встают бинарники `rayd` до v0.31.0 (выпуск старше или сборка без номера), `rayctl` перед установкой смотрит период в базе (`settings.cred_rotation` — флаги, с которыми rayd стартовал последний раз: поменяв флаги в юните, перезапустите rayd до возврата; отрицательный период rayd хранит как 0, а прочитанный — считается за 0; записи нет или она не читается — тоже 0, то есть обновление: лишнее безвредно). Если он 0, `rayctl` останавливает rayd (до решения: отзыв, сделанный пока rayd работает, не должен пройти мимо) и даёт новые данные, как при отзыве без перекрытия, и новый ключ LAN каждому пользователю, у которого любая строка, кроме DoH, в ротации: есть `next` или `prev`, который ещё принимается (`prev_until` впереди), — на копии root, которую кладёт обратно; аудит `user.renew:rollback` (у отката после неудачного обновления актор `rayctl update (automatic rollback)`) или `user.renew:downgrade`. Правило простое и без краёв — ни окон, ни lead, ни секунд: без периода плановых ротаций нет, и всё, что в пути, — либо отзыв с `-overlap`, либо плановая ротация, начатая до того, как период стал 0; её пользователи тоже получают новые данные, и это безвредно (их устройства переподключаются после следующей подписки). Так решено после четвёртого ревью вместо правил окна, в которых каждый раз находился новый край (lead 0, цепочка за границей поздно в ходе цикла, lead, уменьшенный между отзывом и переходом). База другой схемы, чем у этой сборки, для этого не открывается (открытие её бы мигрировало). Ошибка после остановки rayd запускает его снова, и сообщение говорит, в каком состоянии нода; обновление назад, которое не смогло обновить данные, ничего не ставит, откат с `-no-carry` их не трогает, без него — тоже ничего не ставит. Неподтверждённым — проверка первых байт (SNI и `Host` — имя CONNECT или суффикс `inside-only`, ECH с чужим внешним именем — отказ) и выключатель администратора «имена списка на любом адресе»: только по AS, подсетям и провайдерам `cdn:` той же записи (против висячих CNAME), с ценой — фронтинг на CDN, которые его не закрыли (22 из 30 в измерении WWW '24). `connect-udp` — всегда `200` сразу, датаграммы вне политики отбрасываются молча; UoT и ICMP — `403`. **Ядро relay:** два UID — сокеты, которые вход делает сам, ограничены подсетями; соединения подтверждённых набирает и пересылает отдельный помощник под своим UID: он сам выдаёт nonce и проверяет доказательство app-attest по ключам устройств, ведёт сессию 9 минут, которую продлевает только новое доказательство клиента, дескрипторов входу не отдаёт и с концом сессии закрывает её соединения (взломанный вход пользуется подтверждённой сессией не дольше 9 минут после ухода клиента); обоим — политика выхода (сам relay, адрес выхода, который пускает relay без SPA, локальные сети, SMTP, BitTorrent). Метка сокета отвергнута: ей нужен `CAP_NET_ADMIN` (на Rocky 9) или `CAP_NET_RAW`, а у data plane возможностей нет.
