# raycontrol: минимальная версия клиента (client-min-v1)

Статус: **черновик** (2026-11-18, сервер). Порядок владельца: до MVP, первым из продуктовых направлений. Нужны ответы
клиента (§9) — до реализации.

Зачем: владелец ноды задаёт минимальную версию приложения. Старое приложение получает от ноды «обновись» и путь
обновления через ту же ноду, но не профили. Нода не делает вид, что запрещает больше, чем может (§7).

## 1. Заголовок `X-Raycontrol-Client`

```
X-Raycontrol-Client: niko/1.59.0 (android; arm64-v8a)
```

- Грамматика: `<продукт>/<версия>`, затем по желанию ` (<платформа>; <ABI>)`. Продукт — `[a-z][a-z0-9-]{0,15}`,
  версия — semver 2.0 без `+build` (`1.59.0`, `1.59.0-rc.1`), всё вместе до 128 байт ASCII. Платформа и ABI нода
  не разбирает и не хранит.
- Клиент шлёт заголовок в каждом запросе к ноде и к её relay: `GET /sub/v1`, `/app/v1/…`, замер канала (probe-v1) и
  `Register` удалённого API (метаданные `x-raycontrol-client`).
- Ноды до client-min-v1 заголовок не читают: слать его можно сразу, ещё до MVP. Тогда к MVP нода уже видит, кто
  остался на старых версиях (§5).
- Неразборчивый заголовок — то же, что его нет (§4, `unknown`). Ошибки разбора нода не пишет в журнал с адресом.

## 2. Политика ноды

```
rayctl client                                  # политика и сколько устройств на каких версиях (§5)
rayctl client min niko 1.59.0                  # с этой минуты
rayctl client min niko 1.59.0 -from 2027-01-15 # с даты (UTC, полночь); до неё — только предупреждение
rayctl client min niko 1.59.0 -unknown refuse  # и без заголовка — тоже отказ (§4)
rayctl client min niko none                    # снять
```

- Политика — на продукт (`niko`), одна версия на продукт. По умолчанию политики нет, `-unknown allow`.
- Хранится в базе rayd, входит в резервную копию; удалённый API — роль `admin` (api-v1).
- Сравнение по semver 2.0: pre-release ниже релиза (`1.59.0-rc.1` < `1.59.0`), числа сравниваются как числа.

## 3. Поле `client` в payload подписки

Необязательное поле subscription-v1 §3 (подписано, как весь payload):

```json
"client": {"v": 1, "min": {"niko": "1.59.0"}, "from": 1768435200, "refused": true}
```

| Поле | Смысл |
|---|---|
| `min` | минимальные версии по продуктам; есть, пока есть политика |
| `from` | с какого момента действует; нет — уже действует |
| `refused` | только в ответе устройству, которому отказано (§4); иначе поля нет |

Нет поля `client` — политики нет или нода старше.

## 4. Ответы

| Случай | Ответ `/sub/v1` |
|---|---|
| Политики нет | как сейчас, поля `client` нет |
| Версия ≥ `min` | как сейчас и `client.min` для сведения |
| Версия < `min`, `from` впереди | как сейчас и `client` с `from`: клиент заранее показывает «нода с <дата> потребует Niko ≥ X» |
| Версия < `min`, `from` наступил | **200**, подписано, `profiles: []`, `client.refused: true`, `expires` не дальше часа. `app`, `relays`, `spa` остаются: обновиться можно через ноду. Без `next`. Клиент **оставляет** строки профилей (как при `traffic.exhausted`) и показывает «Нода требует Niko ≥ X» с кнопкой обновления |
| Заголовка нет, `-unknown allow` | как сейчас; что сказать старым клиентам, владелец пишет в `note` (его показывают клиенты с raycontrol v0.21.0) |
| Заголовка нет, `-unknown refuse` | как «версия < `min`». Включать только после ответа клиента на §9.1: иначе старые версии могут удалить профили |

- Почему 200, а не 426: любой ответ, кроме 200, клиент считает временной ошибкой — держит кэш, повторяет и ничего не
  показывает. Подписанный 200 нельзя подделать по пути, и он повторяет готовый образец `traffic.exhausted`.
- `/app/v1` версией **не ограничивается никогда**: это выход для старых клиентов (app-update-v1).
- `Register` удалённого API при версии < `min` (после `from`) — `FailedPrecondition` с текстом
  `client too old: min niko 1.59.0`; без заголовка — по `-unknown`.
- Замер канала (probe-v1) версией не ограничивается.

## 5. Что нода видит

- Нода хранит у устройства последнюю версию из заголовка (продукт и версию, без платформы) и время, когда её видела,
  — только после проверки `Authorization`. `rayctl device list` показывает её, `rayctl client` — сколько устройств на
  каких версиях за 30 дней. Это новые данные на ноде; в журнал версия не пишется.
- Метрики (`rayctl metrics`): `raycontrol_client_devices{product, version}` — число устройств, без имён.

## 6. Обязательное обновление: `UPDATE.json` в релизе клиента

Минимальную версию на ноде ставит её владелец; «это обновление обязательно» говорит выпуск самого клиента, ключом его
релиза. Trusted comment подписи остаётся ровно `niko <tag>` (app-update-v1 §2), поэтому флаг — отдельный файл в
`SHA256SUMS`:

```json
{"v": 1, "mandatory": true, "min_supported": "1.59.0", "message": {"en": "…", "ru": "…"}}
```

- Подлинность — через `SHA256SUMS` и его подпись. Зеркало ноды держит все файлы из `SHA256SUMS` (app-update-v1 §3):
  ноде ничего менять не нужно.
- Клиент: `mandatory` или своя версия ниже `min_supported` — обновление без кнопки «позже».

## 7. Чего нода запретить не может

- Data plane (VLESS и REALITY, Hysteria2, naive, dnstt, masterdns, slipstream, Yggdrasil) и стук SPA версию
  приложения не несут. Устройство с сохранёнными учётными данными работает до ближайшей ротации: UUID раз в 30 дней
  и 2 дня перекрытия (R4-1), ключи REALITY (R4-19), пароли naive. Отказанным нода не выдаёт `next`, и они отпадают
  на ротации.
- Сразу — только `rayctl service rotate <svc> -now` (новые клиенты получат новые ссылки по подписке) или
  `rayctl device revoke`.
- Заголовок подделывается: это не защита, а способ сказать честному старому клиенту «обновись». Проверку подлинности
  приложения решает app-attest-v1.

## 8. Совместимость

- Нода без client-min-v1: заголовок не читает, поля `client` нет.
- Клиент без client-min-v1: заголовка нет — `-unknown` (по умолчанию allow); поле `client` клиент не знает и
  пропускает.
- Тег и формат выпусков клиента прежние (`vX.Y.Z[-rc.N]`), ключи minisign и подписи APK те же: иначе ни зеркало, ни
  Android обновление не примут.

## 9. Вопросы клиенту

1. Что делают выпущенные версии Niko на `200` с `profiles: []` без `traffic.exhausted`: оставляют строки профилей
   или удаляют их? От этого зависит, можно ли когда-либо включать `-unknown refuse`.
2. С какой версии клиент шлёт заголовок, и какой номер у MVP. Он должен быть выше последнего выпущенного (1.58.0):
   клиент предлагает только строго более новую версию.
3. Строка платформы: `android; arm64-v8a`, `windows; amd64` — так или иначе.
4. `UPDATE.json` в `SHA256SUMS` — подходит, или флаг удобнее держать иначе.
