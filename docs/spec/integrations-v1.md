# integrations-v1: внешние системы у ноды (боты, биллинг)

Статус: **этапы 1, 1b, 2 и 3 в коде, не выпущены** (2026-11-19): роли `billing` и `support` (§2.1–§2.3), аудит
(§2.5), пределы частоты (§2.6), предохранитель массовых действий и учёт трафика (§2.4), заметки для `support` (§2.2),
`GetUser`, `SetUserExpiry`, `GetIntegrationSettings`, `SetIntegrationSettings` (§10), `rayctl device invite -role
billing|support`, `user expires`, `integration`, `traffic counting` (§11); этап 2 — статические адреса (§3.2–§3.4):
`SetDeviceAllow`, `device invite -allow`, `device allow`, наборы `integ4`/`integ6`, проверка адреса на каждом
вызове; этап 3 — OpenAPI ролей (`api/openapi/billing.openapi.yaml`, `support.openapi.yaml`, §5.1) и `rayctl remote
export -pem` (§5.2). Без событий: администратору о предохранителе пока только аудит `api.mass`, метрика и `rayctl
integration status`. Дальше — события (§4).
Решение владельца 2026-11-16 (цитата — §13; [decisions](../decisions.md) R4-47). Вопросы §14 владелец закрыл 2026-11-16: «в целом по рекомендации».
Основа: удалённый API — [api-v1](api-v1.md) (R3-3), стук — [spa-v2](spa-v2.md), уведомления — webhook (K-2),
журналы доступа выключены (D-12), лимиты — [traffic-limit-v1](traffic-limit-v1.md) и
[conn-limit-v1](conn-limit-v1.md), что получает пользователь — [subscription-v1](subscription-v1.md). Пометка
«(вывод)» — не проверено ни кодом, ни тестом.

Зачем: Telegram-бот, бот WhatsApp Business или чужой биллинг сегодня подключаются к ноде только так:
`rayctl -remote <файл admin-устройства> -json …` со своего хоста. Это плохо по трём причинам:
- `admin` — вся власть: сервисы, ключи, обновление, relay, другие администраторы;
- перед каждым соединением нужен стук SPA, а серверу биллинга его некому делать;
- нода не сообщает о событиях: истёк срок, кончился трафик, зарегистрировано устройство. Интеграции остаётся опрашивать.

Здесь — стандартный способ: две узкие роли на тех же mTLS-устройствах, доступ без стука для серверов с постоянным
адресом, исходящие события по Standard Webhooks и описание OpenAPI для тех, кто ходит обычным JSON по HTTP.

## 1. Коротко

- **Роли** `billing` и `support` — устройства, как `admin`: ключ клиентского сертификата, пин на ноде, приглашение
  `rayctl device invite … -role billing` (§2.1). `billing` ведёт обычных пользователей: создаёт, включает,
  выключает, задаёт срок, лимит трафика и сервисы, удаляет, выдаёт приглашения, читает счётчики. `support` только
  читает, без секретов. Ни одна не трогает сервисы, ключи, настройки ноды, обновление, копии, relay, аудит,
  администраторов и другие интеграции (§2.3, §2.4).
- **Доступ** (§3): (а) SPA, как сейчас, с `rayctl knock -keep` или своей реализацией стука по spa-v2; (б) список
  постоянных адресов у устройства вместо SPA. mTLS остаётся в обоих.
- **События** (§4): нода сама шлёт POST по [Standard Webhooks](https://www.standardwebhooks.com) (заголовки
  `webhook-id`, `webhook-timestamp`, `webhook-signature`). Подпись — Ed25519 (`v1a`): у получателя только открытый
  ключ. HMAC (`v1`) — только по явному выбору. Адрес начинает получать события только после проверки (§4.6).
  Доставка — хотя бы раз, с повторами и очередью на ноде. Без входящего порта — опрос `ListEvents` (§4.9). В
  событиях нет ни адресов, ни назначений, ни ключей. По умолчанию включены только служебные события (§4.3).
- **OpenAPI** (§5) — подмножество `billing` и `support` из тех же proto, генератором `protoc-gen-connect-openapi`.
  Вызов — обычный `POST` JSON с клиентским сертификатом.
- **Секреты** (§6): на ноде — пины устройств (и ключи SPA, как у всех устройств) и ключи подписи событий; токены
  Telegram и WhatsApp и ключ устройства — только у интеграции.
- **По умолчанию выключено всё**: нет ни событий, ни устройств интеграций, ни списков адресов, пока их не заведёт
  администратор (§10).
- **Не в v1** (§14): пределы соединений на пользователя для тарифов, интеграция через локальный сокет ноды, режим
  опроса команд (§8).

## 2. Роли

### 2.1 Роли и как их выдают

| Роль | Для чего | Ответ содержит секрет? |
|---|---|---|
| `admin` | как сейчас (api-v1 §5) | да: `ExportUser`, `CreateDevice`, `CreateInvite` |
| `billing` | жизненный цикл обычных пользователей | только приглашение (`CreateInvite`) |
| `support` | смотреть: состояние ноды и пользователей | нет |
| `user` | устройство пользователя, API ему нужен только для `Register` | — |

Выдача — только приглашением, как у `admin`: ключ рождается на хосте интеграции и ноду не покидает.

```
rayctl user add integrations -services ""          # служебный пользователь без сервисов
rayctl device invite integrations billing -role billing [-allow 198.51.100.7,2001:db8:7::/64] [-ttl 1h] [-pin]
# на хосте интеграции:
rayctl remote enroll 'RCINV2:…' -o billing.rcdev   # файл устройства 0600: rcdev1 и PEM ключа (api-v1 §4)
```

- Приглашение с ролью `billing` или `support` делают root и группа `raycontrol` на ноде и admin-устройства.
  `CreateDevice` с этими ролями — `invalid_argument`: без клиентского сертификата устройству API не дать.
- **Пользователь устройства интеграции — без сервисов.** Нода отказывает (`failed_precondition`) в приглашении для
  пользователя с сервисами и в `SetUserServices` пользователю с устройством или приглашением интеграции. Иначе отзыв
  такого устройства менял бы учётные данные живого человека (R4-36). У пользователя без сервисов отзыв меняет 0
  учётных данных.
- Пакет устройства интеграции, как у admin: `api` и сервис `api`, без сервисов данных. Scope SPA — только `api`, без
  подписки: она интеграции не нужна.
- Роль у устройства не меняется. Другая роль — новое приглашение и отзыв прежнего устройства.

### 2.2 Обычные и служебные пользователи

**Служебный** пользователь — тот, у кого есть неотозванное устройство или неиспользованное приглашение роли `admin`,
`billing` или `support`, или сервис вида `ssh` или `api`. Остальные — **обычные**. Неиспользованное приглашение
считается и истёкшим, пока его не отозвали и не убрала чистка: так строже.

Приглашение роли `billing` или `support`, вставленное в приложение (Niko 1.59+ называет себя в `X-Raycontrol-Client`),
нода не тратит: `Register` отвечает `failed_precondition` с деталью `InviteRole{role}` (api-v1 §4). В пакете
`rcdev1` есть `role` (spa-v2 §8): приложение отказывает и готовому пакету интеграции.

Приглашение, которое выдала интеграция, и устройство из него помечены (`by_integration`):
- такое приглашение не регистрируется, если его пользователь с тех пор стал служебным (`not_found`);
- такое устройство не получает `ssh`, `api` и `site` ни в scope SPA, ни в пакете, что бы потом ни дали его
  пользователю. Иначе `billing` выдал бы приглашение обычному пользователю, зарегистрировал его сам и после
  `ssh` у пользователя открыл бы себе SSH ноды.

`billing` и `support` видят только обычных (`support` только видит):
- `ListUsers`, `ListDevices` служебных не показывают;
- метод по имени служебного отвечает `not_found`, как для неизвестного: ни выключить администратора, ни удалить его
  пользователя, ни отозвать его устройство, ни выдать приглашение на его имя;
- проверка — в той же транзакции, что изменение;
- `CreateUser` с именем служебного — `already_exists`: имя занято, и это видно. Цена принята.
- `support` видит имена пользователей и устройств, но не `note` пользователя: там бывают личные данные (§14 п. 7). Поле
  пустое, пока администратор не разрешит: `rayctl integration set support-notes on` (root, группа `raycontrol`,
  admin-устройства; аудит `integration.set`). `billing` видит `note` всегда: обычно он его и пишет.

`billing` назначает только сервисы данных: `reality`, `hy2-masq`, `hy2-obfs`, `naive`, `doh`, `yggdrasil`, `dnstt`,
`masterdns`, `slipstream`, `olcrtc`, `openflux`, `inner`. `ssh`, `api`, `subscription`, `site` — `permission_denied`.
`SetUserServices` от `billing` меняет только сервисы данных: `site` и `subscription`, которые дал администратор,
остаются.

Числа в `GetStatus` (`users`, `active_devices`) и в `GetMetrics` — по всей ноде, для любой роли одинаковые: это
числа, а не имена. Имена циклов интеграциям приходят только видом (`acme`, `dns-zone`): в полном имени бывают сайт
и зона. В метриках `support` зона — `<вид>#<n>/zone<i>`, цикл — его вид.
Сервис пользователя попадает в scope SPA его устройств (`store.SPADevices`), так что `ssh` у пользователя открыл бы
порт SSH ноды.

### 2.4 Без повышения прав

- `billing` выдаёт приглашения только роли `user`. Ни `admin`, ни `billing`, ни `support`: `permission_denied` до
  записи. `CreateDevice` закрыт совсем. Метода, который меняет роль, нет.
- Служебные пользователи невидимы (§2.2): своё устройство, администратора и другую интеграцию `billing` не выключит,
  не удалит и не отзовёт.
- `RotateCertificate` — только свой ключ, по текущему соединению (api-v1 §6).
- Ни `billing`, ни `support` не трогают списки адресов, webhook, периметр, relay, обновление.
- **Учёт трафика.** Первый лимит на ноде включает учёт, последний снятый выключает, и оба раза Xray перезапускается:
  все соединения REALITY и `inner` рвутся (traffic-limit-v1 §5). `billing` этого не делает: вызов, который включил
  или выключил бы учёт, — `failed_precondition`. Администратор держит учёт включённым новой настройкой
  `rayctl traffic counting on` (`auto` — как сейчас).
- Где `billing` может навредить — массово выключить или удалить обычных пользователей, выдать себе приглашение `user`
  — это его роль. Ограничивают частота (§2.6), аудит (§2.5), события администратору (§4.3) и предохранитель ниже.
- **Предохранитель массовых действий** (§14 п. 6). `DeleteUser`, `SetUserEnabled {enabled: false}` и `SetUserExpiry`
  «истечь сейчас» (это то же выключение; срок не позже чем через 10 минут — тоже: часы интеграции спешат или цикл
  ошибся в периоде), а ещё выключения под другим именем — `SetUserServices` со списком без включённых сервисов (и
  пустым) и `SetUserTraffic` с лимитом меньше 1 МиБ (байты вместо гигабайт) или меньше чем на 1 МиБ выше
  израсходованного за период — от всех устройств `billing` вместе считаются за скользящий час. Сверх предела (по
  умолчанию 50 в час, удаления и выключения вместе) вызов — `failed_precondition` («over the hourly limit of mass actions: confirm»), ничего не изменено, а администратору
  уходит событие `integration.mass_action` (§4.3) и строка в `rayctl status`. Выше предела проходит только вызов с
  флагом подтверждения: новое поле `confirm_mass` в `DeleteUserRequest`, `SetUserEnabledRequest`,
  `SetUserExpiryRequest`, `SetUserServicesRequest` и `SetUserTrafficRequest`. Такой вызов
  выполняется, в аудите — с пометкой `confirm`, а событие администратору уходит всё равно (одно в час, с числом). Флаг
  ставит сам `billing`: предохранитель ловит сбой интеграции (цикл, неверная выборка), а не взлом; от взлома — событие и
  отзыв устройства (§6). Предел — настройка root на ноде: `rayctl integration set mass-limit 50` (`0` — каждое массовое
  действие с флагом). Действия администратора и root предохранитель не считает.

### 2.5 Аудит

| Кто | `actor` | Что пишется |
|---|---|---|
| admin-устройство | `<пользователь>/<устройство> (remote)`, как сейчас | как сейчас |
| `billing` | `<пользователь>/<устройство> (billing)` | каждое изменение, теми же действиями (`user.create`, `user.enable=false`, `user.traffic …`, `user.expires=<время>` — новое, `device.revoke`, `invite.create:user`; сверх предела массовых действий — с `confirm`); отказы по роли; превышения частоты; отказы предохранителя (`api.mass`) |
| `support` | `<пользователь>/<устройство> (support)` | только отказы и превышения; чтения не пишутся |
| нода | `rayd` | `user.expired` (новое, цикл сроков §4.3), смены состояния webhook |
| приглашение | `invite <id>` | `invite.app`: приглашение интеграции открыли в приложении, отказано (§2.2); не чаще строки в 10 минут |
| администратор | как сейчас | `device.allow` (§3.4), `integration.set` (заметки для `support`; предел массовых действий — только root), `integration.limits` (только root), `webhook.add`, `webhook.set`, `webhook.del`, `webhook.verify`, `webhook.rotate`, `webhook.test`, `webhook.retry`; `webhook.gone` и итог проверки адреса пишет `rayd` |

- Отказ по роли — `api.denied`, цель `<метод>`; превышение — `api.limited`; отказ предохранителя — `api.mass`. Не
  чаще строки в 10 минут на устройство и метод, с числом с прошлой строки. Неудачный вызов интеграции (не найден,
  отказ аргументу по роли) — тоже не чаще строки в 10 минут на устройство и действие. Иначе сломанная интеграция
  заполнит журнал (D-11, 90 дней). Число после последней строки ждёт следующего отказа.
- Чтения не пишутся ни у кого, как сейчас (кроме `ExportUser`). Число вызовов и время последнего — в памяти rayd, в
  `rayctl integration status` (§11). Это сервер интеграции, а не человек: D-12 о нём не говорит.
- В аудите нет ни секретов, ни адресов клиентов. Адреса из списка интеграции в `device.allow` есть: это серверы,
  которые администратор открыл сам.

### 2.6 Пределы частоты

На устройство, ведром токенов (запас, пополнение в секунду):

| Роль | Чтения | Изменения | Приглашения, отзыв, `RenewUser` | Одновременно |
|---|---|---|---|---|
| `billing` | 100, 10/с | 50, 5/с | 20, 60 в час | 4 вызова |
| `support` | 20, 2/с | — | — | 2 вызова |
| `admin` | как сейчас, без предела | | | |

- Сверх — `resource_exhausted`, вызов не выполнен. Повтор безопасен: методы `billing` повторяемы (§5.2).
- Общий предел на все устройства интеграций — 20 вызовов в секунду с запасом 200 (запас чтений `billing` и
  `support` вместе): интеграции не забирают у rayd время цикла `apply`.
- Новые пределы действуют с полного запаса: корзины всех устройств начинаются заново. Сброс пределов устройства
  убирает только его собственные, пределы роли остаются.
- `DeviceService` интеграции (`GetSelf`, `RotateCertificate`) идёт под те же пределы как чтение: у `support` нет
  изменений, а свой ключ он меняет сам.
- Неизвестный сертификат — `unauthenticated`. Новые соединения с адреса считает предел входящих периметра
  (conn-limit-v1 §6.2). Адреса из списков интеграций от него не освобождены, в отличие от адресов администратора.
- Числа таблицы — значения по умолчанию, в коде. root на ноде меняет их для роли или для одного устройства: `rayctl
  integration limits billing read=200,20/s write=50,5/s heavy=20,60/h inflight=4` или `… limits DEVICE_ID …`; `heavy` —
  колонка приглашений, отзыва и `RenewUser`; `-reset` возвращает умолчание. Хранится в `settings`, применяется без
  перезапуска, аудит — `integration.limits`. Группа `raycontrol` и admin-устройства пределы видят
  (`GetIntegrationSettings`), но не меняют: администратор с телефона не снимает ограничение с интеграции (§14 п. 10).

## 3. Доступ интеграции к API

### 3.1 Режим SPA: как сейчас

Устройство стучится своим ключом SPA, scope — сервис `api`, и подключается в течение TTL (по умолчанию 10 минут, не
больше часа; spa-v2 §6). Подходит хосту без постоянного адреса.

- **`rayctl knock -keep @billing.rcdev`** (новое): шлёт SPA и держит окно открытым: повторяет через TTL/2 со
  случайным сдвигом ±20 %, сразу — при смене адреса хоста. Проверка окна — TCP до `api.port`, не подписка. Юнит
  systemd рядом с интеграцией — пример в комплекте.
- **Своя реализация** — по spa-v2 §2–§6, формат заморожен. На один стук:
  1. `t` — время по часам хоста (NTP обязателен: допуск ±30 с). `slot`, `port(slot)`, `epoch`, `epoch_key` — spa-v2
     §2–§4.
  2. `L` — случайно в `[len_min, len_max]`. plaintext: `0x02`, BE64 `t`, BE16 TTL (0 — по умолчанию), флаги `0`,
     `n = 1`, BE16 ID сервиса `api` из `services[]`, нули до `L − 40`.
  3. `packet = nonce(24) ‖ XChaCha20-Poly1305(epoch_key, nonce, plaintext, aad = "raycontrol-spa-v2" ‖ node_id)`.
  4. UDP на `host:port(slot)`, ответа нет. Через 150–400 мс — TLS к `api.port`.
  5. Не подключилось — один повтор (слот мог смениться), затем TCP-носитель (spa-v2 §10).

  Проверка — векторы `internal/spa/testdata/vectors.json`. XChaCha20-Poly1305 есть в libsodium (PyNaCl, `sodium`
  для PHP, libsodium-wrappers для Node) и в `golang.org/x/crypto/chacha20poly1305` (`NewX`). Публичный пакет Go для
  стука (`internal/spa` снаружи не импортировать) и эталон на Python (~80 строк) — в комплекте интеграции, вместе с
  кодом (§12).
- Ограничения: облачный NAT с несколькими внешними адресами стучит с одного, а соединяется с другого. Тогда — режим
  §3.2.

### 3.2 Режим статических адресов

Для сервера с постоянным адресом: устройство получает список адресов, и периметр открывает API ему без стука.

- **Периметр.** Новые наборы таблицы `inet raycontrol`: `integ4`, `integ6` (префиксы, `flags interval`, вложенные
  сливаются, как у адресов администратора) и `integ_ports`; в цепочке `admit` после адресов администратора:
  `ip saddr @integ4 meta l4proto . th dport @integ_ports jump in_limit` (и для IPv6). Порт — только TCP `api.port`:
  ни подписки, ни сервисов, ни SSH. Предел входящих на адрес действует (§2.6): в `in_limit` исключения для этих
  адресов нет. В снимке периметра — `integ_prefixes = 14` и `integ_ports = 15`: списки устройств, которые могут
  подключиться сейчас (не отозваны, пользователь включён и не истёк), и приглашений, которыми ещё можно
  зарегистрироваться. Без включённого сервиса `api` наборы пусты. rayspa проверяет порты снимка, как остальные
  (только `tcp`/`udp`, до 65535).
- **Ноду проверяет не только периметр.** Периметр видит адрес, а не устройство. Поэтому rayd на каждом вызове
  сверяет адрес источника соединения (IPv4 в IPv6 — как IPv4):
  - адрес входит в список какого-то устройства → пускается только устройство, чей **собственный** список его
    покрывает, и приглашение с таким списком (для `Register`). Admin-устройство или другая интеграция с этого адреса
    — `permission_denied`, даже если стучались;
  - устройство со списком пришло с адреса не из своего списка → `permission_denied`, в аудите `api.address` (не
    чаще строки в 10 минут, без адреса источника).
  Проверка — до любого метода, в том числе `DeviceService` и `RelayService`, по спискам в базе на момент вызова.
  `Register` с адреса из чьего-то списка проходит, только если список есть у самого приглашения и покрывает адрес;
  приглашение со списком регистрируется только из него. Отказ — до проверки PIN: попытка не тратится. Так «только
  для устройств интеграций» держится на уровне вызова. Цена: администратор, который сидит за тем же
  адресом, что сервер биллинга, ходит не с этого адреса или без списка у биллинга. Тот же порт — решение владельца
  (§14 п. 5).
- **Устройство со списком не стучится.** Его ключа SPA нет в снимке периметра. Ключ в базе остаётся (столбец
  обязателен), но ничего не открывает. Включить список — перевести устройство в этот режим, `-clear` — обратно в
  SPA. Пакет и порт прежние.
- **mTLS не меняется**: клиентский сертификат, пин ноды, `X25519MLKEM768`.
- Через relay — нет: список работает только на выходе, напрямую. И отказ остальным с адреса из списка через relay
  не действует: нода видит адрес relay, а не устройства.
- Почему не отдельный порт: не нужен новый порт, `rayctl apply`, правило в firewalld/ufw (R2-2), новый пакет при
  смене режима. Отдельный порт снял бы ограничение про общий адрес, но владелец выбрал тот же (§14 п. 5).

### 3.3 IPv6

- Элемент списка — адрес или префикс: IPv4 — от `/28` до `/32`, IPv6 — от `/64` до `/128`. Шире — отказ. Сервер с
  IPv6 обычно держит `/64` и сам выбирает в нём адрес. `/64` открывает порт всем соседям в нём, но дальше их не
  пускает mTLS.
- Двойной стек — оба адреса в список. Какой из них увидит нода, решает хост интеграции.
- IPv4 в IPv6 (`::ffff:a.b.c.d`) читается как IPv4, как у адресов администратора (R4-30).
- Нельзя: собственные адреса ноды (адреса её интерфейсов), адреса relay, `0.0.0.0/8`, loopback, link-local,
  multicast, `240.0.0.0/4`, `::`. Частные сети (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7`) можно, с
  предупреждением: биллинг в одной частной сети с нодой встречается. Пересечение с адресами администратора — тоже с
  предупреждением: его устройства с этих адресов получат отказ. Relay в адресах интеграции не добавляется.
- Префикс выравнивается (`198.51.100.9/28` → `198.51.100.0/28`), повторы убираются; список из одних пустых строк —
  `invalid_argument` (снять список — `SetDeviceAllow` без адресов). Список — только у устройства или приглашения роли
  `billing` или `support` (иначе `failed_precondition`, до проверки самих адресов). Открыт порт, на котором rayd
  слушает API (первый порт сервиса `api`).
- Не больше 8 элементов на устройство и 64 на ноду. Только адреса, не имена: имя молча сменило бы адрес.

### 3.4 Управление и аудит

```
rayctl device allow ID 198.51.100.7,2001:db8:7::/64   # список (заменяет прежний); устройство — в режим адресов
rayctl device allow ID -clear                          # обратно в режим SPA
rayctl device list                                     # ROLE, ACCESS: spa | static (2), LAST CALL у интеграций
```

- Меняют root, группа `raycontrol` и admin-устройства (`SetDeviceAllow`), как адреса администратора. `billing` и
  `support` — нет.
- Аудит — `device.allow`, цель `<id> <пользователь>/<устройство>: <адреса>` или `cleared`; приглашение со
  списком — `invite.create:<роль>:allow`, цель `<пользователь>/<устройство>: <адреса>`.
- Время последнего вызова устройства интеграции пишется в базу не чаще раза в час (`last_call`).
- Изменение доходит до периметра со следующим снимком (секунда-две). Открытые соединения с адреса, убранного из
  списка, живут до конца (`ct state established`, как у SPA), но каждый новый вызов по ним сверяется со списком
  (§3.2) и получает `permission_denied`.
- `rayctl status` предупреждает об устройстве со списком без вызовов 30 дней: адрес мог уйти другому (§9 п. 5).
- `GetPorts`: у строки `api` доступ `spa` или `spa,static`.

## 4. События (webhook)

Решение K-2: «Уведомления — webhook». Нода не шлёт ничего, пока администратор не добавил адрес: R4-5 («нода ничего
не отправляет по своей инициативе») это не нарушает — получателя выбирает администратор, как ACME или DNS-провайдера.

### 4.1 Формат: Standard Webhooks

[Спецификация](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md), в `main`
— «Version: 1.0.0» (§15).

```
POST /hooks/raycontrol HTTP/1.1
content-type: application/json
user-agent: raycontrol-webhook
webhook-id: msg_2b7q4mzxkc3kd5fwhjn6p2r7tv
webhook-timestamp: 1767225912
webhook-signature: v1a,<base64 подписи, 64 байта>

{"type":"user.traffic_exhausted","timestamp":"2026-12-01T10:15:00Z","v":1,"seq":1042,"node":"ams",
 "data":{"user":{"id":5,"name":"u-k3f9-x2qa","created_at":1764547200},
         "traffic":{"used":53687091200,"limit":53687091200,"since":1764547200,"reset":1767225600},
         "by":{"role":"node"}}}
```

- `webhook-id` — `msg_` и 26 символов base32 (128 случайных бит), без `.`; один на событие, при повторах тот же.
- `webhook-timestamp` — время попытки, unix-секунды; `timestamp` в теле — время события, ISO 8601 UTC, до секунды.
- Тело — JSON в одну строку, не больше 8 КиБ (у Standard Webhooks рекомендация — меньше 20 КБ). Подписывается ровно
  то, что отправлено.
- `v` — версия тела, `1`. Внутри `v` = 1 добавляются только новые необязательные поля и новые типы.
- `seq` — номер события у этого получателя, растёт без пропусков, в том числе после перезапуска rayd и по
  выброшенным событиям (§4.5). По нему получатель видит пропуски и порядок.
- `node` — метка, которую администратор дал этому адресу (`-label`). `node_id` в теле нет: его знают только клиенты
  ноды (observability §7).
- Данные «тонкие», по рекомендации стандарта: ссылка на сущность и состояние, о котором событие. Остальное
  получатель читает своим методом (`GetUser`).
- `data.user` — `id`, `name`, `created_at`. SQLite отдаёт ID удалённого пользователя снова (R4-30): пользователя
  однозначно определяют три поля, а не `id`.
- `data.by` — кто вызвал: `{"role": "admin" | "billing" | "support" | "node" | "root"}`, и `device` — только если
  это устройство, к которому привязан адрес (`-for`, §4.6). Так интеграция узнаёт эхо своих вызовов. Имён устройств
  администраторов в событии нет.

### 4.2 Подписи

- **По умолчанию — Ed25519, `v1a`.** У каждого адреса свой ключ, как советует стандарт. Закрытый
  ключ (`whsk_…`) не покидает ноду и не печатается. Открытый (`whpk_` + base64 32 байт) печатают `rayctl webhook
  add` и `list -keys`. Получателю нечего утечь: по открытому ключу событие не подделать.
- Подписывается `<webhook-id>.<webhook-timestamp>.<тело>`, подпись — base64 (стандартный алфавит, с `=`), в заголовке
  `v1a,<подпись>`.
- **HMAC-SHA256, `v1`** — по выбору (`-sig v1`), для получателя, который не умеет Ed25519: эталонные библиотеки
  Standard Webhooks (JS, Python, Go) проверяют только `v1` (§15). Секрет `whsec_` + base64 32 байт показывается один
  раз, при `add` и `rotate`. Нода хранит его открытым: ей им подписывать. Кто знает секрет, подделает событие этому
  получателю — только ему: секрет у каждого адреса свой. `v1` разрешён только явным выбором (§14 п. 1).
- Во время смены ключа заголовок несёт две подписи через пробел, новую первой (§4.6). Проверять — пока одна не
  сойдётся.
- Ключ получатель берёт из своей настройки, а не из запроса: тело `webhook.key_rotated` — только справка.

Проверка у получателя (Python, библиотека `cryptography`):

```python
import base64, time
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PublicKey

PUB = Ed25519PublicKey.from_public_bytes(base64.b64decode(WHPK.removeprefix("whpk_")))

def verify(headers, body: bytes) -> bool:
    msg_id, ts = headers["webhook-id"], headers["webhook-timestamp"]
    if abs(time.time() - int(ts)) > 300:            # допуск 5 минут, как в эталонных библиотеках
        return False
    signed = f"{msg_id}.{ts}.".encode() + body
    for item in headers["webhook-signature"].split(" "):
        ver, _, sig = item.partition(",")
        if ver == "v1a":
            try:
                PUB.verify(base64.b64decode(sig), signed)
                return True
            except Exception:
                pass
    return False
```

После подписи — дубль по `webhook-id` (§4.8).

### 4.3 События

«По умолчанию» — входит ли тип в адрес без `-events` для его аудитории (§4.6). По решению владельца (§14 п. 2)
по умолчанию включены только служебные: `user.expired`, `user.traffic_exhausted`, `device.revoked`, `service.down`,
`service.up`, `cert.expiring`, `update.available`. Остальное администратор включает у адреса сам (`-events`).

| Тип | Аудитория | По умолчанию | Когда | `data` (кроме `user`, `by`) |

| `user.deleted` | все | нет | `DeleteUser` | — |

| `user.expiring` | все | нет | за 72 ч и за 24 ч до срока, один раз на порог | `expires_at` |

| `webhook.test` | все | всегда | `rayctl webhook test` | — |

  добавлено, зарегистрировано, отозвано» и «приглашение использовано» — `device.*`; «продление» — `user.renewed`;
  «смена учётных данных» — `user.credentials_rotated`; остальное — по имени. `user.renewed` — это продление срока,
  а не RPC `RenewUser` (его событие — `user.credentials_rotated` с `reason: renew`).
- Плановая ротация учётных данных (R4-1) событий не даёт: клиенты получают её через подписку с перекрытием.
- **`service.down`** — один из признаков держится 2 минуты: перезапуск сервиса не удался и записан как должный
  (`restarts/<сервис>`); сокет статистики процесса не отвечает два опроса подряд; не проходит проверка зоны
  (`dns-zone`) или цели REALITY (`reality-target`). `check` — `process`, `zone`, `target`. **`service.up`** — все
  признаки в норме 2 минуты. Так мигание не даёт пары событий на каждый опрос.
- `integration.mass_action` включено по умолчанию сверх списка служебных: о нём владелец сказал отдельно (§14 п. 6).
  `webhook.*` — механика доставки, не события, и не выключаются.
- `billing` и `support` получают события только об обычных пользователях и их устройствах. Устройства
  администраторов и интеграций — только аудитории `admin`.
- Событие пишется в очередь в той же транзакции, что и изменение, которое его вызвало (или запись цикла о переходе):
  после сбоя rayd нет ни события без изменения, ни изменения без события.

### 4.4 Чего в событиях нет (D-12)

- Ни адресов клиентов, ни назначений, ни портов, ни ключей, ни учётных данных, ни приглашений, ни пакетов. Ни
  `note` пользователя, ни имён устройств администраторов.
- Имена — только заданные администратором или биллингом: имя пользователя (по умолчанию непрозрачное `u-xxxx-xxxx`,
  R4-6), имя устройства, имя сервиса, метка ноды. `-names off` у адреса убирает и их: остаются `id` и
  `created_at`.
- Событий о соединениях нет: ни «устройство в сети», ни «последний раз видели». События — о действиях
  администратора и биллинга и о состоянии ноды. Исключения — счётчики, которые уже есть в подписке и статусе:
  трафик (с точностью до минуты, как его пишет нода) и предел соединений (окно — четверть часа, время события —
  граница окна, как в журнале, conn-limit-v1 §7).
- Ошибки в `service.down` — без текста: в нём бывают имена и адреса (P1). Текст — в `rayctl status`.

### 4.5 Доставка

- **Хотя бы раз.** Очередь — в базе rayd (`webhook_outbox`), не в памяти: переживает перезапуск и обновление.
- **Успех** — ответ `2xx`. Тело ответа нода читает до 1 КиБ и выбрасывает.
- **Повторы** — по расписанию стандарта, с разбросом ±10 %: сразу, 5 с, 5 мин, 30 мин, 2 ч, 5 ч, 10 ч, 14 ч, 20 ч,
  24 ч (всего около 3 суток). Затем сообщение — «не доставлено»: 7 дней лежит для `rayctl webhook retry`, потом
  удаляется. Каждая попытка подписывается заново (новый `webhook-timestamp`).
- **Ответы** (по стандарту): `3xx` — ошибка, по перенаправлениям нода не ходит; `410 Gone` — адрес выключается
  (`gone`, аудит `webhook.gone`, событие адресам аудитории `admin`); `429`, `502`, `503`, `504` — замедлиться
  всем адресом, `Retry-After` учитывается (не дольше 24 ч); остальное — ошибка и повтор.
- **Порядок не гарантирован.** Пока получатель здоров, сообщения уходят по одному, по `seq`. Если не отвечает,
  пробуется только самое старое, остальные ждут; после успеха — остальные по `seq`. Сообщение, которое получает
  постоянный `4xx` (не `408` и не `429`), очередь не держит: следующее пробуется рядом с ним. Получателю: применять
  по `seq`, а не по времени прихода. Данные — состояние на момент события, так что для пользователя действует
  последнее по `seq`.
- **Предел очереди**: на адрес — 10 000 сообщений или 16 МиБ, на ноду — 50 000 и 64 МиБ. Полная — новое событие
  этому адресу не ставится. `seq` ему всё равно выдаётся, счётчик `dropped` растёт, адрес в состоянии `overflow`.
  Когда очередь опустится ниже половины, нода ставит `webhook.gap` с числом и диапазоном `seq` выброшенных.
  Получатель сверяет состояние методами (`ListUsers`, `ListDevices`). Старые сообщения ради новых не выбрасываются:
  дыра одна и непрерывная, и её видно по `seq`.
- Одно сообщение в полёте на адрес, до 4 адресов одновременно, до 8 адресов на ноде.

### 4.6 Управление и смена ключа

```
rayctl webhook add URL [-audience admin|billing|support] [-events a,b,user.*] [-sig v1a|v1] [-label ams]
                       [-names on|off] [-pin SPKI] [-pq-only] [-for DEVICE_ID] [-allow-net CIDR]
rayctl webhook add -poll -for DEVICE_ID [-audience …] [-events …] [-label …] [-names …]   # лента, §4.9
rayctl webhook list [-keys]                    # ID, аудитория, хост, события, состояние, очередь
rayctl webhook set ID [-url URL] [-events …] [-on|-off] [-for DEVICE_ID] [-label …] [-names …]
rayctl webhook verify ID                       # проверка адреса снова: код, время, итог
rayctl webhook del ID
rayctl webhook test ID                         # webhook.test сразу, вне очереди: код, время, группа TLS
rayctl webhook rotate ID [-overlap 72h | -now] [-sig v1|v1a]
rayctl webhook retry ID [-since 24h]           # снова в очередь — не доставленные за срок
rayctl webhook status [ID]                     # §11
```

- Меняют root, группа `raycontrol` и admin-устройства (методы — §2.3). `-allow-net` — только root на ноде: открыть
  частную сеть — дело хоста, как политика выхода (egress-policy-v1 §9).
- URL хранится в базе. В выводе, аудите и статусе — только хост и путь без query: в query получатели часто кладут
  свой токен.
- **Проверка адреса обязательна** (§14 п. 8). Новый адрес — `unverified`: событий ему нет, и в очередь для него
  ничего не ставится (`seq` начинается после проверки). `add` сразу шлёт проверку, ждёт ответа до 15 с и печатает
  итог; не прошла — нода повторяет её по расписанию §4.5 до трёх суток, дальше ждёт `rayctl webhook verify ID`. Смена
  URL (`set -url`) — снова `unverified`. После `rotate` проверка не нужна: в окне действуют оба ключа.
  - Запрос — `POST` на адрес, подписан, как любое сообщение (`webhook-id`, `webhook-timestamp`, `webhook-signature`),
    с заголовком `webhook-challenge: C` (`C` — 32 случайных байта в base64, новые на каждую проверку) и телом
    `{"type":"webhook.verify","timestamp":…,"v":1,"node":…,"data":{"challenge":"C"}}`.
  - Ответ — `2xx` с заголовком `webhook-challenge-response: <схема>,<base64(HMAC-SHA256(VK, C))>`, где
    `VK = HMAC-SHA256(K, "wev-v1")`, `K` — байты ключа адреса у получателя (открытый ключ после `whpk_` у `v1a`,
    секрет после `whsec_` у `v1`), `<схема>` — `v1a` или `v1`, `C` — строка заголовка как пришла. Тело ответа не
    читается.
  - Нода сравнивает весь заголовок за постоянное время с ответом по каждому действующему ключу адреса.
    Перенаправление, тайм-аут, другой код или заголовок — не прошла.
  - Это формат расширения Standard Webhooks «endpoint verification» (`wev-v1`, 2026-10-30), закреплённый как есть.
    Расширение свежее; если оно изменится, наша проверка остаётся `wev-v1`, а новое — отдельной версией.
  - Что доказывает: по адресу отвечает тот, кто поставил у себя ключ именно этого адреса, то есть согласился
    принимать события ноды. Чужой живой сервис (SSRF, поток на третью сторону) проверку не пройдёт: ключ у каждого
    адреса свой. У `v1a` ключ открытый, так что это согласие и верная настройка, а не секрет. Что получатель
    проверяет подпись каждого события, проверка не доказывает.
  - Порядок для получателя: `add` печатает ключ (`whpk_…` или `whsec_…`) → поставить его у получателя → `rayctl
    webhook verify ID`, если первая проверка прошла раньше, чем получатель был готов.
  - Лента `poll` (§4.9) не проверяется: её читает устройство по mTLS.
- `-for DEVICE_ID` привязывает адрес к устройству интеграции: отзыв устройства выключает адрес (`device_revoked`),
  а `data.by.device` показывает эхо её вызовов.
- **Смена ключа.** `rotate` заводит новый ключ. Весь `-overlap` (по умолчанию 72 ч) каждое сообщение несёт две
  подписи, новую первой: получатель со старым ключом и с новым проверяет одинаково. Затем старый ключ удаляется.
  Получателю — поставить новый открытый ключ (или секрет) в пределах окна. `-now` — без окна, при утечке. `-sig`
  меняет схему тем же путём: окно с `v1` и `v1a` сразу. Аудит — `webhook.rotate`, событие —
  `webhook.key_rotated`.

### 4.7 Сеть

- **Только исходящие, только rayd** (UID 9190). Входящего порта webhook не нужно. Data plane и его политика выхода
  (egress-policy-v1) здесь ни при чём: на ноде с `rayd serve -supervise` (тесты) политика выхода касается и rayd,
  и `local` (R4-38) закрыт.
- **Только HTTPS.** TLS 1.2 и новее. Группы — по умолчанию Go, `X25519MLKEM768` первой; `-pq-only` — только она.
  Цепочка — по встроенному списку корней ноды (R4-41, `rayctl roots`), `-pin SPKI` — получатель с самоподписанным
  сертификатом. Какая группа сработала, видно в `webhook status`.
- **Защита от SSRF.** Нода сама разрешает имя, проверяет **каждый** адрес и соединяется с проверенным адресом
  (перепривязка DNS не проходит). Отказ (`refused`), если адрес:
  - loopback, `0.0.0.0/8`, частный (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`), `100.64/10`, link-local
    (`169.254/16`, `fe80::/10`, в том числе адреса метаданных облаков), multicast, `240/4`, `192.0.0/24`,
    `198.18/15`, документационные сети, `64:ff9b::/96` и `::ffff:0:0/96` с такими адресами внутри;
  - собственный адрес ноды или её локальной сети (R4-38, `LocalNets`);
  - кроме сетей из `-allow-net` (root): получатель на соседнем хосте или на самой ноде. `http://` — только к loopback
    из `-allow-net`: трафик не покидает хост.
- Перенаправлений нет. Прокси из окружения (`HTTPS_PROXY`) не используются. Порт — любой.
- **Сроки**: соединение 5 с, TLS 10 с, весь запрос 15 с (стандарт советует 15–30 с).
- Ответ получателя не уходит ни в API, ни в аудит: `test` показывает код и время, но не тело. Ноду не превратить в
  читалку чужих страниц.
- Получатель узнаёт адрес ноды. Если он у третьей стороны (чужой хостинг ботов), эта сторона знает, какой адрес —
  нода VPN (§9 п. 7).

### 4.8 Что делать получателю

0. На запрос с `webhook-challenge` — ответить `webhook-challenge-response` (§4.6) и тело как событие не
   обрабатывать:

   ```python
   import base64, hashlib, hmac
   def challenge_response(challenge: str, key: bytes, scheme: str = "v1a") -> str:
       vk = hmac.new(key, b"wev-v1", hashlib.sha256).digest()
       return scheme + "," + base64.b64encode(hmac.new(vk, challenge.encode(), hashlib.sha256).digest()).decode()
   ```
1. Проверить подпись по своему ключу, допуск `webhook-timestamp` — 5 минут.
2. Отбросить повтор: хранить `webhook-id` хотя бы 4 суток (столько живут повторы, §4.5) или последний `seq` по
   метке ноды.
3. Ответить `2xx` сразу, обрабатывать после. `410` — если адрес больше не нужен.
4. Деньги и доступы решать по состоянию из API (`GetUser`), а не по одному событию: событие — повод посмотреть.
5. Строки из события (имена) — данные, не разметка и не ссылки (§9 п. 2).

### 4.9 Опрос событий: `ListEvents`

Для получателя без входящего порта (§14 п. 11): тот же поток событий, но его забирает само устройство интеграции.

- `rayctl webhook add -poll -for DEVICE_ID …` заводит ленту: адрес без URL, без подписи и без проверки (§4.6). Читает
  её только устройство `-for` (`admin`, `billing` или `support`). Аудитория — не шире его роли.
- `ListEvents {after_seq; limit (1–500, по умолчанию 100); wait_seconds (0–25)} → {events; next_seq}`, где `Event
  {id; seq; type; body}`: `id` — тот же `msg_…`, `body` — то же JSON-тело, что у webhook (§4.1). Один разбор для обоих
  способов.
- **Подтверждение — сам `after_seq`.** События с `seq ≤ after_seq` нода считает доставленными и удаляет. Повтор с
  тем же `after_seq` отдаёт то же самое: потерянный ответ ничего не теряет. Доставка — хотя бы раз, как у webhook.
- `wait_seconds` — длинный опрос: если событий нет, нода держит вызов до первого события или до срока. Один такой
  вызов в полёте на ленту. В пределах частоты (§2.6) это одно чтение.
- Подписи нет: подлинность — mTLS и пин ноды, как у любого вызова.
- Очередь, её предел, `seq` и `webhook.gap` — как §4.5. Не забранное за 3 суток — «не доставлено».
- Отзыв устройства `-for` выключает ленту, как адрес (§4.6).
- `rayctl -remote F events [-follow] [-after SEQ]` печатает ленту, событие на строку. Старая нода — `unimplemented`.

## 5. OpenAPI и JSON по HTTP

### 5.1 Генерация

- **Разметка.** У каждого метода `NodeService` и `DeviceService` — правило видимости
  `google.api.method_visibility`: `restriction` — роли через запятую (`"ADMIN,BILLING,SUPPORT"`), `"ADMIN"`, `"NODE"`
  (только на сокете); у `DeviceService` ещё `USER` (устройство пользователя: `Register`, `GetSelf`). У полей, скрытых
  от роли, — `google.api.field_visibility` (`"ADMIN"`). `visibility.proto` из googleapis лежит в
  `api/proto/google/api/` (Apache-2.0, файл маленький): генерация остаётся без сети, как сейчас. Изменён только
  `go_package` — на сгенерированный пакет raycontrol, чтобы не тянуть модуль googleapis (и с ним gRPC).
- **Одна разметка для прав и описания.** rayd при старте строит таблицу «метод → роли» из дескрипторов и чистит в
  ответе поля, которых роли не видно. Тесты: у каждого метода правило есть, и таблица совпадает с §2.3; метод без
  правила — только `ADMIN`; у каждого скрытого поля в правиле есть `ADMIN`; список полей, которые видят `billing` и
  `support` во всех своих ответах, лежит в `internal/api/testdata/integration-fields.txt`. Новое поле в таком ответе
  роняет тест, пока его не посмотрели и не переписали список.
- **Генератор** — [`protoc-gen-connect-openapi`](https://github.com/connectrpc/protoc-gen-connect-openapi)
  (`connectrpc.com/protoc-gen-connect-openapi`, Apache-2.0, OpenAPI 3.1). Он понимает `allowed-visibilities` и метки
  через запятую. Закреплён версией v0.30.0 в своём модуле `tools/openapi/go.mod`: в общем `tools/go.mod` его
  зависимости подняли бы `protoc-gen-go`, а с ним и весь сгенерированный Go. Свой шаблон `buf.gen.openapi.yaml`,
  основной `buf.gen.yaml` не меняется. На выходе — по одному файлу на роль (`path=`): `api/openapi/billing.openapi.yaml`
  и `api/openapi/support.openapi.yaml`. Тест `TestOpenAPIRoles` сверяет методы каждого файла с таблицей ролей шлюза.
  Набросок шаблона (точный — в репозитории):

```yaml
version: v2
plugins:
  - local: protoc-gen-connect-openapi
    out: api/openapi/billing
    opt: [services=raycontrol.node.v1.NodeService, services=raycontrol.device.v1.DeviceService,
          allowed-visibilities=BILLING, content-types=json, trim-unused-types, short-operation-ids,
          base=api/openapi/base.yaml]
  - local: protoc-gen-connect-openapi
    out: api/openapi/support
    opt: [services=raycontrol.node.v1.NodeService, services=raycontrol.device.v1.DeviceService,
          allowed-visibilities=SUPPORT;NOTES, content-types=json, trim-unused-types, short-operation-ids,
          base=api/openapi/base.yaml]
```

- `User.note` размечен `"ADMIN,BILLING,NOTES"`: в описании `support` поле есть, с пометкой «пусто, пока
  администратор не разрешил» (§2.2). Отдаёт его `support` нода по настройке `support-notes`, а не по разметке.
- `base.yaml` — `info`, сервер-заглушка `https://{host}:{port}`, схема безопасности `mutualTLS` (есть в OpenAPI
  3.1), описание пина: пин сертификатом в OpenAPI не выразить.
- Файлы лежат в репозитории и прикладываются к выпуску как `openapi-billing.yaml` и `openapi-support.yaml`, в
  подписанном `SHA256SUMS` рядом с архивами. CI пересобирает их (`scripts/gen.sh`) и сравнивает, как
  сгенерированный Go.

### 5.2 Запрос

- `POST https://<host>:<api.port>/<пакет>.<сервис>/<метод>`, `Content-Type: application/json`,
  `Connect-Protocol-Version: 1`. Тело — protojson запроса, ответ — protojson ответа. Имена полей — lowerCamelCase
  (на входе принимаются и `snake_case`), `int64` — строкой.
- Ошибка — код HTTP и `{"code": "permission_denied", "message": "…"}` (протокол Connect).
- Требования к клиенту: HTTP/2 (ALPN `h2`), TLS 1.3 только с `X25519MLKEM768`, клиентский сертификат устройства,
  проверка сертификата ноды по пину (имя не проверяется). Где библиотеки этого не умеют — шлюз §5.4.
- **Повторы безопасны**: `CreateUser` второй раз — `already_exists`; `SetUserEnabled`, `SetUserTraffic`,
  `SetUserExpiry` (время абсолютное, поэтому повтор не удваивает продление) — то же состояние; `DeleteUser` —
  `not_found`; `CreateInvite` заменяет неиспользованное (api-v1 §3); `RevokeDevice` — `already` (api-v1 §5a).
- `rayctl remote export billing.rcdev -pem billing.pem` (новое) пишет сертификат и ключ в PEM (новый файл, 0600) и
  печатает адрес и пин в виде для curl и готовый вызов. После `remote rotate` PEM устарел: экспорт заново. Своя
  реализация берёт `api.port` и `api.pin` из пакета `rcdev1` (первая строка файла устройства).

### 5.3 Пример curl

Режим SPA: сначала стук (§3.1); в режиме адресов (§3.2) его нет.

```sh
rayctl knock @billing.rcdev                    # или своя реализация стука
PIN='<api.pin пакета: base64url без =>'
curl --http2 --tlsv1.3 --curves X25519MLKEM768 \
  --cert billing.pem --key billing.pem \
  -k --pinnedpubkey "sha256//$(printf %s "$PIN" | tr '_-' '/+')=" \
  -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
  --data '{"name":"u-k3f9-x2qa","limitBytes":"53687091200","period":"monthly"}' \
  https://203.0.113.7:48213/raycontrol.node.v1.NodeService/SetUserTraffic
```

- `-k` нужен: сертификат самоподписанный, имени в нём нет. Ключ проверяет `--pinnedpubkey`. Пин ноды — base64url без
  `=`, curl ждёт обычный base64, отсюда `tr` и `=`.
- `--curves X25519MLKEM768` — curl с OpenSSL 3.5 или новее, где эта группа есть и по умолчанию (флаг делает требование
  явным). curl с OpenSSL старше 3.5 рукопожатие с нодой не завершит.
- Путь с двоеточием в `--cert` curl читает как путь и пароль ключа: двоеточие там пишется `\:` (`remote export`
  печатает так сам).
- Ответ: `{"user":{"id":"5","name":"u-k3f9-x2qa","enabled":true,"trafficLimitBytes":"53687091200",…}}`. От
  `support` тот же запрос — `403` и `{"code":"permission_denied",…}`.

### 5.4 Шлюз (для языков без PQ)

`rayctl integration gateway -device billing.rcdev -listen unix:/run/rc-billing/api.sock` (новое): рядом с
интеграцией, принимает тот же Connect JSON по HTTP/1.1 без TLS, а к ноде идёт с mTLS, PQ и пином. В режиме SPA сам
держит стук (`-keep`).
- Слушает unix-сокет с правами файла (группа процесса интеграции) или `127.0.0.1` с `-token-file`: тогда нужен
  `Authorization: Bearer`. Шлюз хранит SHA-256 токена и сравнивает за постоянное время.
- Ключ устройства остаётся у шлюза: процесс интеграции его не читает. Права у шлюза — роль его устройства, не больше.
- Смена ключа устройства (`RotateCertificate`) — через шлюз (`-rotate 90d`).

## 6. Секреты: кто что хранит

| Секрет | Где | Читает | В копии ноды |
|---|---|---|---|
| Ключ клиентского сертификата интеграции (ECDSA P-256) | хост интеграции: файл устройства 0600 или менеджер секретов; у шлюза — только у него | интеграция | нет |
| Пин этого сертификата | нода, `devices.cert_pin` | rayd | да |
| Ключ SPA устройства (режим §3.1) | файл устройства и нода (ключ симметричный, как у всех устройств) | rayspa | да |
| Закрытый ключ подписи событий (Ed25519, на адрес) | нода, база rayd (файл rayd, читают rayd и root); ни один метод его не отдаёт | rayd | да; копия зашифрована (R4-13), `Backup` — только root |
| Секрет HMAC (если `v1`) | нода и получатель | rayd | да |
| Открытый ключ `whpk_` | получатель | — | — |
| URL адреса (может нести токен получателя) | нода | rayd; в выводе — без query | да |
| Токен Telegram-бота, токен WhatsApp Business | хост бота: менеджер секретов или переменная окружения службы | бот | **никогда не на ноде** |
| Коды привязки (§7) | бот, только SHA-256 | бот | — |
| Telegram id ↔ пользователь ноды | база бота | бот | **не на ноде** |

- Токенов, которые проверяет нода, спека не добавляет. Где они появляются у интеграции (шлюз §5.4, коды §7),
  хранится SHA-256.
- **Смена ключей.** Устройство интеграции — `RotateCertificate` (`rayctl -remote F remote rotate` или шлюз), раз в
  90 дней. Ключ подписи — `rayctl webhook rotate` с окном (§4.6). Токен бота — у Telegram (BotFather), ноды не
  касается.
- **Отзыв устройства интеграции режет сразу.** `rayctl device revoke ID`: rayd ищет устройство по пину на каждом
  вызове, поэтому следующий вызов — `unauthenticated`, и по уже открытому соединению HTTP/2 тоже. Адреса устройства
  уходят из периметра со следующим снимком, допуски SPA закрываются, как у любого отзыва. Адреса webhook с `-for`
  выключаются (§4.6). Учётные данные служебного пользователя без сервисов не меняются (их нет, §2.1).

## 7. Эталонный Telegram-бот (описание)

Пример устройства, не код. Сам бот — позже, в отдельном репозитории. Для WhatsApp Business то же, с Cloud API вместо
Bot API.

**Как устроен.**
- Бот держит устройство `billing` (малый оператор: бот и есть биллинг) или ходит в свой биллинг, у которого это
  устройство. Устройство `support` боту мало: ему нужны приглашения.
- К Telegram — длинным опросом (`getUpdates`), к ноде за событиями — тоже: лента `ListEvents` (`rayctl webhook add
  -poll -for <устройство бота> -audience billing -events …`, §4.9). Входящего порта у бота нет вовсе. Свой адрес
  webhook — по желанию, тогда с проверкой (§4.6).
- Хранит (SQLite): привязки `telegram_id → (метка ноды, имя пользователя, created_at)`, коды привязки (SHA-256,
  срок, использован ли), счётчики частоты, настройки уведомлений. Не хранит: приглашений после отправки, переписки,
  телефонов, имён из Telegram. Журнал — номер команды и итог, без текста сообщений.
- Секреты: токен бота — в менеджере секретов, файл устройства — 0600 (или шлюз §5.4); со своим адресом webhook —
  ещё открытый ключ `whpk_` в настройке.

**Привязка пользователя** (одноразовый код).
1. Администратор (`/link <пользователь>` в чате из списка администраторов бота) или биллинг (метод самого бота)
   получает код: 128 случайных бит, base64url (22 символа), срок 24 ч. Бот хранит только SHA-256.
2. Пользователь получает ссылку `https://t.me/<бот>?start=<код>` любым каналом. Параметр `start` — до 64 символов
   `A-Za-z0-9_-`, код помещается.
3. `/start <код>`: бот ищет хеш, проверяет срок, привязывает `telegram_id` к пользователю и гасит код. Неверный
   код — один ответ без подробностей; 5 неверных за час с одного `telegram_id` — пауза на час.
4. `user.deleted` от ноды — бот удаляет привязку. `/unlink` — пользователь сам.

**Команды.**

| Команда | Что делает | Метод ноды |
|---|---|---|
| `/status` | включён ли, срок, «N из M ГБ, сброс …», снят ли по лимиту, сколько устройств | `GetUser`, `ListDevices` |
| `/mysub` | приглашение для своего пользователя: строка `rcinv1:` моноширинным текстом (касание копирует, Niko находит её во вставленном тексте) и QR `RCINV2:`. Срок — 1 ч. Новое заменяет неиспользованное (то же имя устройства) | `CreateInvite {role: user, ttl: 3600}` |
| `/devices` | список устройств с кнопкой «отозвать»; предупреждает: остальные устройства переподключатся (R4-36) | `ListDevices`, `RevokeDevice` |
| `/renew` | оплата вне ноды (платёжный провайдер или Telegram Stars), затем продление | у биллинга: `SetUserExpiry`, при необходимости `SetUserEnabled`, `SetUserTraffic {reset_usage}` |

- Кнопкой `rcinv1:` не сделать: кнопки-ссылки Telegram берут только `http(s)` и `tg://` (вывод).
- «Ссылка подписки» здесь — приглашение. Подписка ноды — у каждого устройства своя, по его ключу (subscription-v1
  §2). Ссылки `ExportUser` без SPA устройства пользователя не работают и несут учётные данные (R4-17): бот их не
  выдаёт.
- Приглашение — секрет, пока не использовано, а переписку с ботом видит Telegram: сквозного шифрования у ботов нет.
  Поэтому срок короткий. По `device.registered` бот пишет «зарегистрировано устройство X; если не вы — /devices» и
  удаляет своё сообщение с приглашением; по истечении срока — тоже. PIN приглашения боту ничего не даёт: он ушёл бы
  тем же каналом.
- Уведомления от событий. По умолчанию ленте достаются `user.expired`, `user.traffic_exhausted`, `device.revoked`
  (§4.3); остальное администратор включает у ленты бота сам: `-events user.expired,user.expiring,user.renewed,
  user.traffic_exhausted,user.traffic_reset,user.traffic_threshold,device.registered,device.revoked,user.deleted`.
  Без `device.registered` бот не узнает, что приглашение использовано, без `user.deleted` — что привязку пора снять.
  Текст — шаблоны бота, строки из события только подставляются.

**Частота.**
- На `telegram_id`: команда не чаще раза в 2 с; `/mysub` — 3 в час и 10 в сутки; коды — шаг 3 привязки.
- На весь бот: исходящие — в пределах Telegram (по его FAQ: не больше сообщения в секунду в один чат, около 30 в
  секунду всего), очередью; к ноде — внутри пределов `billing` (§2.6).

## 8. Режим опроса (позже, по желанию)

Набросок. У ноды нет входящего порта для API вовсе: ни SPA, ни списка адресов. Очередь интеграции — любой адрес
HTTPS, хоть статический хостинг: команды подписаны, хосту очереди верить не нужно. Но он видит их содержимое (имена
пользователей): держать у себя или шифровать открытым ключом ноды (позже).

- Интеграция выкладывает очередь команд: `GET /raycontrol/v1/commands?after=<seq>`. Команда — конверт
  `{v, id, seq, node, issued, expires, method, request}` (`request` — protojson), подписанный Ed25519-ключом команд
  интеграции. Устройство заводит администратор на ноде, с этим открытым ключом и адресом очереди: приглашение и
  порт API тут не нужны.
- Нода опрашивает адрес раз в 10–60 с, через ту же защиту исходящих, что webhook (§4.7). Проверяет подпись, `node`
  (метка этой ноды), срок (не больше 10 минут), `seq` больше последнего, `id` новый. Выполняет с ролью устройства,
  с теми же пределами и аудитом. Результат шлёт событием `command.result` `{id, seq, code, response}`.
- Цена: задержка до периода опроса; нода ходит к интеграции постоянно, и та видит её адрес.
- Опрос **событий** без входящего порта — уже в v1: `ListEvents` (§4.9). Здесь — опрос **команд**, он позже.

## 9. Модель угроз

1. **Взломан хост интеграции.** Нападающий получает ключ устройства и ровно его роль (§2.3).
   - С `billing` он может выключить и удалить обычных пользователей, выдать себе приглашение `user` (то есть доступ к
     VPN), поменять лимиты и сроки. Не может: тронуть сервисы, ключи, периметр, relay, обновление, администраторов,
     другие интеграции, прочитать учётные данные (`ExportUser`, `CreateDevice` закрыты) и аудит.
   - Подделать события ноды другим получателям не может: у них только открытые ключи (`v1a`). С `v1` — только себе.
   - Видно: аудит с `(billing)`, счётчики отказов и превышений, событие `integration.mass_action` (включено по
     умолчанию) и другие события администратору, если он их включил (`user.deleted`, `device.registered`).
     Скорость вреда ограничена §2.6, массовые удаления и выключения — предохранителем (§2.4): больше 50 в час — только
     с флагом подтверждения и с событием администратору. Лечение — отзыв устройства (§6), он действует сразу.
2. **Взломана нода.** У нападающего всё, что у ноды: ключи подписи событий (подделает события получателям), пины
   устройств, ключ TLS API (выдаст себя за ноду интеграциям). Токенов Telegram и WhatsApp, ключей устройств
   интеграций и привязок пользователей к Telegram на ноде нет. Поэтому получателю: не доверять событию в деньгах
   (§4.8 п. 4), не выводить строки события как разметку или ссылку (имя пользователя — свободный текст
   администратора), шаблоны сообщений держать у себя.
3. **Повтор события.** Попытка подписана со своим временем: допуск 5 минут. Внутри допуска повтор отсекает
   `webhook-id` или `seq` (§4.8). Перехватить по пути мешает TLS. Утечка журнала прокси получателя даёт повтор не
   дольше 5 минут, и тот отсекается.
4. **SSRF.** Адрес задаёт только администратор (`billing` и `support` не могут). Нода проверяет каждый адрес после
   разрешения и соединяется с ним, без перенаправлений и прокси. Частные сети — только явно и только root (§4.7).
   Тело ответа никуда не возвращается. До проверки (§4.6) адрес получает только сам проверочный запрос, а пройти
   её может лишь тот, кто поставил у себя ключ этого адреса: чужому живому сервису событий не слать.
5. **Адрес из списка достался другому** (облако отдало IP, общий NAT, соседи по `/64`). Он доходит до TLS порта API
   и видит, что порт открыт. Дальше — только с ключом устройства. Остаётся поверхность рукопожатия TLS и нагрузка,
   её держит предел входящих (§2.6). Списки узкие (§3.3), адреса убирать при переезде; без вызовов 30 дней — `rayctl
   status` напоминает.
6. **Злоупотребление частотой.** Пределы на устройство и общий (§2.6), предел входящих на адрес, по одному
   сообщению в полёте на адрес webhook (§4.5). Неизвестный сертификат дальше рукопожатия не проходит.
7. **Приватность.**
   - Бот знает связку `telegram_id ↔ пользователь VPN` — самое чувствительное во всей схеме: это снимает
     обезличенность (R4-6). Держать её только в боте, без резервных копий у третьих лиц.
   - Telegram (и Meta для WhatsApp Business) видит переписку бота, в том числе приглашения и состояние подписки.
   - Биллинг знает пользователей, их сроки, лимиты и счётчики трафика по периодам, имена и время регистрации
     устройств. Если он копит счётчики, история трафика появляется у него, хотя на ноде её нет (traffic-limit-v1 §6).
   - Не узнают ни бот, ни биллинг: адресов клиентов, назначений, времени соединений (кроме четверти часа у предела
     соединений), ключей.
   - Получатель webhook и хост интеграции знают адрес ноды. Третья сторона (чужой хостинг) узнаёт, что этот адрес —
     нода VPN: держать получателя у себя.
8. **Ошибка администратора** — `billing` вместо `support`, широкий список. `rayctl device list` показывает роль и
   режим, `integration status` — что устройство делает.

## 10. Совместимость

- **proto — только добавления**: CI проверяет `buf breaking` (категория `FILE`, как в `buf.yaml`) наших proto
  (`api/proto`, без копии Xray) против выпуска, от которого идёт коммит; правила видимости на прежних методах его не нарушают (против v0.33.0 проходит, удалённое поле
  ловит — проверено 2026-11-19). Добавляется:
  - `GetUser {name} → {User user}`; `SetUserExpiry {name; expires_at (0 — без срока; в прошлом — истечь сейчас)} →
    {User user}`;
  - `SetDeviceAllow {id; repeated string prefixes} → {Device device}`; у `Device` — `allow`, `last_call`;
  - методы webhook (§2.3) и их сообщения, `ListEvents` (§4.9);
  - `GetIntegrationSettings`, `SetIntegrationSettings`: пределы частоты (`Rate {burst; per_hour}`, `IntegrationLimits
    {read; write; heavy; inflight}` для роли или устройства, `to_default` — назад к умолчанию), предел массовых
    действий, заметки для `support`, учёт трафика `on`/`auto` (§2.2, §2.4, §2.6). В ответе ещё устройства
    интеграций с их вызовами с запуска rayd и массовые действия за час (§11). Учёт трафика — тоже здесь: отдельного
    метода для одной настройки не заводили;
  - `confirm_mass` в `DeleteUserRequest`, `SetUserEnabledRequest`, `SetUserExpiryRequest`, `SetUserServicesRequest` и
    `SetUserTrafficRequest` (§2.4); нода до него поле
    не читает, и предохранителя у неё нет;
  - значения `role`: `billing`, `support` (строка, поле прежнее); `role` в пакете `rcdev1` (кроме `user`);
    `InviteRole` — деталь отказа `Register` приложению (api-v1 §4);
  - правила видимости на методах и полях (§5.1).
- **База** — миграция 0017 (этап 1; дальше — следующие свободные номера): `devices` и `invites` пересоздаются с ролями в `CHECK`
  (SQLite не меняет ограничение на месте, как в 0014); `devices.allow`; таблицы `webhooks` (с видом `url` или
  `poll` и состоянием проверки), `webhook_keys`, `webhook_outbox`; отметки сроков (`user.expired`, `user.expiring` —
  один раз на значение). Настройки интеграций — ключи в `settings`.
- **Старая нода, новый rayctl**: приглашение с ролью `billing` — `invalid_argument` («use user or admin»), новые
  методы — `unimplemented`; rayctl называет версию ноды.
- **Новая нода, старый rayctl**: роль печатается как есть. `rayctl -remote` с файлом устройства `billing` работает
  на разрешённых методах. Остальные — `permission_denied`.
- **Откат** (`rayctl update -rollback`) возвращает базу до обновления: устройств интеграций, списков и адресов
  webhook в ней нет, интеграции отрезаны до нового обновления. Перенос отзывов (api-v1 §5a) их не затрагивает: у
  служебного пользователя нет учётных данных.
- **Клиент Niko** — без изменений: подписка, `rcdev1`, `Register` прежние.
- **По умолчанию выключено**: ни адресов webhook, ни лент, ни устройств интеграций, ни списков, `traffic counting
  auto`, `support-notes off`; пределы частоты и массовых действий — умолчания из кода.
  Пока администратор ничего не завёл, нода ведёт себя как v0.31.0: тот же периметр, те же порты, ни одного
  нового исходящего запроса.

## 11. rayctl, статус, метрики

```
rayctl device invite USER NAME -role billing|support [-allow ADDRS] [-ttl 1h] [-pin]
rayctl device allow ID ADDRS | -clear
rayctl device list                               # ROLE, ACCESS, LAST CALL
rayctl integration status                        # по устройствам интеграций: вызовы, отказы, превышения за сутки
rayctl integration set support-notes on|off      # §2.2: admin
rayctl integration set mass-limit 50             # §2.4: только root
rayctl integration limits [ROLE|DEVICE_ID] [read=100,10/s write=50,5/s heavy=20,60/h inflight=4] [-reset]   # §2.6: только root
rayctl integration gateway -device F -listen …   # §5.4
rayctl -remote F events [-follow] [-after SEQ]   # лента ListEvents, §4.9
rayctl knock [-keep] [-ttl 10m] @F               # §3.1
rayctl remote export F -pem OUT                  # §5.2
rayctl user expires NAME 2026-12-31|30d|never    # SetUserExpiry
rayctl traffic counting on|auto                  # §2.4
rayctl webhook add|list|set|verify|del|test|rotate|retry|status   # §4.6, лента — add -poll (§4.9)
```

**`rayctl status`** — строки:
- `webhook wh1 (billing, hooks.example.net): ok, очередь 0, доставлено 2 мин назад (204, 85 мс, X25519MLKEM768)`;
- `webhook wh2 (admin, ops.example.net): не доставляется 3 ч (503, 14 попыток), очередь 340, старейшее 3 ч`;
- `webhook wh3: overflow — 1 200 выброшено с 10:00, ждёт места` и `gone` (`410`);
- `webhook wh4 (billing, bot.example.net): не проверен — нет webhook-challenge-response (204); rayctl webhook verify
  wh4`;
- `webhook wh5 (лента integrations/bot): забрано 30 с назад, очередь 0`;
- `integration mass actions: 50 из 50 за час — отказано 12, подтверждено 0 (integrations/billing)`;
- `integration integrations/billing (billing, static 1): вызов 1 мин назад; отказов 0, превышений 0 за сутки`;
- предупреждения: устройство со списком без вызовов 30 дней; адрес webhook выключен отзывом устройства.

Цикл `webhook <id>` — на доске rayd (`GetStatus.loops`, только `ADMIN`).

**`rayctl webhook status ID`** — состояние, очередь (число, байты, возраст старейшего), последние 20 попыток (время,
`seq`, тип, код или ошибка, длительность, группа TLS), выброшенные, не доставленные. Текст ошибки — без query URL и
без тела ответа.

**Метрики** (`rayctl metrics`, только числа, R4-14; `endpoint` — ID адреса `wh1`, не URL):

- `raycontrol_webhook_deliveries_total{endpoint, result}`, `result`: `ok`, `http_4xx`, `http_429`, `http_5xx`,

  `raycontrol_webhook_oldest_age_seconds{endpoint}`;

- `raycontrol_webhook_last_success_timestamp_seconds{endpoint}`;
- `raycontrol_webhook_verify_total{endpoint, result}`: `ok`, `mismatch`, `http`, `timeout`, `tls`, `refused`;
- `raycontrol_api_calls_total{role, code}` (вызовы зарегистрированных устройств всех ролей через удалённый API,

## 14. Решения по вопросам (закрыты 2026-11-16)

Все двенадцать — «в целом по рекомендации» (§13). Открытых вопросов к владельцу нет.

1. **HMAC (`v1`)** — разрешён, только явным выбором (`-sig v1`). По умолчанию — Ed25519 (`v1a`) (§4.2).
2. **События по умолчанию — только служебные**: `user.expired`, `user.traffic_exhausted`, `device.revoked`;
   `service.down` и `service.up`, `cert.expiring`, `update.available`. Остальное выключено и включается у адреса
   (`-events`) (§4.3). Сверх списка включено `integration.mass_action`: о событии администратору владелец сказал
   отдельно (п. 6). `webhook.*` — механика доставки, не выключается.
3. **`ExportUser` для `billing`** — нет. Пользователю — только приглашение (§2.3, §7).
4. **Пределы соединений на пользователя для тарифов** — позже, не в v1: нужно менять conn-limit-v1 (там решено:
   один выключатель root без чисел, §12) и вводить уровни в Xray (§8 там же).
5. **Список адресов — на том же порту API** (§3.2). Цена — администратор за одним адресом с сервером биллинга.
6. **Предохранитель массовых действий `billing`** — да: больше предела за час (по умолчанию 50 удалений и
   выключений вместе) — отказ и событие администратору; выше предела — только с флагом подтверждения
   (`confirm_mass`). Предел — настройка root (§2.4).
7. **Что видит `support`** — имена пользователей и устройств да, `note` по умолчанию нет (там бывают личные
   данные); администратор разрешает настройкой `support-notes` (§2.2).
8. **Проверка адреса webhook обязательна** при добавлении: адрес получает события только после неё. Формат —
   `wev-v1` расширения Standard Webhooks «endpoint verification», закреплённый у нас как есть (§4.6). В первой
   редакции было «по выбору»: решение — по рекомендации, переданной владельцу.
9. **`user.expiring` и `user.traffic_threshold`** — остаются, выключены по умолчанию (§4.3).
10. **Пределы частоты** — умолчания в коде, root меняет их настройкой для роли или устройства (§2.6). В первой
    редакции было «числа в коде»: решение — по рекомендации, переданной владельцу.
11. **`ListEvents`** (опрос событий без входящего порта) — да, в v1 (§4.9).
12. **Интеграция на самой ноде через локальный сокет** (своя группа) — позже, не в v1. Сейчас — удалённый API на
    `127.0.0.1` с устройством интеграции, как с любого хоста.

## 15. Не проверено

- **Standard Webhooks.** Текст в `main` говорит «Version: 1.0.0». Последняя правка основного текста — 2025-02-16,
  расширение «endpoint verification» — 2026-10-30. Тегов и выпусков спецификации не смотрел: API GitHub отсюда
  недоступен. Заголовки, `v1`/`v1a`, `whsec_`/`whsk_`/`whpk_`, расписание повторов, `410`, SSRF — по тексту из
  `main`.
- **Эталонные библиотеки** Standard Webhooks на JS, Python и Go проверяют только `v1` (HMAC) и допускают 5 минут
  (смотрел исходники в `main`). Остальные (Java, Rust, Ruby, PHP, C#, Elixir) не смотрел.
- **Ответ на проверку адреса** (§4.6) в библиотеке Go уже есть (`EndpointVerificationResponse`), но только для
  `v1`; в JS и Python его не нашёл. Получателю `v1a` — 4 строки §4.8. Пример §4.8 по тексту расширения, не запускал.
- **`protoc-gen-connect-openapi`**: последняя версия — v0.30.0 от 2026-11-06 (прокси модулей Go). Проект переехал в
  организацию `connectrpc`: модуль `connectrpc.com/protoc-gen-connect-openapi`, тот же коммит отдаётся и по старому
  пути `github.com/sudorandom/…`, но `go.mod` v0.30.0 называет новый. До 1.0, около 300 звёзд. Разбор
  `allowed-visibilities` с метками через запятую — по исходнику (`internal/converter/visibility/visibility.go`).
  На наших proto запущен (этап 3): методы обоих файлов совпали с таблицей ролей шлюза, скрытые поля в описания не
  попали, `base.yaml` со схемой `mutualTLS` вошёл как есть. Как сторонние инструменты (генераторы клиентов, Swagger
  UI) читают `mutualTLS`, не проверял.
- **curl** проверен 2026-11-19 (curl 8.14.1, OpenSSL 3.5.7, Debian 13) на удалённом API rayd в тесте, без периметра:
  пример `remote export` (`--curves X25519MLKEM768`, сертификат и ключ из одного PEM, `-k --pinnedpubkey`) — 200 по
  HTTP/2 и JSON, чужой пин — отказ curl (код 90), метод не своей роли — 403 `permission_denied`. С OpenSSL 3.5 работает
  и без `--curves`. Через стук на настоящей ноде не запускал.
- **Поддержка `X25519MLKEM768` в HTTP-клиентах** других языков (Java, .NET, PHP, Python и Node, собранных не с OpenSSL

- Как Go-сервер с ALPN только `h2` отвечает клиенту без ALPN (HTTP/1.1 или отказ) — не проверял; спека требует
  `h2`.
