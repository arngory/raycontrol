# dnsprobe-v1: проверка резолвера для DNS-туннеля

Статус: raycontrol v0.11.1, niko-server v0.8.3. Клиент — Niko 1.33 (перебор резолверов для сети).

## 1. Зачем

DNS-туннель (dnstt, masterdns) работает только через резолвер, который:
- доводит запросы к делегированной зоне туннеля до ноды и не отвечает за неё сам;
- не кеширует ответы и не переписывает их;
- пропускает TXT и ответы того размера, который нужен туннелю.

Какой резолвер такой, зависит от сети. Клиент выбирает его сам: DNS самой сети, найденные через DDR, стартовый список
по стране ([`probe-v1.md`](probe-v1.md) §6.2, `hints.dns`). Проверка кандидата должна занимать 1–2 RTT, без сессии
туннеля. Поэтому фронт ноды отвечает на особый запрос в зоне туннеля сам, до бэкенда.

Требования:
- **Не опознаётся снаружи.** Запрос пробы выглядит как запрос туннеля: одна метка base32 под зоной. Без верного MAC
  нода обрабатывает его как любой запрос туннеля (бэкенд). Сканер делегированных зон не получает узнаваемого ответа.
- **Без dnsauth.** Проба не доходит до бэкенда, поэтому `auth=required` ([`dnsauth-v1.md`](dnsauth-v1.md)) её не
  касается: иначе при нём любой кандидат выглядел бы мёртвым.
- **Подделку видно.** Ответ несёт MAC: резолвер, который отвечает за зону сам, проверку не пройдёт.
- **Нет усиления.** Большой ответ — только по EDNS и с ограничением частоты (§5).

## 2. Ключ

`K` — 32 случайных байта, один на ноду. Нода создаёт его при первой отрисовке с DNS-туннелем. Подписка
([`subscription-v1.md`](subscription-v1.md) §3) несёт его пользователю, у которого есть профиль dnstt или masterdns:

```json
"dns_probe": {"v": 1, "key": "<base64url без дополнения, 32 байта>"}
```

Ключ знает любой пользователь ноды. Он открывает только пробы: ни сессий туннеля, ни SPA.

## 3. Запрос

```
QNAME  = <метка> "." <зона туннеля>      (зона — из ссылки dnstt или masterdns)
QTYPE  = TXT (16), QCLASS = IN (1)
EDNS   = OPT с размером UDP 1232 (для большой пробы обязателен, §4)
```

`<метка>` — base32 (RFC 4648, алфавит `a-z2-7`, нижний регистр, без `=`) от 24 байт, то есть 39 символов:

| Байты | Поле |
|---|---|
| 0 | версия, `1` |
| 1 | размер ответа: `0` — малый, `1` — большой |
| 2–5 | минута: `unix_seconds / 60`, uint32 big-endian |
| 6–13 | nonce, 8 случайных байт, новый на каждый запрос |
| 14–23 | `HMAC-SHA256(K, "dnsprobe-v1 q" ‖ zone ‖ байты 0–13)[:10]` |

`zone` — зона туннеля строчными буквами, без точки в конце, в ASCII. Регистр метки нода не различает: резолверы
меняют его (0x20).

Нода считает запрос пробой, если:
- под зоной ровно одна метка, 39 символов, и она декодируется в 24 байта;
- версия `1`, размер `0` или `1`, QTYPE TXT;
- MAC верен;
- минута отличается от текущей не больше чем на 2;
- nonce за последние 5 минут не встречался.

Иначе это обычный запрос туннеля: он идёт в бэкенд как есть.

## 4. Ответ

`NOERROR`, флаги `QR`, `AA`, `RD` из запроса. Вопрос повторён. Одна запись:

```
NAME = указатель на QNAME (0xC00C), TYPE = TXT, CLASS = IN, TTL = 0
RDATA:
  строка 1: "v1 " ‖ base32(HMAC-SHA256(K, "dnsprobe-v1 a" ‖ 24 байта метки)[:16])   (3 + 26 = 29 символов)
  строка 2: "seen edns=<N> case=<0|1> from=<адрес>"   — что увидела нода
  большой ответ, ещё 4 строки по 240 байт: "0123456789", повторённое 24 раза
```

- **Строка 2** — что нода увидела от резолвера:
  - `edns` — размер UDP из OPT запроса, `0` без OPT;
  - `case` — `1`, если в метке пришли заглавные буквы (резолвер применяет 0x20);
  - `from` — адрес, с которого пришёл запрос: выходной адрес резолвера.

  Строка не под MAC: это сведения, а не доказательство. Клиент может сравнить сеть `from` со своей, а `edns` —
  с нуждами туннеля (dnstt с v0.8.3 работает и при 512, но медленнее).
- Малый ответ — около 180 байт со всем сообщением. Большой — около 1150 байт.
- Если в запросе был OPT, ответ несёт OPT с размером UDP 1232.
- **Большой ответ без места.** Если в запросе нет OPT или его размер UDP меньше длины ответа, нода отвечает без
  записи, с флагом `TC`. Так же отвечал бы dnstt: TCP 53 у фронта нет.

Клиент проверяет:
- ID и вопрос;
- что строка 1 равна ожидаемой;
- у большого ответа — четыре строки заполнения после строки 2 точно.

## 5. Ограничения ноды

- **Частота.** Ведро токенов на источник (резолвер): /24 для IPv4, /48 для IPv6 — 20 токенов в секунду, запас 40.
  И одно общее — 400 в секунду, запас 800. Малая проба стоит 1 токен, большая — 8. Сверх ведра нода не отвечает
  вовсе.
- **Повторы.** Nonce помнятся 5 минут, не больше 8192. Когда места нет, проба идёт в бэкенд, как чужой запрос.
- **Журнал.** На уровне debug: проба, размер, источник. На обычном уровне — ничего.

## 6. Что значит результат

| Результат | Вывод клиента |
|---|---|
| верный малый ответ | резолвер доводит зону до ноды, TXT цел |
| верный большой ответ | пройдут и большие ответы: dnstt на полной скорости |
| большой: `TC` или таймаут, малый: верный | резолвер или путь режут размер: dnstt пойдёт медленнее (niko-server v0.8.3 подстраивает MTU сессии), masterdns — как обычно |
| неверная строка 1 | резолвер отвечает сам или меняет ответ: не годится |
| таймаут, `SERVFAIL`, `REFUSED` на малый | резолвер недоступен или зону не доводит |

Результат — свойство пары «сеть, резолвер». Клиент запоминает рабочий резолвер для сети и шлёт в сводке только вид
(`obs[].dns`, [`probe-v1.md`](probe-v1.md) §6.1), никогда адрес.

## 7. Пример

Тест `TestProbeVectors` в niko-server (`nikoserver/dnsprobe_test.go`):
- ключ `00 01 … 1f`;
- зона `t.example.com`;
- минута `29000000`;
- nonce `a0 a1 … a7`;
- размер `0`.

Тогда метка — `aeaadoubicqkdivduss2nj2inuqqx7vwla4ifvi`, строка 1 ответа — `v1 7wdaqgi6x2divio2oavsyoqvg4`.
Значения посчитаны и отдельно от кода niko-server (Python, `hmac` и `base64`).
