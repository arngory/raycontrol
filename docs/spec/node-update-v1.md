# node-update-v1: обновление ноды по запросу

Статус: **черновик** (2026-11-08). Сервер — raycontrol v0.19.0. Клиент — админ-панель Niko (admin-устройство через
удалённый API).

Зачем: обновить ноду, не заходя на неё по SSH. Есть два способа:
- по кнопке админа в клиенте (remote);
- самой нодой, на патч-версии в окне обслуживания (auto).

Оба по умолчанию **выключены**, включает их только root на ноде. Доверие прежнее: ставится только релиз, подписанный
ключом raycontrol (minisign, закреплён в коде). Через этот путь нельзя подсунуть свою сборку и нельзя откатиться на
старую версию.

## 1. Политика (root на ноде)

```
rayctl update remote on|off                    # админы могут обновлять ноду через API
rayctl update auto off|patch [-window 03:00-05:00]
rayctl update status                           # политика, последняя версия, последнее обновление
```

- Политика — файл root `/var/lib/raycontrol-update/policy.json` (каталог root, 0755). rayd его только читает, а root
  сверяет с ним каждый запрос. Даже взломанный rayd не включит то, что root оставил выключенным. Нет файла или он
  битый — всё выключено. Метода API для политики нет; `remote` и `auto` меняет только root (`status` — и группа
  `raycontrol`).
- `remote on`: метод `StartUpdate` принимается от admin-устройств. `off` (по умолчанию) — `FailedPrecondition`.
  На самой ноде `StartUpdate` через сокет — только root (`PermissionDenied` для группы `raycontrol`): root
  обновляет и так, `rayctl update`.
- `auto patch`: rayd раз в ~6 ч спрашивает у GitHub (`github.com/arngory/raycontrol`) подписанный `SHA256SUMS`
  последнего релиза. GitHub при этом видит адрес ноды. Если вышла новая **патч**-версия той же минорной
  (v0.19.0 → v0.19.3, но не v0.20.0), rayd обновляется в окне:
  - момент каждая нода выбирает случайно: до 30 минут с того, как увидела окно открытым, но так, чтобы успеть
    до его конца;
  - окно — это то, что показывают часы ноды (её `/etc/localtime`); оно может переходить через полночь и должно быть
    не короче 30 минут. В ночь перевода часов вперёд окно короче или его нет вовсе, в ночь перевода назад — длиннее.
    Момент выбирается по реальному времени до конца окна;
  - root принимает запрос auto только в окне (с запасом 5 минут).

  Если последний релиз — новая минорная или мажорная версия, auto его не ставит, но после v0.26.0 говорит о нём
  в строке цикла `auto-update` (`GetStatus.loops`, `detail`): `…: vX.Y.Z is out, a new minor version, which it
  leaves: this node runs …; rayctl update takes it …`.
- **Самый новый патч своей минорной** (с v0.27.0). `latest` GitHub называет только самый новый релиз вообще. Чтобы
  нода на v0.26.0 после выхода v0.27.0 всё же взяла v0.26.2, rayd в этом случае (и только в нём) спрашивает
  следующие номера своей минорной: `releases/download/v0.26.1/SHA256SUMS` и подпись, затем v0.26.2 и так далее.
  API GitHub и список релизов не нужны.
  - Каждый найденный релиз проверяется, как `latest`: подпись закреплённым ключом, версия из trusted comment, и она
    должна совпасть с номером, который спрашивали. Не совпала или подпись не та — поиск кончается на этом с тем,
    что уже нашёл.
  - Один пропущенный номер (404) переступается: релиз могли снять, а следом выпустить исправленный. Два подряд
    кончают поиск. Теги не вида `vX.Y.Z` (pre-release `v0.26.1-rc1`) не спрашиваются вовсе.
  - Не больше 8 номеров за проверку (`release.MaxPatchProbes`): найденный стоит 2 запроса, пропущенный — 1.
    Значит, проверка — это 2 запроса (`latest`), как раньше, плюс при новой минорной от 2 (патчей нет) до 16.
  - Ставит auto самый старший найденный, тем же запросом `vX.Y.Z`, в том же окне. Новая минорная по-прежнему
    только называется: строка `auto-update` о ней — когда патча нет; если поиск не удался, к ней добавляется
    `; newer patch releases of … not known: <причина>`.
  - То же делает `rayd -update-check`: в строке `update` к `vX.Y.Z is out, … : rayctl update` добавляется
    `(vA.B.C, a patch release of this minor version: rayctl update -version vA.B.C)`. И `rayctl update -check`
    root: вторая строка `release vA.B.C, the newest patch release of …, available: rayctl update -version vA.B.C`
    (он, как всегда, может идти и через зеркала).
- `rayctl update status` к GitHub сам не ходит: этот запрос показывает GitHub адрес ноды, и решает его root
  (`rayctl update -check`). Если проверок не было, с v0.27.0 он так и пишет: `latest     not checked: …`, а при
  включённом auto до первой проверки — `latest     not known yet: …`.
- Нода без systemd (`rayd serve -supervise`) и хост relay так не обновляются. Relay обновляет только root на его
  хосте, `rayctl update` (§5).

## 2. API (admin-устройство)

`StartUpdate {version}`:
- `version` — пусто или `latest` (последний релиз) либо `vX.Y.Z`, строго новее версии ноды;
- ответ — сразу `status{state: "requested", id, from, to, target, by, requested_at}`, а само обновление идёт после
  ответа;
- отказы:
  - `FailedPrecondition`:
    - удалённые обновления выключены;
    - нода — не релизная сборка;
    - нет юнита (`rayctl apply`);
    - обновление уже ждёт или идёт;
    - `latest`, а нода уже на последнем релизе, который видели проверки rayd;
  - `InvalidArgument`: версия не `latest` и не `vX.Y.Z`, или не новее версии ноды.

`GetUpdateStatus {}`:
- `status` — последнее обновление по запросу или текущее;
- `installed` — версия ноды;
- `latest` — последний релиз, который видели проверки rayd (`""`, если не видели). Смысл прежний: самый новый
  релиз вообще, в том числе новой минорной;
- `latest_patch` (с v0.27.0) — самый новый патч минорной версии ноды, новее `installed`, который видели проверки
  rayd (§1): `latest`, если тот — патч; после новой минорной — найденный поиском; `""`, если такого нет или
  проверок не было. Это то, что поставит auto. Старая нода поля не шлёт (`""`);
- `remote`, `auto`, `window` — политика root;
- `held` — релизы, обновление на которые откатилось или сломалось: auto их не просит;
- `timezone` — пояс ноды сейчас: сокращение и смещение (`"CET +01:00"`).

`status.state`:

| state | что значит |
|---|---|
| `idle` | обновлений по запросу ещё не было |
| `requested` | запрос записан, root-юнит его ещё не взял |
| `running` | идёт `rayctl update` |
| `done` | готово, `to` — новая версия ноды (для `latest` без нового релиза — та же, что `from`) |
| `rolled_back` | не вышло, прежняя версия работает снова; `error` — причина |
| `failed` | отказ (политика, версия, старый запрос), сбой без отката или `interrupted` — обновление оборвалось (таймаут юнита, выключение) или за час не пришло итога; `error` — причина |

`target` — какую версию просили (`latest` или `vX.Y.Z`). `release` — какой релиз пробовали (`vX.Y.Z`, как только
известен: для `latest` — после проверки подписи). `to` — до запуска то же, что `target`, после — версия, которую
показывает нода (`""`, если неизвестна). `by` — кто просил: `alice/phone (remote)`, `auto` или
`root (rayctl update -rollback)` для отката вручную.

Во время обновления перезапускаются rayd, сам API и data plane. Соединение рвётся на минуту-другую, это ожидаемо.
Клиент переподключается и опрашивает `GetUpdateStatus`, разумно раз в 5–10 с. Обычно обновление занимает 1–3 минуты.
Если в течение часа (`Stale`) не пришёл итог, нода сама покажет `failed`, и новый `StartUpdate` снова принимается:
- `interrupted` — обновление шло и оборвалось;
- `not taken` — root-юнит запрос так и не взял (path-юнит остановлен).

## 3. Как это устроено на ноде

rayd работает без привилегий (`User=rayd`). Поэтому он только записывает запрос, а ставит обновление root:

1. rayd пишет `/var/lib/raycontrol/update-request` (JSON: `id`, `kind` remote|auto, `version`, `by`, `at`; для
   `latest` ещё `release` — последний релиз, который rayd видел, только для `held`, если итога не будет). Файл
   создаётся атомарно и не заменяет чужой запрос, пока тот не старше часа.
2. `raycontrol-update.path` (`PathExists=`) запускает `raycontrol-update.service`. Это oneshot от root, без песочницы,
   после `rayd.service`: он ставит ноду. Запускает `rayctl update -request`.
3. `rayctl` читает запрос без перехода по ссылкам (каталог принадлежит rayd) и **проверяет его заново**:
   - формат, `by` — печатный текст до 128 байт;
   - возраст: запрос старше часа не выполняется;
   - `vX.Y.Z` или `latest`, никогда назад;
   - для auto — только патч и только в окне;
   - политику root из его файла (запрос, записанный до `remote off`, не выполняется).

   Потом пишет статус (`running` или `failed`) и только затем удаляет запрос, что бы там ни лежало (даже каталог),
   чтобы path-юнит не сработал ещё раз. Поэтому нет момента, когда rayd не видит ни запроса, ни статуса, и второй
   запрос посреди первого он не примет.
4. Обновление — обычный `rayctl update -yes -version V` установленным `rayctl`, с `RAYCONTROL_UPDATE_RESULT`. Он, в
   свою очередь, передаёт обновление `rayctl` релиза (`docs/RELEASE.md`, передача). Подпись, проверка data plane и
   откат — как при ручном запуске. Тот, кто сделал обновление, пишет итог в файл (`done`, `rolled_back`, `failed`,
   версия, причина, `untouched` — сбой до изменений на ноде). Формат заморожен в RELEASE.md. Если итога нет (процесс
   умер), берутся код выхода и последние строки вывода.
5. Итог пишется в `/var/lib/raycontrol-update/status.json`. Каталог root (0755), файл 0644, запись атомарная
   (rename), поля обрезаются до размеров, которые rayd читает. rayd его только читает. Если юнит убит (таймаут
   50 мин, выключение), `ExecStopPost` (`rayctl update -request-ended`) меняет `running` на `failed` (`interrupted`).
   Если не сработало и это (питание), rayd сам считает `running` старше часа оборвавшимся.

Повторов auto почти не делает:
- версию, обновление на которую откатилось (`rolled_back`, в том числе откат вручную) или сломалось на ходу
  (`failed`), он больше не просит, кто бы её ни просил (auto или админ через `latest`). Такие релизы root
  держит в `held` статуса, и каждый новый статус их переносит;
- версию, обновление на которую не дошло до изменений на ноде (`failed` с `untouched`: скачивание, проверка), он
  просит ещё раз через сутки.

Двигается дальше более новая патч-версия или root. Каждый запрос и отказ rayd попадает в его аудит (`update.start`).
Отказы и итоги на стороне root — в `status.json` и в журнале юнита (`journalctl -u raycontrol-update`).

**Откат и база.** Обновление сохраняет копию базы (при остановленном `rayd`) и возвращает её при откате, если
сдвинуло схему: прежний `rayd` на новой схеме не работает (Q-2). Отнятое после копии переносится в неё
(`store.CarryRevocations`, R4-30), а учётные данные пользователей откат не возвращает вовсе: каждая строка
`credentials`, которая есть в обеих базах, берётся из нынешней, ключ LAN тоже ([api-v1.md](api-v1.md) §5a). Иначе
откат с v0.27.0 вернул бы данные, которые сменил шаг миграции 0014, — те, что знают отозванные раньше устройства,
— и молча отменил бы `rayctl user renew`. Строки этой таблицы у схем 13 и 14 одинаковы. Откат после неудачного
обновления переносит так же, а если нынешнюю базу не прочесть — возвращает копию как есть; `-rollback -no-carry` —
тоже копия как есть, с прежними данными.

**Чего этот путь не меняет.** До v0.21.0 `rayctl apply` от root ставил план, который отдаёт rayd (юниты, файлы), и
взломанный rayd получал root при следующем `rayctl apply` или `rayctl update` root; с `remote on` или `auto patch` он
ещё и выбирал момент. С v0.21.0 apply плана rayd не ставит: берёт у него входы (`GetDeployInputs`), проверяет и
строит план сам ([apply-plan-v1.md](apply-plan-v1.md)). Момент rayd выбирает по-прежнему, но root от этого не
получает. Ещё он может писать запросы так часто, что systemd остановит path-юнит (start limit); так он только
выключает обновления по запросу, а root снова включает их через `systemctl reset-failed raycontrol-update.path`.

## 4. Версии

- raycontrol v0.19.0:
  - передача обновления `rayctl` релиза;
  - `StartUpdate`, `GetUpdateStatus`;
  - `rayctl update remote|auto|status`;
  - юниты `raycontrol-update.path` и `.service` (их ставит `rayctl apply`).
- Старая нода: на `StartUpdate` отвечает голым HTTP 404 (метода нет), и строку в панели можно скрыть.
- raycontrol v0.26.0: `rayctl update` на хосте relay (§5).
- raycontrol v0.27.0: auto берёт самый новый патч своей минорной и после выхода новой минорной (§1);
  `GetUpdateStatus.latest_patch`. Для клиента: кнопка «обновить» по-прежнему шлёт `StartUpdate {version: ""}`
  (`latest`, самый новый релиз вообще); если `latest_patch` не пуст и не равен `latest`, клиент может предложить
  и его — `StartUpdate {version: latest_patch}`, патч без смены минорной. Без поля (старая нода) — как раньше.

## 5. Relay: `rayctl update` на его хосте

С raycontrol v0.26.0 `rayctl update` на хосте relay ([relay-v1.md](relay-v1.md)), от root, обновляет сам relay. На
хосте relay три бинарника: `rayspa` (периметр, SPA, пересылка), `rayd` (точка замера `rayd relay`; его командой юниты
копируют себе пакет relay) и `rayctl`. Базы ноды там нет.

**На настоящем хосте relay с systemd это обновление ни разу не запускалось** — ни установка из обновления, ни откат,
ни прерывания. Всё ниже следует из кода и модульных тестов на временных каталогах; заданий CI для хоста relay нет.

**Как у ноды** — тот же код (`stageRelease` в `cmd/rayctl`):
- релиз с GitHub или зеркал либо из каталога (`-from DIR`); `SHA256SUMS` и его подпись minisign проверяются
  закреплённым ключом, версия берётся из подписи;
- назад — только названная версия (`-version vX.Y.Z`) или с `-force`: с ним релиз старше установленного ставят и
  `latest`, и `-from`. Та же версия ещё раз — тоже только с `-force`. Так и у ноды;
- `-check` только сообщает, что установлено и есть ли новее; `-check -rollback` — ошибка использования (и у ноды);
- одно обновление или откат за раз (`/run/raycontrol-update.lock`);
- релиз новее установленного обновляет его собственный `rayctl` (передача, [RELEASE.md](../RELEASE.md)); значит,
  установку делает код relay новой версии. `-no-handoff` — этим `rayctl`.

**Что иначе:**
- Релиз не старше v0.26.0. Более старый ставит на relay его собственный `bootstrap.sh`:
  `RAYCONTROL_VERSION=vX.Y.Z bash bootstrap.sh -relay /etc/raycontrol/relay.bundle`. Отказ — до передачи и до
  изменений, и с `-check` тоже.
- Пакет relay (`/etc/raycontrol/relay.bundle`) читается до любых изменений. Если его нет, он доступен не только root
  или не читается, это отказ: `nothing changed`. Новый пакет даёт `rayctl relay bundle` на выходе, и прежний тогда
  перестаёт действовать.
- Замок установки relay (`/run/raycontrol-relay-install.lock`) берётся после передачи и до первого изменения и
  держится до конца: `rayctl install -relay`, который запускает обновление, получает его как fd 3
  (`RAYCONTROL_RELAY_LOCK_FD=3`) и не отпускает между установкой бинарников и своей работой. Идёт `bootstrap.sh -relay`
  или установка, пережившая убитое обновление, — отказ, `nothing changed`. Чужой таймер-страж обновление не трогает.
- Установка — то же, что повторный `bootstrap.sh -relay` с сохранённым пакетом:
  - `rayspa`, `rayd` и `rayctl` релиза встают на место (рядом, затем `rename`). Если не встал первый же (нет места),
    ничего не изменилось: отказ без отката, relay работает как работал;
  - установленный `rayctl` новой версии выполняет `rayctl install -relay /etc/raycontrol/relay.bundle`. Юниты и
    sysctl переписываются, если изменились; `rayspa` перезапускается под таймером-стражем и включается после проверки
    первого снимка от выхода (relay-v1 §7); включается пересылка; перезапускается точка замера.
- Проверка после установки (до 30 с, затем ещё раз через 3 с):
  - `rayspa` работает, и работает тот самый бинарник, что лежит на диске (`/proc/PID/exe` его `MainPID`): процесс,
    оставшийся с прежней версии, проверку не проходит;
  - его таблица (`nft list table inet raycontrol`) применила снимок, с которым `rayspa` работает сейчас (последний
    от выхода или возвращённый откатом, а не тот, что был до обновления: администратор выхода мог его с тех пор
    изменить): в ней есть адреса администратора, а если в снимке есть сервисы, которые relay пересылает, то и DNAT
    к выходу (`relay_dnat`) с портами (`relay_fwd`). Пересылаемые сервисы — те, что не `Local`, с портами
    (`perimeter.Forwarded`, то же, по чему `rayspa` заполняет `relay_fwd`). Собственный SSH relay и точка замера
    в снимке есть всегда, но они `Local` — обслуживаются на самом relay и в `relay_fwd` не попадают; поэтому relay,
    которому выход ничего не пересылает (только DNS-туннели, транспорты выключены), проверку проходит с пустым
    `relay_fwd`. Порты в `relay_fwd` есть сразу после снимка, без стука клиентов (разрешения после стука — в
    `allow4`/`allow6`);
  - `/proc` говорит, что пересылка включена;
  - снимок пускает SSH на порт sshd с адресов администратора relay, адрес этой сессии среди них (если известен);
  - `rayspa version` — новая версия;
  - точка замера работает, если работала до обновления.
- Пересылка прерывается на время установки: обычно меньше минуты; дольше всего, если выход не отвечает — до 150 с
  на старт `rayspa`, 45 с на первый снимок, затем откат с проверкой (до 33 с). Всего — около 5 минут.

**Откат.** До изменений обновление откладывает в `/var/lib/raycontrol-install/previous`:
- бинарники;
- файлы, которые пишет установка relay, или отметку, что файла не было: юниты `rayspa.service` и
  `rayd-relay.service`, файлы sysctl плана, а также те, что установка пишет после подъёма relay —
  `90-raycontrol-conntrack.conf`, `/etc/modules-load.d/raycontrol.conf`, `90-raycontrol-ports.conf`;
- последний снимок `rayspa`;
- включены ли и работают ли оба юнита.

`relay.json` пишется последним: нет его — копия не целая, и откатываться не к чему. Копия делается рядом
(`previous.new`) и заменяет копию прошлого обновления, только когда целая: если сохранить не удалось, прежняя
копия остаётся как была. Журнал установки не копируется: он только растёт, а `rayctl uninstall` снимает то,
что в нём записано. Файл, который пишет только установка другой версии (при `-no-handoff` или откате на более
старый релиз список файлов — этого `rayctl`), не сохраняется и не удаляется. Вреда нет: это настройки ядра в
sysctl.d, `rayspa` их не читает, а то, что установка записала в журнал, снимет `rayctl uninstall`.

Если после первого изменения не встали бинарники, не прошла установка или проверка:
1. таймер-страж прерванной установки снимается (под его замком: либо он уже сработал, либо не сработает);
2. юниты останавливаются; не остановился — откат не идёт дальше (новый `rayspa` не должен работать под видом
   прежнего), и хост открывается (ниже);
3. бинарники (кроме тех, что и так как сохранённые), файлы и снимок возвращаются, а файл, которого не было,
   удаляется;
4. `daemon-reload`; файлы sysctl применяются заново — сначала пересылка, затем защита — так же, как их применяет
   установка (`sysctl -q -e -p`): ключей, которых у ядра нет (`net.ipv6.*` при выключенном IPv6, bbr), он не
   касается, а сбой (ключ только для чтения в контейнере) — предупреждение, не причина открыть хост. Затем, как и
   установка, откат читает значения снова (`sysctl -n`) и называет каждый ключ защиты, который не встал
   (`warning: after the restore … is …, not …`), — тоже только предупреждение. Включена ли пересылка, решает
   проверка в шаге 6 (`/proc/sys/net/ipv4/ip_forward`);
5. юниты включаются и запускаются так, как были;
6. та же проверка, но с прежней версией.

`rayspa` стартует с прежним снимком, поэтому relay возвращается с прежним периметром, даже если выход сейчас
недоступен. Итог — `update failed, the previous version runs again: …`. `rayctl update -rollback` на relay делает то
же вручную; снимок он оставляет нынешний (в нём последний периметр от выхода, и он пустил эту сессию), кроме двух
случаев: обновление не закончилось (метка, ниже) или хост открыт — тогда возвращается и сохранённый снимок.

**Прерванное обновление.** Как только копия целая и до замены первого бинарника обновление пишет метку
`previous/relay.unfinished`. Она уходит, только когда relay проверен — обновлённым или вернувшимся; хост, оставленный
открытым, помечается `open`. Пока метка есть, `rayctl update` отказывает и говорит, что делать (никогда не «installed,
the newest release»); `-check` и `rayctl update status` пишут то же. Ctrl-C, Ctrl-\, обрыв SSH (SIGHUP), SIGTERM
и SIGPIPE (читатель вывода, например `tee`, пропал) `rayctl update` с этого места перехватывает и доводит дело до
конца; установка получает их как обычно и останавливается как при ошибке. Не перехватить можно только kill -9 и
потерю питания.

Выключение или перезагрузка обновление **прерывает**, хотя `rayctl` SIGTERM и перехватывает: logind шлёт SIGTERM
всей сессии, установке тоже, она останавливается, а откат запустить юниты уже не может — systemd во время
выключения запуск отвергает. Откат тогда не удался, и хост открывается, как при любом неудавшемся откате: `rayspa`
выключен, метка `open`, после загрузки relay открыт и не пересылает. Оставить `rayspa` включённым до загрузки
нельзя: неизвестно, на чём остановился откат и пускает ли снимок на диске администратора, а закрытый для него хост
хуже открытого. После загрузки — `rayctl update -rollback`. По месту обрыва:

| где оборвалось | что на хосте | что делать |
|---|---|---|
| до того, как копия целая | ничего не изменилось; `relay.json` нет | `rayctl update` ещё раз |
| при установке бинарников | метка; часть новых бинарников, прежний `rayspa` ещё работает | `rayctl update -rollback` |
| при установке relay | метка; установка идёт дальше сама: при удаче relay на новой версии, при неудаче (выход не ответил, её тоже убили) хост открыт и снимка нет | дождаться её конца (замок установки), затем `rayctl update -rollback` |
| при проверке | метка; relay на новой версии | `rayctl update -rollback` |
| при откате | метка; что угодно между двумя версиями | `rayctl update -rollback` ещё раз |
| выключение или перезагрузка | откат не смог запустить юниты: хост открыт, `rayspa` выключен, метка `open` | после загрузки `rayctl update -rollback` |
| хост оставлен открытым | метка `open` | `rayctl update -rollback` или `bash bootstrap.sh -relay /etc/raycontrol/relay.bundle` |

`-rollback` на открытом хосте (`rayspa` не работает или таблицы нет) не сверяет сессию с периметром — его нет — и
возвращает сохранённый снимок. На работающем он сверяет её, как и обновление.

Повторная установка `bootstrap.sh -relay` (не из обновления), прошедшая проверку, снимает метку и копию прошлого
обновления: relay поставлен заново, и откат к версии, что стояла до установки, вернул бы не тот relay, что работает
(`rayctl update status` перестаёт его предлагать). Снимается только копия relay — та, в которой есть `relay.json`;
в `previous` ноды его нет, а на хосте ноды `rayctl install -relay` отказывает раньше. Так же снимаются
`previous.old` и `previous.new` с `relay.json`: после обрыва между двумя переименованиями копии прежняя лежит в
`previous.old`, и следующее обновление вернуло бы её на место `previous`. Метка без целой копии рядом
(так бывает только после правки руками: копия целая раньше, чем пишется метка) — не тупик: `rayctl update`,
`-rollback` и `status` называют тогда не `-rollback`, а `bash bootstrap.sh -relay /etc/raycontrol/relay.bundle`.

Потеря питания во время установки: `rayspa` выключен (установка выключает его до первой записи), а
`91-raycontrol-relay.conf` остаётся, и хост загружается с `net.ipv4.ip_forward = 1` без периметра. Он открыт и
пересылает то, что сеть провайдера направит через него как через маршрутизатор (обычно ничего). То же окно есть у
повторного `bootstrap.sh -relay`. После загрузки — `rayctl update -rollback` (метка на месте).

**Правило против запирания.** Обновление никогда не оставляет relay закрытым для его администратора. Работавший
relay оно открывает, только если иначе администратор не войдёт:
- Адреса SSH relay приходят от выхода, а не из релиза: обновление их не меняет. Поэтому до изменений `rayctl update`
  проверяет нынешний снимок так же, как его проверит установка:
  - sshd слушает один порт;
  - эта сессия пришла на него;
  - её адрес входит в список администратора relay.

  Иначе отказ (`nothing changed`) с подсказкой: на выходе `rayctl relay set -admin <список>,<ваш адрес> <имя>`, затем
  `rayctl update` снова. Если адрес неизвестен (tmux, консоль) или это loopback (туннель), выводится только
  предупреждение, как при установке.
- Свой периметр новая версия проверяет сама. Если проверка не прошла, установка, как и сегодня, снимает таблицу, и
  хост открыт. Это длится секунды: обновление сразу возвращает прежний relay с прежним снимком, и хост снова закрыт
  для всех, кроме администратора, и снова пересылает.
- Сбой до первого изменения (не встал первый бинарник, занят замок установки) хост не трогает вовсе.
- Открытым хост остаётся, только если не вернулся и прежний relay: не встали бинарники, юнит не остановился,
  `rayspa` не поднялся или не держит таблицу, не прошла проверка. Тогда `rayspa` выключается и снимает таблицу,
  пересылки нет, и `rayctl` так и пишет (`the host left open and not forwarding`) вместе с командой повторной
  установки. Если не удалось снять и таблицу, он пишет, какие команды выполнить до выхода из сессии. Таблицу он
  проверяет дважды — сразу и через 2 с: `rayspa`, который не остановился (`systemctl stop` кончается SIGKILL, так
  что это systemd или D-Bus не отвечает), возвращает её в течение секунды. Тогда хост **не** открыт — SSH пускает
  только с адресов администратора relay, — и `rayctl` так и пишет (`the host is NOT open`) вместе с теми же
  командами.

**`-check` и `status` на relay.** `rayctl update -check` печатает версии и строку о том, что удалённое и
автоматическое обновление к relay не относятся. Если обновление отказало бы (сессия не из списка, метка) — ещё
предупреждение. `rayctl update status` печатает установленную версию, версию, сохранённую для отката, метку, если
она есть, и что `remote` и `auto` к relay не относятся; последний релиз — через `-check` (запрос к GitHub).

**Не поддерживается:**
- удалённое обновление с admin-устройства и автообновление: у relay нет API rayd для устройств. `rayctl update
  remote|auto` на relay отказывают (`remote and automatic updates do not apply to it`), `rayctl update -request` —
  тоже;
- обновление всех relay с выхода;
- `rayctl update` на relay до v0.26.0: такой `rayctl` отказывает
  (`this host is a relay: install/bootstrap.sh -relay …`). На v0.26.0 relay переходит повторным `bootstrap.sh -relay`
  с пакетом.

**Что проверено.** Модульными тестами, весь `rayctl update` и `-rollback` relay — на временных каталогах, с
подменёнными командами хоста (`relayEnv`):
- отказ без пакета; нижняя граница relay, и с `-check`;
- общий с нодой выбор и проверка релиза: подпись, правила версий, `-check`, передача `rayctl` релиза;
- проверка сессии до изменений;
- откат при сбое установки и при сбое проверки, со снимком; хост открывается, только если прежний relay не вернулся;
- сбой первого бинарника ничего не трогает;
- метка: отказ и подсказка, `-check`, `status`; откат открытого хоста без проверки сессии и со снимком;
- проверка после изменения: бинарник процесса, таблица по снимку, с которым `rayspa` работает (relay без
  пересылаемых сервисов; сервисы, снятые на выходе после копии, и `-rollback` после этого); `perimeter.Forwarded`
  сверен с тем, что шлюз кладёт в `relay_fwd`;
- замок установки, переданный как fd 3; окружение установки; перехват SIGTERM и SIGHUP.

На настоящем хосте не проверены: systemd, nft, sysctl, `/proc/PID/exe` процесса `rayspa`, передача fd 3 установке
и сами прерывания.
