# node-update-v1: обновление ноды по запросу

Статус: **черновик** (2026-11-08). Сервер — raycontrol v0.19.0. Клиент — админ-панель Niko (admin-устройство через
удалённый API).

Зачем: обновить ноду, не заходя на неё по SSH. Есть два способа:
- по кнопке админа в клиенте (remote);
- самой нодой, на патч-версии в окне обслуживания (auto).

Оба по умолчанию **выключены**, включает их только root на ноде. Доверие прежнее: ставится только релиз, подписанный
ключом raycontrol (minisign, закреплён в коде). Через этот путь нельзя подсунуть свою сборку и нельзя откатиться на
старую версию.

## 1. Политика (root на ноде)

```
rayctl update remote on|off                    # админы могут обновлять ноду через API
rayctl update auto off|patch [-window 03:00-05:00]
rayctl update status                           # политика, последняя версия, последнее обновление
```

- Политика — файл root `/var/lib/raycontrol-update/policy.json` (каталог root, 0755). rayd его только читает, а root
  сверяет с ним каждый запрос. Даже взломанный rayd не включит то, что root оставил выключенным. Нет файла или он
  битый — всё выключено. Метода API для политики нет; `remote` и `auto` меняет только root (`status` — и группа
  `raycontrol`).
- `remote on`: метод `StartUpdate` принимается от admin-устройств. `off` (по умолчанию) — `FailedPrecondition`.
  На самой ноде `StartUpdate` через сокет — только root (`PermissionDenied` для группы `raycontrol`): root
  обновляет и так, `rayctl update`.
- `auto patch`: rayd раз в ~6 ч спрашивает у GitHub (`github.com/arngory/raycontrol`) подписанный `SHA256SUMS`
  последнего релиза. GitHub при этом видит адрес ноды. Если вышла новая **патч**-версия той же минорной
  (v0.19.0 → v0.19.3, но не v0.20.0), rayd обновляется в окне:
  - момент каждая нода выбирает случайно: до 30 минут с того, как увидела окно открытым, но так, чтобы успеть
    до его конца;
  - окно задаётся по времени ноды (её `/etc/localtime`, с переходом на летнее время), может переходить через полночь
    и должно быть не короче 30 минут;
  - root принимает запрос auto только в окне (с запасом 5 минут).
- Нода без systemd (`rayd serve -supervise`) и хост relay так не обновляются.

## 2. API (admin-устройство)

`StartUpdate {version}`:
- `version` — пусто или `latest` (последний релиз) либо `vX.Y.Z`, строго новее версии ноды;
- ответ — сразу `status{state: "requested", id, from, to, target, by, requested_at}`, а само обновление идёт после
  ответа;
- отказы:
  - `FailedPrecondition`:
    - удалённые обновления выключены;
    - нода — не релизная сборка;
    - нет юнита (`rayctl apply`);
    - обновление уже ждёт или идёт;
    - `latest`, а нода уже на последнем релизе, который видели проверки rayd;
  - `InvalidArgument`: версия не `latest` и не `vX.Y.Z`, или не новее версии ноды.

`GetUpdateStatus {}`:
- `status` — последнее обновление по запросу или текущее;
- `installed` — версия ноды;
- `latest` — последний релиз, который видели проверки rayd (`""`, если не видели);
- `remote`, `auto`, `window` — политика root;
- `held` — релизы, обновление на которые откатилось или сломалось: auto их не просит;
- `timezone` — пояс ноды сейчас: сокращение и смещение (`"CET +01:00"`).

`status.state`:

| state | что значит |
|---|---|
| `idle` | обновлений по запросу ещё не было |
| `requested` | запрос записан, root-юнит его ещё не взял |
| `running` | идёт `rayctl update` |
| `done` | готово, `to` — новая версия ноды (для `latest` без нового релиза — та же, что `from`) |
| `rolled_back` | не вышло, прежняя версия работает снова; `error` — причина |
| `failed` | отказ (политика, версия, старый запрос), сбой без отката или `interrupted` — обновление оборвалось (таймаут юнита, выключение) или за час не пришло итога; `error` — причина |

`target` — какую версию просили (`latest` или `vX.Y.Z`). `release` — какой релиз пробовали (`vX.Y.Z`, как только
известен: для `latest` — после проверки подписи). `to` — до запуска то же, что `target`, после — версия, которую
показывает нода (`""`, если неизвестна). `by` — кто просил: `alice/phone (remote)`, `auto` или
`root (rayctl update -rollback)` для отката вручную.

Во время обновления перезапускаются rayd, сам API и data plane. Соединение рвётся на минуту-другую, это ожидаемо.
Клиент переподключается и опрашивает `GetUpdateStatus`, разумно раз в 5–10 с. Обычно обновление занимает 1–3 минуты.
Если в течение часа (`Stale`) не пришёл итог, нода сама покажет `failed`, и новый `StartUpdate` снова принимается:
- `interrupted` — обновление шло и оборвалось;
- `not taken` — root-юнит запрос так и не взял (path-юнит остановлен).

## 3. Как это устроено на ноде

rayd работает без привилегий (`User=rayd`). Поэтому он только записывает запрос, а ставит обновление root:

1. rayd пишет `/var/lib/raycontrol/update-request` (JSON: `id`, `kind` remote|auto, `version`, `by`, `at`; для
   `latest` ещё `release` — последний релиз, который rayd видел, только для `held`, если итога не будет). Файл
   создаётся атомарно и не заменяет чужой запрос, пока тот не старше часа.
2. `raycontrol-update.path` (`PathExists=`) запускает `raycontrol-update.service`. Это oneshot от root, без песочницы,
   после `rayd.service`: он ставит ноду. Запускает `rayctl update -request`.
3. `rayctl` читает запрос без перехода по ссылкам (каталог принадлежит rayd) и **проверяет его заново**:
   - формат, `by` — печатный текст до 128 байт;
   - возраст: запрос старше часа не выполняется;
   - `vX.Y.Z` или `latest`, никогда назад;
   - для auto — только патч и только в окне;
   - политику root из его файла (запрос, записанный до `remote off`, не выполняется).

   Потом пишет статус (`running` или `failed`) и только затем удаляет запрос, что бы там ни лежало (даже каталог),
   чтобы path-юнит не сработал ещё раз. Поэтому нет момента, когда rayd не видит ни запроса, ни статуса, и второй
   запрос посреди первого он не примет.
4. Обновление — обычный `rayctl update -yes -version V` установленным `rayctl`, с `RAYCONTROL_UPDATE_RESULT`. Он, в
   свою очередь, передаёт обновление `rayctl` релиза (`docs/RELEASE.md`, передача). Подпись, проверка data plane и
   откат — как при ручном запуске. Тот, кто сделал обновление, пишет итог в файл (`done`, `rolled_back`, `failed`,
   версия, причина, `untouched` — сбой до изменений на ноде). Формат заморожен в RELEASE.md. Если итога нет (процесс
   умер), берутся код выхода и последние строки вывода.
5. Итог пишется в `/var/lib/raycontrol-update/status.json`. Каталог root (0755), файл 0644, запись атомарная
   (rename), поля обрезаются до размеров, которые rayd читает. rayd его только читает. Если юнит убит (таймаут
   50 мин, выключение), `ExecStopPost` (`rayctl update -request-ended`) меняет `running` на `failed` (`interrupted`).
   Если не сработало и это (питание), rayd сам считает `running` старше часа оборвавшимся.

Повторов auto почти не делает:
- версию, обновление на которую откатилось (`rolled_back`, в том числе откат вручную) или сломалось на ходу
  (`failed`), он больше не просит, кто бы её ни просил (auto или админ через `latest`). Такие релизы root
  держит в `held` статуса, и каждый новый статус их переносит;
- версию, обновление на которую не дошло до изменений на ноде (`failed` с `untouched`: скачивание, проверка), он
  просит ещё раз через сутки.

Двигается дальше более новая патч-версия или root. Каждый запрос и отказ rayd попадает в его аудит (`update.start`).
Отказы и итоги на стороне root — в `status.json` и в журнале юнита (`journalctl -u raycontrol-update`).

**Чего этот путь не меняет.** `rayctl apply` от root ставит план, который отдаёт rayd (юниты, файлы). Поэтому
взломанный rayd и прежде получал root при следующем `rayctl apply` или `rayctl update` root. С `remote on` или
`auto patch` он может выбрать момент сам, но новых возможностей не получает. Ещё он может писать запросы так
часто, что systemd остановит path-юнит (start limit); так он только выключает обновления по запросу, а root снова
включает их через `systemctl reset-failed raycontrol-update.path`. Закрыть это может только проверка
плана самим `rayctl` — отдельная задача, не этого релиза.

## 4. Версии

- raycontrol v0.19.0:
  - передача обновления `rayctl` релиза;
  - `StartUpdate`, `GetUpdateStatus`;
  - `rayctl update remote|auto|status`;
  - юниты `raycontrol-update.path` и `.service` (их ставит `rayctl apply`).
- Старая нода: на `StartUpdate` отвечает голым HTTP 404 (метода нет), и строку в панели можно скрыть.
