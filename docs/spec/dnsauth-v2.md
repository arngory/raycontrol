# dnsauth-v2: подсказка ключа

Статус: **черновик** (2026-11-06), на согласовании с клиентом. Расширяет [`dnsauth-v1.md`](dnsauth-v1.md) и
[`dnsauth-masterdns.md`](dnsauth-masterdns.md): ключ K, эпохи и место метки в запросе прежние, меняется только
содержимое 8 байт метки.

## 1. Зачем

Запрос без известной сессии нода сейчас проверяет перебором ключей всех устройств — около 3 HMAC на устройство
(три эпохи, dnsauth-v1 §4, dnsauth-masterdns §3). На перебор есть бюджет: пробам MTU и началам сессий по
`max(40 000, 24·n)` HMAC в секунду. Мусор с верной внешней обёрткой (её может собрать любой обладатель ссылки:
ключи сервиса и печати есть в каждой ссылке) выжигает бюджет вида:

| устройств | запросов мусора в секунду на вид |
|---|---|
| 50 | ~270 |
| 500 | ~27 |
| 1000 | ~13 |

После этого новые сессии не открываются ни у кого, вернувшиеся устройства тоже (их проверка идёт из того же
бюджета). Живые сессии работают. dnsauth-v1 §8 откладывал лекарство до v2: подсказку ключа в метке.

## 2. Поле метки

Те же 8 байт на том же месте (dnstt — в начале нагрузки, masterdns — как в dnsauth-masterdns §2):

```
hint (2) || tag (6)
hint = HMAC-SHA256(K, "dnsauth2-hint" || uint32_be(epoch))[:2]
tag  = HMAC-SHA256(K, "dnsauth2-tag"  || uint32_be(epoch) || msg)[:6]
```

- `K`, `epoch` и `msg` — как в v1: K из dnsauth-v1 §2; `epoch = floor(unix_time / 600)`; `msg` у dnstt — нагрузка
  после метки (ClientID и дальше), у masterdns — `nonce || кадр` (dnsauth-masterdns §2).
- Метки `"dnsauth2-hint"` и `"dnsauth2-tag"` различаются уже в 10-м байте: входы HMAC не совпадут ни при каком `msg`.
- Подсказка зависит только от устройства и эпохи: у всех запросов устройства за эпоху она одна. Метка — у каждого
  запроса своя.
- Подделка: угадать `tag` — 2⁻⁴⁸ на попытку (v1: 2⁻⁶⁴); онлайн-подбор этого не достигает.

## 3. Как проверяет нода

- Для эпох `epoch-1`, `epoch`, `epoch+1` нода держит указатель «подсказка → ключи». Указатель новой эпохи
  считается раз в 10 минут: по HMAC на ключ. При тысяче устройств — тысяча HMAC раз в 10 минут.
- Запрос: по подсказке и эпохе берутся ключи-кандидаты (обычно один; совпадение двух подсказок — `n / 65536`) и для
  них проверяется `tag`. Сошлось — устройство найдено. Не сошлось ни у кого — отказ, без перебора.
- Проверка v2 не берёт из бюджета перебора: мусор стоит одного поиска в указателе, а с чужой верной подсказкой
  (её видно, только сняв печать или шифр сервиса, то есть со ссылкой и на пути) — одного-трёх HMAC.
- Живые сессии — как в v1: dnstt по кэшу ClientID, masterdns по устройству сессии (`Device`): у них проверяются
  подсказка и `tag` одного известного ключа.

## 4. Переход

**Объявление.** Строгий клиент (subscription-v1 §4, тест `TestLinksForStrictClient`) молча отбрасывает строку, если
`niko-dnsauth` не `v1`. Поэтому `niko-dnsauth=v2` в ссылке сломал бы старые клиенты. Вместо него нода объявляет v2
полем подписки, которое старые клиенты не читают:

```json
"dnsauth": {"v": [1, 2]}
```

`niko-dnsauth=v1` в ссылке остаётся и значит «подписывать». Клиент, который знает v2 и видит `2` в `dnsauth.v`,
подписывает по v2; иначе — по v1. (Вопрос клиенту: если незнакомые параметры `niko-…` старые клиенты пропускают, можно
вместо поля подписки `niko-dnsauth2=1` в ссылке. Поле подписки надёжнее: JSON-поля, которых клиент не знает, он не
читает.)

**Режимы ноды** (`rayctl service set <dns> auth_hint=…`, dnstt и masterdns):

| `auth_hint` | v2 | v1 | Когда |
|---|---|---|---|
| `optional` | по подсказке, без бюджета | перебором в бюджете (как сейчас) | по умолчанию с пином niko-server, где есть v2 |
| `required` | по подсказке | не принимается: перебора нет совсем | когда все клиенты подписывают по v2 |

В `optional` мусор по-прежнему выжигает бюджет перебора, но страдают только клиенты v1: клиенты v2 входят по подсказке.
В `required` поток мусора не стоит ноде ничего, кроме поиска в указателе.

## 5. Приватность

Подсказка постоянна у устройства в пределах эпохи (10 минут) и лежит под печатью (dnstt, dnsseal-v1) или шифром
сервиса (masterdns). Без ключа сервиса её не видно; с ним — запросы одного устройства связываются в пределах эпохи,
что и так даёт ClientID или сессия. Между эпохами подсказки без K не связываются.

## 6. Векторы

Посчитаны в Python по этой спеке, отдельно от кода. `K` — вектор dnsauth-v1 §2
(`0b485b425e8b19e0ec7c0362d55fdc34338147f984b87ee005455c8f5fc68b1c`), время `1767268800`, `epoch = 2945448`,
`msg = 00 01 … 17` (24 байта):

```
hint             = 2d82
tag              = b1220002a927
поле             = 2d82b1220002a927
hint (epoch - 1) = a5f9
hint (epoch + 1) = e97f
```

## 7. Что менять

- **Клиент:** подписывать по v2 (ядро dnstt; клиент masterdns в форке), если подписка объявляет `2`.
- **niko-server:** `dnsttserver.Auth` и `DeviceAuth` — указатель подсказок по эпохам, проверка v2 без бюджета,
  режим `auth_hint`; masterdns — без изменений в форке (метка для `Authenticator` — те же 8 байт).
- **raycontrol:** опция `auth_hint`, поле `dnsauth` в подписке, пин niko-server с v2.
