# raycontrol: замер канала v1

Сервис замера для устройств ноды (RAYCONTROL.md §13 п. 1 в `arngory/niko`, решение R4-16). Он даёт клиенту
то, что сторонние цели не дают:
- скорость обоих направлений по TCP с видом сервера на соединение (`TCP_INFO`);
- эхо UDP с номерами и временем, как в irtt: RTT, джиттер, потери в каждую сторону, переупорядочивание, MTU.

Неизвестные поля клиент игнорирует; новые поля в ответах и необязательные параметры — без смены версии.

## 1. Где

- **Напрямую.** Эндпоинт подписки: `https://<host>:<sub.port>/probe/v1/…`. TLS тот же, что у подписки
  ([`subscription-v1.md`](subscription-v1.md) §1): TLS 1.3, только `X25519MLKEM768`, сертификат по пину `sub.pin`.
  Эхо UDP — на UDP-порту с тем же номером `sub.port`. SPA открывает его вместе с TCP: оба порта — у сервиса
  подписки, а он в scope любого устройства.
- **Признак.** Нода, которая отвечает на замеры, пишет в payload подписки поле `probe`:

  ```json
  {"v": 1, "udp": true, "tunnel": "probe.raycontrol.invalid", "tunnel_svc": [3, 5]}
  ```

  - `udp: false` — эха нет, работает только TCP.
  - `tunnel_svc` — сервисы, через туннели которых работает замер (§1.1).
  - Нода без поля `probe` замеров не знает.

### 1.1. Через туннель профиля

- Внутри туннеля клиент обращается к имени `tunnel` (`probe.raycontrol.invalid`) на любом порту. Выход туннеля
  передаёт его эндпоинту подписки через loopback ноды.
- Запросы, TLS с пином, авторизация и ограничения — те же, что напрямую. Так замер показывает туннель целиком:
  его шифрование, ограничения пути и выход.
- Выходы:
  - **Xray** — `inner` за DNS-туннелями и Yggdrasil, и REALITY. Правило маршрутизации по имени стоит раньше
    запрета частных сетей; UDP идёт через VLESS UDP.
  - **`rayd naive`** — только TCP.
  - **Бэкенды Hysteria2** (niko-server v0.5) — TCP и UDP; ответы на датаграммы приходят от имени.
- Порт UDP. Эхо UDP через туннель — датаграммы на `tunnel:<port>` из ответа сессии. REALITY с Vision не пропускает
  UDP на 443, поэтому используется порт сессии.
- В `tunnel_svc` попадают только сервисы, чьи выходы это умеют. Любой другой адрес loopback ноды через туннели
  по-прежнему недоступен.

## 2. Авторизация

Как у подписки (`subscription-v1.md` §2): заголовки `X-Raycontrol-Device` и `Authorization: RC1 <minute>.<mac>`.
- Неизвестное или отозванное устройство или неверный токен — `404`.
- Остальные отказы относятся к устройству, которое уже прошло проверку, поэтому коды у них говорящие (§5).

## 3. TCP

| Запрос | Ответ |
|---|---|
| `GET /probe/v1/down?bytes=N` | `200`, `N` байт псевдослучайных данных, затем trailer `Probe-Result` |
| `POST /probe/v1/up?bytes=N`, тело — `N` байт | `200`, JSON с результатом сервера |

- `N` — от 1 до 268 435 456 (256 МиБ). Иначе — `400`.
- **Результат сервера.**
  - Trailer `down` передаётся как `key=value; …`, ответ `up` — как JSON с теми же полями:

    ```json
    {"bytes": 4194304, "ms": 812, "tcp": {"rtt_us": 41250, "rttvar_us": 3100, "min_rtt_us": 38000,
     "retrans": 12, "delivery_bps": 41000000, "cwnd": 64, "pmtu": 1500}}
    ```

  - `bytes` — сколько сервер отправил (`down`) или получил (`up`).
  - `ms` — для `down`: от начала записи до конца. Для `up`: от первого полученного байта до последнего.
  - `tcp` — `TCP_INFO` сокета сервера в конце замера: сглаженный и минимальный RTT, переотправки за всё
    соединение, оценка скорости доставки ядром, окно, PMTU.
  - Если соединение идёт через HTTP/2, в `tcp` попадают и предыдущие запросы этого соединения.
- **Клиент.** Скорость `down` клиент считает сам: от запроса до последнего байта. Для `up` скорость на стороне
  сервера — это `bytes`/`ms`.
- **Остановка TCP.** Если поток встал, клиент видит это по чтению `down`: сколько байт пришло до паузы.

## 4. UDP

1. `POST /probe/v1/udp` открывает сессию. Ответ:

   ```json
   {"token": "<16 байт, base64url>", "port": 34567, "seconds": 30, "max_rate": 1000, "budget": 67108864}
   ```

2. Клиент шлёт на `<host>:<port>` по UDP датаграммы:

   ```
   token (16) | seq (4, BE) | время клиента (8, BE, Unix ns) | время сервера (8) | заполнение
   ```

   - Не короче 36 байт; длину выбирает клиент, ею же проверяется MTU.
   - Нода отбрасывает фрагменты IPv4 и IPv6 (R4-9), поэтому датаграмма больше пути не дойдёт.
3. Сервер возвращает ту же датаграмму той же длины. В поле «время сервера» (байты 28–35) он пишет момент приёма
   (Unix ns). Время клиента возвращается как было, так что клиент считает RTT по своим часам.
4. **Кому сервер отвечает.**
   - Только датаграммам открытой сессии от первого адреса, с которого пришла датаграмма с её токеном. С других
     адресов — ничего.
   - Не больше `max_rate` датаграмм в секунду; лишние не возвращаются.
   - В пределах `budget` байт в обе стороны.
   - Неизвестный токен, короткая датаграмма, закрытая сессия — тишина.
5. `GET /probe/v1/udp?token=<token>` закрывает сессию и отдаёт счёт сервера:

   ```json
   {"received": 50, "echoed": 50, "dropped": 0, "bytes": 120000}
   ```

   - Потери вверх = отправлено − `received`.
   - Потери вниз = `echoed` − получено клиентом.
   - Без этого запроса сессия закрывается через `seconds`, а счёт хранится ещё минуту.

Токен случаен на каждую сессию: в датаграммах нет ни постоянного идентификатора, ни сигнатуры.

## 4.1. Соединения устройства (`link`)

`GET /probe/v1/link` возвращает вид сервера на TCP-соединения с адреса запроса на порт туннелей (443): то, чего
клиент сам не видит. Ответ:

```json
{"address": "198.51.100.7", "connections": 3,
 "rtt_us": {"min": 38000, "median": 41200, "max": 60000}, "min_rtt_us": 37500,
 "retrans": 12, "segs_out": 4200, "retrans_rate": 0.0029,
 "delivery_bps": {"min": 2000000, "median": 9000000, "max": 31000000}}
```

- **Только суммы и разброс.** Соединения по отдельности не выдаются: за одним адресом при CGNAT бывают чужие
  соединения. По той же причине в ответе нет объёма трафика.
- **Источник данных.** `TCP_INFO` сокетов ноды (`sock_diag`, как `ss -ti`) в момент запроса.
- **Только напрямую.** Через туннель запрос приходит с адреса самой ноды, поэтому ответ — `409`.
- **Частота.** Не чаще раза в 5 с на устройство, иначе `429`. В объём замеров не входит и замером не считается:
  `link` можно звать, пока идёт `down`, `up` или открыта сессия UDP.
- **Hysteria2** (niko-server v0.6). Поле `hysteria2` — сессии адреса на каждом сервисе Hysteria2, по ID сервиса:

  ```json
  "hysteria2": {"4": {"connections": 1, "rtt_us": {"min": 52000, "median": 52000, "max": 52000}, "min_rtt_us": 48000,
    "packets_sent": 9100, "packets_lost": 210, "loss_rate": 0.023,
    "brutal": {"connections": 1, "rate_bps": {"min": 20000000, "median": 20000000, "max": 20000000},
               "ack_rate": {"min": 0.97, "median": 0.97, "max": 0.97}}}}
  ```

  - `rtt_us` — сглаженный RTT QUIC.
  - `packets_*` и `loss_rate` — пакеты, которые сервер отправил клиенту, и потерянные из них.
  - `brutal` — соединения, где клиент передал свой темп приёма: сервер шлёт со скоростью `rate_bps` (min(темп
    клиента, `up_mbps`)). `ack_rate` — доля подтверждённых пакетов за последние секунды; по ней Brutal поднимает
    темп отправки. Если `ack_rate` долго ниже 0,9, темп, заявленный клиентом, выше того, что пропускает путь.
  - Сервис без сессий этого адреса отдаёт `connections: 0`.
  - **Свои сессии** (niko-server v0.7). Поле `own` — сессии пользователя устройства, которое спрашивает, с этого
    адреса, по одной. Нода знает сессию по паролю, с которым та авторизовалась, а устройство — по `RC1`. Поэтому
    чужие сессии за тем же CGNAT в `own` не попадают, а клиент видит `ack_rate` своей:

    ```json
    "own": [{"rtt_us": 52000, "min_rtt_us": 48000, "packets_sent": 9100, "packets_lost": 210,
             "brutal": {"rate_bps": 20000000, "ack_rate": 0.97}}]
    ```

    - `brutal` нет, если клиент не задал темп (BBR).
    - Несколько своих сессий (два устройства одного пользователя за одним адресом, переподключение) различаются по
      `rate_bps`, который клиент объявил сам, и по RTT.
    - Нода старше v0.7 или без пользователя — поля нет, остаются суммы.

## 5. Ограничения

| Что | Значение |
|---|---|
| Одновременно | один замер на устройство (TCP-запрос или сессия UDP). Второй — `429` |
| Длительность | до 30 с: сервер прекращает передачу, `down` и `up` отдают то, что успели |
| Объём | по умолчанию 1 ГиБ на устройство за сутки UTC, в обе стороны (`rayd -probe-daily-mib`). Сверх — `429` с `Retry-After` до конца суток |
| Учёт | `down`/`up` резервируют `N`, а неиспользованное возвращают. Сессия UDP резервирует min(64 МиБ, остаток) и возвращает неиспользованное |

Счётчики живут в памяти `rayd`: после перезапуска сутки начинаются заново.

## 6. Сводка от клиентов (`report`) и подсказки (R4-21)

Необязательная метрика: нода принимает отчёты, только если администратор включил приём (`rayctl summary on`).
Клиент шлёт отчёты только с согласия пользователя. Предложение клиента и правки сервера —
`docs/handoff/niko-r14-reply.md` §2–4.

### 6.1. Отчёт

`POST /probe/v1/report`, авторизация `RC1`, тело — JSON до 4 КиБ:

```json
{"v": 1, "net": "cellular", "udp_mtu": "1350-1472",
 "obs": [{"svc": 3, "result": "works", "tcp_stall_kib": 16, "udp": "0-1", "mbps": "5-20"},
         {"svc": 5, "result": "fails", "udp": "none"}]}
```

| Поле | Значения |
|---|---|
| `net` | `cellular`, `wifi`, `ethernet`, `other` |
| `obs[].svc` | ID сервиса из подписки пользователя; по одной записи на сервис, 1–16 записей |
| `obs[].result` | `works`, `degraded` (TCP работает, но поток вставал, скорость < 1 Мбит/с или потери UDP > 20 %), `fails` |
| `obs[].tcp_stall_kib` | необязательно: поток встал; порог, округлённый вниз до 8, 16, 32, 64 или 128 |
| `obs[].udp` | необязательно: потери UDP, %: `0-1`, `1-5`, `5-20`, `20-50`, `50-100`, `none` (не проходит) |
| `obs[].mbps` | необязательно: скорость вниз через туннель: `<1`, `1-5`, `5-20`, `20-100`, `100+` |
| `udp_mtu` | необязательно, о сети в целом (raycontrol v0.8): наибольшая длина эха UDP, что вернулась напрямую: `<1200`, `1200-1350`, `1350-1472`, `1472+`. Меньше 1200 — QUIC в этой сети не пройдёт |
| `path` | необязательно (raycontrol v0.10.2): `direct` или `relay` — как клиент ходит к ноде из этой сети ([`relay-v1.md`](relay-v1.md) §9.3). Без поля — `direct` |
| `obs[].dns` | необязательно (raycontrol v0.11.1), только у DNS-туннелей (`dnstt`, `masterdns`) и только с `works` или `degraded`: вид резолвера, через который туннель работает в этой сети, без адреса: `net` (DNS самой сети), `udp` (публичный резолвер по UDP 53), `doh`, `dot` |

**Необязательные поля сверх первых.** Подписка перечисляет их в `probe.report`
([`subscription-v1.md`](subscription-v1.md) §3), сейчас это `["udp_mtu", "path", "dns"]`. Клиент шлёт такое поле,
только если оно там есть. Нода без поля в списке ответит на отчёт с ним `400`, а `400` у клиента закрывает сутки.

- **Только напрямую.** Отчёт — о сети, из которой он пришёл. Через туннель запрос приходит с адреса самой ноды,
  ответ — `409`.
- **Раз в сутки на сеть.** Сеть — автономная система адреса запроса. Второй отчёт того же устройства из той же AS за
  сутки UTC — `429` с `Retry-After` до конца суток.
  - Нода помнит это в памяти, ключом суток: `HMAC(ключ суток, устройство ‖ AS)`. В конце суток ключ и набор
    выбрасываются. После перезапуска `rayd` сутки начинаются заново.
- **Строгий формат.** Неизвестные поля, значения вне списков и сервисы не из подписки пользователя — `400`.
  `kind` и `mcc_mnc` из первого предложения не принимаются. `dns` у сервиса, который не DNS-туннель, или вместе с
  `fails` — тоже `400`: туннель, который не заработал ни через один резолвер, отчитывается без `dns`.
- Ответы: `204` — принят; `404` — нода отчётов не принимает; `400`, `409`, `429` — как выше.

**Что хранит нода.** AS адреса нода находит по базе: сначала база оператора (`rayctl summary db`), затем IPinfo Lite
из релиза, затем API ipinfo, если администратор его включил. API спрашивают по сети (/24 для IPv4, /48 для IPv6),
никогда по самому адресу. Хранятся только счётчики по (сутки UTC, AS, сервис):
- число отчётов;
- типы сети;
- `result`;
- корзины `udp` и `mbps`;
- пороги `tcp_stall_kib`;
- виды резолвера `dns`;
- корзины `udp_mtu` — по AS, без сервиса.

Адрес, устройство и сам отчёт не пишутся. Счётчики живут 30 дней. Адрес без AS (частный, неизвестный) считается под
AS 0: такие отчёты не дают подсказок.

**Для тестов.** Базы отвечают за любой адрес, который в них есть, частные тоже. API спрашивают только о публичных.
Поэтому подсказки проверяются в CI так:
1. Тестовая база кладёт сеть теста в свою AS: `go run ./test/install/asndb -o asn.mmdb 172.16.0.0/12` из
   raycontrol, затем `rayctl summary db asn.mmdb`.
2. `rayctl summary on`.
3. 10 устройств шлют по отчёту.
4. Следующая подписка несёт `hints`.

Так делает тест установки raycontrol (`test/install/run.sh`).

### 6.2. Подсказка в подписке

Поле `hints` подписки ([`subscription-v1.md`](subscription-v1.md) §3) — для AS адреса, с которого клиент спросил
подписку:

```json
"hints": {"order": [3, 5, 4], "avoid": [4], "udp_blocked": true, "tcp_stall_kib": 16, "udp_mtu": "<1200", "dns": "udp", "devices": 23, "days": 7}
```

- Считается по последним 7 дням, только если из этой AS было не меньше **k = 10** отчётов. Иначе поля нет.
- `order` — сервисы пользователя, по которым есть не меньше k наблюдений. Сортировка — по доле `works`, где
  `degraded` идёт за половину.
- `avoid` — сервисы, у которых `fails` не меньше 60 %.
- `udp_blocked` — `udp: none` не меньше чем у 60 % наблюдений с `udp`.
- `tcp_stall_kib` — порог, на который пришлись не меньше 60 % наблюдений.
- `udp_mtu` — корзина, на которую пришлись не меньше 60 % отчётов с `udp_mtu` (их тоже должно быть не меньше k).
  `<1200` — QUIC (Hysteria2, naive по QUIC, DoH3) в этой AS скорее не пойдёт.
- `dns` — вид резолвера, на который пришлись не меньше 60 % рабочих наблюдений DNS-туннелей пользователя с `dns`
  (их тоже не меньше k). С него клиент начинает перебор резолверов в сети, о которой своих результатов у него нет.
- `via_relay` — отчёты из этой AS приходят в основном через relay ([`relay-v1.md`](relay-v1.md) §9.3).
- `devices` — число отчётов. Нода не различает устройства между сутками.
- Подсказка — только начальный порядок для сети, о которой у клиента нет своих результатов. Свои свежие результаты
  клиента главнее.
- Через туннель (с адреса ноды) подсказки нет.

**Администратору** (`rayctl summary`) нода показывает только сети, где не меньше k отчётов. Остальные — одной суммой.
