# Смена ключа сервиса masterdns

Статус: **черновик** (2026-11-06), на согласовании с клиентом. Касается ключа сервиса masterdns (`ENCRYPTION_KEY`,
в ссылке `niko-dnskey`, subscription-v1 §4): им masterdns шифрует кадры (метод 5, AES-256-GCM), от него выводятся
ключи печати ответов (mdseal-v1 §2).

## 1. Зачем

- Ключ сервиса есть в каждой ссылке. Утёкшая ссылка даёт всё, что даёт ссылка: собрать запрос с верной обёрткой
  (для перебора ключей dnsauth, dnsauth-masterdns §7), снять печать с подсмотренных ответов. Сейчас ключ не меняется
  никак: `rayctl service rotate` берёт только REALITY и dnstt, а пересоздание сервиса меняет и зону.
- mdseal-v1 §8: повтор 8-байтного R под одним ключом вероятен после ~2^32 ответов и открывает XOR двух заголовков
  кадров. Там сказано «лечит ротация ключа сервиса» — ротации нет.

## 2. Как меняется ключ

Как ключ печати dnstt (raycontrol v0.13.0, dnsseal-v1 §8):

```
rayctl service rotate <masterdns-сервис> [-now]
```

- Новый ключ становится текущим сразу и идёт в подписки (`niko-dnskey`).
- Прежний нода принимает ещё срок `-cred-grace` (как прежние учётные данные): клиенты, которые не перезапросили
  подписку, работают дальше. С `-now` прежний не принимается сразу (ключ в чужих руках).
- Прежний ключ один: вторая смена в пределах срока убирает тот, что был до неё.
- Ключи dnsauth (ключ устройства, K по dnsauth-v1 §2) от ключа сервиса не зависят и не меняются.

## 3. Нода

- **Файл ключа** (`encryption_key_file`): по ключу на строку, первым текущий, следом прежний. Сейчас в файле один
  ключ — это тот же формат с одной строкой.
- **Сервер masterdns (форк):**
  - Запрос открывается текущим ключом, а если метка AES-GCM не сошлась — прежним. Какой ключ открыл, тот и ключ
    запроса. Неоткрытый ни одним — как сейчас.
  - Сессия привязана к ключу, которым открыт её SESSION_INIT. Её запросы открываются и ответы шифруются и печатаются
    (mdseal-v1: Kd, Kdt от этого ключа) только им. Запрос сессии, открытый другим ключом, сессии не касается.
  - Ответ до сессии (пробы MTU, ERROR_DROP по неизвестной сессии) — ключом запроса.
  - Файл перечитывается при изменении содержимого, без перезапуска (как ключи печати dnstt в niko-server v0.10.0):
    живые сессии на прежнем ключе не рвутся. Если форку проще читать ключи только при старте, raycontrol перезапускает
    бэкенд при смене — сессии переподключаются, прежний ключ ещё принимается.
- **Цена:** запрос на прежнем ключе — одна лишняя неудачная проверка AES-GCM (доли микросекунды), только в сроке.

## 4. Клиент

Нового ничего: клиент, который получил новый `niko-dnskey`, открывает сессии новым ключом. Клиент, который подписку
не перезапросил, работает прежним, пока он принимается; потом все его пробы получают пустой ответ, и он
перезапрашивает подписку (dnsauth-masterdns §6, «все пробы MTU пусты»).

## 5. Что менять

- **Форк (клиент):** сервер — несколько ключей (текущий и прежний) из файла, привязка сессии к ключу, перечитывание
  файла; клиент — без изменений.
- **niko-server:** `encryption_key_file` с одной или двумя строками; проверка значений; передача ключей в форк.
- **raycontrol:** `rayctl service rotate <mdns> [-now]`, состояние смены (как `SealState` у dnstt), снятие прежнего
  ключа по сроку, файл с двумя строками, подписка с новым ключом.
