# rules-v1: наборы правил через ноду и правила администратора

Статус: **черновик** (2026-11-16), ничего не сделано. Решения владельца — 2026-11-14
([19-mihomo-review](../19-mihomo-review.md) §10) и 2026-11-16 через клиента (§13; [08-decisions](../08-decisions.md)
R4-44). Сторона клиента — `niko:docs/design/ROUTING-APPS.md` (ветка `claude/intelligent-allen-0oa8na`, `8992d8f`),
дальше «ROUTING-APPS»; репозиторий списков — `arngory/niko-routes` (README `1fe9810`), дальше «niko-routes». Вход на
relay, который пользуется этими списками, — [relay-entry-v1](relay-entry-v1.md). Пометка «(вывод)» — не проверено ни
кодом, ни тестом.

Зачем:
- Niko качает наборы правил (`.srs`) с GitHub через туннель. Через DNS-туннель список в 500 КБ идёт минуту, а пока
  списка нет, сервисы идут не тем путём (19-mihomo-review §3.1, ROUTING-APPS §1).
- Владелец хочет списки по приложениям, а не по доменам: при разбивке по доменам сервис видит два адреса.
- Администратор ноды должен задавать маршрут, который пользователь не перепишет парой кнопок (решение владельца
  2026-11-16, §6.4).

## 1. Коротко

- **Списки** ведёт отдельный публичный репозиторий `arngory/niko-routes`: запись на приложение или сервис, сборка в
  CI, два ключа подписи — ключ списков у человека и ключ свежести в CI (§2, §3).
- **Нода — зеркало**, как у релизов Niko ([app-update-v1](app-update-v1.md)): сама берёт файлы с GitHub, проверяет
  обе подписи встроенными ключами и отдаёт на порту подписки. Какие наборы отдавать, выбирает администратор. По
  умолчанию выключено (§4).
- **Подписка** несёт необязательное поле `rules`: ссылки на подписанные файлы и правила администратора `enforce` —
  `block`, `node`, `relay`, `direct` (§5, §6).
- **Клиент** проверяет подписи и хеши сам, версии только растут, заморозку ловит сверкой с GitHub (§7).

## 2. Репозиторий списков

Владелец: «ок» 2026-11-16 (§13). Здесь — то, на что опирается нода; окончательный формат записи и CI — в
niko-routes.

### 2.1. Запись

Один файл на приложение или сервис, `apps/<страна>/<id>.yaml`:

| Поле | Смысл |
|---|---|
| `name` | имя для показа |
| `country` | ISO 3166-1 alpha-2, строчными |
| `kind` | `inside-only` — работает только изнутри страны (сверяет страну адреса); `blocked` — заблокировано в стране; `ads` — реклама и трекеры |
| `android` | имена пакетов |
| `windows` | имена исполняемых файлов |
| `domains` | суффиксы имён |
| `asn` | номера AS самого владельца сервиса |
| `cidr` | явные подсети, если своей AS нет |
| `evidence` | ссылка или запись трафика, где видны имена и адреса |

### 2.2. Проверки CI

На каждый PR и по расписанию:
- схема; конфликты (одно имя или подсеть под двумя `kind`) и имена, общие для многих приложений;
- AS разворачиваются в подсети по таблицам RouteViews (§2.5);
- **подсети CDN и общих облаков не принимаются**: адрес там общий, подсеть потянула бы чужие сайты. Такие части
  сервиса ловятся только по имени. Список CDN и облаков ведётся в самом репозитории;
- подсеть шире /16 для IPv4 и запись без `evidence` не принимаются.

### 2.3. Что собирает CI

Из одних YAML, в одном запуске:

- **Для клиента** — `.srs` sing-box: по одному на приложение и по одному на `kind` и страну. Версия формата — та,
  что читает ядро клиента (форк sing-box 1.14: `RuleSetVersionCurrent` = 5). Это выбор клиента и CI списков.
- **Для сервера** — текст `<tag>.txt`, тот же набор. Нода и relay не разбирают succinct-деревья `.srs`
  (19-mihomo-review §8: `rayd` не тянет sing-box). Формат:
  - строки `suffix:<домен>` и `cidr:<префикс>`;
  - домены строчными, IDN — A-метками (`xn--…`); префиксы канонические (биты хоста обнулены);
  - строки отсортированы, без повторов; UTF-8, конец строки LF, комментариев нет.

  Разбор строгий: неизвестный префикс строки, пустая строка, неканонический префикс — файл отвергается целиком.
- **Наборы стран** — `country-<cc>.txt` и `country-<cc>.srs` (§2.4).

Сборка воспроизводима: из того же коммита и тех же входных данных — те же байты (требование niko-routes).

### 2.4. Наборы стран

Подсети каждой страны по открытым данным. Нужны relay ([relay-entry-v1](relay-entry-v1.md) §7) и клиенту.

- Текст — только строки `cidr:`, слитые и свёрнутые (`collapse`).
- **Адрес входит в набор, только если обе базы относят его к стране** — делегирования RIR (delegated-extended всех
  пяти RIR, сводный файл NRO) **и** IPinfo Lite. Пересечение, а не объединение. Ошибки двух видов стоят по-разному:
  иностранный адрес, принятый за свой, открыл бы relay наружу; свой адрес, принятый за чужой, только отправит
  соединение через узел.
  - RIR пишет страну держателя ресурса, а не сети ([11-asn-sources](../11-asn-sources.md) §2.8). IPinfo Lite —
    страну сети. Пересечение отсекает и адреса держателя за границей, и чужие сети, которые IPinfo видит в стране.
- Вычитаются: подсети CDN и облаков (тот же список, что в §2.2), частные, служебные (RFC 6890) и bogon.
- **Предохранитель:** если набор страны между версиями изменился больше чем на 5 % своих адресов, CI требует в PR
  явной записи человека, почему.
- Размер, для оценки: в сводном файле NRO на 2026-11-16 у RU 11 468 записей IPv4 (8 676 префиксов после слияния,
  45,3 млн адресов) и 2 169 префиксов IPv6; у KZ — 617 и 98, у IR — 1 747 и 578 (подсчёт этой сессии). Пересечение с
  IPinfo дробит префиксы, сколько станет — не проверено.

Что следует:
- **Наборы стран — под CC BY-SA 4.0** с атрибуцией IPinfo («IP address data is powered by IPinfo») и пометкой,
  что данные изменены (пересечение, вычитания). ShareAlike касается этих файлов, а не кода raycontrol и Niko.
- Подсети из AS — с атрибуцией RouteViews.
- Снимок наборов стран в APK — тоже под CC BY-SA 4.0: атрибуция в разделе «О программе» (дело клиента).
- Лицензия самих записей YAML — выбор niko-routes. Каждый файл в манифесте называет свою (§3.1, поле `license`).

### 2.6. Где файлы на GitHub

Предложение; окончательно — в niko-routes:
- манифест, его подпись и все файлы версии — ассеты выпуска `m<версия>`:
  `https://github.com/arngory/niko-routes/releases/download/m<версия>/<имя>`;
- `timestamp.json` и его подпись — в ветке `timestamp`:
  `https://raw.githubusercontent.com/arngory/niko-routes/timestamp/timestamp.json`.

Нода ходит туда своей сетью, TLS — по встроенному списку корней (R4-41).

## 3. Подписи и ключи

Как роли content и timestamp в TUF. Подпись — minisign, как у релизов raycontrol и Niko.

### 3.1. `manifest.json`

```json
{"v": 1, "version": 1042, "issued": 1767225600,
 "freshness_keys": ["RW…", "RW…"],
 "files": [
  {"name": "ru-inside-only.srs", "sha256": "…", "size": 41234, "kind": "inside-only", "country": "ru", "form": "srs", "license": "CC-BY-SA-4.0"},
  {"name": "ru-inside-only.txt", "sha256": "…", "size": 52011, "kind": "inside-only", "country": "ru", "form": "text", "license": "CC-BY-SA-4.0"},
  {"name": "country-ru.txt", "sha256": "…", "size": 180412, "kind": "country", "country": "ru", "form": "text", "license": "CC-BY-SA-4.0"}]}
```

| Поле | Смысл |
|---|---|
| `version` | номер версии, только растёт |
| `issued` | время сборки, unix-секунды; только для показа |
| `freshness_keys` | открытые ключи minisign, которыми можно подписывать `timestamp.json` этой версии (§3.3) |
| `files[].name` | имя файла: `<tag>.srs` или `<tag>.txt`, только `[a-z0-9._-]` |
| `files[].sha256`, `size` | хеш (hex) и размер в байтах |
| `files[].kind` | `inside-only` \| `blocked` \| `ads` \| `country` |
| `files[].country` | страна, строчными; пусто — набор не привязан к стране |
| `files[].form` | `srs` (для клиента) \| `text` (для сервера, §2.3) |
| `files[].license` | идентификатор SPDX |

- Подпись — `manifest.json.minisig`, **ключом списков**. Доверенный комментарий — ровно `niko-routes manifest
  <version>`, как `niko <tag>` у релизов Niko (app-update-v1 §3): подпись одной версии не выдать за другую.
- Предел — 1 МиБ на манифест, 32 МиБ на файл (столько же берёт клиент, 19-mihomo-review §3.1).
- Неизвестные поля пропускаются; неизвестный `kind` или `form` — файл пропускается, манифест остаётся годным.

### 3.2. `timestamp.json`

```json
{"v": 1, "version": 57, "manifest": {"version": 1042, "sha256": "…"}, "signed": 1767225600, "expires": 1768435200}
```

- `version` — свой номер, только растёт; `manifest` — номер и SHA-256 текущего манифеста; `signed` — время подписи;
  `expires` — `signed` плюс 14 дней.
- Подпись — `timestamp.json.minisig`, **ключом свежести**. Доверенный комментарий — `niko-routes timestamp
  <version>`.
- Ключей в нём нет.
- Предел — 4 КиБ.

### 3.3. Два ключа

- **Ключ списков** подписывает манифест при выпуске версии, после PR с ревью двух людей. Задача с ним идёт в
  окружении GitHub с обязательным одобрением человека: каждый выпуск подтверждает человек. Ключ заводит и добавляет
  владелец (решение 2026-11-16, §13).
- **Ключ свежести** подписывает `timestamp.json` по расписанию, раз в 7 дней, даже если списки не менялись.
  - Он лежит не в секретах репозитория, а в окружении GitHub, куда допущена только ветка `main`. Окружение
    ограничивается по веткам, а не по событиям, поэтому задача с ключом сама требует
    `github.event_name == 'schedule'`. `pull_request_target` и `workflow_dispatch` в этом workflow запрещены.
  - Задача коммитит `timestamp.json` в ветку `timestamp` без защиты ревью. Это явное исключение из правила двух
    ревью, только для этого файла: целостность списков держит подпись ключа списков, которого у CI нет, а не защита
    ветки. `main` и теги защищены правилами.
  - Коммит заодно — активность: GitHub выключает расписание публичного репозитория после 60 дней без активности.
    Считается ли коммит от `github-actions[bot]`, не проверено (§15). Если расписание встанет, тревогу поднимет нода
    (§4.4).
  - **Утечка ключа свежести даёт только заморозку**: продлить срок старой версии, но не изменить списки.
- `contents: write` у задачи — на весь репозиторий: одной веткой его не ограничить. Целостность это не ломает
  (подписи), но задача может портить ветки и ассеты выпусков — отказ в обслуживании.

### 3.4. Смена ключей — только уровнем выше

Роль не меняет свой ключ сама.
- **Ключи списков** встроены в raycontrol и в сборку Niko, и только там: для каждой роли — список ключей. Смена —
  выпуском обоих, заранее: новый ключ появляется в списке рядом со старым, старый уходит следующим выпуском.
- **Ключи свежести** перечислены в подписанном манифесте (`freshness_keys`). Отзыв ключа свежести — новый манифест
  без него. Так утёкший ключ свежести не добавит свой ключ и не переживёт отзыв.
- Ключи релизов Niko (app-update-v1) и raycontrol для списков не годятся, и наоборот.

### 3.5. Порядок проверки (нода, relay и клиент — одинаково)

1. Прочитать `timestamp.json` без доверия: узнать, какой манифест он называет.
2. Взять этот манифест. Проверить подпись **ключом списков** (встроенный список), доверенный комментарий и что
   `version` не ниже принятой.
3. Проверить подпись `timestamp.json` **ключами свежести из этого манифеста**, доверенный комментарий, `version` не
   ниже принятой.
4. `manifest.sha256` из `timestamp.json` должен совпасть с SHA-256 байтов манифеста, `manifest.version` — с его
   `version`.
5. Пределы свежести. `timestamp.json` отвергается, если `expires` позже `signed` больше чем на 14 дней или `signed`
   впереди часов больше чем на 2 дня. Нода и relay берут свои часы; клиент — `Date` GitHub с монотонным временем
   (§7.3).
6. Каждый файл — SHA-256 и размер из манифеста.

Так новая версия с новым ключом свежести проходит сразу, а тот, кто принял манифест с отзывом, отозванному ключу
больше не верит. Тому, кому манифест с отзывом не дошёл, отозванный ключ ещё может подписывать свежесть старой
версии: это закрывает сверка клиента с GitHub (§7.3).

Манифест с той же `version`, но с другим SHA-256, — отказ и событие: у одной версии не может быть двух манифестов.

## 4. Зеркало на ноде

Тот же образец, что зеркало релизов Niko (app-update-v1 §3).

### 4.1. Включение и выбор наборов

- `rayctl rules mirror on|off`. **По умолчанию выключено**, как всё новое. `on` требует 256 МиБ свободного места в
  `/var/lib/raycontrol`; `off` удаляет скачанное и убирает поле `rules` из подписки.
- Какие наборы нода отдаёт, выбирает администратор (решение 2026-11-14): `rayctl rules enable <tag>…`,
  `disable <tag>…`. Тег — имя файла `.srs` из манифеста без расширения. Сразу после `on` не включён ни один.
- Если у ноды есть relay со включённым входом ([relay-entry-v1](relay-entry-v1.md) §3), нода держит ещё текстовые
  наборы, которые нужны этим relay: `inside-only` и `country` их стран. Без отдельного выбора.

### 4.2. Когда нода ходит на GitHub

- `timestamp.json` — сразу после `on`, затем раз в сутки (со случайным сдвигом до часа). Когда до `expires` остаётся
  меньше половины срока (`expires − signed`), — раз в час.
- Манифест — только когда `timestamp.json` называет другую версию или другой SHA-256.
- Файлы — только включённые наборы (и текст для relay, §4.1), которых у неё ещё нет. Файл с тем же SHA-256 не
  качается второй раз.
- Не прошло (подпись, хеш, размер, версия ниже принятой) — версия не принимается, остаётся прежняя, ошибка видна в
  `rayctl rules`. Не докачано (сеть) — повтор при следующей проверке.
- Новая версия собирается во временном каталоге и переносится на место целиком, как у app-update-v1.
- Назад нода не идёт: принятая версия манифеста и `timestamp.json` хранится отдельно от файлов, ниже неё ничего не
  ставится.
- При старте `rayd` проверяет то, что лежит на диске: подписи, хеши. Что не сошлось — удаляет и берёт заново.

### 4.3. Что нода отдаёт

На порту подписки, с тем же TLS по пину, SPA v2, `Authorization: RC1 …` и `X-Raycontrol-Device`, что у `/sub/v1`
и `/app/v1` (subscription-v1 §2, app-update-v1 §2):

| Путь | Что |
|---|---|
| `/rules/v1/t/<version>.json` и `.json.minisig` | принятый `timestamp.json` и подпись, байты как с GitHub |
| `/rules/v1/m/<version>.json` и `.json.minisig` | принятый манифест и подпись |
| `/rules/v1/<sha256>.srs` | включённый набор для клиента |

- Без авторизации, при выключенном зеркале, на неизвестный путь и на файл не из включённых — `404`, как у подписки.
  Редиректов нет.
- `Range`, `ETag`, `429` и обрыв медленной загрузки — как у `/app/v1` (app-update-v1 §2), в одном счёте загрузок
  устройства с ним.
- Файлы прежней версии нода отдаёт ещё 72 ч после смены — срок жизни подписки: клиент с прежней подпиской докачает
  то, что она называет.
- Текстовые наборы на порту подписки не отдаются: они нужны relay, не клиенту. Relay берёт их по `RelayService`
  (relay-entry-v1 §8).
- Через relay `/rules/v1` работает, как `/sub/v1`: relay пересылает порт подписки на уровне L4.

### 4.4. Истёкший срок и события

- `timestamp.json` с истёкшим `expires` нода всё равно отдаёт: решает клиент (§7.3).
- `rayctl status`, цикл `rules`:
  - за 3 дня до `expires`: `rules: the lists' freshness ends <дата>; last fetched from GitHub <дата>`;
  - после `expires`: `rules: the lists expired <дата>; last fetched from GitHub <дата>`;
  - отказ версии: что не прошло (подпись, хеш, версия), без содержимого.
- В журнал `rayd` — то же, не чаще строки в час.

## 5. Поле `rules` в подписке

Необязательное поле payload (subscription-v1 §3), под подписью ноды:

```json
"rules": {"v": 1,
  "timestamp": {"version": 57, "path": "/rules/v1/t/57.json", "sig": "/rules/v1/t/57.json.minisig"},
  "manifest": {"version": 1042, "sha256": "…", "path": "/rules/v1/m/1042.json", "sig": "/rules/v1/m/1042.json.minisig"},
  "sets": [
    {"tag": "ads", "sha256": "…", "size": 90211, "path": "/rules/v1/<sha256>.srs"},
    {"tag": "ru-blocked", "sha256": "…", "size": 412345, "path": "/rules/v1/<sha256>.srs"},
    {"tag": "ru-inside-only", "sha256": "…", "size": 41234, "path": "/rules/v1/<sha256>.srs"},
    {"tag": "office", "sha256": "…", "size": 1180, "path": "/rules/v1/<sha256>.srs"}],
  "enforce": [
    {"set": "ads", "action": "block"},
    {"set": "ru-blocked", "action": "node"},
    {"set": "ru-inside-only", "action": "relay", "relay": "r1", "fallback": "none"},
    {"set": "office", "action": "direct"}]}
```

| Поле | Смысл |
|---|---|
| `v` | версия поля; внутри `v` = 1 появляются только новые необязательные поля. Неизвестную `v` клиент пропускает целиком |
| `timestamp` | принятый нодой `timestamp.json`: его `version` и пути к файлу и подписи |
| `manifest` | принятый манифест: `version`, `sha256`, пути |
| `sets[]` | наборы, которые нода отдаёт: `tag`, `sha256`, `size`, `path`. Только формы `srs` |
| `enforce[]` | правила администратора (§6), по порядку |
| `enforce[].set` | `tag` из `sets[]` |
| `enforce[].action` | `block` \| `node` \| `relay` \| `direct` |
| `enforce[].relay` | только у `relay`: `id` из `relays[]` |
| `enforce[].fallback` | только у `relay`: `none` (по умолчанию) \| `node` |

- `kind` в `sets[]` нет и не будет. `kind` клиент берёт только из подписанного манифеста, находя файл по SHA-256.
  Если в `sets[]` понадобится свойство файла, это `behavior` (`domain` \| `ipcidr` \| `mixed`), не `kind`.
- **Свои наборы ноды** — `.srs`, которые администратор кладёт сам (`rayctl rules own add`, §8). Их нет в манифесте:
  клиент узнаёт их по SHA-256, которого в манифесте нет. Подписаны только подписью ноды.
- Поля нет: зеркало выключено, ещё ничего не принято или нода старше.
- Поле отдаётся всем активным устройствам, как `app`: в файлах списков нет ничего, чего нет на GitHub. Свои наборы
  ноды видит каждое устройство её пользователей.

## 6. Правила администратора (`enforce`)

### 6.1. Общее

- Все правила `enforce` стоят **выше правил пользователя**, в порядке массива. Клиент показывает каждое с замком и
  действием («Задано подпиской»), пользователь их не меняет.
- `block` (отбросить), `node` (через узел) и `direct` (напрямую, мимо туннеля) применяются к любому набору, в том
  числе к своим наборам ноды.
- Неизвестное действие клиент пропускает (правило целиком).
- Порядок правил на клиенте — его решение (ROUTING-APPS §5); на сегодня:
  1. `enforce`, по порядку;
  2. свои правила пользователя по приложениям; приложение с таким правилом выпадает из списков (п. 3);
  3. приложения из включённых списков — целиком одним путём;
  4. остальные свои правила пользователя;
  5. имена и подсети сервисов из списков — для остальных приложений;
  6. пресет страны;
  7. остальное — через узел.

### 6.2. `relay`

`relay` — обычное правило администратора, выше правил пользователя: трафик набора идёт на вход relay
([relay-entry-v1](relay-entry-v1.md)), который выпускает его в стране relay.

- **Только на набор с `kind: inside-only` из манифеста под ключом списков**, той же страны, что relay
  (`relays[].local.country`). Это защищает сам relay: в стране пользователя он не должен становиться прокси для
  того, что от этой страны прячут. Вход relay отвергнет чужое и сам (relay-entry-v1 §7), а проверка здесь убирает
  непонятные отказы:
  - клиент правило `relay` на другой набор (на `blocked`, на свой набор ноды, на набор другой страны) отбрасывает и
    показывает предупреждение;
  - `rayctl` такое правило не строит (§8);
  - нода, у которой новый манифест сделал набор не `inside-only` (или набора больше нет), правило в подписку не
    кладёт, хранит его и поднимает событие в `rayctl status`: `rules: enforce relay on <tag> is not published:
    <причина>`.
- `fallback` — что делать, когда вход relay не отвечает:
  - `none` (по умолчанию) — отказ. Сервисы inside-only смотрят на страну адреса, и вход в банк с иностранного адреса
    грозит блокировкой счёта: это хуже отказа. Так же владелец решил 2026-11-14 для недоступного выхода ноды;
  - `node` — через узел; ставит администратор на наборы, где иностранный адрес безвреден;
  - `direct` не бывает. Другое значение — клиент читает как `none`.
- Нет `relays[].local` у этого relay (вход выключен или relay не докладывает) — правило остаётся в подписке, клиент
  применяет `fallback`. Убрать правило значило бы отдать трафик правилам пользователя, то есть, может быть, за
  границу.
- Ответ входа `403` с `Niko-Refused: policy` для назначения из набора inside-only клиент тоже считает отказом по
  `fallback` этого набора (relay-entry-v1 §14).

### 6.3. `direct`

Решение владельца 2026-11-16 (R4-44, цитата — §13): у администратора все возможности, клиент по архитектуре
недоверенный.

- `direct` отправляет набор **мимо туннеля**, с домашнего адреса пользователя.
- **Цена, открыто.** Администратор подписки — или тот, кто взломал ноду, — может отправить выбранные сайты напрямую
  и открыть им домашний адрес пользователя. Ни подпись подписки, ни ключ списков от этого не защищают: набор может
  быть своим набором ноды. Доверяя подписке, пользователь доверяет её администратору. Кому нужна независимость —
  ставит свой raycontrol и Niko.
- Так же `node` и `relay` перекрывают свои правила пользователя: приложение, которое пользователь сам отправил через
  узел, чтобы скрыть от своей страны, нода может перевести на relay в этой стране. Тогда назначения увидят оператор
  relay и провайдер страны.
- Клиент показывает каждое правило ноды, `direct` тоже, и справка объясняет цену (ROUTING-APPS §5). Это
  прозрачность, а не защита.
- На ноде `direct` — явное действие (§8): подтверждение, строка аудита, видно в `rayctl status`.

### 6.4. Чем это отличается от прежней позиции

[19-mihomo-review](../19-mihomo-review.md) §3.2 и §7 п. 6 говорили: нода приносит списки, а правил, которые меняют
выход, не присылает. Владелец решил иначе (2026-11-16, R4-44): цель ноды — hardening, и маршрут, который нужен
ноде, обычный пользователь парой кнопок не перепишет. Действует R4-44 (08 главнее остальных документов).

## 7. Что проверяет клиент (договор)

Сторона клиента — ROUTING-APPS §3, §5. Здесь — то, на что нода может рассчитывать.

### 7.1. Подписи и хеши

- Порядок §3.5, встроенные ключи списков — свои, в сборке Niko.
- Каждый файл из `sets[]` — SHA-256 и размер до того, как его увидит ядро.
- Набор из `rules` и набор пресета страны совпадают **по SHA-256, а не по тегу**: файл с тем же хешем не качается
  второй раз.
- Если порт подписки недоступен — файлы с GitHub через туннель, с теми же проверками.

### 7.2. Версии

- Принятые `version` манифеста и `timestamp.json` только растут. С ноды и с GitHub ниже принятой не ставится.
- Исключение — аварийный снимок из APK, когда на диске нет проверенной версии: принятый номер при этом не меняется
  (ROUTING-APPS §3).

### 7.3. Свежесть

- **Время ноды не хранится и ничего не откладывает.** `issued` из подписи ноды (subscription-v1 §3) — не довод:
  замораживающая нода подпишет любое время, а нода с часами в 2099 году не должна навсегда зажечь тревогу. `issued`
  позже `expires` — только повод сходить на GitHub раньше. Нода `issued` по-прежнему шлёт.
- **Раз в 7 дней, без часов:** клиент сам берёт `timestamp.json` с GitHub через туннель. Если там версия новее, чем
  отдаёт нода, клиент берёт её (с теми же проверками §3.5) и показывает «нода отдаёт старые списки».
- **По сроку:** когда `expires` прошёл по часам устройства, клиент сверяет его с `Date` от GitHub. Решает `Date`.
- **Неудача сверки — тоже тревога:** туннель держит нода, и проверку она может ронять. Две неудачи подряд или 14 дней
  без удачной — «списки, возможно, устарели: проверить не удалось». Сами списки продолжают работать.
- **Предел свежести:** время подписи `timestamp.json` клиент сверяет не с часами телефона, а с последним `Date`
  GitHub плюс монотонное время с него; впереди больше чем на 2 дня — отказ. Как это переживает перезагрузку — у
  клиента (ROUTING-APPS §3).

Что это даёт: нода не может откатить списки; заморозку старой версии с утёкшим ключом свежести ловит еженедельная
сверка, а если нода роняет GitHub — тревога «проверить не удалось» не позже чем через 14 дней.

### 7.4. `enforce`

- Правило со ссылкой на `tag`, которого нет в `sets[]`, пропускается.
- `relay` — проверки §6.2. `kind` и `country` — только из манифеста по SHA-256.
- Новые соединения идут по новым правилам; приложения, у которых сменился маршрут, переподключаются (у клиента).

## 8. `rayctl` (набросок)

```
rayctl rules                              # зеркало, принятые версии, signed/expires, последняя удачная проверка, ошибка
rayctl rules mirror on|off                # по умолчанию off; off удаляет файлы
rayctl rules sets                         # наборы принятого манифеста: tag, kind, country, размер, отдаётся ли
rayctl rules enable|disable TAG…          # какие наборы отдавать
rayctl rules own add TAG FILE.srs         # свой набор ноды (только block, node, direct)
rayctl rules own remove TAG
rayctl rules enforce                      # правила по порядку, с причиной, если правило не публикуется
rayctl rules enforce add [-at N] -action block|node SET
rayctl rules enforce add [-at N] -action relay -relay NAME [-fallback none|node] SET
rayctl rules enforce add [-at N] -action direct [-yes-direct] SET
rayctl rules enforce remove N
```

- Права — как у `rayctl app-mirror`: root или группа `raycontrol` на ноде, admin-устройства через API
  (`-remote`). Каждое изменение — в аудит: `rules.mirror`, `rules.sets`, `rules.own`, `rules.enforce` с тегом
  набора и действием, без содержимого наборов и без назначений.
- `enforce add -action relay` отказывает, если:
  - набор не из манифеста или его `kind` не `inside-only`;
  - страна набора — не страна relay (`rayctl relay list`, relay-entry-v1 §17);
  - relay с таким именем нет.

  Если вход relay выключен, правило принимается с предупреждением: клиент применит `fallback`.
- `enforce add -action direct`:
  - без `-yes-direct` спрашивает подтверждения в терминале; без терминала и без флага — отказ;
  - печатает, что это значит: `direct sends the set's traffic outside the tunnel, from the user's own address:
    the sites in it see where the user is. Users see this rule locked in Niko.`;
  - строка аудита `rules.enforce add direct <tag>`;
  - `rayctl status` перечисляет действующие правила `direct`: `rules: direct for <tag>, <tag>`.
  Через API — поле `yes_direct` в запросе; без него — `FailedPrecondition` с тем же текстом.
- API (`node.v1`, только добавления): `GetRules`, `SetRulesMirror`, `SetRuleSets`, `SetOwnRuleSet`,
  `SetEnforce` — имена при реализации.

## 9. Что нода хранит

- `settings`: `rules_mirror=on`, включённые теги, правила `enforce` (JSON, по порядку).
- `/var/lib/raycontrol/rules/` (rayd, 0600): принятые `timestamp.json`, манифест, подписи; файлы по SHA-256; свои
  наборы ноды. Прежняя версия — 72 ч (§4.3).
- Резервная копия (R4-13) несёт настройки и свои наборы; файлы списков — нет, нода берёт их заново.

## 10. Кто что может

Полная таблица вместе с relay — [relay-entry-v1](relay-entry-v1.md) §15. По спискам и подписке:

| Кто | Может | Не может |
|---|---|---|
| Взломанная нода | всё, что может администратор: `block`, `node`, `relay`, `direct` на любые наборы, свои наборы (§6.3); заморозить списки до сверки клиента с GitHub (§7.3); не отдавать `rules` | подменить файлы списков (ключ списков); откатить версию ниже принятой; дать `relay` на набор не `inside-only` (проверяет клиент и сам relay) |
| Утёкший ключ свежести | заморозить: продлевать старую версию | изменить списки; добавить ключ; пережить отзыв у того, кто принял новый манифест |
| Утёкший ключ списков | подписать любые списки: пометить сайт `inside-only` (клиенты с пресетом пойдут к нему напрямую, провайдер увидит), расширить, что выпускает relay; сменить ключи свежести | ничего сверх этого: ключ — вершина доверия. Отзыв — выпуск raycontrol и Niko без него |
| Запись в niko-routes без ключей | отказ в обслуживании: сломать расписание, удалить ветку `timestamp`, испортить ассеты | подписать что-либо |

## 11. Текст для гайда и шпаргалки

Когда команды появятся, в [cheatsheet](../cheatsheet.md) и гайд — то же, что здесь, прямо:

> `rayctl rules enforce add -action direct SET` — трафик набора у ваших пользователей идёт мимо туннеля, с их
> домашнего адреса: сайты из набора видят, где пользователь. Niko показывает это правило с замком. Пользователь,
> которому это не подходит, может поставить свой raycontrol.

## 12. Версии и совместимость

- raycontrol: зеркало, `rules` в подписке, `/rules/v1`, `rayctl rules` — одним выпуском (номер при реализации).
  Старая нода поля не шлёт, на `/rules/v1` отвечает `404`.
- Niko: читает `rules` после своей версии с ROUTING-APPS. Старый клиент поле пропускает (subscription-v1:
  необязательные поля добавлялись много раз).
- Вход relay — [relay-entry-v1](relay-entry-v1.md); без него `relay` в `enforce` работает как вход, который не
  отвечает (`fallback`).

## 15. Не проверено

- Считает ли GitHub коммит от `github-actions[bot]` активностью, которая держит расписание (§3.3). Официальная
  документация говорит только «no repository activity … in 60 days».
- Сколько префиксов будет у наборов стран после пересечения с IPinfo Lite (§2.4).
- Что ядро клиента перечитывает изменённый `.srs` без разрыва соединений — со слов клиента (ROUTING-APPS §3).
- Условия IPinfo: CC BY-SA 4.0 и FAQ «within a product» против общих ToS «internal business purposes»
  (11-asn-sources §2.2): формулировки расходятся.
- Нужен ли токен IPinfo для скачивания Lite — по странице так (`?token=`), без аккаунта не пробовали.
