# rules-v1: наборы правил через ноду и правила администратора

Статус: **черновик** (2026-11-16), ничего не сделано. Решения владельца — 2026-11-14
([19-mihomo-review](../19-mihomo-review.md) §10) и 2026-11-16 через клиента (§13; [08-decisions](../08-decisions.md)
R4-44). Сторона клиента — `niko:docs/design/ROUTING-APPS.md` (ветка `claude/intelligent-allen-0oa8na`, `24e69d3`),
дальше «ROUTING-APPS»; репозиторий списков — `arngory/niko-routes` (README `02c189a`), дальше «niko-routes». Вход на
relay, который пользуется этими списками, — [relay-entry-v1](relay-entry-v1.md). Пометка «(вывод)» — не проверено ни
кодом, ни тестом.

Зачем:
- Niko качает наборы правил (`.srs`) с GitHub через туннель. Через DNS-туннель список в 500 КБ идёт минуту, а пока
  списка нет, сервисы идут не тем путём (19-mihomo-review §3.1, ROUTING-APPS §1).
- Владелец хочет списки по приложениям, а не по доменам: при разбивке по доменам сервис видит два адреса.
- Администратор ноды должен задавать маршрут, который пользователь не перепишет парой кнопок (решение владельца
  2026-11-16, §6.4).

## 1. Коротко

- **Списки** ведёт отдельный публичный репозиторий `arngory/niko-routes`: запись на приложение или сервис, сборка в
  CI, два ключа подписи — ключ списков у человека и ключ свежести в CI (§2, §3).
- **Нода — зеркало**, как у релизов Niko ([app-update-v1](app-update-v1.md)): сама берёт файлы с GitHub, проверяет
  обе подписи встроенными ключами и отдаёт на порту подписки. Какие наборы отдавать, выбирает администратор. По
  умолчанию выключено (§4).
- **Подписка** несёт необязательное поле `rules`: ссылки на подписанные файлы и правила администратора `enforce` —
  `block`, `node`, `relay`, `direct` (§5, §6).
- **Клиент** проверяет подписи и хеши сам, версии только растут, заморозку ловит сверкой с GitHub (§7).

## 2. Репозиторий списков

Владелец: «ок» 2026-11-16 (§13). Здесь — то, на что опирается нода; окончательный формат записи и CI — в
niko-routes.

### 2.1. Запись

Один файл на приложение или сервис, `apps/<страна>/<id>.yaml`:

| Поле | Смысл |
|---|---|
| `name` | имя для показа |
| `country` | ISO 3166-1 alpha-2, строчными |
| `kind` | `inside-only` — работает только изнутри страны (сверяет страну адреса); `blocked` — заблокировано в стране; `ads` — реклама и трекеры |
| `android` | `[{package, cert_sha256: [...]}]` — пакет и SHA-256 сертификатов его подписи (несколько — при ротации ключа подписи) |
| `windows` | имена исполняемых файлов |
| `domains` | суффиксы имён |
| `asn` | номера AS самого владельца сервиса |
| `cidr` | явные подсети, если своей AS нет |
| `cdn` | имена провайдеров CDN и облаков из списка репозитория, на которых живут имена записи (§2.2) |
| `cname` | цели CNAME, по которым relay идёт, резолвя имена записи (суффиксы целей); другие цели — отказ (relay-entry-v1 §9.2) |
| `superapp` | `true` — во встроенном браузере или мини-приложениях открываются чужие сайты (§2.2) |
| `evidence` | ссылка или запись трафика, где видны имена и адреса |

**Подпись пакета обязательна.** Niko помечает соединение тегом набора, только если подпись установленного пакета
совпала с `cert_sha256` записи ([app-attest-v1](app-attest-v1.md) §5). Иначе приложение, поставленное в обход
магазина под именем пакета банка, получило бы тег `inside-only`, и вход relay выпустил бы его целиком: открытый
прокси для этого пользователя (relay-entry-v1 §15). У `windows` такой проверки нет; компьютер и так
«неподтверждённый» (app-attest-v1 §6).

### 2.2. Проверки CI

На каждый PR и по расписанию:
- схема; конфликты (одно имя или подсеть под двумя `kind`) и имена, общие для многих приложений;
- AS разворачиваются в подсети по таблицам RouteViews (§2.5);
- **подсети CDN и общих облаков не принимаются**: адрес там общий, подсеть потянула бы чужие сайты. Такие части
  сервиса ловятся только по имени. Список CDN и облаков ведётся в самом репозитории;
- подсеть шире /16 для IPv4 и шире /32 для IPv6, запись без `evidence` не принимаются;
- у каждого пакета `android` — хотя бы один `cert_sha256` (64 строчных hex), и `evidence` показывает, откуда он
  (APK из официального источника). Сертификат, от которого производитель ушёл ротацией подписи из-за компрометации,
  из записи убирают: проверка клиента признаёт и прежние сертификаты из истории подписей (app-attest-v1 §5);
- у записи с `cdn` — и `cname`: цели CNAME, на которые указывают её имена (из `evidence`). Висячий CNAME на того же
  провайдера, что в `cdn`, иначе прошёл бы: злоумышленник займёт ресурс и получит сертификат через HTTP-01;
- `cdn` называет только провайдеров из закрытого списка CI (с `evidence` и ревью);
- **суффикс, под которым поддомены отданы чужим DNS** (делегирование NS третьим лицам, wildcard CNAME на чужой
  сервис), не принимается: вместо суффикса — конкретные имена;
- **висячие CNAME**: CI по расписанию резолвит известные имена записей (из `evidence`) и ищет цепочки CNAME на
  удалённые облачные ресурсы (ответ NXDOMAIN или «ресурс не найден» у провайдера). Найденное — issue и снятие
  имени: такое имя может занять кто угодно (relay-entry-v1 §9.2);
- **суперприложения** (`superapp: true`) в `inside-only` — только после отдельного ревью списка: весь их трафик,
  с сайтами из встроенного браузера, подтверждённый вход relay выпускает целиком (relay-entry-v1 §7.1, §15). CI
  требует метку PR от владельца кода списков.

### 2.3. Что собирает CI

Из одних YAML, в одном запуске:

- **Для клиента** — `.srs` sing-box: по одному на приложение и по одному на `kind` и страну. Версия формата — та,
  что читает ядро клиента (форк sing-box 1.14: `RuleSetVersionCurrent` = 5); файл новее ядро не грузит, и туннель
  не стартует (`sing-box:common/srs/binary.go:68`). Манифест называет версию каждого `.srs` (§3.1).
- **Для сервера** — текст `<tag>.txt`, тот же набор. Нода и relay не разбирают succinct-деревья `.srs`
  (19-mihomo-review §8: `rayd` не тянет sing-box). Формат:
  - строки `suffix:<домен>` и `cidr:<префикс>`;
  - домены строчными, IDN — A-метками (`xn--…`); префиксы канонические (биты хоста обнулены);
  - строки отсортированы, без повторов; UTF-8, конец строки LF, комментариев нет.

  Разбор строгий: неизвестный префикс строки, пустая строка, неканонический префикс — файл отвергается целиком.

  **Сравнение имён** (relay и нода, одинаково): имя из CONNECT и SNI приводится к виду списка — без конечной точки,
  строчными, IDN — A-метками (IDNA 2008, UTS #46); `suffix:bank.ru` совпадает с `bank.ru` и с `*.bank.ru` **по
  границе метки**, но не с `evilbank.ru`. Имя, которое не приводится (пустая метка, длина больше 253), не совпадает
  ни с чем.
- **Записи набора** — `<tag>.entries.json`, тот же набор по записям: `[{"id", "android": [{"package",
  "cert_sha256"}], "suffixes", "cidr", "cdn"}]`, `cidr` — уже с развёрнутыми AS. Канонический JSON: ключи и
  массивы отсортированы. Нужен клиенту (подпись пакета, §2.1) и relay (адреса имени, relay-entry-v1 §9.2).
- **Подсети провайдеров CDN** — `cdn-<провайдер>.txt`, только текст (строки `cidr:`), без `.srs`. Из открытых данных
  провайдера, с `evidence`, в манифесте под ключом списков: `kind: cdn`, без `country`. Нода подменить их не может.
  Провайдеры — только из закрытого списка в CI, каждый — с `evidence` и ревью.
  - Читает их **только** проверка relay «адрес из своего резолва имени этой записи» (relay-entry-v1 §9.2).
    Сборка наборов, nftables ноды и правила клиента их пропускают, и схема манифеста это держит (§3.1): иначе
    подсети CDN утекли бы в «подсети списков» для неподтверждённых.
  - Запрет подсетей CDN в наборах (§2.2) остаётся.
- **Наборы стран** — `country-<cc>.txt` и `country-<cc>.srs` (§2.4).

Сборка воспроизводима: из того же коммита и тех же входных данных — те же байты (требование niko-routes).

### 2.4. Наборы стран

Подсети каждой страны по открытым данным. Нужны relay ([relay-entry-v1](relay-entry-v1.md) §7) и клиенту.

- Текст — только строки `cidr:`, слитые и свёрнутые (`collapse`).
- **Адрес входит в набор, только если обе базы относят его к стране** — делегирования RIR (delegated-extended всех
  пяти RIR, сводный файл NRO) **и** IPinfo Lite. Пересечение, а не объединение. Ошибки двух видов стоят по-разному:
  иностранный адрес, принятый за свой, открыл бы relay наружу; свой адрес, принятый за чужой, только отправит
  соединение через узел.
  - RIR пишет страну держателя ресурса, а не сети ([11-asn-sources](../11-asn-sources.md) §2.8). IPinfo Lite —
    страну сети. Пересечение отсекает и адреса держателя за границей, и чужие сети, которые IPinfo видит в стране.
- Вычитаются: подсети CDN и облаков (тот же список, что в §2.2), частные, служебные (RFC 6890) и bogon.
- **Предохранитель:** если набор страны между версиями изменился больше чем на 5 % своих адресов, CI требует в PR
  явной записи человека, почему.
- Размер, для оценки: в сводном файле NRO на 2026-11-16 у RU 11 468 записей IPv4 (8 676 префиксов после слияния,
  45,3 млн адресов) и 2 169 префиксов IPv6; у KZ — 617 и 98, у IR — 1 747 и 578 (подсчёт этой сессии). Пересечение с
  IPinfo дробит префиксы, сколько станет — не проверено.

Что следует:

### 2.6. Где файлы на GitHub

Предложение; окончательно — в niko-routes:
- **каждая версия — защищённый тег `m<версия>`** на коммит, где лежат `manifest.json`, его подписи и файлы версии.
  Набор правил репозитория запрещает удалять и перезаписывать теги `m*`. Манифест и подпись читаются из коммита
  тега, не из ассетов выпусков: выпуски и их ассеты не защищены, и задача CI с `contents: write` могла бы удалить
  новейший;
- **кто создаёт теги:** только задача выпуска — та, что держит ключ списков и чей каждый запуск одобряет владелец
  (§3.3). Она коммитит `manifest.json` с подписью в коммит выпуска и ставит тег `m<версия>`. Создавать теги `m*` она
  может через отдельное GitHub App (или токен), которого у задачи свежести нет: с одним `GITHUB_TOKEN` на обе задачи
  набор правил их не различил бы. Тег, заранее занятый злоумышленником, — отказ в обслуживании, но не тихий: номер
  не сойдётся с версией манифеста, и загорится тревога;
- **как читается тег** (нода, relay и клиент одинаково):
  - только `refs/tags/m<N>`, никогда ветка с тем же именем;
  - у аннотированного тега SHA коммита — из «очищенной» строки `^{}`; файлы берутся **по этому SHA**, не по имени
    (`https://raw.githubusercontent.com/arngory/niko-routes/<SHA коммита>/manifest.json`);
  - `version` манифеста должна быть равна N; расхождение — тревога;
  - последний выпуск — наибольший N среди тегов, чей манифест прошёл проверку. Поддельный тег с большим номером
    поднимает тревогу, но настоящий выпуск не прячет.

  Иначе взломанная задача CI поставила бы ветку или тег `m52` на коммит со старым, но верно подписанным манифестом
  v40, и заморозка прошла бы незамеченной;
- `timestamp.json` и его подпись — в ветке `timestamp`:
  `https://raw.githubusercontent.com/arngory/niko-routes/timestamp/timestamp.json`;
- **список тегов — через git smart-HTTP** (`https://github.com/arngory/niko-routes/info/refs?service=git-upload-pack`),
  не через REST API: у REST 60 запросов в час на адрес без токена, а все клиенты ноды выходят с одного адреса.
  `403` или `429` от пределов — «повторить позже», а не «нода роняет GitHub»: к «двум неудачам подряд» (§7.3) они
  не идут. Но тревога «больше 14 дней без удачной сверки» действует при любом числе таких ответов: через туннель
  нода сама может исчерпать предел адреса выхода.

Нода ходит туда своей сетью, TLS — по встроенному списку корней (R4-41).

## 3. Подписи и ключи

Как роли content и timestamp в TUF. Подпись — minisign, как у релизов raycontrol и Niko.

### 3.1. `manifest.json`

```json
{"v": 1, "epoch": 1, "version": 1042, "issued": 1767225600,
 "freshness_keys": ["RW…", "RW…"],
 "files": [
  {"name": "ru-inside-only.srs", "sha256": "…", "size": 41234, "kind": "inside-only", "country": "ru", "form": "srs", "license": "CC-BY-SA-4.0"},
  {"name": "ru-inside-only.txt", "sha256": "…", "size": 52011, "kind": "inside-only", "country": "ru", "form": "text", "license": "CC-BY-SA-4.0"},
  {"name": "ru-inside-only.entries.json", "sha256": "…", "size": 30412, "kind": "inside-only", "country": "ru", "form": "entries", "license": "CC-BY-SA-4.0"},
  {"name": "cdn-example.txt", "sha256": "…", "size": 2210, "kind": "cdn", "form": "text", "license": "CC-BY-SA-4.0"},
  {"name": "country-ru.txt", "sha256": "…", "size": 180412, "kind": "country", "country": "ru", "form": "text", "license": "CC-BY-SA-4.0"}]}
```

| Поле | Смысл |
|---|---|
| `epoch` | эпоха набора ключей списков (§3.4); равна эпохе в сборке проверяющего |
| `version` | номер версии, только растёт; не больше 2^53 |
| `issued` | время сборки, unix-секунды; только для показа |
| `freshness_keys` | открытые ключи minisign, которыми можно подписывать `timestamp.json` этой версии (§3.3) |
| `files[].name` | имя файла: `<tag>.srs`, `<tag>.txt` или `<tag>.entries.json`. Тег — `[a-z0-9-]` с точками внутри, не кончается на `.entries`, `.srs`, `.txt`; имя файла — тег плюс ровно один из трёх суффиксов, так что тег из имени однозначен. По тегу ищется набор (§5) |
| `files[].sha256`, `size` | хеш (hex) и размер в байтах |
| `files[].kind` | `inside-only` \| `blocked` \| `ads` \| `country` \| `cdn` |
| `files[].country` | страна, строчными; пусто — набор не привязан к стране. У `kind: cdn` поля нет |
| `files[].form` | `srs` (для клиента) \| `text` (для сервера, §2.3) \| `entries` (записи, §2.3) |
| `files[].srs_version` | только у `srs`: версия формата sing-box. Клиент не грузит файл новее своего ядра |
| `files[].license` | идентификатор SPDX |

- Подпись — `manifest.json.minisig`, **ключом списков**. Доверенный комментарий — ровно `niko-routes manifest
  <version>`, как `niko <tag>` у релизов Niko (app-update-v1 §3): подпись одной версии не выдать за другую.
- Предел — 1 МиБ на манифест, 32 МиБ на файл (столько же берёт клиент, 19-mihomo-review §3.1).
- Неизвестные поля пропускаются; неизвестный `kind` или `form` — файл пропускается, манифест остаётся годным.
- **Исключение `kind: cdn` в схеме:** такой файл — только текст (`form: text`), **без `.srs` и без `country`**. Файл
  `kind: cdn` в форме `srs` или с `country` — манифест отвергается целиком. Нода, клиент и сборка наборов файлы
  `kind: cdn` в наборы не берут, и правил `enforce` на них нет (§6.1).

### 3.2. `timestamp.json`

```json
{"v": 1, "manifest": {"version": 1042, "sha256": "…"}, "signed": 1767225600, "expires": 1768435200}
```

- `manifest` — номер и SHA-256 текущего манифеста; `signed` — время подписи; `expires` — `signed` плюс 14 дней.
- Своего номера у `timestamp.json` нет: свежесть упорядочена по версии манифеста, а у двух подписей одного
  манифеста новее та, у которой позже `signed` (§3.5).
- Подпись — `timestamp.json.minisig`, **ключом свежести**. Доверенный комментарий — `niko-routes timestamp
  <signed>`.
- Ключей в нём нет.
- Предел — 4 КиБ.

### 3.3. Два ключа

- **Ключ списков** подписывает манифест при выпуске версии, после PR с ревью двух людей. Ключ заводит и добавляет
  владелец (решение 2026-11-16, §13). Где он живёт — выбор владельца (§14):
  - **окружение GitHub:** обязательный рецензент — только владелец, «prevent self-review» включён, все действия
    workflow закреплены по SHA. Каждый выпуск подтверждает человек;
  - **подпись вне сети** (сильнее): CI собирает манифест и файлы, владелец подписывает манифест у себя и отдаёт
    `.minisig` задаче выпуска, которая коммитит его и ставит тег (§2.6). Ключа нет ни в одном секрете GitHub.

  В обоих случаях теги `m*` ставит только задача выпуска, через своё GitHub App или токен (§2.6).
- **Ключ свежести** подписывает `timestamp.json` по расписанию **раз в сутки**, даже если списки не менялись;
  `expires` — по-прежнему 14 дней. GitHub может задержать или пропустить плановый запуск, и запас в 13 запусков
  лучше, чем в один.
  - Перед подписью задача сама проверяет манифест: подпись ключом списков и версия не ниже прежней в ветке
    `timestamp`. Иначе отказ, без подписи.
  - Все действия workflow закреплены по SHA. Отдельный репозиторий для `timestamp.json` уменьшил бы, что видит
    задача с ключом свежести; решение — вместе с хранением ключа списков (§14).
  - Он лежит не в секретах репозитория, а в окружении GitHub, куда допущена только ветка `main`. Окружение
    ограничивается по веткам, а не по событиям, поэтому задача с ключом сама требует
    `github.event_name == 'schedule'`. `pull_request_target` и `workflow_dispatch` в этом workflow запрещены.
  - Задача коммитит `timestamp.json` в ветку `timestamp` без защиты ревью. Это явное исключение из правила двух
    ревью, только для этого файла: целостность списков держит подпись ключа списков, которого у CI нет, а не защита
    ветки. `main` и теги защищены правилами.
  - Коммит заодно — активность: GitHub выключает расписание публичного репозитория после 60 дней без активности.
    Считается ли коммит от `github-actions[bot]`, не проверено (§15). Если расписание встанет, тревогу поднимет нода
    (§4.4).
  - **Утечка ключа свежести даёт только заморозку**: продлить срок старой версии, но не изменить списки и не
    запереть обновления (§3.5).
- `contents: write` у задачи — на весь репозиторий: одной веткой его не ограничить. Целостность это не ломает
  (подписи), но задача может портить ветки и ассеты выпусков — отказ в обслуживании. Теги `m*` защищены набором
  правил (§2.6): удалить новейшую версию, чтобы заморозить списки, задача не может.

### 3.4. Смена ключей — только уровнем выше

Роль не меняет свой ключ сама.
- **Ключи списков** встроены в raycontrol и в сборку Niko, и только там: для каждой роли — список ключей и **эпоха**.
  Смена — выпуском обоих, заранее: новый ключ появляется в списке рядом со старым, старый уходит следующим выпуском.
  - **Несколько подписей:** у манифеста по `.minisig` на ключ (`manifest.json.<key id>.minisig`); годен, если его
    проверяет хотя бы один доверенный ключ. Пока в сборках оба ключа, CI подписывает обоими; когда сборки без
    старого ключа стали минимальными для ноды и клиента, подпись старым прекращается.
  - **Утечка ключа списков и «перемотка вперёд».** Утёкшим ключом можно подписать `version` = 2^53 — и после выпуска
    без этого ключа честный манифест уже не пройдёт «не ниже принятой». Поэтому принятая версия хранится **по
    эпохе**: выпуск, который убирает утёкший ключ, поднимает эпоху в сборке, и проверяющий начинает отсчёт версий с
    нуля. Манифест с `epoch`, не равной эпохе сборки, не принимается: поднять эпоху может только новый набор ключей.
    Так TUF восстанавливается после fast-forward: при смене ключей ролей принятые метаданные стираются
    (спецификация TUF, §5.3, «Update the root role»). `version` не больше 2^53 — и в JSON, и в проверке.
- **Ключи свежести** перечислены в подписанном манифесте (`freshness_keys`). Отзыв ключа свежести — новый манифест
  без него. Так утёкший ключ свежести не добавит свой ключ и не переживёт отзыв.
- Ключи релизов Niko (app-update-v1) и raycontrol для списков не годятся, и наоборот.

### 3.5. Порядок проверки (нода, relay и клиент — одинаково)

1. Прочитать `timestamp.json` без доверия: узнать, какой манифест он называет.
2. Взять этот манифест. Проверить подпись **ключом списков** (встроенный список; годна любая из его `.minisig`),
   доверенный комментарий, `epoch` равна эпохе сборки и `version` (не больше 2^53) не ниже принятой в этой эпохе.
3. Проверить подпись `timestamp.json` **ключами свежести из этого манифеста** и доверенный комментарий.
4. `manifest.sha256` из `timestamp.json` должен совпасть с SHA-256 байтов манифеста, `manifest.version` — с его
   `version`.
5. Каждый файл — SHA-256 и размер из манифеста.
6. **Манифест ставится** (версия не ниже принятой), что бы ни было со временем: его содержание подлинно независимо
   от часов, и отстающие часы не должны запирать новые списки.
7. **Свежесть** — отдельно от манифеста, по подписям `timestamp.json`:
   - `expires` позже `signed` больше чем на 14 дней — подпись не годится вовсе;
   - **опора** — время, с которым сверяется `signed`. У клиента — последний `Date` GitHub плюс `elapsedRealtime`
     с него или свежий `Date` (§7.3); у ноды и relay — их собственные часы;
   - подпись **подтверждена**, если `signed` сверено с опорой и впереди неё не больше чем на 2 дня;
   - подпись **ждёт** (pending), если опоры нет (у клиента — после перезагрузки, до сверки с GitHub). Она хранится
     как ждущая для своего манифеста **вместе с монотонным временем получения**. Когда опора появится, `signed`
     сверяется с опорой, перенесённой назад к моменту получения: иначе подпись «+10 дней», прождавшая неделю, прошла
     бы предел в 2 дня. После перезагрузки ждущая подпись отбрасывается и берётся заново. Перезагрузку узнают по
     сохранённому идентификатору загрузки, а не по тому, что монотонные часы пошли назад: после перезагрузки они
     могут обогнать сохранённое значение. У клиента — `BOOT_COUNT` или boot_id, у `rayd` —
     `/proc/sys/kernel/random/boot_id`;
   - нода и relay делают то же: сверяют `signed` со своими часами в момент получения;
   - свежесть манифеста засчитывается, только когда подтверждена **его собственная** подпись. Подтверждённая подпись
     более старого манифеста свежесть нового не продлевает;
   - из подтверждённых подписей одного манифеста действует более поздняя;
   - **порядок свежести — по версии манифеста.** Своего номера у `timestamp.json` нет.

Что это даёт против утёкшего ключа свежести:
- подпись старого манифеста с `signed` хоть в 2099 году новую версию не заслоняет: порядок — по версии манифеста, а
  её подпись свежесть нового манифеста не продлевает;
- подпись текущего манифеста «из будущего» не подтверждается; подтверждённая опережает честную не больше чем на 2
  дня, а ждущая честные подписи не вытесняет;
- отзыв — новый манифест без этого ключа: кто его принял, отозванному ключу больше не верит. Кому он не дошёл,
  отозванный ключ ещё может подписывать свежесть старой версии — это закрывает сверка клиента с GitHub (§7.3).

Манифест с той же `version`, но с другим SHA-256, — отказ и событие: у одной версии не может быть двух манифестов.

**Независимая сверка последнего манифеста.** Взломанная задача CI с ключом свежести могла бы тихо подписывать свежесть
старого манифеста. Поэтому нода, relay и еженедельная сверка клиента (§7.3) ещё и сами находят последний защищённый
тег `m<версия>` (§2.6: только `refs/tags`, по SHA коммита, `version` = N), проверяют подпись ключом списков и
поднимают тревогу, если он новее того, что называет `timestamp.json`. Такой манифест ставится (п. 6). Тег, у которого
нет манифеста с годной подписью или чья версия не равна номеру, — тоже тревога.

## 4. Зеркало на ноде

Тот же образец, что зеркало релизов Niko (app-update-v1 §3).

### 4.1. Включение и выбор наборов

- `rayctl rules mirror on|off`. **По умолчанию выключено**, как всё новое. `on` требует 256 МиБ свободного места в
  `/var/lib/raycontrol`; `off` удаляет скачанное и убирает поле `rules` из подписки.
- Какие наборы нода отдаёт, выбирает администратор (решение 2026-11-14): `rayctl rules enable <tag>…`,
  `disable <tag>…`. Тег — имя файла `.srs` из манифеста без расширения. Сразу после `on` не включён ни один.
- Если у ноды есть relay со включённым входом ([relay-entry-v1](relay-entry-v1.md) §3), нода держит ещё всё, что
  нужно этим relay (relay-entry-v1 §8): текстовые `inside-only` их стран, их `<tag>.entries.json`, все
  `cdn-*.txt`, которые эти записи называют, и `country-*.txt` — все, пока relay не сообщил свою страну, затем его.
  Без отдельного выбора.

### 4.2. Когда нода ходит на GitHub

- `timestamp.json` — сразу после `on`, затем раз в сутки (со случайным сдвигом до часа). Когда до `expires` остаётся
  меньше половины срока (`expires − signed`), — раз в час.
- Манифест — когда `timestamp.json` называет другую версию или другой SHA-256, и когда раз в сутки сверка тегов
  `m*` (§2.6, §3.5) находит версию новее. Relay делает ту же сверку.
- Файлы — только включённые наборы (и текст для relay, §4.1), которых у неё ещё нет. Файл с тем же SHA-256 не
  качается второй раз.
- Не прошло (подпись, хеш, размер, версия ниже принятой) — версия не принимается, остаётся прежняя, ошибка видна в
  `rayctl rules`. Не докачано (сеть) — повтор при следующей проверке.
- Новая версия собирается во временном каталоге и переносится на место целиком, как у app-update-v1.
- Назад нода не идёт: принятая версия манифеста и текущая подпись свежести хранятся отдельно от файлов, ниже версии
  ничего не ставится.
- При старте `rayd` проверяет то, что лежит на диске: подписи, хеши. Что не сошлось — удаляет и берёт заново.

### 4.3. Что нода отдаёт

На порту подписки, с тем же TLS по пину, SPA v2, `Authorization: RC1 …` и `X-Raycontrol-Device`, что у `/sub/v1`
и `/app/v1` (subscription-v1 §2, app-update-v1 §2):

| Путь | Что |
|---|---|
| `/rules/v1/t/<signed>.json` и `.json.minisig` | текущий `timestamp.json` и подпись, байты как с GitHub |
| `/rules/v1/m/<version>.json` и `.json.minisig` | принятый манифест и подпись |
| `/rules/v1/<sha256>.srs`, `/rules/v1/<sha256>.json` | включённый набор для клиента и его записи (`entries`) |

- Без авторизации, при выключенном зеркале, на неизвестный путь и на файл не из включённых — `404`, как у подписки.
  Редиректов нет.
- `Range`, `ETag`, `429` и обрыв медленной загрузки — как у `/app/v1` (app-update-v1 §2), в одном счёте загрузок
  устройства с ним.
- Файлы прежней версии нода отдаёт ещё 72 ч после смены — срок жизни подписки: клиент с прежней подпиской докачает
  то, что она называет.
- Текстовые наборы на порту подписки не отдаются: они нужны relay, не клиенту. Relay берёт их по `RelayService`
  (relay-entry-v1 §8).
- Через relay `/rules/v1` работает, как `/sub/v1`: relay пересылает порт подписки на уровне L4.

### 4.4. Истёкший срок и события

- `timestamp.json` с истёкшим `expires` нода всё равно отдаёт: решает клиент (§7.3).
- `rayctl status`, цикл `rules`:
  - за 3 дня до `expires`: `rules: the lists' freshness ends <дата>; last fetched from GitHub <дата>`;
  - после `expires`: `rules: the lists expired <дата>; last fetched from GitHub <дата>`;
  - отказ версии: что не прошло (подпись, хеш, версия), без содержимого.
- В журнал `rayd` — то же, не чаще строки в час.

## 5. Поле `rules` в подписке

Необязательное поле payload (subscription-v1 §3), под подписью ноды:

```json
"rules": {"v": 1,
  "timestamp": {"signed": 1767225600, "path": "/rules/v1/t/1767225600.json", "sig": "/rules/v1/t/1767225600.json.minisig"},
  "manifest": {"version": 1042, "sha256": "…", "path": "/rules/v1/m/1042.json", "sig": "/rules/v1/m/1042.json.minisig"},
  "sets": [
    {"tag": "ads", "sha256": "…", "size": 90211, "path": "/rules/v1/<sha256>.srs"},
    {"tag": "ru-blocked", "sha256": "…", "size": 412345, "path": "/rules/v1/<sha256>.srs"},
    {"tag": "ru-inside-only", "sha256": "…", "size": 41234, "path": "/rules/v1/<sha256>.srs"},
    {"tag": "own:office", "sha256": "…", "size": 1180, "path": "/rules/v1/<sha256>.srs", "own": true}],
  "enforce": [
    {"set": "ads", "action": "block"},
    {"set": "ru-blocked", "action": "node"},
    {"set": "ru-inside-only", "action": "relay", "relay": "r1", "fallback": "none", "adaptive": false},
    {"set": "own:office", "action": "direct"}]}
```

| Поле | Смысл |
|---|---|
| `v` | версия поля; внутри `v` = 1 появляются только новые необязательные поля. Неизвестную `v` клиент пропускает целиком |
| `timestamp` | текущий у ноды `timestamp.json`: его `signed` и пути к файлу и подписи |
| `manifest` | принятый манифест: `version`, `sha256`, пути |
| `sets[]` | наборы, которые нода отдаёт: `tag`, `sha256`, `size`, `path`. Только формы `srs`; записи `entries` того же тега — рядом, `/rules/v1/<sha256>.json` по манифесту |
| `sets[].own` | `true` — свой набор ноды, его нет в манифесте |
| `enforce[]` | правила администратора (§6), по порядку |
| `enforce[].set` | тег набора: имя файла манифеста без расширения или тег своего набора ноды |
| `enforce[].action` | `block` \| `node` \| `relay` \| `direct` |
| `enforce[].relay` | только у `relay`: `id` из `relays[]` |
| `enforce[].fallback` | только у `relay`: `none` (по умолчанию) \| `node` |
| `enforce[].adaptive` | только у `relay`: `true` — адаптивный режим (§6.2); по умолчанию `false`, приложение целиком |

- `kind` в `sets[]` нет и не будет. Если в `sets[]` понадобится свойство файла, это `behavior` (`domain` \|
  `ipcidr` \| `mixed`), не `kind`.
- **Набор ищется по имени, не по хешу.** Клиент находит `<tag>.srs` в **своём** принятом манифесте и берёт оттуда и
  файл, и `kind`. Версии у клиента и ноды могут расходиться (клиент взял 1043 с GitHub, нода отдаёт 1042): тогда
  хеши ноды не из манифеста клиента, но имя то же. Файл с хешем, который есть в манифесте клиента, берётся с ноды;
  другой — с GitHub или из своей копии.
- **Свои наборы ноды** — `.srs`, которые администратор кладёт сам (`rayctl rules own add`, §8), с `own: true` и
  тегом с приставкой **`own:`** (`own:office`): с именами манифеста они не пересекаются. Тег без приставки или тег,
  чьё имя после приставки совпадает с именем набора манифеста, `rayctl rules own add` не принимает, а клиент такой
  набор отбрасывает с предупреждением. Их
  нет в манифесте; клиент берёт файл с ноды по SHA-256. Подписаны только подписью ноды.
- Поля нет: зеркало выключено, ещё ничего не принято или нода старше.
- Поле отдаётся всем активным устройствам, как `app`: в файлах списков нет ничего, чего нет на GitHub. Свои наборы
  ноды видит каждое устройство её пользователей.

## 6. Правила администратора (`enforce`)

### 6.1. Общее

- Все правила `enforce` стоят **выше правил пользователя**, в порядке массива. Клиент показывает каждое с замком и
  действием («Задано подпиской»), пользователь их не меняет.
- `block` (отбросить), `node` (через узел) и `direct` (напрямую, мимо туннеля) применяются к любому набору, в том
  числе к своим наборам ноды, — кроме `kind: cdn`.
- **Правило на набор `kind: cdn` недопустимо**, с любым действием: подсети провайдеров нужны только проверке relay
  (§2.3). Клиент отбрасывает такое правило с предупреждением; `rayctl` его не строит (§8); нода не кладёт его в
  подписку и поднимает событие `rules: enforce <action> on <tag> is not published: <причина>` — как недопустимый
  `relay` (§6.2).
- Неизвестное действие клиент пропускает (правило целиком).
- **Приложение целиком — по умолчанию** (решение владельца 2026-11-16, §13): приложение идёт одним путём со всеми
  своими обращениями, внутри страны и за границу. Деление «своё — одним путём, иностранное — через узел» — только
  адаптивный режим администратора (`enforce[].adaptive`, §6.2).
- Сама нода `enforce` по приложениям проверить не может: приложение знает телефон. С
  [app-attest-v1](app-attest-v1.md) подлинный Niko сообщает тег набора в подтверждённом соединении naive, и нода
  отказывает по `block` и по `relay` сама (app-attest-v1 §7). `direct` нода не проверит никогда.
- Порядок правил на клиенте — его решение (ROUTING-APPS §5); на сегодня:
  1. `enforce`, по порядку;
  2. свои правила пользователя по приложениям; приложение с таким правилом выпадает из списков (п. 3);
  3. приложения из включённых списков — целиком одним путём;
  4. остальные свои правила пользователя;
  5. имена и подсети сервисов из списков — для остальных приложений;
  6. пресет страны;
  7. остальное — через узел.

### 6.2. `relay`

`relay` — обычное правило администратора, выше правил пользователя: трафик набора идёт на вход relay
([relay-entry-v1](relay-entry-v1.md)), который выпускает его в стране relay.

- **Только на набор с `kind: inside-only` из манифеста под ключом списков**, той же страны, что relay
  (`relays[].local.country`). Это защищает сам relay: в стране пользователя он не должен становиться прокси для
  того, что от этой страны прячут. Вход relay отвергнет чужое и сам (relay-entry-v1 §7), а проверка здесь убирает
  непонятные отказы:
  - клиент правило `relay` на другой набор (на `blocked`, на свой набор ноды, на набор другой страны) отбрасывает и
    показывает предупреждение;
  - `rayctl` такое правило не строит (§8);
  - нода, у которой новый манифест сделал набор не `inside-only` (или набора больше нет), правило в подписку не
    кладёт, хранит его и поднимает событие в `rayctl status`: `rules: enforce relay on <tag> is not published:
    <причина>`.
- `fallback` — что делать, когда вход relay не отвечает:
  - `none` (по умолчанию) — отказ. Сервисы inside-only смотрят на страну адреса, и вход в банк с иностранного адреса
    грозит блокировкой счёта: это хуже отказа. Так же владелец решил 2026-11-14 для недоступного выхода ноды;
  - `node` — через узел; ставит администратор на наборы, где иностранный адрес безвреден;
  - `direct` не бывает. Другое значение — клиент читает как `none`.
- Нет `relays[].local` у этого relay (вход выключен или relay не докладывает) — правило остаётся в подписке, клиент
  применяет `fallback`. Убрать правило значило бы отдать трафик правилам пользователя, то есть, может быть, за
  границу.
- **Набор не нашёлся** в манифесте клиента (§5) — тоже `fallback`, правило не выпадает.
- **Ответ входа `403` с `Niko-Refused: policy`** (неподтверждённый клиент, назначение вне наборов и страны relay):
  - по умолчанию — отказ по `fallback`: приложение целиком;
  - `adaptive: true` — назначение, которого нет ни в одном наборе `inside-only` клиента, идёт через узел (никогда не
    напрямую); назначение из набора — всё равно `fallback`.

  Подробно — relay-entry-v1 §14.

### 6.3. `direct`

Решение владельца 2026-11-16 (R4-44, цитата — §13): у администратора все возможности, клиент по архитектуре
недоверенный.

- `direct` отправляет набор **мимо туннеля**, с домашнего адреса пользователя.
- **Цена, открыто.** Администратор подписки — или тот, кто взломал ноду, — может отправить выбранные сайты напрямую
  и открыть им домашний адрес пользователя. Ни подпись подписки, ни ключ списков от этого не защищают: набор может
  быть своим набором ноды. Доверяя подписке, пользователь доверяет её администратору. Кому нужна независимость —
  ставит свой raycontrol и Niko.
- Так же `node` и `relay` перекрывают свои правила пользователя: приложение, которое пользователь сам отправил через
  узел, чтобы скрыть от своей страны, нода может перевести на relay в этой стране. Тогда назначения увидят оператор
  relay и провайдер страны.
- Клиент показывает каждое правило ноды, `direct` тоже, и справка объясняет цену (ROUTING-APPS §5). Это
  прозрачность, а не защита.
- На ноде `direct` — явное действие (§8): подтверждение, строка аудита, видно в `rayctl status`.

### 6.4. Чем это отличается от прежней позиции

[19-mihomo-review](../19-mihomo-review.md) §3.2 и §7 п. 6 говорили: нода приносит списки, а правил, которые меняют
выход, не присылает. Владелец решил иначе (2026-11-16, R4-44): цель ноды — hardening, и маршрут, который нужен
ноде, обычный пользователь парой кнопок не перепишет. Действует R4-44 (08 главнее остальных документов).

## 7. Что проверяет клиент (договор)

Сторона клиента — ROUTING-APPS §3, §5. Здесь — то, на что нода может рассчитывать.

### 7.1. Подписи и хеши

- Порядок §3.5, встроенные ключи списков — свои, в сборке Niko.
- Каждый файл из `sets[]` — SHA-256 и размер до того, как его увидит ядро.
- Набор для `enforce` ищется **по имени** в своём манифесте, `kind` — оттуда же (§5). Файл, хеш которого уже есть у
  клиента (например, в пресете страны), не качается второй раз.
- Если порт подписки недоступен — файлы с GitHub через туннель, с теми же проверками.

### 7.2. Версии

- Принятая версия манифеста только растёт — в пределах эпохи ключей списков (§3.4); сборка с новой эпохой начинает
  с нуля. С ноды и с GitHub ниже принятой не ставится. Своего номера у
  `timestamp.json` нет; текущая подпись свежести — по порядку §3.5.
- Исключение — аварийный снимок из APK, когда на диске нет проверенной версии: принятый номер при этом не меняется
  (ROUTING-APPS §3).

### 7.3. Свежесть

- **Время ноды не хранится и ничего не откладывает.** `issued` из подписи ноды (subscription-v1 §3) — не довод:
  замораживающая нода подпишет любое время, а нода с часами в 2099 году не должна навсегда зажечь тревогу. `issued`
  позже `expires` — только повод сходить на GitHub раньше. Нода `issued` по-прежнему шлёт.
- **Раз в 7 дней, без часов:** клиент сам берёт `timestamp.json` с GitHub через туннель и сам находит последний
  тег `m<версия>` (§2.6, §3.5, «Независимая сверка»). Если там версия манифеста новее той, что отдаёт нода, клиент берёт
  её (с теми же проверками §3.5) и показывает «нода отдаёт старые списки»; если выпуск новее, чем называет
  `timestamp.json`, — тревога о CI списков. Сравниваются версии манифеста, не время подписи.
- **По сроку:** когда `expires` прошёл по часам устройства, клиент сверяет его с `Date` от GitHub. Решает `Date`.
- **Неудача сверки — тоже тревога:** туннель держит нода, и проверку она может ронять. Две неудачи подряд или 14 дней
  без удачной — «списки, возможно, устарели: проверить не удалось». `403` и `429` от пределов GitHub к неудачам
  подряд не идут, но и не останавливают отсчёт 14 дней (§2.6). Сами списки продолжают работать.
- **Предел свежести:** время подписи `timestamp.json` клиент сверяет не с часами телефона, а с последним `Date`
  GitHub плюс `elapsedRealtime` с него; впереди больше чем на 2 дня — подпись не подтверждена (§3.5, п. 7). После
  перезагрузки опоры нет: подпись ждёт до сверки с GitHub, а манифест под ключом списков ставится сразу
  (ROUTING-APPS §3).

Что это даёт: нода не может откатить списки; заморозку старой версии с утёкшим ключом свежести ловит еженедельная
сверка, а если нода роняет GitHub — тревога «проверить не удалось» не позже чем через 14 дней.

### 7.4. `enforce`

- Правило со ссылкой на `tag`, которого нет ни в `sets[]`, ни в манифесте клиента: для `relay` — `fallback` (§6.2);
  остальные действия ждут набор, клиент показывает правило как «набор не найден».
- `relay` — проверки §6.2. `kind` и `country` — только из своего манифеста, по имени.
- Правило на набор `kind: cdn` — отбросить с предупреждением (§6.1).
- Новые соединения идут по новым правилам; приложения, у которых сменился маршрут, переподключаются (у клиента).

## 8. `rayctl` (набросок)

```
rayctl rules                              # зеркало, принятые версии, signed/expires, последняя удачная проверка, ошибка
rayctl rules mirror on|off                # по умолчанию off; off удаляет файлы
rayctl rules sets                         # наборы принятого манифеста: tag, kind, country, размер, отдаётся ли
rayctl rules enable|disable TAG…          # какие наборы отдавать
rayctl rules own add NAME FILE.srs        # свой набор ноды с тегом own:NAME (только block, node, direct)
rayctl rules own remove TAG
rayctl rules enforce                      # правила по порядку, с причиной, если правило не публикуется
rayctl rules enforce add [-at N] -action block|node SET
rayctl rules enforce add [-at N] -action relay -relay NAME [-fallback none|node] [-adaptive] SET
rayctl rules enforce add [-at N] -action direct [-yes-direct] SET
rayctl rules enforce remove N
```

- Права — как у `rayctl app-mirror`: root или группа `raycontrol` на ноде, admin-устройства через API
  (`-remote`). Каждое изменение — в аудит: `rules.mirror`, `rules.sets`, `rules.own`, `rules.enforce` с тегом
  набора и действием, без содержимого наборов и без назначений.
- `own add` проверяет файл: магия `SRS` и версия формата (байт после неё) не выше `rules.MaxSRSVersion` — сейчас 5,
  как `RuleSetVersionCurrent` ядра клиента. Файл новее ядро клиента не грузит, и туннель не стартует
  (`sing-box:common/srs/binary.go:68`). Предел поднимает выпуск raycontrol, когда самый старый Niko, которого нода
  ещё поддерживает, читает новую версию.
- `enforce add` с любым действием отказывает на набор `kind: cdn` (§6.1).
- `enforce add -action relay` отказывает, если:
  - набор не из манифеста или его `kind` не `inside-only`;
  - страна набора — не страна relay (`rayctl relay list`, relay-entry-v1 §17);
  - relay с таким именем нет.

  Если вход relay выключен, правило принимается с предупреждением: клиент применит `fallback`. `-adaptive`
  печатает, что это значит: иностранные назначения приложения вне списка пойдут через узел, приложение
  разделится.
- `enforce add -action direct`:
  - без `-yes-direct` спрашивает подтверждения в терминале; без терминала и без флага — отказ;
  - печатает, что это значит: `direct sends the set's traffic outside the tunnel, from the user's own address:
    the sites in it see where the user is. Users see this rule locked in Niko.`;
  - строка аудита `rules.enforce add direct <tag>`;
  - `rayctl status` перечисляет действующие правила `direct`: `rules: direct for <tag>, <tag>`.
  Через API — поле `yes_direct` в запросе; без него — `FailedPrecondition` с тем же текстом.
- API (`node.v1`, только добавления): `GetRules`, `SetRulesMirror`, `SetRuleSets`, `SetOwnRuleSet`,
  `SetEnforce` — имена при реализации.

## 9. Что нода хранит

- `settings`: `rules_mirror=on`, включённые теги, правила `enforce` (JSON, по порядку).
- `/var/lib/raycontrol/rules/` (rayd, 0600): принятые `timestamp.json`, манифест, подписи; файлы по SHA-256; свои
  наборы ноды. Прежняя версия — 72 ч (§4.3).
- Резервная копия (R4-13) несёт настройки и свои наборы; файлы списков — нет, нода берёт их заново.

## 10. Кто что может

Полная таблица вместе с relay — [relay-entry-v1](relay-entry-v1.md) §15. По спискам и подписке:

| Кто | Может | Не может |
|---|---|---|
| Взломанная нода | всё, что может администратор: `block`, `node`, `relay`, `direct` на любые наборы, свои наборы (§6.3); заморозить списки до сверки клиента с GitHub (§7.3); не отдавать `rules` | подменить файлы списков (ключ списков); откатить версию ниже принятой; дать `relay` на набор не `inside-only` (проверяет клиент и сам relay) |
| Утёкший ключ свежести | заморозить: продлевать старую версию | изменить списки; добавить ключ; запереть обновления (порядок по версии манифеста, только подтверждённые подписи, §3.5); пережить отзыв у того, кто принял новый манифест |
| Утёкший ключ списков | подписать любые списки: пометить сайт `inside-only` (клиенты с пресетом пойдут к нему напрямую, провайдер увидит), расширить, что выпускает relay; сменить ключи свежести | ничего сверх этого: ключ — вершина доверия. Отзыв — выпуск raycontrol и Niko без него |
| Запись в niko-routes без ключей | отказ в обслуживании: сломать расписание, удалить ветку `timestamp`, испортить ассеты | подписать что-либо |

## 11. Текст для гайда и шпаргалки

Когда команды появятся, в [cheatsheet](../cheatsheet.md) и гайд — то же, что здесь, прямо:

> `rayctl rules enforce add -action direct SET` — трафик набора у ваших пользователей идёт мимо туннеля, с их
> домашнего адреса: сайты из набора видят, где пользователь. Niko показывает это правило с замком. Пользователь,
> которому это не подходит, может поставить свой raycontrol.

## 12. Версии и совместимость

- raycontrol: зеркало, `rules` в подписке, `/rules/v1`, `rayctl rules` — одним выпуском (номер при реализации).
  Старая нода поля не шлёт, на `/rules/v1` отвечает `404`.
- Niko: читает `rules` после своей версии с ROUTING-APPS. Старый клиент поле пропускает (subscription-v1:
  необязательные поля добавлялись много раз).
- Вход relay — [relay-entry-v1](relay-entry-v1.md); без него `relay` в `enforce` работает как вход, который не
  отвечает (`fallback`).

## 15. Не проверено

- Считает ли GitHub коммит от `github-actions[bot]` активностью, которая держит расписание (§3.3). Официальная
  документация говорит только «no repository activity … in 60 days».
- Сколько префиксов будет у наборов стран после пересечения с IPinfo Lite (§2.4).
- Что ядро клиента перечитывает изменённый `.srs` без разрыва соединений — со слов клиента (ROUTING-APPS §3). Это
  касается только имён и подсетей. Состав приложений (`user_id`, теги) задаётся при сборке конфига: новые пакеты в
  списке требуют пересборки конфига клиента.
- Условия IPinfo: CC BY-SA 4.0 и FAQ «within a product» против общих ToS «internal business purposes»
  (11-asn-sources §2.2): формулировки расходятся.
- Нужен ли токен IPinfo для скачивания Lite — по странице так (`?token=`), без аккаунта не пробовали.
- Сколько висячих CNAME CI найдёт по именам из `evidence` (§2.2): имён, которых в `evidence` нет, он не увидит.
