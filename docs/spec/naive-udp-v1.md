# naive-udp-v1: UDP датаграммами HTTP/3 через naive

Статус: **черновик для обсуждения** (2026-11-14). Не согласован ни с владельцем, ни с клиентом; кода нет. Что решить до
кода — §12, вопросы клиенту — §13, что не проверено — §14. Основание — решение владельца от 2026-11-14
([17-naive-default](../17-naive-default.md) §5.1, §8 п. 1): настоящий UDP у naive идёт датаграммами HTTP/3 в том же
соединении QUIC, у которого отпечаток Chrome; UoT v2 внутри HTTP/2 ([naive-uot-v1](naive-uot-v1.md)) остаётся запасным
путём. Пара с Hysteria2 отклонена.

Зачем: UoT несёт UDP внутри надёжного потока. Потерянный пакет туннеля задерживает все следующие, а под перегрузкой
датаграммы копятся в буфере ([15-traffic](../15-traffic.md) §2; 17-naive-default §3, B8). Датаграммы QUIC (RFC 9221)
теряются поодиночке, как UDP.

Откуда факты. У каждого утверждения — источник; чего нет в источниках, помечено «оценка» или вынесено в §14.
- Пути без префикса — этот репозиторий, `c3adefb`.

- `qg:` — quic-go v0.64.1 (`go.mod` ноды и niko-server). `sqg:` — форк SagerNet, `sagernet/quic-go`
  v0.61.0-sing-box-mod.12 (на нём sing-quic).
- `cr:` — Chromium 154.0.8037.49, дерево `src/` в klzgrad/naiveproxy, тег `v154.0.8037.49-5`. `sn:` — то же дерево с
  правками SagerNet, ветка `cronet-go-dev-v154`. `quiche:` — `sn:net/third_party/quiche/src/quiche/`. Перенос на 158
  идёт отдельно: номера строк сместятся.
- `cgo:` — cronet-go, `73349ff`.
- `bind-16` — draft-ietf-masque-connect-udp-listen-16 (24.08.2026).

## 1. Коротко

Рекомендуемая схема. Каждый пункт — решение из §12, пока не принятое.

- **Провод (§3).** Один запрос на один UDP-сокет приложения: extended CONNECT с `:protocol: connect-udp` по HTTP/3,
  пароль и `Padding` как у naive. Датаграммы HTTP (RFC 9297) с Context ID 2 несут `[тип адреса][адрес][порт][данные]`:
  адрес назначения в каждой датаграмме, как в UoT v2 и как в «несжатом» контексте bind-16. На ноде — один сокет на
  запрос и прежний port-restricted cone.
- **Размер (§4).** Нода ищет MTU пути до 1452 байт, клиент — до 1400. Без этого вверх проходит не больше 1206 байт
  данных UDP, и вложенный QUIC Chrome (1250) датаграммой не идёт.
- **Больше пути (§4).** Что не влезло в пакет QUIC, идёт капсулой DATAGRAM в потоке того же запроса; у пар, начавшихся с
  QUIC, — только до 1252 байт, длиннее отбрасывается. Капсулой идут и первые датаграммы, пока нода не ответила.
  Фрагментации нет.
- **Сокет QUIC (§5).** Сначала PMTUD и ключ сброса на нынешнем пути через фронт (десятки строк). Затем свой сокет у
  процесса naive: группа `SO_REUSEPORT`, которую создаёт фронт, выбор сокета классическим BPF по метке в Connection ID;
  Initial по-прежнему разбирает фронт.
- **Перегрузка (§6).** BBR: HTTP/3 naive переходит на форк quic-go от SagerNet с BBR из sing-quic, как Hysteria2 в
  niko-server. С NewReno один процент потерь на пути ограничивает все датаграммы соединения примерно 1,2 Мбит/с
  (оценка).
- **Нода (§7).** Обработчик поверх политики UoT: те же места (256 на пользователя вместе с потоками UoT), пары, резолвы,
  учёт, отзыв. Отказ по пределу — `429` до ответа.
- **Клиент (§8).** Объект датаграмм в C API libcronet рядом с bidirectional stream: 10–12 файлов, 600–900 строк патча
  (оценка). Готовый класс Chromium для CONNECT-UDP не подходит; подходят его нижние вызовы.
- **Подписка (§9).** Параметр `udp=1` в строке `naive+https://`. TCP остаётся на HTTP/2, QUIC к той же ноде несёт только
  UDP. Проба — эхо probe-v1 тем же путём; не прошло — UoT.
- **Порядок (§11).** Пять шагов; после каждого прежнее поведение остаётся запасным.

## 2. Что есть сейчас

### 2.1. Нода и фронт

- **HTTP/3 у naive.** `rayd naive` слушает QUIC поверх `nikoipc.PacketConn`: `quic.Config{MaxIdleTimeout: 2 мин,
  KeepAlivePeriod: 0}`, `http3.Server{IdleTimeout: 2 мин}` (`cmd/rayd/main.go:1325-1337`, `:1403-1422`).
  `EnableDatagrams` не задан: ни параметра транспорта, ни `SETTINGS_H3_DATAGRAM` нода не шлёт.
  `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1` сервер quic-go шлёт всегда (`qg:http3/server.go:500-506`).
- **Путь пакета.** Фронт пересылает каждую датаграмму одним сообщением SOCK_SEQPACKET, в обе стороны
  (`internal/nikoipc/packet.go:13-23`; `niko:docs/IPC.md`, режим `packet`). На пакет — копия и выделение памяти в каждом
  процессе (`packet.go:137`, `:188`; `niko:nikoserver/front.go:368-376`).
- **Что из этого следует для quic-go.** `PacketConn` — не UDP-сокет (`packet.go:48-64`). quic-go тогда работает без GSO,
  ECN и чтения пачками, DF считает неустановленным и поиск MTU не запускает: пакеты всегда 1280 байт
  (`qg:sys_conn.go:79-100`, `qg:connection.go:933`, `qg:internal/protocol/params.go:6`).
- **Фронт.** Поток закрепляется за бэкендом по паре (адрес клиента, локальный адрес) первой датаграммой, которую удалось
  классифицировать: QUIC Initial с именем из ClientHello или пакет salamander. Любая другая датаграмма от незнакомой
  пары отбрасывается. Простой — 60 с (`niko:nikoserver/udpfront.go:18-24`, `:71`, `:188-201`, `:215-228`). Сокеты фронта
  шлют с DF (`:294-310`).
- **Hysteria2 идёт тем же путём:** его бэкенд получает датаграммы от фронта в режиме `packet`
  (`niko:nikoserver/hysteria.go:35-36`, `:88`). Своего сокета у него нет. PMTUD у него работает, потому что форк
  SagerNet считает DF установленным и на не-сокете (`sqg:sys_conn.go:70-74`; `hysteria.go:150-161`).
- **Политика UDP у naive отделена от кадров.** `uotStream.resolve`, `mayReach`, `heard`, `touch` и счёт `Traffic` не
  знают о потоке (`internal/naive/uot.go:199-210`, `:241-303`; `users.go:94-105`); места и пары — `limits.uotTake`,
  `uotPut`, `newPair` (`limits.go:353-461`). Кадры UoT — `upstream`, `send`, `downstream` (`uot.go:521-613`).
- **Вход.** `Server.ServeHTTP`: не CONNECT, HTTP/1 или нет `Padding` — ответ сайта; затем пароль; затем `tunnel`
  (`naive.go:61-82`). Ответ `200` уходит раньше, чем берётся место UoT (`:131-149`).
- **Подписка.** Нода выдаёт только `naive+https://…&uot=2[&icmp=1]` (`internal/sub/sub.go:566-589`).
- **Периметр.**
  - Новый входящий поток пускает только допуск SPA на адрес источника: набор `allow4` — адрес, протокол, порт
    назначения, без порта источника; остальное — `established,related` (`internal/perimeter/firewall.go:193`, `:266`,
    `:282-297`). Допуск живёт по умолчанию 10 минут, клиент продлевает ([spa-v2](spa-v2.md) §6 п. 8, §7).
  - UDP-порт сервиса меняется по расписанию: порты слотов `slot−1`, `slot`, `slot+1` перенаправляются на 443
    (`firewall.go:257`; spa-v2 §11). naive в этом списке (`internal/provision/provision.go:1338-1342`).
  - IP-фрагменты, адресованные ноде, отбрасываются до conntrack (`firewall.go:241-243`): ответ назначения длиннее MTU
    пути до ноды не доходит ни при каком формате туннеля.

### 2.2. quic-go v0.64.1

- **Датаграммы HTTP/3 есть.** `http3.Server.EnableDatagrams` (`qg:http3/server.go:169-171`); обработчик получает поток
  через `http3.HTTPStreamer` и вызывает `Stream.SendDatagram`, `Stream.ReceiveDatagram`
  (`qg:http3/response_writer.go:19-24`, `qg:http3/stream.go:180-189`). Extended CONNECT приходит как `Method = CONNECT`,
  `Proto = <:protocol>`, `ProtoMajor = 3` (`qg:http3/headers.go:292-343`). Капсулы читает `http3.CapsuleParser`, пишет
  `http3.WriteCapsule` (`qg:http3/capsule.go`).
- **Отправка блокирует.** Очередь датаграмм соединения — 32; когда она полна, `SendDatagram` ждёт
  (`qg:datagram_queue.go:14-17`, `:49-80`; замер: 200 датаграмм подряд — 2–24 мс). Срока годности у датаграммы в очереди
  нет.
- **Приём.** Очередь соединения — 128, очередь потока — 32, лишнее отбрасывается (`qg:datagram_queue.go:14-17`,
  `qg:http3/state_tracking_stream.go:12`, `:136-146`). Датаграмма для потока, который слой HTTP/3 ещё не принял,
  отбрасывается (`qg:http3/conn.go:303-309`): та, что клиент послал сразу за запросом, может потеряться.
- **Размер.** `SendDatagram` берёт не больше `MTU − 37` байт (`qg:connection.go:3066-3084`, `:3188-3190`); замер на 1280
  — 1243. Потолок пакета — 1452 (`qg:internal/protocol/protocol.go:111`). Параметр транспорта `max_datagram_frame_size`
  — 16383 (`qg:internal/wire/datagram_frame.go:14`, `qg:connection.go:351`).
- **Управление перегрузкой — NewReno**, зашито (`qg:internal/ackhandler/sent_packet_handler.go:155-162`); открытого
  способа подменить алгоритм нет.
- **Сокет.** GSO на отправке (ядро не старше 5.0), чтение пачками по 8, GRO нет (`qg:sys_conn_helper_linux.go:24`,
  `:66-81`). Обёртка сокета может подставить своё чтение пачек: `ReadBatch` (`qg:sys_conn_oob.go:36-38`, `:108-118`).
- **Транспорт.** `ConnectionIDLength` (по умолчанию 4), `ConnectionIDGenerator`, `StatelessResetKey`,
  `TokenGeneratorKey`, `VerifySourceAddress` (`qg:transport.go:79-122`, `:408-417`). Нода сейчас ничего из этого не
  задаёт (`cmd/rayd/main.go:1406`).
- **masque-go v0.6.0** (готовый прокси RFC 9298) не берём: одна цель на запрос, пишет назначения в журнал, требует
  quic-go v0.63 (`masque-go@v0.6.0/proxy.go:18`, `:164-175`, `go.mod`).

### 2.3. Клиент: cronet-go и Chromium

- **Как naive ходит через cronet-go.** Не через прокси-стек Chromium: `NaiveClient` открывает bidirectional stream с
  методом `CONNECT` на URL ноды и заголовками `-connect-authority`, `Padding`, `proxy-authorization`, `-force-quic`,
  `-network-isolation-key` (`cgo:naive_client.go:471-495`). Поток идёт через
  `HttpStreamFactory::RequestBidirectionalStreamImpl` (`sn:net/http/bidirectional_stream.cc:204-231`),
  `-connect-authority` становится `:authority` (`sn:net/spdy/spdy_http_utils.cc:216-219`). Паддинг кадров — в Go
  (`cgo:naive_conn.go:19-131`). `ProxyChain`, `ProxyDelegate` и «преамбулы» есть только в бинарнике `naive` klzgrad
  (`cr:net/tools/naive/naive_proxy.cc:120-194`); в cronet-go их нет.
- **Сессия QUIC к ноде — обычная, не прокси:** `SessionUsage::kDestination`
  (`sn:net/http/http_stream_factory_job.cc:346`, `:898`). Отсюда размер пакета: 1250 байт, на IPv6 — 1230; прибавка 100
  байт положена только сессиям `kProxy` (`quiche:quic/core/quic_constants.h:33`; `sn:net/quic/quic_context.h:119-125`;
  `cr:net/quic/quic_session_pool.cc:2325-2336`; `sn:net/quic/quic_chromium_client_session.cc:108`, `:1153-1156`).
- **Сокет QUIC создаёт Go** (хук `UDPDialer`) и отдаёт Chromium дескриптор (`cgo:naive_client.go:274-343`).
- **`QuicProxyDatagramClientSocket`** — что это на самом деле (`cr:net/quic/quic_proxy_datagram_client_socket.cc`,
  `.h`):

  | Свойство | Где | Нам |
  |---|---|---|
  | extended CONNECT, `:protocol: connect-udp`, `capsule-protocol: ?1` | `.cc:472`, `:481-484` | подходит |
  | одна цель, в пути `/.well-known/masque/udp/<host>/<port>/` | `cr:net/quic/quic_session_pool.cc:2156-2159` | не подходит: нужен адрес в датаграмме |
  | только Context ID 0, в обе стороны | `.cc:157-168`; `cr:net/quic/quic_chromium_client_stream.cc:321-324` | не подходит |
  | очередь приёма 16, лишнее отбрасывается | `.h:140`, `.cc:190-195` | мала для всплеска; очередь нужна своя |
  | ждёт `200`; не ждёт только под выключенной по умолчанию feature | `.cc:517-527`, `:577-587`; `cr:net/base/features.cc:921-922` | нужны ранние данные без ожидания |
  | `Proxy-Authorization` не умеет (TODO) | `.cc:445` | заголовки задаём сами |
  | слишком большая датаграмма сбрасывает поток | `cr:net/quic/quic_chromium_client_stream.cc:336-347` | недопустимо: проверять размер до отправки |
  | создаётся в одном месте — как транспорт вложенной сессии QUIC через QUIC-прокси | `quic_session_pool.cc:2135-2164` | это не сокет общего назначения |
  | HTTP/2 нет: принимает только `QuicChromiumClientStream::Handle` | `.h:74-77` | нам и не нужен |

  Переиспользуется не класс, а то, на чём он стоит: `Handle::RegisterHttp3DatagramVisitor`,
  `QuicSpdySession::SendHttp3Datagram`, `GetGuaranteedLargestMessagePayload`
  (`sn:net/quic/quic_chromium_client_stream.h:127-131`, `:169-172`; `quiche:quic/core/http/quic_spdy_session.cc:1799`).
- **Капсулы quiche уже разбирает.** С зарегистрированным visitor тело ответа читается как капсулы; капсула DATAGRAM
  приходит в тот же `OnHttp3Datagram`, что и датаграмма QUIC; неизвестная — в `OnUnknownCapsule`. Пишет капсулу
  `QuicSpdyStream::WriteCapsule` (`quiche:quic/core/http/quic_spdy_stream.cc:1592-1612`, `:1677-1679`, `:1688`,
  `:1717-1737`, `:1882-1905`).
- **Что клиент отбрасывает сам.** Датаграмму, пришедшую раньше заголовков ответа (`quic_spdy_stream.cc:1844-1850`).
  Отправку до `SETTINGS` ноды quiche не принимает (`quic_spdy_session.cc:1799-1812`). Очередь отправки хранит датаграмму
  не дольше 1,25 минимального RTT (`quiche:quic/core/quic_datagram_queue.cc:20`, `:85-93`).
- **Bound UDP в quiche есть только заготовкой:** `RegisterConnectUdpBindVisitor` и капсулы `COMPRESSION_ASSIGN =
  0x1C0FE323`, `COMPRESSION_CLOSE = 0x1C0FE324` (`quic_spdy_stream.cc:1796`; `quiche:common/capsule.h:44-45`). В bind-16
  капсул три, с номерами 0x11–0x13 (§11.2): номера ещё меняются.
- **Простой и keepalive.** Простой сессии — 30 с; пока открыт хоть один запрос, клиент шлёт PING раз в 15 с
  (`sn:net/quic/quic_context.h:69-75`, `:158`; `cr:net/base/features.cc:852-853`;
  `quiche:quic/core/quic_constants.h:170`; `sn:net/quic/quic_chromium_client_session.cc:1714-1726`). cronet-go простой
  не меняет (`cgo:engine_params_experimental_options.go`, `SetQUICOptions`).
- **0-RTT для CONNECT не используется:** ранние данные — только безопасным методам
  (`sn:net/quic/bidirectional_stream_quic_impl.cc:73-77`); нода 0-RTT не принимает (`cmd/rayd/main.go:1406`).
- **Поиск MTU на клиенте выключен**, включается тегом `MTUH` (цель 1400) или `MTUL` (1380)
  (`quiche:quic/core/quic_connection.cc:494-501`; `quiche:quic/core/quic_mtu_discovery.h:31-32`; флаг
  `quic_enable_mtu_discovery_at_server` по умолчанию false, `quiche:common/quiche_feature_flags_list.h:38`). Тег можно
  дать через `client_connection_options`: они в параметры транспорта не попадают, в отличие от `connection_options`
  (`quiche:quic/core/quic_config.cc:557-566`, `:1298-1300`; `sn:net/quic/quic_context.cc:88-89`;
  `sn:components/cronet/url_request_context_config.cc:509-521`).

### 2.4. Со слов клиента (клиентская сессия, 2026-11-14)

1. В ядре — один `PacketConn` на сокет приложения: NAT sing (`common/udpnat2/service.go:17-29`) держит таблицу по адресу
   источника; с первым пакетом исходящий получает `ListenPacket`, дальше у каждого пакета своё назначение, ответы
   принимаются с любого адреса. Сейчас у naive это один поток UoT v2 на сокет приложения. Клиент согласен: адрес нужен
   внутри датаграммы, сессия — на сокет приложения; CONNECT-UDP с одной целью дал бы симметричный NAT и запрос на каждый
   адрес DNS и STUN.
2. От libcronet клиент хочет объект по образцу bidirectional stream, из того же движка: `Start(url, заголовки)`;
   `OnReady(заголовки, статус)`, `OnDatagramReceived(буфер)`, `OnFailed(код)`, `OnCanceled`; `SendDatagram(буфер)` без
   блокировки, с отказом при полной короткой очереди; `MaxDatagramPayloadSize()` и уведомление о смене; Context ID и
   капсулы — внутри библиотеки; соединение принудительно QUIC, как сейчас `-force-quic`.
3. MTU TUN приложения по умолчанию 9000 (`DataStore.kt:149`), локального «слишком большой» для UDP нет: приложения шлют
   что хотят. 1232 байта данных UDP должны проходить без потерь. Для больших датаграмм клиент предпочитает капсулу в
   потоке того же запроса, не фрагментацию; может добавить локальный «слишком большой» для UDP с DF.
4. Строки `naive+quic://` клиент уже разбирает (`quic: true`). Ротация SNI для него прозрачна.
5. Честный connect (отдельная работа): по `niko-ack=1` в строке клиент шлёт `niko-ack: 1` в каждом CONNECT; нода
   отвечает на TCP CONNECT после соединения с назначением (`200`, `502`, `504`).

## 3. Формат провода

Условие: тип NAT остаётся прежним ([15-traffic](../15-traffic.md) §2) — один сокет ноды на сокет приложения, ответы
только от тех, кому клиент отправлял (`uot.go:199-210`).

### 3.1. Варианты

| | Что это | Тип NAT | Имена | Что готово | Цена |
|---|---|---|---|---|---|
| А | RFC 9298 как есть: цель в пути запроса, Context ID 0 | **симметричный:** запрос и сокет ноды на каждое назначение; STUN увидит разные порты | да, одно на запрос | класс Chromium, masque-go | запрос на каждый адрес DNS и STUN; условие не выполнено |
| Б | bind-16: один запрос, «несжатый» контекст с адресом в датаграмме, «сжатые» — на цель | наш, если нода фильтрует ответы | нет: только адреса | в quiche заготовка со старыми номерами капсул (§2.3); в Chromium и quic-go — ничего | регистрация контекста капсулой `COMPRESSION_ASSIGN` и подтверждение; черновик меняется |
| В | свой профиль в оболочке RFC 9298: запрос как в А, Context ID 2 с адресом в датаграмме, регистрация заголовком | наш | да, в датаграмме | разбор адреса и вся политика из UoT | свой формат; стандартный клиент не подойдёт (и не должен: вход — по паролю и `Padding`) |

RFC 9298 §4 прямо оставляет расширениям регистрацию Context ID заголовками или капсулами: В стандарту не противоречит.

**Рекомендация — В**, с раскладкой адреса как в Б (версия IP, адрес, порт):
- стороннего клиента у ноды быть не может, а готового кода Б нет ни на одной стороне: совместимость со стандартом ничего
  не экономит;
- имена нужны, если ядро шлёт их в UDP (вопрос клиенту, §13 п. 1); в Б их нет;
- регистрация заголовком не стоит ни оборота, ни автомата состояний; у Б первая датаграмма может обогнать капсулу
  регистрации и пропасть (bind-16 §3.1);
- раскладка байт совпадает с Б: если черновик станет RFC и его поддержит Chromium, перейти можно сменой способа
  регистрации.

Чего стоит В: формат наш навсегда, со своей версией; «сжатых» контекстов (без адреса, экономия 7 или 19 байт на
датаграмму) в первой версии нет — см. §4.4.

Отвергнутая разновидность: обычный CONNECT на служебное имя, как у UoT и ICMP. Экономит правку заголовков на клиенте, но
датаграммы на обычном CONNECT — уже не «в духе CONNECT-UDP», и запрос не отличить от TCP до разбора имени.

### 3.2. Рекомендуемый формат

**Что согласуется и где.**

| Слой | Что | Клиент (Chromium) | Нода |
|---|---|---|---|
| QUIC | параметр транспорта `max_datagram_frame_size` (RFC 9221 §3) | шлёт всегда, 65536 (`quiche:quic/core/quic_config.cc:1058`, `:1226`) | начнёт слать: 16383 |
| HTTP/3 | `SETTINGS_H3_DATAGRAM = 1` (RFC 9297 §2.1.1) | шлёт всегда (`quiche:quic/core/http/quic_spdy_session.cc:626-634`, `:2024-2026`) | начнёт слать |
| HTTP/3 | `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1` (RFC 9220) | не шлёт | шлёт уже сейчас (§2.1) |
| запрос | `capsule-protocol: ?1` (RFC 9297 §3.4), `niko-udp: 1` | в запросе | в ответе |

**Запрос** — только HTTP/3:

```
:method = CONNECT
:protocol = connect-udp
:scheme = https
:authority = <имя сервиса, то же, что в SNI>
:path = /.well-known/masque/udp/%2A/%2A/
capsule-protocol = ?1
proxy-authorization = Basic <как у naive>
padding = <как у naive>
niko-udp = 1
```

- Путь — шаблон RFC 9298 §2 с целью `*`, как в bind-16 §2 для запроса без одной цели. Нода принимает и `%2A`, и `*`: что
  из двух оставит канонизация URL в Chromium, не проверено.
- `niko-udp: 1` регистрирует Context ID 2 с форматом ниже. Другое значение — версия, которой нода не знает: ответ сайта.

**Ответ:** `:status = 200`, `capsule-protocol = ?1`, `padding`, `niko-udp = 1`. Нода отвечает, когда место взято и сокет
открыт; ждать нечего, соединения с назначением нет. `niko-ack` на этот запрос не влияет.

| Ответ | Когда |
|---|---|
| `200` с `niko-udp: 1` | принято |
| ответ сайта (пустой `404`) | нет пароля или `Padding`; возможность выключена; неизвестная версия; не HTTP/3 |
| `429` | предел мест пользователя или сервиса (§7); только авторизованному, как у TCP ([conn-limit-v1](conn-limit-v1.md) §4.3) |
| `503` | сокет не открылся |

**Датаграмма HTTP** (RFC 9297 §2.1: после Quarter Stream ID):

```
[Context ID (varint) = 2]
[тип адреса: u8 = 4 | 6 | 3]
[адрес: 4 байта | 16 байт | u8 длина + имя]
[порт: u16 BE]
[данные UDP]
```

- От клиента адрес — назначение; от ноды — источник ответа, всегда тип 4 или 6.
- Тип 3 (имя) — только от клиента. Нода резолвит его как в UoT (naive-uot-v1 §3).
- Context ID 0 не используется (bind-16 §3). Датаграмму с неизвестным Context ID получатель молча отбрасывает (RFC 9298
  §5).
- Нечитаемая датаграмма (короткая, неизвестный тип адреса, пустое имя, порт 0) отбрасывается; поток живёт.

**Капсулы** в потоке запроса (RFC 9297 §3.2, §3.5):
- `DATAGRAM (0x00)` несёт ту же датаграмму HTTP. Когда — §4.4 и «ранние данные» ниже.
- Неизвестный тип пропускается. Капсула длиннее 65 767 байт (Context ID, имя в 255 байт, порт и 65 507 байт данных) —
  сброс потока.
- Кроме капсул, в потоке ничего нет. Паддинга первых кадров naive на нём нет: тело разбирает quiche (§2.3).

**Ранние данные.** Клиент не ждёт ответа: первые датаграммы он шлёт капсулами сразу за заголовками, а на датаграммы QUIC
переходит, получив `200`. Иначе первая датаграмма теряется на ноде (§2.2) или не уходит с клиента до `SETTINGS` (§2.3),
а ожидание ответа стоит оборота телефон — нода на первом пакете каждого сокета: запрос DNS шёл бы вдвое дольше. Нода не
шлёт датаграмм раньше своих заголовков.

**Жизнь запроса.**
- Запрос — один UDP-сокет приложения и один сокет ноды. Адрес и порт ноды для него не меняются.
- Клиент закрывает поток — нода закрывает сокет.
- Простой — 2 минуты без датаграмм в обе стороны: нода закрывает поток чисто. Клиент откроет новый; порт ноды будет
  другим, как у UoT.
- Сброс потока: отзыв пользователя, вытеснение тихого запроса новым (§7), нечитаемая капсула.

### 3.3. Старая нода, старый клиент

- **Новый клиент, старая нода.** Нода не шлёт `SETTINGS_H3_DATAGRAM`: клиент видит это до запроса. Если запрос всё же
  ушёл, нода примет его за TCP CONNECT: либо ответ сайта (`:authority` без порта, `naive.go:88-93`), либо `200` без
  `niko-udp` и сброс (имя ведёт на саму ноду, а она себе не назначение). Успеха не бывает; клиент обязан требовать
  `niko-udp: 1` в ответе.
- **Старый клиент, новая нода.** Extended CONNECT он не шлёт, UoT работает как раньше. Параметр `udp=1` он, по
  прецеденту `uot`, `icmp` и `niko-pin`, пропустит (подтвердить, §13 п. 9).
- **HTTP/2.** Формата нет: запасной путь — UoT v2.

## 4. Размеры и датаграммы больше пути

### 4.1. Сколько влезает

Данные UDP в одной датаграмме QUIC, формат §3.2; Quarter Stream ID — 2 байта (1 у первых 64 запросов соединения, 4 после
16 384-го).

| Направление | Пакет QUIC | Датаграмма QUIC | Данные UDP при адресе IPv4 / IPv6 | Источник |
|---|---|---|---|---|
| клиент → нода | 1250 (сейчас, IPv4) | 1216 | **1206 / 1194** | расчёт по `quiche:quic/core/quic_packet_creator.cc:2299-2338` |
| клиент → нода | 1230 (сейчас, IPv6) | 1196 | 1186 / 1174 | то же |
| клиент → нода | 1400 (после поиска MTU) | 1366 | 1356 / 1344 | то же |
| нода → клиент | 1280 (сейчас) | 1243 | **1233 / 1221** | замер; `qg:connection.go:3188-3190` |
| нода → клиент | до 1452 (после PMTUD) | до 1415; на loopback 1372–1404 | до 1405 / 1393 | расчёт; замер |

- Клиентская формула: пакет − 16 (AEAD) − заголовок − 1 (тип кадра); заголовок берётся худший, 13 + длина Connection ID
  ноды. Сейчас Connection ID — 4 байта; с 8 байтами (§5.2) всё в строках «клиент → нода» меньше на 4.
- Клиент принимает пакеты до 1472 байт (`quiche:quic/core/quic_constants.h:53`): PMTUD ноды упирается в свой потолок
  1452 и в путь.
- На этих числах ничего не мерилось с настоящим клиентом; строки клиента — расчёт по коду.

### 4.2. Что нужно приложениям

| Что | Данные UDP | Источник |
|---|---|---|
| минимум, который должен проходить без потерь | 1232 | клиент (§2.4 п. 3): 1280 − 48 |
| QUIC, наименьший Initial | 1200 | RFC 9000 §14.1 |
| QUIC Chrome | 1250, на IPv6 — 1230 | §2.3 |
| DNS с EDNS | до 1232 | naive-uot-v1 §3 |
| WireGuard, MTU 1420 | до 1452 | клиент |
| WARP, MTU 1280 | до 1312 | оценка: MTU + 32 |
| голос и видео (RTP) | обычно до 1200 | оценка |

Вывод: **на нынешних размерах пакета вверх не проходит даже минимум клиента** (1206 против 1232), а пакет вложенного
QUIC Chrome (1250) не проходит ни вверх, ни вниз (1233). Формат тут ни при чём: без адреса в датаграмме вверх было бы
1213. Нужны пакеты больше — §4.4 п. 1.

### 4.3. Что делать с датаграммой, которая не влезла

| | Как | За | Против |
|---|---|---|---|
| отбросить | RFC 9298 §6.1: прокси «SHOULD drop» и не слать капсулой; плюс «слишком большой» от TUN клиента | честно показывает путь: QUIC с поиском MTU сам подберёт размер | WireGuard с MTU 1420 перестаёт работать (DF он не ставит), хотя через UoT работает; до конца поиска MTU теряется и то, что влезло бы позже |
| капсула DATAGRAM в потоке запроса | RFC 9297 §3.5; предпочтение клиента | ничего нового на проводе; в quiche готово (§2.3); хуже, чем UoT сейчас, не бывает | надёжно и по порядку: потеря задерживает следующие большие; поиск MTU у вложенного QUIC «проходит», и он переходит на размер, который целиком едет потоком |
| фрагментация по образцу Hysteria2 | 8 байт заголовка: номер пакета, номер и число фрагментов (`sq:hysteria2/packet.go:48-56`, `:88-117`; протокол Hysteria2, «Fragmentation») | остаётся ненадёжной, как UDP | свой формат, сборка и её пределы на обеих сторонах, fuzz; потеря фрагмента теряет пакет; поток, раздувшийся после поиска MTU, едет двумя датаграммами на пакет |
| «слишком большой» от TUN клиента | ICMP приложению | приложение с DF снижает размер само | QUIC Chrome ниже 1250 не опустится; без DF бесполезно; задача клиента |

Цена на стороне Chromium у всех трёх одна: библиотека отдаёт наружу нагрузку после Context ID, фрагментация жила бы в
Go.

### 4.4. Рекомендация

1. **Сначала увеличить пакеты**, чтобы большие датаграммы стали редкостью:
   - нода: PMTUD до 1452 (§5.2, шаг 0 — правка в десятки строк);
   - клиент: поиск MTU Chromium до 1400 через `client_connection_options: MTUH` (§2.3). На провод тег не попадает; видны
     только пробный пакет в 1400 байт и пакеты после него (§10). Это единственное, что поднимает потолок «вверх» выше
     1232 и 1250.
2. **Что не влезло — капсулой DATAGRAM** в потоке того же запроса, в обе стороны, с двумя ограничениями:
   - **очередь не копится:** капсула пишется, только если поток принимает её без ожидания дольше 100 мс; иначе
     датаграмма отбрасывается. Это тот же дефект, что B8 у UoT, закрытый сразу;
   - **правило QUIC:** если первая датаграмма клиента к назначению — пакет QUIC с длинным заголовком версии 1 или 2
     (проверка — как у фронта, `niko:nikoserver/quic.go:43-56`), пара помечается; у помеченной пары капсулой идёт только
     датаграмма не длиннее 1252 байт (1280 − 28: базовые размеры стеков QUIC), длиннее — отбрасывается. Рукопожатие и
     обычные пакеты вложенного QUIC проходят всегда, а его пробы MTU выше ёмкости теряются, как на настоящем пути:
     сервер не уходит на размер, который целиком поехал бы потоком.
3. **Потолки:** от клиента — 65 507 байт, как в UoT; от назначения — 1500, как в UoT (длиннее всё равно не доходит до
   ноды целым: фрагменты режет периметр, §2.1).
4. **Клиенту:** локальный «слишком большой» для UDP с DF (§2.4 п. 3) снизит долю капсул; решает клиент.

Почему не фрагментация: она нужна ровно тем потокам, которые не подстраиваются (WireGuard с MTU 1420, редкий большой
DNS), а им капсула даёт то же, что UoT сейчас, без нового формата. Тем, кто подстраивается, не нужны ни она, ни капсула
— им нужен честный отказ, и правило QUIC его даёт. Отступление от «SHOULD NOT» в RFC 9298 §6.1 сознательное; причину,
которую называет RFC (обман поиска MTU), закрывает то же правило.

Что остаётся неизвестным: доля датаграмм, идущих капсулой, на настоящем трафике; работает ли правило QUIC с серверами,
которые начинают выше 1252. Это мерить на шаге 2 (§11).

«Сжатые» контексты (как в bind-16 §5: адрес один раз, дальше без него) дали бы 7 или 19 байт. После п. 1 это ничего не
решает, до него — не хватает и с ними. В первой версии их нет.

## 5. Сокет для QUIC на ноде

### 5.1. Варианты

Числа ревью (4 vCPU, loopback, скачивание по потоку): HTTP/2 — 3,1–3,5 с процессора на ГиБ; HTTP/3 через фронт — 7,6–7,9
у ноды и ещё 6,5 у фронта; quic-go со своим сокетом — 3,3 Гбит/с против 1,2 через фронт (17-naive-default §3) и около
3,5 с/ГиБ (число ревью; в 17-naive-default его нет). Всё в столбце «процессор» ниже, кроме этих чисел, — оценка: ничего
из вариантов не собрано.

(в) не отвечает на вопрос: своего сокета она не даёт, а даёт только стек с BBR — это §6, и для него не нужно переносить
naive в другой процесс.

### 5.2. Рекомендация: (г), после дешёвого шага

**Шаг 0 — на нынешнем пути, без смены IPC.**
- PMTUD: quic-go включает поиск MTU, если у `PacketConn` есть `SyscallConn` и адрес UDP (`qg:sys_conn.go:79-97`).
  `nikoipc.PacketConn` может отдавать `SyscallConn` служебного UDP-сокета: DF на настоящем сокете уже ставит фронт.
  Замер: с такой обёрткой датаграмма выросла с 1243 до 1393–1404 за 3 с. Это опора на внутренности quic-go; при переходе
  на форк (§6) она не нужна вовсе.
- Ключ сброса: `quic.Transport{StatelessResetKey}` вместо `quic.ListenEarly` — уже в работе (17-naive-default §6.3).
- Предел потоков на соединение: каждый запрос UDP — поток; 256 мест пользователя не помещаются в 100 потоков quic-go
  (`qg:internal/protocol/params.go:34`). Это B1, тоже в работе; без него датаграммы упрутся в него первыми.

**Шаг (г).**
1. Фронт при старте создаёт на каждый адрес 443 группу сокетов `SO_REUSEPORT`: сокет 0 — свой, остальные — по одному на
   бэкенд QUIC без обфускации. Дескриптор бэкенд получает по тому же каналу, которым передаются TCP-сокеты
   (`niko:docs/IPC.md`, режим `fd`); копию фронт держит у себя.
2. На группу фронт вешает классический BPF (`SO_ATTACH_REUSEPORT_CBPF`): короткий заголовок или длинный с Connection ID
   нашей длины — проверить метку и вернуть номер сокета; всё остальное — сокет 0. Замер на ядре 6.18: программа видит
   данные UDP с нулевого смещения; сокеты нумеруются в порядке `bind`; дубликат дескриптора сохраняет место в группе;
   номер за пределами группы ядро заменяет выбором по хешу — поэтому по умолчанию программа возвращает 0.
3. Бэкенд выдаёт Connection ID своим генератором (`qg:transport.go:86`), 8 байт: метка сокета, два проверочных байта (от
   секрета ноды и случайной части), пять случайных. Проверочные байты нужны, потому что случайные данные тоже приходят
   на этот порт: пакет salamander и первый Initial Chrome, у которого Connection ID — те же 8 байт, но случайных
   (`quiche:quic/core/quic_connection_id.h:34`). С двумя байтами такой пакет уходит не тому сокету с вероятностью
   порядка 2⁻¹⁶; клиент повторит.
4. Первый Initial клиента несёт случайный Connection ID: он приходит фронту. Фронт, как сейчас, читает имя из
   ClientHello и пересылает эти датаграммы бэкенду прежним режимом `packet`. Бэкенд подмешивает их в чтение своего
   сокета через `ReadBatch` (§2.2) и отвечает уже со своего сокета. Следующие пакеты клиента несут Connection ID бэкенда
   и идут мимо фронта.
5. Hysteria2 с salamander остаётся на прежнем пути: у него заголовков не видно. `hy2-masq` и DoH3 могут перейти позже
   тем же способом.

Что это даёт: путь пакета как у quic-go со своим сокетом; смена порта NAT и пробы нового пути доходят до стека; фронт не
нужен соединению после рукопожатия, и его таблица потоков с простоем 60 с (B3) перестаёт на него влиять.

Чего это стоит: правки в двух репозиториях и в IPC (новое сообщение с дескриптором); примерно по 300 строк с тестами на
каждой стороне (оценка); длина Connection ID 8 вместо 4 отнимает 4 байта у датаграммы клиента (§4.1); фронт и бэкенды
QUIC перезапускаются вместе.

Почему не (а): подключённые сокеты не переживают смену порта NAT, а она на мобильных сетях обычна; сокетов и горутин —
по числу клиентов; подключённые сокеты в одной группе с неподключёнными — место, где ядра разных версий ведут себя
по-разному (не проверено). Почему не (б): два процесса по-прежнему трогают каждый пакет.

### 5.3. Что не меняется в периметре и что надо знать

- Правила входа смотрят на адрес источника и порт назначения до выбора сокета: допуски SPA, предел новых потоков на
  адрес, перенаправление портов расписания работают как раньше (§2.1).
- **Смена порта NAT при том же адресе** проходит, пока жив допуск и пока открыт порт слота, на который клиент пришёл.
  Порт слота открыт до конца следующего слота (spa-v2 §11): соединение переживает смену порта NAT только первые один-два
  слота своей жизни, 5–60 минут, и с (г) тоже. Старые пакеты идут по записи conntrack; новая пара адресов — новый поток,
  а его порт уже никуда не ведёт.
- **Смена сети** (другой адрес) требует нового допуска SPA раньше первого пакета. Приложение при смене сети и так
  закрывает все соединения (17-naive-default §2.2): миграцию QUIC между сетями в этой версии не делаем (§12 п. 8).
- Сокеты группы создаёт фронт: для правил по UID и для cgroup юнита это сокеты фронта, как и сейчас (не проверено
  тестом, §14). Сокеты к назначениям по-прежнему создаёт процесс naive: политика выхода и страж conntrack их видят.

## 6. Управление перегрузкой

Почему это не мелочь. Все датаграммы соединения идут под одним управлением перегрузкой (RFC 9221 §5.4; RFC 9298 §6). У
NewReno скорость при случайных потерях ограничена примерно `1,22 · MSS / (RTT · √p)`: при 1250 байтах, 100 мс и 1 %
потерь — около 1,2 Мбит/с на всё соединение (оценка по формуле, не замер). Вложенный QUIC с BBR через такой туннель
быстрее не поедет. Если TCP остаётся на HTTP/2 (§9.2), для UDP это единственное, что от B5 зависит, — но зависит
целиком.

| quic-go v0.64.1 как есть | NewReno, подменить нельзя (§2.2) | нет | ноль | MIT |
| **форк SagerNet + BBR из sing-quic** | `Conn.SetCongestionControl` (`sqg:connection.go:3188-3191`) и `congestion_meta2` (`sq:hysteria2/service.go:329-335`) | да, тот же, что у Hysteria2 на этой же ноде | база форка — v0.61.0 при v0.64.1 у апстрима; обновления и исправления безопасности приходят с задержкой SagerNet; в `go.mod` ноды два quic-go, как уже в niko-server | форк — MIT; sing-quic — GPL-3.0-or-later, raycontrol — GPL-3.0: совместимо |

| ждать апстрим | — | неизвестно когда | — | — |

Равнозначны ли сервер HTTP/3 и датаграммы в форке: по именам — да. Есть `http3.Server.EnableDatagrams`, `ServeListener`,
`IdleTimeout`, `HTTPStreamer`, `Stream.SendDatagram`/`ReceiveDatagram`, очереди 32 и 128,
`Transport.ConnectionIDGenerator`, `StatelessResetKey`, крючок `ReadBatch` (`sqg:http3/server.go:135-158`, `:265`;
`sqg:http3/stream.go:145-150`; `sqg:datagram_queue.go:13-14`; `sqg:transport.go:84-97`; `sqg:sys_conn_oob.go:38-40`,
`:248`). Сверх того форк верит в DF на не-сокете (§2.1). Построчно три выпуска разницы не сверялись (§14).

**Рекомендация — форк SagerNet с BBR из sing-quic**, только для слушателя HTTP/3 у naive; DoH3 и остальное остаются на
апстриме. Причины: этот BBR уже работает на той же ноде под Hysteria2; шаг 0 из §5.2 получается без обёртки; лицензия та
же, что у репозитория. Цена — зависимость от темпа SagerNet и второй стек QUIC в бинарнике. До решения стоит померить
NewReno против BBR на датаграммах с потерями (§11, шаг 1): формула выше — не замер.

На клиенте алгоритм выбирается без патча: `client_connection_options` (`cgo:naive_client.go:27-35`); приложение его не
задаёт (17-naive-default §2.2). Это влияет на отправку с телефона и решается клиентом.

## 7. Обработчик на ноде

**Где подключается.** В `Server.ServeHTTP` перед общей проверкой: `Method = CONNECT`, `ProtoMajor = 3`, `Proto =
"connect-udp"`, путь из §3.2, есть `Padding` — затем пароль (`Users.admit`), как у всех. `internal/naive` остаётся без
зависимости от quic-go: датаграммы приходят интерфейсом из двух методов (`SendDatagram`, `ReceiveDatagram`), а
`*http3.Stream` в него заворачивает `cmd/rayd`. Политика — та же `uotStream`: `resolve`, `mayReach`, `heard`, `touch`;
новые только кадры.

**Пределы и учёт** — существующие счётчики, новых чисел нет:

| Что | Значение | Откуда |
|---|---|---|
| место | из общего счёта с потоками UoT: 256 на пользователя, 4096 на сервис; на пределе уступает запрос, тихий 10 с | `limits.go:353-395`; conn-limit-v1 §2 п. 4 |
| отказ в месте | `429` до ответа (у UoT — сброс после `200`) | §3.2 |
| новые назначения | 100/с, запас 200; 4096 на запрос; пары — в журнал пользователя после конца запроса | `uot.go:241-267`, `limits.go:406-461` |
| резолвы имён | общая корзина пользователя, кеш процесса | `uot.go:271-331` |
| ответы | только от пар, куда запрос отправлял | `uot.go:199-210` |
| простой | 2 минуты в обе стороны | `uot.go:26` |
| трафик | `up` — данные датаграммы, ушедшей назначению; `down` — данные ответа, принятого к отправке клиенту; отброшенное не считается | `users.go:94-105`; [traffic-limit-v1](traffic-limit-v1.md) §2.3 |
| отзыв | пользователь ушёл из users-файла — сброс потока | `naive.go:77-81` |
| выключатель | `-conn-limit` действует так же, как на UoT | `limits.go:24-26` |

**Очереди.**
- К клиенту: своя очередь запроса на 32 датаграммы перед `SendDatagram`; полна — новая датаграмма отбрасывается. Без неё
  блокирующая отправка quic-go (§2.2) копила бы ответы в буфере сокета ядра, сотни пакетов.
- От клиента: читать `ReceiveDatagram` отдельной горутиной сразу после ответа; очередь потока в quic-go — 32.
- Капсулы — по правилам §4.4.

**ICMP.**
- Ошибки ICMP от назначения запрос не рвут и клиенту не передаются, как в UoT (naive-uot-v1 §3).
- «Слишком большой» назначению нода послать не может: нужен raw-сокет, а data plane без привилегий. Вместо него —
  отбрасывание (§4.4).
- icmp-v1 не меняется: ping остаётся потоком.

**Журналы.** Ни назначений, ни источников. В конце запроса, на уровне debug: число датаграмм в каждую сторону, сколько
ушло капсулой, сколько отброшено и почему (не от пары, длиннее потолка, очередь, правило QUIC, предел). Виды отказов
conn-limit — прежние восемь (`internal/connlimit/connlimit.go:27`); новых не добавляется.

**Что видно до пароля.**
- Любому, кто завершил рукопожатие QUIC с правильным SNI (для этого нужен допуск SPA): `max_datagram_frame_size` в
  параметрах транспорта и `SETTINGS_H3_DATAGRAM = 1`.
- Запрос без пароля или `Padding` получает ответ сайта, как любой другой.
- Датаграммы без принятого запроса отбрасываются; на чужом потоке их копится не больше 32, пока обработчик не ответил
  (§2.2).

## 8. Клиент

Код клиента ведёт клиентская сессия; здесь — что нужно от Chromium и набросок интерфейсов.

### 8.1. Как открыть запрос на той же сессии QUIC

Тем же путём, что и потоки CONNECT naive (§2.3): запрос bidirectional stream из того же движка, на тот же URL, с тем же
`-network-isolation-key` и `-force-quic: true`. Ключ сессии совпадает — пул отдаёт существующую сессию.
`QuicSessionPool::ProxyJob`, `ProxyChain` и `ProxyDelegate` не участвуют. «Преамбул» в cronet-go нет; запрос UDP —
обычный запрос на сессии и от них не зависит.

### 8.2. Что добавить

1. **Заголовки extended CONNECT.** Служебный заголовок `-connect-protocol` по образцу `-connect-authority`: с ним
   `BidirectionalStreamQuicImpl::WriteHeaders` собирает заголовки через готовую
   `CreateSpdyHeadersFromHttpRequestForExtendedConnect` (`sn:net/quic/bidirectional_stream_quic_impl.cc:109-127`;
   `sn:net/spdy/spdy_http_utils.cc:244-264`).
2. **Датаграммы на потоке.** Реализация QUIC регистрирует себя как `Http3DatagramVisitor`, когда поток готов; новый
   метод `Handle` шлёт нагрузку с заданным Context ID и возвращает «слишком велика», не трогая поток (сейчас — сброс,
   §2.3).
3. **Капсулы.** Отправка — `WriteCapsule`; приём уже приходит в тот же visitor (§2.3). Выбор «датаграмма или капсула» —
   внутри библиотеки: до `200` и `SETTINGS` — капсула; после — датаграмма, а если не влезла и вызывающий разрешил —
   капсула.
4. **Размер.** `GetMaxDatagramSize` потока минус Context ID (`quiche:quic/core/http/quic_spdy_stream.cc:1853-1880`);
   уведомление — когда меняется размер пакета сессии.
5. **Объект C API** рядом с `bidirectional_stream_*` (`sn:components/grpc_support/include/bidirectional_stream_c.h`),
   как просил клиент (§2.4 п. 2):

```c
typedef struct datagram_stream { void* obj; void* annotation; } datagram_stream;

typedef struct datagram_stream_callback {
  /* Ответ ноды. Слать можно и до него: библиотека сама выберет капсулу. */
  void (*on_ready)(datagram_stream* s, int status,
                   const bidirectional_stream_header_array* headers);
  /* Одна датаграмма: нагрузка после Context ID. data живёт до возврата. */
  void (*on_datagram_received)(datagram_stream* s, const char* data, int len);
  /* Сколько байт нагрузки теперь уходит одной датаграммой QUIC. */
  void (*on_max_payload_changed)(datagram_stream* s, int max_payload);
  void (*on_failed)(datagram_stream* s, int net_error);
  void (*on_canceled)(datagram_stream* s);
} datagram_stream_callback;

datagram_stream* datagram_stream_create(stream_engine* engine, void* annotation,
                                        const datagram_stream_callback* callback);
int datagram_stream_start(datagram_stream* s, const char* url,
                          const bidirectional_stream_header_array* headers);
/* 0 — принято; < 0 — отброшено: очередь полна, не влезло, поток закрыт.
 * flags: 1 — если не влезло в датаграмму QUIC, послать капсулой. */
int datagram_stream_send(datagram_stream* s, const char* data, int len, int flags);
int datagram_stream_max_payload(datagram_stream* s);
void datagram_stream_cancel(datagram_stream* s);
int datagram_stream_destroy(datagram_stream* s);
```

- **Потоки выполнения.** Колбэки — в сетевом потоке движка, как у bidirectional stream: блокировать его нельзя, данные
  копировать до возврата. `send` зовётся из любого потока: копирует буфер и ставит задачу сетевому потоку.
- **Обратное давление.** `send` не блокирует. Счётчик неотправленных задач ограничен (64): сверх — отказ с кодом. Дальше
  датаграмму держит очередь quiche не дольше 1,25 RTT (§2.3). На приёме библиотека ничего не копит: очередь — у
  вызывающего.
- **Жизнь.** Как у bidirectional stream: `destroy` из любого потока, выполняется отложенно; после `on_failed` и
  `on_canceled` колбэков нет.
- Context ID для этого объекта — константа формата (2); наружу не выходит.
- Нода без `SETTINGS_H3_DATAGRAM` — `on_failed` со своим кодом, запрос не отправляется: клиент сразу берёт UoT.

### 8.4. cronet-go и исходящий naive в ядре (набросок)

- **Ядро:** `ListenPacket` исходящего naive по строке с `udp=1` возвращает `net.PacketConn` поверх этого соединения:
  `WriteTo` дописывает адрес (§3.2) и зовёт `send` с разрешением капсулы по §4.4; чтение разбирает адрес источника. Не
  открылось или проба не прошла (§9.3) — тот же `ListenPacket` отдаёт UoT, как сейчас.
- **Параметры движка:** `client_connection_options` с `MTUH` (§4.4).

## 9. Подписка, проба, откат

### 9.1. Параметр строки

`udp=1` — «нода несёт UDP по naive-udp-v1 на UDP-порту этого сервиса», по образцу `uot=2` и `icmp=1`
([subscription-v1](subscription-v1.md) §4). Имя и значение — предложение. Нода ставит параметр, только когда обработчик
включён; `uot=2` остаётся всегда.

### 9.2. В какой строке и куда идёт TCP

| | Строка | TCP | UDP | Цена |
|---|---|---|---|---|
| X | `naive+https://…&uot=2&udp=1` | HTTP/2, как сейчас | второе соединение — QUIC к той же ноде, только запросы UDP; откат — UoT в HTTP/2 | два соединения к ноде (TCP и UDP 443); PING QUIC раз в 15 с, пока есть сокеты UDP; QUIC без потоков данных выглядит иначе, чем просмотр сайта (§10) |
| Y | вторая строка `naive+quic://…&uot=2&udp=1` | QUIC | то же соединение | весь профиль зависит от QUIC на ноде (сейчас вчетверо дороже HTTP/2 и NewReno); два профиля одного сервиса в подписке; где UDP закрыт, клиент уходит на строку `naive+https://` целиком |

**Рекомендация — X сейчас, Y — когда QUIC на ноде догонит HTTP/2** (17-naive-default §1 считает HTTP/2 основным для
TCP). X не требует строки `naive+quic://`; её выдача (17-naive-default §5.1, шаг 2) — отдельное решение. Нужен ответ
клиента, может ли один движок вести TCP по HTTP/2 и UDP по QUIC (§13 п. 3).

Порт UDP — по расписанию сервиса, как у Hysteria2 (§2.1): клиент должен брать `port_key` сервиса и для naive (§13 п. 8).

### 9.3. Проба и откат

Рукопожатие QUIC ещё ничего не доказывает: по источникам из 17-naive-default §5 соединения к зарубежным хостингам
замирают после 15–20 КБ, а MTU пути бывает меньше 1200 байт данных UDP ([probe-v1](probe-v1.md) §6.1).

Что делает нода, чтобы проба была дешёвой и честной:
- **Подсказка без пробы.** В подписке уже есть `hints.udp_blocked` и `hints.udp_mtu` по сети клиента (probe-v1 §6.2):
  при `udp_blocked` или `udp_mtu: "<1200"` клиент QUIC не пробует.
- **Эхо тем же путём.** Датаграмма на имя замера (`probe.raycontrol.invalid`, порт сессии probe-v1 §4) уходит в эхо UDP
  эндпоинта подписки на loopback ноды. Так уже делает бэкенд Hysteria2 (`niko:nikoserver/hyudp.go:93-97`, `:146-152`); у
  naive сейчас имя замера работает только для TCP (`internal/naive/dial.go:27-36`). Эхо меряет потери в каждую сторону,
  RTT, порядок и размеры (probe-v1 §4) именно на том пути, которым пойдёт трафик: тот же QUIC, те же датаграммы, тот же
  обработчик. Сессия эха в несколько десятков пакетов по 1200 байт проходит и порог 15–20 КБ.
- **Честный отказ.** `429` и ответ сайта отличимы от тайм-аута (§3.2).

Как откатываться — решает клиент. Что гарантирует нода: UoT в HTTP/2 доступен всегда; запросы UDP и потоки UoT одного
пользователя живут одновременно и делят один предел мест; порт ноды у нового запроса новый, как при любом переоткрытии
сокета.

### 9.4. 0-RTT, keepalive, смена сети

- **0-RTT не включаем.** Запрос, повторённый из ранних данных, заставил бы ноду повторить чужой UDP-пакет; выигрыш —
  один оборот при переподключении. Сейчас 0-RTT нет ни на ноде, ни у CONNECT в Chromium (§2.3).
- **Keepalive и батарея.** Пока открыт хоть один запрос UDP, клиент шлёт PING раз в 15 с; запрос живёт 2 минуты после
  последнего пакета; после закрытия последнего запроса сессия гаснет через 30 с (§2.3). Нода keepalive не шлёт. Итого
  после последнего пакета последнего сокета — ещё до 8 PING, затем 30 с тишины и закрытие. Сокращать простой запроса
  ниже 2 минут нельзя: приложения рассчитывают на такой срок привязки NAT (RFC 4787, REQ-5). Сколько это стоит батарее,
  без телефона не узнать.
- **Смена сети.** Приложение закрывает все соединения; запросы открываются заново после нового допуска SPA, порты ноды у
  сокетов приложений меняются — как сейчас с UoT.

## 10. Отпечаток и заметность

Блокировки — по 17-naive-default §5; здесь только то, что добавляет эта схема.

| Что | Кто видит | Отличие от Chrome, идущего на сайт по HTTP/3 |
|---|---|---|
| ClientHello и параметры транспорта клиента | любой на пути (ключи Initial общеизвестны) | **нет:** `max_datagram_frame_size = 65536` Chrome шлёт всем (§3.2); `MTUH` в `client_connection_options` на провод не идёт (§2.3) |
| `SETTINGS` клиента | никто на пути (зашифровано) | нет: `SETTINGS_H3_DATAGRAM = 1` Chrome шлёт всем (§3.2) |
| параметры транспорта и `SETTINGS` ноды | только тот, кто сам завершил рукопожатие с верным SNI (после допуска SPA) | появляются `max_datagram_frame_size = 16383` и `SETTINGS_H3_DATAGRAM = 1`. Нода и так отличима как quic-go (Connection ID в 4 байта, набор параметров); объявляют ли датаграммы обычные сайты — не проверено (§14) |
| доля кадров DATAGRAM, отсутствие повторов | никто на пути: тип кадра и номера пакетов зашифрованы | — |
| размеры и ритм пакетов | любой на пути | **да.** Вложенные протоколы видны размерами: пара пакетов около 1250 в начале вложенного QUIC, ровный поток мелких пакетов в обе стороны при звонке. Паддинга, как у первых кадров TCP-туннеля naive, у датаграмм нет |
| пакеты клиента длиннее 1250 байт | любой на пути | **возможно.** Обычному сайту Chrome шлёт до 1250 (§2.3); 1350 — только своим прокси. После `MTUH` клиент шлёт до 1400. Шлёт ли так настоящий Chrome на каких-то сборках — не проверено |
| соединение QUIC без потоков данных (вариант X) | любой на пути, статистически | **да:** нет рисунка «запрос — большой ответ». Одновременно TCP и QUIC к одному адресу у Chrome бывает (по поведению Chromium с Alt-Svc; не проверено) |
| длина Connection ID ноды (8 в §5.2) | любой на пути | не больше, чем сейчас: 4 байта — умолчание quic-go |
| миграция | любой на пути | Chrome при плохом пути пробует новый порт (`sn:net/quic/quic_context.h:192`, `allow_port_migration = true`); сейчас такая проба до ноды не доходит (фронт её отбрасывает) и клиент остаётся на старом пути; с (г) дойдёт. Смены сети у нас нет: приложение закрывает соединения |

Что из этого следует: рукопожатие датаграммы не выдают; выдать может только рисунок трафика — размеры и ритм. Это не
хуже UoT (там те же размеры видны через записи TLS), но и не лучше. Паддинг датаграмм — отдельная тема, в эту версию не
входит.

Что это значит при известных блокировках (17-naive-default §5):
- фильтр QUIC смотрит SNI в Initial: имя у QUIC то же, что у HTTP/2 этого сервиса, нового он не узнаёт; но остаточная
  блокировка четвёрки адресов на 420 с задела бы и переподключение QUIC;
- замирание после 15–20 КБ касается и UDP: поэтому проба (§9.3) обязана перейти этот порог, а не остановиться на
  рукопожатии;
- замедление за много параллельных TLS-соединений к одному адресу: вариант X добавляет к соединению HTTP/2 одно
  соединение QUIC — это не «много», но уже не одно; считает ли фильтр QUIC вместе с TLS, источники не говорят;
- где UDP или зарубежный хостинг режут целиком, датаграммы не открывают ничего сверх HTTP/2: остаётся UoT.

## 11. Порядок работ и тесты

После каждого шага нода и клиент работают как до него; новое включается параметром строки, который нода ставит
последним.

| Шаг | Что | Где | Что остаётся запасным |
|---|---|---|---|
| 0 | HTTP/3 как он есть: PMTUD через фронт, ключ сброса, предел потоков (§5.2); тесты HTTP/3 для UoT, ICMP, пределов, отзыва | нода | — (это правки без нового поведения) |
| 1 | обработчик §3 и §7 за флагом сервиса, параметр `udp=1` не выдаётся; имя замера для UDP; тестовый клиент на Go; замер NewReno против BBR и решение §6 | нода | UoT; флаг выключен |
| 2 | патч libcronet (§8.2), cronet-go, исходящий в ядре; interop с `rayd naive`; доля капсул и правило QUIC на настоящем трафике | клиент | UoT: клиент включает датаграммы только по `udp=1` |
| 3 | свой сокет (§5.2, шаг (г)), BBR | нода и фронт | прежний путь через фронт — настройкой бэкенда |
| 4 | `udp=1` в строке (по решению — с флагом сервиса или всем); замеры на живых сетях; решение о Y | нода, клиент | UoT в HTTP/2 — всегда |

Шаг 1 не ждёт шага 3: обработчик не зависит от пути пакетов. Шаги 1 и 2 идут параллельно и сходятся на interop.

**Тесты.**
- **Модульные, нода** (шаг 1): политика под новыми кадрами — имена, запрещённые адреса, `heard`, пределы и `429`,
  вытеснение, простой, отзыв, очередь к клиенту, оба правила §4.4, ранние капсулы, неизвестный Context ID и неизвестная
  капсула.
- **Матрица HTTP/3** (шаг 0 и 1): то, что сейчас проверяется только по HTTP/2, — UoT, ICMP, пределы, отзыв — и то же для
  датаграмм; клиент — quic-go поверх `nikoipc.PacketConn`, как уже сделано в `internal/xrayapi/xray_test.go:783-796`.
- **Fuzz** (шаг 1): разбор датаграммы (адрес, имя, порт), чтение капсул (длина, пропуск неизвестных), проверка «пакет
  QUIC» из §4.4. На клиенте — разбор адреса в Go; капсулы разбирает quiche.
- **netns с задержкой и потерями** (шаг 1 и 3): три пространства имён с veth, как в `test/relay/run.sh`, плюс `tc …
  netem delay … loss …` и MTU 1400 на одном звене. Проверить: PMTUD находит размер и не пробивает его; под потерями
  датаграммы не задерживают друг друга, а капсулы — только друг друга; очередь не растёт под перегрузкой; NewReno против
  BBR. netem в репозитории пока нигде не используется; есть ли модуль `sch_netem` на раннерах CI — не проверено.
- **Сокет (г)** (шаг 3): netns — выбор сокета по метке, Initial через фронт, смена порта клиента посреди соединения,
  перезапуск бэкенда (сброс доходит до клиента) и фронта; соседство с salamander.
- **Interop с настоящим клиентом** (шаг 2): в CI форка cronet-go (там уже есть `test/quic_test.go`,
  `test/integration_test.go`) против бинарника `rayd naive`; в CI этого репозитория клиент на Chromium не запускается
  (17-naive-default §3).

**Что меряется на loopback:** процессор на ГиБ и пакеты в секунду для датаграмм против UoT (у UoT — 31,8 с/ГиБ на эхо по
1200 байт, ревью); цена пути через фронт против своего сокета; задержка в очередях; размеры из §4.1 на настоящем
клиенте.

**Что требует настоящей сети или телефона:** MTU мобильных сетей и доля капсул; смена порта NAT у операторов; потери и
RTT, на которых расходятся NewReno и BBR; замирание после 15–20 КБ и закрытый UDP 443; батарея; сравнение рисунка
трафика с настоящим Chrome.

## 13. Вопросы клиенту

1. Шлёт ли ядро в UDP имена вместо адресов (FakeIP, подмена назначения по sniff)? Если нет — тип адреса 3 убираем.
2. Какой наибольший ответ ядро примет одним пакетом при MTU TUN 9000? Сейчас потолок ноды — 1500 байт (naive-uot-v1 §3).
3. Может ли один движок вести TCP по HTTP/2, а запросы UDP — по QUIC (`-force-quic` на запрос), или движок с QUIC уводит
   на QUIC всё? От этого зависит X (§9.2).
4. Если нода выдаст и `naive+https://`, и `naive+quic://` одного сервиса — что клиент сделает с двумя профилями одного
   `svc`?
5. Сделает ли клиент локальный «слишком большой» для UDP и пометку пар QUIC по первому пакету (§4.4), или «вверх» всё
   большое идёт капсулой?
6. Приемлем ли `MTUH` в `client_connection_options`? Какие размеры пакетов показывает настоящий Chrome 158 в сравнении,
   которое клиент готовит (17-naive-default §6.2): есть ли там пакеты клиента длиннее 1250?
7. Кто и через сколько закрывает замолчавший сокет в NAT ядра? Простой ноды — 2 минуты; хорошо, если клиент закрывает
   запрос сам и не раньше.
8. Берёт ли клиент расписание UDP-портов сервиса (`port_key`) для naive по QUIC, как для Hysteria2?
9. Пропускают ли выпущенные версии Niko неизвестный параметр `udp=1` в строке naive?
10. Устраивает ли API §8.2: флаг «можно капсулой» у `send`, один колбэк приёма без различия датаграммы и капсулы,
    уведомление о размере колбэком?
11. Будет ли клиент мерить путь эхом probe-v1 через запрос UDP (§9.3) перед тем, как включать датаграммы в сети?
12. При `InsecureConcurrency` больше одного: на каком движке и с каким `-network-isolation-key` открываются запросы UDP?

## 14. Что не проверено

- **Дерево Chromium.** Читалось 154-е, по файлам с GitHub (klzgrad `v154.0.8037.49-5`, SagerNet `cronet-go-dev-v154`),
  не из локального клона. Поиска по всему дереву не было: «класс создаётся в одном месте» и «заготовку bound UDP никто в
  `net/` не использует» — по прочитанным файлам. На 158 всё надо перепроверить.
- **Настоящий Chrome.** Ни одного захвата трафика: размер Initial, параметры транспорта, `SETTINGS`, пакеты длиннее 1250
  — только по исходникам. Объявляют ли датаграммы обычные сайты — не смотрелось.
- **Расчёты §4.1** для клиента — по коду quiche, не замер. Размеры пакетов сторонних стеков QUIC, WARP, RTP — оценки.
- **Процессор** во всех вариантах §5 и объём патчей — оценки. Нагрузочных прогонов не было: машина общая.
- **(г).** Классический BPF проверен только на ядре 6.18 и от root; что он вешается без привилегий, как сказано в
  socket(7), и что так же ведут себя ядра 5.14–6.12, — не проверено. Чьим UID и cgroup считаются сокеты, созданные
  фронтом и переданные бэкенду, — по памяти о коде ядра, без теста.
- **Форк SagerNet** сверен с апстримом по именам API, не построчно.
- **Формула NewReno** — оценка порядка величины; сравнения с BBR на датаграммах не было.
- **bind-16** — версия от 24.08.2026 на datatracker; в каком он состоянии в IETF, не выяснялось.
- **Клиент** — всё в §2.4 со слов клиентской сессии; код ядра и приложения не читался.
- **`sch_netem` на раннерах CI**, батарея, мобильные сети — не проверялись.
