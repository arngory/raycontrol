# naive-udp-v1: UDP датаграммами HTTP/3 через naive

Статус: **черновик, редакция 2** (2026-11-14). Решения по первой редакции приняты (§12), клиентская сессия ответила на
её вопросы (§2.4). **Сторона ноды сделана** (raycontrol v0.30.0, шаги 0 и 1 §11 без замера NewReno против BBR): что
именно и чем отличается от текста ниже — §16. Клиента нет. Открыты одно условие владельца — размер пакета клиента,
который надо сверить с настоящим Chrome 158 (§4.5), — и замеры (§13). Основание — [17-naive-default](../17-naive-default.md) §5.1, §8 п. 1: настоящий UDP
у naive идёт датаграммами HTTP/3 в соединении QUIC с отпечатком Chrome; UoT v2 внутри HTTP/2
([naive-uot-v1](naive-uot-v1.md)) остаётся запасным путём. Пара с Hysteria2 отклонена.

Зачем: UoT несёт UDP внутри надёжного потока. Потерянный пакет туннеля задерживает все следующие, а под перегрузкой
датаграммы копятся в буфере ([15-traffic](../15-traffic.md) §2; 17-naive-default §3, B8). Датаграммы QUIC (RFC 9221)
теряются поодиночке, как UDP.

Откуда факты. У каждого утверждения — источник; чего нет в источниках, помечено «оценка» или вынесено в §14.
- Пути без префикса — этот репозиторий, `c3adefb`.

- `qg:` — quic-go v0.64.1 (`go.mod` ноды и niko-server). `sqg:` — форк SagerNet, `sagernet/quic-go`

## 1. Коротко

Решено 2026-11-14 (§12):

- **Провод (§3).** Один запрос на один UDP-сокет приложения: extended CONNECT с `:protocol: connect-udp` по HTTP/3,
  пароль и `Padding` как у naive. Датаграммы HTTP (RFC 9297) с Context ID 2 несут `[тип адреса][адрес][порт][данные]`:
  адрес назначения в каждой датаграмме. На ноде — один сокет на запрос и прежний port-restricted cone. Условие владельца
  — формат не должен стать меткой для DPI: на пути из него не видно ничего (§10).
- **Два соединения (§9.2).** TCP остаётся на HTTP/2. UDP несёт отдельное соединение QUIC к той же ноде; у клиента это
  второй движок, первый не меняется ни на байт.
- **Больше пути (§4.4).** Что не влезло в пакет QUIC, идёт капсулой DATAGRAM в потоке того же запроса; у пар, начавшихся
  с QUIC, — только до 1252 байт, длиннее отбрасывается. Капсулой идут и первые датаграммы, пока нода не ответила.
  Фрагментации нет.
- **Размер пакета (§4.4, §4.5).** Нода ищет MTU пути до 1452 байт (после съёмов §4.5 — пересмотрено: пакеты ноды
  по 1250 байт без поиска, §5.2). Клиент MTU не ищет: `MTUH` снят по съёмам §4.5 — Chrome 157 и 159 с полевыми
  испытаниями длиннее 1250 не шлют. Вверх датаграммой проходит до 1206 байт данных UDP (1194 к IPv6), вложенный QUIC
  Chrome (1250) едет капсулами.
- **Сокет QUIC (§5).** Шаг 0 на нынешнем пути через фронт: PMTUD, ключ сброса, предел потоков. Затем свой сокет у
  процесса naive: группа `SO_REUSEPORT`, которую создаёт фронт, выбор сокета классическим BPF по метке в Connection ID.
- **Перегрузка (§6).** BBR: слушатель HTTP/3 у naive переходит на форк quic-go от SagerNet с BBR из sing-quic — после
  замера NewReno против BBR.
- **Нода (§7).** Обработчик поверх политики UoT: те же места (256 на пользователя вместе с потоками UoT), пары, резолвы,
  учёт, отзыв. Отказ по пределу — `429` до ответа. Включается флагом сервиса, по умолчанию выключен.
- **Клиент (§8).** Объект датаграмм в C API libcronet рядом с bidirectional stream: 10–12 файлов, 600–900 строк патча
  (оценка).
- **Подписка (§9).** Параметр `udp=1` в строке `naive+https://`; порт — 443 или порт слота, оба открыты после SPA. На
  новой сети UDP сначала идёт по UoT, эхо probe-v1 через запрос UDP проверяет путь в фоне; прошло — новые сокеты
  открываются датаграммами.
- Смена порта NAT — да (её даёт свой сокет), миграции между сетями нет; 0-RTT выключен.

## 2. Что есть сейчас

### 2.1. Нода и фронт

- **HTTP/3 у naive.** `rayd naive` слушает QUIC поверх `nikoipc.PacketConn`: `quic.Config{MaxIdleTimeout: 2 мин,
  KeepAlivePeriod: 0}`, `http3.Server{IdleTimeout: 2 мин}` (`cmd/rayd/main.go:1325-1337`, `:1403-1422`).
  `EnableDatagrams` не задан: ни параметра транспорта, ни `SETTINGS_H3_DATAGRAM` нода не шлёт.
  `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1` сервер quic-go шлёт всегда (`qg:http3/server.go:500-506`).
- **Путь пакета.** Фронт пересылает каждую датаграмму одним сообщением SOCK_SEQPACKET, в обе стороны
  (`internal/nikoipc/packet.go:13-23`; `niko:docs/IPC.md`, режим `packet`). На пакет — копия и выделение памяти в каждом
  процессе (`packet.go:137`, `:188`; `niko:nikoserver/front.go:368-376`).
- **Что из этого следует для quic-go.** `PacketConn` — не UDP-сокет (`packet.go:48-64`). quic-go тогда работает без GSO,
  ECN и чтения пачками, DF считает неустановленным и поиск MTU не запускает: пакеты всегда 1280 байт
  (`qg:sys_conn.go:79-100`, `qg:connection.go:933`, `qg:internal/protocol/params.go:6`).
- **Фронт.** Поток закрепляется за бэкендом по паре (адрес клиента, локальный адрес) первой датаграммой, которую удалось
  классифицировать: QUIC Initial с именем из ClientHello или пакет salamander. Любая другая датаграмма от незнакомой
  пары отбрасывается. Простой — 60 с (`niko:nikoserver/udpfront.go:18-24`, `:71`, `:188-201`, `:215-228`). Сокеты фронта
  шлют с DF (`:294-310`).
- **Hysteria2 идёт тем же путём:** его бэкенд получает датаграммы от фронта в режиме `packet`
  (`niko:nikoserver/hysteria.go:35-36`, `:88`). Своего сокета у него нет. PMTUD у него работает, потому что форк
  SagerNet считает DF установленным и на не-сокете (`sqg:sys_conn.go:70-74`; `hysteria.go:150-161`).
- **Политика UDP у naive отделена от кадров.** `uotStream.resolve`, `mayReach`, `heard`, `touch` и счёт `Traffic` не
  знают о потоке (`internal/naive/uot.go:199-210`, `:241-303`; `users.go:94-105`); места и пары — `limits.uotTake`,
  `uotPut`, `newPair` (`limits.go:353-461`). Кадры UoT — `upstream`, `send`, `downstream` (`uot.go:521-613`).
- **Вход.** `Server.ServeHTTP`: не CONNECT, HTTP/1 или нет `Padding` — ответ сайта; затем пароль; затем `tunnel`
  (`naive.go:61-82`). Ответ `200` уходит раньше, чем берётся место UoT (`:131-149`).
- **Подписка.** Нода выдаёт только `naive+https://…&uot=2[&icmp=1]` (`internal/sub/sub.go:566-589`).
- **Периметр.**
  - Новый входящий поток пускает только допуск SPA на адрес источника: набор `allow4` — адрес, протокол, порт
    назначения, без порта источника; остальное — `established,related` (`internal/perimeter/firewall.go:193`, `:266`,
    `:282-297`). Допуск живёт по умолчанию 10 минут, клиент продлевает ([spa-v2](spa-v2.md) §6 п. 8, §7).
  - UDP-порт сервиса меняется по расписанию: порты слотов `slot−1`, `slot`, `slot+1` перенаправляются на 443
    (`firewall.go:257`; spa-v2 §11). naive в этом списке (`internal/provision/provision.go:1338-1342`).
  - IP-фрагменты, адресованные ноде, отбрасываются до conntrack (`firewall.go:241-243`): ответ назначения длиннее MTU
    пути до ноды не доходит ни при каком формате туннеля.

### 2.2. quic-go v0.64.1

- **Датаграммы HTTP/3 есть.** `http3.Server.EnableDatagrams` (`qg:http3/server.go:169-171`); обработчик получает поток
  через `http3.HTTPStreamer` и вызывает `Stream.SendDatagram`, `Stream.ReceiveDatagram`
  (`qg:http3/response_writer.go:19-24`, `qg:http3/stream.go:180-189`). Extended CONNECT приходит как `Method = CONNECT`,
  `Proto = <:protocol>`, `ProtoMajor = 3` (`qg:http3/headers.go:292-343`). Капсулы читает `http3.CapsuleParser`, пишет
  `http3.WriteCapsule` (`qg:http3/capsule.go`).
- **Отправка блокирует.** Очередь датаграмм соединения — 32; когда она полна, `SendDatagram` ждёт
  (`qg:datagram_queue.go:14-17`, `:49-80`; замер: 200 датаграмм подряд — 2–24 мс). Срока годности у датаграммы в очереди
  нет.
- **Приём.** Очередь соединения — 128, очередь потока — 32, лишнее отбрасывается (`qg:datagram_queue.go:14-17`,
  `qg:http3/state_tracking_stream.go:12`, `:136-146`). Датаграмма для потока, который слой HTTP/3 ещё не принял,
  отбрасывается (`qg:http3/conn.go:303-309`): та, что клиент послал сразу за запросом, может потеряться.
- **Размер.** `SendDatagram` берёт не больше `MTU − 37` байт (`qg:connection.go:3066-3084`, `:3188-3190`); замер на 1280
  — 1243. Потолок пакета — 1452 (`qg:internal/protocol/protocol.go:111`). Параметр транспорта `max_datagram_frame_size`
  — 16383 (`qg:internal/wire/datagram_frame.go:14`, `qg:connection.go:351`).
- **Управление перегрузкой — NewReno**, зашито (`qg:internal/ackhandler/sent_packet_handler.go:155-162`); открытого
  способа подменить алгоритм нет.
- **Сокет.** GSO на отправке (ядро не старше 5.0), чтение пачками по 8, GRO нет (`qg:sys_conn_helper_linux.go:24`,
  `:66-81`). Обёртка сокета может подставить своё чтение пачек: `ReadBatch` (`qg:sys_conn_oob.go:36-38`, `:108-118`).
- **Транспорт.** `ConnectionIDLength` (по умолчанию 4), `ConnectionIDGenerator`, `StatelessResetKey`,
  `TokenGeneratorKey`, `VerifySourceAddress` (`qg:transport.go:79-122`, `:408-417`). Нода сейчас ничего из этого не
  задаёт (`cmd/rayd/main.go:1406`).
- **masque-go v0.6.0** (готовый прокси RFC 9298) не берём: одна цель на запрос, пишет назначения в журнал, требует
  quic-go v0.63 (`masque-go@v0.6.0/proxy.go:18`, `:164-175`, `go.mod`).

### 2.3. Клиент: cronet-go и Chromium

- **Как naive ходит через cronet-go.** Не через прокси-стек Chromium: `NaiveClient` открывает bidirectional stream с
  методом `CONNECT` на URL ноды и заголовками `-connect-authority`, `Padding`, `proxy-authorization`, `-force-quic`,
  `-network-isolation-key` (`cgo:naive_client.go:471-495`). Поток идёт через
  `HttpStreamFactory::RequestBidirectionalStreamImpl` (`sn:net/http/bidirectional_stream.cc:204-231`),
  `-connect-authority` становится `:authority` (`sn:net/spdy/spdy_http_utils.cc:216-219`). Паддинг кадров — в Go
  (`cgo:naive_conn.go:19-131`). `ProxyChain`, `ProxyDelegate` и «преамбулы» есть только в бинарнике `naive` klzgrad
  (`cr:net/tools/naive/naive_proxy.cc:120-194`); в cronet-go их нет.
- **Сессия QUIC к ноде — обычная, не прокси:** `SessionUsage::kDestination`
  (`sn:net/http/http_stream_factory_job.cc:346`, `:898`). Отсюда размер пакета: 1250 байт, на IPv6 — 1230; прибавка 100
  байт положена только сессиям `kProxy` (`quiche:quic/core/quic_constants.h:33`; `sn:net/quic/quic_context.h:119-125`;
  `cr:net/quic/quic_session_pool.cc:2325-2336`; `sn:net/quic/quic_chromium_client_session.cc:108`, `:1153-1156`).
- **Сокет QUIC создаёт Go** (хук `UDPDialer`) и отдаёт Chromium дескриптор (`cgo:naive_client.go:274-343`).
- **`QuicProxyDatagramClientSocket`** — что это на самом деле (`cr:net/quic/quic_proxy_datagram_client_socket.cc`,
  `.h`):

  | Свойство | Где | Нам |
  |---|---|---|
  | extended CONNECT, `:protocol: connect-udp`, `capsule-protocol: ?1` | `.cc:472`, `:481-484` | подходит |
  | одна цель, в пути `/.well-known/masque/udp/<host>/<port>/` | `cr:net/quic/quic_session_pool.cc:2156-2159` | не подходит: нужен адрес в датаграмме |
  | только Context ID 0, в обе стороны | `.cc:157-168`; `cr:net/quic/quic_chromium_client_stream.cc:321-324` | не подходит |
  | очередь приёма 16, лишнее отбрасывается | `.h:140`, `.cc:190-195` | мала для всплеска; очередь нужна своя |
  | ждёт `200`; не ждёт только под выключенной по умолчанию feature | `.cc:517-527`, `:577-587`; `cr:net/base/features.cc:921-922` | нужны ранние данные без ожидания |

  | HTTP/2 нет: принимает только `QuicChromiumClientStream::Handle` | `.h:74-77` | нам и не нужен |

  Переиспользуется не класс, а то, на чём он стоит: `Handle::RegisterHttp3DatagramVisitor`,
  `QuicSpdySession::SendHttp3Datagram`, `GetGuaranteedLargestMessagePayload`
  (`sn:net/quic/quic_chromium_client_stream.h:127-131`, `:169-172`; `quiche:quic/core/http/quic_spdy_session.cc:1799`).
- **Капсулы quiche уже разбирает.** С зарегистрированным visitor тело ответа читается как капсулы; капсула DATAGRAM
  приходит в тот же `OnHttp3Datagram`, что и датаграмма QUIC; неизвестная — в `OnUnknownCapsule`. Пишет капсулу
  `QuicSpdyStream::WriteCapsule` (`quiche:quic/core/http/quic_spdy_stream.cc:1592-1612`, `:1677-1679`, `:1688`,
  `:1717-1737`, `:1882-1905`).
- **Что клиент отбрасывает сам.** Датаграмму, пришедшую раньше заголовков ответа (`quic_spdy_stream.cc:1844-1850`).
  Отправку до `SETTINGS` ноды quiche не принимает (`quic_spdy_session.cc:1799-1812`). Очередь отправки хранит датаграмму
  не дольше 1,25 минимального RTT (`quiche:quic/core/quic_datagram_queue.cc:20`, `:85-93`).
- **Bound UDP в quiche есть только заготовкой:** `RegisterConnectUdpBindVisitor` и капсулы `COMPRESSION_ASSIGN =

- **Простой и keepalive.** Простой сессии — 30 с; пока открыт хоть один запрос, клиент шлёт PING раз в 15 с

- **0-RTT для CONNECT не используется:** ранние данные — только безопасным методам
  (`sn:net/quic/bidirectional_stream_quic_impl.cc:73-77`); нода 0-RTT не принимает (`cmd/rayd/main.go:1406`).

  (`quiche:quic/core/quic_connection.cc:494-501`; `quiche:quic/core/quic_mtu_discovery.h:31-32`; флаг
  `quic_enable_mtu_discovery_at_server` по умолчанию false, `quiche:common/quiche_feature_flags_list.h:38`). Тег можно
  дать через `client_connection_options`: они в параметры транспорта не попадают, в отличие от `connection_options`
  (`quiche:quic/core/quic_config.cc:557-566`, `:1298-1300`; `sn:net/quic/quic_context.cc:88-89`;
  `sn:components/cronet/url_request_context_config.cc:509-521`).

### 2.4. Клиент (клиентская сессия, 2026-11-14)

Код ядра и приложения здесь не читался; ссылки на файлы — клиента.

| Тема | Что сказал клиент |
|---|---|
| UDP в ядре | один `PacketConn` на сокет приложения: NAT sing (`common/udpnat2/service.go:17-29`) держит таблицу по адресу источника; с первым пакетом исходящий получает `ListenPacket`, дальше у каждого пакета своё назначение, ответы принимаются с любого адреса. CONNECT-UDP с одной целью дал бы симметричный NAT и запрос на каждый адрес DNS и STUN |
| имена | обычное дело: FakeIP в приложении включён по умолчанию, UDP на поддельный адрес приходит в исходящий с именем (`route/route.go:595-607`, `newFakeIPNATPacketConn` `:333`); ещё SOCKS5 UDP ASSOCIATE локального входа. Подмены назначения по sniff нет |
| размеры | MTU TUN по умолчанию 9000 (`DataStore.kt:149`): приложение получает до 8972 байт без фрагментации; буфер пакета в ядре — 16 КиБ. Локального «слишком большой» для UDP нет: приложения шлют что хотят. 1232 байта данных UDP должны проходить без потерь |
| большие датаграммы | капсула в потоке того же запроса, не фрагментация. Правило QUIC (§4.4) клиент повторит у себя: пара — (имя, порт) или (адрес, порт). Локальный «слишком большой» для UDP с DF — позже, не в первой версии: до него всё большое не-QUIC вверх идёт капсулой |
| движки | cronet-go собирает движок либо только с HTTP/2, либо с QUIC и `-force-quic` на каждом запросе (`naive_client.go:408-413`, `:517-519`). Для UDP клиент заведёт **второй движок** в том же `NaiveClient`: свой пул сессий, TCP не меняется ни на байт, отказ QUIC TCP не задевает. Патч Chromium для этого не нужен; цена — память и потоки второго движка (не мерилось) |
| одно соединение QUIC | все запросы UDP идут на втором движке с одним постоянным ключом изоляции: одно соединение, одно управление перегрузкой, одно состояние MTU — и при `InsecureConcurrency` больше одного (TCP тогда расходится по движкам или ключам, `naive_client.go:525-531`). В строках ноды `insecure-concurrency` нет |
| `MTUH` | одна строка в `SetQUICOptions`; ставится только на втором движке. Захвата трафика настоящего Chrome по QUIC у клиента пока нет: длины пакетов Chrome по HTTP/3 он добавит в свою сверку отпечатка. *Итог (§4.5, 2026-11-16): снят, второй движок идёт без тегов MTU, как Chrome* |
| простой сокета | NAT ядра закрывает молчащий сокет по умолчаниям sing-box (`constant/timeout.go`): 5 минут; по первому порту назначения или sniff — DNS (53), NTP (123), STUN (3478) через 10 с, QUIC (443) и DTLS через 30 с. Чистое закрытие потока нодой — конец сокета NAT; следующий пакет откроет новый запрос |
| порты по расписанию | `port_key` сейчас используется только для Hysteria2; для naive по QUIC клиент сделает так же (сокет QUIC создаёт Go через knock-исходящий с `udp_ports`). Что для этого есть на ноде — §9.3 |
| строки | `naive+quic://` клиент разбирает (`quic: true`); две строки одного сервиса стали бы профилями `svc` и `svc#2`. `udp=1` все выпущенные версии, включая 1.45.0, пропускают. Ротация SNI прозрачна |
| проба | на новой сети UDP идёт по UoT; эхо probe-v1 через запрос UDP идёт в фоне; когда оно прошло (потери, порог 15–20 КБ, размер), новые сокеты в этой сети открываются датаграммами, результат помнится по сети. `hints.udp_blocked` и `udp_mtu: "<1200"` пробу отменяют |
| C API | объект по образцу bidirectional stream; Context ID и капсулы — внутри библиотеки. Набросок §8.2 принят с четырьмя правками, они внесены |
| честный connect | отдельная работа: по `niko-ack=1` в строке клиент шлёт `niko-ack: 1` в каждом CONNECT, нода отвечает на TCP CONNECT после соединения с назначением (`200`, `502`, `504`) |
| батарея | PING раз в 15 с, пока жив хоть один запрос UDP, при таких тайм-аутах заметен: мерить на телефоне |

## 3. Формат провода

Условие: тип NAT остаётся прежним ([15-traffic](../15-traffic.md) §2) — один сокет ноды на сокет приложения, ответы
только от тех, кому клиент отправлял (`uot.go:199-210`).

### 3.1. Варианты и решение

| | Что это | Тип NAT | Имена | Что готово | Итог |
|---|---|---|---|---|---|
| А | RFC 9298 как есть: цель в пути запроса, Context ID 0 | **симметричный:** запрос и сокет ноды на каждое назначение; STUN увидит разные порты | да, одно на запрос | класс Chromium, masque-go | отклонён: ломает тип NAT, запрос на каждый адрес DNS и STUN |
| Б | bind-16: один запрос, «несжатый» контекст с адресом в датаграмме, «сжатые» — на цель | наш, если нода фильтрует ответы | нет: только адреса | в quiche заготовка со старыми номерами капсул (§2.3); в Chromium и quic-go — ничего | отклонён: имён нет, а они у клиента обычны (§2.4); регистрация капсулами; черновик ещё меняется |
| В | свой профиль в оболочке RFC 9298: запрос как в А, Context ID 2 с адресом в датаграмме, регистрация заголовком | наш | да, в датаграмме | разбор адреса и вся политика из UoT | **принят** |

RFC 9298 §4 прямо оставляет расширениям регистрацию Context ID заголовками или капсулами: В стандарту не противоречит.
Раскладка адреса — как в Б (версия IP, адрес, порт): если черновик станет RFC и его поддержит Chromium, перейти можно
сменой способа регистрации.

Условие владельца: формат не должен стать меткой для DPI. Ответ — §10: запрос, `:protocol`, заголовки, `SETTINGS`,
Context ID и содержимое датаграмм зашифрованы; в том, что наблюдатель может прочесть (Initial клиента), формат не меняет
ни байта. Заметным остаётся рисунок трафика, и он от формата не зависит.

Цена решения: формат наш, со своей версией; «сжатых» контекстов (без адреса, экономия 7 или 19 байт на датаграмму) в
первой версии нет — см. §4.4.

Ещё одна отвергнутая разновидность: обычный CONNECT на служебное имя, как у UoT и ICMP. Экономит правку заголовков на
клиенте, но запрос не отличить от TCP до разбора имени.

### 3.2. Формат

**Что согласуется и где.**

| Слой | Что | Клиент (Chromium) | Нода |
|---|---|---|---|
| QUIC | параметр транспорта `max_datagram_frame_size` (RFC 9221 §3) | шлёт всегда, 65536 (`quiche:quic/core/quic_config.cc:1058`, `:1226`) | начнёт слать: 16383 |
| HTTP/3 | `SETTINGS_H3_DATAGRAM = 1` (RFC 9297 §2.1.1) | шлёт всегда (`quiche:quic/core/http/quic_spdy_session.cc:626-634`, `:2024-2026`) | начнёт слать |
| HTTP/3 | `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1` (RFC 9220) | не шлёт | шлёт уже сейчас (§2.1) |
| запрос | `capsule-protocol: ?1` (RFC 9297 §3.4), `niko-udp: 1` | в запросе | в ответе |

**Запрос** — только HTTP/3:

```
:method = CONNECT
:protocol = connect-udp
:scheme = https
:authority = <имя сервиса, то же, что в SNI>
:path = /.well-known/masque/udp/%2A/%2A/
capsule-protocol = ?1
proxy-authorization = Basic <как у naive>
padding = <как у naive>
niko-udp = 1
```

- Путь — шаблон RFC 9298 §2 с целью `*`, как в bind-16 §2 для запроса без одной цели. Нода принимает и `%2A`, и `*`: что
  из двух оставит канонизация URL в Chromium, не проверено.
- `niko-udp: 1` регистрирует Context ID 2 с форматом ниже. Другое значение — версия, которой нода не знает: ответ сайта.

**Ответ:** `:status = 200`, `capsule-protocol = ?1`, `padding`, `niko-udp = 1`. Нода отвечает, когда место взято и сокет
открыт; ждать нечего, соединения с назначением нет. От `niko-ack` ответ не зависит (§7).

| Ответ | Когда |
|---|---|
| `200` с `niko-udp: 1` | принято |
| ответ сайта (пустой `404`) | нет пароля или `Padding`; флаг сервиса выключен; неизвестная версия; не HTTP/3 |
| `429` | предел мест пользователя или сервиса (§7); только авторизованному, как у TCP ([conn-limit-v1](conn-limit-v1.md) §4.3) |
| `503` | сокет не открылся |

**Датаграмма HTTP** (RFC 9297 §2.1: после Quarter Stream ID):

```
[Context ID (varint) = 2]
[тип адреса: u8 = 4 | 6 | 3]
[адрес: 4 байта | 16 байт | u8 длина + имя]
[порт: u16 BE]
[данные UDP]
```

- От клиента адрес — назначение; от ноды — источник ответа, всегда тип 4 или 6.
- Тип 3 (имя) — только от клиента: у него это обычный случай (FakeIP, §2.4). Нода резолвит имя как в UoT (naive-uot-v1
  §3).
- Context ID 0 не используется (bind-16 §3). Датаграмму с неизвестным Context ID получатель молча отбрасывает (RFC 9298
  §5).
- Нечитаемая датаграмма (короткая, неизвестный тип адреса, пустое имя, порт 0) отбрасывается; поток живёт.

**Капсулы** в потоке запроса (RFC 9297 §3.2, §3.5):
- `DATAGRAM (0x00)` несёт ту же датаграмму HTTP. Когда — §4.4 и «ранние данные» ниже.
- Неизвестный тип пропускается. Капсула длиннее 65 774 байт (Context ID в самой длинной записи, 8 байт, тип адреса,
  имя в 255 байт с длиной, порт и 65 507 байт данных) — сброс потока.
- Кроме капсул, в потоке ничего нет. Паддинга первых кадров naive на нём нет: тело разбирает quiche (§2.3).

**Ранние данные.** Клиент не ждёт ответа: первые датаграммы он шлёт капсулами сразу за заголовками, а на датаграммы QUIC
переходит, получив `200`. Иначе первая датаграмма теряется на ноде (§2.2) или не уходит с клиента до `SETTINGS` (§2.3),
а ожидание ответа стоит оборота телефон — нода на первом пакете каждого сокета: запрос DNS шёл бы вдвое дольше. Нода не
шлёт датаграмм раньше своих заголовков. Библиотека клиента до ответа сообщает размер датаграммы 0: «пока только
капсулой» (§8.2).

**Жизнь запроса.**
- Запрос — один UDP-сокет приложения и один сокет ноды. Адрес и порт ноды для него не меняются.
- Клиент закрывает поток — нода закрывает сокет.
- Простой — 2 минуты без датаграмм в обе стороны: нода закрывает поток чисто. Клиент считает это концом сокета в своём
  NAT и на следующий пакет откроет новый запрос; порт ноды будет другим, как у UoT (§7).
- Сброс потока: отзыв пользователя, вытеснение тихого запроса новым (§7), нечитаемая капсула.

### 3.3. Старая нода, старый клиент

- **Новый клиент, старая нода.** Нода не шлёт `SETTINGS_H3_DATAGRAM`: клиент видит это до запроса. Если запрос всё же
  ушёл, нода примет его за TCP CONNECT: либо ответ сайта (`:authority` без порта, `naive.go:88-93`), либо `200` без
  `niko-udp` и сброс (имя ведёт на саму ноду, а она себе не назначение). Успеха не бывает; клиент обязан требовать
  `niko-udp: 1` в ответе.
- **Старый клиент, новая нода.** Extended CONNECT он не шлёт, UoT работает как раньше. Параметр `udp=1` все выпущенные
  версии, включая 1.45.0, пропускают (клиент).
- **HTTP/2.** Формата нет: запасной путь — UoT v2.

## 4. Размеры и датаграммы больше пути

### 4.1. Сколько влезает

Данные UDP в одной датаграмме QUIC, формат §3.2; Quarter Stream ID — 2 байта (1 у первых 64 запросов соединения, 4 после
16 384-го).

| Направление | Пакет QUIC | Датаграмма QUIC | Данные UDP при адресе IPv4 / IPv6 | Источник |
|---|---|---|---|---|
| клиент → нода | 1250 (сейчас, IPv4) | 1216 | **1206 / 1194** | расчёт по `quiche:quic/core/quic_packet_creator.cc:2299-2338` |
| клиент → нода | 1230 (сейчас, IPv6) | 1196 | 1186 / 1174 | то же |
| клиент → нода | 1400 (после поиска MTU) | 1366 | 1356 / 1344 | то же |
| нода → клиент | 1280 (сейчас) | 1243 | **1233 / 1221** | замер; `qg:connection.go:3188-3190` |
| нода → клиент | до 1452 (после PMTUD) | до 1415; на loopback 1372–1404 | до 1405 / 1393 | расчёт; замер |

- Клиентская формула: пакет − 16 (AEAD) − заголовок − 1 (тип кадра); заголовок берётся худший, 13 + длина Connection ID
  ноды. Сейчас Connection ID — 4 байта; с 8 байтами (§5.2) всё в строках «клиент → нода» меньше на 4.
- Клиент принимает пакеты до 1472 байт (`quiche:quic/core/quic_constants.h:53`): PMTUD ноды упирается в свой потолок
  1452 и в путь.
- На этих числах ничего не мерилось с настоящим клиентом; строки клиента — расчёт по коду.

### 4.2. Что нужно приложениям

| Что | Данные UDP | Источник |
|---|---|---|
| минимум, который должен проходить без потерь | 1232 | клиент (§2.4): 1280 − 48 |
| QUIC, наименьший Initial | 1200 | RFC 9000 §14.1 |
| QUIC Chrome | 1250, на IPv6 — 1230 | §2.3 |
| DNS с EDNS | до 1232 | naive-uot-v1 §3 |
| WireGuard, MTU 1420 | до 1452 | клиент |
| WARP, MTU 1280 | до 1312 | оценка: MTU + 32 |
| голос и видео (RTP) | обычно до 1200 | оценка |

Вывод: **на нынешних размерах пакета вверх не проходит даже минимум клиента** (1206 против 1232), а пакет вложенного
QUIC Chrome (1250) не проходит ни вверх, ни вниз (1233). Формат тут ни при чём: без адреса в датаграмме вверх было бы
1213. Нужны пакеты больше — §4.4 п. 1 и §4.5.

### 4.3. Что делать с датаграммой, которая не влезла

| | Как | За | Против |
|---|---|---|---|
| отбросить | RFC 9298 §6.1: прокси «SHOULD drop» и не слать капсулой; плюс «слишком большой» от TUN клиента | честно показывает путь: QUIC с поиском MTU сам подберёт размер | WireGuard с MTU 1420 перестаёт работать (DF он не ставит), хотя через UoT работает; до конца поиска MTU теряется и то, что влезло бы позже |
| капсула DATAGRAM в потоке запроса | RFC 9297 §3.5; предпочтение клиента | ничего нового на проводе; в quiche готово (§2.3); хуже, чем UoT сейчас, не бывает | надёжно и по порядку: потеря задерживает следующие большие; поиск MTU у вложенного QUIC «проходит», и он переходит на размер, который целиком едет потоком |
| фрагментация по образцу Hysteria2 | 8 байт заголовка: номер пакета, номер и число фрагментов (`sq:hysteria2/packet.go:48-56`, `:88-117`; протокол Hysteria2, «Fragmentation») | остаётся ненадёжной, как UDP | свой формат, сборка и её пределы на обеих сторонах, fuzz; потеря фрагмента теряет пакет; поток, раздувшийся после поиска MTU, едет двумя датаграммами на пакет |
| «слишком большой» от TUN клиента | ICMP приложению | приложение с DF снижает размер само | QUIC Chrome ниже 1250 не опустится; без DF бесполезно; задача клиента |

Цена на стороне Chromium у всех трёх одна: библиотека отдаёт наружу нагрузку после Context ID, фрагментация жила бы в
Go.

### 4.4. Решение

1. **Увеличить пакеты**, чтобы большие датаграммы стали редкостью:
   - нода: PMTUD до 1452 (§5.2, шаг 0);
   - клиент: поиск MTU Chromium до 1400 через `client_connection_options: MTUH` (§2.3), только на втором движке, то есть
     только на соединении QUIC для UDP (клиент). На провод тег не попадает; видны пробный пакет в 1400 байт и пакеты
     после него. Принято с условием — §4.5. **Снято по §4.5 (2026-11-16):** Chrome длиннее 1250 не шлёт, клиент тоже.
2. **Что не влезло — капсулой DATAGRAM** в потоке того же запроса, в обе стороны, с двумя ограничениями:
   - **очередь не копится:** капсула пишется, только если поток принимает её без ожидания дольше 100 мс; иначе
     датаграмма отбрасывается. Это тот же дефект, что B8 у UoT, закрытый сразу;
   - **правило QUIC:** если первая датаграмма клиента к назначению — пакет QUIC с длинным заголовком версии 1 или 2
     (проверка — как у фронта, `niko:nikoserver/quic.go:43-56`), пара помечается; у помеченной пары капсулой идёт только
     датаграмма не длиннее 1252 байт (1280 − 28: базовые размеры стеков QUIC), длиннее — отбрасывается. Рукопожатие и
     обычные пакеты вложенного QUIC проходят всегда, а его пробы MTU выше ёмкости теряются, как на настоящем пути:
     сервер не уходит на размер, который целиком поехал бы потоком.
   - Пара у клиента — как он её адресовал: (имя, порт) или (адрес, порт) (§2.4). Нода помечает и то, и другое:
     назначение из датаграммы и адрес, в который имя разрешилось, — по адресу она узнаёт ответы.
3. **Потолки:** от клиента — 65 507 байт, как в UoT; от назначения — 1500, как в UoT. Второй потолок — наш, не клиента
   (он принял бы до 8972, §2.4): длиннее MTU пути ответ всё равно не доходит до ноды целым, фрагменты режет периметр
   (§2.1).
4. **Клиент** повторяет оба ограничения п. 2 у себя. Локального «слишком большой» в первой версии нет (§2.4).

Отклонено:
- **фрагментация по образцу Hysteria2** — нужна ровно тем потокам, которые не подстраиваются (WireGuard с MTU 1420,
  редкий большой DNS), а им капсула даёт то же, что UoT сейчас, без нового формата и сборки;
- **отбрасывать всё, что не влезло** — WireGuard с MTU 1420 перестал бы работать, хотя через UoT работает.

Отступление от «SHOULD NOT» в RFC 9298 §6.1 сознательное; причину, которую называет RFC (обман поиска MTU), закрывает
правило QUIC.

Что остаётся неизвестным: доля датаграмм, идущих капсулой, на настоящем трафике; работает ли правило QUIC с серверами,
которые начинают выше 1252 (§13).

«Сжатые» контексты (как в bind-16 §5: адрес один раз, дальше без него) дали бы 7 или 19 байт. С поиском MTU на клиенте
это ничего не решает, без него — не хватает и с ними. В первой версии их нет; вернуться к ним стоит, если §4.5 закроет
`MTUH`. Решение после §4.5 — в конце §4.5.

### 4.5. Условие владельца: сверить `MTUH` с настоящим Chrome 158

Что известно по исходникам. В дереве 158 (`net/`, `components/`) поиск MTU на клиенте не включает ничто: тег `MTUH`
читает только quiche, а размер пакета задаётся один раз — 1250, для сессий к прокси 1350 (§2.3; поиск по дереву, §14).
Но `client_connection_options` Chrome получает и снаружи этого дерева — из полевых испытаний. Исходники не отвечают,
шлёт ли выпущенный Chrome пакеты длиннее 1250.

**Что снять** (делает клиентская сессия в своей сверке отпечатка, 17-naive-default §6.2):

| Что | Как | Зачем |
|---|---|---|

| Исход | Решение |

Вверх остаётся 1206 / 1194 байта: Initial и полные пакеты вложенного QUIC Chrome идут капсулами (правило QUIC это разрешает до 1252), выгрузка по вложенному QUIC едет надёжным потоком; вниз ничего не меняется. Тогда же решить про «сжатые» контексты: с ними вверх 1213 — хватит стекам с пакетом 1200, не Chrome |

Тот же захват отвечает и про ноду: если обычные серверы шлют Chrome пакеты заметно короче 1452, потолок PMTUD ноды
опускается до того, что они шлют (`quic.Config.InitialPacketSize` и предел поиска — настройки, не формат).

## 5. Сокет для QUIC на ноде

### 5.1. Варианты

Числа ревью (4 vCPU, loopback, скачивание по потоку): HTTP/2 — 3,1–3,5 с процессора на ГиБ; HTTP/3 через фронт — 7,6–7,9
у ноды и ещё 6,5 у фронта; quic-go со своим сокетом — 3,3 Гбит/с против 1,2 через фронт (17-naive-default §3) и около
3,5 с/ГиБ (число ревью; в 17-naive-default его нет). Всё в столбце «процессор» ниже, кроме этих чисел, — оценка: ничего
из вариантов не собрано.

(в) не отвечает на вопрос: своего сокета она не даёт, а даёт только стек с BBR — это §6, и для него не нужно переносить
naive в другой процесс.

### 5.2. Решение: шаг 0, затем (г)

**Шаг 0 — на нынешнем пути, без смены IPC.**
- PMTUD: quic-go включает поиск MTU, если у `PacketConn` есть `SyscallConn` и адрес UDP (`qg:sys_conn.go:79-97`).
  `nikoipc.PacketConn` может отдавать `SyscallConn` служебного UDP-сокета: DF на настоящем сокете уже ставит фронт.
  Замер: с такой обёрткой датаграмма выросла с 1243 до 1393–1404 за 3 с. Это опора на внутренности quic-go и временная
  мера: с форком (§6) она не нужна. **Сделано иначе после съёмов (§4.5, третий исход):** серверы Chrome длиннее 1250 не
  шлют, поэтому слушатель QUIC ноды (`internal/h3serve`) шлёт пакеты по 1250 байт клиенту по IPv4 и по 1230 — по
  IPv6, и MTU не ищет вовсе (`h3serve.PacketSize`: `InitialPacketSize` по семейству адреса клиента, раз на соединение,
  `DisablePathMTUDiscovery`). 1230 — по исходникам, не по съёму: Chrome на сокете IPv6 срезает 20 байт, сервер quiche
  начинает с 1000 и повторяет длину Initial клиента (строки по дереву 158: `net/quic/quic_chromium_client_session.cc:102-103`,
  `:1172-1176`; `net/third_party/quiche/src/quiche/quic/core/quic_connection.cc:257-260`, `:3296-3304`); 1250 по IPv6 — ещё и 1298 байт IP, больше минимальных 1280 IPv6.
  Ёмкость «вниз» из §4.1 от этого меньше на 30 байт по IPv4 (1203 / 1191 вместо 1233 / 1221) и на 50 — по IPv6
  (1183 / 1171); если CONNECT-UDP понадобится больше, решать здесь, а не обёрткой.
- Ключ сброса: `quic.Transport{StatelessResetKey}` вместо `quic.ListenEarly` — уже в работе (17-naive-default §6.3).
- Предел потоков на соединение: каждый запрос UDP — поток; 256 мест пользователя не помещаются в 100 потоков quic-go
  (`qg:internal/protocol/params.go:34`). Это B1, тоже в работе; без него датаграммы упрутся в него первыми.

**Шаг (г).**
1. Фронт при старте создаёт на каждый адрес 443 группу сокетов `SO_REUSEPORT`: сокет 0 — свой, остальные — по одному на
   бэкенд QUIC без обфускации. Дескриптор бэкенд получает по тому же каналу, которым передаются TCP-сокеты
   (`niko:docs/IPC.md`, режим `fd`); копию фронт держит у себя.
2. На группу фронт вешает классический BPF (`SO_ATTACH_REUSEPORT_CBPF`): короткий заголовок или длинный с Connection ID
   нашей длины — проверить метку и вернуть номер сокета; всё остальное — сокет 0. Замер на ядре 6.18: программа видит
   данные UDP с нулевого смещения; сокеты нумеруются в порядке `bind`; дубликат дескриптора сохраняет место в группе;
   номер за пределами группы ядро заменяет выбором по хешу — поэтому по умолчанию программа возвращает 0.
3. Бэкенд выдаёт Connection ID своим генератором (`qg:transport.go:86`), 8 байт: метка сокета, два проверочных байта (от
   секрета ноды и случайной части), пять случайных. Проверочные байты нужны, потому что случайные данные тоже приходят
   на этот порт: пакет salamander и первый Initial Chrome, у которого Connection ID — те же 8 байт, но случайных
   (`quiche:quic/core/quic_connection_id.h:34`). С двумя байтами такой пакет уходит не тому сокету с вероятностью
   порядка 2⁻¹⁶; клиент повторит.
4. Первый Initial клиента несёт случайный Connection ID: он приходит фронту. Фронт, как сейчас, читает имя из
   ClientHello и пересылает эти датаграммы бэкенду прежним режимом `packet`. Бэкенд подмешивает их в чтение своего
   сокета через `ReadBatch` (§2.2) и отвечает уже со своего сокета. Следующие пакеты клиента несут Connection ID бэкенда
   и идут мимо фронта.
5. Hysteria2 с salamander остаётся на прежнем пути: у него заголовков не видно. `hy2-masq` и DoH3 могут перейти позже
   тем же способом.

Что это даёт: путь пакета как у quic-go со своим сокетом; смена порта NAT и пробы нового пути доходят до стека; фронт не
нужен соединению после рукопожатия, и его таблица потоков с простоем 60 с (B3) перестаёт на него влиять.

Чего это стоит: правки в двух репозиториях и в IPC (новое сообщение с дескриптором); примерно по 300 строк с тестами на
каждой стороне (оценка); длина Connection ID 8 вместо 4 отнимает 4 байта у датаграммы клиента (§4.1); фронт и бэкенды
QUIC перезапускаются вместе.

Почему не (а): подключённые сокеты не переживают смену порта NAT, а она на мобильных сетях обычна; сокетов и горутин —
по числу клиентов; подключённые сокеты в одной группе с неподключёнными — место, где ядра разных версий ведут себя
по-разному (не проверено). Почему не (б): два процесса по-прежнему трогают каждый пакет.

### 5.3. Что не меняется в периметре и что надо знать

- Правила входа смотрят на адрес источника и порт назначения до выбора сокета: допуски SPA, предел новых потоков на
  адрес, перенаправление портов расписания работают как раньше (§2.1, §9.3).
- **Смена порта NAT при том же адресе** — принята как цель; её даёт (г). На порту 443 она проходит, пока жив допуск. На
  порту слота — пока открыт этот порт, то есть до конца следующего слота (spa-v2 §11): соединение, пришедшее на порт
  слота, переживает смену порта NAT только первые один-два слота своей жизни, 5–60 минут. Старые пакеты идут по записи
  conntrack; новая пара адресов — новый поток, а его порт уже никуда не ведёт.
- **Миграции между сетями нет** (решение, §12): другой адрес требует нового допуска SPA раньше первого пакета, а
  приложение при смене сети и так закрывает все соединения (17-naive-default §2.2).
- Сокеты группы создаёт фронт: для правил по UID и для cgroup юнита это сокеты фронта, как и сейчас (не проверено
  тестом, §14). Сокеты к назначениям по-прежнему создаёт процесс naive: политика выхода и страж conntrack их видят.

## 6. Управление перегрузкой

Почему это не мелочь. Все датаграммы соединения идут под одним управлением перегрузкой (RFC 9221 §5.4; RFC 9298 §6). У
NewReno скорость при случайных потерях ограничена примерно `1,22 · MSS / (RTT · √p)`: при 1250 байтах, 100 мс и 1 %
потерь — около 1,2 Мбит/с на всё соединение (оценка по формуле, не замер). Вложенный QUIC с BBR через такой туннель
быстрее не поедет. TCP остаётся на HTTP/2 (§9.2), так что от B5 зависит только UDP — но целиком.

| quic-go v0.64.1 как есть | NewReno, подменить нельзя (§2.2) | нет | ноль | MIT |
| **форк SagerNet + BBR из sing-quic** (принят) | `Conn.SetCongestionControl` (`sqg:connection.go:3188-3191`) и `congestion_meta2` (`sq:hysteria2/service.go:329-335`) | да, тот же, что у Hysteria2 на этой же ноде | база форка — v0.61.0 при v0.64.1 у апстрима; обновления и исправления безопасности приходят с задержкой SagerNet; в `go.mod` ноды два quic-go, как уже в niko-server | форк — MIT; sing-quic — GPL-3.0-or-later, raycontrol — GPL-3.0: совместимо |
| свой форк quic-go с крючком | правка в ~100 строк (оценка) и BBR из sing-quic или из apernet/quic-go (MIT) | да | перенос правки на каждый выпуск quic-go — наш | MIT + выбранный BBR |
| ждать апстрим | — | неизвестно когда | — | — |

`Transport.ConnectionIDGenerator`, `StatelessResetKey`, крючок `ReadBatch` (`sqg:http3/server.go:135-158`, `:265`;
`sqg:http3/stream.go:145-150`; `sqg:datagram_queue.go:13-14`; `sqg:transport.go:84-97`; `sqg:sys_conn_oob.go:38-40`,
`:248`). Сверх того форк верит в DF на не-сокете (§2.1). Построчно три выпуска разницы не сверялись (§14).

**Решение — форк SagerNet с BBR из sing-quic**, только для слушателя HTTP/3 у naive; DoH3 и остальное остаются на
апстриме. Причины: этот BBR уже работает на той же ноде под Hysteria2; шаг 0 из §5.2 получается без обёртки; лицензия та
же, что у репозитория. Цена — зависимость от темпа SagerNet и второй стек QUIC в бинарнике. Переход — после замера
NewReno против BBR на датаграммах с потерями (§11, шаг 1): формула выше — не замер, и если разница окажется не той,
решение возвращается владельцу.

Отклонено: свой форк quic-go с крючком — перенос правки на каждый выпуск был бы нашим; ждать апстрим — срока нет.

На клиенте алгоритм выбирается без патча: `client_connection_options` (`cgo:naive_client.go:27-35`); приложение его не
задаёт (17-naive-default §2.2). Это влияет на отправку с телефона и решается клиентом; теперь — отдельно для второго
движка.

## 7. Обработчик на ноде

**Где подключается.** В `Server.ServeHTTP` перед общей проверкой: `Method = CONNECT`, `ProtoMajor = 3`, `Proto =
"connect-udp"`, путь из §3.2, есть `Padding` — затем пароль (`Users.admit`), как у всех. `internal/naive` остаётся без
зависимости от quic-go: датаграммы приходят интерфейсом из двух методов (`SendDatagram`, `ReceiveDatagram`), а
`*http3.Stream` в него заворачивает `cmd/rayd`. Политика — та же `uotStream`: `resolve`, `mayReach`, `heard`, `touch`;
новые только кадры.

**Включение.** Флаг сервиса, по образцу `icmp` ([icmp-v1](icmp-v1.md) §1): `rayctl service set <naive> udp=on`, затем
`rayctl apply`; по умолчанию выключен. Выключенный сервис отвечает на запрос UDP как сайт и `SETTINGS_H3_DATAGRAM` не
шлёт. По умолчанию включённым флаг станет после проверки на живой сети (§11, шаг 4).

**Статусы.** Запрос UDP всегда отвечает по существу: `200` — когда место взято и сокет открыт, отказ — статусом до `200`
(§3.2). От `niko-ack` это не зависит: соединения с назначением у запроса нет, ждать нечего. Так поведение совпадает с
честным connect для TCP, где отказ тоже приходит статусом (`502`, `504`), а не сбросом после `200`.

**Пределы и учёт** — существующие счётчики, новых чисел нет:

| Что | Значение | Откуда |
|---|---|---|
| место | из общего счёта с потоками UoT: 256 на пользователя, 4096 на сервис; на пределе уступает запрос, тихий 10 с | `limits.go:353-395`; conn-limit-v1 §2 п. 4 |
| отказ в месте | `429` до ответа (у UoT — сброс после `200`) | §3.2 |
| новые назначения | 100/с, запас 200; 4096 на запрос; пары — в журнал пользователя после конца запроса | `uot.go:241-267`, `limits.go:406-461` |
| резолвы имён | общая корзина пользователя, кеш процесса | `uot.go:271-331` |
| ответы | только от пар, куда запрос отправлял | `uot.go:199-210` |
| простой | 2 минуты в обе стороны; нода закрывает поток чисто | `uot.go:26` |
| трафик | `up` — данные датаграммы, ушедшей назначению; `down` — данные ответа, принятого к отправке клиенту; отброшенное не считается | `users.go:94-105`; [traffic-limit-v1](traffic-limit-v1.md) §2.3 |
| отзыв | пользователь ушёл из users-файла — сброс потока | `naive.go:77-81` |
| выключатель | `-conn-limit` действует так же, как на UoT | `limits.go:24-26` |

Простой и клиент. NAT ядра клиента закрывает сокет DNS через 10 с, QUIC — через 30 с, прочие — через 5 минут (§2.4);
клиент, закрывая сокет, закрывает и поток. Нода закрывает раньше только сокеты «прочие», молчащие дольше 2 минут: клиент
примет чистое закрытие за конец сокета, следующий пакет приложения откроет новый запрос, и порт ноды у него будет
другим. Так же сейчас ведёт себя UoT; срок привязки не короче двух минут, как требует RFC 4787 (REQ-5).

**Очереди.**
- К клиенту: своя очередь запроса на 32 датаграммы, в полной уступает самая старая (позднее значит больше, а
  отбрасывание с головы раньше говорит отправителю о перегрузке; как у UoT). Блокирующий `SendDatagram` quic-go
  (§2.2) зовёт один отправитель на соединение, который берёт из очередей запросов по очереди: запрос не ждёт никогда.
  Без очереди ответы копились бы в буфере сокета ядра, сотни пакетов; ждущий в quic-go запрос пережил бы свой конец
  (§16.3). Это деталь ноды, не часть договора с клиентом.
- От клиента: читать `ReceiveDatagram` отдельной горутиной сразу после ответа; очередь потока в quic-go — 32.
- Капсулы — по правилам §4.4.

**Имя замера.** Датаграмма на `probe.raycontrol.invalid` уходит в эхо UDP эндпоинта подписки на loopback ноды —
единственное исключение из «только публичные адреса», как у бэкенда Hysteria2 (§9.4).

**ICMP.**
- Ошибки ICMP от назначения запрос не рвут и клиенту не передаются, как в UoT (naive-uot-v1 §3).
- «Слишком большой» назначению нода послать не может: нужен raw-сокет, а data plane без привилегий. Вместо него —
  отбрасывание (§4.4).
- icmp-v1 не меняется: ping остаётся потоком.

**Журналы.** Ни назначений, ни источников. В конце запроса, на уровне debug: число датаграмм в каждую сторону, сколько
ушло капсулой, сколько отброшено и почему (не от пары, длиннее потолка, очередь, правило QUIC, предел). Виды отказов
conn-limit — прежние восемь (`internal/connlimit/connlimit.go:27`); новых не добавляется.

**Что видно до пароля.**
- Любому, кто завершил рукопожатие QUIC с правильным SNI (для этого нужен допуск SPA): `max_datagram_frame_size` в
  параметрах транспорта и `SETTINGS_H3_DATAGRAM = 1` — только когда флаг сервиса включён.
- Запрос без пароля или `Padding` получает ответ сайта, как любой другой.
- Датаграммы без принятого запроса отбрасываются; на чужом потоке их копится не больше 32, пока обработчик не ответил
  (§2.2).

## 8. Клиент

Код клиента ведёт клиентская сессия; здесь — что нужно от Chromium и набросок интерфейсов.

### 8.1. На каком соединении открывается запрос

На втором движке того же `NaiveClient` (§2.4): он собран с QUIC, все его запросы идут с `-force-quic: true` и одним
постоянным `-network-isolation-key`, поэтому у пула одна сессия QUIC к ноде на все запросы UDP. Сам запрос идёт тем же
путём, что потоки CONNECT naive (§2.3): bidirectional stream, `HttpStreamFactory`, пул сессий.
`QuicSessionPool::ProxyJob`, `ProxyChain` и `ProxyDelegate` не участвуют; «преамбул» в cronet-go нет. Первый движок
(HTTP/2) не трогается: ни параметров, ни патча.

Сокет QUIC создаёт Go (§2.3) — через knock-исходящий, на порт по §9.3.

### 8.2. Что добавить в libcronet

1. **Заголовки extended CONNECT.** Служебный заголовок `-connect-protocol` по образцу `-connect-authority`: с ним
   `BidirectionalStreamQuicImpl::WriteHeaders` собирает заголовки через готовую
   `CreateSpdyHeadersFromHttpRequestForExtendedConnect` (`sn:net/quic/bidirectional_stream_quic_impl.cc:109-127`;
   `sn:net/spdy/spdy_http_utils.cc:244-264`).
2. **Датаграммы на потоке.** Реализация QUIC регистрирует себя как `Http3DatagramVisitor`, когда поток готов; новый
   метод `Handle` шлёт нагрузку с заданным Context ID и возвращает «слишком велика», не трогая поток (сейчас — сброс,
   §2.3).
3. **Капсулы.** Отправка — `WriteCapsule`; приём уже приходит в тот же visitor (§2.3). Выбор «датаграмма или капсула» —
   внутри библиотеки: до `200` и `SETTINGS` — капсула; после — датаграмма, а если не влезла и вызывающий разрешил —
   капсула. Капсула, которую поток не принял за 100 мс, отбрасывается (§4.4).
4. **Размер.** `GetMaxDatagramSize` потока минус Context ID (`quiche:quic/core/http/quic_spdy_stream.cc:1853-1880`);
   уведомление — когда меняется размер пакета сессии.
5. **Объект C API** рядом с `bidirectional_stream_*` (`sn:components/grpc_support/include/bidirectional_stream_c.h`).
   Набросок первой редакции клиент принял с четырьмя правками (§2.4); они внесены:

```c
typedef struct datagram_stream { void* obj; void* annotation; } datagram_stream;

typedef struct datagram_stream_callback {
  /* Ответ ноды, любой: 200, 429, 503, ответ сайта. Слать можно и до него:
   * библиотека шлёт капсулой. После не-200 придёт on_closed. */
  void (*on_ready)(datagram_stream* s, int status,
                   const bidirectional_stream_header_array* headers);
  /* Одна датаграмма: нагрузка после Context ID, датаграммой QUIC она пришла
   * или капсулой. data живёт до возврата. */
  void (*on_datagram_received)(datagram_stream* s, const char* data, int len);
  /* Сколько байт нагрузки теперь уходит одной датаграммой QUIC. */
  void (*on_max_payload_changed)(datagram_stream* s, int max_payload);
  /* Чистый конец: нода закрыла поток (простой) или ответила не 200. */
  void (*on_closed)(datagram_stream* s);
  /* Сброс потока или потеря соединения; также нода без датаграмм HTTP/3. */
  void (*on_failed)(datagram_stream* s, int net_error);
  void (*on_canceled)(datagram_stream* s);
} datagram_stream_callback;

datagram_stream* datagram_stream_create(stream_engine* engine, void* annotation,
                                        const datagram_stream_callback* callback);
int datagram_stream_start(datagram_stream* s, const char* url,
                          const bidirectional_stream_header_array* headers);

#define DATAGRAM_STREAM_OK 0
#define DATAGRAM_STREAM_QUEUE_FULL -1      /* очередь отправки полна */
#define DATAGRAM_STREAM_TOO_LARGE -2       /* не влезло, капсула не разрешена */
#define DATAGRAM_STREAM_CLOSED -3          /* поток закрыт */
#define DATAGRAM_STREAM_CAPSULE_TIMEOUT -4 /* капсула не ушла за 100 мс */
/* flags: 1 — если не влезло в датаграмму QUIC, послать капсулой.
 * QUEUE_FULL, TOO_LARGE и CLOSED возвращает сам вызов. */
int datagram_stream_send(datagram_stream* s, const char* data, int len, int flags);
/* До on_ready — 0: пока только капсулой. */
int datagram_stream_max_payload(datagram_stream* s);
/* Капсулы, выброшенные библиотекой за 100 мс (добавлено при реализации, под
 * DroppedCapsules §8.4). */
uint64_t datagram_stream_dropped_capsules(datagram_stream* s);
void datagram_stream_cancel(datagram_stream* s);
int datagram_stream_destroy(datagram_stream* s);
```

- **Потоки выполнения.** Колбэки — в сетевом потоке движка, как у bidirectional stream: блокировать его нельзя, данные
  копировать до возврата. `send` зовётся из любого потока: копирует буфер и ставит задачу сетевому потоку.
- **Обратное давление.** `send` не блокирует. Счётчик неотправленных задач ограничен (64): сверх — `QUEUE_FULL`. Дальше
  датаграмму держит очередь quiche не дольше 1,25 RTT (§2.3). На приёме библиотека ничего не копит: очередь — у
  вызывающего.
- **`CAPSULE_TIMEOUT`** сам вызов вернуть не может: капсула пишется позже, в сетевом потоке. Согласовано (§8.4): `send`
  возвращает его только для датаграммы, которой нужна капсула, пока голова очереди капсул ждёт дольше 100 мс; счётчик
  отброшенных капсул — `datagram_stream_dropped_capsules`. В реализации головой считается и капсула, застрявшая в
  буфере отправки потока, а 100 мс отсчитываются не раньше отправки заголовков запроса — ранние капсулы не теряются
  на рукопожатии.
- **Конец.** Три разных: `on_closed` — чистый (после него следующий пакет приложения открывает новый запрос);
  `on_failed` — сброс или обрыв; `on_canceled` — по `cancel`. После любого из них колбэков нет. `destroy` — из любого
  потока, выполняется отложенно.
- **Нода без `SETTINGS_H3_DATAGRAM`** — `on_failed` со своим кодом, запрос не отправляется: это не ответ ноды, и клиент
  остаётся на UoT.
- Context ID для этого объекта — константа формата (2); наружу не выходит.

### 8.4. cronet-go и исходящий naive в ядре (набросок)

- **cronet-go:** обвязка объекта по образцу `bidirectional_stream_*` (cgo и purego), около 400 строк (оценка); второй
  движок в `NaiveClient` и метод, который открывает на нём запрос §3.2 с теми же заголовками авторизации, что
  `DialEarly` (`cgo:naive_client.go:455-506`), и отдаёт соединение датаграмм с очередью приёма.
- **Обвязка Go (черновик к согласованию с клиентом, 2026-11-16).** В корне cronet-go, рядом с `BidirectionalStream`,
  в том же стиле (cgo и purego, колбэки через карту по указателю):

```go
// DatagramStream — запрос connect-udp (§3) на движке, чьи сессии — QUIC.
type DatagramStream struct{ ptr uintptr }

// Колбэки — в сетевом потоке движка: не блокировать; data живёт до возврата.
type DatagramStreamCallback interface {
	OnReady(stream DatagramStream, status int, headers map[string]string) // любой ответ: 200, 429, 503, сайт
	OnDatagram(stream DatagramStream, data []byte)                         // нагрузка после Context ID
	OnMaxPayloadChanged(stream DatagramStream, maxPayload int)
	OnClosed(stream DatagramStream)               // чистый конец; следующий пакет — новый запрос
	OnFailed(stream DatagramStream, netError int) // сброс, обрыв, нода без SETTINGS_H3_DATAGRAM
	OnCanceled(stream DatagramStream)
}

func (e StreamEngine) CreateDatagramStream(callback DatagramStreamCallback) DatagramStream
// Start шлёт extended CONNECT (:protocol connect-udp ставит библиотека) на url
// с заголовками, как у туннеля naive (авторизация, Padding). false — не начат.
func (s DatagramStream) Start(url string, headers map[string]string) bool
// Send копирует data и ставит в очередь сетевого потока, не блокируя.
// allowCapsule: не влезло в датаграмму QUIC — послать капсулой (§4.4).
func (s DatagramStream) Send(data []byte, allowCapsule bool) error
func (s DatagramStream) MaxPayload() int         // 0 до OnReady: пока только капсулой
func (s DatagramStream) DroppedCapsules() uint64 // капсулы, не ушедшие за 100 мс
func (s DatagramStream) Cancel()
func (s DatagramStream) Destroy() bool

var (
	ErrDatagramQueueFull      = errors.New("cronet: datagram queue full")       // DATAGRAM_STREAM_QUEUE_FULL
	ErrDatagramTooLarge       = errors.New("cronet: datagram too large")        // DATAGRAM_STREAM_TOO_LARGE
	ErrDatagramClosed         = errors.New("cronet: datagram stream closed")    // DATAGRAM_STREAM_CLOSED
	ErrDatagramCapsuleTimeout = errors.New("cronet: datagram capsule timeout")  // DATAGRAM_STREAM_CAPSULE_TIMEOUT
)
```

  Согласовано с клиентом (2026-11-16):
  - **`CAPSULE_TIMEOUT`** — только для `Send`, которому нужна капсула (не влезло в датаграмму QUIC или `MaxPayload()`
    ещё 0), пока голова очереди капсул ждёт дольше 100 мс. Датаграмму, которая влезает в кадр QUIC, застрявшая большая
    не задерживает и не отклоняет. Капсулы старше 100 мс библиотека выбрасывает сама и считает в `DroppedCapsules`:
    устаревший UDP хуже потерянного.
  - **Context ID** — константа формата (2): библиотека добавляет его при отправке и снимает при приёме, датаграммы с
    другим ID отбрасывает. Наружу его нет: вызывающий даёт и получает только `[тип адреса][адрес][порт][данные]` (§3.2).
  - **`MaxPayload`** — после Quarter Stream ID и Context ID: ровно столько можно отдать в `Send`, чтобы ушло одной
    датаграммой QUIC.
  - **Заголовки** — `map[string]string`, как у `DialEarly`: порядок и повторы не нужны.
  - **`DatagramConn`** (делает сервер, в cronet-go) по образцу `BidirectionalConn`, под `N.PacketConn` ядра:

```go
func (e StreamEngine) CreateDatagramConn(ctx context.Context, url string, headers map[string]string) *DatagramConn
// Ответ ноды: 200, 429 (предел), 503 (повтор позже) или ответ сайта (флаг выключен,
// старая нода: клиент держит UoT в этой сети); ошибка — OnFailed/OnCanceled/контекст.
func (c *DatagramConn) WaitReady(ctx context.Context) (status int, headers map[string]string, err error)
// В буфер вызывающего, без выделения на пакет; обрезанное — ErrDatagramTruncated, n = len(b).
func (c *DatagramConn) ReadDatagram(ctx context.Context, b []byte) (n int, err error)
// Из нескольких горутин; не блокирует; капсула разрешена (§4.4).
func (c *DatagramConn) WriteDatagram(b []byte) error
func (c *DatagramConn) MaxPayload() int
func (c *DatagramConn) SetReadDeadline(t time.Time) error
func (c *DatagramConn) SetWriteDeadline(t time.Time) error
func (c *DatagramConn) Dropped() (receive, capsules uint64) // очередь приёма полна; капсулы старше 100 мс
func (c *DatagramConn) Done() <-chan struct{}
func (c *DatagramConn) Err() error
func (c *DatagramConn) Close() error // Cancel
```

    Очередь приёма ограничена (256): при переполнении новые датаграммы отбрасываются и считаются. В `naive_client.go`
    у клиента остаются второй движок (создаётся лениво, при первом UDP-сокете строки с `udp=1`), заголовки
    авторизации и адрес §3.2.

  Реализовано (arngory/cronet-go, `c16f6a61`…`c2dbe685`, 2026-11-16) как выше, с добавками:
  - `ErrDatagramUnsupported` и `CheckDatagramSupport() error`: библиотека без `datagram_stream_*` (выпущенная раньше)
    грузится как прежде, а датаграммы отвечают этой ошибкой; `CreateDatagramConn` на ней возвращает уже закрытый conn.
    purego ищет эти символы отдельно; cgo берёт `datagram_stream_c.h`, если он в наборе заголовков, иначе — заглушки
    (заголовки и библиотеки публикуются одной сборкой).
  - `func (c *DatagramConn) SetDeadline(t time.Time) error`.
  - Заголовки: библиотека ставит `:protocol connect-udp` и `capsule-protocol: ?1` (если нет) и всегда идёт по QUIC;
    вызывающий — `niko-udp: 1`, авторизацию и `Padding`, и сам проверяет `niko-udp: 1` в ответе 200.
  - `Err()`: `io.EOF` — нода закрыла чисто или ответила не 200 (`WaitReady` отдаёт статус); `NetError` — сбой,
    в том числе `-322` (`ERR_METHOD_NOT_SUPPORTED`) у ноды без `SETTINGS_H3_DATAGRAM` или extended CONNECT;
    `net.ErrClosed` — после `Close`; ошибка контекста — если он кончился до ответа ноды (контекст
    `CreateDatagramConn` ограничивает только установку).
  - После конца `WriteDatagram` возвращает `ErrDatagramClosed` (после `Close` — `net.ErrClosed`); принятое до конца
    читается до ошибки. До 200 `Send(…, false)` возвращает `ErrDatagramTooLarge` (влезает только капсула): так
    клиент держит правило 1252 байт для пар QUIC (§4.4).
  - Очередь приёма — кольцо переиспользуемых буферов, без выделения памяти на датаграмму; кроме 256 штук — бюджет
    1 МиБ на соединение (капсула бывает до 65 766 байт), сверх него новые отбрасываются и считаются в `receive`.
  - После ревью (cronet-go `dc44abba`, naiveproxy `3219897e`): `cancel` до `start` — `start` возвращает −1, гонка
    `cancel` со стартом кончается `on_canceled`; `datagram_stream_dropped_capsules` считает и капсулы, не влезшие в
    очередь (64), и датаграммы, отброшенные в сетевом потоке (перестали влезать, капсула не разрешена); STOP_SENDING от
    ноды закрывает отправку (`CLOSED`), а не держит `CAPSULE_TIMEOUT` до конца потока; ошибка «не начат» оборачивает
    `os.ErrInvalid`; `WriteDatagram`: `ErrDatagramQueueFull`, `ErrDatagramCapsuleTimeout`, `ErrDatagramTooLarge` —
    потерян один пакет, сессию не закрывать.
  - `MaxPayload` на IPv4 для раннего потока (Stream ID в 1 байт) — 1214; таблица §4.1 считает ID в 2 байта (1206).
- **Ядро:** `ListenPacket` исходящего naive возвращает `net.PacketConn` поверх этого соединения, если строка несёт
  `udp=1` и проба этой сети прошла (§9.4); иначе — UoT, как сейчас. `WriteTo` дописывает адрес или имя (§3.2) и зовёт
  `send`, разрешая капсулу по §4.4; чтение разбирает адрес источника.
- **Параметры второго движка:** без тегов MTU (`MTUH` снят по §4.5, 2026-11-16).

## 9. Подписка, порт, проба, откат

### 9.1. Параметр строки и флаг сервиса

`udp=1` в строке `naive+https://` — «нода несёт UDP по naive-udp-v1 на UDP-порту этого сервиса», по образцу `uot=2` и
`icmp=1` ([subscription-v1](subscription-v1.md) §4). Нода ставит параметр, когда у сервиса включён флаг `udp` (§7) и
есть UDP-порт; `uot=2` остаётся всегда. Все выпущенные версии клиента параметр пропускают (§2.4).

### 9.2. Два соединения: TCP на HTTP/2, UDP на QUIC

Решение: TCP остаётся на HTTP/2, как сейчас; UDP несёт отдельное соединение QUIC к той же ноде. Отката внутри профиля
два: не открылся QUIC или не прошла проба — UoT в HTTP/2.

- У клиента это второй движок (§2.4): первое соединение не меняется ни на байт, отказ QUIC его не задевает.
- Цена: два соединения к одному адресу (TCP 443 и UDP); PING QUIC раз в 15 с, пока есть сокеты UDP; соединение QUIC без
  потоков данных выглядит иначе, чем просмотр сайта (§10); память и потоки второго движка (не мерилось).

Отклонено: весь профиль по QUIC (строка `naive+quic://`) — TCP зависел бы от QUIC на ноде, который пока вчетверо дороже
HTTP/2 (17-naive-default §3). Строка `naive+quic://` для UDP не нужна и нодой не выдаётся; вернуться к ней можно, когда
QUIC на ноде догонит HTTP/2.

### 9.3. Порт UDP: что открыто после SPA и что публикуется

Вопрос клиента: открыт ли после SPA сам UDP 443 или только порты слотов, и где взять расписание для naive.

**Открыто и то, и другое.**
- У naive два порта: `tcp/443` и `udp/443` (`internal/provision/provision.go:478-484`; `internal/store/ports.go:38`).
  Оба уходят в снимок периметра как порты сервиса (`internal/api/perimeter.go:138-145`), и допуск SPA открывает адресу
  отправителя каждый порт сервиса из scope (`internal/perimeter/gate.go:555-564`; набор `allow4`, `firewall.go:193`,
  `:282-297`). Пакет на UDP 443 с допущенного адреса проходит.
- Порты слотов `slot−1`, `slot`, `slot+1` перенаправляются на 443 в prerouting, до проверки допуска (`gate.go:724-737`;
  `firewall.go:257`, `:689-705`): на вход они приходят уже как 443 и проходят по тому же допуску. Отдельного допуска на
  порт слота нет.
- Так и в спеке: «Сервис остаётся доступен и на своём обычном порту (443)» (spa-v2 §11); через relay UDP идёт только на
  443 (subscription-v1 §3, `profiles[].via`).

**Расписание публикуется в пакете регистрации устройства, не в подписке.**
- Расписание у naive есть: оно создаётся вместе с сервисом, если у сервиса есть UDP-порт (`provision.go:587-600`,
  `:1340-1356`), а naive по умолчанию создаётся с `udp/443`.
- `port_key`, `port_base`, `port_range` попадают в `services[]` пакета регистрации для любого сервиса с расписанием,
  naive в том числе (`internal/api/server.go:747-756`; `internal/node/node.go:139-147`; spa-v2 §8). Отдельной правки для
  naive не нужно.
- В подписке расписания нет (`internal/sub` его не выдаёт; subscription-v1 §4 отсылает к пакету регистрации). Пакет
  выдаётся один раз, при регистрации (`internal/api/server.go:695-713`, `internal/api/remote.go:314-322`): у устройства,
  зарегистрированного до появления сервиса naive, расписания naive нет.

**Что из этого следует.**
- Периметр и пакет регистрации менять не надо.
- Клиент берёт расписание naive из `services[]` своего пакета, как для Hysteria2. Нет его там — идёт на 443: порт открыт
  тем же допуском.
- `udp=1` нода ставит только сервису с UDP-портом: у naive, созданного с одним `tcp/443`, нет ни слушателя QUIC, ни
  расписания (`provision.go:1344-1356`).
- Открытым остаётся только удобство: устройству со старым пакетом расписание нового сервиса взять неоткуда, кроме новой
  регистрации. Это общее свойство пакета, у Hysteria2 так же; если его чинить — отдельным полем подписки, не здесь
  (§13).
- Порт слота против 443 — разница для смены порта NAT, §5.3.

### 9.4. Проба и откат

Рукопожатие QUIC ещё ничего не доказывает: по источникам из 17-naive-default §5 соединения к зарубежным хостингам
замирают после 15–20 КБ, а MTU пути бывает меньше 1200 байт данных UDP ([probe-v1](probe-v1.md) §6.1).

Как идёт клиент (§2.4):
1. На новой сети UDP идёт по UoT: первый пакет не ждёт ни рукопожатия QUIC, ни пробы.
2. В фоне клиент открывает QUIC и гонит эхо probe-v1 через запрос UDP. `hints.udp_blocked` и `hints.udp_mtu: "<1200"` из
   подписки (probe-v1 §6.2) пробу отменяют.
3. Эхо прошло — по потерям, порогу 15–20 КБ и размеру — новые сокеты приложений в этой сети открываются датаграммами;
   результат помнится по сети. Сокеты, уже открытые по UoT, доживают по UoT: адрес и порт ноды у них не меняются.
4. Откат по ответу (согласовано с клиентом 2026-11-16):
   - `429` и `503` закрывают только этот сокет: приложение откроет новый на следующем пакете, и он снова пробует
     датаграммы. Места у запросов UDP и потоков UoT общие (§7), так что UoT предел не обходит, а `503` — временный отказ.
     Но три `429`/`503` подряд в одной сети без принятого запроса между ними — отказ, как ниже: нода, которая отвечает
     `503` стабильно (нет исходящего UDP, кончились дескрипторы), иначе ломала бы каждый сокет приложения на первом
     ответе. Принятый запрос сбрасывает счёт, новая сеть считает заново.
   - Новые сокеты этой сети идут по UoT до смены сети, если пришёл ответ сайта (флаг выключен, старая нода), `NetError`
     (в том числе `-322`: нода без `SETTINGS_H3_DATAGRAM` или extended CONNECT), `ErrDatagramUnsupported` (libcronet без
     датаграмм), QUIC не поднялся или оборвался, или не прошла проба (решает приложение).

Что для этого делает нода:
- **Эхо тем же путём.** Датаграмма на имя замера (`probe.raycontrol.invalid`, порт сессии probe-v1 §4) уходит в эхо UDP
  эндпоинта подписки на loopback ноды. Так уже делает бэкенд Hysteria2 (`niko:nikoserver/hyudp.go:93-97`, `:146-152`); у
  naive сейчас имя замера работает только для TCP (`internal/naive/dial.go:27-36`). Эхо меряет потери в каждую сторону,
  RTT, порядок и размеры (probe-v1 §4) на том пути, которым пойдёт трафик: тот же QUIC, те же датаграммы, тот же
  обработчик.
- **Честный отказ.** `429` и ответ сайта отличимы от тайм-аута (§3.2).
- **Оба пути сразу.** UoT в HTTP/2 доступен всегда; запросы UDP и потоки UoT одного пользователя живут одновременно и
  делят один предел мест.

Следствие для ранних данных (§3.2): на новой сети они не нужны — первые пакеты идут по UoT; нужны второму и следующим
сокетам, которые открываются уже датаграммами.

### 9.5. 0-RTT, keepalive, смена сети

- **0-RTT выключен** (решение). Запрос, повторённый из ранних данных, заставил бы ноду повторить чужой UDP-пакет;
  выигрыш — один оборот при переподключении. Сейчас 0-RTT нет ни на ноде, ни у CONNECT в Chromium (§2.3).
- **Keepalive и батарея.** Пока открыт хоть один запрос UDP, клиент шлёт PING раз в 15 с; после закрытия последнего
  запроса сессия гаснет через 30 с (§2.3). Нода keepalive не шлёт. Сколько живёт молчащий запрос, решают тайм-ауты NAT
  клиента (§2.4): 10 с у DNS, 30 с у QUIC, до 2 минут у прочих (дальше закрывает нода). Клиент считает PING заметным для
  батареи; мерить на телефоне (§13).
- **Смена сети.** Приложение закрывает все соединения; запросы открываются заново после нового допуска SPA и новой
  пробы, порты ноды у сокетов приложений меняются — как сейчас с UoT.

## 10. Что видит наблюдатель: условие владельца к формату

Условие: формат не должен стать меткой для DPI. Ниже — что из этой схемы видно на пути, а что нет, и чем видимое
отличается от Chrome, который ходит на обычный сайт по HTTP/3. Захватов настоящего Chrome нет: всё о нём — по исходникам
(§14).

### 10.1. Чего на пути не видно

| Что | Почему не видно |
|---|---|
| extended CONNECT, `:protocol: connect-udp`, путь, `niko-udp`, `capsule-protocol`, пароль, `Padding` | заголовки запроса — в потоке HTTP/3, под ключами 1-RTT |
| `SETTINGS` обеих сторон, в том числе `SETTINGS_H3_DATAGRAM` | управляющий поток HTTP/3, под ключами 1-RTT |
| Context ID, адреса и имена назначений, данные UDP | внутри кадров DATAGRAM и капсул, под ключами 1-RTT |
| сам факт кадров DATAGRAM, их доля, отсутствие повторов | тип кадра и номер пакета зашифрованы: пакет с датаграммой снаружи не отличить от пакета с данными потока |
| параметры транспорта ноды, в том числе `max_datagram_frame_size = 16383` | идут в EncryptedExtensions, под ключами рукопожатия (RFC 9001 §8.2); их выводят из обмена ключами, наблюдателю они недоступны |

Параметры транспорта и `SETTINGS` ноды может прочесть только тот, кто сам завершил рукопожатие с верным SNI, — для этого
нужен допуск SPA. Ему нода и так видна как quic-go (Connection ID в 4 байта, набор параметров), а с флагом `udp`
добавятся две строки; объявляют ли датаграммы обычные сайты — не проверено.

Содержимое зашифровано, но длины пакетов — нет: с флагом `udp` пакеты ноды с этими строками длиннее на несколько байт
(замер на loopback, quic-go v0.64.1: пакет рукопожатия с параметрами транспорта — 686 → 689 байт, пакет с `SETTINGS` —
31 → 33, пакет с билетом сессии — 292 → 296; первый пакет, 1250 байт, тот же). Пассивный наблюдатель, сравнивающий
длины, может так отличить сервис с флагом от того же сервиса без него. От DoH3 на том же адресе naive-quic и так
отличает имя в SNI, которое видно в Initial (§10.2).

### 10.2. Что наблюдатель может прочесть: Initial клиента

Ключи пакетов Initial выводятся из Connection ID, который идёт открыто (RFC 9001 §5.2): любой на пути расшифрует
ClientHello и параметры транспорта клиента. Фронт ноды делает это сам (`niko:nikoserver/quic.go:15-18`, `:125-134`), и
фильтр, режущий QUIC по SNI, — тоже (17-naive-default §5).

Формат в Initial не меняет ни байта:
- `max_datagram_frame_size = 65536` Chrome шлёт каждому серверу: значение ставится в умолчаниях конфигурации и уходит в
  параметры транспорта без условий (`quiche:quic/core/quic_config.cc:1043-1058`, `:1226`; в `net/quic` его никто не
  переопределяет);
- поддержку датаграмм HTTP/3 Chrome объявляет каждому серверу (`quiche:quic/core/http/quic_spdy_session.cc:619-634`,
  `:2024-2026`) — но это `SETTINGS`, на пути их не видно в любом случае;
- `MTUH` стоял бы в `client_connection_options`: в параметры транспорта идут только `connection_options`
  (`quiche:quic/core/quic_config.cc:557-566`, `:1298-1300`); после §4.5 его нет вовсе;
- первый движок (TCP по HTTP/2) не меняется вовсе.

Отличается ли Initial второго движка от Initial Chrome 158 — вопрос ко всей сборке libcronet, не к этой схеме; его
закрывает сверка отпечатка клиента (17-naive-default §6.2), в которую входит и §4.5.

### 10.3. Что остаётся видно и отличается ли это от Chrome

| Что видно | Отличие от Chrome на обычном сайте по HTTP/3 |
|---|---|
| размеры пакетов | **да.** Вложенные протоколы видны размерами: пара пакетов около 1250 в начале вложенного QUIC, пакеты WireGuard, запросы DNS. Паддинга, как у первых кадров TCP-туннеля naive, у датаграмм нет |
| пакеты клиента длиннее 1250 байт | **нет.** `MTUH` снят (§4.5): клиент, как Chrome 157 и 159 с полевыми испытаниями, длиннее 1250 не шлёт |
| ритм | **да, для части трафика.** Ровный поток мелких пакетов в обе стороны при звонке; у просмотра сайта — всплески. PING раз в 15 с при открытом запросе — как у Chrome |
| соотношение направлений | **да, для части трафика.** Просмотр сайта — в основном вниз; звонок, игра, WireGuard дают близкие объёмы в обе стороны или больше вверх |
| соединение QUIC почти без потоков данных | **да, статистически.** Сам состав пакета не виден (§10.1), но нет рисунка «короткий запрос — большой ответ»; первые пакеты после рукопожатия — запрос и капсула, как запрос страницы у Chrome |
| два соединения к одному адресу: TCP с TLS и QUIC | **отчасти.** Порядок как у Chrome: сначала TCP, потом QUIC (Chrome узнаёт о HTTP/3 из ответа по HTTP/2). Но Chrome после этого переносит запросы на QUIC, и соединение TCP затихает, а у нас оба активны одновременно (по поведению Chromium с Alt-Svc; захватом не проверено) |
| длина Connection ID ноды (8 байт после §5.2) | не больше, чем сейчас: 4 байта — умолчание quic-go |
| смена порта клиентом | Chrome при плохом пути пробует новый порт (`sn:net/quic/quic_context.h:192`); сейчас проба до ноды не доходит (фронт её отбрасывает), с (г) дойдёт. Смены сети у нас нет: приложение закрывает соединения |

Итог: формат и рукопожатие датаграммы не выдают. Выдать может рисунок трафика — размеры, ритм, направления, два активных
соединения. Он не зависит от формата и был бы тем же при стандартном RFC 9298; у UoT размеры и ритм видны так же, через
записи TLS. Паддинг датаграмм — отдельная тема, в эту версию не входит.

### 10.4. При известных блокировках

По 17-naive-default §5:
- фильтр QUIC смотрит SNI в Initial: имя у QUIC то же, что у HTTP/2 этого сервиса, нового он не узнаёт; но остаточная
  блокировка четвёрки адресов на 420 с задела бы и переподключение QUIC;
- замирание после 15–20 КБ касается и UDP: поэтому проба (§9.4) обязана перейти этот порог, а не остановиться на
  рукопожатии;
- замедление за много параллельных TLS-соединений к одному адресу: к соединению HTTP/2 добавляется одно соединение QUIC
  — это не «много», но уже не одно; считает ли фильтр QUIC вместе с TLS, источники не говорят;
- где UDP или зарубежный хостинг режут целиком, датаграммы не открывают ничего сверх HTTP/2: остаётся UoT.

### 16.3. Отличия и как решены неясности

1. **Где заворачивается поток quic-go** (§7: «`*http3.Stream` … заворачивает `cmd/rayd`»). Обёртка — в `internal/h3serve`
   (`Datagrams`, `Stream`), а `cmd/rayd` лишь отдаёт её naive (`naiveH3`): так тесты naive служат через h3serve, как
   rayd, и не повторяют обёртку. `internal/naive` по-прежнему не импортирует quic-go: интерфейс `H3Stream` сверх двух
   методов датаграмм несёт содержимое потока (капсулы), сроки и два конца — чистый (`FIN`) и сброс; «не влезло» —
   булевым значением, а не ошибкой quic-go. Датаграммы запроса уходят не его вызовом quic-go, а через отправителя
   соединения (п. 16).
2. **Клиент без `SETTINGS_H3_DATAGRAM`.** В таблице §3.2 его нет; решено как «не HTTP/3»: ответ сайта, не `200`. Нода
   ждёт `SETTINGS` клиента не дольше 10 с (`h3serve.SettingsWait`), уже после пароля.
3. **Другой `:protocol`.** §3.3 требует только, чтобы он не давал `200` с `niko-udp: 1`. Сделано строже: extended
   CONNECT любого протокола, кроме `connect-udp`, получает ответ сайта и не становится TCP-туннелем (раньше
   авторизованный с портом в `:authority` по HTTP/3 им становился).
4. **`capsule-protocol: ?1` в запросе** нода не требует: в ответе он есть всегда, а формат регистрирует `niko-udp`.
5. **Пометка пары по правилу QUIC** (§4.4: «нода помечает и то, и другое»). Нода помечает пару по адресу — тому, что в
   датаграмме, или тому, в который разрешилось имя; пара клиента по имени покрыта этим адресом (имя у запроса
   разрешается в один адрес, пока его помнит запрос). Правило нода применяет в обе стороны: к своим капсулам и к
   капсулам клиента. Пометка ставится при создании пары и живёт, пока жива пара (30 с без ответа, 120 с после
   последнего пакета).
6. **100 мс у капсулы.** Возраст ответа считается с его прихода от назначения: отбрасывается капсула, которой к началу
   записи больше 100 мс; начатая пишется целиком: оборванная посередине сломала бы поток. В полной очереди капсул (32)
   уступает самая старая. Застрявшая запись (клиент не читает) в конце запроса получает секунду, затем поток
   сбрасывается.
7. **Предел 65 774 байт** — у капсулы любого типа: самая длинная законная датаграмма HTTP (Context ID в 8 байтах, тип
   адреса, длина и имя в 255 байт, порт, 65 507 байт данных); длиннее — сброс до чтения её содержимого. Данные длиннее
   65 507 байт от клиента (возможно с адресом IPv4 в капсуле) отбрасываются. Правило QUIC проверяется до создания
   пары: отброшенная им капсула пары не создаёт и токен нового назначения не тратит.
8. **Имя замера** ведёт в эхо эндпоинта подписки только на его порту (`-probe`, порт `sub.port`); любой другой порт —
   отказ, как непубличный адрес. Ответ эха приходит с источником `127.0.0.1:<порт>` (тип 4): §3.2 требует от ноды
   только адреса. Ответы Hysteria2 «от имени» здесь не повторены.
9. **Отказы и счётчики.** Новых видов отказов conn-limit нет: `429` считается как `udp`, вытеснение — как `evicted`.
   Счётчики процесса (запросы, отказы `429`/`503`, датаграммы в обе стороны, капсулы, отброшенные) — в строке сокета
   статистики naive (поле `udp`); rayd его не читает. В конце запроса — строка debug с числами и причинами
   отбрасывания (`bad`, `context`, `denied`, `limit`, `stranger`, `long`, `queue`, `quic`, `late`, `write`). `write` —
   запись к назначению не удалась: нет маршрута (IPv6 на ноде без него), отказ правил ядра. Каждая датаграмма клиента
   либо отправлена, либо отброшена по одной из причин: счёт сходится.
10. **`udp=1` и UDP-порт.** Юнит получает `-udp` при флаге всегда; `udp=1` в подписке — только при UDP-порте сервиса
    (`provision.NaiveUDPLink`); `rayctl service set` предупреждает, если порта нет.
11. **Отличие от DoH3 и видимость флага.** С флагом naive-quic отличается от DoH3 на том же адресе двумя строками
    (параметр транспорта и `SETTINGS_H3_DATAGRAM`), как и сказано в §7 и §10.1; DoH3 датаграммы не объявляет. Тест
    `TestQUICNamesDatagrams` держит, что больше ничего не отличается, а `TestQUICNamesAnswerAlike` — что запрос
    `connect-udp` без пароля получает тот же ответ, что от DoH3. Содержимое этих строк зашифровано, но длины пакетов с
    ними меняются на несколько байт (§10.1: +3, +2, +4): наблюдатель на пути, сравнивающий длины, видит, включён ли
    флаг. naive-quic от DoH3 и так отличает SNI. Поведение после рукопожатия эти строки тоже меняют: DoH3 закрывает
    соединение, приславшее кадр DATAGRAM (`FRAME_ENCODING_ERROR` quic-go, как на любой не согласованный кадр), а
    naive-quic с флагом закрывает с `H3_SETTINGS_ERROR` соединение, чьи `SETTINGS` объявляют датаграммы HTTP/3 без
    параметра транспорта (RFC 9297 §2.1.1). Ни то, ни другое не говорит зондирующему больше, чем сам параметр.
12. **Отправка одного запроса — по одной.** Датаграммы и капсулы клиента отправляет к назначению один отправитель за раз
    (имена запроса — как у потока UoT, одного читателя): резолв имени (до 5 с) задерживает и другой путь этого
    запроса, не другие запросы.
13. **Простой и фронт.** Простой запроса 2 минуты, QUIC — 2 минуты, фронт помнит поток 2 мин 30 с
    (`render.FrontUDPIdle`): фронт переживает оба. Пока открыт запрос, клиент шлёт PING раз в 15 с (§2.3).
14. **Память.** На запрос — очередь датаграмм к клиенту (32 по 1,4 КиБ) и очередь капсул (32 по 1,5 КиБ), вместе под
    100 КиБ, буфер чтения 4 КиБ и буфер длинной капсулы клиента (64 КиБ, из пула) на всё время её чтения. Чтение
    длится, сколько хочет клиент: заголовок капсулы и тишина держат буфер до простоя или вытеснения запроса — 256 ×
    64 КиБ = 16 МиБ на пользователя, как у потоков UoT (`uotBufs`). Кончившийся запрос не держит ничего: его очереди
    пустеют в конце, а отправитель соединения держит не больше одной датаграммы (п. 16).
15. **Датаграммы на чужих потоках** (§7, «Что видно до пароля»). quic-go копит до 32 датаграмм не только на потоке,
    который обработчик ещё не принял, а на любом потоке запроса, который их не читает, — туннеле TCP, потоке UoT или
    ICMP по HTTP/3 — всю его жизнь (`qg:http3/state_tracking_stream.go:136-146`; читать их или выключить приём для
    одного потока http3 не даёт без захвата потока). С флагом `udp` пользователь, который шлёт датаграммы на свои
    потоки, держит до 32 × ~1,4 КиБ на поток: при 1284 потоках пользователя (1024 TCP, 256 UDP, 4 ICMP) около 56 МиБ —
    того же порядка, что предел очередей UoT на пользователя (до 49,5 МиБ, `uot.go`). Без пароля — только потоки без
    заголовка, но и они: http3 заводит поток для датаграмм до того, как прочтён его заголовок (`TrackStream` в
    `HandleRequestStream`). 64 таких потока на соединение (`naive.PendingStreams`) × 32 × ~1,4 КиБ ≈ 2,8 МиБ на
    соединение, не дольше 10 с (затем соединение, полное ими, закрывается, и прошедший SPA открывает новое), против
    не больше 1 МиБ буферов заголовков (64 × 16 КиБ) без флага. Без флага датаграммы не принимаются вовсе.
16. **Отправитель датаграмм на соединение** (найдено ревью). `SendDatagram` quic-go ждёт, пока полна очередь соединения
    (32), а клиент, который шлёт пакеты, но ничего не подтверждает, держит её полной сколько угодно: каждый его пакет
    продлевает простой. Раньше каждый запрос отдавал свои ответы в quic-go сам, ждал там и переживал свой конец со всем,
    что держал, — около 100 КиБ на запрос, без предела. Теперь у соединения один отправитель (`h3serve`): запрос
    кладёт датаграмму в свою очередь (32, уступает старая, отброшенные считаются как `queue`) и не ждёт никогда;
    отправитель берёт из очередей запросов по одной датаграмме по кругу и один ждёт quic-go. «Не влезло» запрос узнаёт
    сразу, без копии: предел соединения постоянен (пакеты постоянного размера, поиска MTU нет), и отправитель узнаёт
    его один раз у самого quic-go — `SendDatagram` с заведомо длинной датаграммой отказывает с пределом, ничего не
    посылая; если предел всё же станет меньше, отправитель узнает его снова на первой датаграмме, которую quic-go не
    возьмёт. Учёт трафика и простой — когда датаграмма отдана quic-go. Сторожа нет: застрявший навсегда отправитель
    держит одну датаграмму и очереди ещё открытых запросов своего соединения, задерживает только датаграммы того же
    клиента, который их не подтверждает, и кончается вместе с соединением.
