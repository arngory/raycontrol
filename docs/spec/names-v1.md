# names-v1: клиент ходит к ноде по имени, адрес — запасной

Статус: **черновик 2026-11-19, сервер — в raycontrol v0.34.0**. Решение владельца 2026-11-19: трафик к ноде идёт по
нашему домену, как у браузера, — сначала разрешение имени, затем соединение с результатом, и SNI разрешается в тот же
адрес. Адрес ноды — запасной путь, а не правило. Клиентская сторона ответила 2026-11-19 (Niko, ядро 688d100): клиент
перейдёт в 1.62 или 1.63. Решения владельца и открытый вопрос — §9.

## 1. Зачем

Модель угроз владельца: на клиенте бывают поддельные сертификаты, DNS бывает подделан, сеть теряет пакеты. Клиент
изначально похож на браузер (или мессенджер, стриминг), он для своих, и порты ноды закрыты до стука.

До этой спецификации ссылки подписки и пакет устройства несли адрес из `rayctl install -host`. Клиент соединялся с голым
IP и SNI нашего домена, не разрешая имя. Так браузер не ходит:

- нет DNS-запроса перед соединением;
- через relay SNI разрешается не в тот адрес, на который идёт соединение (§7).

От подмены узла защищают пины: niko-pin, `sub_pin`, `pbk` у REALITY. Подделанный DNS поэтому даёт только недоступность,
и её закрывает запасной адрес. Довод «не разрешать имя в сети клиента» (коммит 8355e8c) против этой модели угроз не
держится.

## 2. Имена

- **Имя сервиса** — его `sni`: REALITY с self-steal, naive (текущее и `sni_next`), hy2-masq, DoH, Yggdrasil. Клиент
  соединяется по имени, которое кладёт в SNI.
- **Имя ноды** (`dns_name`; не путать с `name` подписки — отображаемым именем «Amsterdam») — `<метка>.<домен>`.
  Метка случайная, как у сервисов, и не совпадает с именами сервисов и зон. Имя не меняется, пока у ноды тот же
  домен; откат обновления (`rayctl update -rollback` с переносом, как по умолчанию) его сохраняет. Нода заводит его сама, при первом обращении после
  обновления, если у неё есть домен (`-domain`) и `-host` — адрес. По нему идут:
  - стук, подписка, удалённый API и замер (probe-v1);
  - сервисы, у которых своего имени нет: hy2-obfs (`sni` вида `<hex>.invalid`) и REALITY с чужой целью.
- **DNS.** Имя ноды и имена сервисов — метки на одном уровне под доменом. Их покрывает запись `*.<домен>` (A или AAAA в
  семействе адреса ноды), которую нода ведёт в Cloudflare без проксирования. Без Cloudflare эту запись заводит
  администратор: её показывает `rayctl dns`. Новую зону DNS-туннеля нода не примет под именем, которое клиенты
  разрешают через `*.<домен>`: имя ноды и имя сервиса на метку под доменом (у REALITY — только с self-steal).
  Делегирование делает такое имя узлом без своих записей, и `*.<домен>` на него больше не отвечает (RFC 4592). Зону,
  заведённую раньше, нода оставляет, а `rayctl dns` называет проблемой, если это имя ноды или включённого сервиса.
- **Адреса** (`addrs`) — адреса ноды, которые клиент берёт, если имя не разрешилось: сейчас это `-host`, если это адрес.
- **`-host` — имя** (так можно и сейчас, без Cloudflare и через `rayd init -host`): у ноды нет ни `addrs`, ни своего
  имени, а клиенты ходят по `-host`, как раньше. Без адреса клиенту некуда отступить и не с чем сверить ответ DNS
  (§5 п. 5).

## 3. Пакет устройства (`rcdev1`, spa-v2 §8)

Новые поля, только добавление; клиент без поддержки их не читает:

| Поле | Что |
|---|---|
| `dns_name` | имя ноды (§2) |
| `addrs` | адреса ноды (§2) |

`host` остаётся прежним (то, что задано в `-host`), поэтому старые клиенты не меняют поведения. `dns_name` приходит
только вместе с `addrs`. Приглашения (`rcinv1`, `rcinv2`) не
меняются: первое обращение при регистрации идёт по `host` приглашения, а пакет, который возвращает `Register`, уже
несёт `dns_name` и `addrs`.

## 4. Подписка (subscription-v1 §4)

- **Клиент заявляет поддержку** заголовком `X-Raycontrol-Features: names` в запросе подписки (список через запятую;
  незнакомые слова нода пропускает). Номер версии клиента для этого не нужен: нода с этой спецификацией отвечает любой
  версии, которая заявила поддержку.
- **Клиенту, который заявил поддержку** (у ноды, где `-host` — имя, ссылки для всех как раньше, без `niko-ip`):
  - хост ссылки — имя, по которому соединяться (§2): `sni` сервиса, если это метка под доменом ноды и имя наше (у
    REALITY — только с self-steal), иначе имя ноды, а без него — адрес;
  - параметр `niko-ip=<адрес>[,<адрес>…]` — адреса ноды, IPv4 и IPv6 через запятую, IPv6 без скобок;
  - порт, `sni` и прочие параметры — как раньше.

  Так ведут себя `vless://` (REALITY), `hysteria2://`, `naive+https://` и их `next`, а также `niko-ygg=tls://<имя>:443`
  у Yggdrasil. DoH уже по имени (`https://<sni>/dns-query/…`), у него добавляется только `niko-ip`.
- **В полезной нагрузке подписки** появились `dns_name` и `addrs` (§2). Подписка подписана, поэтому это доверенный
  источник адресов для правила стука (§5).
- **Клиенту, который поддержку не заявил**, — ссылки как раньше, хост = адрес. Причина в том, что старые Niko примут
  имя, но не прочтут `niko-ip`: в сети, где имя не разрешается или подменено, они перестали бы подключаться там, где
  по адресу работали.

## 5. Поведение клиента

1. **Один резолв на попытку.** Клиент разрешает имя один раз (A/AAAA по своей стратегии), шлёт стук и соединяется
   на этот же адрес. Два независимых разрешения с round-robin могут дать разные адреса: стук на один, соединение на
   другой.
2. **Резолвер** — тот, что настроен для прямого трафика (у Niko — «Прямой DNS»; можно задать свой, например DoH).
3. **Сроки:**
   - разрешение не дольше 3 с;
   - пустой ответ, ошибка или таймаут → адреса из `niko-ip` (или `addrs` пакета);
   - соединение на адрес не удалось за 5 с → следующий адрес, если он другой.
4. **Последний удачный адрес** клиент помнит для каждой сети и пробует его, если разрешение не удалось. Вместо
   разрешения его не берёт: иначе клиент не пойдёт за сменой записи DNS.
5. **Стук только на известный адрес** — пока нода не объявила spa-v3 (`spa.versions` с `3`, v0.35.0). С v3 правило
   снимается: стук идёт на любой адрес из DNS, а пойманный на чужом адресе на ноде не проходит ([spa-v3](spa-v3.md)
   §6). Ниже — правило для v2. Адрес, полученный из DNS, клиент использует для стука,
   только если он есть среди адресов ноды из подписанных данных: `addrs` пакета и последней подписки, `niko-ip`. Иначе
   клиент считает ответ DNS подозрительным и стучится на известные адреса. Где есть `dns_name`, там есть и `addrs`.

   Почему: стук spa-v2 не привязан ни к адресу источника, ни к адресу ноды (§9 spa-v2). Тот, кто подделал DNS и
   получил стук, может за 30 с повторить его на настоящую ноду со своего адреса и открыть себе её порты. Повтор после
   того, как стук уже принят нодой, она отвергает (кэш на 60 с).

   Как переехать на новый адрес. Нода публикует его в `addrs` подписки заранее, до переезда, а клиенты, которые видели
   подписку, принимают его из DNS. Если переезд не запланирован, нужны новые пакеты устройств — как и до этой
   спецификации.
6. **SNI** — прежний `sni` ссылки. Носитель стука `tls` (spa-v2 §10.1) кладёт в ClientHello server_name = имя, которое
   клиент разрешал (хост ссылки или `dns_name` пакета). ClientHello с server_name принимает любая нода с носителем
   `tls`: парсер с первой версии пропускает все расширения, кроме session_ticket. Версию ноды проверять не нужно.
7. **Подписка, API, замер** — по `dns_name` пакета, по тем же правилам; SNI = `dns_name`. Эндпоинты ноды отдают один
   сертификат на любой SNI и проверяются пином, а не именем.

## 6. Нода

- **Имя ноды** хранится в настройке `node_dns_name` и создаётся при первом обращении (§2). Оно попадает в пакет
  устройства (при регистрации и при создании устройства на ноде) и в подписку (`dns_name`). Сменился домен —
  нода заводит новое имя под ним; пакеты со старым именем клиент разрешить не сможет и пойдёт на `addrs`.
- **`-host` должен быть адресом, когда записи ведёт нода.** Запись `*.<домен>` не может указывать на имя, а до
  v0.34.0 имя в `-host` при синхронизации удаляло её.
  - `rayctl install -host <имя> -cloudflare-token-file …` отказывает с объяснением.
  - На ноде, где в `-host` уже имя, синхронизация зону не трогает, а `rayctl dns` показывает проблему (и метрика
    `raycontrol_dns_problems`).
- **`rayctl` как клиент** (`knock`, `probe`, `remote`, `-remote`) ходит по `dns_name` пакета, если пакет его несёт, по
  п. 1 и 5 §5: одно разрешение на попытку, стук только на известный адрес. С spa-v3 адрес выбирается так же, стук
  идёт v3, а v2 — только на известный адрес (spa-v3 §6). Следующего адреса после 5 с и последнего
  удачного адреса у него нет. Носитель стука `tls` и TLS к подписке и API — с SNI = `dns_name`. `-addr` по-прежнему
  задаёт адрес вручную.

## 7. Relay

Через relay клиент заменяет хост ссылки адресом relay, а SNI остаётся именем выхода: SNI не разрешается в адрес, на
который идёт соединение. В v0.34.0 это не меняется; решение — §9 п. 2, в v0.35.0. Ограничения любого варианта:

- TLS сквозной до выхода, поэтому SNI через relay должен быть именем, которое выход доказывает:
  - для naive — есть в SAN его сертификата;
  - для REALITY — есть в его `serverNames`;
  - фронт выхода направляет его в нужный сервис.
- Имя relay поэтому — своё на каждый сервис выхода, и оно разрешается в адрес relay. HTTP-01 для имени, которое
  указывает на relay, проходит, только если relay пропускает порт 80 к выходу; иначе такие имена покрывает лишь
  wildcard-сертификат выхода (Cloudflare).
- Дописать адрес relay в A-записи имён выхода нельзя: любой, кто разрешает наше имя, увидит relay.

## 8. Совместимость

- **Старый клиент, новая нода:** пакет и ссылки как раньше, поля `dns_name` и `addrs` он не читает.
- **Новый клиент, старая нода:** `dns_name` нет, клиент ходит по `host`, как раньше.
- **DNS-туннели** этой спецификацией не затронуты: они и так работают по именам.
- **Откат ноды до v0.33** убирает `dns_name` из новых пакетов. Клиенты с пакетом, где `dns_name` есть, продолжают
  ходить по имени: запись `*.<домен>` указывает на ту же ноду. Откат базы с переносом (по умолчанию) сохраняет имя, и
  следующее обновление возвращает то же. Без переноса (`-no-carry`) и после восстановления из копии, сделанной до
  v0.34.0, нода заведёт новое, а пакеты со старым пойдут на `addrs`.

## 9. Решения владельца

Решено 2026-11-19; всё новое ниже — в raycontrol v0.35.0, вместе с клиентом. v0.34.0 выходит с тем, что описано выше.

1. **Стук привязать к адресу ноды** — сделано: [spa-v3](spa-v3.md). Клиент стучится на любой адрес из DNS, а риск повтора закрывает новая версия
   стука (spa-v3): адрес, на который клиент шлёт стук, входит в подписанную часть пакета, и нода принимает стук,
   только если это один из её адресов. Стук, перехваченный на чужом адресе, на ноде не пройдёт. Это меняет протокол
   обеих сторон; до spa-v3 у обеих — правило §5 п. 5.
2. **Relay по имени:** своё имя на каждую пару «relay × сервис», оно разрешается в адрес relay (§7). TLS сквозной до
   выхода, поэтому имя должно быть в сертификате выхода:
   - с Cloudflare его покрывает wildcard-сертификат выхода, а в журналах CT видно только `*.<домен>`;
   - без Cloudflare relay пропускает порт 80 к выходу, и выход получает сертификат на каждое такое имя по HTTP-01.
     Каждое имя relay тогда попадает в публичные журналы CT, и по домену можно найти адреса relay; владелец это
     принимает.
3. **Приглашения по имени** — черновик: `RCINV3:` (api-v1 §3b). Приглашение несёт имя ноды и её адреса. Это новая раскладка: читатель `rcinv2` отказывает
   на незнакомом бите флагов и на лишних байтах, поэтому её согласуем с клиентом. Пока первое обращение одно, и идёт
   оно по `host`.
