# dnszones-v1: запасные зоны DNS-туннелей

Статус: согласовано с клиентом (2026-11-06, `handoff/SYNC.md`), для raycontrol v0.14.0 и niko-server v0.11.0. Сторона
ноды (§4, §5) сделана; клиент — после interop печати и dnsauth masterdns.

## 1. Зачем

Против блокировки по известной зоне маскировка не помогает. Фильтр по суффиксу имени у резолвера или DPI отрезает
туннель целиком, что бы ни лежало в метках. Новая зона сегодня — это новая подписка, а до неё клиенту ещё нужно
дотянуться. Запасные зоны делегируются заранее и приходят в той же ссылке, так что клиент переключается сам.

## 2. Ссылка

У строки `dnstt` или `masterdns` (subscription-v1 §4) — новый параметр:

```
niko-dns-spare=<зона>,<зона>,…      порядок — порядок перебора; до 4 зон
```

- Основная зона по-прежнему в `niko-dns`.
- Запасные зоны того же сервиса делят с основной всё: ключ (pubkey dnstt, `niko-dnskey` masterdns), печать
  (`niko-dnsseal`, `niko-mdseal`), метку dnsauth (ключ выводится из ID сервиса, а не из зоны) и ключ пробы
  dnsprobe-v1. Меняется только суффикс имени.
- Старый клиент параметр не знает и работает с основной зоной, как раньше (строгий разбор Niko 1.26 неизвестные
  параметры не отвергает).
- Клиент отбрасывает зону, которая не проходит той же проверки имени, что основная, и дубль основной; пятую и дальше
  молча пропускает.

## 3. Клиент

Критерий «не работает» и память — у клиента; спека задаёт провод и то, что видит нода. Как делает клиент:

- **dnstt.** Зона «не работает», если малая проба dnsprobe-v1 не прошла ни через один кандидат-резолвер сети, а их не
  меньше двух. Тогда та же проба по запасным, по порядку. Выбор (зона, резолвер) помнится по сети там же, где выбор
  резолвера, на сутки; потом снова основная — блокировки бывают временными. Отдельного запроса SOA нет: проба и так
  отличает «зона молчит» от «резолвер молчит», а лишний запрос — лишняя примета. Смена зоны — новая сессия с новым
  ClientID.
- **masterdns.** Зону выбирает приложение по сети, как у dnstt; в `DOMAINS` — одна зона. Запасные — только когда
  основная в этой сети не работает: зоны, которые гоняют вместе, видны любому, кто смотрит трафик, и их режут вместе
  с основной. Пробы в зонах masterdns нет (ответ в форме dnstt был бы там приметой), сигнал — отказ самого туннеля:
  watchdog видит, что профиль не работает в этой сети, обновление подписки не помогло — берётся следующая зона,
  запоминается по сети на сутки, туннель перезапускается. Из-за одного плохого резолвера основная не уходит.
- **Сводка** (probe-v1 §6): `obs[].zone` — номер работающей зоны в `[основная, запасные…]`, 0 — основная; только у dnstt
  и только когда выбор известен (у masterdns зона общая для балансира). Имена в сводку не идут. Нода принимает поле,
  если `dns_zone` есть в `probe.report`.

## 4. Нода

- **Сервис:** `zone` — основная зона, `spare_zones` — запасные. Список, до 4 зон; все — имена DNS.
- **DNSRecords:** NS-делегирование для каждой зоны на то же имя NS. Синхронизация с Cloudflare заводит записи для всех
  зон.
- **Фронт:** запись `dns.zones[]` на каждую зону. Бэкенд, `probe`, `ns` и `seal_pad` у них общие с основной.
- **dnstt** принимает список зон: опция `zones` у бэкенда (niko-server v0.11.0) в дополнение к `zone`. Запрос в
  любую из зон — тот же туннель.
- **masterdns** уже принимает список (`DOMAIN`).
- **Самопроверка** (`rayctl dns check`) проверяет все зоны: делегирование, фронт, резолверы. В `rayctl status` основная
  зона — цикл `dns-zone <сервис>`, как раньше, запасная — `dns-zone <сервис> <зона>`.
- **Счётчики** (niko-server v0.11.0): с самой ноды, без отчётов клиентов, видно, до какой зоны доходят клиенты, — по
  запросам dnstt с верной меткой dnsauth по каждой зоне (`zones` в `stats_socket` бэкенда): подделать их без ключа
  устройства нельзя. Запросы фронта по зонам (`dns.stats_socket`) — только нагрузка: имя зоны на UDP 53 может
  прислать кто угодно.
- **Зоны не вкладываются** одна в другую и не совпадают — ни у одного сервиса, ни между сервисами, ни с именем, на
  которое делегированы: имя под обеими было бы любой из них (niko-server v0.11.0 такой конфиг не примет).

## 5. Ротация

```
rayctl service set <svc> spare_zones=2         две случайные запасные зоны в домене ноды (как основная)
rayctl service set <svc> spare_zones=a.ex.com,b.ex.com   свои
rayctl service set <svc> zone=<запасная>      запасная становится основной; прежняя основная уходит из сервиса
```

- `spare_zones=N` оставляет уже заданные запасные (первые N) и добавляет недостающие; `none` убирает все.
- `zone=` принимает только запасную зону: основной может стать лишь зона, которая у клиентов уже есть.
- Смена основной не рвёт клиентов: у них прежняя основная пропадает из ссылки только со следующей подпиской, а новая
  основная у них уже есть как запасная.
- Удалённую зону нода больше не делегирует; записи в Cloudflare удаляются синхронизацией. Свою делегацию оператор
  убирает сам.

## 6. Что видно снаружи

Запасные зоны видны в DNS: NS-записи у родительской зоны, и, если домен один, они рядом с основной. Блокировщик,
нашедший основную зону, может перечислить зоны домена и заблокировать запасные заранее. Разносить запасные зоны по
разным доменам — дело оператора: `spare_zones=` со своими именами. Для своих доменов с Cloudflare нода заводит
записи, если токен покрывает эти зоны.
