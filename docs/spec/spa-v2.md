# raycontrol SPA v2

Статус: **заморожен** (R0); §10 (TCP-носитель) и поля `node_keys`, `sub` добавлены в R1 без изменения формата пакета. Изменение формата = новая версия (`Version` в пакете и префикс пакета регистрации).
Эталонная реализация — [`internal/spa`](../../internal/spa); тестовые векторы —
[`internal/spa/testdata/vectors.json`](../../internal/spa/testdata/vectors.json). Векторы проверены второй,
независимой реализацией (Python + libsodium).

**v3** ([`spa-v3.md`](spa-v3.md), raycontrol v0.35.0): тот же пакет с адресом назначения внутри; нода принимает обе
версии и объявляет их полем `versions` (`spa.versions` пакета регистрации и подписки).

Все порты ноды закрыты. Клиент отправляет один UDP-пакет на порт SPA текущего слота; если пакет подлинный,
адрес отправителя получает доступ к разрешённым портам на время TTL. Сервер никогда не отвечает на SPA-пакеты.

## 1. Параметры ноды

Выбираются случайно при установке (`rayd init`) и не меняются. Клиент получает их в пакете регистрации (§6).

| Поле | Тип | Диапазон при установке | Смысл |
|---|---|---|---|
| `node_id` | 16 байт | случайные | идентификатор ноды, соль HKDF, часть AAD |
| `epoch_len_s` | целое, секунды | 6–24 ч, кратно минуте | период смены ключа устройства |
| `slot_len_s` | целое, секунды | 5–30 мин, кратно минуте | период смены порта |
| `port_key` | 32 байта | случайные | ключ расписания портов (общий для всех устройств ноды) |
| `port_base` | uint16 | 20000 … 60999 − range | начало диапазона портов SPA |
| `port_range` | uint16 | 1024–4096 | размер диапазона |
| `len_min`, `len_max` | целые | `len_min` ∈ [85, 160], `len_max` = `len_min` + [32, 128], ≤ 512 | допустимая длина пакета |

## 2. Время, эпоха, слот

`t` — unix-время в секундах (UTC).

```
epoch = floor(t / epoch_len_s)
slot  = floor(t / slot_len_s)
```

## 3. Порт

```
port(slot) = port_base + (BE64(HMAC-SHA256(port_key, "raycontrol-spa-v2 port" ‖ BE64(slot))[0:8]) mod port_range)
```

`BE64` — 8 байт big-endian. Сервер держит открытыми порты слотов `slot−1`, `slot`, `slot+1`.
Диапазон `port_base` пересекается с эфемерными портами ядра (32768–60999): `rayctl apply` резервирует его (`net.ipv4.ip_local_reserved_ports`, `/etc/sysctl.d/90-raycontrol-ports.conf`), иначе исходящее соединение ноды занимает порт слота и TCP-носитель на нём не слушает.
Клиент шлёт на порт **текущего** слота по своим часам.

## 4. Ключ эпохи

У каждого устройства мастер-ключ `device_key` (32 байта, выдаётся при регистрации).

```
epoch_key = HKDF-SHA256(ikm = device_key, salt = node_id, info = "raycontrol-spa-v2 key" ‖ BE64(epoch), L = 32)
```

HKDF — RFC 5869 (extract + expand).

## 5. Пакет

Один UDP-датаграм длиной `L`, где `len_min ≤ L ≤ len_max`; клиент выбирает `L` случайно и равномерно.

```
packet     = nonce ‖ ciphertext
nonce      = 24 случайных байта
ciphertext = XChaCha20-Poly1305-Seal(key = epoch_key, nonce, plaintext, aad = "raycontrol-spa-v2" ‖ node_id)
```

`plaintext` длиной `L − 24 − 16`:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | версия = `0x02` |
| 1 | 8 | время отправки, unix-секунды, BE |
| 9 | 2 | запрошенный TTL в секундах, BE; 0 = значение сервера по умолчанию |
| 11 | 1 | флаги, должны быть 0 |
| 12 | 1 | `n` — число сервисов в scope, 0–16; 0 = все разрешённые устройству |
| 13 | 2·n | ID сервисов, uint16 BE |
| 13 + 2·n | остаток | нули (padding; после шифрования неотличим от случайного) |

Эпоха, по которой выбран `epoch_key`, должна совпадать с эпохой поля «время».
Весь пакет неотличим от случайных байтов: постоянных полей и фиксированной длины нет.

## 6. Проверка на сервере

1. Пакет пришёл на один из открытых портов SPA; длина в `[len_min, len_max]`. Ограничение частоты выполняется до
   криптографии, в nftables: на адрес IPv4 и на IPv6 /64 — 20 пакетов в секунду, всплеск 40; у SYN TCP-носителя
   (§10) свои наборы с тем же пределом. Отброшенное считают счётчики `spa-rate` и `spa-syn-rate`.

   Ни общего потолка, ни потолка на IPv6 /48 в nftables нет: SYN и датаграммы с подменённых адресов заняли бы его
   даром для атакующего и закрыли бы стук всем (или всей сети /48). Набор источников — 65 536 мест на минуту: около
   1100 новых источников в секунду держат его полным (одна /48 — это 65 536 /64). Тогда предел для новых источников
   не срабатывает, и держат бюджеты ниже (S-8).

   `rayspa` проверяет пакеты в пределах бюджетов, по оценке 2 мкс на устройство за пакет (3 эпохи, пакет в 288 байт —
   самый большой `len_max`, что выбирает `rayd`; Xeon 2,1 ГГц). `len_max` до 512, заданный вручную, стоит 2,6–2,9 мкс,
   и бюджеты тогда дороже своих долей. Все проверки идут под одной блокировкой, а UDP
   читает один поток. Поэтому вместе бюджеты оставляют ядру больше половины времени:
   - пакеты источников без допуска — 150 мс в секунду, не меньше 1 пакета в секунду (на ноде больше 75 000
     устройств бюджет поэтому дороже своей доли);
   - стуки TCP-носителя — столько же, отдельно;
   - источник с допуском — адрес IPv4 или IPv6 /64, с которого устройство держит допуск (п. 9). Его пакет сначала
     проверяется только против устройств, что держат с него допуски (не больше 32), вне двух бюджетов выше: на все
     такие источники — 100 мс в секунду, каждое проверенное устройство — одна проверка из этих 100 мс; на один
     источник — 8 пакетов в секунду. Кто подделывает источник клиента, тратит долю только этого источника. Пакет,
     который ни одно из этих устройств не открыло, идёт в бюджет своего вида. За одним источником больше 32
     устройств (большой офис за одним адресом): пакет проверяется против 32 из них, остальные продлевают допуск
     через бюджет своего вида — во время заливки не всегда.

   Длину и повтор `nonce` (п. 2) `rayspa` проверяет до бюджетов, даром. Сверх бюджета пакет не проверяется
   (`ErrFlood`).
2. Если `nonce` уже принят и не истёк — отбросить.
3. Для эпох `e`, `e−1`, `e+1` (по часам сервера) и каждого активного устройства — попытка `Open`. Первая удачная
   определяет устройство.
4. Версия `0x02`, флаги 0, `n ≤ 16`, scope помещается в plaintext; эпоха времени пакета совпадает с эпохой ключа.
5. `|now − время| ≤ 30 с`.
6. Запомнить `nonce` (срок — ниже). От одного устройства за минуту принимают не больше 256 `nonce`, прошли пакеты
   дальше или нет (отказ по scope или адресу назначения тоже считается): сверх этого откажут только ему, и кэш
   останется другим. Если кэш полон и в нём нет истёкших записей — отказать (а не вытеснять). Пакет со временем не
   позже времени уже забытого пакета — отказать как повтор (ниже).
7. Scope = запрошенные ∩ разрешённые устройству (пустой запрос = все разрешённые). Пусто — отказать.
8. TTL = запрошенный или значение по умолчанию (10 мин), не больше максимума ноды (1 ч) и не меньше секунды:
   элемент nft без таймаута (0) остался бы навсегда, и отзыв бы его не закрыл. `rayd` не запускается с
   `-spa-ttl` или `-spa-max-ttl` меньше секунды.
9. Добавить адрес-источник (IPv4 или IPv6, после NAT) в allow-наборы портов из scope на TTL. Ответ не отправлять.
   Все порты стука — одной транзакцией nft, у каждого элемента свой таймаут: допуск длится, сколько его самый
   долгий держатель, и более короткий стук другого устройства с того же адреса (CGNAT) его не укорачивает. Свой
   более короткий стук устройство делает само. Замена элемента ждёт ядра (~20 мс под блокировкой; добавление нового
   — ~3 мс с `destroy element`, ~20 мс без него: nft до 1.0.8, ядро до 6.3), одна транзакция ждёт один раз, сколько
   бы элементов в ней ни было.

   Порт, чей конец стук сдвинул бы меньше чем на `min(30 с, TTL/2)` вперёд или не сдвинул бы вовсе, остаётся как
   есть: таблицу такой стук не трогает. Устройство держит этот порт до конца своего TTL, но не дольше элемента, а
   элемент длится не меньше TTL − `min(30 с, TTL/2)` от стука. Повтор стука, стук под более долгим допуском другого
   устройства (и с нового для устройства адреса) и продление чаще, чем раз в 30 с, обходятся без nft. Порт, чьё
   укорачивание или закрытие ещё ждёт (отказ nft), стук пишет заново, каким бы ни был его конец.

   Одно устройство держит допуски не больше чем с 32 адресов сразу; допуск с нового адреса сверх этого закрывает тот,
   что кончается первым (у другого устройства с того же адреса он остаётся). Не отказ: адрес источника стука не
   доказательство, и тот, кто пересылает стуки устройства со своих адресов (§9), не должен его запереть.

   Стук меняет таблицу, если пишет в неё хоть один порт (новый допуск, допуск, что растёт или укорачивается, порт,
   чьё изменение ждёт) или вытесняет адрес. Таких стуков у устройства — не больше 32 в минуту и 32 сразу, иначе отказ
   (`ErrChanges`). Устройство, что так часто меняет допуски, — не телефон в новой сети, а пересылка его стуков или
   утёкшее приглашение. Закрытия и укорачивания, что просит вытеснение, идут в транзакции самого стука: один стук —
   одна транзакция, одно изменение. Отказ nft на них не держит стук: тогда его порты пишутся отдельно, а
   вытеснение ждёт повтора. Отзывы и укорачивания из снимка — одной транзакцией на все. Отказ nft вне снимка
   повторяется всё реже (1 с, удваиваясь до 30 с), первый в серии — в журнал на уровне warn; удача любого сброса
   серию заканчивает.

Отказ по квоте устройства (п. 6) и по изменениям таблицы (п. 9) `rayspa` пишет в журнал на уровне warn, раз в минуту
на устройство, с ID устройства, но не с его адресом: так виден утёкший пакет или приглашение. Заливку (п. 1), полный
кэш (п. 6) и отказы по шагу часов назад (ниже) — тоже раз в минуту. Ошибки nft уходят в журнал без адресов: nft
повторяет в них отвергнутую команду.

Кэш `nonce` (п. 6) держит запись, пока пакет с ней мог бы пройти проверку времени, и по обоим часам: минуту с
небольшим по монотонным часам и до времени пакета плюс 31 с (30 с и секунда на округление) по настенным, которые
читает проверка времени (п. 5).
Одних настенных мало: при их шаге вперёд запись ушла бы, а после шага назад пакет снова прошёл бы п. 5. Одних
монотонных тоже: после шага настенных назад пакет проходит п. 5 и спустя минуту. Квота устройства (п. 6) — та же
минута по монотонным часам: шаг настенных её не занимает и не освобождает.

Если настенные часы отступят уже после того, как запись забыта, её пакет снова прошёл бы п. 5. Поэтому нода помнит
время самого позднего забытого пакета и отказывает пакетам со временем не позже него. С часами, которые не
отступают, это не срабатывает никогда. Отметка одна на все устройства: после шага назад на Δ пакет, датированный на
s секунд от часов ноды, получает отказ около Δ − 31 − s секунд, но не дольше Δ − 1 с. Отметку ставит клиент, что
спешит больше всех: если он спешит на 30 с, уже после шага назад на 2 с отказ ненадолго получают пакеты клиентов,
что отстают на 30 с, а его собственные — только после шага от 62 с. Новый верификатор (смена параметров SPA) и перезапуск `rayspa` начинают с пустым кэшем;
смена TTL кэш оставляет. После перезапуска
источники с допуском, пока не постучат снова, проверяются как источники без допуска.

Устройство активно, если оно не отозвано, его пользователь включён и не истёк, а сервис включён.

## 7. Поведение клиента

- Перед подключением, если действующего доступа нет: отправить SPA, выждать 150–400 мс (случайно), подключаться.
- Продлевать доступ до истечения TTL независимо от моментов подключения, со случайным смещением, чтобы связка
  «SPA → сразу соединение» не была постоянной, и не позже чем за `min(30 с, TTL/2)` до конца, отсчитанного от
  последнего стука: стук, что продлил бы допуск меньше чем на столько, таблицу не меняет, и допуск длится не меньше
  TTL − `min(30 с, TTL/2)` от него (§6 п. 9). С TTL меньше ~4 с продление каждую секунду пишет в таблицу каждым
  стуком и упирается в бюджет изменений (32 в минуту, §6 п. 9): такой короткий TTL продлевать реже или не брать.
- После смены сети (Wi-Fi ↔ мобильная) — новый SPA сразу: адрес изменился.
- При неудачном подключении — один повтор SPA (порт мог смениться на границе слота); если и он не помог —
  TCP-носитель (§10).
- Часы: допустимое расхождение ±30 с; при большем клиент должен сообщить пользователю о неверном времени.

## 8. Пакет регистрации устройства

`rayctl device add USER NAME` печатает строку один раз:

```
rcdev1:<base64url без '=' от JSON>
```

```json
{
  "v": 1,
  "host": "203.0.113.7",
  "spa": {
    "node_id": "<32 hex>", "epoch_len_s": 34380, "slot_len_s": 1620,
    "port_key": "<64 hex>", "port_base": 21907, "port_range": 2955,
    "len_min": 136, "len_max": 206
  },
  "device_id": "<16 hex>",
  "device_key": "<64 hex>",
  "services": [{"id": 1, "kind": "reality", "name": "reality"}, {"id": 2, "kind": "dnstt", "name": "dns"}]
}
```

У сервиса с ротацией UDP-порта (§11) в `services[]` есть ещё `port_key` (64 hex), `port_base`, `port_range`.

Необязательное поле `sub` — эндпоинт подписки ([`subscription-v1.md`](subscription-v1.md)):
`{"port": <tcp>, "pin": "<base64url SHA-256 SPKI>"}`.

Необязательное поле `node_keys` — публичные ключи ноды для проверки подписи подписки:
`{"ed25519": "<64 hex>", "mldsa65": "<base64url>"}`. Клиент, который его не знает, игнорирует поле;
остальные поля и версия `v` не меняются.

Необязательное поле `api` — удалённый API ([`api-v1.md`](api-v1.md)): `{"port": <tcp>, "pin": "<base64url SHA-256 SPKI>"}`,
только у устройств-администраторов и интеграций, зарегистрированных через API; сервис `api` тогда есть и в `services[]`.

Необязательное поле `spa.versions` — версии SPA, которые нода принимает ([spa-v3](spa-v3.md) §5), с raycontrol v0.35.0:
`[2, 3]`, если стук v3 к ноде пройдёт (условия — там же). Нет поля — `[2]`. У приглашений (`rcinv1:`, `rcinv2:`) его нет.

Необязательное поле `role` — роль устройства, кроме `user`: `"admin"`, `"billing"`, `"support"`
([integrations-v1](integrations-v1.md) §2.1). У пакета пользователя поля нет, как до него. Приложение отказывает
пакету с ролью `billing` или `support`: это устройство внешней системы, у него нет ни подписки, ни сервисов данных.

Строка содержит секрет устройства: передаётся только по доверенному каналу (QR с экрана администратора, личная передача).
С R3 есть второй путь: одноразовое приглашение `rcinv1:` того же формата (с полями `api` и `expires`), по которому
клиент сам получает пакет через API по каналу с `X25519MLKEM768` ([`api-v1.md`](api-v1.md) §3–4).

## 9. Безопасность

- Симметричные ключи 256 бит: устойчивость к квантовому перебору на уровне 128 бит.
- Утечка `epoch_key` раскрывает только одну эпоху одного устройства; утечка `port_key` раскрывает расписание портов,
  но не позволяет создать подлинный пакет.
- Перехватчик на пути может переслать пойманный пакет со своего адреса раньше клиента. Он получит только сетевой
  доступ; сервисы за SPA требуют собственных учётных данных.
- Попытка расшифровки перебирает устройства × 3 эпохи. Её цену держат бюджеты §6 п. 1: заливка стоит атакующему
  стука новых клиентов, но не продления допусков (кроме устройств сверх 32 за одним источником). Цену nft — бюджет
  изменений устройства (§6 п. 9): одно изменение — одна транзакция (~18–20 мс, с `destroy element` и без), так что
  утёкшее приглашение держит блокировку nft около 11 мс в секунду, сверх того — 32 изменения сразу (~0,6 с) раз в
  минуту. Без `destroy element` полный набор допусков (65 536 элементов) делает отказом любой сброс с элементом,
  которого нет; одно приглашение его не заполнит (32 адреса).

## 10. TCP-носитель

Для сетей, где неизвестный UDP режется целиком, тот же пакет можно доставить по TCP.

- Порт — тот же `port(slot)` (§3); сервер принимает TCP на портах слотов `slot−1`, `slot`, `slot+1`, если носитель
  включён на ноде.
- Клиент открывает TCP-соединение, пишет пакет SPA v2 без изменений (§5) первыми данными и закрывает соединение.
  Запись можно резать на любые сегменты. Ответа нет: сервер читает до EOF (не больше `len_max + 1` байт, не дольше 3 с)
  и сбрасывает соединение (RST).
- Проверка — §6, длина пакета — число прочитанных байт. Кэш nonce общий для UDP и TCP.
- Ограничение частоты SYN на адрес IPv4 и IPv6 /64 — в nftables, свои наборы, тот же предел, что для UDP (§6 п. 1).
  Стуки носителя проверяются в своём бюджете; источник с допуском — сначала против своих устройств.
- Порядок в клиенте: сначала UDP; если подключение после UDP-пакета и его повтора не удалось — один раз TCP-носитель
  и снова подключение. Запоминать для сети, какой носитель сработал.
- Цена: пока слот активен, его порт отвечает на SYN и виден сканеру как открытый. Порт меняется каждый слот
  и ничего не отдаёт.

### 10.1. TCP-носитель в форме ClientHello

96–512 случайных байт первыми данными TCP-соединения — класс трафика, который часть цензоров режет без разбора
(RAYCONTROL.md §22.2.3). Поэтому тот же пакет можно отправить в форме начала рукопожатия TLS. Формат пакета (§5)
не меняется, меняется только обёртка.

- Клиент пишет одну TLS-запись `16 03 01 <длина>` с ClientHello:
  - `legacy_version` `03 03`, случайные `random` (32 байта) и `session_id` (32 байта);
  - шифры и расширения — как у настоящего Chrome: снимок Google Chrome 156 stable (`internal/spa/chrome_hello.hex`,
    снят CI клиента, форк sing-box 427f972) с ML-DSA и GREASE в `signature_algorithms`, `trust_anchors`, ALPS,
    GREASE ECH. На каждое соединение заново, как у Chrome:
    - `random`, `session_id`;
    - ключи в `key_share`: настоящий ML-KEM-768 и x25519;
    - все значения GREASE;
    - GREASE ECH, как у BoringSSL: `enc` — свежий открытый ключ X25519 (у случайных байт старший бит был бы взведён в
      половине случаев, у ключа — никогда), данные — случайные, длины 144, 176, 208 или 240 байт;
    - порядок расширений: GREASE остаются первым и последним.
  - SNI нет, как при обращении по адресу. JA4 — `t13i1516h2_8daaf6152771_cb7bf5808d99`, у носителя клиента такой же;
  - **пакет SPA (§5) целиком — данные расширения `session_ticket` (`0x0023`)**: так выглядит непрозрачный тикет
    клиента, который возобновляет сессию.
- Дальше — как в §10: соединение закрывается, ответа нет.
- Нода различает формы по первым байтам: `16 03 0x` — ClientHello. Она читает не больше 4096 байт, достаёт данные
  `session_ticket` и проверяет их как пакет (§6). Иначе — голый пакет из §10. Принимаются обе формы.
- Эталон: `internal/spa` `TLSCarrier` / `FromTLSCarrier`. Тест проверяет, что `crypto/tls` разбирает запись как
  ClientHello.
- Порядок в клиенте: UDP, затем ClientHello, затем голый TCP — для нод до raycontrol v0.10.0: они ClientHello не понимают. Подсказка `spa.carriers` в подписке (subscription-v1) перечисляет носители в этом же порядке. `rayctl -carrier auto` идёт так же.

## 11. Ротация UDP-портов сервисов

Сервисы на UDP 443 (Hysteria2, naive-quic, DoH3) доступны ещё и на порту, который меняется по расписанию: так поток
не держится на одном порту дольше слота.

- Расписание сервиса — те же формулы §2–§3 с ключом и диапазоном сервиса вместо ключа и диапазона SPA:
  `port(slot) = port_base + (BE64(HMAC-SHA256(port_key, "raycontrol-spa-v2 port" ‖ BE64(slot))[0:8]) mod port_range)`.
  Длина слота — `slot_len_s` ноды (§1). Параметры — в `services[]` пакета регистрации (§8).
- Нода (`rayspa`) перенаправляет порты слотов `slot−1`, `slot`, `slot+1` на порт сервиса (nftables, NAT); ответы идут
  с порта слота. Доступ к сервису — тот же SPA-доступ к его UDP-порту: пакет на порт слота без SPA отбрасывается.
- Клиент шлёт поток сервиса на порт текущего слота и при смене слота открывает **новое соединение QUIC** (новый
  сокет, новый Initial) на порт нового слота. Уже открытые соединения доживают на своём порту: NAT-запись conntrack
  держится, пока идёт трафик, а периметр пропускает `ct state established` до проверки портов; окно `slot−1…slot+1`
  касается только новых потоков.
- **Тот же сокет на порт нового слота** (проверено 2026-11-16, `TestNetnsSlotChange`, Linux 6.18 и 7.0): вторая
  запись conntrack получила бы тот же обратный кортеж, что и первая (оба порта слота — redirect в один порт), и ядро
  при подтверждении записи даёт ей другой порт клиента (нулевая привязка SNAT на входе). Пакет доходит до сервиса с
  **новым портом источника**, ответ уходит с порта слота; прежний поток на старом порту живёт. Для сервиса это то же,
  что смена порта NAT у клиента. Ядро, которое такой пакет отбрасывает, тест тоже допускает; клиенту полагаться на
  проход не стоит. Раньше здесь было написано «отбрасывается» — это было неверно.
- Без маршрутизации во фронте по connection ID миграции соединения нет: и с того же сокета (новый порт источника),
  и с нового сокета фронт (udpmux) поток не узнаёт — новый поток он принимает только по Initial (SNI или salamander),
  короткие заголовки с незнакомого адреса отбрасывает. То же при смене порта NAT у клиента.
- Маршрутизация во фронте по connection ID ([`quic-cid-route-v1.md`](quic-cid-route-v1.md)) это снимает: server
  connection ID несут зашифрованную метку бэкенда, и фронт заводит поток по короткому заголовку с незнакомого адреса.
  С ней (niko-server v0.18.0 на ноде и её пин в raycontrol) клиент может при смене слота не открывать новое
  соединение, а перенести старое на порт нового слота — с нового сокета (Hysteria2 — port hopping, quic-go —
  `AddPath`/`Probe`/`Switch`) или с того же (сервер увидит новый порт источника, как при смене порта NAT); сервер
  проверяет новый путь и переходит на него. Смену порта NAT соединение переживает само. На порт слота нужен допуск SPA,
  как для нового потока; с нодой без маршрутизации по ID — новое соединение, как выше.
- Диапазоны сервисов не пересекаются друг с другом, с диапазоном SPA и с фиксированными портами сервисов.
- Сервис остаётся доступен и на своём обычном порту (443).
