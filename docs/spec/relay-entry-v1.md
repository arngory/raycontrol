# relay-entry-v1: вход на relay — выход в интернет страны relay

Статус: **черновик, редакция 3** (2026-11-16), ничего не сделано. Основание — решения владельца 2026-11-16: выход в
стране пользователя («да, но стоит трижды подумать»), приложение целиком по умолчанию, риск оператора relay
принят (цитаты — §18; [decisions](../decisions.md) R4-45). Согласовано с клиентом. Списки и правило `relay` в
подписке — [rules-v1](rules-v1.md); подлинность приложения — [app-attest-v1](app-attest-v1.md). Сторона клиента —
`niko:docs/design/ROUTING-APPS.md` (ветка `claude/intelligent-allen-0oa8na`, `77c3988`), дальше «ROUTING-APPS».
Редакция 3: приложение целиком (§7), доверие к точному сертификату вместо Let's Encrypt (§4.2), два класса сокетов в
ядре (§9). Пометка «(вывод)» — не проверено ни кодом, ни тестом.

Зачем: сервисы «только изнутри» (банки, госуслуги) смотрят на страну адреса. Через ноду за границей они не работают,
а «напрямую» открывает им домашний адрес. Нужен выход в интернет со своего адреса в стране пользователя. Relay уже
стоит в этой стране (relay-v1 §1), но он — L4: пересылает зашифрованный трафик на выход и не видит ни имени, ни адреса
назначения. Расшифровывать на нём всё сервер отвергает. Здесь relay получает **отдельный вход** со своим маленьким
data plane.

## 1. Коротко

- **Вход** — naive из `rayd` на хосте relay, h2 и h3, UDP через `connect-udp`. Свой порт; свой самоподписанный
  сертификат, клиент доверяет ровно ему (два сертификата в `relays[].local`). Пускает после SPA relay и пароля
  пользователя (§4, §5).
- **Учётные данные** — свои у каждого relay, выводятся на выходе; на диске relay — только их хеши (§5).
- **Что выпускает** (§7):
  - **подтверждённое приложение** (app-attest-v1: соединение подписано аттестованным ключом и несёт тег набора
    `inside-only`) — **целиком**, по любому адресу; остаётся только политика выхода;
  - **неподтверждённый клиент** — назначения из наборов `inside-only` страны relay и адреса из подписанного набора
    этой страны. Остальное — `403` с `Niko-Refused: policy`: по умолчанию это отказ по `fallback` набора; в
    адаптивном режиме администратора клиент ведёт такое назначение через узел, если его нет ни в одном наборе
    `inside-only`.
- **Страну** relay определяет сам, по своему адресу и подписанным наборам (§7.3). Списки берёт и проверяет сам (§8).
- **Ядро relay** различает два класса сокетов по UID: неподтверждённым — только разрешённые подсети (§9).
- Без свежего снимка выхода 24 ч вход перестаёт принимать (§6). Путь L4 к выходу не меняется (§2).
- **Включают двое:** root на хосте relay и администратор выхода. По умолчанию выключено (§3).

## 2. Что не меняется

- Пересылка L4 к выходу: DNAT на TCP 443, UDP 443, порты подписки и API; REALITY, naive и Hysteria2 сквозные до
  выхода (relay-v1 §2, §3.1). Цепочки `prerouting`, `forward`, `postrouting` те же.
- SPA relay и ключи `K_relay` (relay-v1 §3), точка замера `rayd relay` (relay-v1 §9).
- Путь «через relay к узлу» — по-прежнему на relay нечего расшифровать. Вход — отдельный путь, его выбирает клиент
  по правилу `relay` или своим правилам (rules-v1 §6.2).

## 3. Включение

Два согласия, оба нужны; по умолчанию оба выключены:

1. **Root на хосте relay:** `rayctl relay entry on` (§17.1). Хост relay может держать другой человек, чем выход
   (relay-v1 §2). Вход делает его адрес выходом в интернет для чужих пользователей — без его согласия этого быть не
   должно. Так же сделано у обновления relay по слову выхода (`rayctl update remote on` на relay).
2. **Администратор выхода:** `rayctl relay set -entry on NAME` (§17.2).

Дальше вход ждёт, пока есть всё: свежий снимок выхода с учётными данными (§6), принятые списки (§8), страна (§7.3).
Тогда он принимает соединения, а выход публикует `relays[].local` (§13).

## 4. Вход

### 4.1. Процессы и порт

- **`rayd relay-entry`**, юнит `rayd-relay-entry`. Код — тот же, что `rayd naive` на ноде (`internal/naive`):
  CONNECT, `connect-udp` (naive-udp-v1), паддинг, пределы, счёт по пользователям; плюс поток `attest.niko.arpa`
  (app-attest-v1 §4).
- **`rayd relay-entry-sock`** («помощник»), юнит рядом, свой UID: выдаёт nonce app-attest, сам проверяет
  доказательство по открытым ключам устройств и только после этого сам ведёт подтверждённые соединения: набирает
  назначение и пересылает данные (§9.3). Слову входа не верит, дескрипторов входу не отдаёт. Сетевых слушателей
  нет.
- Оба — под **UID data plane** (диапазон 9100–9179, на relay он свободен), разными UID. Без привилегий,
  `IPAddressDeny` — как у naive на ноде (egress-policy-v1 §10, `denyLocal`).
- Ключа пакета relay (mTLS к API выхода) у входа нет. Поток `WatchRelay` держит `rayd relay`: он пишет входу файл
  пользователей (§5) и берёт списки (§8). Вход смотрит в интернет, и его взлом не должен давать личность relay перед
  выходом.
- **Порт** — свой, TCP и UDP на одном номере. Выбирает root на relay при `entry on`: `-port N` или первый свободный
  от случайного в 10000–59999. Свободный — не пересылаемый (ни TCP, ни UDP), не SSH relay, не точка замера, вне
  диапазона SPA relay. На 443 вход встать не может: 443 relay пересылает ядром, без разбора TLS.
- Порт открывает SPA relay (`K_relay`) как **локальный сервис relay**, как точку замера (relay-v1 §9.1). ID —
  `65534`. Выход считает порт из `ReportEntry` занятым, как порт точки замера: сервис выхода, которому потом дали этот
  порт, через relay на нём не пересылается. Стук с пустым scope открывает и его; с явным — если в scope есть
  `local.svc` (§13).

### 4.2. TLS: доверие к точному сертификату

**Почему не Let's Encrypt.** Клиент идёт на relay по адресу, а пин ключа нужен имени: cronet-go отказывает в пинах
без имени сервера (`naive_client.go:140-142`: «public key pins need a server name, not an address»), пины Chromium
тоже только для имён. Сертификат на адрес без пина доверял бы любому УЦ из списка Chrome. Поэтому — свой сертификат
и доверие ровно к нему.

**Как клиент доверяет.** Новый API cronet-go (`arngory/cronet-go`, наш; делает клиент): движок принимает сервер,
только если DER листа **равен одному из заданных** сертификатов. Ни цепочки, ни имени, ни сроков; для h2 и h3.
Сертификаты — в `relays[].local.certs` (§13).

**Сертификаты.**
- Самоподписанные: пути через УЦ нет, и он не нужен. ECDSA P-256; в SAN — публичный IPv4 relay (§7.3), для
  порядка: клиент его не сверяет. Срок — 10 лет: сроки клиент не смотрит, смена — по §4.2 ниже.
- Клиент идёт на адрес без SNI.
- TLS 1.3, только `X25519MLKEM768`, как у naive ноды.
- Ключи и сертификаты делает root на relay при `entry on`, на самом relay: ключи не покидают хост и не идут ни в
  пакет, ни к выходу.
- **Их два: текущий и запасной.** Запасной лежит отдельно: файл root (0600), который вход не читает, — взлом
  процесса входа его не даёт. Root может унести его копию с хоста (`rayctl relay entry spare export`), чтобы
  пережить переустановку.
- **Запасной — это следующий, и он опубликован заранее:** оба сертификата всегда в подписке. Иначе после смены
  ключа банки отказывали бы по `fallback` до следующей подписки клиента.
- Сертификаты (DER) `rayd relay` отдаёт выходу (`ReportEntry`, §11.3), выход кладёт их в `relays[].local.certs`.

**Смена ключа — два порядка.**

*Плановая* (`rayctl relay entry rotate-key`): сначала опубликовать, потом переключить.
1. Root делает новый запасной ключ и сертификат. Подписка несёт три сертификата — текущий, прежний запасной, новый
   запасной. Выход подтверждает публикацию в потоке.
2. Relay переключается на прежний запасной: он у клиентов уже был.
3. Снятый сертификат выход убирает позже — через срок жизни подписки (72 ч).

*Ключ потерян или утёк* (`rayctl relay entry rotate-key -now`, только root на relay: запасной ключ читает только
root): сначала переключить, потом опубликовать.
1. Relay сразу переключается на запасной — он уже в подписке. Утёкший больше не обслуживается.
2. Выход сразу убирает утёкший сертификат из подписки.
3. Root делает новый запасной, он расходится в снимке и подписке.

Ждать, пока разойдётся новый сертификат, при утечке нельзя: всё это время утёкший оставался бы доверенным. Но и так
клиенты со старой подпиской доверяют утёкшему сертификату, пока не возьмут новую, — до 72 ч (срок подписки). Кто
держит утёкший ключ, может в это время выдать себя за вход для них и видеть их трафик `inside-only` — то же, что
видит relay (§15).

Потеряны оба (хост переустановлен без копии запасного) — новая пара. Сначала она расходится, выход подтверждает
публикацию, и только потом relay принимает. Клиенты без новой подписки до её выборки не достают вход, и действует
`fallback` (rules-v1 §6.2). Два сертификата нужны, чтобы так было только в этом случае.

### 4.3. Ответы

Как у naive ноды (subscription-v1 §4, «Профиль naive»), плюс отказ по политике:

| Ответ | Когда |
|---|---|
| ответ сайта (пустой `404`) | нет пароля, неверный, нет `Padding`; неизвестная версия `niko-udp` |
| `200` | принято: CONNECT (с `niko-ack: 1` — после dial); `connect-udp` — всегда сразу (§7.5) |
| `403` с `Niko-Refused: policy` и `Niko-Lists-Version: <версия>` | CONNECT неподтверждённого: назначение вне политики (§7.1); UoT и ICMP. Без тела. На `connect-udp` по назначению не бывает (§7.5) |
| `403` с `Niko-Refused: policy` или `attest` | режим «строго» app-attest-v1: соединение или класс приложения не пускаются (app-attest-v1 §7.2), и на `connect-udp` тоже |
| `403` с `Niko-Refused: attest-required` | у потока тег `Niko-App-Set`, а соединение не подтверждено или его сессия у помощника кончилась (9 минут, §9.3; app-attest-v1 §7.3): клиент подтверждает это соединение и повторяет поток один раз; на `connect-udp` — подтверждает и один раз открывает новый сокет, это не отказ подряд |
| `429` | предел пользователя (§11.1) |
| `502` с `niko-ack: refused \| unreachable \| denied` | как у ноды: назначение отказало, недоступно; `denied` — политика выхода relay (§9: локальные сети, сам relay, выход) |
| `504` | назначение молчало весь тайм-аут dial (10 с) |
| `503` | `connect-udp`: сокет не открылся |

- `Niko-Lists-Version` — версия манифеста списков, которую relay принял (rules-v1 §3.1). Клиент сравнивает её со
  своей (§14).
- `403`, как `429`, несёт `Padding`: без него клиент naive счёл бы, что сервер не паддит (conn-limit-v1 §3.1).
- `403` — только авторизованному. Без пароля — ответ сайта, как всегда.
- `403` и `502 denied` разные: `403` — «не здесь, решает `fallback` или адаптивный режим», `denied` — «нельзя
  никуда».
- UoT (`uot=2`) и ICMP (`icmp.niko.arpa`) вход в v1 не несёт: у пакета внутри потока нет способа получить отказ.
  CONNECT к этим именам — `403`. Клиент шлёт на вход только TCP и `connect-udp` (§14).

## 5. Учётные данные

- На выходе у пользователя есть **секрет входа relay** — один на пользователя, для всех relay. Ротация — как у
  учётных данных сервисов (R4-1): следующий за 3 дня до перехода, прежний ещё 2 дня. Отзыв любого устройства сразу
  меняет его (R4-36). Где хранится (строка `credentials`) — при реализации.
- Пароль на relay выводит выход, для каждого секрета (текущего, следующего, прежнего):

  ```
  password = base64url(HMAC-SHA256(key = секрет входа,
                                   msg = "relay-entry-v1" || 0x00 || node_id relay || relay_id))
  ```

  - `node_id relay` — 16 байт из `relays[].spa.node_id`, `relay_id` — имя relay в UTF-8 (как в `K_relay`,
    relay-v1 §3). `node_id relay` меняется с каждым пакетом: пароли захваченного relay не работают на relay после
    нового пакета, даже под тем же именем.
  - Пароль одного relay ничего не говорит о секрете и о паролях других relay.
- **Устройство** получает свой пароль и следующий в `relays[].local` (§13).
- **В снимке и на диске relay — только хеши.** Поток `WatchRelay` у `rayd relay` несёт для входа пары
  «SHA-256(пароль) → имя», как файл пользователей naive на ноде (`naive.HashPassword`, traffic-limit-v1 §2.3). Имя —
  `u<id>-<отпечаток>` (`store.CredentialName` от пароля). Работающий вход, конечно, видит пароли в
  `Proxy-Authorization` каждого CONNECT (§15).
- `rayd relay` пишет файл пользователей входа; вход перечитывает его, как naive (`naive.Users.Watch`, раз в 5 с).
  Хеш, которого больше нет, теряет все свои потоки: отзыв, снятый по лимиту, выключенный пользователь — сразу после
  нового снимка.
- В снимок попадают только активные пользователи (`User.Active`: включён, не истёк, не сверх лимита), как в конфиги
  data plane ноды (traffic-limit-v1 §3.1).

## 6. Снимок и его свежесть

- Выход шлёт часть снимка для входа после каждого изменения и не реже раза в 30 минут без изменений.
- `rayd relay` пишет файл пользователей с отметкой времени получения по своим часам.
- **Нет свежего снимка 24 ч — вход перестаёт принимать** (fail closed): новые соединения не принимаются, открытые
  закрываются, событие в `rayctl status` relay. Путь L4 не затронут. Пришёл снимок — вход снова принимает.
- 24 ч — с запасом против перекрытий ротации (3 дня до, 2 дня после): за сутки без выхода текущие пароли не кончатся.
  Отозванный пользователь при живом потоке теряет вход за секунды, при лежащем — не позже чем через 24 ч.

## 7. Что вход выпускает

### 7.1. Правило: два класса

**Решение владельца (§18): приложение идёт одним путём со всеми своими обращениями — и внутри страны, и за
границу.** Деление «своё — через relay, иностранное — через узел» по умолчанию не строится; оно — адаптивный режим
администратора.

1. **Подтверждённое приложение** — соединение подтверждено по app-attest-v1 (§4 там), а CONNECT или `connect-udp`
   несёт тег набора `inside-only` страны relay (app-attest-v1 §5). Вход выпускает его **целиком, по любому адресу**,
   в стране и за границей. Остаётся только политика выхода (§9): частные сети, сам relay и выход закрыты, SMTP и
   BitTorrent режутся. Класс приложения доказан ключом, а не взят со слов клиента.
   - Опция администратора выхода — фильтр и для подтверждённых (`rayctl relay set -entry-attested filtered`): тогда
     класс 1 проходит те же проверки, что класс 2. По умолчанию — `whole`, приложение целиком.
2. **Неподтверждённый клиент** — всё остальное: соединение без подтверждения, без тега или с другим тегом. Вход не
   знает приложения и выпускает только:
   - назначение из наборов `inside-only` страны relay (текстовая форма, rules-v1 §2.3): имя под суффиксом или адрес
     в подсети;
   - **любой адрес из набора страны relay** `country-<cc>` (rules-v1 §2.4).

   Остальное — `403` с `Niko-Refused: policy`, без тела. Иначе relay стал бы прокси для чего угодно.

Режим «строго» app-attest-v1 пускает только класс 1 (app-attest-v1 §7.2).

Почему адреса страны для класса 2:
- внутренние адреса и так достижимы из страны: relay обхода не добавляет;
- отечественные аналитика, карты, CDN приложения проходят;
- исходящий трафик relay идёт через фильтры его провайдера, как трафик любого абонента в стране (вывод). Это же
  верно и для класса 1: заблокированное в стране через relay не откроется — как и при «напрямую».

Наборы — только под ключом списков (rules-v1 §3). Свои наборы ноды relay не использует: ключа списков у ноды нет, и
взломанная нода не может расширить то, что выпускает relay.

### 7.2. Сторонние имена приложения

Приложение ходит и на имена вне списка. Варианты, которые обсуждались:
- (а) relay выпускает всё, что прислал клиент — без доказательства relay стал бы прокси для чего угодно;
- (б) клиент шлёт на relay только назначения из списка, остальные имена приложения — через узел;
- (в) relay выпускает назначения из списка и адреса своей страны, иностранное — `403`, клиент ведёт его через узел.

**Решение владельца 2026-11-16 (§18): приложение целиком.** Отсюда:
- для подтверждённого приложения — (а): теперь класс доказан аттестацией (§7.1, п. 1);
- для неподтверждённого — фильтр (в), но `403` — **отказ по `fallback` набора**, без деления приложения;
- **адаптивный режим** (`enforce[].adaptive`, rules-v1 §6.2; по умолчанию выключен) — прежнее поведение (в): клиент
  ведёт через узел назначения, которых нет ни в одном наборе `inside-only`.

### 7.3. Страна relay

- Не из снимка: взломанная нода поставила бы `us` и сделала relay открытым прокси в чужой стране.
- Relay берёт свой публичный адрес: IPv4 на своём интерфейсе вне локальных сетей (`local4`, egress-policy-v1 §10),
  а за NAT — адрес, который root назвал при `entry on` (`-public-addr`). Адрес из снимка или пакета для этого не
  берётся.
- Страна — та, чей подписанный набор `country-<cc>` содержит этот адрес. Наборы не пересекаются (у адреса одна
  страна в каждой из двух баз, rules-v1 §2.4), так что страна одна или её нет.
- Снимок может назвать ожидаемую страну (`rayctl relay set -country CC`). Relay не принимает страну, в чей набор его
  адрес не входит: вход не включается, событие `entry: the exit says <cc>, the relay's address is in <cc2|no set>`.
- Адреса нет ни в одном наборе (новый префикс, облако, которое вычли) — вход не включается, с причиной.
- Новая версия списков вывела адрес из набора — вход выключается до следующей версии, событие.
- Адрес relay у выхода (`rayctl relay add`) и найденный relay расходятся — предупреждение: клиенты идут по адресу из
  подписки.

### 7.4. Неподтверждённый класс: назначение и первые байты

Только для класса 2 (§7.1). Одного имени в CONNECT мало: клиент мог бы открыть CONNECT на разрешённое имя и внутри
TLS назвать другое. Поэтому вход смотрит начало потока клиента, прежде чем отдать назначению хоть один его байт.
Имена сравниваются по rules-v1 §2.3: relay снимает одну конечную точку с имени CONNECT и с SNI, сравнивает строчными
и по границе метки; имя не из ASCII именем списка не бывает.

CONNECT по имени N:
1. **До ответа:** relay резолвит N (§10) и оставляет только адреса из подсетей §7.1, будь N в списке или нет. Ни
   одного не осталось — `403`. Набирает только оставшиеся.
   - С выключателем **«имена списка на любом адресе»** (§9.2; администратор выхода, по умолчанию выключен) N под
     суффиксом `inside-only` набирается по любому своему адресу: так работают банки на CDN и в облаках, чьих
     подсетей нет ни в одном наборе.
2. **Первые байты** (до 16 КиБ, до 10 с):
   - **Ответ назначения идёт клиенту сразу.** Ждут только байты клиента к назначению: протоколы, где первым говорит
     сервер (SSH, IMAP, POP3, FTP, MySQL), иначе встали бы. Клиент молчит, пока не ответит сервер, — решает адрес
     (п. 1); его первые байты, когда придут, проверяются, если это TLS или HTTP;
   - TLS ClientHello — SNI должно быть равно N или само быть под суффиксом `inside-only` страны relay. SNI нет —
     решает адрес (п. 1); для адреса, открытого выключателем п. 1, видимый и совпадающий SNI обязателен;
   - **ECH**: правило SNI — к внешнему имени. Chromium шлёт расширение ECH-GREASE и без настройки ECH, и тогда
     внешнее имя — это и есть N; отказ по одному наличию ECH сломал бы класс 2. Внешнее имя не проходит — сброс;
   - HTTP/1.x — `Host` без порта по тому же правилу;
   - не TLS и не HTTP — только по адресу из подсетей §7.1.
3. Не прошло — поток сбрасывается (ответ `200` уже ушёл, вписать `403` в поток приложения нельзя), счётчик
   `first_bytes`. Честный клиент сюда не попадает: имя в CONNECT он берёт из того же сниффинга или FakeIP (§14).

CONNECT по адресу: адрес — по §7.1. Адрес из набора страны — без проверки SNI и `Host`: CONNECT по имени к тому же
сайту прошёл бы, а сброс приходит после `200`, и `fallback` у клиента не сработал бы. Адрес только из подсетей
`inside-only` (не из набора страны) — TLS с SNI под суффиксом `inside-only`, HTTP с таким `Host`, иначе сброс.

Для класса 1 ни назначение, ни первые байты не проверяются: приложение выпускается целиком.

### 7.5. `connect-udp`

Формат — naive-udp-v1 §3.2: один запрос на сокет приложения, адрес в каждой датаграмме.

- **Ответ — как у ноды: `200` сразу**, не дожидаясь первой датаграммы. По назначению вход на `connect-udp` не
  отказывает никогда; кроме `200` бывают `429` и `503` (naive-udp-v1 §3.2) и ответ сайта неавторизованному.
  `403` бывает только по классу приложения или подтверждению (app-attest-v1 §7: `policy` в «строго», `attest`,
  `attest-required`): сокет принадлежит одному приложению. Клиент читает его как отказ этому сокету, не считая
  отказом подряд и никогда не переходя на UoT.
- **Класс 1:** датаграммы — по любому адресу, через помощника (§9.3).
- **Класс 2: каждая датаграмма проверяется.** Адрес — из подсетей §7.1. Датаграмма с именем (тип 3; с FakeIP у
  клиента это обычный случай) — резолв relay, затем то же правило по адресу; имя под суффиксом `inside-only` с
  выключателем §9.2 — по любому своему адресу. SNI в QUIC не разбирается (позже, §19).
- **Датаграмма вне политики отбрасывается молча**, счётчик `udp_refused`. Запрос живёт.

Почему не отказ запросом:
- запрос `/.well-known/masque/udp/*/*/` — один сокет приложения на много назначений: отказ по одной датаграмме
  убил бы весь сокет;
- `429` и `503` клиент считает отказами подряд: три подряд переводят его на UoT до смены сети. Отказы по назначению
  такими ответами сломали бы UDP всей сети.

Неподтверждённый клиент шлёт на вход UDP только к адресам и именам из наборов (§14), так что у честного клиента
отбросов почти нет: это расхождение версий списков или чужой клиент.

### 7.6. Известные пределы

- **Фронтинг внутри TLS** — `:authority` (или `Host` внутри TLS) не равен SNI — так не ловится: relay TLS приложения
  не вскрывает. Тут поможет только то, что CDN сам сверяет SNI и `Host`. На 2026-11-16, по источникам: Google в 2018;
  Amazon CloudFront в 2018 закрыл только фронтинг между разными аккаунтами, а запрос без SNI, получивший сертификат
  по умолчанию `*.cloudfront.net`, всё ещё направляется по `Host` (документация AWS); Cloudflare отвергает
  расхождение давно; Azure — с 2022–2024; Fastly — с 2024-02-27 (anti-censorship-team Tor). Но измерение 2023 года
  (Subramani и др., WWW '24, arXiv 2310.17851) нашло фронтинг возможным у 22 из 30 CDN, среди них Akamai. «Крупные CDN закрыли это в 2018» — неточно.
  - Касается класса 2. Где это открыто: адрес CDN в наборе страны — вычитание подсетей CDN из наборов стран
    (rules-v1 §2.4) убирает адреса самих CDN, но кеши CDN в сетях местных провайдеров (с адресами провайдера)
    остаются (вывод); и **выключатель §9.2**: имя банка на таком CDN открывает адрес CDN, а внутри TLS можно
    назвать другой сайт того же CDN. Поэтому выключатель — решение администратора, по умолчанию выключен.
  - Что это даёт: доступ к сайту за тем же CDN через relay. Но и этот трафик идёт через фильтры провайдера relay
    (вывод).
- **Имя из списка на иностранном адресе** без выключателя §9.2 у класса 2 — `403`; клиент считает его отказом по
  `fallback` набора (§14). У класса 1 вопроса нет.

## 8. Списки на relay

- Тот же код, что у зеркала ноды (rules-v1 §4.2), но **relay берёт списки сам**: `rayd relay` ходит сначала на GitHub
  (rules-v1 §2.6), затем, если GitHub не ответил, к зеркалу выхода.
- Зеркало выхода — по `RelayService` (§11.3): `FetchRules{name}` отдаёт файлы принятого выходом манифеста, его
  подпись и `timestamp.json`. Тем же сертификатом пакета, с адреса relay.
- Relay проверяет обе подписи сам, встроенными ключами (rules-v1 §3.5), и **никогда не верит спискам, которые
  подписала только нода**.
- Нужны: манифест, `timestamp.json`, `country-<cc>.txt`, текстовые `inside-only` своей страны, их
  `<tag>.entries.json` и `cdn-<провайдер>.txt`, которые эти записи называют (§9.2). До первой страны (§7.3) relay
  берёт все `country-*.txt`, потом только свой.
- Расписание — как у ноды (rules-v1 §4.2). Порядок свежести — по версии манифеста (rules-v1 §3.5): утёкший ключ
  свежести не запрёт обновления relay. Опора свежести у relay — его часы в момент получения подписи, откуда бы она
  ни пришла, с GitHub или с зеркала выхода; манифест под ключом списков ставится сразу (rules-v1 §3.5, п. 6–7).
- **Срок `timestamp.json` истёк** — relay держит последние принятые списки, вход работает, событие в `rayctl status`
  relay и в докладе выходу (§11.3).
- Принятых списков нет вовсе — вход не принимает.
- Вход и `rayspa` проверяют подписи и хеши файлов ещё раз, прежде чем взять их: `rayd relay` их только приносит.

## 9. Ядро на relay

### 9.1. Два класса сокетов

Ядро не знает, подтверждено ли соединение. Знает процесс — и кладёт это в UID сокета:
- **UID входа** (`$ENTRY`, `rayd relay-entry`) — все сокеты, которые вход создаёт сам: класс 2, DNS. Ядро пускает
  их только в разрешённые подсети;
- **UID подтверждённых** (`$ATTESTED`, `rayd relay-entry-sock`) — сокеты класса 1. Их создаёт, набирает и
  пересылает по ним сам помощник, и только под проверенное им самим доказательство app-attest (§9.3). Вход держит
  только свою сторону unix-соединения с помощником, дескриптора подтверждённого сокета у него нет.
- `meta skuid` в nftables берёт учётные данные файла сокета — `file->f_cred->fsuid` (`net/netfilter/nft_meta.c`), то
  есть процесса, который сокет создал. Здесь создатель и пользователь — один процесс.

```
set entry_allow4 { type ipv4_addr; flags interval; }   # country-<cc> ∪ подсети inside-only <cc>
set entry_allow6 { type ipv6_addr; flags interval; }
set entry_names4 { type ipv4_addr; flags timeout; size 4096; }   # §9.2, пуст без выключателя
set entry_names6 { type ipv6_addr; flags timeout; size 4096; }
set entry_dns4   { type ipv4_addr; }                   # резолверы хоста на 53
set entry_dns6   { type ipv6_addr; }
set exit4        { type ipv4_addr; }                   # все адреса выхода
set exit6        { type ipv6_addr; }
chain output {
	type filter hook output priority 0; policy accept;
	meta skuid { $ENTRY, $ATTESTED } jump entry_egress   # оба класса: политика выхода
	meta skuid $ENTRY jump entry_limit                   # класс 2: только подсети
}
chain entry_egress {
	fib daddr type local counter reject with icmpx admin-prohibited comment "self"   # как to_node на ноде
	ip daddr @exit4 counter reject with icmpx admin-prohibited comment "exit"
	ip6 daddr @exit6 counter reject with icmpx admin-prohibited comment "exit"
	ct state new,untracked jump egress_local             # как на ноде, egress-policy-v1 §10
	jump egress                                          # SMTP и BitTorrent, egress-policy-v1 §3
}
chain entry_limit {
	meta l4proto { tcp, udp } ip daddr @entry_dns4 th dport 53 return
	meta l4proto { tcp, udp } ip6 daddr @entry_dns6 th dport 53 return
	ct state new ip daddr @entry_names4 return
	ct state new ip6 daddr @entry_names6 return
	ct state new meta nfproto ipv4 ip daddr != @entry_allow4 counter reject with icmpx admin-prohibited comment "entry"
	ct state new meta nfproto ipv6 ip6 daddr != @entry_allow6 counter reject with icmpx admin-prohibited comment "entry"
}
```

Набросок; TCP получает сброс, как в egress-policy-v1 §3 (`reject with tcp reset` отдельными правилами). Собственные
адреса хоста закрываются так же, как `to_node` у ноды — `fib daddr type local` (`internal/perimeter/firewall.go`,
цепочка `output`, правила `to_node`); выход — набором всех его адресов, IPv4 и IPv6.

Что это даёт и чего нет:
- По умолчанию любой сокет входа — класс 2 и ограничен ядром. Ошибка в коде входа (путь dial, который забыл
  проверку) не выпустит класс 2 наружу.
- Подтверждённое соединение помощник ведёт только под живую сессию, которую он открыл сам, проверив подпись ключом TEE
  телефона (§9.3). Помощник, который верил бы слову входа, не защищал бы ничего: вход, взломанный удалённо,
  попросил бы «подтверждённое» соединение, и relay стал бы открытым прокси. Что остаётся у взломанного входа — §9.3,
  «Остаточный риск».
- **Почему не метка сокета** (`SO_MARK`, так предлагал клиент): поставить метку можно только с `CAP_NET_ADMIN`, а с
  Linux 5.17 — ещё с `CAP_NET_RAW` (socket(7)). У Rocky 9 ядро 5.14: там только `CAP_NET_ADMIN`, то есть право
  переписать сам периметр. `CAP_NET_RAW` — сырые сокеты, подделка пакетов. Сейчас ни у одного юнита data plane
  возможностей нет (`CapabilityBoundingSet=` пуст; `internal/deploy/check.go` пускает `CAP_NET_ADMIN` только у
  `rayspa`), и вход, который смотрит в интернет, их не получит. Два UID обходятся без привилегий; nftables видит
  класс так же надёжно, по `meta skuid`.

Остальное:
- **Адрес выхода закрыт** не ради порядка: выход пускает адрес relay к портам своих сервисов без SPA (relay-v1 §3).
  Вход, который достаёт выход, дал бы любому пользователю входа обход SPA выхода.
- **SMTP и BitTorrent на relay закрыты всегда**, не по выключателю выхода: жалобы придут на адрес relay.
- `egress_local` и списки — те же, что на ноде (`local4`, `local6`).
- Резолверы — адреса из `/etc/resolv.conf` хоста, только порт 53; заглушки 127.0.0.53/54 — как `LocalResolvers` на
  ноде.
- Наборы меняются одной транзакцией nft при новой версии списков, как политика выхода (1–2 с). Не принялось — прежние
  наборы остаются, событие.
- Страж conntrack (conn-limit-v1 §6.3) берёт оба UID: соединения входа — новые записи в таблице relay.
- Размер: у RU после слияния ~8 700 префиксов IPv4 только по RIR (rules-v1 §2.4); после пересечения — больше.
  Интервальный набор nft на десятки тысяч элементов — обычное дело (вывод, замерить на ядрах Debian 12 и Rocky 9).
- Цепочка `forward` (DNAT к выходу) входа не касается: его пакеты — свои, `output`.

### 9.2. Выключатель «имена списка на любом адресе» (класс 2)

`rayctl relay set -entry-names on NAME` (администратор выхода; по умолчанию выключен). Для имён под суффиксом
`inside-only` у неподтверждённого класса:
- вход резолвит имя сам (§10), и **каждая цель в цепочке CNAME** должна быть под `domains` той же записи или в её
  `cname:` (то же правило сравнения, rules-v1 §2.3); иначе `403`. Пустой `cname:` — CNAME вне своих `domains`
  запрещены. Иначе висячий CNAME на того же провайдера, что в `cdn:`, прошёл бы: злоумышленник займёт ресурс и
  получит на него сертификат через HTTP-01;
- **адрес набирается, только если лежит в адресах той записи списка, под чей суффикс попало имя:** её AS и подсети
  (`cidr` в `<tag>.entries.json`) или подсети провайдеров из её поля `cdn:` (`cdn-<провайдер>.txt`, `kind: cdn`,
  только текст, под ключом списков, rules-v1 §2.3). `cdn:` — ровно то место, где relay выпускает адрес, полученный
  резолвом имени из `inside-only`. В `entry_allow` и другие наборы файлы `kind: cdn` не входят. Чужой адрес —
  `403`. Иначе висячий CNAME под суффиксом банка (`promo.<банк>` указывает на удалённый облачный
  ресурс, который занял кто-то другой) выпустил бы неподтверждённого клиента на адрес злоумышленника;
- подходящие адреса вход просит `rayspa` через локальный сокет (проверка UID собеседника) добавить в
  `entry_names4/6` на время dial этого соединения — 2 минуты; затем набирает их;
- первые байты обязательны: только TLS с SNI под суффиксом `inside-only` или HTTP с таким `Host` (§7.4);
- предел набора — 4096 адресов; полон — `403`;
- **политика выхода действует и на эти адреса:** частные сети, loopback, сам relay и выход закрывает ядро для UID
  входа (`entry_egress`, §9.1) до набора `entry_names`, что бы ни ответил DNS.

Цена — фронтинг на CDN, которые его не закрыли (§7.6), в пределах провайдеров, названных записью: поэтому
выключатель, а не умолчание. Для класса 1 он не нужен. Взломанный вход попросит любой адрес — это страховка от
ошибок, не от взлома, как §9.1.

### 9.3. Помощник сокетов: доказательство, а не слово входа

**Кто что держит.**
- **Цепочки аттестации и контекст регистрации** (вызов, `node_id` выхода, `sub.pin`) подтверждённых устройств
  `rayd relay` берёт из снимка выхода и передаёт **помощнику**, не входу. Помощник **сам проверяет каждую цепочку**
  тем же кодом, что выход (app-attest-v1 §3.5, §7.2), и принимает только ключи, чью цепочку проверил: ни взломанный
  выход, ни взломанный `rayd relay` не впишут программный ключ как «устройство». Список отзыва Google `rayd relay`
  берёт сам, у Google, и передаёт помощнику; придержать его взломанный `rayd relay` может, но ключ и тогда —
  настоящего телефона.
- Помощнику же — `node_id` relay, режим, флаг `unattested deny`, разрешённые теги и наборы сертификатов входа для
  `binding`.
- Ключ пропал из снимка (отзыв устройства, удаление пользователя) — помощник сразу закрывает его сессии и их
  соединения.
- У входа ключей нет: проверить доказательство он не может и не должен.

**Ход доказательства на relay** (app-attest-v1 §4, с nonce помощника):
1. Клиент открывает `CONNECT attest.niko.arpa:0`. Вход просит у помощника nonce и получает `(nonce_id, nonce)`.
   Помощник помнит nonce 30 с, один раз.
2. Вход отвечает клиенту `200` с `Niko-Attest-Nonce: <nonce>`.
3. Клиент пишет кадр (app-attest-v1 §4.2). Вход передаёт помощнику **сырое доказательство**: `nonce_id`,
   отпечаток ключа и подпись — как пришли.
4. Помощник сам: nonce его, свежий, не использован; ключ есть в его списке и `until` не прошёл; подпись ECDSA
   P-256 над `"app-attest-v1" ‖ 0x00 ‖ nonce ‖ node_id relay ‖ binding` верна, где `binding` — по набору
   сертификатов входа (app-attest-v1 §4.2, `kind` 2): текущему или предыдущему, и ни одному с отозванным
   сертификатом. Наборы помощнику пишет `rayd relay`; после смены при утечке (§4.2) набор с утёкшим
   сертификатом снимается сразу.
5. Прошло — помощник открывает **сессию** и отдаёт входу её номер (`handle`, 16 случайных байт). Вход отвечает
   клиенту байтом `0x00`. Не прошло — код отказа, вход отвечает `0x01`–`0x04`.

**Сессия.**
- Привязана к этой проверке: устройство, пользователь, время.
- **Срок — 9 минут от последнего успеха** и не дольше `until` ключа. Продлевает его **только новое доказательство
  клиента**, никогда не вход: клиент повторяет его в том же соединении на половине срока, примерно раз в 4 минуты,
  с повтором при ошибке и сразу при пробуждении и смене сети (app-attest-v1 §4.1). Каждый успех даёт сессии ещё 9
  минут, соединение не переоткрывается.
- **Исходящее соединение открывает сам помощник.** На каждое подтверждённое соединение клиента вход открывает к
  помощнику unix-соединение: потоковое для TCP, `SOCK_SEQPACKET` для UDP, — и первым кадром называет `handle` и
  назначение. Помощник проверяет, что сессия жива и в пределах, набирает назначение и пересылает: TCP — `splice`
  через pipe, UDP — по датаграмме. У входа — только его конец этого unix-соединения (или пары `socketpair`), не
  исходящий сокет. Для `connect-udp` одно такое соединение — на один запрос (один сокет приложения).
- **Почему не отдавать дескриптор.** Отданный дескриптор не отозвать: `close()` закрывает только одну копию, а
  `shutdown()` и `SOCK_DESTROY` не останавливают `sendto` по неподключённому UDP-сокету. Копия у взломанного входа
  выходила бы куда угодно и после ухода клиента.
- **Исходящие соединения живут, пока живёт сессия.** Каждое новое доказательство продлевает сессию и все её
  соединения, так что долгий UDP банка не рвётся. Сессия кончилась без продления (9 минут) — помощник закрывает все
  её соединения и пересылки. Это настоящий отзыв: их больше никто не держит. Клиенту это выглядит как обрыв; на
  `connect-udp` он подтверждает соединение и один раз открывает новый сокет, не считая отказом подряд.
- **Телефон спал дольше 9 минут** — соединения `inside-only` через relay рвутся, приложение переподключается;
  доказательство при пробуждении восстанавливает сессию только для новых потоков. Льготы «пока идут данные» нет
  нарочно: взломанный вход мог бы поддерживать поток данных сам. Известное поведение.
- Сессия кончилась — новый поток с тегом получает `403` с `Niko-Refused: attest-required` (§4.3), поток без тега —
  класс 2.
- **Пределы на сессию:** не больше 20 новых соединений в секунду (корзина на 200) и не больше 1280 живых (1024 TCP
  и 256 UDP — как пределы пользователя у naive, conn-limit-v1 §5). Живые помощник считает сам: все они у него.
- Счётчики — §12.

**Тег потока — слово входа.** Помощник не видит потоков: соединение просят под сессию, а не под поток. Значит, какой
поток несёт тег `inside-only`, внутри подтверждённой сессии решает вход. Это в остаточном риске ниже.

**Остаточный риск, честно.** Вход, взломанный удалённо, может пользоваться подтверждённой сессией, пока клиент
подключён, и после его ухода — до конца сессии, не дольше 9 минут: продлить её сам он не может, а с концом сессии
помощник закрывает все её соединения. Всё это — в пределах помощника (20 в секунду, 1280 живых на сессию) и называя
любой поток в сессии подтверждённым. Новых сессий без телефонов он не откроет: нужны ключи TEE. Нет подтверждённых
клиентов — нет и соединений без ограничений: у взломанного входа остаётся только класс 2 в пределах ядра.

**Защита самого помощника.**
- Свой UID data plane, свой юнит; `CapabilityBoundingSet=` пуст, `NoNewPrivileges=yes`.
- Сетевых слушателей нет: он только набирает исходящие соединения и пересылает по ним.
- Поверхность атаки — только unix-сокет от UID входа: каталог, куда доступ есть только у него, и проверка каждого
  соединения по `SO_PEERCRED` (только `$ENTRY`).
- Управляющие кадры (nonce, доказательство, открытие соединения) — фиксированной длины, строгий разбор: неизвестный
  тип, лишний байт, чужая длина — разрыв. Цели фаззинга — разбор управляющих кадров и проверка доказательства.
- **Песочница — вся `denyLocal` naive** (egress-policy-v1 §10): `IPAddressDeny` локальных сетей, но не `any`, и
  `RestrictAddressFamilies` с `AF_INET` и `AF_INET6`, не только `AF_UNIX`. Фильтры cgroup (BPF, `IPAddressDeny`)
  привязаны к сокету при создании — `sk_cgrp_data` в `sk_alloc` (`net/core/sock.c`), то есть к cgroup помощника:
  `any` или один `AF_UNIX` закрыли бы все подтверждённые соединения.

**Кадры помощника.** Запросы 1 и 2 — по управляющему unix-соединению `SOCK_SEQPACKET`, кадр — одно сообщение.
Запрос 3 — первый кадр **нового** unix-соединения на одно исходящее: `SOCK_SEQPACKET` для UDP, потоковое для TCP (там
кадр фиксированной длины идёт первыми байтами). Все числа big-endian:

| Запрос (`type`, u8) | Поля | Ответ |
|---|---|---|
| `1` nonce | — | `0x00`, `nonce_id` (16), `nonce` (32) |
| `2` доказательство | `nonce_id` (16), `key_id` (32), `sig_len` (u16), `sig` (8–72) | `0x00`, `handle` (16) или код отказа |
| `3` соединение | `handle` (16), протокол (u8: `6` TCP, `17` UDP), тип адреса (u8: 4, 6), адрес (4 или 16), порт (u16) | `0x00` — дальше это соединение несёт данные (TCP — поток, UDP — по датаграмме на сообщение); или код отказа и закрытие |

Коды отказа (u8): `0x01` ключ не известен, `0x02` подпись не сошлась, `0x03` nonce чужой, старый или использован,
`0x04` кадр не читается, `0x05` сессии нет или кончилась, `0x06` предел сессии, `0x07` назначение не прошло политику
выхода, `0x08` dial не удался. Неизвестный `type`, лишний байт, чужая длина — разрыв без ответа. Имена в запросе
`3` не бывают: вход резолвит сам (§10) и называет адрес.

## 10. DNS

- Вход резолвит имена сам, резолвером хоста relay — в стране. Что видит этот резолвер, увидел бы провайдер и при
  «напрямую».
- Кеш имён процесса — как у naive (conn-limit-v1 §2): 60 с, отрицательный 30 с; промах платит токен резолва.
- Ответ в частную сеть, на сам relay или на выход не проходит ни политику §7, ни ядро §9 — подмена DNS на локальный
  адрес (rebinding) ничего не открывает. У класса 1 это держит `entry_egress`.
- Клиент шлёт CONNECT по имени и сам не резолвит (§14).
- `rayctl relay entry on` предупреждает, если резолвер хоста — не в наборе страны (публичный за границей): ответы
  CDN будут не для этой страны.

## 11. Пределы, счёт, вызовы

### 11.1. Пределы

- Модель conn-limit-v1 §2 у входа целиком, на пользователя в процессе, числа — как у naive (conn-limit-v1 §5). Оба
  класса — в одном счёте пользователя.
- Предел новых входящих на адрес в периметре relay уже есть (conn-limit-v1 §6.2).

### 11.2. Трафик

- Вход считает байты по имени, как naive (traffic-limit-v1 §2.3), сокет статистики — как у него.
- `rayd relay` читает его раз в 15 с и шлёт выходу `ReportTraffic` (§11.3): счётчики с запуска процесса и `boot`.
  Дельты считает выход, как для своих процессов (traffic-limit-v1 §2.4).
- Байты входа идут в `up + down` пользователя, как с любого профиля. Сверх лимита решает выход: снятый уходит из
  снимка, вход рвёт его потоки (§5).
- Выход берёт только имена из снимка этого relay. Дельту больше потолка (порядок — скорость линии relay за 15 с)
  выход режет и пишет событие: взломанный relay иначе снял бы любого пользователя по лимиту (§19).

### 11.3. Вызовы `RelayService` (perimeter.v1, только добавления)

Тем же сертификатом пакета и с адреса relay, как `Report` и `ReportUpdate`:

| Вызов | Что |
|---|---|
| `ReportEntry` | состояние входа (`off`, `waiting` с причиной, `on`), порт, сертификаты (DER: текущий и запасные, §4.2), страна, принятые версии манифеста и `timestamp.json`, их `expires`, время последней удачной проверки. Раз в 5 минут и при смене |
| `ReportTraffic` | `boot` и счётчики по именам (§11.2) |
| `FetchRules` | файл списков у выхода (§8), потоком частей |

- `RelayService.Report` остаётся для сводок клиентов (relay-v1 §9.3): у него свой смысл и свои коды.
- В `WatchRelayResponse` — часть для входа: включён ли он на выходе, ожидаемая страна, выключатели §9.2 и §7.1, хеши и
  имена (§5), адрес relay у выхода; с app-attest-v1 — режим, флаг `unattested deny`, разрешённые теги и **цепочки
  аттестации с контекстом регистрации** подтверждённых устройств (app-attest-v1 §3.7, §7.2), которые `rayd relay`
  передаёт помощнику, а тот проверяет сам (§9.3). Поле получает только поток `rayd relay`
  (`WatchRelayRequest.probe`), не `rayspa`.
- Локальный сервис `65534` с портом из `ReportEntry` выход кладёт в снимок периметра relay, как точку замера.
- Выход подтверждает в потоке, с какого момента новый список сертификатов в подписке: по этому relay переключает
  ключ при плановой смене (§4.2).
- Старый выход вызовы не знает (`Unimplemented`): вход не включается. Старый relay их не шлёт: `relays[].local` нет.

## 12. Журналы и счётчики

- **Назначений нет нигде**, как на ноде (D-12): ни в журнале, ни в метриках, ни в докладах. В правилах nft нет `log`.
  Тега набора тоже нет (app-attest-v1 §8).
- Счётчики, только числа: `raycontrol_relay_entry_refused_total{reason="policy|policy_listed|first_bytes|udp|limit"}`
  (`policy_listed` — `403` по имени из `inside-only`, мера для выключателя §9.2),
  `raycontrol_relay_entry_streams_total{class="attested|unattested"}`, байты входа, число пользователей со снимка,
  состояние входа, возраст снимка и списков.
- Помощник (§9.3): `raycontrol_relay_entry_sessions` (живые),
  `raycontrol_relay_entry_proofs_total{result="ok|unknown_key|bad_signature|stale_nonce|bad_frame"}`,
  `raycontrol_relay_entry_attested_conns_total{result="opened|rate|limit|expired"}`, байты пересылки.
- Журнал `rayd relay-entry` — запуск, смена состояния, ошибки; имена пользователей — непрозрачные `u<id>-…`, как
  на ноде.

## 13. Подписка: `relays[].local`

Новое необязательное поле у relay (relay-v1 §9.2: поля добавляются совместимо):

```json
"relays": [{"id": "r1", "host": "198.51.100.20", "spa": {"...": "…"}, "probe": {"...": "…"},
  "local": {"v": 1, "svc": 65534, "port": 20443, "udp": true, "country": "ru", "lists": 1042,
            "certs": ["<base64url DER: текущий>", "<base64url DER: запасной>"],
            "user": "niko", "password": "<base64url>", "next": {"password": "…", "from": 1767268800}}}]
```

| Поле | Смысл |
|---|---|
| `v` | версия поля; неизвестную клиент пропускает |
| `svc` | ID локального сервиса для явного scope стука (§4.1) |
| `port` | порт входа на `host`, TCP; с `udp` — и UDP (`connect-udp` по HTTP/3) |
| `country` | страна relay, как её нашёл relay (§7.3) |
| `lists` | версия манифеста, которую relay принял |
| `certs` | сертификаты входа, base64url DER: текущий и запасной, при плановой смене три (§4.2). Клиент принимает сервер, только если лист равен одному из них |
| `user`, `password` | Basic для `Proxy-Authorization`, как у naive; пароль — этого relay (§5) |
| `next` | следующий пароль и момент перехода, как `profiles[].next` |

- У `local` нет ни UoT, ни ICMP (§4.3), ни точки замера: замер relay — по `relays[].probe`, как прежде.
- Выход кладёт `local`, пока есть всё: выключатель выхода, доклад relay `on` за последние 10 минут, сертификаты,
  страна, пользователь активен. При режиме app-attest не `off` — ещё и версия relay, которая сама проверяет цепочки
  устройств (app-attest-v1 §13). Нет поля — входа нет или он не докладывает; правило `relay` тогда даёт `fallback`
  (rules-v1 §6.2).
- Подписка через relay и через туннель несёт `local` так же: это не подсказка, а профиль.

## 14. Клиент

Сторона клиента — его (ROUTING-APPS §5); записано здесь как договор:
- **Подтверждённое приложение** (app-attest-v1) с тегом `inside-only` — на вход целиком: TCP и весь UDP
  (`connect-udp`), все назначения.
- **Неподтверждённый клиент:**
  - CONNECT **по имени**, без своего резолва: FakeIP по умолчанию;
  - имени нет (FakeIP выключен, сниффинг не дал) — CONNECT **по адресу** на вход; вход его принимает (§7.4). Для
    адреса из подсетей `inside-only` это обязательно: через узел банк ушёл бы за границу при `fallback: none`;
  - UDP на relay — только к адресам и именам из наборов (с FakeIP в датаграммах имена); остальной UDP приложения —
    по умолчанию отказ по `fallback`, через узел — только в адаптивном режиме.
- **На вход — только TCP и `connect-udp`.** UoT у исходящего на relay выключен: вход v1 его не принимает. Не вышло
  `connect-udp` на relay — это отказ UDP по `fallback` набора, а не переход на UoT. `403` с `Niko-Refused`
  (`policy`, `attest`, `attest-required`) на `connect-udp` — отказ этому сокету, не считается отказом подряд и
  никогда не переводит на UoT.
- **`403 Niko-Refused: attest-required` на CONNECT** (поток с тегом попал в неподтверждённое соединение): клиент
  подтверждает это соединение и повторяет поток один раз; снова — отказ по `fallback`. На `connect-udp` — подтверждает
  и один раз открывает новый сокет.
- **`403 Niko-Refused: attest`** (режим «строго», соединение не подтверждено): отказ по `fallback`; клиент
  регистрируется заново, если регистрации нет или она истекла, и подтверждает соединение.
- **Подтверждение** — на половине срока сессии (~4 минуты), с повтором при ошибке и сразу при пробуждении и смене
  сети: таймеры Go во сне стоят. Соединения, закрытые с концом сессии, клиенту выглядят как обрыв.
- **После `403 Niko-Refused: policy` на CONNECT:**
  - по умолчанию — отказ по `fallback` набора: приложение целиком, без деления;
  - в адаптивном режиме (`enforce[].adaptive`) назначение, которого нет ни в одном наборе `inside-only` клиента, —
    через узел (никогда не напрямую), запоминается на время жизни версии списков и показывается в «Проверке
    маршрута»;
  - назначение из набора `inside-only` — всегда отказ по `fallback`: устаревший или взломанный relay не должен
    увезти банк за границу. Клиент показывает расхождение `Niko-Lists-Version` со своей версией.
- **TLS:** соединение на адрес relay без SNI; доверие — к точному сертификату из `relays[].local.certs` (новый API
  cronet-go, §4.2), не к цепочке и не к пину. Отдельно от пина точки замера.
- Вход не отвечает — `fallback` правила (rules-v1 §6.2).

## 15. Модель угроз

| Кто | Что получает | Чего не получает |
|---|---|---|
| **Взломанный клиент** (или украденные пароль и SPA-ключ), неподтверждённый | через вход — соединения к внутренним адресам страны relay и к назначениям `inside-only`: то, что и так доступно из страны. Адрес relay как источник для них (жалобы придут оператору relay). Фронтинг на CDN, который его не закрыл, — шире с выключателем §9.2 (§7.6) | выход и его сервисы мимо SPA (§9), частные сети, сам relay, SMTP и BitTorrent; иностранные адреса; другие relay (пароли свои) |
| **Подтверждённый Niko и приложение с чужим именем пакета** (поставлено в обход магазина) | если бы Niko тегировал по имени пакета — relay выпускал бы такое приложение целиком: прокси по любому адресу для этого пользователя | Niko тегирует, только если подпись установленного пакета совпала с `cert_sha256` записи списка (rules-v1 §2.1; app-attest-v1 §9) |
| **Взломанный процесс входа** (удалённое выполнение кода) | подтверждённые сессии клиентов, пока те подключены, и не дольше 9 минут после ухода (продлить сессию вход не может), — в пределах помощника (20 соединений в секунду, 1280 живых на сессию), и только через помощника; назвать любой поток в них подтверждённым; класс 2 в пределах ядра; пароли из CONNECT, назначения | новые подтверждённые сессии без телефонов (нужны ключи TEE, проверяет помощник, §9.3); дескрипторы подтверждённых сокетов (их держит только помощник и закрывает с концом сессии); соединения без ограничений, когда подтверждённых клиентов нет; ключи устройств и пакет relay (их у входа нет) |
| **Висячий CNAME под суффиксом из списка** (поддомен банка указывает на удалённый облачный ресурс, его занял злоумышленник) | с выключателем §9.2 — неподтверждённый клиент вышел бы на адрес злоумышленника; рядом с фронтингом (§7.6). Ограничение адресов по `cdn:` само по себе не спасает: ресурс может быть у того же провайдера, и сертификат на имя злоумышленник получит через HTTP-01 | каждая цель цепочки CNAME — под `domains` записи или в её узком `cname:`, и relay набирает только адреса из AS, подсетей или `cdn:` этой записи (§9.2); CI ищет висячие CNAME и не принимает суффиксы с чужим DNS (rules-v1 §2.2). У класса 1 вопроса нет: приложение и так выпускается целиком |
| **Суперприложение с WebView в `inside-only`** (подлинное) | весь его трафик, в том числе сайты, открытые во встроенном браузере, идёт через relay целиком — это прокси по любому адресу внутри подлинного приложения | такие записи — только после отдельного ревью списка (rules-v1 §2.2); администратор может включить фильтр и для подтверждённых (§7.1) |

TEE телефона и подпись приложения. Нода решает, кто ходит и куда направлять трафик клиента.

## 16. Цена

- **TLS на relay** — только для трафика, который идёт через вход. Теперь это приложения `inside-only` целиком, с их
  иностранным трафиком. Банки — мало, видео — много: выбирать relay под это. Сколько CPU — не мерили; порядок — как
  у naive на ноде (вывод).
- **Трафик:** каждый байт входа проходит канал relay дважды (от клиента и к назначению), как и при L4.
- **Поток с тегом — один RTT:** клиент ждёт заголовков ответа, прежде чем отдать поток приложению; вход отвечает,
  как только решена политика, до dial (с `niko-ack: 1` — после). Ответа нет за тайм-аут — `fallback`
  (app-attest-v1 §5).
- **Помощник:** проверка подписи ECDSA P-256 на каждое туннельное соединение с app-attest (десятки микросекунд,
  оценка). Подтверждённый трафик идёт через него: лишнее копирование и переключение контекста на каждый кусок
  потока или датаграмму. Это только приложения `inside-only` на relay; TCP — через `splice`, без копии в память
  процесса. Замерить (§20).
- **Адрес хостинга:** некоторые банки не пускают адреса дата-центров. Проверять по каждому сервису; помочь может
  relay у домашнего или мобильного провайдера, но это другой класс хоста.
- **Риск оператора relay** — он становится в своей стране прокси для чужого трафика, а с приложением целиком — и для
  иностранного трафика подтверждённых приложений `inside-only`. **Владелец этот риск принял** (2026-11-16, «делаем»,
  §18). Не юридический совет. Снижает его (вывод): класс 2 выходит только во внутреннее, оба класса — через фильтры
  провайдера relay.
- **Размеры:** память — наборы nft на десятки тысяч префиксов и два процесса; диск — текстовые наборы страны (сотни
  КБ). Хост relay остаётся маленьким (relay-update-remote-v1 §4.4).

## 17. `rayctl` и установка

### 17.1. На хосте relay (root)

```
rayctl relay entry                                  # состояние: off | waiting (<причина>) | on; порт, страна, списки, возраст снимка
rayctl relay entry on [-port N] [-public-addr IP]   # согласие root; проверки; ключи и сертификаты; юниты
rayctl relay entry off                              # выключить, удалить ключи
rayctl relay entry rotate-key [-now]                # смена ключа: плановая или при утечке (§4.2)
rayctl relay entry spare export -o FILE             # копия запасного ключа, унести с хоста
```

`entry on` проверяет до любых изменений:
- это хост relay: пакет, `rayspa` в роли relay, `rayd relay` работает (он держит поток и списки);
- версия relay и выхода знают вход (`ReportEntry` не `Unimplemented`);
- ядро берёт цепочки §9 (`nft -c`), в том числе `@ih` для BitTorrent и наборы с `timeout`, как `rayctl egress` на
  ноде;
- порт свободен по TCP и UDP и годится (§4.1); два UID data plane свободны;
- публичный адрес: на интерфейсе или `-public-addr`; с адресом relay у выхода — совпадает или предупреждение;
- резолвер хоста (§10);
- цепочки ufw или firewalld с политикой drop на входе — предупреждение, как у `rayctl install -relay`.

Затем: текущий и запасной ключи с сертификатами (текущий — 0600, владелец — UID входа; запасной — только root),
политика в файле root, `systemctl enable --now rayd-relay-entry rayd-relay-entry-sock`. Печатает:

```
entry on: port 20443 (TCP and UDP). Open it in the provider's firewall; SPA closes it until the knock.
The exit's admin turns it on too: rayctl relay set -entry on NAME. Attested inside-only apps go out whole;
other clients reach only this country's addresses and the signed inside-only lists.
```

`rayctl status` на relay — цикл `entry`: состояние, причина ожидания, срок списков, возраст снимка, выключатель
§9.2.

### 17.2. На выходе

```
rayctl relay set -entry on|off [-country CC] NAME   # второе согласие; -country — ожидаемая страна;
                                                    # при attest off — предупреждение (ниже)
rayctl relay set -entry-names on|off NAME           # §9.2, по умолчанию off
rayctl relay set -entry-attested whole|filtered NAME   # §7.1, по умолчанию whole
rayctl relay list                                   # + ENTRY: off | relay off | waiting (<причина>) | on ru lists 1042 | silent
rayctl relay ports NAME                             # + строка entry
```

- `relay set -entry on` при выключенном app-attest (`rayctl attest mode off`, по умолчанию) предупреждает: все
  клиенты — неподтверждённые, и «приложение целиком» на relay не случится никогда; включить — `rayctl attest mode
  consider`.
- `relay set -entry`, `-entry-names`, `-entry-attested` — права, как у `relay set` сегодня; аудит
  `relay.entry on|off <имя>`, `relay.entry-names on|off <имя>`, `relay.entry-attested <значение> <имя>`.
  `-entry-names on` печатает цену: фронтинг на CDN (§7.6).
- `rayctl relay ports NAME` получает строку:

  ```
  PROTO    PORTS  NAME   TO          REACHED BY
  tcp+udp  20443  entry  relay host  after the knock
  ```

  В файрволе провайдера перед хостом relay открыть этот порт, TCP и UDP, для всех — как точку замера.
- `rayctl rules enforce add -action relay` берёт страну relay из `rayctl relay list` (rules-v1 §8).

### 17.3. Установка и обновление

- `bootstrap.sh -relay` и `rayctl install -relay` ставят юниты `rayd-relay-entry` и `rayd-relay-entry-sock`, но не
  включают их.
- `rayctl update` на relay обновляет и вход: короткий перерыв, у клиента — `fallback`.
- `rayctl uninstall` убирает юниты, ключи, файлы списков и цепочки по журналу установки.
