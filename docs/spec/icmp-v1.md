# icmp-v1: ping и трассировка через туннель

Статус: **согласован** (2026-11-08): владелец одобрил, клиент прочёл и поправил (темп echo, «слишком большой»,
«запрещено» вместо молчания). После ревью кода провод изменился: «слишком большой» — теперь свой `kind = 4` с MTU,
а не `kind = 3` с `code = 4` (§2, §6). Сервер — raycontrol v0.21.0 (naive), позже niko-server (Hysteria2). Клиент —
Niko. Возможность новая: по правилу проекта выключена по умолчанию, включает root на ноде.

Зачем: ICMP через прокси сейчас не идёт ([15-traffic](../15-traffic.md) §4). На прокси-профилях ping отвечает сам
стек TUN клиента за 0–1 мс, хотя до назначения ничего не дошло, а mtr показывает один хоп. Здесь нода посылает echo
сама, со своим TTL, и возвращает клиенту ответы и ошибки. Пользователь получает:
- настоящий ping: RTT до цели плюс туннель;
- mtr, где первый видимый хоп — нода. Путь телефон → нода скрыт, и это плюс;
- поиск MTU пути (`ping -M do -s …`): нода echo не фрагментирует и говорит, какой пакет проходит.

REALITY и `inner` (через Xray) поддержки не получают. Сначала naive, потом Hysteria2.

## 1. Сигнал

- Параметр `icmp=1` в ссылке naive (позже и Hysteria2), только когда на сервисе включено
  `rayctl service set <naive> icmp=on`. По умолчанию выключено.
- Ссылка получает `icmp=1` сразу, а сервер — после `rayctl apply` (флаг `-icmp` у `rayd naive` в юните). До apply
  поток ICMP сбрасывается: включать стоит вместе, `service set`, затем `apply`.
- Без параметра клиент ICMP на ноду не шлёт. Что он делает с echo на прокси-маршрутах — решает клиент; сейчас стек
  отвечает сам.

## 2. Поток

1. **Открытие.** Поток туннеля к имени `icmp.niko.arpa` (порт любой, клиент шлёт `0`): в naive это CONNECT с
   `Proxy-Authorization` и `Padding`, как обычно, по HTTP/2 или HTTP/3. Один поток на ядро клиента; внутри —
   мультиплекс по `id`.
2. **Версия.** Первый байт от клиента — `1`. Другой — сброс потока. Версия должна прийти за время простоя (§3).
3. Дальше — кадры в обе стороны, все числа big-endian.

**Кадр клиента** (echo):

```
[u8 kind = 1][u8 af = 4 | 6][dst: 4 | 16][u8 ttl, 0 = 64][u16 id][u16 seq][u16 len][payload: len]
```

**Кадр сервера:**

```
[u8 kind][u8 code][u8 af][from: 4 | 16][u16 id][u16 seq][u16 len][payload: len]
```

- `kind`:
  - `1` — echo reply. `from` — назначение. `payload` — данные ответа, как пришли.
  - `2` — time exceeded. `from` — маршрутизатор. `code` — код ICMP (ICMPv6 — его код). `payload` пустой.
  - `3` — destination unreachable. `from` — тот, кто ответил. `code` — код ICMP (ICMPv6 — его код), как пришёл.
    `payload` пустой. IPv4 `code = 4` (fragmentation needed) сюда не попадает никогда: это `kind = 4`.
  - `4` — packet too big. `code = 0`. `payload` — ровно `u16` MTU (`len = 2`), для `af` 4 и 6 одинаково: самый
    большой IP-пакет, который проходит. Бывает трёх видов (ниже).
- `id` и `seq` — те, что прислал клиент.
- Исходный заголовок и 8 байт для цитаты в ICMP-ошибке приложению клиент берёт у себя: у ноды заголовок пакета свой,
  приложению он не нужен.

**Packet too big** (`kind = 4`), MTU всегда в `payload`:
- echo длиннее 1452 байт (`len` больше 1452) — ответ самой ноды: `from` — назначение, MTU — самый большой IP-пакет,
  который нода шлёт: 1480 (1452 + 8 + 20) для IPv4, 1500 (1452 + 8 + 40) для IPv6. Данные такого кадра нода дочитывает
  и не шлёт; поток живёт. Так работает `ping -s 1472` при поиске MTU;
- echo не длиннее 1452, но больше пути ноды (её интерфейс или MTU пути, который ядро уже знает): ядро его не шлёт,
  нода отвечает сама: `from` — назначение, MTU — путь до назначения, как его знает ядро ноды;
- маршрутизатор за нодой ответил IPv4 fragmentation needed (тип 3, код 4) или ICMPv6 Packet Too Big (тип 2): `from` —
  маршрутизатор, MTU — из его сообщения (next-hop MTU; старые маршрутизаторы ставят 0 — так и передаётся).

Клиент сам строит приложению нужное сообщение: для IPv4 fragmentation needed, для IPv6 Packet Too Big.

**Запрещено** — ответ самой ноды: назначение не публичное (§3). `kind = 3`, `from` — назначение из кадра клиента
(`af` тоже его), `code = 13` для IPv4 (communication administratively prohibited), `code = 1` для IPv6 (то же в
ICMPv6). Так ping честно говорит «нельзя», а не ждёт таймаута. Если назначение запрещено и кадр к тому же длиннее
1452 — ответ «запрещено».

## 3. Сервер

**Сокеты.**
- Непривилегированный ICMP: `SOCK_DGRAM`, `IPPROTO_ICMP` и `IPPROTO_ICMPV6`, по одному на поток и семейство; сокет
  семейства открывается с первым echo к нему. Raw-сокеты и `CAP_NET_RAW` не нужны. `SO_BROADCAST` выключен.
- Без фрагментов: `IP_MTU_DISCOVER = IP_PMTUDISC_DO` / `IPV6_MTU_DISCOVER = IPV6_PMTUDISC_DO`. echo больше пути ядро не
  шлёт (`EMSGSIZE`); нода берёт MTU пути у UDP-сокета, подключённого к назначению (`IP_MTU` / `IPV6_MTU`; у
  неподключённого ICMP-сокета его нет), и отвечает `kind = 4` (§2). Такой echo не считается потерянным.
- TTL — `IP_TTL` / `IPV6_UNICAST_HOPS`, ставится перед echo, когда меняется (в сокет пишет один поток выполнения).
- Ошибки — `IP_RECVERR` / `IPV6_RECVERR`, чтение `MSG_ERRQUEUE`: тип, код и `ee_info` (MTU у «too big») из
  `sock_extended_err` (только `SO_EE_ORIGIN_ICMP` / `SO_EE_ORIGIN_ICMP6`), маршрутизатор — `SO_EE_OFFENDER`, назначение
  echo — адрес из `recvmsg`, `seq` — из процитированного echo.
  - IPv4: тип 11 → `kind 2`; тип 3 код 4 → `kind 4`; тип 3 иначе → `kind 3`.
  - IPv6: тип 3 → `kind 2`; тип 2 → `kind 4`; тип 1 → `kind 3`.
  - Остальное (parameter problem, source quench, redirect, локальные ошибки) клиенту не идёт.
- Ошибка, пришедшая на сокет, валит ядру следующий `sendto` своим errno (`sk_err`) — один раз: этот вызов её и
  забирает. Поэтому при отказе с errno (кроме `EAGAIN` и `ENOBUFS`) нода повторяет отправку один раз; настоящий отказ
  (нет маршрута, слишком большой) повторяется, а ложной потери нет. Сама ошибка остаётся в очереди и приходит клиенту.
- Ядро ставит в echo свой `id` (порт сокета), поэтому сервер ставит свой `seq` и помнит, чей он:
  `seq ноды → (id, seq клиента, назначение)`. Счётчик `seq` у потока один на оба семейства, начинается со случайного
  числа (`crypto/rand`) и пропускает номера, что ещё ждут ответа.
- Ответ клиенту идёт, только если `seq` ждёт ответа и назначение совпадает: у echo reply — его источник, у ошибки —
  назначение процитированного echo. Ответ идёт один раз; запись после этого забывается.
- **Маршрутизаторы с частными адресами молчат.** Ошибку (`kind` 2, 3 и 4) от маршрутизатора, которому нода не дала бы
  echo (та же проверка `Public()`, что для назначений: частные сети, CGNAT, loopback, сама нода), нода клиенту не
  передаёт. Такие хопы mtr покажет молчащими. Фильтрует сама нода: `IPAddressDeny=` юнита ошибок не видит — ядро
  кладёт их в очередь ошибок сокета мимо входного фильтра cgroup. Клиент с этим согласен.
- Сокет не открылся (группа вне `ping_group_range`, на ноде нет IPv6) — echo отбрасывается, в журнал раз в минуту
  попадает предупреждение без адресов. Не ушёл (нет маршрута) — echo тоже отбрасывается: клиент считает таймаут.

**Права.**
- Сокеты требуют, чтобы группа процесса попала в `net.ipv4.ping_group_range` (действует и для IPv6).
  - systemd на Debian, Ubuntu и Rocky обычно ставит `0 2147483647` — этого хватает.
  - Если диапазон не покрывает группы data plane (9100–9179; например, `1 0` — ping выключен), `rayctl apply` при
    `icmp=on` расширяет его: пишет `/etc/sysctl.d/10-raycontrol-icmp.conf` с диапазоном, который покрывает и прежний,
    и группы data plane (`1 0` → `9100 9179`, `0 0` → `0 9179`), загружает его и пишет, что было и что стало. Сузить
    диапазон он не может. Значение, которое не читается как диапазон, он не трогает: предупреждает и ничего не
    пишет. Файл остаётся: следующий `apply` видит, что диапазон уже широк. `rayctl uninstall` убирает файл и
    возвращает прежнее значение.
  - Файл называется на `10-`, чтобы идти первым: файлы дистрибутива и администратора, что идут после него, при
    загрузке побеждают. Если они сужают диапазон, `rayctl check` (при `icmp=on` у сервиса) и `apply` предупреждают:
    сокет не откроется (контейнер тоже может не дать диапазон поменять).
- Юнит: `RestrictAddressFamilies=AF_INET AF_INET6` и `@system-service` такие сокеты пускают.
- `IPAddressDeny=` юнита не пускает echo в частные сети (процесс отвечает «запрещено» раньше), но ошибок от
  маршрутизаторов не видит: их фильтрует процесс (выше).

**Правила.**
- Назначения — только публичные unicast, как у TCP и UoT через naive (`Public()`): не сама нода, не loopback, не
  частные сети, не link-local, не CGNAT, не multicast и не broadcast. IPv6 с IPv4 внутри (NAT64, 6to4,
  IPv4-compatible, IPv4-mapped) тоже нельзя. Запрещённое назначение — ответ «запрещено» (§2), поток живёт.
- `ttl` — 1…64; `0` и больше 64 — 64 (Windows шлёт 128 по умолчанию).
- `payload` — не больше 1452 байт. Больше — ответ «packet too big» (§2), поток живёт.
- **Пределы на пользователя:**
  - echo — 30 в секунду, запас 60, во всех его потоках: mtr шлёт по пробе на хоп в секунду, а хопов 15–30. Каждый
    кадр сначала тратит свой токен, и ответы самой ноды тоже: без токена кадр отбрасывается молча, так что ответ ноды
    никогда не обгоняет echo клиента. Запас не восстанавливается закрытием потоков: он копится только со временем.
    Токены пользователя под своим замком: общий замок сервиса берут только открытие и закрытие потока;
  - ожидающих ответа — не больше 64 на поток. Ответа нет 5 с — запись забывается, клиенту ничего не идёт; он
    считает таймаут сам. Ответ позже 5 с тоже не идёт;
  - потоков ICMP — 4 на пользователя и 1024 на сервис.

  Сверх: echo отбрасывается, сверх потоков — сброс.
- **Простой:** две минуты без кадров в обе стороны (по монотонным часам) — поток закрывается чисто. Клиент, который
  перестал читать (окно HTTP/2 или QUIC полно), поток не держит: через секунду после конца простоя запись обрывается,
  поток сбрасывается, как у UoT.
- **Периметр** ничего нового не открывает:
  - echo уходит из data plane наружу;
  - ответ — `established`;
  - time exceeded, unreachable и packet too big — `related`;
  - на ping снаружи нода по-прежнему не отвечает.
- **Журналы:** ни назначений, ни `from`. Только счётчики (на уровне debug, в конце потока: echo, ответы,
  отброшенные).

**Отказы** — сброс потока, как в [naive-uot-v1](naive-uot-v1.md) §4. Для клиента сброс значит «ICMP недоступен»;
другого сигнала нет. Сброс бывает при:
- `icmp=off` на сервисе;
- неверной версии;
- кадре, который нельзя прочесть как кадр: `kind` не `1`, `af` не `4` и не `6`;
- пределе потоков.

## 4. Клиент (для справки, решает клиент)

- ICMP-поток в ядре для профилей с `icmp=1`.
- Ответ `1` — echo reply приложению.
- `2` и `3` — ICMP-ошибка приложению, с цитатой исходного пакета приложения.
- `4` — packet too big: MTU из `payload`; для IPv4 приложению fragmentation needed (тип 3, код 4, next-hop MTU), для
  IPv6 Packet Too Big (тип 2, MTU). Если `from` — назначение, это ответ самой ноды (её предел или путь); если нет —
  маршрутизатор за ней.
- Сброс потока — ICMP недоступен.
- Стек gVisor в sing-tun отдаёт приложению time exceeded и unreachable для IPv4, а для IPv6 — только echo reply.
  mtr по IPv6 потребует патча клиента.

## 5. Версии

- raycontrol v0.21.0: naive (HTTP/2 и HTTP/3), `rayctl service set <naive> icmp=on|off`, `icmp=1` в ссылке,
  расширение `ping_group_range` в `rayctl apply`, проверка в `rayctl check`.
- niko-server: Hysteria2 — следующим шагом, тем же проводом поверх TCP-потока hy2.
- Niko: по `icmp=1`.

## 6. Изменения после ревью кода (до выпуска)

- «Слишком большой» был `kind = 3`, `code = 4` с MTU в `payload`; стал `kind = 4` (§2): у IPv4 код 4 под `kind = 3`
  значил бы и «слишком большой», и fragmentation needed маршрутизатора без MTU. Теперь `kind = 4` несёт MTU всегда и
  приходит и от ноды, и от маршрутизаторов; `kind = 3` — только destination unreachable с кодом как пришёл.
- Нода больше не фрагментирует echo, и echo больше пути — тоже `kind = 4` с MTU пути.
- Ошибки от маршрутизаторов с частными адресами нода отбрасывает сама: `IPAddressDeny=` их, как выяснилось, не видит.
- Отправка после ошибки, которую ядро ещё держит, повторяется один раз: иначе mtr видел ложные потери.
