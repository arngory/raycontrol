# raycontrol: подписка v1

Статус: **заморожен** (R1, вместе с эндпоинтом `/sub/v1`). Несовместимые изменения — только как подписка v2 с новым путём. Эталонная реализация — [`internal/sub`](../../internal/sub). Основа — предложение сессии Niko
([`RAYCONTROL.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/server/RAYCONTROL.md) §6),
решение R1-4 в [`08-decisions.md`](../08-decisions.md).

## 1. Где

- Адрес: `https://<host>:<port>/sub/v1`. `host` — поле `host`, `port` — `sub.port` пакета регистрации ([`spa-v2.md`](spa-v2.md) §8).
- Порт закрыт до SPA, как всё остальное: каждое устройство может открыть его своим SPA-пакетом (подписка входит в scope
  любого устройства).
- TLS 1.3, только `X25519MLKEM768`; классический обмен ключами сервер отклоняет.
- Сертификат самоподписанный. Клиент проверяет его по пину: `sub.pin` = base64url(SHA-256(SubjectPublicKeyInfo)).
  Имя в сертификате не проверяется.
- В R2 эндпоинт переезжает за tcpmux на 443 с сертификатом поддомена; формат запроса и ответа не меняется.

## 2. Запрос

```
GET /sub/v1
X-Raycontrol-Device: <device_id>
Authorization: RC1 <minute>.<mac>
```

- `minute` — `floor(unix_time / 60)` по часам клиента, десятичное число.
- `mac` = base64url(HMAC-SHA256(`device_key`, `"raycontrol-sub-v1 auth"` ‖ BE64(`minute`))).
- Сервер принимает `minute` в пределах ±2 от своей минуты.
- Любая ошибка (неизвестное или отозванное устройство, неверный токен, неактивный пользователь) — `404` с обычным
  текстом, без подробностей.

## 3. Ответ

`200`, `application/json`:

```json
{"payload": "<base64url от JSON payload>", "sig": {"ed25519": "<base64url>", "mldsa65": "<base64url>"}}
```

- Подписываемое сообщение: `"raycontrol-sub-v1"` ‖ байты payload (до base64url).
- Ed25519 и ML-DSA-65 (FIPS 204, пустой контекст). Клиент принимает ответ только если **обе** подписи верны.
- Публичные ключи — `node_keys` пакета регистрации: `ed25519` (hex), `mldsa65` (base64url).

Payload:

```json
{
  "v": 1,
  "node_id": "<32 hex>",
  "seq": 42,
  "time": 1767225600,
  "issued": 1767225600,
  "expires": 1767484800,
  "profiles": [
    {"svc": 3, "name": "dns", "link": "vless://…", "next": {"link": "vless://…", "from": 1767268800}}
  ]
}
```

| Поле | Смысл |
|---|---|
| `seq` | растёт с каждым ответом ноды, в том числе после перезапуска. Клиент хранит последний и отклоняет ответ с меньшим `seq` |
| `time` | время сервера при ответе; клиент сравнивает со своими часами (SPA v2 требует ±30 с, `spa-v2.md` §7) |
| `issued`, `expires` | срок жизни ответа (сейчас 72 ч); после `expires` клиент перезапрашивает подписку |
| `probe` | необязательно (R4-16): `{"v": 1, "udp": true, "report": ["udp_mtu", "path", "dns", "dns_tcp"], "tunnel": "probe.raycontrol.invalid", "tunnel_svc": [...]}`. Эндпоинт отвечает на замеры канала ([`probe-v1.md`](probe-v1.md)); `udp` — есть эхо UDP на том же номере порта; `report` — необязательные поля отчёта, которые нода принимает (raycontrol v0.8, `probe-v1.md` §6.1); `tunnel` — имя, ведущее к замеру изнутри туннелей сервисов `tunnel_svc` |
| `dns_probe` | необязательно (raycontrol v0.11.1): `{"v": 1, "key": "<base64url, 32 байта>"}` — ключ проверки резолвера ([`dnsprobe-v1.md`](dnsprobe-v1.md)); только у пользователя с профилем dnstt (пробы — только в зонах dnstt) |
| `hints` | необязательно (R4-21): начальный порядок профилей для сети, из которой спросили подписку, по сводке от клиентов — `{"order": [...], "avoid": [...], "udp_blocked": bool, "tcp_stall_kib": N, "udp_mtu": "…", "via_relay": bool, "dns": {"dnstt": "…", "masterdns": "…"}, "devices": N, "days": 7}`; только при k ≥ 10 отчётах из этой AS ([`probe-v1.md`](probe-v1.md) §6.2) |
| `spa` | с raycontrol v0.10.1: `{"carriers": ["udp", "tls", "tcp"]}` — носители SPA, которые нода принимает, в порядке, в котором их пробовать: `udp` (§5), `tls` (ClientHello, spa-v2 §10.1), `tcp` (голый, §10). Клиент не пробует то, чего нет. Нет поля — нода старше: UDP, затем ClientHello, затем голый TCP |
| `profiles[].svc` | ID сервиса: идёт в scope SPA |
| `relays` | с raycontrol v0.10.1, если у ноды есть relay с выданным пакетом (relay-v1 §4): `[{"id": "r1", "host": "198.51.100.20", "spa": {…}}]`. `spa` — параметры SPA relay в том же виде, что у ноды в пакете устройства; стучаться к relay ключом `K_relay` (relay-v1 §3). `sub_pin` — с R6-c. Нет поля — relay нет |
| `profiles[].via` | ID relay из `relays`, через которые идёт профиль: та же ссылка, хост — `host` relay, UDP — на 443 (ротации через relay нет). У DNS-туннелей и Yggdrasil `via` нет |
| `profiles[].next` | ротация (R4): после `from` клиент переключается на `next.link`, не разрывая текущие соединения; если `next` не работает — возвращается к `link` до `expires`, а если не работают оба — перезапрашивает подписку. Нода публикует `next` за 3 дня до `from`. Новый UUID (R4-1) нода принимает сразу, прежний — ещё 2 дня после `from`. Новые ключи REALITY (R4-7) нода включает за 2 минуты до `from`, прежние принимает ещё 2 дня после `from` (R4-19); после `rayctl service rotate -now` прежние не принимаются |

## 4. Ссылки

Обычные ссылки протоколов плюс параметры Niko в query (значения URL-кодированы; `;` внутри значения кодируется как `%3B`).

| Параметр | Значение |
|---|---|
| `niko-node` | `node_id` импортированной ноды: профиль получает её SPA v2 и адрес |
| `niko-svc` | ID сервиса для scope SPA |
| `niko-dns` | DNS-туннель: `dnstt;<резолвер>;<зона>;<pubkey hex>` или `masterdns;<резолверы через ,>;<зона>;<метод>` |
| `niko-dnskey` | ключ MasterDnsVPN (текст, как в его файле ключа) |
| `niko-dnsauth` | `v1`: подписывать запросы dnstt ключом устройства ([`dnsauth-v1.md`](dnsauth-v1.md)); нет параметра — не подписывать |
| `niko-pin` | SHA-256 SPKI сертификата (base64url), например для `hy2-obfs` (R3) |
| `niko-inner` | вторая ступень для протоколов с собственной ссылкой (R5) |
| `niko-ygg` | Yggdrasil: `<пир>;<ключ пользователя>` — URI пира и seed ed25519 (hex, 32 байта) (R4-15) |
| `niko-ygg-via` | Yggdrasil, повторяемый: публичный пир ноды — запасной путь через сеть Yggdrasil (R4-18) |

Пустой резолвер означает «выбирает клиент» (резолвер сети, свой список).

**Строгий разбор (Niko 1.26, RAYCONTROL.md §22).** Строку, которая нарушает одно из правил, клиент отбрасывает молча:
- схемы — только `vless://`, `hysteria2://`, `naive+https://`, `naive+quic://` и `https://` для DoH;
- у VLESS есть `encryption`, и это не `none`; у REALITY есть `pqv`;
- параметров `insecure` и `allowInsecure` нет совсем, даже со значением 0;
- `hy2-obfs` — только с `niko-pin`;
- у naive `cert` и `extra-headers` клиент не читает: нода на них не полагается.

Подписка, API и замеры не перенаправляют: ответ 3xx клиент считает ошибкой, и нода на любой такой путь отвечает 404.
Правила проверяет тест `internal/sub` `TestLinksForStrictClient`: ссылки всех видов сервисов и ссылки `next` при
ротации.

Те же ссылки без подписи печатает `rayctl user export NAME` (P-10, R4-17): по строке комментария и ссылке на профиль,
при ожидаемой смене — и следующая ссылка с моментом `from`.

### Профиль DNS-туннеля (R1)

Ссылка — VLESS к внутренней ступени `inner`; носитель — DNS-туннель из `niko-dns`:

```
vless://<uuid>@inner:1?type=raw&encryption=mlkem768x25519plus.native.0rtt.<ключ>&niko-node=<node_id>&niko-svc=3&niko-dns=dnstt%3B%3B<зона>%3B<pubkey>#dns
```

- Хост и порт (`inner:1`) не используются: туннель всегда ведёт в `inner`, произвольных адресов нода не открывает.
- `encryption` — клиентская строка Xray VLESS encryption с ML-KEM-768: постквант для всего, что идёт через туннель.
- Для MasterDnsVPN метод — `5` (AES-256-GCM): нода разрешает только AEAD.
- Ключ устройства в ссылках не передаётся.

### Профиль REALITY (R2)

Стандартная ссылка VLESS + REALITY + Vision (как в Xray) с вторым слоем VLESS encryption и параметрами Niko:

```
vless://<uuid>@<host>:443?type=raw&security=reality&flow=xtls-rprx-vision&encryption=mlkem768x25519plus.native.0rtt.<ключ>
  &sni=<имя>&fp=chrome&pbk=<X25519, base64url>&sid=<shortId>&pqv=<ML-DSA-65, base64url>&niko-node=<node_id>&niko-svc=<id>#reality
```

- `pqv` — открытый ключ ML-DSA-65 (`mldsa65Verify` в Xray, 2603 символа): клиент обязан проверять им подпись
  сертификата REALITY. Без `pqv` профиль не считается постквантовым и клиент его не принимает.
- Ключ обмена — только `X25519MLKEM768` (отпечаток `fp` его предлагает).
- `encryption` — второй слой, VLESS encryption с ML-KEM-768, как у `inner`; `flow` — `xtls-rprx-vision`.
- `sid` у разных пользователей разный (у сервиса несколько shortId), `sni` и цель задаются при создании сервиса.
- Ключи (`pbk`, `pqv`, `encryption`), shortId и, при self-steal, `sni` меняются раз в эпоху (R4-7): новый набор
  приходит в `next`; новое `sni` — всегда поддомен домена ноды.
- Порт — 443 (или порт сервиса из настроек, пока REALITY слушает сам, без фронта: решение R2-7).
- Пользователи добавляются и удаляются через API Xray без перезапуска, как у `inner`.

### Профиль Hysteria2 (R3)

Стандартная ссылка Hysteria2 с параметрами Niko:

```
hysteria2://<пароль>@<host>:<порт>/?sni=<имя>&niko-node=<node_id>&niko-svc=<id>#hy2-masq
hysteria2://<пароль>@<host>:<порт>/?sni=<имя>&obfs=salamander&obfs-password=<пароль salamander>
  &niko-pin=<SPKI SHA-256, base64url>&pinSHA256=<SHA-256 сертификата, hex>&niko-node=<node_id>&niko-svc=<id>#hy2-obfs
```

- `hy2-masq`: UDP 443, сертификат от CA на `sni` (поддомен ноды); проверка обычная.
- `hy2-obfs`: тоже UDP 443 (фронт отличает его по salamander, R3-4), самоподписанный сертификат на `sni` (имя вне DNS). Niko пинит ключ по
  `niko-pin`; `pinSHA256` — для сторонних клиентов.
- TLS 1.3, только `X25519MLKEM768`. Пароль — учётные данные пользователя с ротацией: новый приходит в `next`.
- У обоих сервисов ротация UDP-портов: `services[].port_key` в пакете регистрации, как у остальных сервисов на UDP.

### Профиль DoH (R3)

```
https://<имя>/dns-query/<токен>?niko-node=<node_id>&niko-svc=<id>#doh
```

- Параметры `niko-*` клиент отбрасывает и спрашивает `https://<имя>/dns-query/<токен>` (RFC 8484, GET `?dns=` или
  POST `application/dns-message`) по TCP 443 ноды после SPA; `<имя>` — поддомен ноды под её сертификатом.
- TLS 1.3, только `X25519MLKEM768`, h2. Токен — учётные данные с ротацией: новый приходит в `next`.
- DoH3: тот же URL по HTTP/3 на UDP 443 (R3-5).

### Профиль naive (R2)

```
naive+https://niko:<пароль>@<адрес ноды>:443?sni=<имя>&niko-node=<node_id>&niko-svc=<id>#naive
```

- В хосте — адрес ноды, как у `hysteria2://` и `vless://`; `<имя>` — поддомен ноды под её сертификатом, он идёт в
  SNI. Клиенту не нужен DNS-запрос имени в своей сети, и ноду он находит по адресу. До raycontrol v0.11.1 в хосте было
  имя, а `sni` не было; Niko берёт `sni` у naive во всех версиях.
- HTTP/2 CONNECT к адресу ноды на TCP 443 после SPA, TLS с SNI `<имя>`,
  `Proxy-Authorization: Basic` с этими именем и паролем, заголовок `Padding` и паддинг первых 8 кадров в каждую
  сторону — как у NaiveProxy. Сервер проверяет только пароль.
- TLS 1.3, только `X25519MLKEM768`. Пароль — учётные данные с ротацией: новый приходит в `next`.
- Без пароля, с неверным или без паддинга сервер отвечает как сайт (пустой `404`), а не `407`.
- naive-quic: тот же адрес по UDP 443 (HTTP/3, QUIC v1 с `X25519MLKEM768`), те же имя и пароль — `naive+quic://` с
  теми же параметрами; фронт отдаёт по имени из QUIC Initial (R3-5).

### Профиль Yggdrasil (R4)

Ссылка — VLESS к `inner` на адресе ноды в сети Yggdrasil; носитель — Yggdrasil с одним пиром, самой нодой:

```
vless://<uuid>@[<адрес ноды в Yggdrasil>]:<порт выхода>?type=raw&encryption=mlkem768x25519plus.native.0rtt.<ключ>
  &niko-node=<node_id>&niko-svc=<id>&niko-ygg=tls%3A%2F%2F<имя>%3A443%3Fkey%3D<ключ ноды>%26sni%3D<имя>%3B<seed>#ygg
```

- **Пир** — `tls://<имя>:443?key=<ключ ноды>&sni=<имя>`:
  - `<имя>` — поддомен ноды под сертификатом её сайта, TCP 443 после SPA;
  - `key` — открытый ключ ed25519 ноды в Yggdrasil (hex), клиент закрепляет его (`pinnedEd25519Keys` в yggdrasil-go);
  - сертификат TLS не проверяется: Yggdrasil проверяет ключ сам. TLS 1.3, только `X25519MLKEM768`;
  - по умолчанию других пиров у профиля нет: подключение только прямое (P-14).
- **Публичные пиры** (R4-18) — `niko-ygg-via`, по одному на параметр, если у ноды они включены. Клиент берёт их,
  только когда прямой пир не подключается, и идёт к тому же адресу и порту через сеть Yggdrasil. Узел клиента
  входящих не принимает. Постквант на таком линке не гарантирован; `inner` с `encryption` остаётся.
  Пиры `quic://` — только с IP-адресом: имя yggdrasil-go резолвит сам, системным резолвером, мимо DNS клиента
  (просьба клиента, RAYCONTROL.md §15.2). Нода не принимает `quic://` с именем, а такие, заданные раньше, в ссылку
  не попадают.
- **Ключ пользователя** — seed ed25519 (hex, 32 байта), закрытый ключ узла клиента. Он выводится из UUID в ссылке,
  поэтому в `next` приходит новая пара: UUID и ключ. Нода принимает оба набора так же, как UUID в `inner` (R4-1).
- **Адрес и порт.**
  - Адрес — адрес ноды в Yggdrasil (`200::/7`), он выводится из `key`.
  - Порт выхода случаен для каждой ноды; на остальные порты нода отвечает сбросом, UDP не принимает.
  - Через Yggdrasil к этому адресу и порту клиент идёт VLESS с `encryption`, как в профиле DNS-туннеля. Сквозное
    шифрование Yggdrasil классическое, поэтому постквант даёт линк и `inner`.
- **Что не линк Yggdrasil**, получает от `<имя>` ответ сайта: пустой `404` по h2 или HTTP/1.1.

## 5. Проверки в клиенте (порядок)

1. TLS: `X25519MLKEM768`, пин SPKI.
2. Обе подписи.
3. `node_id` совпадает с импортированной нодой.
4. `seq` не меньше сохранённого; `expires` в будущем.
5. `time` против своих часов: при расхождении больше 30 с — предупредить пользователя.
