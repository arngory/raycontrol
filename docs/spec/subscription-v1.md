# raycontrol: подписка v1

Статус: **заморожен** (R1, вместе с эндпоинтом `/sub/v1`). Несовместимые изменения — только как подписка v2 с новым путём. Эталонная реализация — [`internal/sub`](../../internal/sub). Основа — предложение сессии Niko
([`RAYCONTROL.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/server/RAYCONTROL.md) §6),
решение R1-4 в [`08-decisions.md`](../08-decisions.md).

## 1. Где

- Адрес: `https://<host>:<port>/sub/v1`. `host` — поле `host`, `port` — `sub.port` пакета регистрации ([`spa-v2.md`](spa-v2.md) §8).
- Порт закрыт до SPA, как всё остальное: каждое устройство может открыть его своим SPA-пакетом (подписка входит в scope
  любого устройства).
- TLS 1.3, только `X25519MLKEM768`; классический обмен ключами сервер отклоняет.
- Сертификат самоподписанный. Клиент проверяет его по пину: `sub.pin` = base64url(SHA-256(SubjectPublicKeyInfo)).
  Имя в сертификате не проверяется.
- В R2 эндпоинт переезжает за tcpmux на 443 с сертификатом поддомена; формат запроса и ответа не меняется.

## 2. Запрос

```
GET /sub/v1
X-Raycontrol-Device: <device_id>
Authorization: RC1 <minute>.<mac>
X-Raycontrol-LAN: on|off
```

- `minute` — `floor(unix_time / 60)` по часам клиента, десятичное число.
- `mac` = base64url(HMAC-SHA256(`device_key`, `"raycontrol-sub-v1 auth"` ‖ BE64(`minute`))).
- Сервер принимает `minute` в пределах ±2 от своей минуты.
- `X-Raycontrol-LAN` — необязательно (raycontrol v0.23.0): согласие устройства на локальную сеть пользователя
  ([`lan-v1.md`](lan-v1.md) §1.1). `on` — показывать это устройство остальным устройствам пользователя, `off` — не
  показывать; регистр и пробелы по краям не важны. Нода хранит последнее значение и пишет только смену, после проверки
  `Authorization` и до ответа, который уже следует ему: `off` — сразу, `on` — не раньше чем через минуту после
  предыдущей смены (иначе устройство остаётся скрытым до запроса после этой минуты). Нет заголовка или другое значение —
  ничего не меняется: клиент, который его не шлёт, в список не попадает никогда. Нода старше заголовок не читает.
- Любая ошибка (неизвестное или отозванное устройство, неверный токен, неактивный пользователь) — `404` с обычным
  текстом, без подробностей.

## 3. Ответ

`200`, `application/json`:

```json
{"payload": "<base64url от JSON payload>", "sig": {"ed25519": "<base64url>", "mldsa65": "<base64url>"}}
```

- Подписываемое сообщение: `"raycontrol-sub-v1"` ‖ байты payload (до base64url).
- Ed25519 и ML-DSA-65 (FIPS 204, пустой контекст). Клиент принимает ответ только если **обе** подписи верны.
- Публичные ключи — `node_keys` пакета регистрации: `ed25519` (hex), `mldsa65` (base64url).

Payload:

```json
{
  "v": 1,
  "node_id": "<32 hex>",
  "name": "Амстердам",
  "seq": 42,
  "time": 1767225600,
  "issued": 1767225600,
  "expires": 1767484800,
  "profiles": [
    {"svc": 3, "name": "dns", "link": "vless://…", "next": {"link": "vless://…", "from": 1767268800}}
  ]
}
```

| Поле | Смысл |
|---|---|
| `name` | необязательно (raycontrol v0.15.0): имя ноды (`rayctl install -name`, `rayctl node name`), клиент показывает его рядом с адресом. Нет поля — у ноды нет имени. Нода принимает только буквы, знаки (M), цифры, пунктуацию, символы и пробелы: пробелы схлопываются в один U+0020 и обрезаются по краям, длина — 1–48 code points; управляющие и format-символы (в том числе U+200D, U+202E), private use, неназначенные, U+2028/U+2029, невидимые (Default_Ignorable: заполнители хангыля, U+034F), селекторы вариантов (кроме U+FE0E/U+FE0F после символа), знак (M) в начале или после пробела и больше 4 знаков на одном символе — отказ. Имя справа налево допустимо: клиент показывает его в изоляте (FSI…PDI), чтобы оно не меняло порядок с адресом. Клиент всё равно чистит имя сам (Niko: Cc, Cf, private use, неназначенные, обрезка до 48) |
| `note` | необязательно (raycontrol v0.21.0): описание ноды от её владельца для пользователей (`rayctl node note`), одна строка простого текста, до 200 code points. Нет поля — описания нет. Правила — как у `name`, и ещё пропускаются то, что нужно эмодзи и письменностям: U+200C и U+200D только между двумя символами (👨‍👩‍👧, персидский), теги U+E0020–U+E007E только после U+1F3F4 и закрытые U+E007F (флаги Англии, Шотландии, Уэльса). Эмодзи-последовательность считается всеми своими code points. Клиент показывает текст как простой: без разметки и ссылок, в изоляте (FSI…PDI), переносом по словам, не обрезая молча; чистит его сам так же, как `name` |
| `seq` | растёт с каждым ответом ноды, в том числе после перезапуска. Клиент хранит последний и отклоняет ответ с меньшим `seq`. С raycontrol v0.15.0 `seq` не меньше времени ноды в миллисекундах (через 10 минут после старта rayd: обновление, которое откатывается в первые минуты, возвращает базу старой версии со старым счётчиком) (число вырастает до ~1,8·10¹², в пределах 2⁵³): база, возвращённая откатом обновления или `rayctl restore`, не откатывает его ниже ответов, которые клиенты уже видели |
| `time` | время сервера при ответе; клиент сравнивает со своими часами (SPA v2 требует ±30 с, `spa-v2.md` §7) |
| `issued`, `expires` | срок жизни ответа (сейчас 72 ч; у пользователя сверх лимита — до часа, см. `traffic`); после `expires` клиент перезапрашивает подписку |
| `traffic` | необязательно (raycontrol v0.22.0), только у пользователя с лимитом трафика ([`traffic-limit-v1.md`](traffic-limit-v1.md) §4): `{"v": 1, "used": 12884901888, "limit": 53687091200, "since": 1767225600, "reset": 1769904000}`. `used` — `up + down` с `since` в байтах (нода пишет счёт раз в минуту), `limit` — байты, `since` — начало периода, `reset` — следующий сброс (`0` — период `none`, только администратор). У снятого по лимиту ещё `"exhausted": true`: решает нода, клиент не сравнивает `used` и `limit` сам. Тогда ответ `200` с `"profiles": []` (не `404`, как у выключенного и просроченного), а `expires` — не позже `reset` плюс до 10 минут случайно и не дальше часа: клиент сам узнает о сбросе или поднятом лимите. Строки профилей ноды клиент при `exhausted` сохраняет. Нет поля — у пользователя нет лимита или нода старше |
| `lan` | необязательно (raycontrol v0.23.0): локальная сеть устройств пользователя через Yggdrasil ([`lan-v1.md`](lan-v1.md) §1.2): `{"v": 1, "svc": 7, "relay": 20, "label": "ams", "password": "<base64url, 32 байта>", "next": {"password": "…", "from": 1767268800}, "devices": [{"id": "<16 hex>", "name": "work.laptop", "label": "work-laptop", "addr": "201:…", "next": {"addr": "203:…", "from": 1767268800}}]}`. Только у пользователя, которому администратор её включил (`rayctl user lan NAME on`), с профилем Yggdrasil: `svc` — его сервис, `relay` — потолок связи устройство—устройство через ноду, Мбит/с на пользователя (`0` — только напрямую в одной Wi-Fi), `label` — метка DNS ноды. `password`, `next` и `devices` — только устройству, которое показало себя (`X-Raycontrol-LAN: on`, §2); `devices` — показавшие себя неотозванные устройства пользователя, это тоже, по `id`; `addr` — адрес Yggdrasil текущего ключа устройства, `next` — следующего ключа и пароля с переходом UUID (тот же `from`, что у `profiles[].next`). Имени пользователя, его ключа, скрытых, отозванных и чужих устройств в поле нет. Внутри `v` = 1 появляются только новые необязательные поля; неизвестную `v` клиент пропускает целиком. Нет поля — не включено, нет профиля Yggdrasil или нода старше |
| `probe` | необязательно (R4-16): `{"v": 1, "udp": true, "report": ["udp_mtu", "path", "dns", "dns_tcp"], "tunnel": "probe.raycontrol.invalid", "tunnel_svc": [...]}`. Эндпоинт отвечает на замеры канала ([`probe-v1.md`](probe-v1.md)); `udp` — есть эхо UDP на том же номере порта; `report` — необязательные поля отчёта, которые нода принимает (raycontrol v0.8, `probe-v1.md` §6.1); `tunnel` — имя, ведущее к замеру изнутри туннелей сервисов `tunnel_svc` |
| `dnsauth` | необязательно (raycontrol v0.15.0): `{"v": [1, 2]}` — версии dnsauth, которые нода берёт на DNS-туннелях пользователя с проверкой меток ([`dnsauth-v2.md`](dnsauth-v2.md) §4). Клиент, который знает v2 и видит `2`, подписывает по v2, иначе — по v1 (`niko-dnsauth=v1` в ссылке по-прежнему значит «подписывать»). `1` нет, если у одного из туннелей `auth_hint=required`; `2` нет, если у одного из них `auth_hint=off`; когда туннели расходятся в обе стороны — только `2`. Нет поля — нет таких туннелей или нода старше (только v1) |
| `app` | необязательно (raycontrol v0.18.0): `{"niko": [{"tag": "v1.38.0", "prerelease": false}, …]}` — релизы Niko, которые нода держит целиком и отдаёт по `/app/v1/niko/<tag>/<имя>` на этом же порту ([`app-update-v1.md`](app-update-v1.md)); не больше двух, стабильный первым. Нет поля — зеркало выключено (по умолчанию), ещё пусто или нода старше |
| `dns_probe` | необязательно (raycontrol v0.11.1): `{"v": 1, "key": "<base64url, 32 байта>"}` — ключ проверки резолвера ([`dnsprobe-v1.md`](dnsprobe-v1.md)); только у пользователя с профилем dnstt (пробы — только в зонах dnstt) |
| `hints` | необязательно (R4-21): начальный порядок профилей для сети, из которой спросили подписку, по сводке от клиентов — `{"order": [...], "avoid": [...], "udp_blocked": bool, "tcp_stall_kib": N, "udp_mtu": "…", "via_relay": bool, "dns": {"dnstt": "…", "masterdns": "…"}, "devices": N, "days": 7}`; только при k ≥ 10 отчётах из этой AS ([`probe-v1.md`](probe-v1.md) §6.2) |
| `spa` | с raycontrol v0.10.1: `{"carriers": ["udp", "tls", "tcp"]}` — носители SPA, которые нода принимает, в порядке, в котором их пробовать: `udp` (§5), `tls` (ClientHello, spa-v2 §10.1), `tcp` (голый, §10). Клиент не пробует то, чего нет. Нет поля — нода старше: UDP, затем ClientHello, затем голый TCP |
| `profiles[].svc` | ID сервиса: идёт в scope SPA |
| `relays` | с raycontrol v0.10.1, если у ноды есть relay с выданным пакетом (relay-v1 §4): `[{"id": "r1", "host": "198.51.100.20", "spa": {…}}]`. `spa` — параметры SPA relay в том же виде, что у ноды в пакете устройства; стучаться к relay ключом `K_relay` (relay-v1 §3). `sub_pin` — с R6-c. Нет поля — relay нет |
| `profiles[].via` | ID relay из `relays`, через которые идёт профиль: та же ссылка, хост — `host` relay, UDP — на 443 (ротации через relay нет). У DNS-туннелей и Yggdrasil `via` нет |
| `profiles[].next` | ротация (R4): после `from` клиент переключается на `next.link`, не разрывая текущие соединения; если `next` не работает — возвращается к `link` до `expires`, а если не работают оба — перезапрашивает подписку. Нода публикует `next` за 3 дня до `from`. Новый UUID (R4-1) нода принимает сразу, прежний — ещё 2 дня после `from`. Новые ключи REALITY (R4-7) нода включает за 2 минуты до `from`, прежние принимает ещё 2 дня после `from` (R4-19); после `rayctl service rotate -now` прежние не принимаются. У naive (raycontrol с v0.29.0, R4-42) `next` может нести новое имя: та же строка с другим `sni` (и следующим паролем, если он уже опубликован), остальное — `niko-pin`, параметры, адрес — то же; клиент берёт строку целиком, нового поля нет. Нода обслуживает новое имя ещё до публикации (`next` можно пробовать раньше `from`), а прежнее — до следующей смены имени, а не 2 дня: устройство, не забравшее подписку после публикации, работает на `link`. В одном `next` — ближайшая смена, имени или пароля |

## 4. Ссылки

Обычные ссылки протоколов плюс параметры Niko в query (значения URL-кодированы; `;` внутри значения кодируется как `%3B`).

| Параметр | Значение |
|---|---|
| `niko-node` | `node_id` импортированной ноды: профиль получает её SPA v2 и адрес |
| `niko-svc` | ID сервиса для scope SPA |
| `niko-dns` | DNS-туннель: `dnstt;<резолвер>;<зона>;<pubkey hex>` или `masterdns;<резолверы через ,>;<зона>;<метод>` |
| `niko-dnskey` | ключ MasterDnsVPN (текст, как в его файле ключа) |
| `niko-dnsauth` | `v1`: подписывать запросы ключом устройства — dnstt ([`dnsauth-v1.md`](dnsauth-v1.md)), с raycontrol v0.14.0 и masterdns ([`dnsauth-masterdns.md`](dnsauth-masterdns.md)); K для ID сервиса из `niko-svc`; нет параметра — не подписывать |
| `niko-dnsseal` | dnstt: `v1;<ключ base64url>` — печать обвязки ([`dnsseal-v1.md`](dnsseal-v1.md), raycontrol v0.13.0); нет параметра — печать выключена |
| `niko-mdseal` | masterdns (raycontrol v0.14.0): `v1` — нода печатает ответы тем, кто просит (`optional`), `v1;required` — только запечатанные, открытые отбрасывать ([`mdseal-v1.md`](mdseal-v1.md)); ключ — `niko-dnskey`; нет параметра — печать выключена |
| `niko-dns-spare` | dnstt и masterdns (raycontrol v0.14.0): запасные зоны того же туннеля через `,`, до 4, в порядке перебора ([`dnszones-v1.md`](dnszones-v1.md)); ключи, печать и метка — как у основной |
| `niko-pin` | пин сертификата: base64url без дополнения от SHA-256 над `SubjectPublicKeyInfo` листа, 32 байта. У `hy2-obfs` — один, его самоподписанного сертификата (R3). У naive, `hy2-masq` и DoH (raycontrol с v0.26.0, [`cert-pin-v1.md`](cert-pin-v1.md)) — список через `,` (в URL — `%2C`) из двух или трёх пинов: первый — ключ листа сайта ноды, затем следующий ключ и, час после смены ключа, прежний. Есть параметр — лист должен иметь один из этих ключей; список, который не читается, — строка отбрасывается целиком; нет параметра — проверяется только цепочка, как раньше. У строки naive с пинами всегда есть `sni` |
| `niko-inner` | вторая ступень для протоколов с собственной ссылкой (R5) |
| `niko-ygg` | Yggdrasil: `<пир>;<ключ устройства>` — URI пира и seed ed25519 (hex, 32 байта) (R4-15). С v0.20.1 ключ у каждого устройства свой, из его SPA-ключа и UUID (у `rayctl user export` — ключ пользователя, из одного UUID): два устройства с одним ключом забирают линки друг у друга. Нода пускает и ключ пользователя, пока есть экспорт и старые подписки: отозванное устройство теряет свой ключ сразу, а доступ по ключу пользователя — со сменой UUID (на прямом пути его держит SPA) |
| `niko-ygg-via` | Yggdrasil, повторяемый: публичный пир ноды — запасной путь через сеть Yggdrasil (R4-18) |

Пустой резолвер означает «выбирает клиент» (резолвер сети, свой список).

**Строгий разбор (Niko 1.26, RAYCONTROL.md §22).** Строку, которая нарушает одно из правил, клиент отбрасывает молча:
- схемы — только `vless://`, `hysteria2://`, `naive+https://`, `naive+quic://` и `https://` для DoH;
- у VLESS есть `encryption`, и это не `none`; у REALITY есть `pqv`;
- параметров `insecure` и `allowInsecure` нет совсем, даже со значением 0;
- `hy2-obfs` — только с `niko-pin`;
- у naive `cert` и `extra-headers` клиент не читает: нода на них не полагается.

Подписка, API и замеры не перенаправляют: ответ 3xx клиент считает ошибкой, и нода на любой такой путь отвечает 404.
Правила проверяет тест `internal/sub` `TestLinksForStrictClient`: ссылки всех видов сервисов и ссылки `next` при
ротации, в том числе `next` naive с новым именем и следующим паролем. Он же проверяет вид `niko-pin` и то, что
параметр есть только в строках Hysteria2, naive и DoH.

Те же ссылки без подписи печатает `rayctl user export NAME` (P-10, R4-17): по строке комментария и ссылке на профиль,
при ожидаемой смене — и следующая ссылка с моментом `from`.

### Профиль DNS-туннеля (R1)

Ссылка — VLESS к внутренней ступени `inner`; носитель — DNS-туннель из `niko-dns`:

```
vless://<uuid>@inner:1?type=raw&encryption=mlkem768x25519plus.native.0rtt.<ключ>&niko-node=<node_id>&niko-svc=3&niko-dns=dnstt%3B%3B<зона>%3B<pubkey>#dns
```

- Хост и порт (`inner:1`) не используются: туннель всегда ведёт в `inner`, произвольных адресов нода не открывает.
- `encryption` — клиентская строка Xray VLESS encryption с ML-KEM-768: постквант для всего, что идёт через туннель.
- Для MasterDnsVPN метод — `5` (AES-256-GCM): нода разрешает только AEAD.
- Ключ устройства в ссылках не передаётся.

### Профиль REALITY (R2)

Стандартная ссылка VLESS + REALITY + Vision (как в Xray) с вторым слоем VLESS encryption и параметрами Niko:

```
vless://<uuid>@<host>:443?type=raw&security=reality&flow=xtls-rprx-vision&encryption=mlkem768x25519plus.native.0rtt.<ключ>
  &sni=<имя>&fp=chrome&pbk=<X25519, base64url>&sid=<shortId>&pqv=<ML-DSA-65, base64url>&niko-node=<node_id>&niko-svc=<id>#reality
```

- `pqv` — открытый ключ ML-DSA-65 (`mldsa65Verify` в Xray, 2603 символа): клиент обязан проверять им подпись
  сертификата REALITY. Без `pqv` профиль не считается постквантовым и клиент его не принимает.
- Ключ обмена — только `X25519MLKEM768` (отпечаток `fp` его предлагает).
- `encryption` — второй слой, VLESS encryption с ML-KEM-768, как у `inner`; `flow` — `xtls-rprx-vision`.
- `sid` у разных пользователей разный (у сервиса несколько shortId), `sni` и цель задаются при создании сервиса.
- Ключи (`pbk`, `pqv`, `encryption`), shortId и, при self-steal, `sni` меняются раз в эпоху (R4-7): новый набор
  приходит в `next`; новое `sni` — всегда поддомен домена ноды. С raycontrol v0.29.0 `sni` по расписанию меняется
  только под wildcard-сертификатом ноды, иначе — только при смене по команде (R4-42); ключи и shortId — как прежде.
- Порт — 443 (или порт сервиса из настроек, пока REALITY слушает сам, без фронта: решение R2-7).
- Пользователи добавляются и удаляются через API Xray без перезапуска, как у `inner`.

### Профиль Hysteria2 (R3)

Стандартная ссылка Hysteria2 с параметрами Niko:

```
hysteria2://<пароль>@<host>:<порт>/?sni=<имя>[&niko-pin=<пин листа>%2C<пин следующего ключа>]
  &niko-node=<node_id>&niko-svc=<id>&niko-ack=1#hy2-masq
hysteria2://<пароль>@<host>:<порт>/?sni=<имя>&obfs=salamander&obfs-password=<пароль salamander>
  &niko-pin=<SPKI SHA-256, base64url>&pinSHA256=<SHA-256 сертификата, hex>&niko-node=<node_id>&niko-svc=<id>&niko-ack=1#hy2-obfs
```

- `hy2-masq`: UDP 443, сертификат от CA на `sni` (поддомен ноды). С `niko-pin` (raycontrol с v0.26.0,
  [cert-pin-v1](cert-pin-v1.md)) лист должен иметь один из ключей списка: ключ сертификата сайта в работе, следующий
  или, час после смены, прежний (в примерах показаны два); `pinSHA256` у него нет. Без параметра (нода до этой
  версии, свой сертификат оператора) проверка обычная, по цепочке.
- `hy2-obfs`: тоже UDP 443 (фронт отличает его по salamander, R3-4), самоподписанный сертификат на `sni` (имя вне DNS). Niko пинит ключ по
  `niko-pin`; `pinSHA256` — для сторонних клиентов.
- TLS 1.3, только `X25519MLKEM768`. Пароль — учётные данные пользователя с ротацией: новый приходит в `next`.
- `niko-ack=1` (с v0.21.0, niko-server v0.14.1): нода отвечает на TCP-поток сразу после dial, не дожидаясь первых байт
  назначения, а при неудаче — с причиной (refused, no route, no such host, lookup failed, not allowed, timeout,
  unreachable). Клиент может держать SYN-ACK приложению до ответа ноды. Без параметра так делать нельзя: старая нода
  ждёт данных назначения, а приложение, где первым говорит клиент (HTTP, TLS), ждёт SYN-ACK.
- У обоих сервисов ротация UDP-портов: `services[].port_key` в пакете регистрации, как у остальных сервисов на UDP.

### Профиль DoH (R3)

```
https://<имя>/dns-query/<токен>?niko-node=<node_id>&niko-svc=<id>[&niko-pin=<пин листа>%2C<пин следующего ключа>]#doh
```

- Параметры `niko-*` клиент отбрасывает и спрашивает `https://<имя>/dns-query/<токен>` (RFC 8484, GET `?dns=` или
  POST `application/dns-message`) по TCP 443 ноды после SPA; `<имя>` — поддомен ноды под её сертификатом.
- `niko-pin` (raycontrol с v0.26.0, [cert-pin-v1](cert-pin-v1.md)) — пины ключа листа и следующего ключа
  сертификата сайта, как у `hy2-masq`; Niko 1.45.0 в этой строке его не читает.
- TLS 1.3, только `X25519MLKEM768`, h2. Токен — учётные данные с ротацией: новый приходит в `next`.
- DoH3: тот же URL по HTTP/3 на UDP 443 (R3-5).
- **Токен — устройства** (raycontrol v0.27.0, R4-37). У каждого устройства свой: HMAC-SHA256 с ключом SPA
  устройства от секрета DoH пользователя с меткой `raycontrol-doh-device-v1`, первые 16 байт записаны как UUID v4.
  Вид строки прежний: та же схема, тот же путь `/dns-query/<36 символов>`, те же параметры и `niko-pin`. Клиент
  токен не вычисляет, а берёт из строки как есть. `next` несёт следующий токен этого же устройства. Секрет
  пользователя в строки больше не попадает. В `rayctl user export` строки DoH нет: устройства, для которого делать
  токен, там нет.
- **Прежний токен пользователя после обновления.** Подписки до v0.27.0 несли всем устройствам один токен —
  секрет пользователя. Нода, у которой при обновлении (миграция 0015) был DoH, принимает его ещё 72 ч — срок жизни
  подписки (§3): за это время каждое включённое устройство берёт подписку со своим токеном. Отзыв любого устройства
  пользователя в эти 72 ч сразу закрывает этот токен для всего пользователя: отозванное устройство его знало.
  Устройства, ещё не взявшие подписку, тогда получают на него быстрый `404` (ниже) и берут подписку.
- **Что отвечает нода.** Принятый токен — ответ DNS. Чужой путь и неизвестный токен — ответ сайта, как у naive
  (R3-2); у `silent` это удержание до минуты и сброс потока. Токен, который нода принимала и перестала принимать
  не больше 10 минут назад (отозванное устройство, прежний после смены, токен пользователя после окна), получает
  сразу пустой `404`, без ответа DNS, по h2 и по h3 одинаково: устройство с таким токеном не ждёт минуту, а сразу
  видит отказ и берёт подписку. Нода держит не токены, а первые 16 байт их SHA-256, не больше 8192; самые старые
  уходят первыми и дальше получают ответ сайта. Пока нода не может прочитать токены из своей базы, `404` сразу
  получает запрос, в пути которого есть сегмент вида токена (36 символов, как UUID), — и с верным токеном, и с
  чужим; остальные запросы — ответ сайта, как всегда.
- **Когда токены перечитываются** (raycontrol v0.27.0). Нода читает их в фоне: раз в 30 с, и после каждого
  изменения своего состояния (отзыв, замена данных, пользователь выключен). Запросы не ждут чтения, кроме одного
  случая: после изменения запрос с токеном (сегмент после `/dns-query/` вида токена: 36 символов, как UUID; других
  токенов у ноды не бывает) не получает ответа по токенам, прочитанным до него, — он ждёт чтения, начатого после
  изменения, не дольше 5 с (10 с, если перед ним шло ещё одно), а дальше получает быстрый `404`. Изменение
  отмечается в том же вызове, что его сделал, до ответа API: когда `RevokeDevice` ответил, следующий же запрос с
  токеном отозванного устройства не принимается. Любой другой запрос не ждёт никогда, и по его времени не видно,
  что состояние ноды менялось. Чтение после изменения начинается сразу; изменения, пришедшие во время чтения или
  чаще, дают одно следующее чтение, а не по одному на каждое, и оно начинается сразу, только если его ждёт запрос,
  иначе через 200 мс после конца прошлого: поток изменений без запросов DoH стоит одного чтения на 200 мс.
- **Почему `404`, а не сброс потока.** Статус клиент читает однозначно: запрос дошёл, токен не принят. Сброс
  (`RST_STREAM` по h2, отмена потока с `H3_INTERNAL_ERROR` по h3) сетевой стек может принять за сбой транспорта и
  повторить запрос, в том числе по другому протоколу, а проверка в клиенте — за временную ошибку. Пустой `404` —
  тот же ответ, что у сайта в режиме `404`; отличить его от ответа сайта может только тот, кто держит токен,
  принятый несколько минут назад, а не любой, кто спросит `/dns-query/что-угодно`.

### Профиль naive (R2)

```
naive+https://niko:<пароль>@<адрес ноды>:443?sni=<имя>&niko-node=<node_id>&niko-svc=<id>&uot=2[&icmp=1]&niko-ack=1
  [&niko-pin=<пин листа>%2C<пин следующего ключа>]#naive
```

- `niko-pin` (raycontrol с v0.26.0, [cert-pin-v1](cert-pin-v1.md)) — пины ключа листа и следующего ключа
  сертификата сайта, как у `hy2-masq`: лист с другим ключом клиент не принимает, какой бы CA его ни подписал, а
  цепочку Chromium проверяет по-прежнему. Niko 1.45.0 в этой строке параметр не читает. Для `naive+quic://` пины те
  же.
- В хосте — адрес ноды, как у `hysteria2://` и `vless://`; `<имя>` — поддомен ноды под её сертификатом, он идёт в
  SNI. Клиенту не нужен DNS-запрос имени в своей сети, и ноду он находит по адресу. До raycontrol v0.11.1 в хосте было
  имя, а `sni` не было; Niko берёт `sni` у naive во всех версиях.
- HTTP/2 CONNECT к адресу ноды на TCP 443 после SPA, TLS с SNI `<имя>`,
  `Proxy-Authorization: Basic` с этими именем и паролем, заголовок `Padding` и паддинг первых 8 кадров в каждую
  сторону — как у NaiveProxy. Сервер проверяет только пароль.
- TLS 1.3, только `X25519MLKEM768`. Пароль — учётные данные с ротацией: новый приходит в `next`.
- Имя (`sni`) меняется эпохами (raycontrol с v0.29.0, R4-42): по расписанию раз в 90 дней только под
  wildcard-сертификатом ноды, иначе — по команде оператора (`rayctl service rotate <naive>`). Новое имя приходит в
  `next` за 3 дня до `from` — та же строка с другим `sni`; с ним — следующий пароль, если он уже опубликован. Пины
  `niko-pin` в `link` и в `next` одни и те же: ключ сайта при смене имени не меняется. Новое имя нода обслуживает
  ещё до публикации, прежнее — до следующей смены имени (по h2 и по QUIC); `rayctl service rotate <naive> -now`
  переключает сразу, прежнее имя и тогда работает до следующей смены. При сменах чаще раза в период (90 дней) прежние
  имена работают каждое до смены через период после своей, не больше трёх. Новое имя — всегда поддомен домена ноды.
- Без пароля, с неверным или без паддинга сервер отвечает как сайт (пустой `404`), а не `407`.
- `uot=2` (с v0.20.0) — сервер несёт UDP поверх потока, UDP-over-TCP v2 из sing-box
  ([naive-uot-v1](naive-uot-v1.md)). Без параметра клиент UDP через naive не шлёт. Недоступное назначение
  сбрасывает поток, а не закрывает его чисто.
- `icmp=1` (с v0.21.0) — сервер несёт ping и трассировку: поток к `icmp.niko.arpa`, echo шлёт нода со своих
  ICMP-сокетов ([icmp-v1](icmp-v1.md)). Только когда на сервисе `rayctl service set <naive> icmp=on`; по умолчанию
  параметра нет, и клиент ICMP на ноду не шлёт.
- `niko-ack=1` — нода понимает заголовок запроса `niko-ack: 1`: на CONNECT с ним она отвечает после dial, а не до
  него ([naive-uot-v1](naive-uot-v1.md) §4). `200` — назначение приняло соединение; `502` — отказало, недоступно, имя
  не нашлось или его запрещает политика ноды, причина — в заголовке ответа `niko-ack` (`refused`, `unreachable`,
  `denied`); `504` — назначение молчало весь тайм-аут dial (10 с), и не раньше него. Все эти ответы, как и `429`,
  несут `Padding`. Клиент может держать SYN-ACK приложению до этого ответа, как у Hysteria2. Заголовок можно слать во
  всех запросах соединения: потоки UoT и ICMP получают `200` сразу. Без параметра слать заголовок бессмысленно: старая
  нода его не знает и отвечает `200` до dial.
- naive-quic: тот же адрес по UDP 443 (HTTP/3, QUIC v1 с `X25519MLKEM768`), те же имя и пароль — `naive+quic://` с
  теми же параметрами; фронт отдаёт по имени из QUIC Initial (R3-5).

### Профиль Yggdrasil (R4)

Ссылка — VLESS к `inner` на адресе ноды в сети Yggdrasil; носитель — Yggdrasil с одним пиром, самой нодой:

```
vless://<uuid>@[<адрес ноды в Yggdrasil>]:<порт выхода>?type=raw&encryption=mlkem768x25519plus.native.0rtt.<ключ>
  &niko-node=<node_id>&niko-svc=<id>&niko-ygg=tls%3A%2F%2F<адрес ноды>%3A443%3Fkey%3D<ключ ноды>%26sni%3D<имя>%3B<seed>#ygg
```

- **Пир** — `tls://<адрес ноды>:443?key=<ключ ноды>&sni=<имя>`:
  - `<адрес ноды>` — тот же, что у остальных профилей: TCP 443 после SPA. Имя клиент не резолвит;
  - `<имя>` — поддомен ноды под сертификатом её сайта, только в SNI: по нему фронт отдаёт поток Yggdrasil. До
    v0.19.1 вместо адреса стояло имя: клиенты с 5cd6c0b набирают адрес ноды в любом случае;
  - `key` — открытый ключ ed25519 ноды в Yggdrasil (hex), клиент закрепляет его (`pinnedEd25519Keys` в yggdrasil-go);
  - сертификат TLS не проверяется: Yggdrasil проверяет ключ сам. TLS 1.3, только `X25519MLKEM768`;
  - по умолчанию других пиров у профиля нет: подключение только прямое (P-14).
- **Публичные пиры** (R4-18) — `niko-ygg-via`, по одному на параметр, если у ноды они включены. Клиент берёт их,
  только когда прямой пир не подключается, и идёт к тому же адресу и порту через сеть Yggdrasil. Узел клиента
  входящих не принимает. Постквант на таком линке не гарантирован; `inner` с `encryption` остаётся.
  Пиры `quic://` — только с IP-адресом: имя yggdrasil-go резолвит сам, системным резолвером, мимо DNS клиента
  (просьба клиента, RAYCONTROL.md §15.2). Нода не принимает `quic://` с именем, а такие, заданные раньше, в ссылку
  не попадают.
- **Ключ пользователя** — seed ed25519 (hex, 32 байта), закрытый ключ узла клиента. Он выводится из UUID в ссылке,
  поэтому в `next` приходит новая пара: UUID и ключ. Нода принимает оба набора так же, как UUID в `inner` (R4-1).
- **Адрес и порт.**
  - Адрес — адрес ноды в Yggdrasil (`200::/7`), он выводится из `key`.
  - Порт выхода случаен для каждой ноды; на остальные порты нода отвечает сбросом, UDP не принимает.
  - Через Yggdrasil к этому адресу и порту клиент идёт VLESS с `encryption`, как в профиле DNS-туннеля. Сквозное
    шифрование Yggdrasil классическое, поэтому постквант даёт линк и `inner`.
- **Что не линк Yggdrasil**, получает от `<имя>` ответ сайта: пустой `404` по h2 или HTTP/1.1.

## 5. Проверки в клиенте (порядок)

1. TLS: `X25519MLKEM768`, пин SPKI.
2. Обе подписи.
3. `node_id` совпадает с импортированной нодой.
4. `seq` не меньше сохранённого; `expires` в будущем.
5. `time` против своих часов: при расхождении больше 30 с — предупредить пользователя.

## 6. Отзыв другого устройства пользователя (raycontrol v0.27.0)

Формат подписки не меняется. Меняется то, когда старые ссылки перестают работать.

Отзыв любого устройства пользователя сразу меняет все его учётные данные, без перекрытия (R4-36,
[api-v1.md](api-v1.md) §5a). Что видит другое, не отозванное устройство того же пользователя:

1. Через секунды после отзыва его соединения на REALITY, `inner` (DNS-туннели, Yggdrasil), Hysteria2 и naive
   рвутся, новые с прежними UUID и паролями не проходят. Ключ Yggdrasil в ссылке выводится из UUID `inner`,
   поэтому он тоже прежний и не принимается. Пароль LAN (lan-v1) тоже новый.
   **DoH продолжает отвечать** (с v0.27.0, R4-37): токен у каждого устройства свой, секрет DoH пользователя отзыв
   не меняет, умирает только токен отозванного устройства. Резолвер, через который устройство берёт подписку,
   поэтому не пропадает. Исключение — устройство, которое с обновления ноды до v0.27.0 подписку ещё не брало и
   держит общий токен пользователя: он закрывается отзывом сразу (§4, «Профиль DoH»), нода отвечает на него `404`.
2. SPA, TLS подписки и `Authorization: RC1` — ключи самого устройства, отзыв другого устройства их не трогает:
   подписка по-прежнему отвечает `200`.
3. Клиент, у которого не работает текущий профиль, перезапрашивает подписку, как при неработающих `link` и `next`
   (§3, `profiles[].next`). Niko делает это после двух неудачных проверок подряд: плановая идёт раз в 10 минут
   (после смены сети — через 15–30 с), повторная — через 15 с после неудачной, затем подписка берётся сразу;
   повторные выборки — с отсрочкой от 5 минут до часа. Итого до ~10,5 минуты, в режиме сна телефона — после
   пробуждения (со слов сессии клиента; так с Niko 1.14.0).
4. В новом ответе `seq` больше; в профилях новые UUID и пароли, без `next`: следующая плановая смена — через
   период ротации от момента отзыва. Строка DoH прежняя, с прежним `next`, если он был. Ключи сервисов (REALITY,
   туннелей, пины сайта) прежние.
5. С новыми ссылками всё работает, как раньше. Лимит трафика (`traffic`) продолжает тот же период и счёт.

Профили других пользователей отзыв не затрагивает. Отозванное устройство получает на подписку `404` (§2).
