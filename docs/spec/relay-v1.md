# relay-v1: вход через промежуточный узел (черновик)

Статус: **черновик для согласования с клиентом** (RAYCONTROL.md §22.1). Кода пока нет. Формат может измениться,
пока здесь не написано «заморожен».

## 1. Зачем

Две главные угрозы — свойства пути, а не протоколов:
- на мобильных сетях TCP к зарубежным хостингам замирает после 16–20 КБ;
- в режиме белого списка доступны только разрешённые адреса, а UDP 443 и UDP 53 режутся.

Ответ — вход через узел в стране (лучше в AS из белого списка), дальше к зарубежному выходу. Ключей сервисов на
этом узле нет.

## 2. Роли

- **Выход** — обычная нода raycontrol: сервисы, пользователи, подписка.
- **Relay** — второй хост с минимальной установкой. Он состоит из двух частей:
  - фронт niko-server в режиме пересылки L4, без разбора TLS и без ключей сервисов. Он пересылает к выходу:
    - TCP 443 и UDP 443;
    - порт подписки и порт API выхода: в белом списке иначе истечёт подписка;
  - своё SPA (`rayspa`) и свой замер `probe-v1` (§5).

REALITY, Hysteria2 и naive остаются сквозными от клиента до выхода: на relay нечего расшифровать.

## 3. Доверие и ключи

- **SPA relay.** У relay своё SPA со своими параметрами (`node_id`, порты, длины). Ключ устройства для relay
  выводится из SPA-ключа устройства:

  ```
  K_relay = HKDF-SHA256(ikm = SPA-ключ устройства, salt = node_id выхода,
                        info = "raycontrol-relay-v1" || relay_id, L = 32)
  ```

  Захваченный relay не может стучаться к выходу ключами устройств и не отличает одно устройство от другого вне
  своего SPA.
- **Выход пускает адрес relay** на порты сервисов, которые relay пересылает, постоянно и без SPA. Это отдельный набор
  в таблице периметра, как адреса администратора, но только для портов сервисов, не для SSH.
- **Установка.** `rayctl relay add <имя> <адрес>` на выходе выдаёт пакет relay:
  - адрес выхода и порты;
  - параметры SPA relay;
  - выведенные ключи устройств;
  - ключ подписи для обновлений.

  `bootstrap.sh -relay <пакет>` ставит на втором хосте фронт, `rayspa` и маленький `rayd` в роли relay. Новые
  и отозванные устройства relay получает от выхода по mTLS.

## 4. Подписка

```json
"relays": [{"id": "r1", "host": "198.51.100.20", "sub_pin": "…", "spa": {"node_id": "…", "...": "…"}}],
"profiles": [{"svc": 3, "name": "reality", "link": "vless://…", "via": ["r1"]}]
```

- `relays[]`:
  - `host` — адрес relay;
  - `sub_pin` — пин TLS его эндпоинта замера;
  - `spa` — параметры SPA relay, в том же виде, что у выхода в пакете регистрации.
- `profiles[].via` — через какие relay можно идти к этому профилю. Ссылка та же. Клиент заменяет хост на хост relay
  и стучится к relay его SPA (ключ `K_relay`).
- Переключение «напрямую ↔ через relay» — у клиента, как переключение профилей.
- DNS-туннели и Yggdrasil через relay не ходят: у них свой путь.
- Relay — списком на ноду, обычно 1–3. Клиент выбирает по сети: замер relay плюс запомненный результат пути.
- **Пины.** Пин TLS выхода (подписка, API, `niko-pin`) у клиента прежний, соединение сквозное. `sub_pin` relay
  нужен только для его замера (§5).
- **Ротация UDP-портов** (spa-v2 §11) через relay в v1 выключена. Relay слушает UDP 443 и пересылает на UDP 443 выхода.
  Клиент через relay ходит на 443. Причины:
  - relay стоит в своей сети, обычно в разрешённой AS: от подмены портов там меньше пользы;
  - пересылать весь диапазон ротации значит держать открытыми тысячи портов на relay.

  Позже relay может вести свою ротацию со своим `port_key`.

## 5. Детектор белого списка

- На relay работает эндпоинт `probe-v1` (как на выходе: эхо, загрузка, отдача) за его SPA.
- Relay отвечает, а выход напрямую нет — значит, это белый список или заморозка. Клиент сразу берёт путь через
  relay.
- В сводку клиент добавляет поле `path` (`direct` или `relay`), как `udp_mtu`. Нода объявляет его в
  `probe.report`, подсказки считаются по путям отдельно.

## 6. Что видит выход

- Источник соединений через relay — адрес relay. Сводка по AS клиента идёт из отчёта клиента, а не из адреса.
- Замер `link` (сессии клиента на ноде) через relay не работает: адрес общий. Клиент меряет relay напрямую (§5).
- PROXY v2 от relay к выходу (адрес клиента) — позже, если понадобится выходу.

## 7. Этапы

1. **R6-a.**
   - **Сторона выхода — готово** (raycontrol после v0.10.0): `rayctl relay add <имя> <адрес>`, `list`, `remove`, только
     root на ноде. Адрес — один публичный IP. Он доходит до портов всех включённых сервисов, кроме SSH и публичных,
     без SPA (наборы `relay4`, `relay6`, `relay_ports` в таблице периметра).
   - **Сторона relay — дальше.** Пересылка ядром вместо фронта niko-server: на relay `rayspa` пускает тех, кто
     постучался SPA, а nftables делает DNAT и masquerade к выходу. Трафик не проходит через userspace.
     `bootstrap.sh -relay`.
2. **R6-b.** `relays` и `via` в подписке, SPA к relay, ключ `K_relay`. Клиент: разбор, путь через relay в watchdog.
3. **R6-c.** `probe-v1` на relay, поле `path` в сводке, детектор белого списка у клиента.

## 8. Решено с клиентом (2026-11-04)

- `via` — на уровне профиля; relay на уровне ноды не нужен.
- Relay — списком на ноду, выбор по сети у клиента.
- Relay пересылает и порты подписки и API; пин выхода сквозной; ротации через relay в v1 нет.
