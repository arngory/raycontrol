# naive-uot-v1: UDP через naive (UDP-over-TCP v2)

Статус: **черновик** (2026-11-08). Сервер — raycontrol v0.20.0. Клиент — Niko с `04d713c` (`uot=2`).

Зачем: через naive-профиль сейчас идёт только TCP. WARP, wireproxy (WireGuard), QUIC, игры и голосовые звонки
по UDP через него не работают: клиент получает 200 и сразу конец потока. Через REALITY и Hysteria2 UDP уже идёт.
Здесь naive учится нести UDP внутри своего же потока, протоколом UDP-over-TCP v2 из sing-box
(`github.com/sagernet/sing/common/uot`). Новых портов и точек входа нет: это то же аутентифицированное соединение.

## 1. Сигнал в подписке

В naive-ссылке (`naive+https://…`, [subscription-v1](subscription-v1.md) §4) появляется параметр `uot=2`. Сервер
ставит его, только если поддерживает этот протокол (с v0.20.0). Клиент:
- с `uot=2` включает у naive-исходящего `udp_over_tcp` (версия 2);
- без него UDP через naive не отправляет вовсе: приложения сразу переходят на TCP или на другой профиль.

## 2. Протокол

Совместим с naive-исходящим sing-box (`udp_over_tcp: {enabled: true, version: 2}`) и с `uot.ServerConn` из sing.

1. **CONNECT** на `sp.v2.udp-over-tcp.arpa:<любой порт>`, с `Proxy-Authorization` и `Padding`, как обычный naive.
   Годится и HTTP/2, и HTTP/3 (naive-quic). Ответ — 200 с `Padding`. Дальше поток, с паддингом первых кадров, как
   у обычного naive.
2. **Запрос** — первые байты потока от клиента:

   ```
   [isConnect: u8, 0 или 1][адрес в формате SOCKS: ATYP 0x01 IPv4 (4) | 0x03 имя (u8 длина + имя) | 0x04 IPv6 (16)][порт: u16 BE]
   ```

3. **isConnect = 1** — одно назначение, из запроса. Пакеты в обе стороны: `[длина: u16 BE][данные]`.
4. **isConnect = 0** — назначение у каждого пакета своё. Пакет от клиента:

   ```
   [адрес: 0x00 IPv4 (4) | 0x01 IPv6 (16) | 0x02 имя (u8 длина + имя)][порт: u16 BE][длина: u16 BE][данные]
   ```

   От сервера — так же, адрес в нём — источник ответа. Адрес из запроса в этом режиме не используется.
5. **v1** (`sp.udp-over-tcp.arpa`, без запроса в начале) не поддерживается: поток сбрасывается (§4). Клиент её не
   шлёт.

## 3. Правила сервера

- **Куда можно.** Только публичные unicast-адреса, как для TCP через naive. Нельзя:
  - саму ноду;
  - loopback, частные сети, link-local, CGNAT (100.64.0.0/10), multicast.

  Это проверяет процесс, адрес за адресом, а юнит и периметр ноды запрещают то же ещё раз.
- **Имена** резолвит нода. Берётся первый публичный адрес из ответа. Ответ запоминается на время потока, не больше
  чем на 64 имени.
- **Ответы.** Принимаются только с адресов и портов, куда клиент сам отправлял в этом потоке (port-restricted cone).
  Так же пропускает и периметр ноды. Full cone нет: ответ с незнакомого адреса до клиента не дойдёт.
  - При isConnect = 1 сокет подключён к назначению: ответы только от него.
- **Пакеты.**
  - Данные — не больше 65 507 байт. Длиннее — поток закрывается.
  - Пакет на запрещённое назначение при isConnect = 0 отбрасывается, поток живёт.
  - Запрещённое назначение в запросе при isConnect = 1 — поток сбрасывается.
- **Простой.** Две минуты без пакетов в обе стороны — поток закрывается. Клиент при надобности откроет новый.
- **Пределы.**
  - Один UDP-сокет на поток.
  - Потоков UoT не больше 64 на одного пользователя (пароль) и 4096 на сервис.
  - Сверх предела — сброс потока.

## 4. Отказы (и TCP CONNECT тоже)

Ответ 200 по-прежнему уходит до соединения с назначением. Ждать dial до ответа стоило бы клиенту на каждом
соединении задержки до одного RTT клиент—нода сверх времени dial: клиент начал бы слать данные только после ответа.

Если назначение недоступно или запрещено, сервер **сбрасывает поток**, а не закрывает его чисто:
- HTTP/2 — `RST_STREAM`;
- HTTP/3 — сброс потока.

Клиент так видит ошибку соединения, а не пустой ответ. То же для обычного TCP CONNECT, для v1 и для пределов из §3.

## 5. Версии

- raycontrol v0.20.0: UoT v2 в naive (HTTP/2 и HTTP/3), `uot=2` в ссылке, сброс потока при отказах.
- Niko `04d713c`: `udp_over_tcp` по `uot=2`.
- Нода до v0.20.0 параметр не ставит, и клиент UDP через naive не шлёт.
