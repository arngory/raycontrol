# quic-cid-route-v1: маршрутизация QUIC во фронте по connection ID

Статус: niko-server — ветка `claude/clever-feynman-w0e2v1`, к выпуску v0.18.0 (фронт, бэкенды Hysteria2); raycontrol —
naive-quic и DoH3 выдают ID с меткой сразу, фронту и Hysteria2 опции пишутся с пина niko-server v0.18.0
(`render.NikoCIDRouteFrom`; сейчас пин v0.17.1). Клиентам ничего менять не нужно. Уточнено 2026-11-16 по ревью: ключ
у каждой метки свой (§2), сброса для будущих ID нет (§5), Hysteria2 проверяет новый путь (§5), угрозы с замерами (§10).

## 1. Зачем

Фронт ноды (udpmux niko-server) ведёт датаграммы по потокам «адрес клиента, адрес фронта». Новый поток он заводит
только по QUIC Initial (имя из ClientHello) или по Initial под salamander (hy2-obfs). Пакеты с коротким заголовком с
незнакомого адреса он отбрасывает: соединение, у которого сменился адрес клиента, умирает к своему тайм-ауту простоя.
Так бывает:
- **NAT rebinding** — NAT клиента выдал ему другой порт (на мобильных сетях обычно, после паузы в трафике);
- **перенос соединения на новый сокет** — клиент сам переходит на новый порт, например на порт нового слота ротации
  ([`spa-v2.md`](spa-v2.md) §11): со старого сокета на новый порт слота нельзя (вторая запись conntrack получает тот же
  обратный кортеж, что и первая), а с нового сокета фронт поток не узнавал;
- **перезапуск фронта** и **простой потока дольше `udp.idle`** — фронт забыл поток, а соединение живо.

Решение по образцу QUIC-LB (draft-ietf-quic-load-balancers): каждый бэкенд QUIC выдаёт свои server connection ID с
меткой, по которой фронт без состояния от рукопожатия находит бэкенд. Метку видит только нода.

Требования:
- **Метка не видна на проводе.** ID случайны для всех без ключа: наблюдатель не отличает бэкенды и не связывает ID
  одного соединения между собой.
- **ID не повторяются** — в пределах бэкенда и между бэкендами.
- **Сервисы разделены.** Процесс одного сервиса не получает ничего, что открывает соединения другого.
- **Промах дёшев.** Чужой пакет — несколько шифр-блоков без выделений памяти; случайные данные проходят за метку
  редко.
- **Совместимо в обе стороны.** Старый фронт с новыми бэкендами и новый фронт со старыми работают как раньше для
  клиентов, которые адрес не меняют.
- **Годится и для шага (г)** [`naive-udp-v1.md`](naive-udp-v1.md) §5.2: метку должна читать классическая BPF-программа
  `SO_ATTACH_REUSEPORT_CBPF` (без привилегий), а в ней только 32-битные сложения, сдвиги и xor.

## 2. Секрет и ключи меток

Секрет — один на ноду: 32 случайных байта, настройка `quic_cid_key` в базе (`store.QUICCIDKey`), создаётся при первом
сборе модели, как ключ dnsprobe. Клиентам не уходит.

У каждой метки свой ключ шифра:

```
K_метка = HMAC-SHA256(секрет, "quic-cid-route-v1" ‖ BE16(метка))[0:16]
```

Кто что знает:
- фронт — секрет: файл `rendered/front/quic-cid.key` (64 hex-цифры и перевод строки, 0640, группа фронта), путь в
  `udp.cid_key_file`; ключи меток своих бэкендов фронт выводит сам;
- бэкенд Hysteria2 — только ключ своей метки: `rendered/<сервис>/quic-cid.key` (32 hex-цифры, 0640, группа сервиса),
  путь в `options.cid_key_file`, метка в `options.cid_label`;
- naive-quic — только ключ своей метки: `rendered/<сервис>/quic-cid` — `<метка> <32 hex-цифры>` (0640, группа
  сервиса), флаг `rayd naive -cid`; метка в файле, а не в юните: `rayctl apply` строит юнит из входов без ID сервиса;
- DoH3 — rayd выводит ключ метки из секрета в базе сам, при запуске сервиса DoH.

Процесс читает свой файл при запуске. Файл не `AtStart`: его изменение (база, восстановленная с другим секретом,
потерянная настройка) перезапускает процесс, и фронт с бэкендами не остаются на разных ключах (тест
`live.TestApplyQUICCIDKeyChange`). Файла нет или он не читается — warning без содержимого, и процесс работает как
раньше: бэкенд со случайными ID, фронт без маршрутизации по ID. Ротации секрета нет (§11).

## 3. Метка

Метка бэкенда — ID его сервиса в базе raycontrol (1–65535; 0 — «метки нет»). У naive и DoH метка относится к их
стороне QUIC (`<сервис>/quic` во фронте). ID сервиса уникален и не меняется, поэтому:
- у двух бэкендов ноды меток одинаковых не бывает (фронт и `niko-server check` проверяют ещё и сами);
- метка не меняется между отрисовками, перезапусками и добавлением сервисов;
- сервис с ID больше 65535 метки не получает: его клиенты теряют соединение при смене адреса, как раньше.

## 4. Формат connection ID

8 байт — длина, которую используют крупные серверы и которую у naive-quic и DoH3 уже давала `h3serve.ConnIDLen`.

Открытый текст — 64 бита, два слова big-endian:

```
x = метка (16 бит) ‖ 0x00 (8 бит) ‖ счётчик[39:32] (8 бит)
y = счётчик[31:0]
ID = BE32(x') ‖ BE32(y'),  (x', y') = Speck64/128_{K_метка}(x, y)
```

- **Speck64/128** (Beaulieu и др., «The SIMON and SPECK Families of Lightweight Block Ciphers», 2013): блок 64 бита,
  ключ 128 бит, 27 раундов; раунд `x = (ROR(x, 8) + y) ⊕ k_i; y = ROL(y, 3) ⊕ x`. Ключевые слова `l2 l1 l0 k0` —
  `K[0:4] K[4:8] K[8:12] K[12:16]` (big-endian), как в векторах статьи; вектор Speck64/128 из её приложения C —
  в тестах обеих реализаций.
- **Счётчик** — 40 бит, свой у каждого генератора (процесса и метки): старт случайный, +1 на каждый ID, по модулю
  2^40.
- **Нулевой байт** — проверка: фронт принимает метку, только если после расшифрования ключом метки он 0 и метка —
  та же (§6).

Почему так:
- блочный шифр на различных открытых текстах даёт различные ID: ID одного генератора не повторяются раньше 2^40
  штук (при 10 000 ID в секунду — 3,5 года), ID разных меток не совпадают никогда (кроме как по случайности двух
  разных ключей, 2⁻⁶⁴). У quic-go по умолчанию ID случайные, 4 байта, и совпадения возможны;
- для всех без ключа метки ID — выход псевдослучайной перестановки на различных входах: метки и счётчик не видны, ID
  одного соединения и одного бэкенда не связать;
- случайные 8 байт читаются как одна из k меток с вероятностью k·2⁻²⁴;
- Speck — 32-битные сложения, сдвиги и xor: классическая BPF-программа расшифровывает ID ключом метки примерно за
  590 инструкций; с ключом на метку — до шести меток в пределах 4096 (тест `TestCIDBPF` niko-server сверяет её с
  фронтом). Шаг (г) naive-udp-v1 §5.2 берёт этот же формат.

Что рассматривалось:
- QUIC-LB single-pass: AES-128-ECB над ID в 16 байт (+ байт конфигурации открытым) — длина 17 выделяется, AES в
  классическом BPF не делается;
- QUIC-LB four-pass: Feistel из AES — та же беда с BPF, слабее при коротких половинах;
- «случайная часть + метка под маской от неё»: ID случайные, но совпадения только вероятностные, и при совпадении
  случайной части видно равенство меток;
- один ключ на ноду (первая редакция): процесс любого сервиса читал счётчик в ID всех остальных (§10).

## 5. Бэкенды

**Hysteria2 (niko-server, sing-quic на sagernet/quic-go v0.61.0-sing-box-mod.12).** `options.cid_key_file` (ключ
метки) и `options.cid_label` (оба или ни одного) — генератор отдаётся `quic.Transport.ConnectionIDGenerator` через
вендоренный sing-quic (`ServiceOptions.ConnectionIDGenerator`). Без опций — ID quic-go, случайные, 4 байта.
Новый адрес клиента сервер **проверяет** (`ServiceOptions.PathValidation`, менеджер путей quic-go, RFC 9000 §9): шлёт
туда PATH_CHALLENGE и переходит после ответа. Upstream ставит `DisablePathManager` и переносит весь поток отдачи на
любой адрес, с которого пришёл расшифрованный неповторный пакет соединения (§10). Port hopping клиента Hysteria2 (новый
сокет на новый порт, то же соединение) через фронт работает, переход — на один RTT позже (тест
`TestNekoServerHysteriaPortHopping`: два порта фронта, прыжки раз в 5 с, hy2-masq и hy2-obfs). Brutal и BBR, которые
ставит сервер, переход переживают (quic-go сохраняет внедрённый контроллер).

**naive-quic и DoH3 (rayd, quic-go v0.64.1).** `h3serve.Options.ConnIDs`; генератор с длиной не 8 отвергается
(короче — таблица токенов stateless reset становится читаемой). Серверный менеджер путей quic-go проверяет новый путь
и переходит после проверки; до неё ответы идут на старый адрес — при NAT rebinding это около одного RTT потерь.
Пакетный сокет IPC даёт каждой датаграмме свой адрес клиента, и проверка через него работает: тест niko-server
`TestNekoServerQUICRebind` (NAT rebinding и переход клиента `AddPath`/`Probe`/`Switch`) и raycontrol
`TestQUICRebindWithNikoServer` (через настоящий фронт).

**Сброса для будущих ID нет.** quic-go отвечает на пакет с неизвестным ID stateless reset (42 байта, только на пакет
длиннее 42 байт), токен — функция ID и ключа сброса, у naive-quic и DoH3 ключ не меняется. Кто знает ключ метки, читает
счётчик и знает следующие ID; спросив их сброс заранее, он получил бы токены, которыми позже рвал бы соединения с этими
ID. Поэтому генератор знает, какие ID он ещё выдаст (`Ahead`: метка своя, счётчик в следующих 2^32), а сокет сервера
отбрасывает короткие заголовки с такими ID, прежде чем их увидит quic-go: в rayd — `h3serve` (`aheadConn`), в
niko-server — hy2-masq (`aheadFilter`; у hy2-obfs сброса нет). ID прежнего процесса попадает в окно случайно, в 2⁻⁸
случаев: тогда его клиент ждёт тайм-аут простоя вместо сброса.

**Что не меняется.**
- Stateless reset для ID, которых процесс не выдавал и не выдаст: как раньше; пакет с меткой верной, но с ID, которого
  бэкенд не знает (бэкенд перезапущен, соединение закрыто), теперь доходит до бэкенда, и тот отвечает сбросом — как
  обычный сервер QUIC. Без метки — тишина, как раньше.
- Retry: quic-go шлёт его только с `VerifySourceAddress`, которого у нас нет. SCID Retry — тоже с меткой; новый
  Initial идёт по имени.
- Version negotiation, `DisableVersionNegotiationPackets` у hy2-obfs, длины ID клиента — как были. Длина ID сервера
  видна клиенту в длинных заголовках, клиенты (quic-go, Chromium, sing-quic) её принимают любой.

## 6. Фронт

Конфиг: `udp.cid_key_file` (секрет) и `backends.<имя>.cid_label` (только бэкенд маршрута UDP; без ключа — ошибка
`check`).

Для датаграммы, которую не объясняет ни один поток:

1. QUIC Initial известной версии — по имени, как раньше. Первый DCID клиента — его собственный, по метке Initial не
   идёт никогда.
2. Короткий заголовок (`первый байт & 0xC0 = 0x40`, длина не меньше 29: заголовок, 8 байт ID, 4 байта до образца
   защиты заголовка и сам образец) или Handshake QUIC v1/v2 с длиной DCID 8: расшифровать DCID ключом каждой метки
   бэкендов **обычного QUIC** (маршрутов по имени); где нулевой байт 0 и метка своя — поток этого бэкенда.
3. Для каждого маршрута salamander: ключ `BLAKE2b-256(пароль ‖ соль)` (тот же, что для проверки Initial), снять
   обфускацию с первых 14 байт; Initial — как раньше; короткий заголовок или Handshake, который ключ метки **этого
   маршрута** читает как его метку, — поток его.
4. Иначе — drop, поток не закрепляется.

Пакет одного вида не попадает к бэкенду другого: метку бэкенда salamander в открытом пакете и метку обычного бэкенда
под salamander фронт не ищет. Датаграмма уходит бэкенду как пришла.

Пределы:
- поток по метке — обычный поток: простой `udp.idle`, общий потолок таблицы (2¹⁸);
- новых потоков по метке с одного источника (адрес IPv4, /64 IPv6) — 32 в секунду, запас 128; источники помнятся в
  двух поколениях по минуте и не больше чем по 16384 в поколении. Это предел доли источника и памяти ограничителя, а
  не таблицы потоков: источник, который перебирает больше 32768 адресов (IPv6 /48 хватит), получает долю на каждый,
  как и подделанные Initial, у которых предела нет вовсе.

Цена промаха (сверх прежнего): по одному Speck (27 раундов, десятки наносекунд) на метку обычного QUIC, если пакет
похож на короткий заголовок или Handshake, и по одному на маршрут salamander. Без выделений памяти (тест
`TestUDPFrontCIDMissNoAllocations`); замер `BenchmarkUDPFrontCIDMiss` — 0,2–0,35 мкс на датаграмму.

Попутно: перезапуск фронта и забытый по простою поток больше не обрывают соединения бэкендов с меткой.

## 7. Что видит наблюдатель

- Server connection ID — 8 байт у всех сервисов QUIC ноды (у hy2-masq было 4, у naive-quic и DoH3 давно 8): одна
  длина, распространённая у больших серверов. Каждый ID новый и случаен без ключа; метка, счётчик и связь ID одного
  соединения не видны.
- hy2-obfs: заголовков не видно вовсе (salamander).
- Активный зонд со случайными пакетами получает от фронта тишину, как раньше. Пакет с меткой (ID из своего
  рукопожатия — их раздаёт любое рукопожатие, подсматривать не нужно) доходит до бэкенда; на ID, которого бэкенд не
  знает и не выдаст, тот отвечает stateless reset — как обычный сервер QUIC.

## 8. Пример

```
секрет      = 00 01 02 … 1f (32 байта подряд)
метка       = 0x0102
K_метка     = 167e64ae0e81012cf5f8667f5525e7ee
счётчик     = 0x0405060708
x, y        = 01020004 05060708
ID          = 0243e188ccdc1084
```

Обе реализации (`nikoserver/quiccid.go`; `internal/quiccid`, `internal/quiccid/cidkey`) проверяют этот пример и вектор
Speck64/128 из статьи (ключ `1b1a1918 13121110 0b0a0908 03020100`, текст `3b726574 7475432d` → `8c6fa548 454e028b`);
пример сверен ещё и с отдельной реализацией на Python.

## 9. Совместимость

- **Старый фронт, новые бэкенды.** Фронт меток не читает: всё как раньше; ID бэкендов — 8 байт вместо 4 (hy2), это
  клиентам безразлично.
- **Новый фронт, старые бэкенды.** Метку фронт ищет только у бэкендов с `cid_label`; у бэкенда без меток в ID (старый
  процесс, ключ не прочитался) случайные 8 байт проходят за метку с вероятностью k·2⁻²⁴ — такой пакет уходит бэкенду
  и отбрасывается им; клиентам, которые адрес не меняют, ничего не меняется.
- **Конфиги.** niko-server читает конфиги строго: до v0.18.0 незнакомое поле — отказ всего конфига. Поэтому
  raycontrol пишет опции фронта и Hysteria2 только при пине niko-server v0.18.0 и новее (`render.NikoCIDRouteFrom`).
  rayd свои ID метит сразу: старый фронт их просто не читает. Тест через настоящий фронт
  (`TestQUICRebindWithNikoServer`) пропускается, пока `NIKO_SERVER_BIN` — пин без этих опций, то есть в CI до пина
  v0.18.0.
- **По умолчанию включено**, потому что совместимо в обе стороны и клиентам ничего не нужно: секрет создаётся сам,
  выключателя нет. Цена: 4 байта на пакет клиента к hy2-masq (у naive и DoH3 их уже было 8), и бэкенд за фронтом
  отвечает сбросом на пакеты с меткой, которых раньше не видел.

## 10. Угрозы

Замеры — на loopback, тестами niko-server (ревью и регрессионные).

- **Направить свою загрузку на чужой адрес (Hysteria2, исправлено).** С `DisablePathManager` сервер Hysteria2
  переносил весь поток отдачи на любой адрес, с которого пришёл расшифрованный неповторный пакет соединения, без
  проверки пути и без тройного предела. Пользователь с паролем и возможностью подделать адрес источника слал один свой
  пакет с адреса жертвы, а фронт закреплял её адрес по метке: **один пакет в 36 байт — около 711 КБ у жертвы за 3 с**;
  повторяя пакет каждые 50 мс (3,8 КБ подделанных пакетов за 5 с) — около 1,5 МБ. Старый фронт этого не закрывал:
  адрес жертвы закреплял подделанный Initial с именем (около 2,4 КБ), дальше то же. Теперь сервер проверяет путь
  (§5): один подделанный пакет — один PATH_CHALLENGE в 1200 байт; 3,7 КБ подделанных пакетов за 5 с — 6000 байт у
  жертвы в пяти пробах, загрузка идёт пользователю дальше (тест `TestNekoServerHysteriaSpoofedSource`; без проверки
  пути он видит у жертвы 18–23 КБ за один пакет).
- **Усиление проверкой пути (было и раньше).** Проверку пути quic-go дополняет до 1200 байт без тройного предела
  RFC 9000 §8. Вызывает её любой свежий неповторный пакет соединения с нового адреса, в том числе с подделанного: свой
  же пакет клиента, отправленный с адреса жертвы, — атакующему на пути быть не нужно, а у naive-quic и DoH3 не нужна и
  учётная запись (рукопожатие проходит любой). Замер: один пакет в 36 байт — одна проба в 1200 байт; 932 подделанных
  пакета за 5 с на 64 адреса — 18 проб: quic-go держит не больше трёх путей и растягивает повторы. Это было и раньше
  (адрес закреплял подделанный Initial), у Hysteria2 теперь так же, а не 700 КБ.
- **Stateless reset.** 42 байта и только в ответ на пакет длиннее 42 байт: не усиление. Для ID, которые бэкенд ещё
  выдаст, сброса нет (§5).
- **Поток случайных коротких заголовков** — промах без памяти и без состояния (§6).
- **Повтор пакета с меткой с подделанных адресов** заводит потоки (до потолка таблицы) и шлёт бэкенду пакеты, которые
  тот отбрасывает или проверяет путём. Подсматривать для этого ничего не надо: ID с меткой раздаёт любое рукопожатие.
  То же уже давал подделанный Initial с маршрутизируемым именем; предел на источник бережёт долю источника, а не
  таблицу (§6).
- **Утечка ключа.** Процесс сервиса знает только ключ своей метки: с ним он читает счётчик своих ID и делает свои ID,
  но не чужие. Секрет (а с ним ключи всех меток) знают фронт и rayd. С ключом метки можно было бы, зная следующие ID,
  заранее собрать токены их сброса — сервер на такие ID не отвечает (§5); данных пользователей ключ не открывает. В
  журналы не пишется ни секрет, ни ключи, ни содержимое файлов.
