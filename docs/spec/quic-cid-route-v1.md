# quic-cid-route-v1: маршрутизация QUIC во фронте по connection ID

Статус: niko-server — ветка `claude/clever-feynman-w0e2v1`, к выпуску v0.18.0 (фронт, бэкенды Hysteria2); raycontrol —
naive-quic и DoH3 выдают ID с меткой сразу, фронту и Hysteria2 опции пишутся с пина niko-server v0.18.0
(`render.NikoCIDRouteFrom`; сейчас пин v0.17.1). Клиентам ничего менять не нужно.

## 1. Зачем

Фронт ноды (udpmux niko-server) ведёт датаграммы по потокам «адрес клиента, адрес фронта». Новый поток он заводит
только по QUIC Initial (имя из ClientHello) или по Initial под salamander (hy2-obfs). Пакеты с коротким заголовком с
незнакомого адреса он отбрасывает: соединение, у которого сменился адрес клиента, умирает к своему тайм-ауту простоя.
Так бывает:
- **NAT rebinding** — NAT клиента выдал ему другой порт (на мобильных сетях обычно, после паузы в трафике);
- **перенос соединения на новый сокет** — клиент сам переходит на новый порт, например на порт нового слота ротации
  ([`spa-v2.md`](spa-v2.md) §11): со старого сокета на новый порт слота нельзя (вторая запись conntrack получает тот же
  обратный кортеж, что и первая), а с нового сокета фронт поток не узнавал;
- **перезапуск фронта** и **простой потока дольше `udp.idle`** — фронт забыл поток, а соединение живо.

Решение по образцу QUIC-LB (draft-ietf-quic-load-balancers): каждый бэкенд QUIC выдаёт свои server connection ID с
меткой, по которой фронт без состояния от рукопожатия находит бэкенд. Метку видит только нода.

Требования:
- **Метка не видна на проводе.** ID случайны для всех без ключа: наблюдатель не отличает бэкенды и не связывает ID
  одного соединения между собой.
- **ID не повторяются** — в пределах бэкенда и между бэкендами.
- **Промах дёшев.** Чужой пакет — один шифр-блок без выделений памяти; случайные данные проходят за метку редко.
- **Совместимо в обе стороны.** Старый фронт с новыми бэкендами и новый фронт со старыми работают как раньше для
  клиентов, которые адрес не меняют.
- **Годится и для шага (г)** [`naive-udp-v1.md`](naive-udp-v1.md) §5.2: метку должна читать классическая BPF-программа
  `SO_ATTACH_REUSEPORT_CBPF` (без привилегий), а в ней только 32-битные сложения, сдвиги и xor.

## 2. Секрет

Один на ноду: 32 случайных байта, настройка `quic_cid_key` в базе (`store.QUICCIDKey`), создаётся при первом сборе
модели, как ключ dnsprobe. Клиентам не уходит.

Кто знает:
- фронт — файл `rendered/front/quic-cid.key` (64 hex-цифры и перевод строки, 0640, группа фронта), путь в
  `udp.cid_key_file`;
- бэкенд Hysteria2 — `rendered/<сервис>/quic-cid.key` (0640, группа сервиса), путь в `options.cid_key_file`;
- naive-quic — `rendered/<сервис>/quic-cid`: `<метка> <64 hex-цифры>` (0640, группа сервиса), флаг `rayd naive -cid`;
  метка в файле, а не в юните: `rayctl apply` строит юнит из входов без ID сервиса;
- DoH3 — rayd берёт секрет из базы сам.

Все файлы читаются один раз при запуске процесса (`render.File.AtStart`): их появление ничего не перезапускает. Файла
нет или он не читается — warning без содержимого, и процесс работает как раньше: бэкенд со случайными ID, фронт без
маршрутизации по ID. Секрет не меняется; ротации нет (§11).

Ключ шифра: `K = HMAC-SHA256(секрет, "quic-cid-route-v1")[0:16]`.

## 3. Метка

Метка бэкенда — ID его сервиса в базе raycontrol (1–65535; 0 — «метки нет»). У naive и DoH метка относится к их
стороне QUIC (`<сервис>/quic` во фронте). ID сервиса уникален и не меняется, поэтому:
- у двух бэкендов ноды меток одинаковых не бывает (фронт и `niko-server check` проверяют ещё и сами);
- метка не меняется между отрисовками, перезапусками и добавлением сервисов;
- сервис с ID больше 65535 метки не получает: его клиенты теряют соединение при смене адреса, как раньше.

## 4. Формат connection ID

8 байт — длина, которую используют крупные серверы и которую у naive-quic и DoH3 уже давала `h3serve.ConnIDLen`.

Открытый текст — 64 бита, два слова big-endian:

```
x = метка (16 бит) ‖ 0x00 (8 бит) ‖ счётчик[39:32] (8 бит)
y = счётчик[31:0]
ID = BE32(x') ‖ BE32(y'),  (x', y') = Speck64/128_K(x, y)
```

- **Speck64/128** (Beaulieu и др., «The SIMON and SPECK Families of Lightweight Block Ciphers», 2013): блок 64 бита,
  ключ 128 бит, 27 раундов; раунд `x = (ROR(x, 8) + y) ⊕ k_i; y = ROL(y, 3) ⊕ x`. Ключевые слова `l2 l1 l0 k0` —
  `K[0:4] K[4:8] K[8:12] K[12:16]` (big-endian), как в векторах статьи; вектор Speck64/128 из её приложения C —
  в тестах обеих реализаций.
- **Счётчик** — 40 бит, свой у каждого генератора (процесса и метки): старт случайный, +1 на каждый ID, по модулю
  2^40.
- **Нулевой байт** — проверка: фронт принимает метку, только если после расшифрования он 0 и метка — метка бэкенда
  своего вида (§6).

Почему так:
- блочный шифр на различных открытых текстах даёт различные ID: ID одного генератора не повторяются раньше 2^40
  штук (при 10 000 ID в секунду — 3,5 года), ID разных меток не совпадают никогда. У quic-go по умолчанию ID
  случайные, 4 байта, и совпадения возможны;
- для всех без ключа ID — выход псевдослучайной перестановки на различных входах: метки и счётчик не видны, ID
  одного соединения и одного бэкенда не связать;
- случайные 8 байт читаются как одна из k меток с вероятностью k·2⁻²⁴;
- Speck — 32-битные сложения, сдвиги и xor: классическая BPF-программа расшифровывает ID за 590 инструкций из 4096
  (тест `TestCIDBPF` niko-server сверяет её с фронтом). Шаг (г) naive-udp-v1 §5.2 берёт этот же формат.

Что рассматривалось:
- QUIC-LB single-pass: AES-128-ECB над ID в 16 байт (+ байт конфигурации открытым) — длина 17 выделяется, AES в
  классическом BPF не делается;
- QUIC-LB four-pass: Feistel из AES — та же беда с BPF, слабее при коротких половинах;
- «случайная часть + метка под маской от неё»: ID случайные, но совпадения только вероятностные, и при совпадении
  случайной части видно равенство меток.

## 5. Бэкенды

**Hysteria2 (niko-server, sing-quic на sagernet/quic-go v0.61.0-sing-box-mod.12).** `options.cid_key_file` и
`options.cid_label` (оба или ни одного) — генератор отдаётся `quic.Transport.ConnectionIDGenerator` через вендоренный
sing-quic (`ServiceOptions.ConnectionIDGenerator`). Сервер собран с `DisablePathManager`: на новый адрес он переходит
с первого расшифрованного, не повторного пакета оттуда, без проверки пути (так работает port hopping Hysteria2). Так
что клиент Hysteria2 с port hopping (новый сокет на новый порт, то же соединение) ходит по портам слотов через фронт.
Без опций — ID quic-go, случайные, 4 байта.

**naive-quic и DoH3 (rayd, quic-go v0.64.1).** `h3serve.Options.ConnIDs`; генератор с длиной не 8 отвергается
(короче — таблица токенов stateless reset становится читаемой). Серверный менеджер путей quic-go проверяет новый путь
(PATH_CHALLENGE на новый адрес через фронт, PATH_RESPONSE обратно) и переходит после проверки; до неё ответы идут на
старый адрес — при NAT rebinding это около одного RTT потерь. Пакетный сокет IPC даёт каждой датаграмме свой адрес
клиента, и проверка через него работает: тест niko-server `TestNekoServerQUICRebind` (NAT rebinding и переход клиента
`AddPath`/`Probe`/`Switch`) и raycontrol `TestQUICRebindWithNikoServer` (через настоящий фронт).

**Что не меняется.**
- Stateless reset: токен — функция ID и ключа сброса сервиса, как раньше; ID длиной 8, как у h3serve. Пакет с меткой
  верной, но с ID, которого бэкенд не знает (бэкенд перезапущен, соединение закрыто), теперь доходит до бэкенда, и тот
  отвечает сбросом — как обычный сервер QUIC. Без метки — тишина, как раньше.
- Retry: quic-go шлёт его только с `VerifySourceAddress`, которого у нас нет. SCID Retry — тоже с меткой; новый
  Initial идёт по имени.
- Version negotiation, `DisableVersionNegotiationPackets` у hy2-obfs, длины ID клиента — как были. Длина ID сервера
  видна клиенту в длинных заголовках, клиенты (quic-go, Chromium, sing-quic) её принимают любой.

## 6. Фронт

Конфиг: `udp.cid_key_file` и `backends.<имя>.cid_label` (только бэкенд маршрута UDP; без ключа — ошибка `check`).

Для датаграммы, которую не объясняет ни один поток:

1. QUIC Initial известной версии — по имени, как раньше. Первый DCID клиента — его собственный, по метке Initial не
   идёт никогда.
2. Короткий заголовок (`первый байт & 0xC0 = 0x40`, длина не меньше 29: заголовок, 8 байт ID, 4 байта до образца
   защиты заголовка и сам образец) или Handshake QUIC v1/v2 с длиной DCID 8: расшифровать DCID; если нулевой байт 0 и
   метка — метка бэкенда **обычного QUIC** (маршрута по имени), поток закрепляется за ним.
3. Для каждого маршрута salamander: ключ `BLAKE2b-256(пароль ‖ соль)` (тот же, что для проверки Initial), снять
   обфускацию с первых 14 байт; Initial — как раньше; короткий заголовок или Handshake с меткой **этого маршрута** —
   поток его.
4. Иначе — drop, поток не закрепляется.

Метка бэкенда salamander в открытом пакете и метка обычного бэкенда под salamander не принимаются: пакет одного вида не
попадает к бэкенду другого. Датаграмма уходит бэкенду как пришла.

Пределы:
- поток по метке — обычный поток: простой `udp.idle`, общий потолок таблицы (2¹⁸);
- новых потоков по метке с одного источника (адрес IPv4, /64 IPv6) — 32 в секунду, запас 128 (два поколения по
  минуте, как у dnsprobe). Клиент со сменой адреса заводит по потоку на соединение, адрес CGNAT — несколько на всех
  своих; больше бывает только у копий подсмотренных пакетов.

Цена промаха (сверх прежнего): один Speck (27 раундов, десятки наносекунд), если пакет похож на короткий заголовок или
Handshake, и по одному на пароль salamander. Без выделений памяти (тест `TestUDPFrontCIDMissNoAllocations`); замер
`BenchmarkUDPFrontCIDMiss` — 0,2–0,35 мкс на датаграмму.

Попутно: перезапуск фронта и забытый по простою поток больше не обрывают соединения бэкендов с меткой.

## 7. Что видит наблюдатель

- Server connection ID — 8 байт у всех сервисов QUIC ноды (у hy2-masq было 4, у naive-quic и DoH3 давно 8): одна
  длина, распространённая у больших серверов. Каждый ID новый и случаен без ключа; метка, счётчик и связь ID одного
  соединения не видны.
- hy2-obfs: заголовков не видно вовсе (salamander).
- Активный зонд со случайными пакетами получает от фронта тишину, как раньше. Зонд, повторивший подсмотренный пакет
  со своего адреса, доводит его до бэкенда: quic-go отбрасывает повтор (номер пакета уже был); пакет закрытого
  соединения получает stateless reset — как от обычного сервера QUIC.

## 8. Пример

```
секрет  = 00 01 02 … 1f (32 байта подряд)
K       = a99dc1dde3145b2b67350207284bc183
метка   = 0x0102, счётчик = 0x0405060708
x, y    = 01020004 05060708
ID      = 61224892a4254ad8
```

Обе реализации (`nikoserver/quiccid.go`, `internal/quiccid`) проверяют этот пример и вектор Speck64/128 из статьи
(ключ `1b1a1918 13121110 0b0a0908 03020100`, текст `3b726574 7475432d` → `8c6fa548 454e028b`).

## 9. Совместимость

- **Старый фронт, новые бэкенды.** Фронт меток не читает: всё как раньше; ID бэкендов — 8 байт вместо 4 (hy2), это
  клиентам безразлично.
- **Новый фронт, старые бэкенды.** Метку фронт ищет только у бэкендов с `cid_label`; у бэкенда без меток в ID (старый
  процесс, ключ не прочитался) случайные 8 байт проходят за метку с вероятностью k·2⁻²⁴ — такой пакет уходит бэкенду
  и отбрасывается им; клиентам, которые адрес не меняют, ничего не меняется.
- **Конфиги.** niko-server читает конфиги строго: до v0.18.0 незнакомое поле — отказ всего конфига. Поэтому
  raycontrol пишет опции фронта и Hysteria2 только при пине niko-server v0.18.0 и новее (`render.NikoCIDRouteFrom`).
  rayd свои ID метит сразу: старый фронт их просто не читает.
- **По умолчанию включено**, потому что совместимо в обе стороны и клиентам ничего не нужно: секрет создаётся сам,
  выключателя нет. Цена: 4 байта на пакет клиента к hy2-masq (у naive и DoH3 их уже было 8), и бэкенд за фронтом
  отвечает сбросом на пакеты с меткой, которых раньше не видел.

## 10. Угрозы

- **Поток случайных коротких заголовков** — промах без памяти и без состояния (§6).
- **Повтор подсмотренного пакета с подделанных адресов** заводит потоки (до потолка таблицы) и шлёт бэкенду повторы,
  которые тот отбрасывает. То же уже даёт подделанный Initial с маршрутизируемым именем, для которого и подсматривать
  ничего не надо: фронт хуже не стал.
- **Hysteria2 и атакующий на пути.** С `DisablePathManager` сервер переходит на адрес, с которого первым пришёл новый
  (не повторный) пакет; кто на пути и успеет переслать пакет раньше клиента, уведёт поток ответов к себе. Так
  Hysteria2 работает и без фронта (port hopping); раньше фронт закрывал это попутно. quic-go у naive и DoH3 проверяет
  путь.
- **Усиление.** Stateless reset quic-go — 21 байт и только в ответ на пакет длиннее (фронт пропускает от 29). Проверку
  пути quic-go дополняет до 1200 байт без тройного предела RFC 9000 §8, но вызывает её только свежий, не повторный
  пакет живого соединения — то есть атакующий на пути, который задержал оригинал; путей не больше трёх, повторы с
  растущей паузой. Так же quic-go ведёт себя и на голом сокете; за фронтом раньше этого просто не было видно.
- **Утечка секрета.** Его знают фронт, процессы Hysteria2 и naive, rayd. С ним можно читать метки (какой сервис у
  соединения) и делать ID с меткой — то есть слать фронту пакеты, которые он отдаст бэкенду; данных пользователей он
  не открывает. В журналы не пишется ни секрет, ни содержимое файлов.

## 11. Что не сделано

- Выпуск niko-server v0.18.0 и поднятие пина в `deploy/versions.env`: до него фронт меток не читает.
- Клиент: Niko при смене слота может переносить соединение на новый сокет (Hysteria2 — port hopping, quic-go —
  `AddPath`/`Switch`) вместо нового соединения (spa-v2 §11); это работа клиента. На порт нового слота нужен допуск
  SPA, как для нового потока.
- Тест в netns с настоящим `nft redirect` порта слота и сменой порта клиента; замер на телефоне.
- Ротации секрета нет: смена секрета лишает переживших её соединений только маршрутизации по ID.
- Шаг (г) naive-udp-v1 §5.2 — свой сокет у naive с выбором по метке; формат к нему готов.
