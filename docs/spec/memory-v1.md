# memory-v1: память ноды под пределом cgroup

Статус: **решения владельца** (2026-11-24, §1, §9). Реализация — по шагам §8, начиная с niko-server. Обзор
компонентов — §2 (2026-11-24, raycontrol `d1eb229`, niko-server `2c1a054`, форк Xray `a683d47`, slipstream
`server-v0.3.0`).

## 1. Принципы (владелец, 2026-11-24)

1. **Бюджет ноды** — вся память хоста без доли системы: `B = RAM − R`, где `R = max(RAM/20, min(RAM/10, 256 МиБ))`
   (5–10 %: 10 % на малых VPS, не больше 256 МиБ на больших, но не меньше 5 %). В `B` укладывается всё наше:
   control plane и data plane. Из `B` не вылезаем.
2. **Сначала давление, потом убийство.** Каждый компонент держит свои буферы в доле бюджета и при приближении к ней
   притормаживает источник: не читает дальше, не растит окна, не берёт новое. Убийство процесса по OOM — только самый
   крайний случай, когда давление не помогло.
3. **Две цифры.** Пределы юнитов systemd задаются долями памяти (systemd сам пересчитывает их при смене размера VPS),
   а rayctl при `apply` считает те же доли в байтах — для бюджетов внутри процессов, проверок и `rayctl check`. Процесс
   при старте читает свой настоящий предел cgroup; расхождение с рассчитанным rayctl показывает `rayctl check`.
4. **512 МиБ поддерживается.** Нода только с DNS-туннелем и REALITY укладывается в 100–200 МиБ на пике. `rayctl check`
   оценивает сумму включённых сервисов против `B` и предупреждает, если её не хватает, а не отказывает.
5. **Своп — по желанию.** По умолчанию своп хоста остаётся подстраховкой; выключить его для data plane
   (`MemorySwapMax=0`) — настройка ноды.

## 2. Что есть сейчас

- Ни в одном юните нет `Memory*`, `OOMScoreAdjust`, `GOMEMLIMIT`, `GOGC` (`internal/deploy/deploy.go:121-140`).
  `Plan.Check` таких строк и не пропускает (`check.go:224`, `fuzz_test.go:68-70`).
- Go 1.27 память по cgroup сам не учитывает: он читает только `cpu.max`; `GOMEMLIMIT` — только из окружения
  (golang/go#75164 не вошёл).
- Буферы TCP и UDP сокетов ядро записывает на memcg (cgroup v2): при пределе пакеты отбрасываются, процесс не
  убивается. Очереди unix-сокетов не учитываются нигде.
- Бюджет из cgroup есть у Hysteria2 (`niko:nikoserver/hymem.go`) и выходов Yggdrasil (`yggexitmem.go`), но «полы» на
  пользователя и на выход — вне бюджета.
- Самое тяжёлое на пользователя: naive — до ~2 ГиБ (1024 туннеля по 2 МиБ непрочитанного, `naive/limits.go:28`),
  Xray — ~1 ГиБ (1024 соединения по 512 КиБ на направление). rayd (сайт, DoH, API) ограничен только числом соединений.

## 3. В процессе

- **Помощник памяти** — в каждом модуле (niko-server, raycontrol, форк Xray): наименьший `memory.max` и `memory.high`
  процесса и его предков (cgroup v2, затем v1), и `MemTotal`.
- Если `GOMEMLIMIT` не задан и предел cgroup есть, процесс при старте ставит `debug.SetMemoryLimit` ≈ 7/8 предела
  (у фронта ¾: его очереди сокетов Go не видит), не меньше 64 МиБ; одна строка в журнале. Без предела cgroup — ничего:
  `GOMEMLIMIT` от всей памяти хоста ничего не даёт.
- **Бюджеты от того же предела:** Hysteria2 — 3/8 предела юнита (полы на пользователя внутри бюджета, решение §9 п. 6);
  выходы Yggdrasil — треть, число выходов — по бюджету; naive — §5.

## 4. systemd

- `raycontrol-data.slice` для data plane (фронт, бэкенды, Xray, сайт). У slice `MemoryHigh` и `MemoryMax` — его доля
  `B`; у каждого юнита данных свой `MemoryMax` (половина slice, не меньше 128 МиБ) и `MemoryHigh` = 7/8 его `Max`.
  Юниты могут вместе обещать больше slice: один разбушевавшийся упирается в свой предел.
- rayd и rayspa — вне slice, со своими пределами внутри `B`: control plane и SSH переживают любой data plane.
- `OOMPolicy=stop` с `Restart=always`; `OOMScoreAdjust` (первым умирает бэкенд, последним rayspa): rayspa −900,
  rayd −800, фронт −500, Xray −200, сайт 0, остальные бэкенды +200.
- Доли задаются процентами в юнитах (§1 п. 3); `Plan.Check` пропускает только числовые `Memory*` и значения
  `OOMScoreAdjust` из таблицы по виду юнита.

**Как сделано (шаг 4, `internal/deploy/memory.go`).** Память хоста (`MemTotal`) читает тот, кто строит план: rayctl
apply — сам, от root, а не со слов rayd. Из неё:

| | Байты | 512 МиБ | 1 ГиБ | 4 ГиБ | 16 ГиБ |
|---|---|---|---|---|---|
| система `R` | `max(RAM/20, min(RAM/10, 256 МиБ))` | 51 МиБ | 102 МиБ | 256 МиБ | 819 МиБ |
| rayd | `B/4`, от 128 до 512 МиБ | 25,00 % | 22,49 % | 12,50 % | 3,12 % |
| rayspa | 64 МиБ | 12,50 % | 6,25 % | 1,56 % | 0,39 % |
| slice | `B` без rayd и rayspa, не меньше 128 МиБ | 52,50 % | 61,25 % | 79,68 % | 91,48 % |
| юнит данных | половина slice, не меньше 128 МиБ | 26,24 % | 30,62 % | 39,84 % | 45,74 % |

`MemoryHigh` — 7/8 `MemoryMax`. Доли — с двумя знаками (больше systemd не берёт), с округлением вниз. Без известной
памяти хоста строк нет (тесты, `rayd serve -supervise` их и не читает). Slice — файл плана, но не юнит для запуска:
юниты данных создают его своим `Slice=`. В контейнере без делегированного контроллера памяти systemd пределы не
ставит, а понизить `OOMScoreAdjust` без прав не может и это пропускает: юнит работает, как раньше.

## 5. naive: непрочитанное (решение §9 п. 5)

Окна h2/h3 менять нельзя: они те же, что у сайта и DoH. Поэтому:

- **Давление.** Пока назначение не читает, туннель не читает загрузку клиента дальше своей доли, и клиент упирается в
  окно потока. Бюджет ноды и пользователя на непрочитанное — как у Hysteria2.
- **Решение по состоянию потока, а не по возрасту.** Поток, чей клиент жив (подтверждения, `WINDOW_UPDATE`, PING,
  данные в любую сторону), но медленный — например, у него только что появилась сеть и он нагоняет, — держится и
  ждёт. Поток, в котором ни одна сторона не двигается дольше предела, а клиент не подаёт признаков жизни, сбрасывается
  («забыть»). Пределы времени — в реализации, с замером.

**Как сделано (шаг 5, `internal/naive/pressure.go`).** Только TCP-туннели; UoT, UDP и ICMP — как были.

- **Учёт.** Каждый TCP-туннель записан с допуска (до ожидания жетона попытки и до набора) до конца, по пользователю и
  соединению (h2 — сокет соединения, h3 — соединение QUIC, его даёт `h3serve.Conn`). Цена туннеля — `F` всегда и доля
  окна `W`, пока он ждёт (допущен, копирование не началось) или его запись назначению стоит. h2: `W` — окно потока (2
  МиБ), у соединения вместе не больше окна соединения (8 МиБ). h3: `W` — 11 × min(6 МиБ, окно соединения), у соединения
  вместе не больше 11 × окна соединения (768 КиБ и то, на сколько крючок дал ему вырасти): quic-go держит до 11 окон в
  буферах пакетов. Кроме того, соединение h3, где у пользователя есть туннель с незакончившейся загрузкой, стоит ему не
  меньше одного своего окна (несколько пользователей на соединении — каждому): QUIC держит пришедшее не по порядку в
  пакетах, пока дыра не закроется, обработчик этого не видит и ждёт в чтении. Цена соединения — max(1 × окно, min(сумма
  `W`, 11 × окно)). Одно окно — то, что соединение обычно держит, а не худший случай: худший (11 окон при мелких кадрах
  не по порядку) не входит в цену, иначе на хосте в 512 МиБ каждый пользователь h3 был бы сверх доли, а цена включала бы
  давление по верхним оценкам без настоящего; его ограничивает отметка 2 (ниже, последний этап). Поток, чья запись
  клиенту стоит, процессу больше не стоит ничего: он держит память сокета назначения в ядре (`SO_MEMINFO`: принятое,
  очередь отправки, выделенное наперёд, backlog), её читают только в раунде сброса. Сброшенный поток сразу ничего не
  стоит. Отметки «пишет с…» (и у h3 «читает загрузку с…») — атомики на поток, две записи на запись или чтение 32 КиБ,
  без блокировок. Сканер проходит туннели один раз под блокировкой, читая только атомики, а список кандидатов строит,
  лишь когда сигнал у первой отметки или давление уже есть: на 10⁵ туннелях блокировка держится 2–4 мс в секунду без
  выделений памяти (было 18–23 мс и 8 МБ, `BenchmarkTick`).
- **`F` = 96 КиБ** — замер `TestTunnelCost` (Go 1.27, amd64, петля, 200 туннелей, клиент — другой процесс): куча и
  стеки простаивающего туннеля, h2 90–91 КиБ, h3 80–81 КиБ, в том числе два буфера копирования по 32 КиБ.
- **Бюджет `B`** — половина основы предела юнита (`memlimit.Limits.Base`: меньшее из `memory.high` и 15/16
  `memory.max`, та же, от которой предел Go), без пола; без предела cgroup — восьмая часть памяти хоста, 32 МиБ – 2 ГиБ.
  Справедливая доля — `B` на число пользователей с туннелем, не меньше чем на 8. Для юнита данных:

  | Хост | `MemoryMax` юнита | `B` | Доля (на 8) |
  |---|---|---|---|
  | 512 МиБ | 134,4 МиБ | 58,8 МиБ | 7,3 МиБ |
  | 1 ГиБ | 313,5 МиБ | 137,2 МиБ | 17,1 МиБ |
  | 4 ГиБ | 1632 МиБ | 714 МиБ | 89,3 МиБ |

- **Отметка 1 — рост останавливается.** Пока цена ноды ≥ `B` или есть давление, новый TCP CONNECT пользователя, чья
  цена — его доля или больше, получает 429 до 200 (вид отказа `memory`, как у Hysteria2; с niko-ack и без — как
  другие 429 пределов), при любом выключателе пределов; окна соединений h3 не растут (крючок
  `AllowConnectionWindowIncrease` через `h3serve.Options.Window`; окна и параметры транспорта, с которыми соединение
  начинается, те же, что у DoH3, — `TestQUICNamesLookAlike`). Проверка и запись — один шаг под одной блокировкой: залп
  CONNECT взвешивается по одному. Ниже `B` никого не ограничивают сверх прежних пределов. Отметка 1 — только допуск:
  память она не ограничивает, это делает отметка 2.
- **Отметка 2 — сброс, только при настоящем давлении.** Сканер раз в секунду (`Server.WatchMemory`). Давление
  включается, когда хоть одно:
  1. живая куча + стеки + `sock` из `memory.stat` юнита ≥ 85 % предела Go (7/8 предела юнита); выключается ≤ 70 %;
  2. min(цель кучи, предел Go) + стеки + `sock` ≥ 95 % меньшего из `memory.high` и 15/16 `memory.max`; выкл. ≤ 85 %;
  3. цена ноды ≥ 1,5 `B`; выкл. ≤ 1,25 `B`. Работает и без cgroup; без предела cgroup — единственный.

  Давление снимается, когда все три ниже своих вторых отметок. Раунд сбрасывает не больше 64 потоков и останавливается,
  как только по оценке (цена потока, у загрузки — его `SO_MEMINFO`) сигнал уйдёт под первую отметку; между второй и
  первой раунда нет. После раунда по сигналу 1 или 2 следующий такой ждёт двух циклов GC (`/gc/cycles/total`) от
  взгляда после раунда — к нему сброшенные туннели уже ушли (стоящую запись снимают за секунду), а цикл, что шёл,
  мог разметить кучу до того. Пока ждёт, куча считается такой, какой её видел раунд, без того, что он счёл
  освобождённым (только кучу: `F` и доли окна; память сокетов, что он освободил, уже в свежем `sock`): раунд раньше GC
  приходит, только если сигнал выше отметки за счёт роста `sock`. И не позже пятого взгляда после раунда, пока отметка
  превышена, — GC или нет. Раунды по цене не ждут.
- **Кого.** Сбрасываются только ждущие и стоящие в записи (в любую сторону); туннель без того и другого (простаивающий
  SSH, websocket) — никогда (`TestIdleTunnelsStay`), с одним исключением ниже. Сначала пользователи сверх доли, самый
  дорогой первым; у пользователя — стоящие дольше 10 с (как тишина UoT, `quietAfter`), дольше стоящие первыми; затем
  ждущие и стоящие меньше 10 с — только у пользователя на двух долях и больше, или когда стоящих дольше 10 с у
  пользователей сверх доли не осталось. В каждом классе сначала держащие окно (ждущие и стоящие на загрузке назначению),
  потом стоящие на записи клиенту, по `SO_MEMINFO`. Исключение — h3: когда у пользователей сверх доли не осталось ни
  ждущих, ни стоящих, а давление держится, сбрасываются их туннели h3, чьё чтение загрузки ждёт дольше 10 с, дольше
  ждущие первыми: то, что пришло не по порядку, обработчику не видно, а память держит (`TestEvictReading`). У h2 такого
  нет (тело потока видно целиком). Последний этап — пользователи в своей доле, пока давление держится, самый дорогой
  первым: их стоящие дольше 10 с, а пока держится давление памяти (сигналы 1 и 2, не цена) — и их туннели h3, чьё чтение
  загрузки ждёт дольше 10 с (`TestEvictReadingWithinShare`). Цена этапа: при настоящем давлении, когда у пользователей
  сверх доли отдать нечего, сбрасываются простаивающие туннели h3 самых дорогих пользователей. Туннели h2 без ждущего и
  стоящего не сбрасываются ни на каком этапе. Поток, сброшенный в ожидании жетона или набора, и поток, чей пользователь
  отозван в ожидании жетона, получают сброс, а не 429, и отказом `rate` не считаются. Сброс — отмена с `errEvicted` и
  `http.ErrAbortHandler`: клиент видит `RST_STREAM` или сброс h3, а не чистый конец оборванной загрузки; запись, что
  стоит, снимает прежний путь (1 с, затем `SetWriteDeadline`).
- **Мёртвые клиенты.** Таймера на туннели нет. Сокет h2-соединения получает `TCP_USER_TIMEOUT` 2 мин (Linux) один раз,
  при первом потоке с принятым паролем, не раньше: до пароля сокет — сайта, и предел его повторов передачи (~15 мин
  ядра) тот же, что у сайта. Клиент, что не подтверждает данные сервера 2 минуты, уходит вместе с туннелями; так же
  клиент, замерший на 2 минуты, пока у ноды есть для него неотправленное, теряет соединение h2 со всеми туннелями; h3
  так и было — через 2 мин тишины. Принято как оговорка: клиент, который держит нулевое окно TCP 2 минуты, отвечая на
  пробы окна, тоже обрывается (ядро 6.18: при таймауте 1 с — через 1,4 с, `TestUserTimeoutZeroWindow`). Клиент h2 читает
  свой сокет, пока жив: нулевое окно TCP — это процесс, который сокет не читает вовсе.
- **Видно.** Ответ `traffic` сокета статистики — поле `memory` (бюджет, цена, давление, отказы, сбросы с запуска, только
  числа); `rayctl metrics` — `raycontrol_naive_tunnels_*` (строка читается один раз и для них, и для UDP). Отказы — ещё
  и вид `memory` по пользователю (§3.2 conn-limit-v1). Одно предупреждение в журнале не чаще раза в минуту, только
  числа.
- **Цена.** `BenchmarkTunnel` (петля, 1 МиБ за итерацию, по 10 прогонов, benchstat): h2 и h3 в обе стороны — без
  значимой разницы с `main` (p ≥ 0,19, среднее геометрическое −2,6 % времени, в пределах шума).
- **Не в этом шаге:**
  - PING сервера по h2 — видны на проводе у сервера, общего с сайтом; решение владельца;
  - `TCP_NOTSENT_LOWAT` на сокетах назначения — на сокетах клиента он стоил ~7 % на петле (`socket.go`), а память
    ядра под стоящей загрузкой и так учтена отметкой 2;
  - `TCP_USER_TIMEOUT` на сокетах назначения — назначение, что не подтверждает, держит лишь свой сокет, его учитывает
    `sock`;
  - меньшая `F` (общие буферы копирования) — отдельная работа ради ~64 КиБ на туннель;
  - привязка крючка h3 к пользователю — соединение h3 ещё не знает пароля, когда растёт окно.

## 6. slipstream и Xray

- slipstream: raycontrol передаёт `--max-pending-mib` (¼ предела юнита, 8–64) и ограничивает `--max-connections` по
  пределу (≈400 КиБ на соединение). Правок в C не нужно.
- Xray: raycontrol задаёт `policy.levels.0.bufferSize` по бюджету (64–256 КиБ). В форк — только помощник памяти.
  Пределы XHTTP (`scMaxBufferedPosts`, `scMaxEachPostBytes`) — вместе с клиентом, в спецификации XHTTP формы A.

## 7. Проверка

- Тесты помощника на поддельных `/proc/self/cgroup` и `memory.*`.
- Нагрузка niko-loadgen под `systemd-run --scope -p MemoryMax=256M` в CI: `memory.events` без `oom_kill`,
  пропускная способность в пределах.
- Установка в контейнерах на 512 МиБ и 1 ГиБ: `EffectiveMemoryMax` у каждого юнита; под злым потоком растут
  `NRestarts` только у бэкенда, rayd, rayspa и фронт живы.

   контейнерах с пределом. **Сделано:** slice, `Memory*`, `OOMScoreAdjust`, `OOMPolicy`, `Plan.Check` и fuzz (§4).
   Аргументы slipstream (§6): `--max-pending-mib` — четверть предела юнита, 8–64; `--max-connections` — не больше, чем
   помещается по 400 КиБ, 16 и больше. `bufferSize` Xray (§6): rayd при старте считает юнит данных от памяти хоста, и
   1024 соединения в обе стороны укладываются в него, 64–256 КиБ (у Xray было 512). `rayctl check` (предупреждения):
   бюджет хоста и его доли; держит ли ядро каждый работающий юнит в его пределе (`memory.max` cgroup против
   `MemoryMax` systemd: в контейнере без контроллера памяти и на cgroup v1 предела нет); data plane на своей отметке
   `memory.high` — сервисы вместе хотят больше, чем есть. Тест установки проверяет slice, оценки OOM и предел фронта.
   Осталось: своп, юниты relay, установка с пределом памяти контейнера в CI.
5. raycontrol C: naive — давление и решение по состоянию потока (§5). **Сделано:** учёт TCP-туннелей (`F` 96 КиБ по
   замеру и доля окна), отметка 1 — 429 сверх доли и окна h3 не растут при цене у бюджета, отметка 2 — сброс стоящих
   под давлением кучи, `sock` или цены, сначала у пользователей сверх доли; `TCP_USER_TIMEOUT` у h2-клиентов; поле
   `memory` сокета статистики и `rayctl metrics` (§5).
6. raycontrol D: DoH в отдельный юнит (решение §9 п. 4).
7. С XHTTP: его пределы и бюджет загрузок в форке.

## 9. Решения владельца (2026-11-24)

1. Бюджет — память без 5–10 % системы; сначала давление, OOM — крайний случай (§1).
2. Пределы — двумя цифрами: доли в systemd и байты в rayctl (§1 п. 3).
3. 512 МиБ поддерживается; DNS + REALITY — 100–200 МиБ (§1 п. 4).
4. DoH — в отдельный юнит, отдельным шагом.
5. naive — решать по состоянию потока и признакам клиента: медленного ждать, мёртвого забыть (§5).
6. Hysteria2 — полы на пользователя внутри общего бюджета.
7. Своп — по желанию, как подстраховка (§1 п. 5).
8. XHTTP — пределы согласуем с клиентом в спецификации формы A.
