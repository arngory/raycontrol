# memory-v1: память ноды под пределом cgroup

Статус: **решения владельца** (2026-11-24, §1, §9). Реализация — по шагам §8, начиная с niko-server. Обзор
компонентов — §2 (2026-11-24, raycontrol `d1eb229`, niko-server `2c1a054`, форк Xray `a683d47`, slipstream
`server-v0.3.0`).

## 1. Принципы (владелец, 2026-11-24)

1. **Бюджет ноды** — вся память хоста без доли системы: `B = RAM − R`, где `R = max(RAM/20, min(RAM/10, 256 МиБ))`
   (5–10 %: 10 % на малых VPS, не больше 256 МиБ на больших, но не меньше 5 %). В `B` укладывается всё наше:
   control plane и data plane. Из `B` не вылезаем.
2. **Сначала давление, потом убийство.** Каждый компонент держит свои буферы в доле бюджета и при приближении к ней
   притормаживает источник: не читает дальше, не растит окна, не берёт новое. Убийство процесса по OOM — только самый
   крайний случай, когда давление не помогло.
3. **Две цифры.** Пределы юнитов systemd задаются долями памяти (systemd сам пересчитывает их при смене размера VPS),
   а rayctl при `apply` считает те же доли в байтах — для бюджетов внутри процессов, проверок и `rayctl check`. Процесс
   при старте читает свой настоящий предел cgroup; расхождение с рассчитанным rayctl показывает `rayctl check`.
4. **512 МиБ поддерживается.** Нода только с DNS-туннелем и REALITY укладывается в 100–200 МиБ на пике. `rayctl check`
   оценивает сумму включённых сервисов против `B` и предупреждает, если её не хватает, а не отказывает.
5. **Своп — по желанию.** По умолчанию своп хоста остаётся подстраховкой; выключить его для data plane
   (`MemorySwapMax=0`) — настройка ноды.

## 2. Что есть сейчас

- Ни в одном юните нет `Memory*`, `OOMScoreAdjust`, `GOMEMLIMIT`, `GOGC` (`internal/deploy/deploy.go:121-140`).
  `Plan.Check` таких строк и не пропускает (`check.go:224`, `fuzz_test.go:68-70`).
- Go 1.27 память по cgroup сам не учитывает: он читает только `cpu.max`; `GOMEMLIMIT` — только из окружения
  (golang/go#75164 не вошёл).
- Буферы TCP и UDP сокетов ядро записывает на memcg (cgroup v2): при пределе пакеты отбрасываются, процесс не
  убивается. Очереди unix-сокетов не учитываются нигде.
- Бюджет из cgroup есть у Hysteria2 (`niko:nikoserver/hymem.go`) и выходов Yggdrasil (`yggexitmem.go`), но «полы» на
  пользователя и на выход — вне бюджета.
- Самое тяжёлое на пользователя: naive — до ~2 ГиБ (1024 туннеля по 2 МиБ непрочитанного, `naive/limits.go:28`),
  Xray — ~1 ГиБ (1024 соединения по 512 КиБ на направление). rayd (сайт, DoH, API) ограничен только числом соединений.

## 3. В процессе

- **Помощник памяти** — в каждом модуле (niko-server, raycontrol, форк Xray): наименьший `memory.max` и `memory.high`
  процесса и его предков (cgroup v2, затем v1), и `MemTotal`.
- Если `GOMEMLIMIT` не задан и предел cgroup есть, процесс при старте ставит `debug.SetMemoryLimit` ≈ 7/8 предела
  (у фронта ¾: его очереди сокетов Go не видит), не меньше 64 МиБ; одна строка в журнале. Без предела cgroup — ничего:
  `GOMEMLIMIT` от всей памяти хоста ничего не даёт.
- **Бюджеты от того же предела:** Hysteria2 — 3/8 предела юнита (полы на пользователя внутри бюджета, решение §9 п. 6);
  выходы Yggdrasil — треть, число выходов — по бюджету; naive — §5.

## 4. systemd

- `raycontrol-data.slice` для data plane (фронт, бэкенды, Xray, сайт). У slice `MemoryHigh` и `MemoryMax` — его доля
  `B`; у каждого юнита данных свой `MemoryMax` (половина slice, не меньше 128 МиБ) и `MemoryHigh` = 7/8 его `Max`.
  Юниты могут вместе обещать больше slice: один разбушевавшийся упирается в свой предел.
- rayd и rayspa — вне slice, со своими пределами внутри `B`: control plane и SSH переживают любой data plane.
- `OOMPolicy=stop` с `Restart=always`; `OOMScoreAdjust` (первым умирает бэкенд, последним rayspa): rayspa −900,
  rayd −800, фронт −500, Xray −200, сайт 0, остальные бэкенды +200.
- Доли задаются процентами в юнитах (§1 п. 3); `Plan.Check` пропускает только числовые `Memory*` и значения
  `OOMScoreAdjust` из таблицы по виду юнита.

**Как сделано (шаг 4, `internal/deploy/memory.go`).** Память хоста (`MemTotal`) читает тот, кто строит план: rayctl
apply — сам, от root, а не со слов rayd. Из неё:

| | Байты | 512 МиБ | 1 ГиБ | 4 ГиБ | 16 ГиБ |
|---|---|---|---|---|---|
| система `R` | `max(RAM/20, min(RAM/10, 256 МиБ))` | 51 МиБ | 102 МиБ | 256 МиБ | 819 МиБ |
| rayd | `B/4`, от 128 до 512 МиБ | 25,00 % | 22,49 % | 12,50 % | 3,12 % |
| rayspa | 64 МиБ | 12,50 % | 6,25 % | 1,56 % | 0,39 % |
| slice | `B` без rayd и rayspa, не меньше 128 МиБ | 52,50 % | 61,25 % | 79,68 % | 91,48 % |
| юнит данных | половина slice, не меньше 128 МиБ | 26,24 % | 30,62 % | 39,84 % | 45,74 % |

`MemoryHigh` — 7/8 `MemoryMax`. Доли — с двумя знаками (больше systemd не берёт), с округлением вниз. Без известной
памяти хоста строк нет (тесты, `rayd serve -supervise` их и не читает). Slice — файл плана, но не юнит для запуска:
юниты данных создают его своим `Slice=`. В контейнере без делегированного контроллера памяти systemd пределы не
ставит, а понизить `OOMScoreAdjust` без прав не может и это пропускает: юнит работает, как раньше.

## 5. naive: непрочитанное (решение §9 п. 5)

Окна h2/h3 менять нельзя: они те же, что у сайта и DoH. Поэтому:

- **Давление.** Пока назначение не читает, туннель не читает загрузку клиента дальше своей доли, и клиент упирается в
  окно потока. Бюджет ноды и пользователя на непрочитанное — как у Hysteria2.
- **Решение по состоянию потока, а не по возрасту.** Поток, чей клиент жив (подтверждения, `WINDOW_UPDATE`, PING,
  данные в любую сторону), но медленный — например, у него только что появилась сеть и он нагоняет, — держится и
  ждёт. Поток, в котором ни одна сторона не двигается дольше предела, а клиент не подаёт признаков жизни, сбрасывается
  («забыть»). Пределы времени — в реализации, с замером.

## 6. slipstream и Xray

- slipstream: raycontrol передаёт `--max-pending-mib` (¼ предела юнита, 8–64) и ограничивает `--max-connections` по
  пределу (≈400 КиБ на соединение). Правок в C не нужно.
- Xray: raycontrol задаёт `policy.levels.0.bufferSize` по бюджету (64–256 КиБ). В форк — только помощник памяти.
  Пределы XHTTP (`scMaxBufferedPosts`, `scMaxEachPostBytes`) — вместе с клиентом, в спецификации XHTTP формы A.

## 7. Проверка

- Тесты помощника на поддельных `/proc/self/cgroup` и `memory.*`.
- Нагрузка niko-loadgen под `systemd-run --scope -p MemoryMax=256M` в CI: `memory.events` без `oom_kill`,
  пропускная способность в пределах.
- Установка в контейнерах на 512 МиБ и 1 ГиБ: `EffectiveMemoryMax` у каждого юнита; под злым потоком растут
  `NRestarts` только у бэкенда, rayd, rayspa и фронт живы.

## 8. Шаги

1. niko-server: помощник памяти, `GOMEMLIMIT` фронта и бэкендов, доли Hysteria2 и Yggdrasil, полы внутри бюджета,
   niko-loadgen на cgroup v2. **Сделано:** niko-server v0.19.3.
2. Форк Xray (`raycontrol/v26.11.9`): помощник памяти; FORK.md и пин. **Сделано:** `common/memlimit`, FORK.md §6
   (arngory/Xray-core#10), пин `4eed279`.
3. raycontrol A: помощник в rayd, naive, сайте, rayspa. **Сделано:** `internal/memlimit`; `rayd serve`, `site`,
   `naive`, `relay` и `rayspa run` ставят предел Go 7/8 от предела cgroup.
4. raycontrol B: slice, `Memory*`, `OOMScoreAdjust`, `OOMPolicy`, своп по настройке, `Plan.Check` и fuzz,
   `rayctl check` (бюджет, сумма сервисов, расхождение с cgroup), `bufferSize` Xray, аргументы slipstream, установка в
   контейнерах с пределом. **Сделано:** slice, `Memory*`, `OOMScoreAdjust`, `OOMPolicy`, `Plan.Check` и fuzz (§4).
   Аргументы slipstream (§6): `--max-pending-mib` — четверть предела юнита, 8–64; `--max-connections` — не больше, чем
   помещается по 400 КиБ, 16 и больше. `bufferSize` Xray (§6): rayd при старте считает юнит данных от памяти хоста, и
   1024 соединения в обе стороны укладываются в него, 64–256 КиБ (у Xray было 512). Осталось: своп, `rayctl check`,
   юниты relay, установка с пределом в CI.
5. raycontrol C: naive — давление и решение по состоянию потока (§5).
6. raycontrol D: DoH в отдельный юнит (решение §9 п. 4).
7. С XHTTP: его пределы и бюджет загрузок в форке.

## 9. Решения владельца (2026-11-24)

1. Бюджет — память без 5–10 % системы; сначала давление, OOM — крайний случай (§1).
2. Пределы — двумя цифрами: доли в systemd и байты в rayctl (§1 п. 3).
3. 512 МиБ поддерживается; DNS + REALITY — 100–200 МиБ (§1 п. 4).
4. DoH — в отдельный юнит, отдельным шагом.
5. naive — решать по состоянию потока и признакам клиента: медленного ждать, мёртвого забыть (§5).
6. Hysteria2 — полы на пользователя внутри общего бюджета.
7. Своп — по желанию, как подстраховка (§1 п. 5).
8. XHTTP — пределы согласуем с клиентом в спецификации формы A.
