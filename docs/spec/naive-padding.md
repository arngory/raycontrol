# naive-padding: паддинг naive на ноде

Статус: **действует** со следующего выпуска после raycontrol v0.26.0 (`rayd naive`, HTTP/2 и HTTP/3). Код — `internal/naive/padding.go`,
тесты — `internal/naive/padding_test.go`. Источник протокола — klzgrad/naiveproxy (`src/net/tools/naive/`, сверено с
`/home/user/naiveproxy` на 158.0.8127.36, файлы паддинга совпадают с веткой master klzgrad байт в байт); образец
сервера — форк forwardproxy для Caddy (`klzgrad/forwardproxy`, ветка `naive`, `forwardproxy.go`). Ссылки на строки
ниже — по этим файлам.

## 1. Что такое паддинг naive

Две вещи, обе против анализа длин:

1. **Заголовок `Padding`** в запросе CONNECT и в ответе: строка случайной длины. Прячет длину остального блока
   заголовков (пароль, адрес назначения).
2. **Кадры паддинга** — первые 8 записей в каждую сторону внутри потока туннеля:

   ```
   [длина данных: u16 BE][длина паддинга: u8][данные][нули: длина паддинга]
   ```

   Девятая запись и дальше — поток как есть, без кадров. Одна запись — один кадр; пустых записей не бывает.

## 2. Согласование типа

Типы (`naive_protocol.h`): `0` — без паддинга, `1` — вариант 1, кадры из §1.

- Клиент, который знает больше одного типа, шлёт `padding-type-request: 1, 0` — через запятую, предпочтительный
  первым (`naive_proxy_delegate.cc:35-36`; список `{kVariant1, kNone}` — `naive_proxy_bin.cc:256`, `:556-557`).
- Сервер отвечает одним типом в `padding-type-reply`.
- Без ответа клиент решает сам: есть `padding` в ответе — тип 1, нет — 0 (`naive_proxy_delegate.cc:118-139`). Решение
  он принимает по **каждому** ответу на CONNECT, с любым статусом (разбор заголовков идёт раньше проверки статуса:
  `spdy_proxy_client_socket.cc:572` и `:598`, `quic_proxy_client_socket.cc:533` и `:559`), и помнит один тип на весь
  прокси. Следующий туннель с fast open начинает писать по запомненному типу, не дожидаясь своего ответа.
- Ответ, который клиент не может разобрать (`padding-type-reply: 7`), — ошибка `ERR_INVALID_RESPONSE`.

Что делает нода:

| Запрос | Ответ | Кадры туннеля |
|---|---|---|
| `Padding`, без `Padding-Type-Request` (Niko, sing-box, старые клиенты) | `Padding`, без `Padding-Type-Reply` — как раньше | тип 1 |
| `Padding-Type-Request`, первый известный тип — `1` (`1, 0`) | `Padding` и `Padding-Type-Reply: 1` | тип 1 |
| первый известный тип — `0` (`0, 1`, `0`) | `Padding` и `Padding-Type-Reply: 0` | без кадров в обе стороны |
| в списке нет ни `0`, ни `1` (`2`) | как без заголовка: `Padding`, ответа нет | тип 1 |
| без `Padding` | ответ сайта (пустой `404`), заголовок типа не смотрится | — |
| неверный пароль | ответ сайта, ни `Padding`, ни ответа о типе | — |

- Неизвестный тип в списке пропускается, а не ломает запрос. Собственный сервер klzgrad на неизвестном типе
  отказывает (`http_proxy_server_socket.cc:290-305`): клиент будущей версии, который поставит свой тип первым,
  получил бы отказ вместо известного ему типа из того же списка.
- Ответ о типе и `Padding` несёт **каждый** ответ на аутентифицированный CONNECT: `200` туннеля TCP, потоков UoT
  (`sp.v2.udp-over-tcp.arpa`) и ICMP (`icmp.niko.arpa`), `502` и `504` честного connect, `429` пределов и `502`
  `denied` плохой цели с `niko-ack`. Иначе ответ с другим смыслом сбил бы клиенту тип для соседнего туннеля
  ([naive-uot-v1](naive-uot-v1.md) §4.1).
- Потоки UoT и ICMP паддятся так же, как TCP: их формат ([naive-uot-v1](naive-uot-v1.md) §2,
  [icmp-v1](icmp-v1.md) §2) — внутри потока туннеля, после снятия кадров. С типом `0` — без кадров.
- Плохая цель без `niko-ack` получает ответ сайта, без `Padding`: клиент на Chromium такой цели не шлёт.

## 3. Кадры: сверка с апстримом

| Что | Нода | klzgrad | forwardproxy |
|---|---|---|---|
| сколько записей паддится | 8 в каждую сторону (`paddingFrames`) | 8 (`naive_padding_socket.cc:20`) | 8 (`forwardproxy.go:665`) |
| заголовок кадра | 3 байта: длина u16 BE, паддинг u8 | то же (`naive_padding_framer.cc:111-113`) | то же (`forwardproxy.go:716-718`) |
| паддинг | нули | нули (`naive_padding_framer.cc:115`) | нули |
| длина паддинга от сервера | равномерно 0–255 | на стороне сервера равномерно 0–255 (`naive_padding_socket.cc:204`) | `rand.Intn(256)` (`:712`) |
| наибольший кадр | 64 КиБ вместе с заголовком и паддингом: данных не больше 65 533 − паддинг, остаток — следующим кадром | то же: кадр строится в буфере `kMaxBufferSize` 64 КиБ (`naive_padding_socket.cc:19`, `:194-208`; `naive_padding_framer.cc:106-107`) | данных не больше 65 530 − паддинг (`:713-714`) |
| кадр без данных при чтении | принимается | принимается (`naive_padding_framer.cc:28-94`) | — |
| поток кончился внутри кадра | ошибка `ErrUnexpectedEOF` | конец потока | конец потока |

Раньше у ноды кадр бывал до 65 793 байт (данных до 65 535 при любом паддинге). Клиентам это не мешало: читатель
klzgrad держит состояние кадра между чтениями любого размера. На деле запись туннеля не длиннее 32 КиБ (буфер
копирования), так что на проводе ничего не меняется.

**Чего у ноды нет и почему.**
- **Формовка мелких записей.** Клиент klzgrad, отправляя серверу, ставит записи короче 100 байт паддинг от
  `255 − длина` до 255 и режет записи 200–1024 байт на куски по 100–200 байт (`naive_padding_socket.cc:196-202`,
  `:255-258`, направление `kServer` — сокет к прокси-серверу, `naive_connection.cc:306-307`). Это поведение
  **клиента** на выгрузке. Сервер klzgrad (направление `kClient`, `naive_connection.cc:193-194`) и forwardproxy
  паддят равномерно; нода — как они.
- **Паддинг перед `RST_STREAM`.** Chromium перед каждым своим `RST_STREAM` шлёт пустой кадр DATA с паддингом, чтобы
  вместе выходило 48–72 байта (`net/spdy/spdy_session.cc:1926-1943`). Тоже поведение клиента; сервер HTTP/2 в Go
  (и Caddy) шлёт голый `RST_STREAM` в 13 байт, и обработчик это не меняет.

## 4. Заголовок `Padding`

| | Нода (ответ) | forwardproxy (ответ) | сервер klzgrad (ответ, HTTP/1.1) | клиент klzgrad (запрос) | Niko (cronet-go, запрос) |
|---|---|---|---|---|---|
| длина | 30–61 | 30–61 (`forwardproxy.go:309`) | 30–62 (`http_proxy_server_socket.cc:41-42`, `:450-451`) | 16–32 (`naive_proxy_delegate.cc:64`) | 30–61 (`naive_conn.go:24`) |
| первые 16 символов | случайные, по 4 бита, из `!#$()+<>?@[]^`{}` | то же (`:311-316`) | из `!"#$&'()*+,;<>?@` | то же, что сервер klzgrad | как у ноды |
| остальные | `~` | `~` (`:317-319`) | `X` | `X` | `~` |

Алфавит klzgrad — первые 17 символов ASCII с кодом Хаффмана HPACK не короче 8 бит (`padding_utils.cc:18-33`,
`:36-46`); алфавит forwardproxy и ноды — другой набор с тем же свойством (RFC 7541, приложение B: от 10 до 15 бит).
Свойство нужно затем, чтобы кодировщик HPACK, который берёт Хаффман только там, где он короче (Go и Chromium), слал
строку как есть: длина заголовка на проводе — та, что выпала. Образец для сервера — forwardproxy: это сервер, с
которым клиенты naive работают на деле, а собственный сервер klzgrad говорит только HTTP/1.1. Нода с ним совпадает.

Расхождение, которое остаётся: кодировщик QPACK в quic-go (qpack v0.6.0, `encoder.go:68-86`) кодирует Хаффманом
всегда. По HTTP/3 заголовок ответа на проводе в полтора-два раза длиннее выпавшей строки; у DoH3 и naive-quic это
одинаково (один сервер), у Caddy — так же.

## 5. Совместимость

- Клиенты без `Padding-Type-Request` — Niko (cronet-go `NaiveClient`: заголовка нет, `naive_client.go:510-513`;
  паддит всегда, ответ не смотрит, `naive_conn.go:19`, `:91-107`, `:197-224`), sing-box, старые клиенты — видят
  ровно то, что раньше.
- Клиенту, который начнёт слать `Padding-Type-Request`, нужно либо следовать ответу, либо перечислять только `1`:
  cronet-go паддит первые кадры, что бы ни ответил сервер, и с ответом `0` его поток разошёлся бы с сервером.
