# 09. Логи, телеметрия, QA и обезличенные идентификаторы

Статус: **принят** (решения R4-3…R4-6 в [08-decisions.md](08-decisions.md)). Реализация: `internal/redact`,
`rayctl report`, `rayctl probe -redact`, уровни логов `rayspa`, анонимные имена пользователей.

## 1. Принципы

1. **Нода ничего не отправляет сама.** Ни телеметрии, ни отчётов о падениях, ни «проверки обновлений» с идентификатором.
   Всё, что уходит наружу, уходит руками администратора и после того, как он это прочитал.
2. **Минимум данных о людях.** Нода не знает ни почты, ни телефона, ни имени: пользователь — это непрозрачный номер
   (как учётные номера у iVPN или Xeovo), устройство — случайный ID.
3. **Активность пользователей не пишется.** Кто, откуда и куда подключался, не попадает в журналы на обычном уровне;
   подробности есть только в режиме отладки, который включают на время.
4. **Делиться безопасно должно быть просто.** Для issue есть одна команда, `rayctl report`, и её вывод уже очищен.

## 2. Классы данных

| Класс | Что это | Где бывает | Можно ли делиться |
|---|---|---|---|
| **P0 — открытое** | версии компонентов, ОС, ядро, systemd, nft, включённые виды сервисов и их число, результаты проверок, состояние юнитов, категории ошибок | `rayctl report` | да, всегда |
| **P1 — узнаваемое** | адрес и домен ноды, поддомены, зоны туннелей, SNI, порты (диапазон SPA, сервисы, ACME), имена сервисов, ID ноды и устройств | конфиги, журналы при ошибках | только в виде токенов (`<domain>`, `<ip4:1a2b3c>`, `<id>`) |
| **P2 — секреты** | ключи ноды, REALITY, туннелей, аккаунта ACME; токен Cloudflare; UUID; пакеты `rcdev1`; ссылки; база | `/var/lib/raycontrol`, отрисованные файлы | никогда; только зашифрованный бэкап владельца |
| **P3 — активность** | IP клиентов, время подключений, устройства, адреса назначения | нигде по умолчанию | нет |

## 3. Журналы

Всё пишется в journald хоста, файлов своих логов нет.

| Компонент | Обычный уровень (info) | Отладка (`-debug` или окно `rayctl debug`) |
|---|---|---|
| `rayspa` | таблица поднята или восстановлена, снимок применён (число устройств), окно ACME, ошибки | каждый SPA-доступ и отказ с адресом и устройством, отзыв с адресом |
| `rayd` | запуск, сертификаты, ротация (число записей), ошибки отрисовки и API | отказы подписки с адресом |
| Xray (`inner`, REALITY) | `loglevel warning`, `access none` | в окне: `loglevel info`, `access none` |
| niko-server | `warn` | в окне: `debug` |
| сайт-приманка | ошибки запуска | ошибки TLS-рукопожатий |

Отладку включают на время разбора и выключают: адреса клиентов в журнале — это P3.

**Окно отладки** (raycontrol v0.11.1): `rayctl debug on -for 30m` поднимает уровни rayd, rayspa и data plane до
конца окна, не дольше суток, и окно закрывается само. Только на ноде, от root: удалённый API его не открывает, а
журнал читает только root. Службы data plane перезапускаются при открытии и закрытии окна. Окно и его длина
пишутся в аудит. Выгрузка — `rayctl report -logs debug -since … -id …`. Ротацией журнала занимается
journald хоста (`SystemMaxUse`, `MaxRetentionSec`).

## 4. Отчёт для issue: `rayctl report`

- Собирает P0 и очищенные журналы: версии, систему, проверки хоста (`preflight`), состояние и число перезапусков юнитов,
  есть ли таблица периметра, счётчики (пользователи, устройства, сервисы по видам — без имён), сводку журнала установки,
  предупреждения из journald за сутки (`-logs info`, `-since 72h` — больше; `-logs debug` — со строками отладки
  `rayd -debug` и `rayspa -debug`, они тоже проходят очистку).
- Очистка (`internal/redact`): адреса → `<ip4:…>`/`<ip6:…>`, токены совпадают внутри одного отчёта (видно, что строки
  про один адрес) и не совпадают между отчётами (соль на отчёт); имена ноды и её поддомены → `<sub>.<domain>`; UUID,
  ссылки, пакеты, PEM, длинные base64/hex (ключи, подписи) и ID → заглушки. Loopback и `0.0.0.0` остаются.
- Ещё в отчёте: какой DNS-провайдер и сколько проблем с записями (без имён), сколько пакетов отброшено цепочкой
  `early` до стека ядра (R4-9), предупреждения о неперезагруженном ядре и выключенных автообновлениях.
- У отчёта случайный ID (`r-…`), с нодой не связанный. Для серии отчётов по одной проблеме — `-id` с прежним ID.
- Ничего не отправляет: вывод на экран или в файл (`-o`, права 0600). Администратор читает и решает.
- `rayctl probe -redact` — то же для проверки снаружи (с машины клиента).

## 5. Телеметрия

Нет. Если когда-нибудь понадобится статистика, то только как добровольная ручная отправка отчёта P0, без постоянного
идентификатора ноды.

**Сводка от клиентов** (R4-21) — не телеметрия: данные идут от клиентов к их же ноде и никуда дальше.
- Приём включает администратор, клиенты шлют только с согласия пользователя.
- Нода хранит только счётчики по (сутки, AS, сервис) 30 дней.
- Показывает и использует нода только сети, где не меньше 10 отчётов.
- Внешний запрос возможен один: API ipinfo, если администратор его включил. Спрашивают по сети /24 или /48, только
  когда адреса нет в базах. Формат — `spec/probe-v1.md` §6.

## 6. QA

| Уровень | Что проверяет | Где |
|---|---|---|
| модульные | SPA (векторы), хранилище, отрисовка, ротация, журнал установки, очистка отчётов | CI `test` |
| периметр | настоящий nftables в network namespace: SPA по UDP/TCP, ротация портов, окно ACME, восстановление таблицы | CI `perimeter` |
| interop | `inner` и REALITY (в том числе self-steal с нашим сайтом) на Xray из закреплённого форка | CI `xray` |
| сертификаты | выпуск через HTTP-01 против Pebble | CI `acme` |
| установка | `bootstrap.sh` на Debian 12/13, Ubuntu 24.04, Rocky 9/10 с их файрволами; проверка снаружи как клиент; перезагрузка; **удаление и сравнение со снимком системы до установки**; аварийный пакет в логе замаскирован | CI `install` |
| полевые | клиент Niko и `rayctl probe -redact` из целевых сетей (RU, CN, KZ, KG, UZ) | вручную, отчёт P0 |

Полевой отчёт содержит только P0: для каждого профиля — прошёл или нет и на каком шаге (SPA, подписка, рукопожатие,
трафик), тип сети (мобильная, домашняя, корпоративная) и страну, без адресов и операторов точнее страны.

## 7. Обезличенные идентификаторы

- **Пользователь** — `rayctl user add` без имени даёт непрозрачный номер вида `u-k3f9-x2qa`; имя можно задать, но
  рекомендуется номер. Журналы и отчёты имён не содержат.
- **Устройство** — случайный ID, ключ устройства — в пакете `rcdev1`, на ноде больше ничего о нём нет.
- **Нода** — `node_id` случайный, знают его только её клиенты; в отчётах он скрыт.
- **Отчёт** — случайный ID на отчёт.

Аккаунты платформ для белых списков (R5) — отдельная тема: там учётные данные чужие, и правила для них решаются вместе с
движками olcRTC и OpenFlux.

## 8. Профили под нагрузкой

Для разбора производительности на VPS (разбор, O-3). По умолчанию выключено: профиль показывает, что делает процесс,
и пока снимается, ест CPU.

- **rayd** (и `rayd naive`, `rayd site`) отдаёт профили Go, если задана переменная `RAYD_PPROF`: `unix:ПУТЬ` (сокет
  только для владельца с момента создания). Другие адреса не принимаются, loopback тоже: до него достают процессы
  сервисов.

  ```
  systemctl edit rayd        # [Service] Environment=RAYD_PPROF=unix:/run/raycontrol/rayd-pprof.sock
  systemctl restart rayd
  curl --unix-socket /run/raycontrol/rayd-pprof.sock -o cpu.pb.gz 'http://x/debug/pprof/profile?seconds=30'
  go tool pprof -top cpu.pb.gz
  ```

  После замера — `systemctl revert rayd && systemctl restart rayd`.
- **niko-server и Xray** — `perf record -g -p <PID> -- sleep 30`, затем `perf report`: символы Go в бинарниках есть.
- Замеры на loopback раздувают долю фронта: мерить на ноде под настоящим трафиком.
