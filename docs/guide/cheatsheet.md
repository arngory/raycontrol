# Шпаргалка

Все команды — на ноде, от root или от члена группы `raycontrol`; `install`, `apply`, `update` (и `update
remote|auto`), `uninstall`, `backup`, `restore`, `debug on|off`, `egress block|allow`, `conn-limit on|off`,
`roots system|file`, `relay bundle`, `service cert`, `service rotate САЙТ` и `summary db` — только root.
`-json` перед командой даёт машинный вывод (`rayctl -json status`). Пошаговая установка —
[quickstart-debian13.md](quickstart-debian13.md).

## Установка и удаление

| Команда | Что делает |
|---|---|
| `bash bootstrap.sh -remove-v0 -host IP …` · `rayctl legacy [-remove]` | убрать прежний raycontrol (v0, `ray.sh`) перед установкой: копия в `/root`, затем только его следы; `-purge-v0-packages` — и его пакеты (R4-26) |
| `rayctl knock @bundle` | только SPA: открыть службы устройства своему адресу; с аварийным пакетом — SSH, затем `ssh` (R4-27) |
| `rayctl check [-host A] [-domain D] [-services a,b] [-ports …]` · `bash bootstrap.sh -check …` | годится ли хост: обязательное (без него установка откажет) и желательное; ничего не меняет (R4-24). С `-ports` — свободны ли выбранные порты. На установленной ноде от root — ещё `ssh port`: совпадают ли порты sshd (`sshd -T`) с портами сервисов `ssh`, на которых периметр пускает SSH (то же — строка `ssh port` в `rayctl status`) |
| `bash bootstrap.sh -host IP -domain D -cloudflare-token-file F [-services reality,dnstt,masterdns,slipstream]` | поставить ноду: зависимости, подписанный релиз с data plane, `rayctl install`, сервисы |
| `rayctl install -host IP [-domain D] [-name NAME] [-admin A] [-cloudflare-token-file F] [-services …\|none] [-dataplane DIR]` | то же без bootstrap; `-dataplane` — каталог с проверенными `xray` и `niko-server` |
| `bootstrap.sh … -ports spa=40000-40099,sub=40100,api=40101,rotation=41000-41399` | с v0.27.0: свои порты вместо случайных, для файрвола провайдера или NAT — стук (TCP и UDP, диапазон или один порт), подписка (TCP и UDP), API (TCP), ротация UDP (четверть диапазона на сервис; `rotation=off` — без неё); от 1024; что не названо — случайное. **Только при первой установке:** клиенты знают эти порты из пакета устройства, повторная установка с другими отказывает ([quickstart-debian13.md](quickstart-debian13.md) §5.2) |
| `rayctl ports` · `rayctl -json ports` | с v0.27.0: все порты ноды для файрвола провайдера — протокол, номер или диапазон, кто достаёт (все, после стука, адреса администратора), как задан (`fixed`, `random`, `chosen`, `sshd`), у меняющихся — порт сейчас и время смены; root или группа `raycontrol`, или `-remote ФАЙЛ` |
| `rayctl apply` | поставить то, что нужно новым сервисам: пользователи, юниты, файлы |
| `rayctl update [-check] [-version vX.Y.Z] [-from DIR] [-yes] [-no-handoff] [-no-relays]` | обновить ноду до проверенного релиза; при сбое — сам откат. С v0.19: обновление делает `rayctl` самого релиза (`-no-handoff` — этим `rayctl`, если новый здесь не запускается). С v0.15.0: юниты data plane, которые работали до обновления, должны заработать снова (иначе откат); файлы релиза, которых прежняя версия не знает, ставит новый rayctl; в конце — DNS-туннели, у которых режимы слабее, чем у нового сервиса. С v0.28: ручное обновление пишет статус (`by rayctl on the node`, его видит и телефон; откатившееся — в `held`), и relay с `remote on` идут за удавшимся, по одному; `-no-relays` — не идут |
| `rayctl update -rollback [-no-carry]` | вернуть бинарники, которые заменило последнее обновление; базу — только если обновление сдвинуло её схему, с вопросом. `-no-carry` — вернуть копию базы как есть, без отозванного с тех пор (когда нынешнюю базу не прочитать) |
| `rayctl update remote on\|off` | с v0.19, только root: admin-устройства могут обновлять ноду через API (StartUpdate) — только на подписанный релиз новее ноды; по умолчанию выкл. Политика — файл root `/var/lib/raycontrol-update/policy.json`, rayd его только читает ([`spec/node-update-v1.md`](../spec/node-update-v1.md)) |
| `rayctl update auto patch [-window 03:00-05:00]` / `auto off` | с v0.19, только root: rayd сам обновляется на патч-версии своей минорной в окне (время ноды, окно не короче 30 мин); раз в ~6 ч спрашивает GitHub; по умолчанию выкл. После отката эту версию больше не просит; после сбоя до изменений на ноде (скачивание) — через сутки. Новую минорную (или мажорную) не ставит, а называет: строка `auto-update` в `rayctl status` и `newer` в `rayctl update status` (после v0.26.0). С v0.27.0 после выхода новой минорной берёт самый новый патч своей: спрашивает следующие номера (не больше 8 за проверку; один пропуск переступает), строка `patch` в `rayctl update status` |
| `rayctl update status` | политика обновлений, последний релиз (что видели проверки rayd; сам к GitHub не ходит, без проверок — `latest     not checked`), последнее обновление по запросу (с v0.28 — и ручное); журнал самого обновления — `journalctl -u raycontrol-update`. С v0.28 — по строке на relay: версия и где его обновление по слову ноды (`unknown`, `off`, `current`, `waiting for …`, `offered`, `requested`, `running`, `done`, `rolled_back`, `failed` с кодом и текстом); `-json` — поле `relays` ([quickstart-debian13.md](quickstart-debian13.md) §6.7.9) |
| `rayctl update -version v0.15.0` → `rayctl update` | нода на v0.10–v0.14: в два шага, их `rayctl` не берёт архив с новыми файлами (`unexpected "slipstream-server"`); [RELEASE.md](../RELEASE.md) |
| `rayctl uninstall [-yes] [-keep-state] [-keep-dns] [-purge-packages]` | убрать всё по журналу установки, записи в Cloudflare тоже |
| `rayctl admin <ваш IP> [прежние адреса…]` | с консоли провайдера: пустить свой адрес к SSH без SPA (список заменяется целиком) |
| `systemctl stop rayspa && rayspa teardown` | с консоли: снять периметр целиком, пока rayspa не запустится снова (при работающем rayspa таблица возвращается за секунды) |

## Резервная копия

| Команда | Что делает |
|---|---|
| `rayctl backup [-o F] [-passphrase-file P]` | вся нода (ключи, пользователи, сервисы, сертификаты, токен DNS) одним файлом 0600 под фразой; хранить вне ноды |
| `rayctl restore -i F [-passphrase-file P] [-yes] [-no-carry]` | вернуть копию на этой ноде; прежняя база остаётся в `/var/lib/raycontrol/rayd.db.before-restore`. `seq` подписки сразу продолжается от часов: клиенты не отбрасывают ответы восстановленной ноды. С v0.27 устройства, отозванные здесь после копии, остаются отозванными, их пользователи получают новые учётные данные; устройства копии, о которых нынешняя база не знает, печатаются с предупреждением; `-no-carry` — копия как есть |
| `rayctl install -host NEW …` → `rayctl restore -i F -host NEW` | перенести ноду на новый хост; записи DNS обновятся, устройствам — новые бандлы |

## Состояние и диагностика

| Команда | Что делает |
|---|---|
| `rayctl node name "Амстердам"` (`""` — убрать) | имя ноды: клиенты показывают его рядом с адресом со следующей подписки; до 48 символов, без управляющих и невидимых. При установке — `bootstrap.sh … -name "Амстердам"` |
| `rayctl node note "До 1 Гбит/с, торренты нельзя 🙏"` (`""` — убрать) | описание ноды для пользователей: клиенты показывают его со следующей подписки; одна строка, до 200 символов, эмодзи и любые письменности, без управляющих, невидимых и символов смены направления |
| `rayctl version` | версия этого `rayctl` и, на ноде или хосте relay, установленная (`installed`, её говорит `rayd version`; root не нужен). С `-remote ФАЙЛ` — ещё и версия ноды (`node`), из её состояния. Работает и на macOS и FreeBSD; `-json` — объект `{"rayctl", "installed", "node"}` без неизвестного |
| `rayctl status` | версия, нода (и её имя), число пользователей, сервисов, устройств, порты SPA сейчас, политика выхода (`egress`); с v0.29 — строка `naive <сервис>` с именем сервера и опубликованным следующим; циклы rayd (`naive-names` — фронт обслуживает опубликованное имя naive), `dns-zone <сервис>` — самопроверка зоны туннеля; `conn-limit` — кто упёрся в предел соединений за 15 мин (`u<id>` и сервис), `conntrack` — таблица от 70 %, страж за сутки, отбросы ядра |
| `rayctl service list` | сервисы; в `KEYS`: у REALITY — когда сменились ключи и когда следующая смена, у naive — имя сервера, назначенная смена и прежние имена (с v0.29), у сайта — ключи сертификата и пины, у DNS-туннелей — режимы и ключи |
| `rayctl audit [-n 50]` | журнал действий администратора |
| `rayctl debug on [-for 30m]` / `off` / `show` | окно отладки: rayd, rayspa и data plane пишут подробно, с адресами клиентов; закрывается само (до суток); службы data plane перезапускаются |
| `rayctl egress` | политика выхода ноды (с v0.21): что закрыто, для кого, действует ли; root видит и счётчики правил; `local exempt` — цель REALITY на локальном адресе (или `localhost`: две строки, 127.0.0.1 и ::1), которую пропускает только процессу её сервиса |
| `rayctl egress block\|allow bittorrent` | только root, на ноде: закрыть или открыть BitTorrent на всех профилях сразу, в ядре (рукопожатие, uTP, UDP-трекеры, DHT; зашифрованный по TCP проходит). Действует через 1–2 с, data plane не перезапускается. Нода, где были сервисы Xray, после обновления держит BitTorrent закрытым ([`spec/egress-policy-v1.md`](../spec/egress-policy-v1.md)) |
| `rayctl egress block\|allow smtp` | только root, на ноде: закрыть или открыть TCP 25 на всех профилях; 465 и 587 (почта в телефоне) открыты. По умолчанию открыт |
| `rayctl egress block\|allow local` | только root, на ноде: собственные и локальные сети ноды (loopback, частные, link-local с адресом метаданных, CGNAT, multicast) для новых соединений data plane, в ядре (с v0.27). По умолчанию закрыты; резолверы на порту 53 открыты: заглушка systemd-resolved (127.0.0.53/54) и резолвер Azure 168.63.129.16. `allow` снимает только правило периметра, проверки naive, Xray и Hysteria2 остаются ([`spec/egress-policy-v1.md`](../spec/egress-policy-v1.md) §10) |
| `rayctl conn-limit` | пределы соединений (с v0.24): включены ли, где действуют (naive, Xray с v0.25, Hysteria2 с niko-server v0.17.0), их числа, таблица conntrack (занято, `max`, отбросы), страж (включён ли, переключения, отказы, вычищено), кто упёрся за 15 мин и отказы по сервису и виду; root видит и отброшенное пределом на адрес |
| `rayctl conn-limit on\|off` | только root, на ноде: пределы на пользователя в каждом процессе naive, Hysteria2 (с niko-server v0.17.0) и Xray (REALITY, `inner`; с v0.25) — TCP: 1024 сразу, 30 новых/с, неудачные dial в долг; UDP: 256 сессий, журнал пар; резолвы; отказ naive — ответ `429`, Hysteria2 — `too many connections` — и предел новых входящих TCP и UDP на адрес, здесь и на relay ноды. По умолчанию включены. Действует за секунды; naive и Hysteria2 перечитывают файл и не перезапускаются, каждый Xray перезапускается один раз — открытые через него соединения рвутся. Размер таблицы, `notrack` DNS-туннелей и страж остаются всегда ([`spec/conn-limit-v1.md`](../spec/conn-limit-v1.md)) |
| `rayctl roots [show]` · `roots system on\|off` · `roots file PEM\|none` | корни своих исходящих TLS ноды (ACME, GitHub и зеркала, Cloudflare, IPinfo, зеркало приложения, DoH): встроенный список — Chrome и Mozilla без центров из Китая, 91 корень, как у клиента; хранилище системы и свой PEM (прокси, вскрывающий TLS; частный ACME-УЦ) — только если root добавит. `rayd` подхватывает в течение секунды. Отказы — строка `tls-roots` в `rayctl status`: за 12 часов при этих корнях, пока к хосту не прошло соединение; в журнале — строка в минуту на хост с числом. Загрузка релиза при отказе повторяется с хранилищем системы и предупреждением (подпись проверяется всё равно) |
| `rayctl report [-o F] [-logs warning\|info\|debug\|none] [-since 24h] [-id ID]` | очищенный отчёт для issue, ничего не отправляет; `-logs debug` — со строками `-debug`, один `-id` на прогон |
| `rayctl probe [-carrier udp\|tls\|tcp\|auto] [-addr A] [-links] [-redact] [-channel] @bundle` | проверить ноду снаружи, как клиент; `auto` — UDP, ClientHello, голый TCP; `-channel` — ещё и замер канала (TCP в обе стороны, эхо UDP); `-links` — со ссылками профилей (в них учётные данные) |
| `journalctl -u rayd -u rayspa -u 'niko-*' -f` | журналы ноды |
| `systemctl status rayd rayspa 'niko-*'` | состояние юнитов; у `rayspa` строка `Status:` — где его таблица (`perimeter up: rayd's snapshot; rayspa V, pid N` — своя, со снимком `rayd`; `perimeter up: the saved snapshot` — своя, с сохранённым снимком, пока `rayd` нет, это нормально; `perimeter behind rayd` — `rayspa` отверг новый снимок `rayd`, действует прежний: `journalctl -u rayspa` скажет почему) |
| `nft list table inet raycontrol` | периметр; цепочка `early` — отброшенное до сборки фрагментов, `egress` — политика выхода, `in_rate` — предел новых входящих на адрес, `conn_guard` — страж conntrack (пуста, пока он выключен) |
| `sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max` | таблица conntrack: `apply` ставит размер по памяти (65 536–262 144) и сроки SYN_SENT 30 с, FIN_WAIT 30 с, TIME_WAIT 60 с — только больше размер и только меньше сроки, чем были (`/etc/sysctl.d/90-raycontrol-conntrack.conf`) |
| `rayctl metrics [-o /var/lib/node_exporter/textfile/raycontrol.prom]` | счётчики в формате Prometheus: только числа, без имён и адресов. С v0.31.0 — и UDP naive по каждому сервису с `udp=on`, с его запуска: запросы (`raycontrol_naive_udp_requests_total`), отказы `429`/`503` (`…_refused_total`), датаграммы и капсулы к назначениям и клиенту (`…_datagrams_total`, `…_capsules_total`, `direction="in\|out"`), отброшенные по причинам (`…_dropped_total`, `reason`: `denied`, `write`, `limit`…) — без адресов и назначений |
| `rayctl stats [-last 1h] [-id RUN] [-o F]` | последний час (5m…2h) одним JSON: приросты счётчиков `rayctl metrics` и уровни (конец, минимум, максимум), CPU, память, сеть и диск хоста, ответы подписки по исходу, устройства по версиям клиента, на ноде под root — записи журнала по юнитам (без текста). Сервисы — `naive#1`, без имён, адресов, доменов и ключей: файл можно передать; `-id` — run ID тест-прогона клиента, чтобы склеить с его статистикой ([`spec/stats-v1.md`](../spec/stats-v1.md)). С v0.33 |

## Сводка от клиентов (необязательно, R4-21)

| Команда | Что делает |
|---|---|
| `rayctl summary on\|off` | принимать отчёты клиентов о сетях (клиенты шлют только с согласия пользователя) и давать подсказки о порядке профилей |
| `rayctl app-mirror on\|off` · `rayctl app-mirror` | обновления Niko через ноду (с v0.18, по умолчанию выключено): нода раз в ~6 ч берёт с GitHub последний релиз и pre-release, проверяет подпись minisign Niko и SHA-256 и отдаёт своим устройствам на порту подписки; там, где GitHub недоступен, клиент без VPN узнаёт о новой версии и скачивает её с ноды. `on` хочет 1 ГиБ свободного места; `off` удаляет скачанное. Без аргумента — что держит и когда проверяла ([`spec/app-update-v1.md`](../spec/app-update-v1.md)) |
| `rayctl client min niko 1.59.0 [-from 2027-01-15]` · `rayctl client` | минимальная версия клиента (с v0.32): устройство ниже неё получает подписку без профилей и с причиной, обновиться через ноду может (`rayctl app-mirror on`); `-from` — с даты, до неё клиенты только предупреждены; `none` — снять. Клиенты без версии (Niko до 1.58) по умолчанию пропускаются; `-unknown refuse -yes` отказывает и им, но они тогда удаляют профили ноды. Без аргумента — политика и сколько устройств на каких версиях за 30 дней ([`spec/client-min-v1.md`](../spec/client-min-v1.md)). Android 6–9 остаются на Niko 1.59 (с 1.60 нужен Android 10): минимум выше 1.59 отрезает их насовсем |
| `rayctl summary [-days 7]` | сети, где не меньше 10 отчётов: что работает, потери UDP, скорость; остальное — одной суммой; базы AS и их даты |
| `rayctl summary api ipinfo [-token-file F]` · `rayctl summary api none` | API ipinfo для адресов, которых нет в базах: спрашивает по сети /24 или /48, не по адресу |
| `rayctl summary db F.mmdb` · `rayctl summary db -remove` | своя база AS (IPinfo Lite своим токеном, GeoLite2 ASN своим ключом) впереди базы из релиза; root, на ноде |
| `rayctl probe -payload @bundle` | ещё и payload подписки в JSON отдельной строкой после `payload ` (с учётными данными, как `-links`) |
| `rayctl probe -report '{"v":1,…}' @bundle` | отправить отчёт как клиент (probe-v1 §6), для проверки |
| `rayctl probe -dns [-resolver system,google,udp:IP] @bundle` | DNS-туннели из подписки глазами этой машины: делегирование у родителя, фронт и бэкенд ноды (опрос с печатью и меткой этого устройства), зоны через резолвер машины или `-resolver` — то же, что `rayctl dns check` с ноды, но из сети администратора |

## Пользователи и устройства

| Команда | Что делает |
|---|---|
| `rayctl user add [NAME] -services a,b [-expires 30d\|2026-12-31] [-limit 50G [-period monthly\|none] [-reset-day 1]] [-note TEXT]` | без имени — непрозрачный `u-xxxx-xxxx`; `-services` — имена сервисов (`dns`, не `dnstt`); `-limit` — лимит трафика (ниже); `-note` — заметка для себя |
| `rayctl user list` | пользователи; `USED` — расход периода из лимита (`12.0G/50G`, `(over)` — снят) |
| `rayctl user limit NAME 50G\|off [-period monthly\|none] [-reset-day N]` | лимит трафика (с v0.22): `up + down` на стороне назначений за период — месяц с дня N (1–28, 00:00 UTC) или `none` (всё время пользователя). Достиг — снят со всех профилей, как просроченный, до сброса или поднятого лимита; подписка остаётся (`profiles: []`, `exhausted`). Первый лимит на ноде включает счёт: `inner` и REALITY перезапустятся один раз ([`spec/traffic-limit-v1.md`](../spec/traffic-limit-v1.md)) |
| `rayctl user usage [NAME]` | расход, лимит, период, начало, сброс, состояние (отстаёт до минуты) |
| `rayctl user reset-usage NAME` | обнулить текущий период сейчас; снятый вернётся в течение секунд |
| `rayctl user services NAME a,b` | какие сервисы доступны |
| `rayctl user lan NAME on\|off` | локальная сеть устройств пользователя через Yggdrasil (с v0.23, [`spec/lan-v1.md`](../spec/lan-v1.md)): устройства видят друг друга по адресам Yggdrasil — через ноду или напрямую в одной Wi-Fi. Нужен сервис Yggdrasil у пользователя. В сети только устройства, которые сами показали себя в клиенте (столбец `LAN` в `device list`); пароль и список соседей получают только они. `on` ещё раз — новый пароль; отзыв устройства тоже меняет пароль. Без `on\|off` — показать. Через ноду работает с niko-server v0.16.0 |
| `rayctl user export NAME [-o F]` | ссылки пользователя, как в подписке (и следующие, если ждёт смена), без DoH: его токен — у устройства; в них учётные данные, вызов попадает в аудит; работают только с адреса, который открыл SPA |
| `rayctl user renew NAME` | с v0.27: новые учётные данные пользователя сразу, без перекрытия, и новый пароль LAN — как при отзыве устройства (R4-36); его устройства переподключаются после следующей подписки (Niko — на ближайшей проверке соединения, до ~10 минут); в аудите `user.renew`. После `device revoke -overlap` — чтобы всё-таки отрезать отозванное сразу. Обновление до v0.27.0 само делает это один раз для каждого, у кого есть устройство, отозванное раньше |
| `rayctl user enable\|disable\|del NAME` | включить, отключить, удалить |
| `rayctl user expires NAME 2026-12-31\|30d\|never\|now` | срок пользователя: позже, без срока или истечь сейчас (нода новее v0.33) |
| `rayctl device add USER NAME [-role admin] [-o F]` | пакет устройства `rcdev1:…` — один раз, на экран или в файл 0600 |
| `rayctl device list [USER]` | устройства; `LAN` — показало ли устройство себя в локальной сети пользователя (последний заголовок клиента; в сети оно, когда у пользователя `user lan on`) |
| `rayctl device revoke ID` | отозвать: SPA, подписка и API для него закрываются; с v0.27 у пользователя сразу новые учётные данные (R4-36): то, что осталось в устройстве, не действует, остальные его устройства переподключаются после следующей подписки (Niko — на ближайшей проверке соединения, до ~10 минут); имя устройства снова свободно; неиспользованное приглашение — отозвать |
| `rayctl device revoke -overlap ID` | с v0.31 (R4-43), для плановой замены — устройство отдали или оно сломалось, не украдено: отзыв тот же (SPA, подписка, API, ключи устройства — сразу, пароль LAN новый), но учётные данные пользователя не новые сразу, а сменяются, как по расписанию: следующие в подписке и принимаются сразу, переход через `-cred-lead` (3 дня), прежние принимаются ещё `-cred-grace` (2 дня); остальные устройства переходят со следующей подпиской без разрыва; то, что знал отозванный, работает до конца срока (команда пишет время; несколько таких отзывов подряд — не дольше 2 × lead + grace); отрезать сразу — затем `user renew`; с admin-устройства через `-remote` — тоже. Нода до v0.31: `rayctl` ничего не отзывает и говорит почему (приглашение — отзывает); последнее активное устройство — предупреждение; повторный отзыв говорит, до какого времени ещё принимается то, что знал отозванный. `restore` переносит идущую смену; `update -rollback` и `update -version` на версию до v0.31 при `-cred-period 0` останавливают rayd и дают новые данные каждому, у кого смена в пути (и плановой, начатой до периода 0, — безвредно), в аудите `user.renew:rollback` или `:downgrade`; период — из базы, после смены флагов сначала перезапустить rayd; с периодом смену доводит прежняя версия; `bootstrap.sh` старый релиз поверх ноды не ставит (без версии `rayd` — ничего до v0.31) |
| `rayctl device invite USER NAME [-role admin] [-ttl 24h] [-o F \| -qr] [-pin] [-format rcinv1]` | одноразовое приглашение, с v0.14 по умолчанию короткое `RCINV2:…` (QR вдвое меньше, Niko 1.35+): клиент сам регистрирует устройство через API (нужен сервис `api`); `-qr` рисует QR в терминале; `-pin` — ещё PIN из 6 цифр, сообщить другим каналом; `-format rcinv1` — длинное `rcinv1:…` для Niko старше 1.35 |

## Удалённое администрирование (R3)

| Команда | Что делает |
|---|---|
| `rayctl service add api api` → `rayctl apply` | включить удалённый API: свой порт за SPA, mTLS |
| `rayctl device invite admin laptop -role admin` | на ноде: приглашение для устройства администратора |
| `rayctl remote enroll -o laptop.rcdev [-pin 123456] 'RCINV2:…'` | на своей машине: новый ключ, SPA, регистрация; файл устройства 0600. Берёт и `rcinv1:…`; PIN без `-pin` спрашивается без показа на экране |
| `rayctl -remote laptop.rcdev status` | любая команда `status`, `node`, `user`, `service`, `device`, `audit`, `admin`, `ports`, `relay` (`list`, `ports`, `set`), `dns`, `summary`, `app-mirror`, `client`, `metrics`, `debug`, `version` через API |
| `rayctl -remote laptop.rcdev remote rotate` | новый клиентский ключ, старый перестаёт работать |
| `rayctl -remote laptop.rcdev remote whoami` | какое это устройство: ID, пользователь, имя, роль, нода |
| `rayctl user add integrations -services ""` → `rayctl device invite integrations billing -role billing` | устройство внешней системы (бот, биллинг; [integrations-v1](../spec/integrations-v1.md)): пользователь без сервисов, приглашение роли `billing` (заводит и ведёт обычных пользователей, приглашения только роли `user`) или `support` (только читает, без заметок). Служебных пользователей (с устройствами `admin`, `billing`, `support`, сервисами `ssh`, `api`) интеграция не видит (нода новее v0.33) |
| `rayctl remote export billing.rcdev -pem billing.pem` | сертификат и ключ устройства интеграции в PEM (новый файл, 0600) и адрес с пином API в том виде, как их берёт curl; описание API для ролей — `openapi-billing.yaml` и `openapi-support.yaml` в выпуске ([integrations-v1](../spec/integrations-v1.md) §5) |
| `rayctl integration [status]` | устройства интеграций: вызовы, отказы, превышения с запуска rayd; массовые действия за час; пределы |
| `rayctl integration set support-notes on\|off` | `support` видит заметки пользователей (по умолчанию нет) |
| `rayctl integration set mass-limit 50` | root: удалений и выключений от `billing` за час, сверх — только с `confirm_mass`; `0` — каждое с ним |
| `rayctl integration limits billing read=100,10/s write=50,5/s heavy=20,60/h inflight=4` | root: пределы частоты роли или устройства (`DEVICE_ID`), `-reset` — по умолчанию; сверх — `resource_exhausted` |
| `rayctl traffic counting on\|auto` | `on`: Xray считает трафик и без лимитов, и первый лимит или снятие последнего его не перезапускают; так `billing` может задавать лимиты (иначе — `failed_precondition`) |

`rayctl` для своей машины: Linux — из архива ноды; macOS и FreeBSD — архивы `rayctl-darwin-arm64`,
`rayctl-darwin-amd64` и `rayctl-freebsd-amd64` (`.tar.gz`) с v0.26.0, под той же подписью
`SHA256SUMS`. Там работают `remote enroll`, всё с `-remote`, `knock`, `probe` и `version`; команды самого сервера (`install`,
`apply`, `update`, `backup`, `report`, `check`, `egress`, `conn-limit`, `service cert`, `relay bundle` и
другие) отвечают `… works on a Linux node only`. С того же релиза `-remote` не читает файл устройства, открытый
группе или остальным либо чужой (кроме root): `chmod 600 ФАЙЛ` (и на Linux). Подробно —
[quickstart-debian13.md](quickstart-debian13.md), §7.

## Сервисы

| Команда | Что делает |
|---|---|
| `rayctl service add reality reality` | REALITY с self-steal на своём сайте-приманке |
| `rayctl service add hy2-masq hy2-masq` · `rayctl service add hy2-obfs hy2-obfs` | Hysteria2: оба на UDP 443 за фронтом — с маскировкой и в salamander |
| `rayctl service add doh doh` | DoH для клиентов на TCP 443 (после REALITY) |
| `rayctl service add naive naive` | NaiveProxy (HTTP/2) на TCP 443 (после REALITY); потом `rayctl apply` |
| `rayctl service add yggdrasil ygg` | Yggdrasil: прямой TLS-линк на TCP 443 за фронтом (после REALITY), трафик идёт в `inner`; потом `rayctl apply` |
| `rayctl service add dnstt dns` · `rayctl service add masterdns mdns` | DNS-туннели (резервный канал) |
| `rayctl service add slipstream slip [-settings '{"zone":"s.example.net"}']` → `rayctl apply` | slipstream (с v0.16, [`spec/slipstream-v1.md`](../spec/slipstream-v1.md)): DNS-туннель поверх QUIC с multipath, за DNS-фронтом. Зона — до 20 символов (иначе пакет QUIC Initial не влезет в запрос): своя — `zone`, без неё — случайная в домене ноды (если домен длиннее 16 символов, задайте свою). Каждый запрос несёт метку dnsauth-v2 устройства, фронт проверяет её до сервера; опций нет, ключ сервера (P-256) клиенты закрепляют, ротации нет. Ссылку берут Niko 1.37+, более старые пропускают строку |
| `rayctl service set slip max_connections=512` · `device_connections=2` → `rayctl apply` | пределы slipstream (с v0.17): соединений на сервис (16–1024, по умолчанию 256) и на одно устройство (1–16, по умолчанию 4; сверх любого из пределов уступает соединение устройства, молчащее дольше 5 с). `0` — по умолчанию. Пределы — аргументы сервера в его юните: действуют после `rayctl apply`, который перезапускает сервер. Сколько это людей — [`../design/capacity.md`](../design/capacity.md) |
| `rayctl service add api api` | удалённый API для устройств-администраторов и регистрации по приглашениям |
| `rayctl service enable\|disable\|del NAME [-force]` | включить, выключить, удалить. Последний включённый сервис вида `ssh` без `-force` не выключается и не удаляется: на его портах периметр пускает SSH, без него SSH закрыт для всех со следующего снимка (то же через API) |
| `rayctl service set site answer=404\|403\|silent\|pages` | что сайт отвечает тем, кого отклонил REALITY; потом `rayctl apply` |
| `rayctl service set reality rotate_sni=on\|off\|auto` | менять ли имя REALITY при смене ключей: `auto` (по умолчанию) — при плановой только под wildcard-сертификатом, по команде всегда; `on` — всегда (при HTTP-01 новое имя за 3–4 дня в журналах CT); `off` — никогда |
| `rayctl service set naive rotate_sni=on\|off\|auto` | плановая смена имени naive раз в `-naive-sni-period`: `auto` (по умолчанию) — только под wildcard-сертификатом, `on` — и при HTTP-01 (следующее имя в журналах CT за эпоху), `off` — нет; `rotate` меняет имя при любом значении |
| `rayctl service set reality target=127.0.0.1:8443` | новая цель REALITY (с v0.27): кому он отдаёт не-клиентов; проверяется, как при создании (TLS 1.3, X25519MLKEM768, HTTP/2, длина цепочки; не `0.0.0.0` и не собственный адрес ноды, кроме loopback; имя — не в локальную сеть). Ключи, shortIds и имя (`sni`) остаются — ссылки клиентов не меняются; `rayd` сам перезапускает Xray. Цель `localhost:PORT` — это 127.0.0.1 и ::1. Не для самокражи (`site`). `rayctl check` и `rayctl update` называют сервисы, чью цель data plane не достанет, с этой командой |
| `rayctl service set naive udp=on\|off` → `rayctl apply` | UDP через naive датаграммами HTTP/3 (с v0.30, [`spec/naive-udp-v1.md`](../spec/naive-udp-v1.md)): extended CONNECT `connect-udp` по QUIC на UDP 443, адрес назначения в каждой датаграмме, что не влезло в пакет — капсулой в потоке запроса; в ссылке `udp=1`, `uot=2` остаётся. По умолчанию выключено. `apply` перезапускает naive с `-udp`: его QUIC объявляет датаграммы. Места (256 на пользователя вместе с UoT), пары, резолвы, учёт, отзыв и политика выхода — как у UoT; отказ по месту — `429` до ответа. Без UDP-порта у сервиса — предупреждение, `udp=1` нет. Пользуется клиент со вторым движком naive; выпущенные Niko параметр пропускают |
| `rayctl service set naive icmp=on\|off` → `rayctl apply` | ping и трассировка через naive (с v0.21, [`spec/icmp-v1.md`](../spec/icmp-v1.md)): echo клиента шлёт нода со своих ICMP-сокетов; в ссылке `icmp=1`. По умолчанию выключено. `apply` перезапускает naive и, если `net.ipv4.ping_group_range` не покрывает группы data plane (9100–9179), расширяет его (`/etc/sysctl.d/10-raycontrol-icmp.conf`: идёт первым, файлы дистрибутива и администратора после него при загрузке побеждают); `rayctl check` и `apply` предупреждают, если сокеты не откроются |
| `rayctl service set hy2-masq up_mbps=500` | потолок серверного Brutal на соединение: нода шлёт клиенту не быстрее min(500 Мбит/с, темп клиента); `down_mbps` — потолок отдачи клиента; `0` — без потолка |
| `rayctl service set dns auth=optional\|required\|off` | dnsauth-v1: метка устройства в каждом запросе dnstt ([`spec/dnsauth-v1.md`](../spec/dnsauth-v1.md)); `required` — только когда все клиенты её ставят (Niko 1.27+). Новый dnstt-сервис создаётся с `required` (v0.13.0), прежние остаются как были — `rayctl service list` показывает `auth … (open: …)`. Без `required` ключ не нужен: любой, кто знает зону (она видна в делегировании), а при `seal=required` — любой со ссылкой, может занять места рукопожатий dnstt (128), и новые сессии будут ждать; память нода держит в пределах и так (niko-server v0.10.0, нагрузочный тест) |
| `rayctl service set dns seal=optional\|required\|off` | dnsseal-v1: обвязка dnstt запечатана ключом зоны ([`spec/dnsseal-v1.md`](../spec/dnsseal-v1.md)); ключ уходит в ссылку; `optional` берёт и открытые запросы, `required` — только когда все клиенты запечатывают (с v0.13, Niko 1.35+). Новый dnstt-сервис с v0.14 создаётся с `optional` |
| `rayctl service set mdns seal=… auth=…` | masterdns (с v0.14, niko-server v0.11.0): `seal` — ответы запечатаны ключом сервиса (mdseal-v1, [`spec/mdseal-v1.md`](../spec/mdseal-v1.md)), `auth` — метка устройства в каждом запросе, сессия привязана к устройству ([`spec/dnsauth-masterdns.md`](../spec/dnsauth-masterdns.md)); `optional` — для тех клиентов, что умеют, `required` — когда умеют все. Новый masterdns-сервис создаётся с `optional` для обоих |
| `rayctl service set dns auth_hint=required` (`optional` — по умолчанию, `off`) | dnsauth-v2 ([`spec/dnsauth-v2.md`](../spec/dnsauth-v2.md)): ключ устройства находится по подсказке в метке, без перебора. `optional` берёт и метки v1 перебором, как раньше; `required` — только v2 (мусор с верной обёрткой ничего не стоит ноде), когда все клиенты подписывают по v2; только при `auth=required`. Подписка говорит клиентам, какую версию брать (`dnsauth.v`) |
| `rayctl service set dns spare_zones=2` (или `=a.example.net,b.example.org`, `=none`) → `rayctl apply` | запасные зоны DNS-туннеля, до 4 ([`spec/dnszones-v1.md`](../spec/dnszones-v1.md)): число — случайные зоны в домене ноды, как основная (уже заданные остаются); список — свои (для чужих доменов делегирование заводит оператор, Cloudflare — если токен покрывает зону). Нода делегирует, обслуживает и проверяет каждую, как основную (`rayctl status`: `dns-zone dns <зона>`). Зоны не совпадают и не вкладываются друг в друга ни внутри сервиса, ни между сервисами. Для dnstt и masterdns |
| `rayctl service set dns zone=<запасная>` → `rayctl apply` | запасная зона становится основной, прежняя основная уходит: только запасная — она у клиентов уже есть; прежнюю они теряют со следующей подпиской |
| `rayctl service rotate dns [-now] [-force]` | новый ключ печати сразу, в подписке с этого момента; прежний нода принимает ещё `-cred-grace` (2 дня), с `-now` — не принимает (ключ утёк): клиенты без новой подписки не получают ничего, пока её не обновят. Второй сброс в пределах срока — отказ (ключ до прежнего ещё нужен клиентам); `-force` — всё равно, снимая его. Заодно меняется ключ самопроверки ноды (строка `node-check` в ключах dnsauth всех dnstt-сервисов). `rayctl service list` показывает режим, дату ключа и срок прежнего |
| `rayctl service set ygg lan_relay=50` | потолок связи устройство—устройство через ноду в локальной сети (`user lan`), Мбит/с на пользователя: без настройки 20, `0` — только напрямую в одной Wi-Fi; эти байты идут в лимит трафика. Бэкенд перезапускается сам. Только с niko-server v0.16.0: более старый отвергает настройку, и Yggdrasil не поднимется |
| `rayctl service set ygg peers=tls://host:443,quic://203.0.113.9:443` → `rayctl apply` | пиры Yggdrasil — публичные или свой (yggdrasil-go 0.5; 0.4 несовместим), до 8 (по умолчанию нет; адрес — публичный или имя, частные не принимаются; `quic` — только по IP; лучше разные операторы и `tls`/`quic`/`wss`): нода соединяется с ними сама, с публичными видна в сети Yggdrasil, клиенты получают пиры как запасной путь; `peers=none` — выключить. Свой пир и что видят пиры — [quickstart-debian13.md](quickstart-debian13.md) §8, Yggdrasil |
| `rayctl service peer-keys [-names] ygg` | с v0.31.0: открытые ключи для `AllowedPublicKeys` своего пира (yggdrasil-go 0.5) — блок HJSON, который вставляется в его конфиг: ключ ноды, затем ключи каждого пользователя (для ссылок `user export`) и каждого его неотозванного устройства, у активных пользователей; над каждым — метка из файла пользователей ноды (`u<id пользователя>`, `-<id устройства>`, `-n` следующий, `-p` прежний: id — в `rayctl -json user list` и `rayctl device list`), имён нет; при смене UUID — и следующие (`next: from …`) и прежние (`previous: until …`). `-names` — ещё и имена пользователей и устройств, с предупреждением: конфиг пира лежит вне ноды, и по нему адрес пиринга связывается с человеком (lan-v1 §4.3). Только открытые ключи; `-json` — с адресами в сети Yggdrasil, имена тоже только с `-names`. Список меняется с устройствами, пользователями и каждой сменой UUID (раз в `-cred-period`), пир надо обновлять — проще оставить `AllowedPublicKeys` пустым, но тогда к пиру подключится любой, кто узнал адрес: узнает ключи ноды и подключённых устройств и достанет до клиентов через пир мимо фильтра ноды (lan-v1 §2.1, §2.3; руководство §8, «Что видят пиры»). Root, группа `raycontrol` или `-remote ФАЙЛ` (как `device list`) |
| `rayctl service cert site -chain chain.pem -key key.pem [-force]` | root: свой сертификат сайта вместо ACME (свой CA, другой ACME-клиент, тестовый CA): для REALITY, hy2-masq, naive, DoH и Yggdrasil под сайтом; должен покрывать все имена сайта. Под своим сертификатом ссылки naive, `hy2-masq` и DoH идут без `niko-pin`. Если они уже несут пины ноды, а ключ другой, — отказ: клиенты не прошли бы пин до новой подписки; `-force` — всё равно |
| …после `service cert` | строка о цепочке: `leads to …, a public root clients know` — naive и DoH примут; `a root that is not in the clients' list` — частный УЦ: клиент примет, только если корень добавлен в поле сертификата каждого профиля naive (по QUIC — только так; корни, установленные в телефон, — отдельная настройка приложения и только для HTTP/2); `incomplete` — импортируйте цепочку целиком. Предупреждение, не отказ |
| `rayctl service rotate mdns [-now] [-force]` | новый ключ сервиса masterdns сразу, в подписке с этого момента; прежний бэкенд принимает ещё `-cred-grace` (сессии на нём идут дальше), с `-now` — нет (его сессии закрываются). Второй сброс в пределах срока — отказ, `-force` — всё равно. Файл ключей перечитывается без перезапуска. `rayctl service list` показывает дату ключа и срок прежнего |
| `rayctl service rotate site [-force \| -fresh]` | root: сертификат сайта переходит на следующий ключ — тот, чей пин уже в ссылках naive, `hy2-masq` и DoH ([`spec/cert-pin-v1.md`](../spec/cert-pin-v1.md)). `rayd` делает одну попытку заказа сразу (и мимо выдержки после неудач), дальше по выдержке; до сохранения сертификата в работе прежний ключ. Потом naive, сайт, `hy2-masq` и Yggdrasil один раз перезапускаются, DoH нет; час прежний ключ остаётся в списке пинов. Отказ, пока следующий ключ не пробыл в подписках `-site-key-lead` (14 дней). `-force` — всё равно (утёк ключ в работе), прежний пин не остаётся; не раньше 72 часов после прошлой смены. `-fresh` — на ключ, сделанный сейчас, следующий тоже заменяется (утекла база или копия): все клиенты с пинами отрезаны до новой подписки. Для своего сертификата (`service cert`) и без ACME — отказ. `rayctl service list` показывает состояние |
| `rayctl service rotate reality [-now]` | новые ключи (и имя) REALITY: через срок публикации или сразу; с `-now` прежние ключи сразу перестают работать, иначе принимаются ещё `-cred-grace`. naive того же сайта, чья плановая смена ближе половины эпохи, меняет имя вместе с ним, в том же проходе (один перезапуск фронта), и с `-now` тоже |
| `rayctl service rotate naive [-now]` | новое имя naive (R4-42; имя заблокировали): через срок публикации или сразу, на следующее имя, которое фронт уже ведёт. Прежнее имя принимается до следующей смены, и с `-now` тоже; при сменах чаще периода — до смены через период после своей, не больше трёх прежних (команда печатает, какие останутся и какое снимется); клиенты переходят с ближайшей подпиской. При HTTP-01 новое имя сначала ждёт сертификат (не дольше `-reality-prepare`). Фронт перезапускается один раз, в момент смены. `rayctl status` и `service list` показывают имя и опубликованное следующее |

## Отдать подписку клиенту

```bash
rayctl user add -services reality,dns -expires 90d
```

```bash
rayctl device add u-k3f9-x2qa phone -o /root/phone.bundle
```

Передать `/root/phone.bundle` по доверенному каналу, клиент импортирует его в Niko, потом:

```bash
shred -u /root/phone.bundle
```

Подписку клиент берёт сам по пакету. Смены UUID и ключей REALITY приходят в ней заранее (`next`).

## Сроки ротации (флаги `rayd serve`)

Команды для этих флагов нет: юнит `rayd.service` пишет `rayctl apply`, и в нём только `-db`, `-socket` и `-rendered`.
Ниже — значения, с которыми работает нода.

| Флаг | По умолчанию | Что |
|---|---|---|
| `-cred-period` / `-cred-lead` / `-cred-grace` | 30 д / 3 д / 2 д | UUID пользователей: срок, публикация заранее, приём старого; `-cred-grace` — и приём прежних ключей REALITY (R4-19); lead и grace — и у `device revoke -overlap`, с v0.31 и при `-cred-period 0` |
| `-reality-period` / `-reality-prepare` | 90 д / 1 д | ключи и имя REALITY (имя по расписанию — только под wildcard-сертификатом, с v0.29.0); время на сертификат нового имени, у naive тоже |
| `-naive-sni-period` | 90 д | имя naive (R4-42): публикация за `-cred-lead`; по расписанию — только под wildcard-сертификатом или с `rotate_sni=on`; `0` — только `rayctl service rotate <naive>` |
| `-site-key-period` / `-site-key-lead` | 180 д / 14 д | ключ сертификата сайта (пины в ссылках, [`spec/cert-pin-v1.md`](../spec/cert-pin-v1.md)): при выпуске после этого срока его сменяет следующий ключ, если тот пробыл в подписках срок публикации; `0` у периода — только `rayctl service rotate <сайт>`; срок публикации — не меньше 72 часов |
| `-spa-tcp` | true | TCP-носитель SPA; `false`, если хватает UDP |
| `-acme-directory` | Let's Encrypt | CA; пусто — без сертификатов; корень частного CA — `rayctl roots file` |
| `-tls-roots` | `/etc/raycontrol/tls-roots.json` | чему верят свои соединения ноды кроме встроенного списка (`rayctl roots`); другой файл — для стендов |
| `-dns-check` · `-dns-check-resolvers` | 1 ч ±10 % · `google,cloudflare,quad9` | самопроверка DNS-зон с ноды; `0` — только `rayctl dns check -now` |
| `-update-check` | `0` (выкл.) | искать новый релиз так часто, не чаще раза в час (±10 %): нода берёт подписанный SHA256SUMS последнего релиза только с github.com — он видит адрес ноды (зеркала — только у `rayctl update`); итог — строка `update` в `rayctl status`, новая версия — один раз в журнал. Только у релизных сборок (vX.Y.Z), независимо от `-dns-check` |
| `-spa-ttl` / `-spa-max-ttl` | 10 мин / 1 ч | доступ по SPA, когда пакет просит срок по умолчанию; самый долгий доступ, который пакет может попросить |
| `-probe-daily-mib` | 1024 | замеры канала: МиБ на устройство за сутки UTC, в обе стороны |
| `-run` | `/run/niko` | каталог сокетов и копий секретов data plane |
| `-supervise` · `-xray` · `-niko-server` | выкл. | без systemd (CI, контейнеры): data plane — дочерние процессы rayd под его пользователем; не для ноды (R4-22, `test/supervise/run.sh`) |

## Relay (relay-v1)

Пошагово — [quickstart-debian13.md](quickstart-debian13.md) §6.7: второй VPS с публичным IPv4 (Debian 13), sshd
на нём — ровно на одном порту, на ноде — сервис `api`.

```
rayctl relay add msk 198.51.100.20   # адрес relay (IPv4) доходит до портов сервисов без SPA, но не до SSH
rayctl relay bundle -o msk.bundle msk   # пакет для хоста relay: новый сертификат и ключи SPA, прежние не работают;
                                        # SSH relay: его список, у нового — адрес этой SSH-сессии (или -admin);
                                        # с v0.31.0 — все порты, которые открыть в файрволе провайдера relay;
                                        # -o не перезаписывает: прежний файл сначала shred -u
rayctl relay ports msk   # с v0.31.0: порты хоста relay для файрвола провайдера — SSH relay, диапазон SPA relay
                         # (TCP и UDP), точка замера (TCP и UDP), пересылаемые к выходу: TCP и UDP 443, подписка, API;
                         # куда идёт (relay host или the exit) и кто достаёт; root, группа raycontrol или -remote ФАЙЛ;
                         # диапазон SPA и точку замера — только после relay bundle (relay set до него их не даёт);
                         # с Yggdrasil — и строка ygg (tcp/443), но профиль Yggdrasil через relay клиенты не ведут
rayctl relay set -admin 203.0.113.9 msk   # адреса для SSH хоста relay (и -ssh-port), без нового пакета; при смене
                                          # порта sshd на relay сначала слушает оба, потом новый (руководство §12.4)
rayctl relay list   # с портом замера (PROBE)
rayctl relay remove msk   # потерянный relay: только remove отнимает у его адреса порты сервисов
```

Пакет скопировать на хост relay и только туда — в нём ключ. Со своей машины, через неё (на ноде ключа SSH к relay
обычно нет): `scp -3 root@203.0.113.7:msk.bundle root@198.51.100.20:`, затем на ноде `shred -u msk.bundle`. На хосте
relay:

```
sudo bash bootstrap.sh -relay msk.bundle   # rayspa, пересылка ядром к выходу; SSH — с адресов администратора relay;
                                           # rayd relay — точка замера relay (если её нет, relay работает и без неё)
journalctl -u rayd-relay                   # точка замера relay: поток от выхода, отчёты
systemctl is-active rayspa rayd-relay      # оба active: периметр с пересылкой и точка замера
systemctl stop rayspa && rayspa teardown   # с консоли провайдера, если SSH relay закрыт и для вас: relay открыт и не
                                           # пересылает; затем на ноде relay set -admin, здесь systemctl start rayspa
```

Проверка с ноды: в `rayctl update status` у relay `current` (точка замера связалась и доложила версию; `unknown` —
нет связи); `rayctl probe -payload @bundle` с другой машины — relay в `relays` подписки и `via` у профилей. Через
relay `rayctl probe` и `rayctl knock` не стучатся.

Обновление relay с v0.26.0 — на его хосте, от root. **На настоящем хосте relay оно ни разу не запускалось**
(модульные тесты; в CI тот же код идёт как обновление по слову ноды, задание `relay-host`): держите доступ к
консоли провайдера.

```
sudo rayctl update -check   # версии; откажет ли обновление (SSH-сессия не с адреса администратора relay)
sudo rayctl update          # релиз проверяется как на ноде; установка relay с /etc/raycontrol/relay.bundle;
                            # не поднялся — откат к прежней версии с прежним снимком периметра
sudo rayctl update -rollback   # вернуть версию до последнего обновления; и после оборванного обновления
```

Не перезагружайте и не выключайте хост relay во время `rayctl update`: после загрузки relay может быть открытым и
без пересылки. Тогда — `sudo rayctl update -rollback`; прервано ли обновление, говорит `rayctl update status`.

С v0.28.0 relay идёт и за обновлением ноды — по слову ноды, если root на relay это разрешил (по умолчанию нет).
Тоже не запускалось на настоящем хосте.

```
sudo rayctl update remote on    # нужны relay v0.28.0+ (сначала rayctl update) и rayd relay; по одному relay за раз,
                                # только подписанный релиз новее установленного, качает сам relay
sudo rayctl update remote off   # relay остаётся на своей версии; ждущий запрос удаляется
sudo rayctl update status       # remote, last (по слову ноды, с кодом причины), held, error; без root last не читается
journalctl -u raycontrol-relay-update   # само обновление по слову ноды; journalctl -u rayd-relay — слово ноды и доклады
```

На ноде: `rayctl update -no-relays` — relay не идут за этим обновлением; выключателя relay на ноде нет.
`rayctl update auto` на relay отказывает: relay идёт за выходом. До v0.28.0 `rayctl update remote|auto` на relay
отказывали. Relay до v0.26.0 и запасной путь — тот же запуск ещё раз, с пакетом, который установка оставила на хосте
relay: `sudo bash bootstrap.sh -relay /etc/raycontrol/relay.bundle`
([quickstart-debian13.md](quickstart-debian13.md) §6.7, [spec/node-update-v1.md](../spec/node-update-v1.md) §5,
[spec/relay-update-remote-v1.md](../spec/relay-update-remote-v1.md)).
