## Что сделано в R0

- Go-модуль, CI (генерация кода, shellcheck, vet, тесты с `-race`, golangci-lint, сборка amd64/arm64); v0 в `legacy/`.
- `internal/spa`: SPA v2 — параметры установки, ключи эпох, порты слотов, пакет, проверка с кэшем nonce;
  векторы сверены независимой реализацией.
- `internal/store`: SQLite с миграциями — пользователи, сервисы (ID = scope SPA, без повторного использования),
  устройства, доступ пользователей к сервисам, настройки, аудит.
- `internal/node`: случайные параметры установки, пакет регистрации `rcdev1:`.
- API `raycontrol.node.v1` (ConnectRPC) на unix-сокете с проверкой `SO_PEERCRED`; `rayd init|serve`, `rayctl`.

Не входит в R0 и переносится в R1: релизный workflow с подписью minisign (нужен ключ в секретах репозитория),
systemd-юниты, хранение секретов через systemd credentials, подпись подписки.

## R1: итог

Сделано:

  с таймаутом, отзыв, аварийный доступ к SSH для адресов администратора.
- **Ключи ноды** Ed25519 + ML-DSA-65; **подписка** с двумя подписями, `seq`, `time`, TLS только с `X25519MLKEM768`

- **`rayd` на лету**: перерисовывает файлы, синхронизирует пользователей `inner` через gRPC API Xray без перезапуска,

- **Установщик** `install/bootstrap.sh` с проверкой подписи minisign и workflow релиза.
- **Проверки в CI**: периметр на настоящем nftables в network namespace; `inner` на Xray из закреплённого форка —
  проверка конфига, пользователи через API, трафик через VLESS с ML-KEM-768.

- **Ротация UDP-портов** сервисов (spa-v2.md §11) в `rayspa` и `rcdev1`; подписка v1 заморожена.
- **Внешние зависимости закрыты**: ключ подписи релизов есть (`A9C7802E23B87A01`), `niko-server-v0.1.1` выпущен

- **Переносимость** (решения R2-1…R2-6): проверка хоста вместо списка систем, firewalld и ufw, восстановление
  таблицы после `flush ruleset`, порядок `rayctl apply` (`rayd` отрисовывает файлы до старта сервисов), хосты без IPv6,

Релиз raycontrol v0.2.0 выпущен.

## После проверки на VPS: кандидаты

Решать по фактам с настоящей сети (VPS-CHECK, журналы, `rayctl metrics`, сводки). Разбор безопасности, качества и
производительности — [12-review.md](12-review.md).

- **Авторизация запросов DNS-туннелей.** SPA по IP здесь невозможен: запросы приходят от резолверов, а не от клиентов,
  и у резолверов тысячи адресов, общих для всех.
  - **Сейчас:**
    - фронт на UDP 53 отвечает только за зоны туннелей, на остальное — `REFUSED`;
    - сессию туннеля открывает ключ сервиса: Noise у dnstt, AES-256-GCM у masterdns;
    - пользователя проверяет VLESS с ML-KEM-768 и его UUID в `inner`.
  - **Слабые места:**
    - ключ туннеля общий и лежит в ссылке у каждого пользователя. По утёкшей или старой ссылке можно открывать сессии
      (дальше `inner` не пройти, но тратятся ресурсы ноды);
    - делегирование зоны публично, а dnstt отвечает на любой запрос в зоне. Активной проверкой туннель можно
      опознать.
  - **Кандидат:** подпись каждого запроса ключом устройства. Без верной подписи нода отвечает как пустая зона.
    Отозванное устройство отсекается уже на уровне туннеля.
  - **Цена:**
    - меняется протокол dnstt и masterdns с обеих сторон: форки в niko-server и клиент Niko;
    - около 5 % ёмкости запроса;
    - подпись не должна отличать пользователей друг от друга на проводе.
  - **Сделано на сервере** в raycontrol v0.10.0 и niko-server v0.8.0: `docs/spec/dnsauth-v1.md`, `rayctl service set
    <dnstt> auth=…`: у сервисов, заведённых до v0.13.0, по умолчанию `off`, новый dnstt-сервис с v0.13.0 —
    `required` (нагрузочный тест niko-server: без метки любой, кто знает зону, занимает места рукопожатий). Клиент
    подписывает запросы с Niko 1.27 (T2, `handoff/SYNC.md`). Для MasterDnsVPN — черновик
    `spec/dnsauth-masterdns.md`, v0.14.0.
- **PIN у приглашения** — сервер сделан (v0.13, `rayctl device invite … -pin`, api-v1 §3, §4), клиент — Niko 1.34.
  `rcinv1:` — секрет до первого использования: кто зарегистрируется первым, тот и получит
  устройство.
  - Кандидат: короткий код, который сообщают другим каналом. Ключ проверки регистрации — HMAC(ключ приглашения, код).
    После нескольких неверных попыток приглашение сгорает.
  - Тогда QR в мессенджере без кода бесполезен.
  - Нужны изменение `api-v1` §4 и поле в клиенте. Вопрос клиенту задан (`handoff/SYNC.md`).
- **QR приглашения в `rayctl`** — сделано: `rayctl device invite … -qr` рисует QR в терминале (v0.12.0).
  - Кандидат: короче `rcinv1:`. Приглашение — около 650 символов: QR версии 17, 93 колонки, плотный для камеры.
    Бинарная упаковка вместо JSON в base64url дала бы примерно вдвое меньше. Это смена формата вместе с клиентом.

  - **Клиент → нода напрямую по TCP 53**: нужен и TCP-транспорт клиента, и TCP 53 у фронта. Слушать `0.0.0.0:53`
    по TCP рядом с заглушкой systemd-resolved нельзя: две слушающие TCP-сокета с пересекающимися адресами ядро не
    допускает и с `SO_REUSEADDR` (проверено). Значит, адреса самой ноды по одному и их обновление при смене.
  - **Резолвер → нода по TCP после TC**: dnstt укладывает ответы в размер запрашивающего и TC не ставит, этот путь не
    срабатывает.
  - Вариант «нода по TCP 53» — после замеров варианта «резолвер по TCP 53» в клиенте (решение пользователя, 2026-11-06).
- [x] Окно отладки `rayctl debug on -for 30m`: уровни rayd, rayspa, niko-server, Xray с откатом (без `-device`).
- [x] CI: фронт делит UDP 53 с настоящим systemd-resolved раннера, и заглушка встаёт после его перезапуска (`test/dns53`).
- [x] Маркер возврата стаба — в каталоге журнала установки, только root (`resolved-stub.pending`); метка v0.11.0 (`.gone`) понимается.

## Маскировка DNS-туннелей

Сделано на сервере: печать обвязки dnstt, [`spec/dnsseal-v1.md`](spec/dnsseal-v1.md) — niko-server v0.10 (в ветке),
raycontrol v0.13; ротация ключа (§8). Клиент — по спеке после ревью (формат финальный с нашей стороны). Класс «DNS-туннель» по статистике остаётся заметен (ниже). Две задачи,
и решаются они по-разному.

**Подпись dnstt — убирается.** Сейчас dnstt узнаётся по открытой обвязке, а не по содержимому:
- В запросе открыт ClientID (8 байт, одинаков во всей сессии), маркер и длина набивки. Опрос — 17 байт, это 28
  символов base32; с меткой dnsauth — 25 байт, 40 символов. Запросы с данными длиннее и делятся на метки.
- В ответе внутри TXT открыты префиксы длины uint16 и заголовки KCP: conv, cmd, wnd, ts, sn, una, len. sn и ts растут
  от ответа к ответу.
- У masterdns (AES-256-GCM, как его рендерит raycontrol) запрос шифруется целиком, со случайным nonce. Ответ — нет:
  в TXT открыты ID сессии, cookie, тип, номера потока и пакета, `PO:` у PONG, `INV`, нули у ответов на пробы MTU
  ([`spec/dnsauth-masterdns.md`](spec/dnsauth-masterdns.md) §1). По ответам masterdns узнаётся; закрыть — печатью
  ответов, как dnsseal-v1 (форк masterdns ведёт клиент).

Чем закрыть у dnstt:
- потоковым шифром поверх всей обвязки;
- скрытым ClientID;
- набивкой длин и разбросом длины меток.

Тогда DPI видит «какой-то высокоэнтропийный DNS-туннель», а не dnstt, и проба dnsprobe-v1 сама становится неотличимой.
Цена: свой формат dnstt с версией, несовместимый с обычными клиентами. Нужны niko-server и Niko вместе, это не
v0.11.1. Делать, если в целевых сетях появятся признаки DPI именно по dnstt.

**Класс «DNS-туннель» — не убирается без потери скорости.** Туннель видно по поведению:
- длинные метки с высокой энтропией у предела длины;
- ни одного попадания в кеш;
- много запросов в одну зону ровным ритмом;
- TXT около 1 КБ вместо мелких A/AAAA.

Выглядеть как обычный DNS — это единицы кбит/с. Что помогает на деле:
- **DoH или DoT до резолвера.** Наблюдатель на пути не видит ни меток, ни TXT, только объём к резолверу. Подпись
  тогда видит лишь оператор резолвера. Клиенту — предпочитать их, где работают (`hints.dns`, перебор Niko 1.33).
- **Смена зон.** Против блокировки по известной зоне маскировка не помогает. Нужны запасные зоны и их ротация
  (`rayctl`), и чтобы подписка переносила их без ручной работы.
