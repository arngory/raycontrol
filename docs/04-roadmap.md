Статус: **принят** (редакция 3, по решениям из [08-decisions.md](08-decisions.md); ход работ — на 2026-11-03).

Работа идёт в двух местах:

- **niko-server** ([`arngory/niko-server`](https://github.com/arngory/niko-server), ведёт серверная сессия) — data plane, по SPEC (`docs/SPEC.md` там же) с изменениями из 08, «Следствие 3».
  Клиентские доработки — в `arngory/niko`.

## Что сделано в R0

- Go-модуль, CI (генерация кода, shellcheck, vet, тесты с `-race`, golangci-lint, сборка amd64/arm64); v0 в `legacy/`.
- `internal/spa`: SPA v2 — параметры установки, ключи эпох, порты слотов, пакет, проверка с кэшем nonce;
  векторы сверены независимой реализацией.
- `internal/store`: SQLite с миграциями — пользователи, сервисы (ID = scope SPA, без повторного использования),
  устройства, доступ пользователей к сервисам, настройки, аудит.
- `internal/node`: случайные параметры установки, пакет регистрации `rcdev1:`.
- API `raycontrol.node.v1` (ConnectRPC) на unix-сокете с проверкой `SO_PEERCRED`; `rayd init|serve`, `rayctl`.

Не входит в R0 и переносится в R1: релизный workflow с подписью minisign (нужен ключ в секретах репозитория),
systemd-юниты, хранение секретов через systemd credentials, подпись подписки.

## R1: итог

Сделано:

- **Периметр** `rayspa`: таблица `inet raycontrol`, SPA v2 по UDP (NFLOG) и TCP, ограничение частоты, доступы IPv4/IPv6
  с таймаутом, отзыв, аварийный доступ к SSH для адресов администратора.
- **Ключи ноды** Ed25519 + ML-DSA-65; **подписка** с двумя подписями, `seq`, `time`, TLS только с `X25519MLKEM768`
  и пином; поля `node_keys` и `sub` в `rcdev1`.
- **Сервисы**: UID из 9100–9199, учётные данные пользователей, секреты сервисов; зоны DNS-туннелей, ключи dnstt и
  MasterDnsVPN (AES-256-GCM), `inner` с ML-KEM-768 создаётся автоматически.
- **Генерация конфигов** по CONFIG.md схемы 1: фронт (dnsmux), бэкенды dnstt и MasterDnsVPN, `inner` на Xray.
- **`rayd` на лету**: перерисовывает файлы, синхронизирует пользователей `inner` через gRPC API Xray без перезапуска,
  перезапускает изменённые процессы.
- **Развёртывание**: юниты с hardening по IPC.md, пользователи и группы, tmpfiles, polkit, sysctl, отключение stub
  resolved; `rayctl install` (периметр поднимается последним, после адреса администратора и аварийного устройства)
  и `rayctl apply`.
- **Установщик** `install/bootstrap.sh` с проверкой подписи minisign и workflow релиза.
- **Проверки в CI**: периметр на настоящем nftables в network namespace; `inner` на Xray из закреплённого форка —
  проверка конфига, пользователи через API, трафик через VLESS с ML-KEM-768.

- **Ротация UDP-портов** сервисов (spa-v2.md §11) в `rayspa` и `rcdev1`; подписка v1 заморожена.
- **Внешние зависимости закрыты**: ключ подписи релизов есть (`A9C7802E23B87A01`), `niko-server-v0.1.1` выпущен
  (фронт на UDP 53, бэкенды dnstt и masterdns; сквозной тест клиент Niko ↔ туннели ↔ `inner` — в CI niko).

- **Переносимость** (решения R2-1…R2-6): проверка хоста вместо списка систем, firewalld и ufw, восстановление
  таблицы после `flush ruleset`, порядок `rayctl apply` (`rayd` отрисовывает файлы до старта сервисов), хосты без IPv6,
  `rayctl probe`. Тест установки в CI: `bootstrap.sh` в systemd-контейнере каждой системы с её обычным файрволом,
  проверка вторым контейнером как клиентом — SPA по UDP и TCP, подписка, отзыв устройства, перезагрузка файрвола,
  `flush ruleset`, перезагрузка ноды (`test/install/`).

Релиз raycontrol v0.2.0 выпущен.

## R2: итог

Сделано (R2a):

- **REALITY на Xray**: ключи X25519 и ML-DSA-65, второй слой VLESS encryption с ML-KEM-768, Vision, 4 shortId,
  пользователи через API Xray без перезапуска, ссылка в подписке (`spec/subscription-v1.md` §4), юнит с
  `CAP_NET_BIND_SERVICE` (R2-7). Проверка цели при создании (R2-8).
- **Сквозной тест** на Xray из закреплённого форка (CI): клиент из ссылки подписки ↔ REALITY ↔ сайт, пользователь из API,
  зонд без ключей получает сертификат цели.
- **Ключи бэкендов без systemd credentials** (R2-9): тест установки поднимает весь data plane в контейнере каждой системы.

Сделано (R2b):

- **Сертификаты**: ACME HTTP-01 с окном в периметре (TCP 80 на ответчик `rayd`, элементы nftables с таймаутом),
  проверка DNS имени, продление при трети срока, отступ при ошибках; тест против Pebble в CI (R2-11).
- **Сайт-приманка и self-steal**: генерируемый сайт, `rayd site` на unix-сокете (TLS 1.3, X25519MLKEM768, h2, цепочка
  с корнем); REALITY с доменом по умолчанию целится в него; сквозной тест на Xray (R2-12).

Сделано (R2c):

- **TCP 443 за фронтом niko-server** (tcpmux, v0.2): REALITY на unix-сокете с PROXY v2, DoH и naive получают сокеты
  от фронта по SNI; 443 слушает только фронт (R2-15, заменяет R2-7 и R2-13).
- **naive (h2)** — `rayd naive`: пароль — учётные данные пользователя с ротацией, всем остальным пустой 404 сайта,
  выход только на публичные адреса (R2-14).

## R3: итог

- **Hysteria2 ×2 — бэкенды niko-server за udpmux** (v0.3): `hy2-masq` по имени в QUIC Initial с сертификатом сайта и
  пустым 404, `hy2-obfs` по salamander с пиннингом; пароли с ротацией без перезапуска (R3-4; временный вариант на Xray,

- **naive-quic и DoH3** — те же имена по HTTP/3 на UDP 443 за udpmux (R3-5).

- **Удалённый API**: свой порт за SPA, mTLS по ключу устройства, роли, регистрация устройств по приглашениям

- **Yggdrasil** — бэкенд niko-server за tcpmux (v0.4): прямой TLS-линк с `X25519MLKEM768`, ключ пользователя из его

## После проверки на VPS: кандидаты

Решать по фактам с настоящей сети (VPS-CHECK, журналы, `rayctl metrics`, сводки). Разбор безопасности, качества и
производительности — [12-review.md](12-review.md).

- **Авторизация запросов DNS-туннелей.** SPA по IP здесь невозможен: запросы приходят от резолверов, а не от клиентов,
  и у резолверов тысячи адресов, общих для всех.
  - **Сейчас:**
    - фронт на UDP 53 отвечает только за зоны туннелей, на остальное — `REFUSED`;
    - сессию туннеля открывает ключ сервиса: Noise у dnstt, AES-256-GCM у masterdns;
    - пользователя проверяет VLESS с ML-KEM-768 и его UUID в `inner`.
  - **Слабые места:**
    - ключ туннеля общий и лежит в ссылке у каждого пользователя. По утёкшей или старой ссылке можно открывать сессии
      (дальше `inner` не пройти, но тратятся ресурсы ноды);
    - делегирование зоны публично, а dnstt отвечает на любой запрос в зоне. Активной проверкой туннель можно
      опознать.
  - **Кандидат:** подпись каждого запроса ключом устройства. Без верной подписи нода отвечает как пустая зона.
    Отозванное устройство отсекается уже на уровне туннеля.
  - **Цена:**
    - меняется протокол dnstt и masterdns с обеих сторон: форки в niko-server и клиент Niko;
    - около 5 % ёмкости запроса;
    - подпись не должна отличать пользователей друг от друга на проводе.
  - Делать, если VPS-CHECK покажет, что DNS-туннели — живой резервный канал.
- **PIN у приглашения.** `rcinv1:` — секрет до первого использования: кто зарегистрируется первым, тот и получит
  устройство.
  - Кандидат: короткий код, который сообщают другим каналом. Ключ проверки регистрации — HMAC(ключ приглашения, код).
    После нескольких неверных попыток приглашение сгорает.
  - Тогда QR в мессенджере без кода бесполезен.
  - Нужны изменение `api-v1` §4 и поле в клиенте.
- **QR приглашения в `rayctl`.** Сейчас приглашение выводится строкой, а QR рисует внешний `qrencode`
  (`10-quickstart-debian13.md` §9).

## Технические проверки

Из [08-decisions.md](08-decisions.md), раздел «Следствия»:

| Проверка | Итог |
|---|---|
| Серверная часть VLESS encryption в форке sing-box | её нет — `inner` на Xray (R1-2); вернуться, если появится |
| Нагрузка UDP через фронт после разделения процессов | нагрузочный тест niko-server (SPEC §6.6): 200 потоков через каждый мультиплексор, 10 минут — 878 611 раундов, 0,005 % неудач UDP, без утечек горутин и памяти; `SO_REUSEPORT` + eBPF не нужен. Пересмотреть по `rayctl metrics` на настоящей ноде |
| PQ для Yggdrasil | внешний линк — TLS 1.3 только с `X25519MLKEM768`; сквозное шифрование Yggdrasil классическое, поэтому полезный трафик — VLESS с ML-KEM-768 к `inner` (R4-15) |
| DNS-провайдер с API для DNS-01 | Cloudflare (R4-10); другие — по запросу |
| Транспорты белых списков для Китая | открыто: отдельное исследование после v1 |
