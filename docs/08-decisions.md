## Ключевые решения

| № | Решение | Как принято |

## Следствия, которые нужно учесть

1. **Ротация SNI и сертификаты.** Каждый новый поддомен получает свой сертификат, а все сертификаты публикуются
   в журналах Certificate Transparency: домен, выпускающий много случайных поддоменов, сам становится отпечатком.
   Wildcard-сертификат этого избегает, но требует DNS-01 через API DNS-провайдера. Решение по умолчанию:
   wildcard-запись `*.example.com A`; если у провайдера есть API — wildcard-сертификат через DNS-01;
   если нет — поддомены из коротко-оконного ACME и редкая ротация SNI.
2. **Общий IP (CGNAT).** SPA открывает доступ для адреса, за которым может быть много людей, включая проверяющего.
   Поэтому сервисы остаются устойчивыми к активному зондированию сами по себе: REALITY с self-steal, naive без `407`,
   Hysteria2 masquerade — как в SPEC, только за SPA.
3. **SPEC niko-server нужно обновить** (она в `arngory/niko`, отсюда её не правим):
   - неавторизованный IP получает drop, а не приманку (§3.1, §3.5);
   - SPA обрабатывает `rayspa` через NFLOG на ротируемом порту, а не udpmux (§3.2, §3.5);
   - формат SPA v2 вместо v1 (§3.5);
   - фронт и бэкенды — отдельные процессы (§2, §3);
   - конфиги генерирует raycontrol, `init` и `export` вызываются через него (§4);
   - обязательный PQ в TLS (`X25519MLKEM768`) для Hysteria2, naive и DoH.
4. **Доработки клиента Niko:** SPA v2 с эпохами и ротируемым портом; автообновление подписки с перекрытием
   учётных данных; olcRTC и OpenFlux как исходящие; вторая ступень с VLESS encryption внутри DNS-туннелей,
   olcRTC и OpenFlux; ACME-окно не затрагивает клиент.
5. **Внутренняя ступень с PQ.** Для DNS-туннелей, olcRTC и OpenFlux внутренняя ступень — VLESS с `decryption`
   ML-KEM-768. Нужно проверить, умеет ли серверную часть VLESS encryption форк sing-box; если нет — ступень на Xray.
6. **Китай.** Выбранные транспорты белых списков работают через российские платформы (Телемост, Яндекс Документы,
   WB Stream); для Китая нужны свои платформы — отдельное исследование после v1. Hysteria2/QUIC в Китае часто
   ограничивают — основной там REALITY.

| № | Решение |
|---|---|
| R1-1 | **SPA v2 по TCP — принят** как второй носитель на тех же портах слотов ([`spec/spa-v2.md`](spec/spa-v2.md) §10). Реализация на ноде — обычный слушающий сокет в `rayspa`, а не `synproxy` + NFLOG: сокет собирает пакет из любого числа сегментов (клиент режет записи против DPI), NFLOG видит только первый. Снаружи разницы нет: порт слота отвечает на SYN, пока слот активен. Включён по умолчанию (`rayd serve -spa-tcp`). |
| R1-2 | **`inner` — на Xray** (`arngory/xray-core`), пока в форке sing-box нет серверной части VLESS encryption. |
| R1-3 | **Постквант Yggdrasil**: линк TLS 1.3 только с `X25519MLKEM768`; сквозное шифрование Yggdrasil классическое, полезный трафик идёт в `inner`. Публичные пиры — флагом, по умолчанию выключены (P-14). |
| R1-4 | **Ссылки и подписка** — предложение Niko принято как основа: параметры `niko-node`, `niko-svc`, `niko-pin`, `niko-dns`, `niko-dnskey`, `niko-inner`; подписка — JSON-конверт с двумя подписями (Ed25519 и ML-DSA-65, обе обязательны), `seq` против отката, `next` для ротации. Дополнительно в payload — поле `time` (время сервера) для проверки часов клиента. Ключи ноды — необязательное поле `node_keys` пакета `rcdev1` (§8 спецификации SPA). Формат замораживается вместе с эндпоинтом подписки в R1. |
| R1-5 | **CONFIG.md и IPC.md (схема 1, IPC 1)** приняты как основа; замечания — в [`handoff/niko-r1-reply.md`](handoff/niko-r1-reply.md). raycontrol генерирует конфиги по ним. |
| R1-6 | **UID процессов ноды** — фиксированный диапазон 9100–9199: `niko-front` 9100, бэкенды и Xray 9110–9179, `rayd` 9190, `rayspa` 9191. Таблицу ведёт аллокатор `rayd`; niko-server получает UID только из конфигов. |
| R1-7 | **Периметр закрыт при сбое**: таблица nftables остаётся, если `rayspa` остановлен. Восстановление с консоли — `rayspa teardown`. |
| R1-8 | **MasterDnsVPN — метод 5 (AES-256-GCM)**, а не 2: метод 2 у MasterDnsVPN — ChaCha20 без аутентификации, а нода разрешает только AEAD. Ключ — 32 hex-символа, как его генерирует сам MasterDnsVPN. |
| R1-9 | **Кто что пишет.** `rayd` (без привилегий) сам генерирует конфиги и секреты data plane в `/var/lib/raycontrol/rendered/<сервис>/`, синхронизирует пользователей `inner` через gRPC API Xray и перезапускает изменённые процессы (правило polkit разрешает ему только `niko-*.service`). root (`rayctl apply`) ставит системных пользователей, юниты и системные файлы — только при добавлении или удалении сервисов. Поэтому `rayd` входит в группы сервисов: ему нужно выставлять группу на их файлы. |
| R1-10 | **API ноды**: сокет `rayd.sock` открыт всем локальным пользователям (0666); кто что может, решает проверка `SO_PEERCRED` (root, сам `rayd`, группа `raycontrol`). `rayspa` к API управления не допускается, ему доступна только лента периметра. |
| R1-11 | **API Xray `inner`** — unix-сокет в отдельном каталоге `/run/niko/<inner>-api` (setgid, группа `rayd`): DNS-туннели, которые ходят в `inner` по VLESS, до API не дотягиваются. |
| R1-12 | **`inner` резолвит через DoH** (1.1.1.1, 9.9.9.9): резолвер хоста может быть в приватном диапазоне, который `inner` блокирует. Приватные сети закрыты дважды: правилом маршрутизации и собственной защитой `freedom` в Xray 26. |
| R1-13 | **Подписка в R1** — собственный порт `rayd` за SPA, TLS 1.3 только с `X25519MLKEM768`, самоподписанный сертификат с пином в `rcdev1` ([`spec/subscription-v1.md`](spec/subscription-v1.md)). В R2 переезжает за tcpmux на 443. |
| R1-14 | **Изоляция DNS-бэкендов**: `PrivateNetwork=yes`, только `AF_UNIX`, без capabilities — сети у них нет вовсе, пакеты приносит фронт, потоки уходят в `inner`. |
| R1-15 | **Лицензия** — GPL-3.0 (M-1), файл `LICENSE`. |
| R1-16 | **Ротация UDP-портов сервисов** ([`spec/spa-v2.md`](spec/spa-v2.md) §11): у сервисов на UDP 443 своё расписание порта (ключ, диапазон), формула как у SPA. `rayspa` перенаправляет порты слотов на порт сервиса через NAT; доступ — тот же SPA-доступ к UDP-порту сервиса. Параметры уходят клиенту в `services[]` пакета `rcdev1`. niko-server ничего не меняет. |
| R1-17 | **Подписка v1 заморожена** вместе с эндпоинтом `/sub/v1`; несовместимые изменения — только подписка v2 с новым путём. |
| R1-18 | **Релиз raycontrol** запускается из GitHub (workflow `Release`, ручной запуск с тегом): из сессий пушить теги нельзя. |

## Решения R2

| ID | Решение |
|---|---|
| R2-1 | **Целевые системы** (заменяет B-6): последние релизы Debian и Rocky Linux как минимум, и любой современный Linux с systemd. Проверяются в CI полной установкой: Debian 12/13, Ubuntu 24.04, Rocky Linux 9/10 (amd64; arm64 — сборка). На остальных `rayctl install` не отказывает по названию системы, а проверяет то, что нужно ноде: systemd ≥ 247 и шина D-Bus, polkit, `nft` и ядро, которые загружают таблицу периметра (пробная загрузка `nft -c`), команды `useradd`/`groupadd`/`usermod`/`runuser`/`systemd-tmpfiles`/`sysctl`; непроверенная система — только предупреждение. `bootstrap.sh` ставит зависимости через apt, dnf, zypper или pacman и проверяет подпись через openssl, без minisign. |
| R2-2 | **Файрвол хоста.** Таблица `inet raycontrol` решает, кому какой порт открыт, но пакет проходит, только если его принимают все базовые цепочки хука. Поэтому `rayctl apply` сам открывает порты ноды (диапазон SPA по UDP и TCP, порты включённых сервисов) в firewalld (сервис `raycontrol` в зоне по умолчанию и активных зонах) и в ufw (профиль приложения `raycontrol`); перенаправленные порты ротации в этом не нуждаются — NAT срабатывает раньше. Про другие таблицы nftables с `policy drop` на входе выводится предупреждение со списком портов. |
| R2-3 | **Таблица переживает чужой `flush ruleset`**: `rayspa` раз в секунду проверяет, что таблица на месте, и восстанавливает её вместе с выданными доступами (с оставшимся временем). Перезапуск nftables.service на Debian, перезагрузка firewalld или ufw открывают ноду не дольше чем на секунду. Юнит `rayspa` стартует после `nftables`, `firewalld` и `ufw`. |
| R2-4 | **Порядок `rayctl apply`**: юниты по порядку плана, `rayd` первым. Если юнит `rayd` изменился (новые группы сервисов), он перезапускается, отрисовывает файлы сервисов до открытия сокета, и только потом стартуют юниты data plane, которые эти файлы читают. Сервис, файлы которого записать нельзя, пропускается, остальные отрисовываются. |
| R2-5 | **Хост без IPv6** (`ipv6.disable=1`): фронт слушает только `0.0.0.0:53`, иначе он не стартует вовсе. |
| R2-6 | **`rayctl probe`** проверяет ноду снаружи по пакету `rcdev1`, как клиент: SPA по UDP (затем TCP), подписка с пином и обеими подписями. Им же пользуется установочный тест. |
| R2-7 | **REALITY до tcpmux слушает TCP 443 сам.** В niko-server v0.1.1 нет TCP-фронта (`check` отклоняет секцию `tcp`), поэтому Xray с REALITY получает `CAP_NET_BIND_SERVICE` и слушает порт сервиса напрямую; SPA-доступ к нему выдаёт `rayspa`, как к любому сервису. Когда у фронта появится tcpmux, Xray переезжает на unix-сокет с PROXY v2 (маршрут по SNI, CONFIG.md); код отрисовки обоих вариантов уже есть (`render.Model.FrontTCP`). Ссылки при переезде не меняются: порт 443. |
| R2-8 | **REALITY: постквант и цель.** Обмен ключами — `X25519MLKEM768`, подпись сертификата — ML-DSA-65 (`mldsa65Seed`), второй слой — VLESS encryption с ML-KEM-768, Vision. У сервиса 4 shortId случайной длины, пользователи распределены по ним. Цель пока задаётся явно (вариант B; self-steal на своём сайте-приманке — R2b, нужен сертификат). При создании `rayd` проверяет цель с ноды: TLS 1.3, `X25519MLKEM768`, HTTP/2, валидный сертификат для `sni` и **длина цепочки сертификатов не меньше сертификата REALITY с подписью ML-DSA-65** (~3,5 КБ): REALITY подгоняет свои сообщения под длины цели и с короткой цепочкой не работает (многие сайты с ECDSA-цепочками не подходят). |
| R2-9 | **Ключи бэкендов — копия в каталоге сервиса, а не `LoadCredential=`.** В контейнерах (Docker, LXC — частый вариант VPS) systemd 257 не создаёт каталог credentials сервиса, и бэкенды не стартуют. Поэтому перед стартом systemd от root копирует отрисованный ключ в `RuntimeDirectory` сервиса: `ExecStartPre=+install -m 0400 -o niko-<сервис>`, путь в конфиге — `/run/niko/<сервис>/<файл>`. Изоляция та же: читает только пользователь сервиса (фронт, хоть и в группе сервиса для сокета, — нет), исходный файл — `0600 rayd`, копия исчезает с остановкой сервиса. Работает везде, где есть systemd. |
| R2-10 | **Перерисовка чинит права.** Файл, отрисованный до появления группы сервиса, получает её при следующем проходе `rayd`, даже если содержимое не изменилось, и процесс перезапускается. Юниты без ограничения частоты запусков (`StartLimitIntervalSec=0`): процесс, которому ещё нечего читать, пробует снова каждые 2 с, а не останавливается навсегда. |
| R2-11 | **Сертификаты — ACME HTTP-01 в коротком окне.** По умолчанию Let's Encrypt. На время заказа (не дольше 3 мин) `rayspa` перенаправляет TCP 80 от любых адресов на ответчик `rayd` (порт случайный для установки и входит в порты для firewalld/ufw, потому что после перенаправления хост видит его), который отдаёт только токены этого заказа; элементы nftables живут с таймаутом и закрываются сами, даже если `rayd` или `rayspa` упадут. Перед заказом `rayd` проверяет, что имя резолвится в адрес ноды. Порт 443 при этом не открывается (TLS-ALPN-01 через tcpmux — когда он будет у niko-server; DNS-01 — если у провайдера есть API). Продление — когда осталась треть срока. |
| R2-12 | **Сайт-приманка и self-steal.** С доменом REALITY по умолчанию берёт целью свой сайт: при первом сервисе REALITY без `target` создаётся сервис `site` со случайным поддоменом. Содержимое генерируется из seed установки (небольшой сайт мастерской с журналом; у каждой установки своё), сертификат — ACME (R2-11), RSA: цепочка Let's Encrypt с корнем, который сайт досылает, длиннее сертификата REALITY с ML-DSA-65. Пока у niko-server нет бэкенда `site`, сайт обслуживает `rayd site` отдельным юнитом и пользователем, только unix-сокет `/run/niko/site/tls.sock` (`PrivateNetwork=yes`), TLS 1.3, X25519MLKEM768, h2. Сайт и REALITY ждут сертификата: юниты с `ConditionPathExists=` на свои файлы, и `rayd` запускает их, когда файлы впервые появляются. |

## Решения R3

Серверная часть R2 и R3 (мультиплексоры на 443, naive, DoH, Hysteria2) перешла из сессии Niko сюда: фронт
niko-server на 443 отложен. Пока его нет, протоколы работают на тех движках, что уже есть на ноде, каждый на своём
порту; ссылки и подписка от этого не зависят.

| ID | Решение |
|---|---|
| R3-1 | **Hysteria2 ×2 на Xray.** `hy2-masq` — UDP 443, TLS 1.3 только с `X25519MLKEM768`, сертификат сайта ноды под своим случайным поддоменом (wildcard через DNS-01 или имя в сертификате сайта), без пароля — `masquerade` с пустым `404`, как у сайта (R4-8). `hy2-obfs` — внутри salamander, на своём случайном UDP-порту (443 занят `hy2-masq`, пока нет udpmux), с самоподписанным сертификатом: клиент пинит его ключ (`niko-pin`), имени нет ни в DNS, ни в CT. Пароли пользователей — учётные данные с ротацией и перекрытием (R4-1); Xray получает их через API без перезапуска. Оба за SPA и с ротацией UDP-портов. Переход на udpmux niko-server ссылки не меняет. |
| R3-2 | **DoH в `rayd` за REALITY.** `https://<имя>/dns-query/<токен>` (RFC 8484, GET и POST, h2), TLS 1.3 только с `X25519MLKEM768`, сертификат сайта. Токен — учётные данные пользователя с ротацией; без верного токена — пустой `404`. Запросы уходят к DoH-резолверам (1.1.1.1, 9.9.9.9), в журналы не пишутся (P3). TCP 443 общий с REALITY по R2-13, поэтому DoH ставится после REALITY с self-steal. DoH3 (UDP 443) ждёт udpmux. |
| R2-13 | **TCP 443 делится через сайт, пока нет tcpmux.** REALITY отдаёт всё, что не его клиент, процессу сайта. Сайт читает ClientHello, не завершая TLS, и по SNI передаёт поток, ещё зашифрованный, в сокет службы (`routes.json`; сейчас — DoH в `rayd`). Остальное сайт обслуживает сам (R4-8), не TLS закрывает без ответа. У сайта по-прежнему нет сети: только unix-сокеты. |

## Решения R4

| ID | Решение |
|---|---|
| R4-1 | **Ротация учётных данных пользователей с перекрытием.** Каждые 30 дней у пары «пользователь — сервис» (UUID для REALITY и `inner`) появляется следующий секрет: за 3 дня до перехода он попадает в подписку как `next` с моментом `from`, и сервер уже принимает его; в момент перехода он становится текущим, а прежний принимается ещё 2 дня. Сервер (Xray) получает действующие секреты через API, без перезапуска. Следующий круг отсчитывается от перехода; после долгого простоя ноды переход не раньше чем через полный срок публикации. Сроки — флаги `rayd serve` (`-cred-period`, `-cred-lead`, `-cred-grace`). |
| R4-2 | **Удаление без следа.** Перед каждым изменением системы `rayctl install`/`apply` записывают его в журнал установки (`/var/lib/raycontrol-install`, только root): какие файлы созданы, а какие заменены (оригинал сохраняется), созданные каталоги, пользователи, группы, включённые юниты, прежние значения sysctl, прежняя цель `/etc/resolv.conf`, файлы зон firewalld и правил ufw до изменения, установленные бинарники и пакеты bootstrap. `rayctl uninstall` возвращает всё в обратном порядке и удаляет журнал; `-keep-state` оставляет базу, `-purge-packages` удаляет пакеты, поставленные bootstrap (по умолчанию остаются: ими могли начать пользоваться). Без журнала (старые установки) удаляется то, что raycontrol заведомо создаёт. Тест установки на каждой системе сравнивает снимок системы до установки и после удаления: пользователи, группы, хеши всех файлов `/etc`, ссылки, включённые юниты, правила nftables, sysctl, файрволы. |
| R4-3 | **Журналы без активности пользователей**: на обычном уровне нет адресов клиентов и устройств; подробности — только в режиме отладки на время разбора ([09-observability.md](09-observability.md)). |
| R4-4 | **Отчёт для issue** — `rayctl report`: только открытые данные и очищенные журналы, случайный ID на отчёт, ничего не отправляет сам. |
| R4-5 | **Телеметрии нет.** Нода ничего не отправляет по своей инициативе. |
| R4-6 | **Обезличенные пользователи**: без имени пользователь получает непрозрачный номер `u-xxxx-xxxx`; нода не хранит персональных данных. |
| R4-7 | **Ротация REALITY эпохами, только self-steal для имён.** У Xray один закрытый ключ на inbound, поэтому ключи не перекрываются: раз в 90 дней (`-reality-period`) нода заводит следующий набор — ключи X25519 и ML-DSA-65, зерно ML-KEM-768 второго слоя, shortId и, если REALITY ворует у своего сайта, новое имя — и за срок публикации (`-cred-lead`, 3 дня) до перехода кладёт его в подписку как `next`. В момент `from` (с точностью до минуты) нода переключается и перезапускает REALITY; прежний набор после перехода не работает, клиент, не успевший обновить подписку, обновляет её (подписка от REALITY не зависит). Имя меняется только на случайный поддомен собственного домена ноды: чужие сайты не ищутся и не сканируются, соседние адреса тоже. Новое имя берётся, только если оно уже указывает на ноду (wildcard `*.<domain>`), и публикуется, когда сертификат сайта покрывает оба имени (менеджер сертификатов просит оба; если новое не выходит, старое всё равно продлевается); не успел за сутки (`-reality-prepare`) — меняются только ключи. Сайт переезжает на новое имя вместе с REALITY; старое имя остаётся в сертификате до продления. `rayctl service rotate NAME` переносит переход на «через срок публикации», `-now` — немедленно (утечка ключей, блокировка имени). Если в одном профиле ждут и смена UUID (R4-1), и смена ключей, `next` описывает ближайшую; следующий UUID в ссылке со сменой ключей ставится сразу, сервер принимает его с момента публикации. |
| R4-8 | **Сайт-приманка никого не обслуживает.** До сайта доходит только тот, кому REALITY отказал, а 443 закрыт SPA, так что это соседи клиента по адресу (CGNAT) или зонд, подменивший адрес. Сайт завершает TLS с настоящим сертификатом (без этого REALITY не работает), а дальше по умолчанию отвечает на всё пустым `404` без заголовков сервера. Другие режимы — `403`, `silent` (держит запрос минуту и рвёт соединение без ответа) и `pages` (сгенерированный сайт, только по явному выбору). Файлы читает только `pages`; остальные режимы дальше строки запроса и заголовков ничего не разбирают. Режим меняется командой `rayctl service set site answer=…`. |
| R4-9 | **Меньше ядра для чужих.** Удалённые уязвимости стека (сборка фрагментов, IP-опции, заголовки расширений IPv6, разбор TCP) закрывает обновление ядра; нода сокращает то, что до них доходит. (1) Цепочка `early` в таблице периметра — `prerouting`, приоритет −450, то есть до сборки фрагментов (−400) и conntrack. Она касается только пакетов к самой ноде (`fib daddr type local`) и отбрасывает все фрагменты IPv4/IPv6, IPv4 с опциями, IPv6 с заголовками routing/destination options и hop-by-hop не от link-local, а также невозможные сочетания флагов TCP. Клиентам ничего из этого не нужно: SPA укладывается в один пакет, QUIC ставит DF, TCP находит MTU сам; ICMP-ошибки, включая packet-too-big, проходят. (2) sysctl: без source routing и redirects, SYN cookies, RFC 1337, без фиктивных ICMP-ошибок. Всё это в журнале установки и откатывается. (3) `rayctl install` и `report` предупреждают, если установлено более новое ядро, чем загружено, если система просит перезагрузку и если обновления безопасности не ставятся сами. (4) Без SPA снаружи видны только порты SPA и публичные (DNS 53). TCP-носитель SPA принимает соединение до проверки пакета; на сетях, где хватает UDP, его выключает `rayd serve -spa-tcp=false`. |
| R4-10 | **Cloudflare — базовый DNS-провайдер.** С токеном (права Zone.DNS:Edit и Zone.Zone:Read на зону домена ноды; задаётся `rayctl install -cloudflare-token-file` или `rayctl dns cloudflare`, хранится только в базе, класс P2) нода сама ведёт свои записи. Это wildcard `*.<домен>` (A/AAAA на адрес ноды), через который резолвятся сайт и все имена REALITY, включая будущие, и для DNS-туннелей — случайное имя NS-сервера с NS-делегированием каждой зоны туннеля. Все записи без проксирования, с комментарием `raycontrol`. Чужие записи не трогаются: если под нужным именем стоит чужая запись с другим значением или оранжевое облако, это конфликт, нода его показывает и имя не меняет. Синхронизация идёт при изменении нужного набора и раз в час. Сертификаты выпускаются через DNS-01 одним `*.<домен>`: окно на TCP 80 больше не открывается, смена имени REALITY не требует нового сертификата, а в CT-логах виден только `*.<домен>` без поддоменов ноды. `rayctl uninstall` удаляет записи raycontrol (`-keep-dns` оставляет их), `rayctl dns remove` — то же без удаления ноды. Без провайдера всё работает как прежде: записи вручную, HTTP-01 в окне. |
| R4-11 | **Data plane приходит с релизом.** Архив релиза raycontrol содержит, кроме `rayd`, `rayspa`, `rayctl`, ещё Xray, собранный в Release-workflow из закреплённого коммита форка, и niko-server из его релиза, сверенный с SHA-256 из `deploy/versions.env`. Всё под одной подписью minisign: у bootstrap один корень доверия, и зеркала GitHub работают для всего сразу. `rayctl install -dataplane` кладёт бинарники в `/usr/local/libexec/raycontrol/`, а не в `/usr/local/bin`: Xray или niko-server, которые хост держит для другого софта, не заменяются; всё через журнал установки. Установка сразу заводит сервисы: `-services reality,dnstt,masterdns`, с доменом по умолчанию REALITY, `none` — ничего. |
| R4-12 | **`rayctl update` — обновление на месте с откатом.** Скачивает релиз (последний или `-version vX.Y.Z`) с GitHub, при недоступности — через те же зеркала, что bootstrap (`RAYCONTROL_MIRRORS`). Проверяет подпись SHA256SUMS тем же ключом minisign, что зашит в bootstrap (сверка ключей — в тестах), затем хеш архива. Версия берётся из подписанного trusted comment, поэтому зеркало не подсунет старый релиз под видом нового: `latest` никогда не понижает версию, откат на старый релиз — только явным `-version`. Узлам без доступа наружу — `-from DIR` с теми же тремя файлами, проверка та же. Текущие бинарники сохраняются в `/var/lib/raycontrol-install/previous` (только root, удаляются вместе с журналом). Дальше: замена бинарников (control plane — атомарным переименованием, data plane — через журнал), перезапуск `rayd`, `rayctl apply` уже новой версией, перезапуск `rayspa` и работающих `niko-*`. Нода должна ответить нужной версией, а периметр — вернуться; если нет, прежние бинарники ставятся обратно сами. `-rollback` делает то же вручную, без сети. Перезапуск рвёт соединения на секунды; клиенты переподключаются и шлют SPA заново. |
