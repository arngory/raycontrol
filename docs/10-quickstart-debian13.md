# 10. Нода с нуля: Debian 13 (trixie) + Cloudflare

Полное руководство: от чистого VPS с Debian 13 до работающих клиентов. Рассчитано на человека, который умеет зайти
на сервер по SSH и выполнить команду. Короткий список всех команд — в [шпаргалке](cheatsheet.md).

**Как читать.** У каждого шага четыре части: команда, что вы должны увидеть, что это значит и что делать, если
вы видите другое. Не переходите к следующему шагу, пока текущий не дал ожидаемого результата.

**Условные значения.** Подставляйте свои:

| В тексте | Что это |
|---|---|
| `203.0.113.7` | публичный адрес вашего VPS |
| `example.com` | ваш домен |
| `198.51.100.50` | адрес, с которого вы заходите на сервер по SSH |
| `u-k3f9-x2qa` | имя пользователя, которое выдаст нода |
| `v0.26.0` | версия релиза; руководство описывает её |

Команды выполняются на сервере от root, если не сказано иначе. Вывод команд — английский, как его печатают
программы; значения в примерах (номера портов, имена, даты) у вас будут свои.

> выводом собранных `rayctl` и `rayd`; то, что добавлено для v0.26.0, взято из строк формата в коде и из тестов.
>
> - **Не запускалось на настоящем VPS.** Установка по этому тексту на настоящий Debian 13 при его написании не
>   выполнялась. В репозитории записана одна установка на настоящий VPS — версий v0.10.1–v0.11.0 (Debian 13,
>   Let's Encrypt, Cloudflare); полная проверка с клиентом на настоящей сети числится открытой
>   ([handoff/SYNC.md](handoff/SYNC.md)).
> - **CI, job `install`** (`test/install/run.sh`): полная установка через `bootstrap.sh` в контейнерах с systemd на

>   v0, установка, DNS-туннели (dnstt, masterdns, slipstream) и hy2-obfs с работающими процессами, удалённый API
>   с регистрацией по приглашению, проба снаружи из второго контейнера (SPA по UDP и TCP, подписка, замер

>   закрытая), поэтому REALITY, naive и Yggdrasil там только ставятся — их процессы ждут сертификата.
> - **CI, остальное:** туннели на настоящих Xray, niko-server и slipstream (`xray`); сертификаты на Pebble,
>   тестовом CA Let's Encrypt, через HTTP-01 и DNS-01 (`acme`); подпись релиза против настоящего minisign
>   (`bootstrap`); периметр и relay в сетевых пространствах имён (`perimeter`); обновление с прежних релизов на
>   Debian 13 (`upgrade`). Cloudflare — на имитации его API. Установка relay скриптом на хост с systemd и
>   обновление relay (`rayctl update`) в CI не запускаются (§12.4).
> - **Interop с клиентом Niko:** тест клиента против ноды без systemd (`rayd serve -supervise`) на Linux, без
>   телефона. По записи в [handoff/SYNC.md](handoff/SYNC.md) (строка T15.1) он зелёный на v0.25.1;
>   для v0.26.0 записи при правке руководства ещё не было.
> - **Проверено при написании:** подпись и контрольная сумма опубликованного релиза v0.25.1 (§3); вывод команд
>   `rayctl` — на локальном `rayd` без data plane и без systemd, тоже для v0.25.1. v0.26.0 при правке руководства
>   ещё не был опубликован.
> - **Пины сертификата** (§8, §12.5): сквозного прогона клиента с пинами из подписки не было
>   ([spec/cert-pin-v1.md](spec/cert-pin-v1.md) §12).
> - **Клиент Niko** описан по документам этого репозитория и по сообщениям сессии, которая ведёт клиент; экраны
>   приложения здесь не проверялись.
> - **`rayctl` для macOS и FreeBSD** (§7) — с v0.26.0. Он собирается с Linux. На macOS он запускался только в CI
>   (справочный job), на FreeBSD **не запускался** нигде.
> - **Ping через ноду** (§11) проверен только в автоматическом interop на Linux, не на физическом телефоне.

## 0. Что вы получите и что для этого нужно

### Что такое нода

Нода — один сервер, на котором стоит всё нужное для обхода блокировок: несколько протоколов, файрвол и
управление. Соседних серверов, баз данных и панелей ей не нужно.

- **`rayd`** — управление: пользователи, устройства, ключи, сертификаты, подписка.
- **`rayspa`** — периметр: файрвол nftables, в котором закрыто всё. Порт открывается только адресу, который прислал
  верный одноразовый SPA-пакет. Это называют «стуком»: клиент стучится перед каждым подключением сам. Для
  постороннего сервер выглядит выключенным.
- **Data plane** — программы, которые несут трафик: Xray (наш форк), niko-server и slipstream-server. Они приходят
  в том же подписанном архиве, ставить их отдельно не нужно.
- **Клиент** — приложение Niko на Android. Оно получает от ноды подписанную **подписку**: список **профилей**
  (по одному на каждый сервис, доступный пользователю) — и само выбирает рабочий.

Слова, которые встретятся дальше:

| Слово | Что значит |
|---|---|
| сервис | протокол, поднятый на ноде: `reality`, `naive`, `dns` и так далее |
| профиль | сервис глазами клиента: строка подписки, по которой он подключается |
| пользователь | человек; у него срок, лимит и набор сервисов |
| устройство | телефон или ноутбук пользователя; у каждого свой ключ, отзывается отдельно |
| приглашение | одноразовая строка или QR, по которой устройство регистрируется само |
| пакет устройства | строка `rcdev1:…` с ключом устройства: старый способ, без приглашения. «Аварийный пакет» — такой же, для входа по SSH |
| пакет relay | строка `rcrelay1:…` с ключом relay (§12.4) |
| SPA-пакет, стук | одна датаграмма или одно короткое TCP-соединение с подписью устройства; после него нода на время открывает порты адресу отправителя |

Слово «пакет» без уточнения дальше не используется: системные пакеты Debian названы системными, сетевые —
сетевыми.

### Что несёт каждый профиль

Факты — из [15-traffic.md](15-traffic.md); там же подробности.

| Профиль | TCP | UDP | DNS | ICMP (ping) | Когда использовать |
|---|---|---|---|---|---|
| REALITY (`reality`) | да | да, внутри TCP | любой | нет | основной: TCP 443, снаружи — TLS к обычному сайту |
| Hysteria2 (`hy2-masq`, `hy2-obfs`) | да | да, настоящие датаграммы QUIC | любой | нет | самый быстрый; звонки, игры, WireGuard. Нужен UDP 443 |
| naive (`naive`) | да | да, внутри потока (с v0.20.0) | любой | да, если включить (§9, §11) | второй TCP-профиль (HTTP/2 и HTTP/3); единственный с ping через ноду |
| DoH (`doh`) | — | — | это и есть DNS | — | резолвер ноды для клиента, по 443 |
| Yggdrasil (`ygg`) | да, через `inner` | да, через `inner` | как у `inner` | только ping адреса ноды в mesh | запасной путь через публичные пиры; сеть между своими устройствами (§9) |
| DNS-туннели (`dns`, `mdns`, `slip`) | да, через `inner` | да, но поверх надёжного потока | как у `inner` | нет | аварийный канал, когда закрыто всё, кроме DNS: 0,1–3 Мбит/с |
| relay | как у профиля за ним | как у профиля | как у профиля | нет | вход через второй хост, когда прямой путь к ноде режется |

- **`inner`** — внутренняя ступень: Xray, в который приходят DNS-туннели и Yggdrasil. Создаётся сама, отдельно её
  не заводят.
- **Назначения — только публичные адреса.** Частные сети, loopback и сама нода закрыты на всех профилях.
- **UDP поверх TCP** (REALITY, naive) работает, но при потерях даёт рывки задержки. Звонки и игры лучше вести через
  Hysteria2.

### Требования к VPS

| | Минимум | Рекомендуется |
|---|---|---|
| Процессор | 1 vCPU | 2 vCPU и больше |
| Память | 1 ГиБ | 2 ГиБ |
| Диск | 10 ГБ | 20 ГБ |
| Виртуализация | KVM или другая с собственным ядром | — |
| Архитектура | amd64 или arm64 | — |
| Сеть | статический публичный IPv4; входящий UDP не режется | плюс IPv6 |
| Система | Debian 13 | — |

**Откуда цифры.**

- **Память.** Замер от 2026-11-04 на облачном vCPU Xeon 2,1 ГГц, весь тогдашний стек: процессы ноды в простое —
  около 225 МиБ, вместе с `rayspa` — около 240 МиБ, под нагрузкой на десяток МиБ больше. Debian сам берёт
  150–250 МиБ. После замера добавился slipstream: его сервер — около 13 МБ и ещё около 80 КБ на соединение
  ([14-capacity.md](14-capacity.md)). Заново весь стек не мерили.
  - Проверка хоста отказывает при памяти меньше 400 МиБ и предупреждает при меньше 900 МиБ.
- **Процессор** (тот же замер, CPU ноды на 1 ГиБ скачанного, loopback):
  - REALITY — около 3,5 с: одно ядро тянет порядка 2 Гбит/с;
  - Hysteria2 — около 32 с: 250–300 Мбит/с на ядро. UDP-сервисы упираются в процессор первыми.
  - Проверка хоста предупреждает, если ядер меньше двух.
- **Диск.** Архив релиза для amd64 — около 57 МБ, распакованный — около 146 МБ (замер по опубликованному v0.25.1;
  архив v0.26.0 не мерился).
  `rayctl update` держит прежние бинарники для отката, а на время обновления на диске лежат ещё архив и его
  распакованная копия. Проверка хоста отказывает, если в `/usr/local` или `/var/lib` свободно меньше 500 МиБ, и
  предупреждает при меньше 2 ГиБ. База ноды — единицы МБ, журналы ведёт journald.
- **Сколько людей тянет нода** — [14-capacity.md](14-capacity.md). Коротко: на 1 vCPU это сотни пользователей, из
  которых одновременно активны десятки.
- **Нода не зависит от хранилища корней образа.** Свои соединения (Let's Encrypt, GitHub, Cloudflare, IPinfo,
  вышестоящие DoH) нода проверяет по встроенному списку корней — тому же, что у клиента: Chrome и Mozilla без
  центров из Китая, 91 корень. Пустое, устаревшее или подделанное хранилище в образе ей не мешает и её соединения
  не открывает. Если исходящий HTTPS идёт через прокси, который вскрывает TLS (корпоративная сеть), его корень
  нужно дать ноде явно: `rayctl roots file proxy-root.pem` (подробнее — в §6.4). Сам `bootstrap.sh` качает
  через curl и хранилище системы; файлы он проверяет по подписи.
- **Каталог состояния** `/var/lib/raycontrol` нельзя делать ссылкой на другой диск: ключи сервисов root копирует,
  не переходя по ссылкам, и сервисы не стартуют. Другой диск подключают через bind mount — строкой в `/etc/fstab`:
  `/data/raycontrol /var/lib/raycontrol none bind 0 0`.

### Что проверить у провайдера до покупки

- **Виртуализация.** Нужна KVM или другая с собственным ядром.
  - OpenVZ не подходит: периметру нужны nftables ядра 5.2 и новее.
  - LXC — только если хост даёт свежее ядро с модулями nftables и `nesting=1`. В контейнере обновления ядра и размер
    таблицы соединений — в руках провайдера.
  - Что есть у конкретного VPS, покажет проверка хоста (§4).
- **Входящий UDP на 443 и 53.** Без него не работают Hysteria2, naive по QUIC, DoH3 и DNS-туннели. Некоторые
  провайдеры закрывают входящий UDP 53.
- **Статический IPv4.** Адрес задаётся при установке и сам не отслеживается. Смена адреса — это переезд (§12).
- **Трафик.** Узнайте квоту в месяц и скорость порта. Замеры канала клиентом тоже тратят трафик: до 1 ГиБ на
  устройство в сутки.
- **Файрвол провайдера** (security group, cloud firewall). Если он есть, его надо открыть, иначе клиенты не дойдут
  до ноды: правил провайдера нода не видит. Что открывать:

  | Что | Протокол | Зачем |
  |---|---|---|
  | порт SSH (обычно 22) | TCP | ваш вход на сервер |
  | 443 | TCP и UDP | все сервисы, кроме DNS-туннелей |
  | 53 | UDP | DNS-туннели, если вы их ставите |
  | диапазон SPA — свой у каждой ноды | TCP и UDP | SPA-пакеты, которые открывают порты |
  | порт подписки — свой у каждой ноды | TCP и UDP | подписка и замер канала |
  | порт API — свой у каждой ноды | TCP | регистрация по приглашениям, управление с телефона |
  | диапазоны UDP-сервисов — свои у каждой ноды | UDP | Hysteria2, naive по QUIC и DoH3 на меняющихся портах |
  | 80 | TCP | только без Cloudflare: выпуск сертификата |

  Точные номера печатает установка (§6). Проще всего открыть у провайдера **весь входящий трафик**: периметр ноды
  сам закрывает всё, кроме SPA и открытого по SPA. Если файрвола у провайдера нет, делать ничего не нужно.

  Цена этого выбора: периметр ноды тогда — единственная защита сервера, и у неё есть окна (§6.1). Поэтому вход по
  SSH только по ключам обязателен (§2.6).

### Что ещё понадобится

- **Вход на VPS по SSH-ключу от root.** Адрес, с которого вы ставите ноду, станет адресом администратора: SSH с
  него открыт всегда. Остальным SSH после установки закрыт.
- **Решение, как вы будете попадать на сервер потом.** Адрес администратора — это один адрес: тот, с которого
  пришла SSH-сессия установки. Если он у вас меняется — домашний интернет без постоянного адреса, мобильная сеть,
  временные адреса IPv6, — то после первой же смены сервер перестанет пускать вас по SSH. Выберите заранее одно из
  двух (или оба):
  - **сеть вместо адреса** — при установке задать `-admin` сетью вашего провайдера, из которой приходят ваши
    адреса (§5.2). Сеть — не шире /16 для IPv4 и /48 для IPv6; для IPv6 обычно хватает своей /64. Чем шире сеть,
    тем больше чужих адресов достают до вашего sshd, так что вход только по ключам обязателен;
  - **вход аварийным пакетом устройства** — команда `rayctl knock` открывает SSH вашему текущему адресу, каким бы
    он ни был (§7). Для неё нужен `rayctl` на вашей машине: он есть для Linux, macOS и FreeBSD (§7, «`rayctl` на
    своей машине»). Сборки для Windows нет.

  Если не сделать ни того, ни другого, обратно пустит только консоль провайдера (§7).
- **Своя машина с `rayctl`** — для `rayctl knock` и для проверки ноды снаружи (§8): с Linux (подойдёт виртуальная),
  macOS или FreeBSD.
- **Домен, делегированный в Cloudflare**, и **API-токен Cloudflare** — подробно в §1.
- **Телефон с Niko** — для проверки в конце.

### Что не нужно

- **Ставить Xray, sing-box, nginx, certbot, Docker, базу данных или панель.** Всё нужное приходит в одном архиве,
  сертификаты нода выпускает сама.
- **Настраивать файрвол на сервере.** Его ведёт `rayspa`. Свои правила ufw или nftables для ноды писать не нужно.
- **Ставить minisign.** Подпись релиза установщик проверяет через openssl. minisign нужен, только если вы хотите
  проверить подпись сами (§3).
- **Выключать systemd-resolved.** Нода делит с ним UDP 53.
- **Заводить записи DNS руками** — если есть токен Cloudflare.
- **Регистрировать что-либо у нас.** Нода никому о себе не сообщает, учётных записей и телеметрии нет.

## 1. Домен и токен Cloudflare

### Домен

1. Нужен домен, у которого серверы имён (NS) у регистратора указывают на Cloudflare, и Cloudflare показывает его
   подключённым.
2. Проксирование Cloudflare (оранжевое облако) записям ноды не включается: REALITY и DNS-туннелям нужен режим
   DNS only. Записи, которые нода завела сама, она создаёт без проксирования.

**Что нода делает с зоной.**

- Заводит только свои записи, с комментарием `raycontrol`:
  - `*.<домен>` на адрес ноды;
  - если есть DNS-туннели — имя NS-сервера и NS-делегирование зоны каждого туннеля.
- На сам домен (корень) не ставит ничего.
- Чужие записи не меняет и не удаляет. Если под нужным ей именем уже есть чужая запись, это конфликт: нода
  оставляет имя как было, а `rayctl dns` показывает строку `problem: …`.
- `rayctl uninstall` удаляет только записи с комментарием `raycontrol`.

**Одна зона Cloudflare — одна нода.** Свои записи нода узнаёт по комментарию `raycontrol` во всей зоне, а не по
своему поддомену. При каждой сверке (раз в час и по `rayctl dns sync`) она удаляет из зоны все записи с этим
комментарием, которых нет в её собственном списке, а `rayctl uninstall` удаляет их все. Две ноды в одной зоне —
даже под разными поддоменами — будут стирать записи друг друга. Второй ноде нужна другая зона Cloudflare (другой
домен) или режим без Cloudflare.

**Если домен уже используется** (сайт, почта), дайте ноде отдельный поддомен: `-domain node.example.com`. Зона
Cloudflare та же, а все записи ноды будут под ним: `*.node.example.com` и делегирование туннелей.

- Wildcard не мешает именам, у которых есть свои записи: `www`, `mail` и прочие отвечают как раньше.
- Но он отвечает за любое несуществующее имя. Без поддомена на ноду указывали бы все опечатки основного домена.
- Если в зоне уже есть свой `*.example.com`, нода его не тронет, и её имена тогда не будут указывать на неё. В этом
  случае поддомен обязателен.

### Токен Cloudflare

Токен создаётся в панели Cloudflare: *My Profile → API Tokens → Create Token*. Панель Cloudflare при написании
руководства не открывалась: названия пунктов взяты из прежней версии этого текста. Если они изменились, ищите по
смыслу — важны права из шага 2.

1. Возьмите шаблон «Edit zone DNS» или «Create Custom Token».
2. Права — ровно два, нода проверяет оба:
   - **Zone · DNS · Edit** — заводить записи;
   - **Zone · Zone · Read** — найти зону домена. Если шаблон дал только первое право, добавьте второе сами.
3. Zone Resources — *Include · Specific zone ·* ваш домен. Доступ к остальным зонам ноде не нужен.
4. Создайте токен и скопируйте его **значение**. Оно показывается один раз.

Что важно:

- Нужно значение токена, а не его ID из списка токенов.
- Подходит и токен аккаунта (*Manage Account → Account API Tokens*) с теми же правами.
- Глобальный API-ключ (Global API Key) не подходит.
- В командную строку токен не пишут: он попадёт в историю оболочки и в список процессов. В §5 он кладётся в файл.

### Без Cloudflare

Можно, но это больше ручной работы. Этот путь проверен в CI на тестовом CA; записи о его проверке на настоящем VPS
в репозитории нет.

- Записи заводятся вручную у вашего DNS-провайдера — какие именно, покажет `rayctl dns`: одна запись
  `*.<домен>` на адрес ноды, а с DNS-туннелями ещё имя NS-сервера и по NS-записи на зону.
- Сертификат выпускается через HTTP-01: нода на несколько минут открывает TCP 80, и этот порт должен быть открыт у
  провайдера.
- Сертификат выпускается на конкретные имена сервисов, а не wildcard: эти имена попадают в публичные журналы
  сертификатов.

Тогда в командах ниже просто не указывайте `-cloudflare-token-file`. Подключить Cloudflare можно и позже:
`rayctl dns cloudflare`.

## 2. Подготовка системы

Зайдите на сервер по SSH от root. Команды установки запускайте из обычной SSH-сессии, **не из tmux и не из screen**:
установка берёт адрес администратора из текущей SSH-сессии и изнутри tmux его не видит (§5, флаг `-admin`).

### 2.1. Обновления

Сначала системные пакеты, потом обновление — в таком порядке: файл, по которому видно, что нужна перезагрузка,
создаёт системный пакет `unattended-upgrades`, и он должен стоять до обновления ядра.

```bash
apt update && apt install -y unattended-upgrades systemd-timesyncd curl
```

```bash
apt full-upgrade -y
```

```bash
cat /etc/apt/apt.conf.d/20auto-upgrades
```

Что вы должны увидеть — среди строк есть такая:

```
APT::Periodic::Unattended-Upgrade "1";
```

- **Что это значит.** Обновления безопасности ставятся сами. Удалённые уязвимости сетевого стека закрывает только
  новое ядро; нода сокращает то, что до ядра доходит, но обновлений не заменяет.
- **Если файла нет или там `"0"`:** `dpkg-reconfigure unattended-upgrades` и ответ «Yes».

### 2.2. Перезагрузка после обновления

```bash
ls /var/run/reboot-required
```

```bash
uname -r; ls /lib/modules
```

- **Файл есть** или в `/lib/modules` есть версия новее той, что печатает `uname -r` — обновление поставило новое
  ядро, а работает старое. Перезагрузитесь и зайдите снова:

```bash
reboot
```

- **Файла нет** (`No such file or directory`) и версия в `/lib/modules` одна, та же, что у `uname -r`, —
  перезагрузка не нужна.
- **Не уверены** — перезагрузитесь: на сервере, где ещё ничего нет, это ничего не стоит. Проверка хоста (§4)
  сравнивает ядра сама и предупредит строкой `warn  updates`.

### 2.3. Часы

```bash
timedatectl
```

Что вы должны увидеть — среди строк:

```
System clock synchronized: yes
```

- **Что это значит.** По часам считаются SPA, срок приглашений и сертификаты. SPA допускает расхождение не больше
  30 секунд.
- **Если `no`:** подождите минуту после установки `systemd-timesyncd` и повторите. Если не помогло, у провайдера
  может быть закрыт исходящий UDP 123.

### 2.4. Порты 443 и 53 свободны

```bash
ss -ltnup 'sport = :443'
```

Что вы должны увидеть — только строку заголовка (`Netid State …`), без процессов под ней.

- **Если там nginx, apache или что-то ещё** (бывает в образах провайдеров): остановите и выключите, например
  `systemctl disable --now nginx`. Порт 443 нода обслуживает сама.

Если вы будете ставить DNS-туннели, проверьте и UDP 53:

```bash
ss -lunp 'sport = :53'
```

- **Пусто или только `systemd-resolve` на `127.0.0.53` и `127.0.0.54`** — всё в порядке: с ним нода порт делит.
- **Там bind9, dnsmasq или unbound** — остановите и выключите их. Иначе проверка хоста откажет.

### 2.5. umask и `/etc/resolv.conf`

```bash
umask
```

Что вы должны увидеть:

```
0022
```

- **Что это значит.** Службы ноды работают под своими пользователями и должны читать свои файлы. Установщик и
  `rayctl` сами работают с umask 022, но файлы, которые вы создаёте руками, следуют umask вашей оболочки.
- **Если `0077` или `0027`:** выполните `umask 022` в этой сессии.

```bash
ls -lL /etc/resolv.conf
```

Права должны начинаться с `-rw-r--r--`, а в файле должна быть хотя бы одна строка `nameserver`.

- `rayctl install` и `rayctl apply` сами открывают файл на чтение, если он принадлежит root, но строки
  `nameserver` за вас не напишут.
- Если в первых трёх строках `nameserver` только частный резолвер (10.0.0.2, 169.254.169.254 у части облаков),
  локальный (127.0.0.1) или адрес самой ноды, то Hysteria2 и пиры Yggdrasil не найдут имён: их юниты не пускают в
  частные сети. Заглушка systemd-resolved (127.0.0.53, 127.0.0.54) им открыта, публичный резолвер тоже подходит.
  Проверка хоста об этом предупредит.

### 2.6. SSH

raycontrol не настраивает sshd. Вход только по ключам и запрет паролей (`PasswordAuthentication no` в
`/etc/ssh/sshd_config`) — на вашей стороне. Сделайте это до установки и убедитесь, что вход по ключу работает.

**Порт sshd выберите до установки.** Установка один раз читает порт, на котором слушает sshd, и открывает в
периметре именно его. Если потом перенести sshd на другой порт, новый порт окажется закрыт для всех, включая
адреса администратора и аварийный пакет устройства. Нужен нестандартный порт — смените его сейчас, перезапустите sshd,
зайдите заново на новый порт и только потом ставьте ноду. Как сменить порт на уже установленной ноде — §7.

**Узнайте адрес, каким вас видит сервер:**

```bash
echo $SSH_CONNECTION
```

Первое поле вывода — ваш адрес глазами сервера, третье — адрес сервера. Именно первое поле установка запишет
адресом администратора. Если вы зашли через VPN или промежуточный сервер, там будет адрес выхода VPN или этого
сервера, а не вашего дома: тогда задайте `-admin` сами (§5.2).

## 3. Релиз: откуда берётся и как проверяется

Нода ставится скриптом `bootstrap.sh`. Он скачивает релиз, проверяет его подпись и только потом что-то ставит.

### 3.1. Скачать и прочитать установщик

```bash
curl -fsSL https://raw.githubusercontent.com/arngory/raycontrol/v0.26.0/install/bootstrap.sh -o bootstrap.sh
```

```bash
less bootstrap.sh
```

```bash
sha256sum bootstrap.sh
```

Что вы должны увидеть:

```
627dede2e62fce85ab576b0ab5ce903388be53597a2f74fe0dd19b2bbe7dadce  bootstrap.sh
```

- **Сам скрипт не подписан.** Подписан только релиз — архив, который скрипт скачает. Подлинность скрипта держится
  на трёх вещах: вы берёте его по HTTPS с GitHub, из тега релиза, а не из ветки; вы его читаете; и сумма
  совпадает с этой страницей. Скрипт небольшой, около 400 строк, и запускаете вы его от root — просмотрите его.
- **Что это значит.** Сумма посчитана для `install/bootstrap.sh` тега `v0.25.1`; в v0.26.0 этот файл не менялся,
  и сумма у него та же. Файл в ветке `main` на момент v0.25.1 был байт в байт таким же.
- **Если сумма другая:** вы скачали другую версию скрипта (другой тег или ветку) или его подменили по пути. Не
  запускайте, пока не поймёте, какая из причин ваша.
- **Какой релиз он поставит.** Последний опубликованный, а не обязательно v0.26.0. Ровно v0.26.0 —
  `RAYCONTROL_VERSION=v0.26.0` перед командой (§3.3). Руководство описывает v0.26.0; в более новом релизе вывод
  и возможности могут отличаться.

### 3.2. Сверить ключ подписи

```bash
grep '^PUBKEY=' bootstrap.sh
```

Что вы должны увидеть:

```
PUBKEY="RWQBergjLoDHqeme5vyIuIRXJLjTj1EF3jR1nlWBVJO3rWxgy9SZj4bD"
```

- **Что это значит.** Это публичный ключ minisign, которым подписаны релизы raycontrol; ID ключа —
  `A9C7802E23B87A01`. Он записан в трёх местах, и все три должны совпадать: в `install/bootstrap.sh`, в
  [RELEASE.md](RELEASE.md) («Текущий ключ») и в самом `rayctl`, который тем же ключом проверяет обновления.
  Закрытая часть ключа есть только у владельца проекта и в секретах сборки релизов.
- **Если строка другая:** не запускайте скрипт. Вы скачали не тот файл или его подменили по пути.
- **Чего эта проверка не доказывает.** Что скрипт настоящий: подменённый скрипт может нести любую строку, в том
  числе эту. Она нужна для другого — убедиться, что релиз будет проверяться нашим ключом, а не чьим-то ещё.
  Подлинность самого скрипта — шаг 3.1.

### 3.3. Что проверяет установщик сам

Запускать ничего не нужно, это описание того, что произойдёт в §4 и §5:

1. Скачивает три файла последнего релиза: архив `raycontrol-linux-amd64.tar.gz` (на arm64 —
   `raycontrol-linux-arm64.tar.gz`), `SHA256SUMS` и `SHA256SUMS.minisig`.
2. Проверяет подпись `SHA256SUMS` ключом из шага 3.2.
3. Читает версию из подписанного комментария. Релиз старше v0.10.0 или не тот, что вы просили, не ставится.
4. Сверяет SHA-256 архива с `SHA256SUMS`.

В архиве: `rayd`, `rayspa`, `rayctl`, `xray`, `niko-server`, `slipstream-server`, база AS `ipinfo_lite.mmdb`,
`NOTICE` и `VERSIONS` — из каких коммитов что собрано.

Если всё сошлось, установщик печатает:

```
bootstrap: release v0.26.0, signature verified
```

Если нет — одну из строк ниже и останавливается, ничего не поставив:

| Строка | Причина | Что делать |
|---|---|---|
| `bootstrap: cannot download …` | github.com недоступен и зеркала тоже | проверьте сеть; свои зеркала — `RAYCONTROL_MIRRORS` (ниже) |
| `bootstrap: release signature does not verify` | файлы не те, что подписаны | не продолжайте; повторите позже, сравните с шагом 3.4 |
| `bootstrap: checksum mismatch` | архив повреждён или подменён | повторите запуск |
| `bootstrap: asked for …, the signature says …` | зеркало отдало другой релиз | повторите; смените зеркало |

**Переменные окружения установщика:**

- `RAYCONTROL_VERSION=v0.26.0` — поставить конкретный релиз, а не последний.
- `RAYCONTROL_MIRRORS="https://mirror.example/"` — свои префиксы зеркал через пробел. Зеркала используются, только
  когда github.com не отвечает; подпись делает безопасным любое зеркало. По умолчанию — два публичных прокси GitHub.
- `TMPDIR=/root/tmp` — если `/tmp` смонтирован с `noexec`: установщик запускает `rayctl` из временного каталога.

### 3.4. Проверить подпись самому (по желанию)

Этот шаг повторяет то, что установщик делает сам. Он нужен, если вы хотите убедиться своими глазами.

```bash
apt install -y minisign
```

```bash
mkdir -p /root/rc-release && cd /root/rc-release
```

```bash
curl -fsSLO https://github.com/arngory/raycontrol/releases/download/v0.26.0/SHA256SUMS
```

```bash
curl -fsSLO https://github.com/arngory/raycontrol/releases/download/v0.26.0/SHA256SUMS.minisig
```

```bash
curl -fsSLO https://github.com/arngory/raycontrol/releases/download/v0.26.0/raycontrol-linux-amd64.tar.gz
```

```bash
minisign -Vm SHA256SUMS -P RWQBergjLoDHqeme5vyIuIRXJLjTj1EF3jR1nlWBVJO3rWxgy9SZj4bD
```

Что вы должны увидеть:

```
Signature and comment signature verified
Trusted comment: raycontrol v0.26.0
```

```bash
sha256sum -c SHA256SUMS --ignore-missing
```

Что вы должны увидеть:

```
raycontrol-linux-amd64.tar.gz: OK
```

- **Что это значит.** Подпись покрывает `SHA256SUMS`, а он — архивы. Первая команда доказывает, что список сумм
  подписан нашим ключом и относится к v0.26.0, вторая — что архив тот самый.
- **Если minisign пишет про другой key id или `Signature verification failed`:** файлы не подписаны нашим ключом.
  Не ставьте их.
- **Если `sha256sum` пишет `FAILED`:** архив скачался с ошибкой или подменён. Скачайте снова.
- На arm64 замените в имени архива `amd64` на `arm64`.

Эти две команды с этим ключом выполнены над опубликованным релизом v0.25.1, когда писалась прежняя редакция
руководства: вывод был ровно таким, с `v0.25.1` в последней строке подписи. v0.26.0 при правке ещё не был
опубликован.

Эти файлы можно потом отдать ноде для обновления без доступа к GitHub: `rayctl update -from /root/rc-release` (§12).
Вернитесь в домашний каталог:

```bash
cd /root
```

## 4. Проверка хоста

Проверка ничего не ставит и ничего не меняет. Она отвечает, заработает ли нода на этом сервере.

```bash
bash bootstrap.sh -check -host 203.0.113.7 -domain example.com -services reality,dnstt,masterdns
```

В `-services` перечислите то, что собираетесь ставить (список видов — в §5): от этого зависит, проверять ли UDP 53.
Если задаёте свои порты (`-ports`, §5.2), добавьте и их: проверка скажет, свободны ли они.

Установщик скачивает и проверяет релиз во временный каталог, запускает его `rayctl check`, а потом убирает и каталог,
и системные пакеты, которые поставил ради проверки (nftables, polkit). Хост остаётся как был.

**Что вы должны увидеть.** Пример для годного сервера; числа и версии у вас свои:

```
bootstrap: release v0.26.0, signature verified
no raycontrol v0 (ray.sh) on this host
Required: without these the node does not work
  ok    root
  ok    systemd: systemd 257
  ok    D-Bus
  ok    commands
  ok    polkit
  ok    nftables: the perimeter table loads in kernel 6.12.48+deb13-amd64
  ok    systemd sandbox: namespaces, seccomp and the read-only system work in units
  ok    memory: 1967 MiB
  ok    disk: /usr/local 17211 MiB free, /var/lib 17211 MiB free
  ok    raycontrol v0: not installed
  ok    port tcp 443: free
  ok    port udp 443: free
  ok    port udp 53: free
Advised: the node works without them, worse
  ok    egress policy: the BitTorrent, SMTP and local networks filter loads (rayctl egress)
  ok    virtualization: kvm
  ok    system: debian 13
  ok    memory: 1967 MiB
  ok    processors: 2
  ok    disk: /usr/local 17211 MiB free, /var/lib 17211 MiB free
  ok    clock: synchronized
  ok    BBR
  ok    UDP buffers
  ok    unit IP firewall: IPAddressDeny= holds
  ok    resolver
  warn  IPv6: none
          → an IPv6 address reaches clients on networks without IPv4 more directly
  ok    public address: 203.0.113.7 is on an interface
  ok    Let's Encrypt: reachable
  ok    conntrack table: nf_conntrack is not loaded yet: rayctl apply loads it at boot (/etc/modules-load.d/raycontrol.conf) and sizes the table
Only a probe from outside shows the provider's firewall, UDP filtered on the way and blocks of the address: after the install, rayctl probe -channel from another machine.
This host can run a node (1 advised item not met).
bootstrap: check only: nothing installed
```

**Как читать.**

| Пометка | Уровень | Что значит |
|---|---|---|
| `ok` | любой | пункт выполнен |
| `FAIL` | `Required` | без этого нода не работает: установка откажет и ничего не поставит |
| `warn` | `Advised` | нода работает, но хуже; установка продолжится |

Под каждым непройденным пунктом строка со стрелкой `→` говорит, как его исправить. Строка
`This host can run a node` в конце значит, что можно ставить. Строка `conntrack table` до установки бывает разной:
`nf_conntrack is not loaded yet` или текущий размер таблицы — оба варианта нормальны.

**Обязательные пункты и что делать при `FAIL`:**

| Пункт | Что проверяется | Что делать |
|---|---|---|
| `root` | запуск от root | запустите от root |
| `systemd` | systemd запущен, версия 245 и новее | на Debian 13 выполняется всегда; в контейнере без systemd нода не ставится |
| `D-Bus` | системная шина | `apt install dbus` |
| `commands` | `nft`, `systemctl`, `systemd-run`, `useradd`, `runuser`, `sysctl` и другие | `nft` установщик ставит сам; остальное есть в базовой системе |
| `polkit` | через него `rayd` перезапускает сервисы | установщик ставит `polkitd` сам |
| `nftables` | таблица периметра загружается в ядро | нужно ядро 5.2 и новее с nftables; в контейнере модули должен дать хост |
| `systemd sandbox` | юнит с песочницей стартует | нужна VM; в LXC — `nesting=1` |
| `memory` | от 400 МиБ | VPS с большей памятью |
| `disk` | от 500 МиБ свободно в `/usr/local` и `/var/lib` | освободите место |
| `raycontrol v0` | нет прежней версии (`ray.sh`) | раздел «Прежний raycontrol» ниже |
| `port tcp 443`, `port udp 443` | порт свободен | остановите то, что его держит (§2.4) |
| `port udp 53` | только с DNS-туннелями: порт свободен | остановите bind9, dnsmasq или unbound (§2.4) |

**Желательные пункты:** не контейнер; проверенная система; память от 900 МиБ; от двух ядер; от 2 ГиБ на диске; часы
синхронизированы; BBR; буферы UDP; IP-фильтр юнитов; нет ожидающей перезагрузки и включены автообновления;
`/etc/resolv.conf` читается; публичный IPv6; с доменом — свободный TCP 80 и доступный Let's Encrypt; размер таблицы
соединений.

- `warn updates: … reboot` — перезагрузитесь (§2.2) и повторите проверку.
- `warn clock` — вернитесь к §2.3.
- `warn virtualization: container …` — нода заработает, но обновления ядра и размер таблицы соединений останутся у
  провайдера. Для людей, которые на ноду рассчитывают, берите VM.
- `public address: … is not on an interface: behind 1:1 NAT (cloud)` — это не ошибка: так устроены многие облака.

**Чего проверка не видит.** Файрвол провайдера, фильтрацию UDP по пути и блокировки адреса. Это покажет только проба
с другой машины после установки (§8).

После установки то же самое показывает `rayctl check` — например, после смены ядра.

### Прежний raycontrol (v0, `ray.sh`)

Если на сервере стоит прежняя версия — bash-установщик `ray.sh` («Ray-AIO») с Xray, Hysteria2 и PostgreSQL, —
проверка покажет `FAIL  raycontrol v0`. Рядом с ним нода не заработает: его Xray держит 443, а его таблица nftables
отбрасывает трафик ноды.

Отдельной команды «только убрать v0» у установщика нет: `-remove-v0` — это вся установка, перед которой
убирается v0. Поэтому здесь ничего не запускайте, а в §5:

1. сначала создайте файл токена (§5.1). Порядок важен: v0 удаляется раньше, чем установка читает токен, и с
   ошибкой в пути к файлу вы останетесь без v0 и без ноды;
2. возьмите **полную** команду из §5.2, со всеми вашими флагами и `-services`, и поставьте `-remove-v0` первым
   аргументом:

```bash
bash bootstrap.sh -remove-v0 -host 203.0.113.7 -domain example.com -name "Amsterdam" -cloudflare-token-file /root/cf.token -services reality,hy2-masq,naive,dnstt,api
```

Что при этом происходит:

- **Сначала проверка остального хоста.** Если нода не заработает и без v0, v0 остаётся как был.
- **Затем резервная копия** — `/root/raycontrol-v0-<время>.tar.gz`: настройки, секреты и дамп базы пользователей.
  Удалите её, когда она не нужна.
- **Потом удаляется только то, что ставил v0:** его службы, таблица nftables, база и роль PostgreSQL, сертификат
  certbot, `/etc/ray-aio`.
- **Чужое не трогается:** другие сертификаты, базы и файлы.
- С `-purge-v0-packages` вместо `-remove-v0` уходят ещё certbot, PostgreSQL и qrencode, если ими больше никто не
  пользуется.
- **И только после этого** идёт обычная установка из §5.3. Пользователи v0 в новую ноду не переносятся.

## 5. Установка

### 5.1. Токен Cloudflare — в файл

```bash
(umask 077; read -rsp 'Cloudflare token: ' T; printf '%s\n' "$T" > /root/cf.token); echo
```

Команда спросит токен без показа на экране. Вставьте значение из §1 и нажмите Enter.

- **Что это значит.** Токен лежит в файле, доступном только root, и не попал в историю оболочки. Скобки — подоболочка:
  umask 077 действует только на этот файл и не остаётся в вашей сессии.

### 5.2. Запуск

Выберите сервисы (таблица ниже) и запустите одну команду. Пример с основным набором:

```bash
bash bootstrap.sh -host 203.0.113.7 -domain example.com -name "Amsterdam" -cloudflare-token-file /root/cf.token -services reality,hy2-masq,naive,dnstt,api
```

**Флаги:**

| Флаг | Обязателен | Что задаёт |
|---|---|---|
| `-host 203.0.113.7` | да | публичный адрес ноды, по которому идут клиенты. Задавайте IP-адрес, не имя: на имя нода не может направить записи DNS |
| `-domain example.com` | для всех сервисов, кроме `api` | домен ноды (§1). Имена сервисов — случайные поддомены из трёх символов |
| `-name "Amsterdam"` | нет | имя ноды, которое клиенты показывают рядом с адресом; до 48 символов. Позже — `rayctl node name` |
| `-cloudflare-token-file /root/cf.token` | нет | файл с токеном: записи DNS и wildcard-сертификат через Cloudflare. Требует `-domain` |
| `-services a,b,c` | нет | какие сервисы поднять сразу. Без флага с доменом ставится только `reality`; `none` — ничего |
| `-admin 198.51.100.50` | нет | адреса, которым SSH открыт без SPA, через запятую; можно сети (`198.51.100.0/24`), не шире /16 для IPv4 и /48 для IPv6. По умолчанию — один адрес текущей SSH-сессии (первое поле `echo $SSH_CONNECTION`). Если ваш адрес меняется, задайте здесь сеть провайдера или рассчитывайте на `rayctl knock` (§0, §7) |
| `-ports spa=40000-40099,…` | нет | свои номера портов вместо случайных — только при первой установке (ниже, «Свои порты»). С v0.27.0 |

**Значения для `-services`** (через запятую, порядок не важен):

| Значение | Имя сервиса на ноде | Что это |
|---|---|---|
| `reality` | `reality` | REALITY на TCP 443 с собственным сайтом-приманкой |
| `hy2-masq` | `hy2-masq` | Hysteria2 с маскировкой под HTTP/3, UDP 443 |
| `hy2-obfs` | `hy2-obfs` | Hysteria2 в обфускации salamander, UDP 443 |
| `naive` | `naive` | NaiveProxy, TCP и UDP 443. Требует `reality` |
| `doh` | `doh` | DNS over HTTPS для клиентов. Требует `reality` |
| `yggdrasil` | `ygg` | Yggdrasil, TCP 443. Требует `reality` |
| `dnstt` | `dns` | DNS-туннель dnstt, UDP 53 |
| `masterdns` | `mdns` | DNS-туннель MasterDnsVPN, UDP 53 |
| `slipstream` | `slip` | DNS-туннель slipstream, UDP 53. Домен — не длиннее 16 символов (§8) |
| `api` | `api` | удалённый API: приглашения с QR, управление с телефона |

- **С чего начать.** `reality,hy2-masq,naive,dnstt,api` покрывает основной TCP-профиль, быстрый UDP, второй TCP,
  аварийный канал через DNS и приглашения по QR. Остальное добавляется потом одной командой (§8).
- **`api` нужен почти всегда:** без него устройство нельзя добавить по QR — только длинным пакетом устройства (§10).
- Всё сразу: `-services reality,hy2-masq,hy2-obfs,naive,doh,yggdrasil,dnstt,masterdns,slipstream,api`.

**Особые первые аргументы установщика.** Они должны стоять раньше остальных:

| Аргумент | Что делает |
|---|---|
| `-check` | только проверка хоста (§4) |
| `-remove-v0` | сначала убрать прежний raycontrol v0 (§4) |
| `-purge-v0-packages` | то же и удалить его системные пакеты |
| `-relay ФАЙЛ` | поставить не ноду, а relay перед ней (§12.4) |

#### Свои порты

С v0.27.0. Нужно, если перед сервером файрвол провайдера или NAT, который пропускает только заданные порты. 443 и
53 у ноды всегда одни и те же. Остальные порты нода без флага выбирает случайно, у каждой ноды свои. Флаг `-ports`
задаёт их заранее:

```bash
bash bootstrap.sh -host 203.0.113.7 -domain example.com -cloudflare-token-file /root/cf.token -services reality,hy2-masq,naive,api -ports spa=40000-40099,sub=40100,api=40101,rotation=41000-41399
```

| Имя | Протокол | Что это | Без флага |
|---|---|---|---|
| `spa=A-B` | TCP и UDP | порты стука (SPA). Порт, на который стучится клиент, меняется каждые 5–30 минут внутри диапазона. Можно один порт: `spa=40000`, но такой порт проще заблокировать | случайный диапазон из 1024–4096 портов в 20000–60999 |
| `sub=N` | TCP и UDP | подписка | случайный |
| `api=N` | TCP | удалённый API. Порт берётся, когда создаётся сервис `api`: при установке или позже | случайный |
| `rotation=A-B` | UDP | ротация портов сервисов на UDP 443 (Hysteria2, naive по QUIC, DoH3). Каждому такому сервису достаётся четверть диапазона: хватает на четыре | случайный диапазон из 1024–4096 портов у каждого сервиса |
| `rotation=off` | — | без ротации: такие сервисы слушают только UDP 443 | |

- Номера — от 1024. Диапазоны не пересекаются между собой и с портом sshd. Что не названо — случайное, как без флага.
- Проверка хоста (§4) получает те же `-ports` и требует, чтобы порты были свободны. Занятый порт — строка `FAIL`,
  например `port tcp+udp 40000-40099: spa (-ports): udp 0.0.0.0:40050 is taken by unbound (pid 401)`.
- **Только при первой установке.** Клиенты узнают эти порты, когда подключают устройство: из пакета устройства и
  приглашения. Если бы порт стука, подписки или API сменился, каждое подключённое устройство потеряло бы ноду. Поэтому
  повторная установка принимает только те же порты или установку без `-ports`, а с другими отказывает до любых
  изменений: `ports are chosen at a node's first install only, and clients know this node's (…)`. Перенести эти
  порты на работающей ноде нельзя.

Что открыть у провайдера для примера выше:

| Протокол | Порты | Зачем |
|---|---|---|
| TCP | порт sshd (22) | SSH |
| TCP и UDP | 443 | сервисы |
| TCP и UDP | 40000–40099 | стук |
| TCP и UDP | 40100 | подписка |
| TCP | 40101 | API |
| UDP | 41000–41399 | ротация UDP: первые две четверти заняли `hy2-masq` и `naive`, две свободны для сервисов, добавленных позже |
| UDP | 53 | только с DNS-туннелями |
| TCP | 80 | только без Cloudflare, на время выпуска сертификата |

После установки все порты ноды показывает `rayctl ports` (§6.1).

### 5.3. Что происходит и что вы увидите

1. **Зависимости.** Установщик ставит недостающее из curl, openssl, nftables и polkitd и печатает
   `bootstrap: installing …`.
2. **Релиз.** Скачивание и проверка подписи (§3.3): `bootstrap: release v0.26.0, signature verified`.
3. **Проверка хоста** — тот же вывод, что в §4. При `FAIL` установка останавливается, системные пакеты из шага 1
   удаляются, из raycontrol не ставится ничего.
4. **Бинарники.** `rayd`, `rayspa` и `rayctl` кладутся в `/usr/local/bin`, data plane — в
   `/usr/local/libexec/raycontrol`: строки `installed /usr/local/libexec/raycontrol/xray` и такие же для
   `niko-server` и `slipstream-server`. Xray или sing-box, которые уже стояли на сервере для другого софта, не
   трогаются.
5. **Cloudflare.** Токен проверяется и сохраняется в базе ноды; создаются записи:

   ```
   Cloudflare zone example.com: records kept by rayd, certificates through DNS-01.
     created A *.example.com
   ```

   С DNS-туннелями записей больше: имя NS-сервера и по одной NS-записи на зону.
6. **Службы.** Строки `wrote /etc/systemd/system/…` — юниты и системные файлы.
7. **Файрвол провайдера** — строка со списком портов, см. §6.1.
8. **Итог:**

   ```
   Services: reality, hy2-masq, naive, dns, api. REALITY starts once its certificate is stored (journalctl -u rayd -f).

   raycontrol is installed. The perimeter is up: every port is closed except
   SPA, public services and SSH (tcp/22) from 198.51.100.50.
   More admin addresses or networks (IPv4 /16 or IPv6 /48 at the widest): rayctl admin with all of them, the list is replaced whole.

   Emergency device (SSH only). Store it offline, it is shown once:

   rcdev1:…

   Recovery from the provider console: rayspa teardown
   ```

**Сохраните аварийный пакет устройства** — длинную строку `rcdev1:…`. Скопируйте её в файл на своём компьютере, например
`emergency.bundle`, и держите вне сервера. Это запасной вход: по нему можно попасть на сервер по SSH с адреса,
которого нет в списке администратора (§7). Второй раз он не покажется.

**Проверьте строку `SSH (tcp/22) from 198.51.100.50`.** В ней два значения, и оба надо сверить, не закрывая
сессию.

- **Адрес** — тот, каким вас видит сервер. Если вы зашли через VPN или промежуточный сервер, там адрес выхода VPN
  или этого сервера: SSH будет открыт ему, а не вашему дому, и без VPN вы не зайдёте. Впишите адреса, с которых
  действительно будете заходить:

  ```bash
  rayctl admin 198.51.100.50
  ```

- **Адрес один и точный.** Если он у вас меняется, после смены сервер вас не пустит. Либо впишите сеть провайдера
  (`rayctl admin 198.51.100.0/24`), либо убедитесь сейчас, что работает вход аварийным пакетом устройства (§7).
- **Второе рабочее место** — в тот же список: `rayctl admin 198.51.100.50 192.0.2.77`. Список заменяется целиком,
  прежние адреса пишите тоже. Как дописать адрес, войдя с него стуком, — §7.
- **Порт** — тот, на котором sshd слушал в момент установки. Менять порт sshd после этого — только по §7.

Уже открытая SSH-сессия не оборвётся в любом случае: периметр закрывает только новые соединения. Пока вы не
открыли вторую сессию и не убедились, что она проходит, первую не закрывайте.

### 5.4. Удалить файл токена

```bash
shred -u /root/cf.token
```

Токен теперь хранится в базе ноды, файл больше не нужен.

### 5.5. Если установка остановилась

| Что вы видите | Причина | Что делать |
|---|---|---|
| `bootstrap: run as root` | запуск не от root | `sudo -i`, затем повторить |
| `bootstrap: systemd is required` | система без systemd | нода не ставится в такой контейнер |
| `bootstrap: unsupported architecture …` | не amd64 и не arm64 | другой VPS |
| `bootstrap: this host cannot run a node (see above); it was left as it was` | в проверке хоста есть `FAIL` | исправьте пункт (§4) и запустите снова |
| `bootstrap: the arguments are not right (see above)` | опечатка во флагах | сверьте с таблицей в §5.2 |
| `bootstrap: cannot run programs from … (mounted noexec?)` | `/tmp` с `noexec` | `mkdir /root/tmp`, затем `TMPDIR=/root/tmp bash bootstrap.sh …` |
| `rayctl: no admin address: pass -admin, or install from an SSH session (not from tmux or screen)` | запуск из tmux, screen или с консоли | добавьте `-admin 198.51.100.50` со своим адресом |
| `rayctl: -services naive needs -domain` (или другой сервис) | нет `-domain` | добавьте домен |
| `rayctl: -cloudflare-token-file needs -domain, the zone's domain` | токен без домена | добавьте `-domain` |
| `warning: Cloudflare not set up (rayctl dns cloudflare later): … cloudflare: HTTP 401: 1000 Invalid API Token …` | вставлен ID токена, а не значение, или токен отозван | установка при этом **продолжается**. Создайте токен заново (§1) и выполните `rayctl dns cloudflare` |
| `warning: Cloudflare not set up …: … cloudflare: no zone for … that this token can see` | токену не дана эта зона или нет права Zone · Read | исправьте токен, затем `rayctl dns cloudflare` |
| `warning: service … not created (rayctl service add … later): …` | сервис не создался; причина в конце строки | исправьте причину и добавьте сервис командой из строки (§8) |
| `rayctl: another … is running (…)` | идёт другая установка, apply или обновление | дождитесь её конца |

Установку можно запускать повторно: она не создаёт заново то, что уже есть, и аварийный пакет устройства второй
раз не печатает. Но **список адресов администратора повторная установка заменяет** адресом текущей SSH-сессии
(или тем, что задано в `-admin`): адреса и сети, которые вы вписали через `rayctl admin`, пропадут. После
повторной установки проверьте `rayctl admin`.

## 6. Сразу после установки

### 6.1. Файрвол провайдера

В выводе установки (и после каждого `rayctl apply`) есть строка:

```
a firewall of the provider in front of the host (security group, cloud firewall) must let in: tcp 22, udp 53, tcp+udp 443, tcp 23295, tcp+udp 26651-28756, tcp+udp 55671
```

- **Что это значит.** Это порты вашей ноды: SSH, 53 для DNS-туннелей, 443, порт API, диапазон SPA и порт подписки.
  Диапазон и одиночные порты у каждой ноды свои: случайные или заданные при установке (`-ports`, §5.2). TCP 80
  появляется в списке только без Cloudflare.
- **Если у провайдера есть файрвол** — откройте в нём эти порты для входящих соединений с любых адресов. Если
  файрвола нет — ничего делать не нужно.
- **Ротация UDP.** Сервисы на UDP 443 (Hysteria2, naive по QUIC, DoH3) доступны ещё и на портах, которые
  меняются по расписанию, — у каждого такого сервиса свой диапазон. С v0.27.0 строка включает и эти диапазоны;
  до v0.27.0 их в ней не было, хотя открыть их у провайдера тоже надо.
- **Все порты по одному, с назначением** (с v0.27.0):

  ```bash
  rayctl ports
  ```

  ```
  PROTO    PORTS        NAME               SET     REACHED BY                                        NOW
  tcp+udp  40000-40099  spa                chosen  everyone                                          40042 until 14:05 UTC
  tcp+udp  40100        sub                chosen  after the knock                                   -
  tcp      22           ssh                sshd    admin addresses; after the knock for SSH devices  -
  tcp      443          reality            fixed   after the knock                                   -
  udp      443          hy2-masq           fixed   after the knock                                   -
  udp      41000-41099  hy2-masq rotation  chosen  after the knock                                   41007 until 14:05 UTC
  tcp+udp  443          naive              fixed   after the knock                                   -
  udp      41100-41199  naive rotation     chosen  after the knock                                   41163 until 14:05 UTC
  tcp      40101        api                chosen  after the knock                                   -
  ```

  `SET`: `fixed` — постоянный номер (443, 53, 80), `random` — выбран нодой, `chosen` — задан при установке
  (`-ports`, §5.2), `sshd` — порт sshd. `NOW` у диапазонов, которые меняются по расписанию, — порт текущего слота
  и время смены (соседние слоты тоже открыты). Без Cloudflare есть ещё строка `acme` — TCP 80 на время выпуска
  сертификата; с DNS-туннелями — UDP 53 для всех. `rayctl -json ports` — то же в JSON; со своей машины —
  `rayctl -remote ФАЙЛ ports`. Работает от root и от группы `raycontrol`, как `rayctl service list`.
- **Самый простой вариант** — открыть у провайдера весь входящий TCP и UDP. Периметр ноды сам закрывает всё, кроме
  SPA и открытого по SPA. Но тогда он — единственная защита сервера, и у него есть окна:
  - **при загрузке** — таблицы нет, пока не стартует `rayspa`, а он стартует после сети. Эти секунды сервер
    открыт так же, как до установки;
  - **после `rayspa teardown` и после `rayctl uninstall`** сервер открыт целиком;
  - **порты, опубликованные Docker,** и любая другая пересылка идут мимо входной цепочки периметра: он их не
    закрывает. Не публикуйте на ноде контейнеры наружу.

  Поэтому вход по SSH только по ключам обязателен (§2.6), а всё, что слушает на сервере помимо ноды, должно
  быть готово к тому, что его увидят.

Повторно увидеть строку можно в любой момент — команда ничего не меняет, если менять нечего:

```bash
rayctl apply
```

```
active devices       1
spa ports            [27441 28500 27844]
egress               blocked: local networks (rayctl egress)
acme site            ok 2m10s ago
apply                ok 40s ago
conn-limit           ok 8s ago: on; nobody at a limit in 15 min
credential-rotation  ok 2m30s ago
dns                  ok 2m5s ago
dns-zone dns         ok 1m50s ago: …
…
```

**Как читать.**

- Верхняя часть — версия, ID и адрес ноды, счётчики. Один пользователь и одно устройство — это аварийный доступ,
  который создала установка. В счёт сервисов входят и служебные: подписка, SSH, сайт-приманка, `inner`.
- Ниже — по строке на каждый фоновый цикл `rayd`. `ok 40s ago` — последний круг удался. `FAILED 3m ago: <ошибка>
  (last ok …)` — не удался; текст ошибки говорит, что именно.

| Строка | Что это |
|---|---|
| `apply` | конфиги сервисов отрисованы и применены |
| `acme site` | сертификат сайта и сервисов под ним |
| `dns` | записи в Cloudflare такие, как нужно |
| `dns-zone <сервис>` | самопроверка зоны DNS-туннеля (§8) |
| `dns-front`, `dnstt <сервис>` | счётчики DNS-туннелей за час |
| `port53` | UDP 53 рядом с нодой никто не занял |
| `resolver` | `/etc/resolv.conf` читается службами |
| `reality-target <сервис>` | чужая цель REALITY жива (только если вы её задали) |
| `traffic`, `traffic <сервис>` | счёт трафика пользователей |
| `conn-limit`, `conntrack` | пределы соединений и таблица соединений |
| `credential-rotation`, `reality-rotation`, `prune` | плановые смены ключей и чистка |
| `update`, `auto-update` | проверка и установка обновлений, если включены (§9) |

**Если `rayctl: … connect: no such file or directory` или `connection refused`:** `rayd` не запущен. Смотрите
`journalctl -u rayd -n 50`.

### 6.3. Записи DNS

```bash
rayctl dns
```

Что вы должны увидеть (пример с одним DNS-туннелем):

```
provider  cloudflare, zone example.com

TYPE  NAME             CONTENT
A     *.example.com    203.0.113.7
A     ji9.example.com  203.0.113.7
NS    vi3.example.com  ji9.example.com
```

- **Что это значит.** Провайдер подключён, нужные записи перечислены. Строк `problem:` нет — зона в порядке.
- **Если `provider  none: records by hand …`:** Cloudflare не подключён. Либо заведите перечисленные записи у своего
  DNS-провайдера, либо подключите Cloudflare: `rayctl dns cloudflare` (токен спросит без показа на экране).
- **Если есть `problem: …`:** под нужным именем есть чужая запись или у неё включено проксирование. Исправьте её в
  панели Cloudflare, затем `rayctl dns sync`.

### 6.4. Сертификат и REALITY

С Cloudflare сертификат `*.example.com` выпускается через DNS-01 обычно за минуту-две. Проверьте журнал:

```bash
journalctl -u rayd | grep 'certificate stored'
```

Команда должна напечатать строку с `certificate stored`. Пусто — сертификата ещё нет: повторите через минуту.
(`journalctl -u rayd -f` для этого не годится: он показывает только последние десять строк и то, что придёт
позже; уже прошедшую строку вы в нём не увидите.) После этой строки `rayd` отрисует сайт и сервисы под ним, и они
запустятся:

```bash
systemctl is-active niko-site niko-reality niko-front
```

Что вы должны увидеть:

```
active
active
active
```

- **Что это значит.** Сайт-приманка, REALITY и фронт (он держит порты 443 и 53 и раздаёт соединения сервисам)
  работают. До сертификата юниты сайта, REALITY, naive и Yggdrasil не стартуют: systemd пропускает их, пока нет
  файла, — это не ошибка.
- **Если строки `certificate stored` нет и через несколько минут,** а в `rayctl status` — `acme site FAILED …`: см. §13,
  «Сертификат не выпускается».

**Каким корням верит сама нода.** Когда нода идёт к Let's Encrypt, GitHub, Cloudflare, IPinfo или к вышестоящим DoH,
она проверяет их сертификаты по встроенному списку корней, а не по хранилищу системы. Это тот же список, что у
клиента: пересечение списков Chrome и Mozilla без центров из Китая, 91 корень на 2026-11-14. Хранилищу образа
нода по умолчанию не верит: корень, который туда положили провайдер, сборщик образа или взломщик, её соединения не
откроет, а пустое или устаревшее хранилище ей не мешает. Посмотреть:

```bash
rayctl roots
```

Строка `tls-roots` в `rayctl status` показывает то же коротко и сколько соединений список отклонил с запуска `rayd`
(с именем хоста и причиной). Добавить корни может только root, и нода подхватывает их со следующего соединения,
без перезапуска:

- `rayctl roots file ROOT.pem` — свой корень: прокси, который вскрывает TLS (корпоративная сеть), или частный
  ACME-УЦ, если `rayd serve -acme-directory` указывает не на Let's Encrypt. Файл копируется в
  `/etc/raycontrol/tls-roots.pem`; `rayctl roots file none` убирает его.
- `rayctl roots system on` — добавить хранилище системы целиком; `off` — убрать.

Загрузка обновления — единственное исключение: если встроенный список отклонил GitHub или зеркало, `rayctl update`
предупреждает и повторяет загрузку с хранилищем системы. Файлы релиза защищает подпись, а старый релиз `update` не
ставит, так что устаревший список не запирает ноду, и следующий релиз приносит новый. У ACME, Cloudflare, IPinfo
и DoH такого пути нет.

### 6.5. Все службы на месте

```bash
systemctl --no-pager list-units --all 'niko-*' rayd.service rayspa.service
```

У каждой службы в столбце `ACTIVE` должно быть `active`, в столбце `SUB` — `running`. Флаг `--all` нужен: без него
команда не показывает службы, которые не запустились, — как раз те, что вы ищете. `inactive dead` у сайта,
REALITY, naive или Yggdrasil значит, что сертификата ещё нет (§6.4).

Имена юнитов: `rayd.service`, `rayspa.service`, `niko-front.service` и `niko-<имя сервиса>.service` — например
`niko-reality`, `niko-hy2-masq`, `niko-naive`, `niko-dns`, `niko-inner`. У `doh` и `api` своих юнитов нет: их
обслуживает сам `rayd`.

### 6.6. Работать с нодой не от root

Член группы `raycontrol` может запускать `rayctl` без root:

```bash
usermod -aG raycontrol ИМЯ
```

**Это почти полный администратор ноды, а не «только смотреть».** Группе доступно всё, кроме короткого списка
ниже. В частности, член группы может:

- заменить адреса администратора (`rayctl admin`) — то есть открыть SSH своему адресу и закрыть вашему;
- добавить, перенастроить и убрать relay (`relay add`, `relay set`, `relay remove`);
- добавлять, выключать и удалять сервисы, в том числе служебные (§8);
- удалить записи ноды из DNS и отвязать Cloudflare (`dns remove`);
- выгрузить ссылки любого пользователя с его учётными данными (`user export`);
- выдать приглашение с ролью `admin` и получить управление нодой с другого устройства.

Добавляйте в группу только тех, кому доверяете ноду целиком. То же относится к admin-устройствам (§10.3).

Только root: `install`, `apply`, `update` (и `update remote|auto`), `uninstall`, `backup`, `restore`,
`debug on|off`, `egress block|allow`, `conn-limit on|off`, `relay bundle`, `service cert`, `service rotate САЙТ`,
`summary db`. `service cert` — только root с v0.26.0; раньше её могли и члены группы.

## 7. Порты и доступ к серверу

Периметр — таблица nftables `inet raycontrol`. По умолчанию всё входящее отбрасывается молча.

| Что | Кому открыто |
|---|---|
| UDP 53 (с DNS-туннелями) | всем: DNS-резолверы не умеют SPA |
| порты SPA (диапазон свой у каждой ноды, UDP и TCP) | всем, но SPA-пакет без верного ключа молча отбрасывается, ответа нет |
| TCP 80 | только на время выпуска сертификата и только без Cloudflare |
| TCP и UDP 443, порт подписки, порт API | адресу, который прислал верный SPA, на время доступа: по умолчанию 10 минут, клиент повторяет SPA сам |
| SSH | адресам администратора — всегда; любому адресу — после SPA устройства, у пользователя которого есть сервис `ssh` |
| всё остальное | никому |

- Открытое соединение, в том числе сессия SSH, живёт и после конца окна SPA: закрывается только возможность открыть
  новое.
- На ping снаружи нода не отвечает.

### Как попасть на сервер по SSH

**1. С адреса администратора.** Список задан при установке. Показать:

```bash
rayctl admin
```

Заменить — список заменяется целиком, поэтому впишите и прежние адреса:

```bash
rayctl admin 198.51.100.50 198.51.100.0/24
```

- Адрес в списке должен совпасть с тем, каким вас видит сервер: `echo $SSH_CONNECTION` в текущей сессии, первое
  поле.
- Сеть — не шире /16 для IPv4 и /48 для IPv6: более широкую команда не примет.
- **Если ваш адрес меняется,** одного адреса в списке мало: после смены сервер вас не пустит. Впишите сеть
  провайдера или пользуйтесь способом 2.
- **Адресов и сетей в списке может быть несколько,** IPv4 и IPv6 вперемешку: два рабочих места, дом и сеть
  провайдера телефона. При установке — через запятую, `-admin 198.51.100.50,203.0.113.0/24,2001:db8:42::/48`;
  потом — через пробел, как выше.
- Заменив список, откройте вторую SSH-сессию, не закрывая первую, и убедитесь, что она проходит.

**Новый адрес, когда вы уже вошли стуком** (способ 2 ниже): допишите его к списку из той же сессии, и
следующий раз стук не понадобится. Сначала узнайте, каким сервер видит вас сейчас (первое поле), и прежний
список:

```bash
echo $SSH_CONNECTION
rayctl admin
```

Затем впишите новый адрес вместе с прежними — список заменяется целиком:

```bash
rayctl admin 192.0.2.77 198.51.100.50 203.0.113.0/24
```

Под `sudo -i` переменной `SSH_CONNECTION` нет: посмотрите её до `sudo`.

**2. С любого адреса — аварийным пакетом устройства.** Нужна машина с Linux (amd64 или arm64) и `rayctl` на ней — тот же
бинарник из архива релиза, он статический и работает без установки. Для macOS и FreeBSD есть отдельные архивы с
одним `rayctl` (ниже, «`rayctl` на своей машине»); сборки для Windows нет: там
подойдёт любая виртуальная машина с Linux. Достать бинарник для Linux: скачайте и проверьте архив, как в §3.4, затем

```bash
tar -xzf raycontrol-linux-amd64.tar.gz rayctl
```

Дальше он запускается как `./rayctl`. Файл `emergency.bundle` — аварийный пакет устройства, сохранённый при
установке:

```bash
./rayctl knock @emergency.bundle
```

Что вы должны увидеть:

```
open: 203.0.113.7 lets this address reach device …'s services for the node's default time (10 min unless set otherwise); for SSH, connect now (ssh root@203.0.113.7)
```

```bash
ssh root@203.0.113.7
```

- `knock` шлёт только SPA-пакет и проверяет, что окно открылось. Подключиться по SSH нужно в течение 10 минут.
- Если `the node did not open`: проверьте часы на своём компьютере и диапазон SPA в файрволе провайдера; в сети, где
  режется UDP, попробуйте `./rayctl knock -carrier tls @emergency.bundle`.
- Потеряли пакет устройства, но доступ ещё есть — сделайте новый:
  `rayctl device add emergency spare -o /root/spare.bundle`. Заберите файл с сервера и сразу удалите его там:
  `shred -u /root/spare.bundle`. Потерянный пакет отзовите: `rayctl device list emergency`, затем
  `rayctl device revoke ID`.
- Проверьте этот вход заранее, а не в день, когда он понадобится.

**3. С консоли провайдера (VNC),** если не работает ни то, ни другое:

- пустить свой адрес к SSH: `rayctl admin <ваш адрес> <прежние адреса>`;
- или снять периметр целиком:

  ```bash
  systemctl stop rayspa && rayspa teardown
  ```

  Сервер открыт, пока вы не выполните `systemctl start rayspa` или не перезагрузитесь. Пока `rayspa` работает,
  `teardown` откажет: служба возвращает таблицу за секунды.

### `rayctl` на своей машине: Linux, macOS, FreeBSD

`rayctl` нужен не только на ноде. На своей машине им открывают SSH аварийным пакетом (`knock`, выше), проверяют
ноду снаружи (`probe`, §8) и управляют ею через удалённый API (`-remote`, §10.4).

- **Linux (amd64, arm64):** `rayctl` из архива ноды, как показано выше.
- **macOS и FreeBSD — с v0.26.0.** Архивы: `rayctl-darwin-arm64.tar.gz` (Mac на Apple silicon), `rayctl-darwin-amd64.tar.gz` (Mac на Intel),
  `rayctl-freebsd-amd64.tar.gz`. Внутри только `rayctl` и файл `VERSIONS` — без `rayd`, Xray и остального: нода
  остаётся на Linux.
- **Windows:** сборки нет. Подойдёт виртуальная машина с Linux.

> **Статус.** Сборки для macOS и FreeBSD делаются с Linux кросс-компиляцией. На macOS `rayctl` запускался только в
> CI (job `rayctl (macOS, run)`: справочный, на runner с macOS arm64 зелёный); на настоящем Mac руками — нет. На
> FreeBSD он **не запускался нигде**. Команды этого раздела для macOS и FreeBSD написаны по общим сведениям об этих
> системах, без проверки.

**Скачать и проверить.** Подпись та же, что у архивов ноды: один `SHA256SUMS` на весь релиз, подписанный тем же
ключом (§3.2). На Mac с Apple silicon, где `vX.Y.Z` — номер релиза, v0.26.0 или новее:

```bash
curl -fsSLO https://github.com/arngory/raycontrol/releases/download/vX.Y.Z/SHA256SUMS
```

```bash
curl -fsSLO https://github.com/arngory/raycontrol/releases/download/vX.Y.Z/SHA256SUMS.minisig
```

```bash
curl -fsSLO https://github.com/arngory/raycontrol/releases/download/vX.Y.Z/rayctl-darwin-arm64.tar.gz
```

```bash
minisign -Vm SHA256SUMS -P RWQBergjLoDHqeme5vyIuIRXJLjTj1EF3jR1nlWBVJO3rWxgy9SZj4bD
```

Что вы должны увидеть:

```
Signature and comment signature verified
Trusted comment: raycontrol vX.Y.Z
```

```bash
shasum -a 256 --ignore-missing -c SHA256SUMS
```

Что вы должны увидеть:

```
rayctl-darwin-arm64.tar.gz: OK
```

```bash
tar -xzf rayctl-darwin-arm64.tar.gz rayctl
```

- **Что это значит.** То же, что в §3.4: подпись покрывает `SHA256SUMS`, а он — все архивы релиза, и для ноды, и
  с `rayctl`. `--ignore-missing` пропускает архивы, которых вы не скачивали.
- **minisign** на macOS ставится через Homebrew (`brew install minisign`), на FreeBSD — `pkg install minisign`.
- **На FreeBSD** архив — `rayctl-freebsd-amd64.tar.gz`, а суммы проверяет `sha256sum -c SHA256SUMS --ignore-missing`,
  как на Linux.
- Если minisign или проверка суммы отвечают иначе — не запускайте файл (§3.4).

**Особенности macOS.** Бинарник не подписан сертификатом разработчика Apple и не нотаризован. Файл, скачанный
браузером, macOS помечает карантином и запускать откажется. Снять метку:

```bash
xattr -d com.apple.quarantine rayctl
```

Файл, скачанный `curl`, как выше, такой метки не получает. Это общие сведения о macOS, здесь они не проверялись.
Проверку подписи minisign метка не заменяет: делайте её в любом случае.

**Что работает вне ноды:**

- `knock` и `probe` — им нужен только пакет устройства;
- `version` — версия `rayctl`; с `-remote ФАЙЛ` — и версия ноды;
- `remote enroll` — регистрация по приглашению (§10.4), PIN спрашивается без показа на экране;
- с файлом устройства, `-remote ФАЙЛ`: `remote whoami`, `remote rotate` и то же, что через `-remote` на Linux, —
  `status`, `node`, `user`, `service`, `device` (в том числе приглашение с QR в терминале), `audit`, `admin`, `dns`,
  `summary`, `app-mirror`, `metrics`, `debug`, `version`. Что из этого нода разрешает удалённому устройству, решает она сама
  (§10.4): так, окно отладки открывает и закрывает только root на ноде, через `-remote` работает лишь `debug show`.
- `knock` и `probe` с `-remote` не запускаются, а отвечают одной строкой, например
  `knock takes no -remote: it works from this machine with the bundle on its command line (run it without -remote)`.
  `remote enroll` флаг `-remote` пропускает: файл устройства он пишет сам (`-o`).
  Неизвестная команда с `-remote` — ошибка использования: файл устройства не читается, в ноду никто не стучит.

**Что не работает:** всё, что действует на самом сервере, — `install`, `apply`, `update`, `uninstall`, `backup`,
`restore`, `report`, `check`, `legacy`, `egress`, `conn-limit`, `service cert`, `relay bundle`, `summary db`. Такая
команда ничего не делает и отвечает одной строкой с кодом выхода 1:

```
rayctl: install works on a Linux node only, and this is darwin: run it on the node (here: -remote FILE, remote enroll, knock, probe)
```

Команда управления без `-remote` тоже отвечает одной строкой: ноды на этой машине нет.

```
rayctl: status asks a node, and there is none on darwin: rayctl -remote FILE status (rayctl remote enroll writes the device file)
```

**Где лежат ключи.** Пакет устройства и файл устройства (`.rcdev`) на ноутбуке — это доступ к ноде, а файл
admin-устройства — удалённый доступ администратора. Не держите их в папках, которые синхронизируются с облаком
(iCloud Drive, Dropbox и подобные). Файл устройства должен принадлежать вам и иметь права 0600: иначе `-remote` его
не прочитает. Чужой файл может взять только root (§10.4).

### Сменить порт sshd на установленной ноде

Установка прочитала порт sshd один раз. Просто перенести sshd на другой порт нельзя: периметр о новом порте не
знает и закроет его для всех. Сам за sshd нода не следит. Что порты разошлись, говорят `rayctl check` и
`rayctl status` от root на ноде: они сравнивают порты из `sshd -T` с портами сервисов `ssh`. Разошлись — в
`rayctl check` строка

```
  warn  ssh port: sshd is configured for 2222, which the perimeter does not admit (it admits SSH on 22 (ssh)): once sshd runs as configured, SSH from the admin addresses and after a knock is closed to everyone
```

а под ней команды шага 1; в `rayctl status` — строка `ssh port` с тем же текстом после `WARNING`. Нет OpenSSH
(sshd нет совсем или это другой сервер, например Dropbear) — сравнивать нечего: `status` молчит, `check` пишет одну
строку об этом. sshd запускает сокет (`ssh.socket` включён) — SSH принимается на портах его `ListenStream`, а не
там, где говорит `sshd -T`; эти порты проверка не читает и так и пишет (`systemctl cat ssh.socket`). Порядок ниже следует из кода — периметр открывает адресам администратора порты
всех сервисов вида `ssh`, — но целиком на сервере он не проверялся. Держите текущую сессию открытой до конца и
убедитесь заранее, что у вас есть консоль провайдера.

1. Завести второй сервис SSH с новым портом и дать его аварийному пользователю (список сервисов заменяется
   целиком):

   ```bash
   rayctl service add ssh ssh2 -settings '{"ports":["tcp/2222"]}'
   ```

   ```bash
   rayctl user services emergency ssh,ssh2
   ```

   ```bash
   rayctl apply
   ```

   В строке про файрвол провайдера (§6.1) появится `tcp 2222`: откройте его у провайдера.
2. Добавить порт в sshd, **не убирая старый**: в `/etc/ssh/sshd_config` две строки, `Port 22` и `Port 2222`.
   Перезапустить sshd: `systemctl restart ssh`.
3. Не закрывая текущую сессию, открыть новую: `ssh -p 2222 root@203.0.113.7`. Проходит — новый порт работает.
4. Только теперь убрать `Port 22` из `sshd_config` и перезапустить sshd. Сервис `ssh` со старым портом можно
   оставить: за его портом никто не слушает.

Если на шаге 3 новая сессия не проходит, ничего не убирайте: старый порт по-прежнему работает.

## 8. Сервисы

### Общие правила

- **Добавить сервис** — две команды. Первая создаёт сервис в базе, вторая (только root) ставит ему юнит, системного
  пользователя и порты:

  ```bash
  rayctl service add ВИД ИМЯ
  ```

  ```bash
  rayctl apply
  ```

  `rayctl apply` запускайте после каждого `service add`, `service del`, `service enable` и `service disable`. Он
  ничего не ломает и не перезапускает то, что не менялось.
- **Имя** — до 27 символов из `a-z`, `0-9` и `-`. Ниже используются те же имена, что даёт установка. Имя `front` и
  имена, которые кончаются на `-in` или `-api`, заняты: нода их не примет.
- **Выключить** сервис, не удаляя его ключей: `rayctl service disable ИМЯ`, затем `rayctl apply`. Профиль пропадёт из
  подписок. **Включить** обратно: `rayctl service enable ИМЯ` и `rayctl apply`.
- **Удалить:** `rayctl service del ИМЯ`, затем `rayctl apply`. Сервис, через который работают другие, не удаляется,
  пока те включены: например, `site` — пока есть `naive`.
- **`service disable` и `service del` ничего не спрашивают и выполняются сразу** — и для служебных сервисов тоже.
  Защиты от опечатки в имени нет. Исключение одно: последний включённый сервис вида `ssh` (после v0.26.0). Его
  `rayctl service disable ssh` и `rayctl service del ssh` не трогают и отвечают

  ```
  rayctl: failed_precondition: not now: rayctl service disable ssh -force does it anyway (rayctl before v0.27.0 has no -force): the last enabled ssh service; without it SSH is closed to everyone at the next snapshot, open sessions go on
  ```

  Строка начинается с команды с `-force`, которая сделает это всё равно. То же отвечает нода и на запрос через API, с
  телефона или `-remote`. У `rayctl` старше v0.27.0 флага `-force` нет: обновите его или возьмите `rayctl` на
  самой ноде. Не трогайте служебные сервисы:

  | Команда | Что она сломает |
  |---|---|
  | `rayctl service disable ssh -force` или `service del ssh -force` | SSH закрывается для всех: и для адресов администратора, и для аварийного пакета устройства. Уже открытая сессия живёт: сразу верните `rayctl service enable ssh`. Если сессии нет — только с консоли провайдера. Без `-force` нода откажет, пока включённый сервис `ssh` — последний |
  | `rayctl service del subscription` | подписка пропадает у всех устройств. Вернуть её можно только повторной установкой, и у новой будут другой порт и другой сертификат, а прежние закреплены в пакете каждого устройства: все устройства придётся добавлять заново |
  | `rayctl service del api` | новый `api` получит другой порт и сертификат: admin-устройства и relay перестанут работать, пока их не зарегистрировать заново |
  | `rayctl service del site`, `service del inner` | удаляются вместе со своими ключами и сертификатом сайта. Нода откажет, только пока включены сервисы, которые через них работают |
- **Сервис доступен пользователю, только если он есть в его списке** (§10). Новый сервис существующим
  пользователям сам не добавляется: `rayctl user services ИМЯ a,b,c`.
- **Список сервисов:**

  ```bash
  rayctl service list
  ```

  ```
  ID  NAME          KIND          ENABLED  KEYS
  1   subscription  subscription  true
  2   ssh           ssh           true
  3   site          site          true     key since 2026-11-14 13:58, next key pinned since 2026-11-14 13:58
  4   reality       reality       true     since creation
  5   hy2-masq      hy2-masq      true
  7   naive         naive         true
  9   inner         inner         true
  11  dns           dnstt         true     auth required, v2 optional, seal optional
  14  api           api           true

  kinds: reality hy2-masq hy2-obfs naive doh yggdrasil dnstt masterdns slipstream olcrtc openflux inner site subscription api ssh
  ```

  `subscription`, `ssh`, `site` и `inner` — служебные, нода заводит их сама; `api` вы добавили сами, но для
  устройств он такой же несущий. В `KEYS` у `site` — ключ его сертификата (ниже, «Сертификат сайта и пины»). Виды `olcrtc` и `openflux` в строке `kinds` есть, но эта версия их не
  разворачивает: не добавляйте их.

### Как проверить, что сервис работает

Отдельной команды «проверить протокол» нет. Проверка складывается из четырёх частей:

1. **На ноде: юнит работает.** `systemctl is-active niko-ИМЯ` должно ответить `active`, в `rayctl status` нет строк
   `FAILED`.
2. **На ноде: хост в порядке.** `rayctl check` — те же проверки, что перед установкой, плюс зоны DNS-туннелей.
3. **Снаружи: нода видна как клиенту.** `rayctl probe` с другой машины (ниже): SPA, подписка и список профилей в
   ней.
4. **Сам туннель** проверяет только клиент: подключитесь профилем в Niko и откройте любой сайт.

### Проба снаружи: `rayctl probe`

Проба делает то же, что клиент: шлёт SPA-пакет, забирает подписку и проверяет её подписи. Ей нужен пакет устройства.
Заведите для этого отдельное устройство (пользователь — из §10):

```bash
rayctl device add u-k3f9-x2qa probe -o /root/probe.bundle
```

Перенесите файл на **другую** машину, где есть `rayctl`: Linux, macOS или FreeBSD (§7 — про то, где его взять). Там
выполните:

```bash
./rayctl probe -channel @probe.bundle
```

Что вы должны увидеть (пример):

```
node 203.0.113.7 (203.0.113.7), device fbe632f9b3f9a754
SPA over udp to port 28500, subscription in 311ms: both signatures valid
seq 2, expires 2026-11-17T13:59:58Z, 3 profiles
  reality (service 4)
  naive (service 7)
  dns (service 11)
channel down: 8388608 bytes in 1.9s, 35.3 Mbit/s (node: rtt 48.0 ms, retransmits 2)
channel up: 4194304 bytes, 21.4 Mbit/s at the node (node: rtt 47.1 ms, retransmits 0)
channel link: 0 connections of this address on 443 at the node; rtt median 0.0 ms, retransmits 0.00%
channel udp: 50 sent, 50 back; lost up 0, down 0; rtt min/avg/max 46.9/48.3/55.0 ms, jitter 1.2 ms, reordered 0
```

**Что это значит.**

- `SPA over udp … both signatures valid` — SPA дошёл, порт подписки открылся, подписка подписана ключами этой ноды.
- Список профилей — то, что получит клиент этого пользователя.
- `channel down`, `channel up` — скорость TCP между этой машиной и нодой: 8 МиБ вниз и 4 МиБ вверх.
- `channel link` — сколько TCP-соединений с вашего адреса на 443 нода видит прямо сейчас. С машины, где не
  запущен клиент, там ноль — это нормально.
- `channel udp` — эхо из 50 датаграмм: потери и задержка UDP.

**Если вы видите другое:**

| Что вы видите | Причина | Что делать |
|---|---|---|
| `SPA over udp to port …, then subscription: …`, затем `SPA over tls … both signatures valid` | UDP до ноды не доходит, сработал запасной носитель по TCP | сеть этой машины или провайдер ноды режет UDP: проверьте диапазон SPA по UDP в файрволе провайдера |
| `node not reachable: …` после трёх попыток | SPA не дошёл или порт подписки закрыт | часы на обеих машинах; файрвол провайдера (§6.1); `systemctl is-active rayspa rayd` на ноде |
| `subscription refused (404)` | устройство отозвано, пользователь выключен или истёк | `rayctl device list`, `rayctl user list` на ноде |
| `channel udp: … lost up 50` или большие потери | UDP режется по пути | UDP-профили в этой сети работать не будут; остаются REALITY и naive |
| профиля нет в списке | сервиса нет у пользователя или он выключен | `rayctl user services`, `rayctl service list` |

- `-redact` заменяет адреса, имена и ID в выводе: его можно показать кому угодно.
- `-carrier udp|tls|tcp` — проверить один носитель SPA.
- После проверки удалите файл пакета устройства и отзовите устройство: `rayctl device list u-k3f9-x2qa`, затем
  `rayctl device revoke ID`.

### REALITY (`reality`) и сайт (`site`)

- **Что это.** VLESS + REALITY + Vision на Xray, TCP 443. Для постороннего нода — обычный сайт с настоящим
  сертификатом: неавторизованным отвечает собственный сайт-приманка (сервис `site`, создаётся вместе с REALITY) на
  случайном поддомене.
- **После установки по умолчанию:** включён, если задан `-domain`.
- **Добавить, если не ставился** (`-services none`):

  ```bash
  rayctl service add reality reality
  ```

  ```bash
  rayctl apply
  ```

- **Проверить на ноде:** `systemctl is-active niko-site niko-reality`; в `rayctl status` строка `acme site` — с `ok`.
- **Настройки:**

  | Команда | По умолчанию | Что делает |
  |---|---|---|
  | `rayctl service set site answer=404\|403\|silent\|pages` | `404` | что сайт отвечает тем, кого отклонил REALITY: пустой 404, пустой 403, молчание до обрыва или сгенерированный сайт. Затем `rayctl apply` |
  | `rayctl service set reality rotate_sni=false` | `true` | не менять имя сервера при плановой смене ключей |
  | `rayctl service set reality open=true` | выключено | TCP 443 открыт всем, без SPA (§9) |
  | `rayctl service rotate reality [-now]` | — | сменить ключи раньше срока (§12.7) |
  | `rayctl service cert site -chain F -key F [-force]` | ACME | только root: свой сертификат вместо Let's Encrypt; должен покрывать все имена сайта. Ссылки под ним идут без пина (ниже) |
  | `rayctl service rotate site [-force \| -fresh]` | — | только root: сменить ключ сертификата сайта (ниже) |

- **Чужая цель вместо своего сайта.** Без домена REALITY можно завести на чужой сайт с TLS 1.3:
  `rayctl service add reality reality -settings '{"target":"www.example.org:443"}'`. Сервисы `naive`, `doh` и
  `yggdrasil` при этом недоступны: им нужен свой сайт.

### Сертификат сайта и пины (`niko-pin`)

С v0.26.0 ссылки naive, `hy2-masq` и DoH в подписке несут параметр `niko-pin` — отпечатки ключа сертификата сайта.
Подписку подписывает сама нода, поэтому пин из неё не зависит от удостоверяющих центров.

- **Зачем.** Без пина клиент примет любой сертификат на имя ноды от любого центра, которому верит телефон. С пином —
  только сертификат с ключом из списка: сертификат на имя ноды, выпущенный кем-то другим, не пройдёт.
- **Что в списке.** Ключ сертификата в работе и следующий ключ; час после плановой смены — ещё и прежний.
- **Кто проверяет.** Niko 1.46.0 и новее: в naive — пин и цепочку, в `hy2-masq` и DoH — пин вместо цепочки. Более
  ранние версии в naive и DoH параметр не читают; Niko 1.45.0 проверяет его только в `hy2-masq`.
- **Где пина нет.** REALITY, DNS-туннели и Yggdrasil его не получают. У `hy2-obfs` свой пин, как раньше. Под своим
  сертификатом (`rayctl service cert`) пина нет и у naive, `hy2-masq` и DoH.
- **Ключ живёт долго.** При продлении сертификата ключ прежний, пины не меняются. Следующий ключ нода готовит
  заранее и сама переходит на него при первом продлении после 180 дней, если он пробыл в подписках 14 дней: к этому
  времени клиенты его пин уже знают.
- **Когда пины появляются.** На новой ноде — с первым сертификатом, но не раньше чем через десять минут после
  запуска `rayd`. На ноде, обновлённой до v0.26.0, — через десять минут после обновления (§12.5). Клиент берёт их при
  очередном запросе подписки.
- **Состояние** — столбец `KEYS` у сайта в `rayctl service list`:

  | Что в `KEYS` | Что значит |
  |---|---|
  | `key since 2026-11-14 13:58, next key pinned since 2026-11-14 14:08` | с какого времени ключ в работе и с какого следующий ключ в подписках |
  | в конце `, switch to it asked` или `, switch to a fresh key asked` | смена запрошена командой и ещё не сделана |
  | в конце `, previous key pinned until …` | час после плановой смены: прежний ключ ещё в списке |
  | `certificate of your own: no pins` | свой сертификат, пинов нет |
  | пусто | следующего ключа ещё нет, пинов нет: например, первые десять минут после обновления |

**Сменить ключ вручную** — только root на ноде; каждый вызов записывается в аудит.

| Команда | Когда | Цена |
|---|---|---|
| `rayctl service rotate site` | плановая смена раньше 180 дней | никакой. Отказ, пока следующий ключ не пробыл в подписках 14 дней |
| `rayctl service rotate site -force` | утёк ключ в работе | клиенты, которые не обновляли подписку с появления следующего ключа, не проходят naive, `hy2-masq` и DoH, пока не обновят. Отказ, пока ключу в работе меньше 72 часов |
| `rayctl service rotate site -fresh` | утекла база, резервная копия или весь сервер, то есть оба ключа | все клиенты с пинами не проходят naive, `hy2-masq` и DoH, пока не обновят подписку |

- Пока новый сертификат не выпущен и не сохранён, работает прежний ключ. Команда делает одну попытку выпуска сразу;
  если она не удалась, дальше — по обычной выдержке, ход виден в строке `acme site` в `rayctl status`. Тот же запрос
  повторно получает попытку не раньше чем через 15 минут после последней неудачной; более сильный (`-fresh` после
  `-force`) — сразу.
- После смены naive, сайт, `hy2-masq` и Yggdrasil один раз перезапускаются, их соединения рвутся.
- Клиент, у которого пин не сошёлся, сам перезапрашивает подписку, если этот профиль у него рабочий: не раньше чем
  через 15–30 секунд. Остальные получат новый список при очередном запросе подписки (она живёт 72 часа).

**Свой сертификат** — `rayctl service cert site -chain F -key F`, только root на ноде. До v0.26.0 эту команду могли и
члены группы `raycontrol`; теперь они получают `rayctl: permission_denied: a site's certificate: root on the node
only`. Ссылки под своим сертификатом идут без `niko-pin`: клиенты проверяют только цепочку, как раньше. Если ссылки
уже несли пины ноды, а у нового сертификата другой ключ, команда отказывает: клиенты с пинами не прошли бы, пока не
обновят подписку. `-force` ставит сертификат всё равно, с этой ценой. С включённым ACME (так ставит установка) нода,
когда подойдёт срок, заменит свой сертификат собственным, и пины вернутся.

### Hysteria2 (`hy2-masq`, `hy2-obfs`)

- **Что это.** Hysteria2 на UDP 443 за фронтом. Два вида:
  - `hy2-masq` — выглядит как HTTP/3 к сайту, сертификат сайта;
  - `hy2-obfs` — весь поток в обфускации salamander, снаружи это случайные байты; сертификат свой, клиенты его
    закрепляют.

  Можно держать оба: фронт различает их сам.
- **После установки по умолчанию:** выключены.
- **Добавить:**

  ```bash
  rayctl service add hy2-masq hy2-masq
  ```

  ```bash
  rayctl service add hy2-obfs hy2-obfs
  ```

  ```bash
  rayctl apply
  ```

- **Проверить на ноде:** `systemctl is-active niko-hy2-masq niko-hy2-obfs`. Снаружи — `rayctl probe -channel`: строка
  `channel udp` показывает, проходит ли UDP вообще.
- **Настройки:**

  | Команда | По умолчанию | Что делает |
  |---|---|---|
  | `rayctl service set hy2-masq up_mbps=500` | нет потолка | нода шлёт одному соединению не быстрее 500 Мбит/с |
  | `rayctl service set hy2-masq down_mbps=200` | нет потолка | потолок отдачи клиента в сторону ноды |

  Значение `0` снимает потолок. `rayctl apply` не нужен: `rayd` перезапустит сервис сам.

### naive (`naive`)

- **Что это.** NaiveProxy по HTTP/2 (TCP 443) и HTTP/3 (UDP 443) под сертификатом сайта. Несёт TCP, UDP внутри
  потока и — единственный — ping через ноду, если его включить.
- **После установки по умолчанию:** выключен. Нужен `reality`: naive делит с ним сайт.
- **Добавить:**

  ```bash
  rayctl service add naive naive
  ```

  ```bash
  rayctl apply
  ```

- **Проверить на ноде:** `systemctl is-active niko-naive`.
- **Настройки:**

  | Команда | По умолчанию | Что делает |
  |---|---|---|
  | `rayctl service set naive icmp=on`, затем `rayctl apply` | `off` | ping и traceroute через ноду (§9, §11) |

- **Клиент:** UDP через naive понимает Niko 1.42.0 и новее.
- **Честный connect** (с v0.26.0). В ссылке naive есть `niko-ack=1`. Клиент, который шлёт заголовок `niko-ack: 1`,
  получает ответ, когда нода уже соединилась с адресатом: `200` — соединение есть; `502` с причиной `refused`
  (адресат отказал), `unreachable` (нет маршрута, имя не нашлось) или `denied` (адрес закрыт политикой ноды:
  частные сети, сама нода); `504` — адресат молчал все 10 секунд. Niko 1.46.0 шлёт заголовок и показывает причину,
  только когда в нём включён эксперимент «Честный connect» (по умолчанию выключен). Как причина выглядит в
  приложении, здесь не проверялось. Клиент без заголовка видит всё как раньше.

### DoH (`doh`)

- **Что это.** DNS over HTTPS для клиентов ноды на TCP 443 и DoH3 на UDP 443. С v0.27.0 у каждого устройства свой
  токен в ссылке (до этого — один на пользователя). Своего процесса нет: отвечает `rayd`.
- **Отзыв устройства** DoH остальных устройств человека не трогает: умирает только токен отозванного, со
  следующего запроса.
- **После обновления до v0.27.0** прежний общий токен пользователя действует ещё 72 часа, пока устройства не
  возьмут подписку со своими токенами; Niko делает это сам. Если в эти 72 часа отозвать устройство человека, его
  общий токен закрывается сразу.
- **Чего нет:** строки DoH в `rayctl user export` — токен бывает только у устройства.
- **После установки по умолчанию:** выключен. Нужен `reality`.
- **Добавить:**

  ```bash
  rayctl service add doh doh
  ```

  ```bash
  rayctl apply
  ```

- **Проверить:** профиль `doh` есть в выводе `rayctl probe`. Настроек нет.

### Yggdrasil (`ygg`)

- **Что это.** Узел сети Yggdrasil: клиент поднимает с нодой TLS-линк на TCP 443, а трафик уходит в `inner`. Даёт
  запасной путь через публичные пиры и сеть между устройствами одного пользователя.
- **После установки по умолчанию:** выключен. Нужен `reality`.
- **Добавить:**

  ```bash
  rayctl service add yggdrasil ygg
  ```

  ```bash
  rayctl apply
  ```

- **Проверить на ноде:** `systemctl is-active niko-ygg niko-inner`.
- **Настройки:**

  | Команда | По умолчанию | Что делает |
  |---|---|---|
  | `rayctl service set ygg peers=URI,URI`, затем `rayctl apply` | нет пиров | публичные пиры, до 8 (ниже) |
  | `rayctl service set ygg peers=none`, затем `rayctl apply` | — | убрать пиры |
  | `rayctl service set ygg lan_relay=50` | `20` | потолок сети между устройствами через ноду, Мбит/с на пользователя (§9) |

- **Публичные пиры.**

  ```bash
  rayctl service set ygg peers=tls://198.51.100.10:443,quic://198.51.100.11:443
  ```

  ```bash
  rayctl apply
  ```

  - Пиры берите с [publicpeers.neilalexander.dev](https://publicpeers.neilalexander.dev/).
  - До 8 разных: у разных операторов и в разных странах, вперемешку `tls://`, `quic://` и `wss://`. Клиент
    получает их в подписке как запасной путь к ноде; как он выбирает между ними, решает клиент.
  - `quic://` — только по IP-адресу.
  - `tcp://` и `ws://` нода примет, но линк в них открытый: протокол Yggdrasil виден на проводе.
  - С пирами нода видна в общей сети Yggdrasil. Команда сама предупреждает: с публичными пирами изменённый клиент
    может провести данные мимо потолка `lan_relay` и лимитов трафика. На ноде с лимитами пиры лучше не включать.

### DNS-туннели: dnstt (`dns`), masterdns (`mdns`), slipstream (`slip`)

- **Что это.** Аварийный канал через DNS-резолверы, когда закрыто всё остальное. Клиент шлёт запросы резолверу
  (своей сети или публичному), тот доходит до ноды по делегированию зоны. Скорость — 0,1–3 Мбит/с на человека:
  её режут резолверы.
  - `dnstt` — туннель поверх DNS с меткой устройства в каждом запросе.
  - `masterdns` — MasterDnsVPN, другой протокол туннеля: где не проходит один, может пройти другой.
  - `slipstream` — QUIC поверх DNS с несколькими резолверами сразу. Клиент — Niko 1.37 и новее.

  Разумно держать dnstt и masterdns вместе: клиент выбирает рабочий сам.
- **После установки по умолчанию:** выключены.
- **Добавить:**

  ```bash
  rayctl service add dnstt dns
  ```

  ```bash
  rayctl service add masterdns mdns
  ```

  ```bash
  rayctl service add slipstream slip
  ```

  ```bash
  rayctl apply
  ```

  Зона slipstream — не длиннее 20 символов, а нода делает её из трёх символов и вашего домена. Если домен длиннее
  16 символов, задайте зону сами: `rayctl service add slipstream slip -settings '{"zone":"s.example.net"}'`.
  Для зоны вне домена ноды делегирование вы заводите сами: нужные записи покажет `rayctl dns`.
- **UDP 53 открыт всем:** резолверы не умеют SPA. Фронт отвечает только за зоны туннелей, на остальное — отказ.
- **Резолвер выбирает клиент.** Туннель работает, только если выбранный резолвер доходит до ноды и пропускает её
  ответы. Публичный резолвер, который работает в одной сети, в другой может быть закрыт.
- **Проверить на ноде** — записи, затем зоны:

  ```bash
  rayctl dns
  ```

  ```bash
  rayctl dns check -now
  ```

  Вторая команда проверяет каждую зону по шагам и печатает по блоку на зону:
  - `parent` — делегирование у серверов родительской зоны, без кэшей;
  - `front` и `backend` — фронт и сервер туннеля на самой ноде;
  - таблица резолверов — проходит ли проба через Google, Cloudflare и Quad9.

  У исправной зоны в заголовке блока нет слова `FAILED`, а шаги помечены `ok`. Сразу после установки делегирование
  может ещё не разойтись: тогда блок говорит `resolvers not asked: the parent does not delegate the zone to the
  node` — подождите несколько минут и повторите. `-now` работает не чаще раза в 30 секунд.

  `rayd` повторяет эту проверку сам раз в час; итог — строки `dns-zone …` в `rayctl status`.
- **Проверить из своей сети** — с машины администратора, пакетом устройства:

  ```bash
  ./rayctl probe -dns @probe.bundle
  ```

  То же, что `rayctl dns check`, но через резолвер этой машины. С ноды всё проходит, а отсюда нет — дело в
  резолвере этой сети. Через другие резолверы: `./rayctl probe -dns -resolver google,cloudflare @probe.bundle`.
- **Настройки dnstt и masterdns:**

  | Команда | По умолчанию у нового сервиса | Что делает |
  |---|---|---|
  | `rayctl service set dns auth=off\|optional\|required` | dnstt — `required`, masterdns — `optional` | метка устройства в каждом запросе. Без `required` любой, кто знает зону, может занять места новых сессий |
  | `rayctl service set dns seal=off\|optional\|required` | `optional` | запечатать то, по чему туннель узнаётся на проводе. `required` — когда все клиенты это умеют (dnstt — Niko 1.35, masterdns — Niko 1.36) |
  | `rayctl service set dns auth_hint=off\|optional\|required` | `optional` | вторая версия метки; `required` — только при `auth=required` |
  | `rayctl service set dns spare_zones=2`, затем `rayctl apply` | нет | запасные зоны, до 4 (§9) |
  | `rayctl service rotate dns [-now] [-force]` | — | новый ключ (§12.7) |

- **Настройки slipstream:**

  | Команда | По умолчанию | Что делает |
  |---|---|---|
  | `rayctl service set slip max_connections=512`, затем `rayctl apply` | `256` | соединений на сервис, 16–1024 |
  | `rayctl service set slip device_connections=2`, затем `rayctl apply` | `4` | соединений на одно устройство, 1–16 |

  `0` возвращает значение по умолчанию. Пределы — аргументы запуска сервера в его юните, а юнит пишет только
  `rayctl apply`: до него новое значение не действует. `apply` перезапускает сервер, клиенты переподключаются.

### Удалённый API (`api`)

  по приглашению (QR), управления нодой с телефона или своего компьютера и для relay.
- **После установки по умолчанию:** выключен, если не указан в `-services`.
- **Добавить:**

  ```bash
  rayctl service add api api
  ```

  ```bash
  rayctl apply
  ```

  После `apply` снова посмотрите строку про файрвол провайдера (§6.1): в ней появился порт API.
- **Проверить:** приглашение из §10 регистрируется. Настроек нет, API на ноде один.

машина администратора через удалённый API (§10). И группа, и admin-устройство — почти полные администраторы

Подробности по строкам.

**Ping через ноду.** Нужны оба конца: `icmp=on` на сервисе naive ноды и настройка в приложении. Без любого из двух
телефон отвечает на ping сам (§11). `rayctl apply` обязателен: до него сервер сбрасывает ICMP-потоки клиентов.
Если на хосте ICMP-сокеты закрыты для служб, `apply` расширяет `net.ipv4.ping_group_range` и пишет об этом;
`rayctl check` предупреждает, если сокеты не откроются.

**Политика выхода.** Проверка после включения:

```bash
rayctl egress
```

В выводе пять строк и, у root, счётчики:

- `bittorrent`, `smtp (tcp 25)` и `local networks` — `blocked` или `allowed`: что записано в политике. `local networks`
  (собственные и локальные сети ноды, с v0.27.0) закрыты с самого начала, §13;
- `covers` — на кого она действует: все процессы data plane;
- `in force` — `yes`, когда `rayspa` уже применил её в ядре. `not yet: …` дольше нескольких секунд — смотрите
  `journalctl -u rayspa`;
- `blocked <правило>` — сколько сетевых пакетов и байт остановило каждое действующее правило. Адресов и
  пользователей там нет.

Вернуть: `rayctl egress allow bittorrent`, `rayctl egress allow smtp`. Нода, которая обновилась с версии до v0.21.0
и имела сервисы на Xray, держит BitTorrent закрытым, как раньше.

**Лимит трафика.**

```bash
rayctl user limit u-k3f9-x2qa 50G
```

```bash
rayctl user usage
```

```
USER         USED  LIMIT  PERIOD          SINCE              RESET              STATE
u-k3f9-x2qa  0     50G    monthly, day 1  2026-11-14 13:59Z  2026-12-01 00:00Z  active
```

- **Первая команда печатает строку, похожую на ошибку,** — это не ошибка, а предупреждение:

  ```
  rayctl: the first traffic limit turns counting on: inner and REALITY restart once, and their connections drop
  u-k3f9-x2qa: 0/50G, monthly, day 1, active
  ```

  Первый лимит на ноде включает счёт трафика: `inner` и REALITY перезапускаются, соединения через них рвутся
  один раз. То же происходит, когда лимит снимают с последнего пользователя. Следующие лимиты ничего не
  перезапускают.
- `50G` — это 50 ГиБ (по 1024); годятся `K`, `M`, `G`, `T`.
- Считается сумма в обе стороны за период. Период — месяц с дня `-reset-day` (1–28, 00:00 UTC) или
  `-period none` — всё время пользователя.
- Достиг лимита — снят со всех профилей сразу, открытые соединения рвутся. Подписка остаётся: Niko 1.43.0 и новее
  показывает, что трафик исчерпан и до какого времени.
- Вернуть раньше срока: поднять лимит или `rayctl user reset-usage ИМЯ`. Снять лимит: `rayctl user limit ИМЯ off`.
- Не считаются DoH ноды и служебное: SPA, подписка, замеры на порт подписки.

**Пределы соединений** включены сразу и защищают ноду: на пользователя в каждом процессе (TCP — 1024 одновременно и
30 новых в секунду; UDP — 256 сессий) и на адрес для новых входящих соединений. Что видит пользователь, упёршийся в
предел: naive — ответ `429`, Hysteria2 — `too many connections`, REALITY — соединение закрывается без данных. Кто
упирался за последние 15 минут — в `rayctl conn-limit` и `rayctl status`.

**Сеть между устройствами (LAN).** Нужны два согласия: администратора — `rayctl user lan ИМЯ on` — и каждого
устройства, которое показывает себя в Niko. Пользователь должен иметь сервис Yggdrasil, иначе команда откажет.

- **В одной Wi-Fi — пока тоже через ноду.** По спецификации устройства в одной Wi-Fi связываются напрямую, без
  ограничений и без учёта. В Niko 1.45.0 этот прямой путь ещё не сделан: по сообщению сессии, которая ведёт клиент,
  задача открыта. Поэтому сегодня и соседи по одной Wi-Fi ходят друг к другу через ноду, под тем же потолком.
- Из разных сетей связь идёт через ноду. **Потолок 20 Мбит/с** относится только к этому трафику — устройство ↔
  устройство через ноду — и считается на пользователя, то есть на все его устройства вместе. Сверх потолка кадры
  отбрасываются, и соединение сбавляет темп. Обычный выход в интернет через профиль Yggdrasil потолок не задевает.
- Байты, прошедшие через ноду, идут в лимит трафика пользователя.
- `rayctl user lan ИМЯ on` ещё раз — новый пароль сети; отзыв любого устройства пользователя тоже меняет пароль.

**Автообновление и обновление с телефона** — §12.3. **Relay** — §12.4. **Окно отладки** — §12.1.

**Запасные зоны.** `spare_zones=2` заводит две случайные зоны в домене ноды; `spare_zones=a.example.net,b.example.org`
— свои; `spare_zones=none` — убрать. Нода делегирует, обслуживает и проверяет каждую, как основную; для зоны вне
домена ноды делегирование заводите вы. Сделать запасную зону основной: `rayctl service set dns zone=ЗАПАСНАЯ`, затем
`rayctl apply` — клиенты её уже знают.

**Сроки и интервалы `rayd`.** Срок смены учётных данных, длина окна SPA, частота самопроверки DNS и проверка новых
релизов (`-update-check`) — флаги `rayd serve` (таблица в [шпаргалке](cheatsheet.md)). Штатной команды для них нет:
юнит `rayd.service` пишет `rayctl apply`, и этих флагов в нём нет. Значения по умолчанию подобраны для обычной ноды;
менять их руководство не предлагает.

## 10. Пользователи, устройства и приглашения

Схема: **пользователь** (человек) → его **устройства** (телефон, ноутбук). Сервисы, срок и лимит задаются
пользователю. Ключ у каждого устройства свой, отзывается оно отдельно.

### 10.1. Создать пользователя

```bash
rayctl user add -services reality,hy2-masq,naive,dns -expires 90d
```

Что вы должны увидеть:

```
user u-k3f9-x2qa created
```

- **Что это значит.** Нода выдала непрозрачное имя. Так задумано: в журналах и отчётах ноды нет ничего личного.
  Запишите у себя, кому какое имя принадлежит. Своё имя задать можно — `rayctl user add alice -services …`, — но
  лучше не надо.
- `-services` — **имена** сервисов из `rayctl service list` (`dns`, а не `dnstt`). Сервиса с таким именем нет —
  `rayctl: not_found: service "…"`.
- `-expires 90d`, `-expires 12h` или `-expires 2026-12-31` — срок; без флага — бессрочно. После срока пользователь
  пропадает из всех профилей, его соединения рвутся.
- `-limit 50G` — лимит трафика сразу при создании (§9); `-note "текст"` — заметка для себя.

Посмотреть и поменять:

```bash
rayctl user list
```

```
NAME         ENABLED  EXPIRES           USED  SERVICES                   NOTE
u-k3f9-x2qa  true     2027-02-12 13:59  -     reality,hy2-masq,naive,dns
```

```bash
rayctl user services u-k3f9-x2qa reality,hy2-masq,naive,dns,ygg
```

Список сервисов заменяется целиком. При успехе команда ничего не печатает — как и `user enable`, `user disable`,
`user del`, `device revoke`, `service enable`, `service disable` и `service del`: проверяйте результат списком.

### 10.2. Устройство по приглашению с QR (рекомендуется)

Нужны сервис `api` (§8) и Niko 1.35 или новее.

```bash
rayctl device invite u-k3f9-x2qa phone -ttl 30m -qr -pin
```

- `phone` — имя устройства, любое; по нему вы потом узнаете устройство в списке.
- `-ttl 30m` — сколько живёт приглашение: по умолчанию сутки, не больше недели. Давайте короткий срок.
- `-qr` — нарисовать QR прямо в терминале. Нужна ширина окна около 60 колонок; тема терминала любая.
- `-pin` — приглашению нужен ещё PIN из 6 цифр.

**Что вы должны увидеть:**

1. Строку `invite … for u-k3f9-x2qa/phone (user), once, until … Scan it in Niko:` и QR под ней.
2. Под QR: `Once the QR is scanned or sent, Enter wipes it and shows the PIN.`
3. После Enter QR стирается с экрана и появляется PIN:

   ```
   PIN 472 908: tell it by another channel than the invite; 5 wrong tries withdraw it
   ```

- **Что это значит.** QR и PIN никогда не стоят на экране вместе, чтобы один снимок экрана не унёс оба. PIN
  сообщите другим каналом: голосом или в другом мессенджере.
- **Если `-qr with -pin needs a terminal (ssh -t)`:** вы запустили команду не в интерактивном терминале. Зайдите по
  SSH обычным образом или запишите приглашение в файл (ниже).
- **Если rayctl пишет `the invite is rcinv1: the node makes no rcinv2 …`:** адрес ноды задан именем, а не
  IP-адресом. Приглашение выдано в длинном формате; оно тоже работает, но QR шире — около 97 колонок.

**Что делает человек с телефоном.** Экраны Niko здесь описаны по смыслу; названия пунктов смотрите в самом
приложении.

1. Ставит Niko. Релизы приложения — в репозитории `arngory/niko` на GitHub.
2. В Niko открывает добавление ноды и **сканирует QR сканером самого приложения** или вставляет приглашение
   строкой. Открыть его как ссылку из другого приложения, например из системной камеры, не получится: так
   устроен короткий формат приглашения ([spec/api-v1.md](spec/api-v1.md) §3a).
3. Вводит PIN, если приложение его спросило.
4. Niko сам создаёт ключ своего сертификата, стучится на ноду и регистрируется. Этот ключ рождается на телефоне, и
   нода узнаёт только его отпечаток. Ключ устройства для SPA телефон получает в ответе на регистрацию, по
   защищённому каналу: на вашем экране и в QR его нет.
5. В приложении появляется нода со списком профилей. Человек включает VPN; рабочий профиль приложение выбирает само.

**Проверьте, что зарегистрировался именно он:**

```bash
rayctl device list u-k3f9-x2qa
```

```
ID                USER         NAME   ROLE  CREATED           REVOKED  LAN  API
d4a97c47a64973bd  u-k3f9-x2qa  phone  user  2026-11-14 14:00  -        off  registered
```

- `registered` в столбце `API` — устройство зарегистрировано.
- Строка с `invite until …` вместо этого — приглашение ещё не использовано.
- **Если человек пишет, что свежее приглашение отклонено,** а в списке уже стоит `registered` — приглашением
  воспользовался кто-то другой. Отзовите устройство (`rayctl device revoke ID`; учётные данные человека при этом
  меняются, §10.6) и выдайте новое приглашение, можно с тем же именем.
- **Имя отозванного устройства с v0.27.0 свободно:** приглашение взамен можно выдать с тем же именем. Занято
  только имя устройства, которое не отозвано: `rayctl: … device "phone" of u-k3f9-x2qa: the name is taken`. На
  ноде старше v0.27.0 имя отозванного остаётся занятым навсегда.

До регистрации приглашение — секрет: кто зарегистрируется первым, тот и получит устройство. Поэтому — короткий срок,
PIN и показ QR лично или в видеозвонке.

**Варианты.**

- QR не помещается или нужна картинка — приглашение в файл:

  ```bash
  rayctl device invite u-k3f9-x2qa phone -ttl 30m -pin -o /root/invite.txt
  ```

  PIN печатается на экран, в файл не попадает. Картинку делает `qrencode` (`apt install qrencode`):

  ```bash
  tr -d '\n' < /root/invite.txt | qrencode -o /root/invite.png; shred -u /root/invite.txt
  ```

  Картинку покажите и удалите: `shred -u /root/invite.png`.
- Niko старше 1.35 — длинное приглашение: добавьте `-format rcinv1`. QR тогда около 97 колонок.
- Новое приглашение тому же пользователю с тем же именем устройства заменяет неиспользованное. Если же
  приглашение уже использовано и устройство с этим именем не отозвано, имя занято: берите другое.

### 10.3. Администратор с телефона

Роль — у устройства, а не у пользователя: телефон может быть администратором, а ноутбук того же человека — нет.

```bash
rayctl device invite u-k3f9-x2qa admin-phone -role admin -ttl 30m -qr -pin
```

- Повысить готовое устройство нельзя: выдайте новое приглашение с `-role admin` и другим именем устройства, старое
  устройство отзовите.
- Admin-устройству удалённый API ноды даёт то же, что `rayctl` на ноде, кроме списка ниже
  ([spec/api-v1.md](spec/api-v1.md) §5). Какие экраны для этого есть в Niko, руководство не описывает: смотрите в
  приложении. Из записей этого репозитория известно одно: с Niko 1.40.0 в нём есть строка обновления ноды
  ([handoff/SYNC.md](handoff/SYNC.md), строка T9); её кнопка работает, только если root включил
  `rayctl update remote on`.
- Каждое действие записывается в журнал с именем устройства: `rayctl audit`.
- **Чего admin-устройство не может.** То, что меняет сам сервер, делает только root на ноде: `apply` (значит, новый
  сервис, добавленный с телефона, заработает после `rayctl apply` на ноде), `update`, `backup`, `restore`,
  `uninstall`, `service cert`, `service rotate site`, политика выхода, пределы соединений, окно отладки,
  добавление и удаление relay и выпуск пакета relay.
- Администратор видит всех пользователей и может выгрузить их ссылки. Давайте роль только тем, кому доверяете ноду
  целиком.

### 10.4. Администрирование со своей машины

На ноде — приглашение в файл:

```bash
rayctl device invite u-k3f9-x2qa laptop -role admin -ttl 30m -o /root/laptop.inv
```

Перенесите файл на свою машину, где есть `rayctl` (Linux — из архива релиза; macOS и FreeBSD — из своих архивов,
§7), и удалите его на ноде:

```bash
shred -u /root/laptop.inv
```

На своей машине приглашение читается из файла — так оно не попадает в историю оболочки и в список процессов:

```bash
./rayctl remote enroll -o laptop.rcdev @laptop.inv
```

После регистрации файл `laptop.inv` больше не нужен: удалите его.

Что вы должны увидеть:

```
device d4a97c47a64973bd registered (admin); its bundle and client key are in laptop.rcdev, keep it like a key
checked: rayctl -remote laptop.rcdev status
```

Дальше любая команда управления — через `-remote`:

```bash
./rayctl -remote laptop.rcdev status
```

```bash
./rayctl -remote laptop.rcdev device invite u-k3f9-x2qa phone2 -ttl 30m
```

- Файл `laptop.rcdev` — ключ устройства: права 0600, храните как SSH-ключ.
- **`-remote` проверяет права файла** (с v0.26.0) — на любой системе, и на Linux тоже. Файл, который может читать
  или менять группа или остальные, он не читает и называет исправление; файл другого пользователя тоже, но root
  его читать может (`sudo rayctl -remote ~/laptop.rcdev …`), как OpenSSH читает ключ. `rayctl` до v0.26.0 права не
  проверял. Сам `rayctl` пишет файл с правами 0600; открытым он обычно становится после копирования. На файловой системе без прав (FAT, exFAT, SMB, `/mnt/c` в WSL) `chmod` не поможет: скопируйте
  файл в домашний каталог.

  ```
  rayctl: device file laptop.rcdev is mode -rw-r--r--: it holds a private key, make it 0600: chmod 600 laptop.rcdev (if its filesystem keeps no modes: copy it to your home directory, chmod 600 the copy)
  ```
- Через `-remote` работают `status`, `node`, `user`, `service`, `device`, `audit`, `admin`, `dns`, `summary`,
  `app-mirror`, `metrics` и `debug show`. Остальное отвечает отказом одного из трёх видов:
  - `… works on the node itself, not through -remote` — у `install`, `apply`, `update`, `uninstall`, `backup`,
    `restore`, `report`, `egress`, `conn-limit`;
  - `… takes no -remote` — у `knock` и `probe`: им нужен только пакет на командной строке, запускайте их без
    `-remote`;
  - `… on the node only (rayctl as root)` — у отдельных действий внутри разрешённых команд: `service cert`,
    `relay add`, `relay remove`, `debug on`.
- На macOS и FreeBSD команды самого сервера отказывают ещё до обращения к ноде, своим видом строки:
  `… works on a Linux node only` (§7, «`rayctl` на своей машине»).
- Новый ключ устройству: `rayctl -remote laptop.rcdev remote rotate`.

### 10.5. Устройство пакетом устройства (без `api`)

Старый способ, когда сервиса `api` нет:

```bash
rayctl device add u-k3f9-x2qa phone -o /root/phone.bundle
```

```
device fbe632f9b3f9a754 (u-k3f9-x2qa/phone) enrolled; bundle in /root/phone.bundle: pass it over a trusted channel, then delete it
```

- Пакет — это и доступ, и ключ: у кого он есть, тот подключается. Передавайте лично или в мессенджере со сквозным
  шифрованием и исчезающими сообщениями, не почтой.
- В Niko — импорт устройства: вставить пакет устройства целиком или открыть файл.
- Пакет длинный (несколько килобайт), в QR он не помещается.
- После передачи: `shred -u /root/phone.bundle`.

Чем приглашение лучше: долгоживущий ключ не появляется ни на вашем экране, ни в канале передачи; в QR — одноразовый
секрет со сроком.

### 10.6. Отозвать устройство, отключить или удалить пользователя

| Что нужно | Команда | Что происходит |
|---|---|---|
| потерян или украден телефон | `rayctl device list ИМЯ`, затем `rayctl device revoke ID` | устройство больше не пройдёт SPA, не получит подписку и не войдёт в API. С v0.27.0 у человека сразу новые учётные данные: всё, что осталось в телефоне, перестаёт действовать, его соединения рвутся. Остальные устройства человека теряют связь на 15–30 секунд и сами берут новую подписку; DoH у них не прерывается |
| отменить неиспользованное приглашение | `rayctl device revoke ID` | приглашение перестаёт действовать |
| приостановить человека | `rayctl user disable ИМЯ` | он снят со всех профилей на всех своих устройствах, открытые соединения рвутся за секунды |
| вернуть | `rayctl user enable ИМЯ` | профили возвращаются с прежними учётными данными |
| удалить насовсем | `rayctl user del ИМЯ` | пользователь, его устройства и его учётные данные удалены |

`user disable`, `user enable` и `user del` при успехе ничего не печатают; `device revoke` говорит, чьё это было
устройство и сколько учётных данных человека заменено. Проверка — `rayctl device list` (столбец `REVOKED`) и
`rayctl user list` (столбец `ENABLED`).

Отозванное устройство вернуть нельзя: выдайте новое приглашение. С v0.27.0 имя отозванного устройства свободно,
новое можно назвать так же (§10.2).

**Украденный телефон: что делает отзыв.** Учётные данные профилей (UUID, пароли) — у пользователя, а не у
устройства: они одни на все его устройства. Поэтому с v0.27.0 отзыв устройства всегда меняет их все, сразу, без
перекрытия (решение R4-36 в [08-decisions.md](08-decisions.md)). Флага «не менять» нет. Токен DoH — исключение:
он у каждого устройства свой (R4-37), отзыв закрывает только токен отозванного.

```bash
rayctl device revoke ID
```

```
device 3f0c9a1e5b7d2468 (u-k3f9-x2qa/phone) revoked. u-k3f9-x2qa's credentials are new (4 credentials): ...
```

- **Что закрывается сразу:** SPA, подписка и API для этого устройства; его метка в dnstt с `auth=required` и в
  slipstream; его ключ в Yggdrasil.
- **Что перестаёт действовать за секунды** (как только `rayd` применит изменение): все учётные данные, которые
  остались в телефоне, в том числе следующие, если подписка их уже принесла, и строки, скопированные из
  `rayctl user export`. Открытые соединения на них рвутся: REALITY и `inner` (а с ним DNS-туннели и Yggdrasil) —
  сразу, через API Xray; Hysteria2 и naive — когда процесс перечитает файл пользователей, до 5 секунд; токен DoH
  отозванного устройства — со следующего запроса. Пути без SPA (`reality open=true`, DNS-туннель без
  `auth=required`, чужой адрес, которому порт открыло другое устройство) больше ничего не дают: туннель без метки
  ещё донесёт запросы до ноды, но `inner` их не пустит.
- **Что видят остальные устройства человека:** их профили тоже перестают работать — старые данные у них те же.
  Кроме DoH: с v0.27.0 токен DoH у каждого устройства свой, и он продолжает работать.
  Niko замечает это за 15–30 секунд (две неудачные проверки), сам берёт подписку — её открывают собственные
  ключи устройства, отзыв их не трогает — и подключается с новыми данными. Предупреждать людей не нужно; разве
  что телефон, который долго был без сети, переподключится, когда включится.
- **Последнее устройство человека** отзывается так же: данные меняются, даже если устройств у него больше нет —
  строки могли скопировать.
- **Лимит трафика и пределы соединений** — у пользователя, а не у данных: счёт периода продолжается.
- **Повторный отзыв** того же устройства ничего не меняет и данные второй раз не трогает.
- Если процесс не принял изменение (Xray не ответил по API, а его перезапуск не удался), `rayctl status` покажет
  ошибку применения, и `rayd` повторяет перезапуск каждую минуту, пока он не пройдёт. До этого прежние данные на
  этом сервисе ещё действуют.

Выключать и включать пользователя, чтобы оборвать соединения, и пересоздавать его ради новых данных больше не
нужно.

**Устройства, отозванные до v0.27.0.** Тогда отзыв данные не менял, а повторный отзыв теперь ничего не делает.
Поэтому обновление до v0.27.0 один раз даёт новые учётные данные каждому человеку, у которого есть отозванное
устройство: так же, как отзыв, без перекрытия. Остальные устройства этих людей переподключаются через 15–30
секунд; в `rayctl audit` — строка `user.renew:revoked-before` на каждого. При следующих стартах это не
повторяется.

Новые данные человеку без отзыва (например, ссылки из `rayctl user export` ушли дальше, чем нужно):

```bash
rayctl user renew ИМЯ
```

Всё как при отзыве: старые данные перестают действовать за секунды, устройства человека переподключаются после
следующей подписки.

На ноде старше v0.27.0 отзыв учётные данные не меняет; `rayctl device revoke` нового `rayctl` к такой ноде так и
скажет. Там по-прежнему: `rayctl user disable` и `enable` — оборвать соединения, а при пути без SPA — удалить
пользователя и завести заново.

### 10.7. Смена учётных данных и что замечают пользователи

Ссылки в подписке — не постоянные. Нода меняет их сама:

- **Учётные данные пользователя** (UUID и пароли профилей) — раз в 30 дней. Новые появляются в подписке за 3 дня
  до смены, прежние принимаются ещё 2 дня после.
- **Ключи REALITY и имя его сервера** — раз в 90 дней, с таким же перекрытием.

Клиент забирает подписку сам и переходит на новые ссылки заранее.

- **Что замечает пользователь: ничего.** С v0.23.0 смена не рвёт даже открытые соединения.
- **Исключение.** Устройство, которое не выходило на связь с нодой дольше этого перекрытия — около пяти дней
  вокруг смены, — подключится не с первого раза: сначала клиент обновит подписку. Ключ устройства и доступ к
  подписке при сменах не меняются, так что заново добавлять устройство не нужно.
- **Досрочная смена** (ключ утёк) — §12.7. С флагом `-now` прежние ключи перестают работать сразу, и клиенты без
  свежей подписки теряют этот профиль, пока её не обновят.
- **Отзыв устройства** (§10.6) меняет учётные данные его пользователя сразу и без перекрытия: остальные
  устройства этого человека теряют связь на 15–30 секунд, пока Niko не возьмёт новую подписку. Других
  пользователей это не касается.

Выгрузить ссылки пользователя руками — как в подписке, для клиента без Niko:

```bash
rayctl user export u-k3f9-x2qa
```

В ссылках учётные данные; вызов попадает в журнал действий. Ссылки работают только с адреса, который открыл SPA, и
до ближайшей смены.

## 11. Ping, traceroute и скорость: что вы увидите и почему

Коротко: **ping через VPN почти всегда показывает неправду**, и это не поломка.

### Что происходит с ping на обычном профиле

REALITY, Hysteria2 и naive — прокси. Они переносят соединения программ (TCP) и датаграммы (UDP), но не эхо-запросы
ping (ICMP). Поэтому на любом профиле без поддержки ICMP — это REALITY, Hysteria2 и naive, пока «ping через ноду»
выключен хотя бы на одной стороне, — происходит вот что:

- на эхо-запрос **отвечает сам телефон**: сетевая часть VPN-приложения формирует ответ на месте;
- эхо-запрос **не покидает телефон** — ни до ноды, ни до адреса назначения он не доходит;
- время в ответе — это время обработки внутри телефона. Оно может быть и 1 мс, и 10–20 мс, и не говорит ничего ни
  о ноде, ни о сайте;
- traceroute показывает **один хоп** — сразу адрес назначения. Этот хоп тоже нарисован телефоном.

Отсюда типичная картина: «пингую сервер на другом конце света, вижу 15 мс и ни одного промежуточного узла». Это не
значит, что VPN не работает или трафик идёт мимо него. Это значит, что ответил телефон.

### Как отличить ответ телефона от настоящего

Пропингуйте с телефона адрес, которого не существует, — в любом приложении для ping или в терминале:

```bash
ping 203.0.113.77
```

- **Адрес «отвечает»** — отвечает телефон. Настоящего ping через этот профиль нет.
- **Ответа нет** (таймаут) или приходит ошибка — ping настоящий или не идёт вовсе.

Адрес `203.0.113.77` зарезервирован для документации и в интернете не существует, ответить с него некому.

### Когда ping настоящий

Нужны сразу три условия:

1. профиль **naive**;
2. на ноде на сервисе naive включено `icmp=on` и после этого выполнен `rayctl apply` (§9);
3. в Niko включена экспериментальная настройка **«Ping через ноду»** (Niko 1.43.1 и новее — по записи в
   [handoff/SYNC.md](handoff/SYNC.md)).

Тогда эхо-запрос уходит в туннель, а отправляет его уже нода — от своего адреса. Что вы увидите:

- **время** — это путь телефон → нода → цель и обратно: задержка до ноды плюс задержка от ноды до цели;
- **traceroute** показывает узлы **за нодой**: от ноды до цели. Путь от телефона до ноды не показывается никогда —
  он внутри туннеля;
- узлы с частными адресами (внутри сетей провайдеров) в трассировке молчат: их ответы нода отбрасывает;
- цели — только публичные адреса. На частный адрес нода отвечает «запрещено», а не молчит;
- предел — 30 запросов в секунду на пользователя. Обычному ping и mtr хватает; флуд обрежется.

**Что проверено.** Настоящий ping через ноду пока проверен только в автоматическом interop-тесте клиента на Linux.
На физическом телефоне его никто не проверял. Если на вашем телефоне при всех трёх условиях несуществующий адрес
всё равно «отвечает» — сообщите об этом с отчётом (§12.1).

### Настройка «Не отвечать на ping с телефона»

В первом выпуске Niko после 1.45.0 появляется необязательная настройка **«Не отвечать на ping с телефона»**. В
Niko 1.45.0 и раньше её нет: она готова в ветке клиента и ждёт выпуска. По умолчанию она выключена.

| Настройка | Что происходит с ping, который не несёт ни один профиль |
|---|---|
| выключена (по умолчанию) | отвечает сам телефон, как описано выше |
| включена | запрос отклоняется: телефон на него не отвечает |

- **Что вы увидите с включённой настройкой.** `ping 203.0.113.77` перестаёт «отвечать»: ping показывает 100 %
  потерь. На сетевом стеке приложения по умолчанию ответа просто нет; на системном стеке приложение получает
  «unreachable».
- **Что продолжает работать.** Маршруты, которые действительно несут ICMP: напрямую — локальная сеть и правила
  обхода VPN — и профиль naive с включённым ping через ноду.
- **Почему она не включена по умолчанию.** Игры и приложения, которые меряют задержку через ICMP, увидят
  «нет сети» там, где сейчас видят ответ телефона. Поэтому выбор оставлен вам.
- **Кому её включать.** Тем, кто хочет, чтобы ping говорил правду: ответ есть — он настоящий, ответа нет — через
  этот профиль ping не идёт.
- **Что проверено.** Поведение проверено в interop-тесте клиента: несуществующий адрес по умолчанию «отвечает», с
  настройкой — нет. В выпущенной версии приложения настройки ещё нет, на телефоне её не проверяли.

### Как измерить задержку и скорость честно

- **Задержка через профиль** — тест задержки профиля в Niko. По сообщению сессии, которая ведёт клиент, он меряет
  время HTTP-запроса через туннель, а не ICMP, и потому работает на любом профиле.
- **Канал между телефоном и нодой** — «Проверить канал» в Niko: скорость TCP, потери и задержка UDP. То же самое со
  своей машины в той же сети — `rayctl probe -channel` (§8).
- **Скорость** — любой тест скорости в браузере при включённом VPN. Он меряет весь путь: телефон → нода → сервер
  теста.
- **Сама нода на ping снаружи не отвечает.** `ping 203.0.113.7` без VPN закончится таймаутом. Это не признак того,
  что сервер лежит: проверяйте его командой `rayctl probe`.

## 12. Эксплуатация

### 12.1. Состояние и журналы

Каждый день достаточно одной команды:

```bash
rayctl status
```

Нет строк `FAILED` — нода в порядке. Остальное:

```bash
systemctl --no-pager list-units --all 'niko-*' rayd.service rayspa.service
```

```bash
journalctl -u rayd -u rayspa -u 'niko-*' -p warning --since -1h
```

```bash
rayctl audit -n 20
```

Последняя команда — журнал действий администраторов: кто, что и когда менял.

**Что пишется в журналы и что нет.** Все журналы — в journald сервера, своих файлов у ноды нет.

| Пишется | Не пишется никогда |
|---|---|
| запуск и остановка служб, ошибки | адреса назначения: куда ходят пользователи |
| выпуск сертификатов, смены ключей (числом) | содержимое трафика |
| применённые изменения периметра (числом устройств) | на обычном уровне — адреса клиентов и кто когда подключался |
| что пользователь номер N перешёл лимит трафика | история трафика: только счётчик текущего периода |

Xray всегда работает на уровне `warning` без журнала доступа — даже в окне отладки: на более подробном уровне он
писал бы адреса назначения.

**Окно отладки.** Когда нужно разобрать, почему клиент не подключается:

```bash
rayctl debug on -for 30m
```

```
debug window open until 15:00 UTC (16:00 CET): rayd, rayspa and niko-server log at debug level (Xray stays at warning)
the data-plane services restart now and when the window closes; their connections drop
client addresses go to the journal: rayctl debug off when done
logs of the window: rayctl report -logs debug -since 40m -id <run> -o FILE
```

- До конца окна `rayspa` пишет каждый SPA-доступ и отказ с адресом и устройством: видно, дошёл ли стук клиента.
- В журнал попадают адреса людей. Окно закрывается само, не дольше суток; раньше — `rayctl debug off`.
- Сервисы перезапускаются при открытии и закрытии окна: соединения рвутся.

**Отчёт для обращения за помощью.** Очищенный: адреса, имена, ключи и ID заменены.

```bash
rayctl report -logs info -since 24h -o /root/report.txt
```

Отчёт никуда не отправляется. Прочитайте файл и решите сами, показывать ли его. Со строками окна отладки —
`-logs debug`; несколько отчётов по одной проблеме — с одним `-id`.

Полная выгрузка журналов — только для себя: в ней адреса и имена. Время начала подставьте своё:

```bash
journalctl -u rayd -u rayspa -u 'niko-*' --since '2026-11-14 10:00:00 UTC' -o short-iso-precise > /root/run.raw.log
```

### 12.2. Резервная копия, восстановление, переезд

В базе ноды все её ключи, поэтому копия шифруется парольной фразой.

```bash
rayctl backup -o /root/node-$(date +%F).rcbak
```

Команда дважды спросит фразу, не короче 12 символов. Что вы должны увидеть:

```
wrote /root/node-2026-11-14.rcbak (… bytes): every key of the node, sealed with the passphrase.
Keep it off the node and the passphrase apart from it; rayctl restore puts it back.
```

Заберите файл с сервера — на своём компьютере:

```bash
scp root@203.0.113.7:/root/node-*.rcbak .
```

Затем удалите его на ноде. Без фразы копию не открыть: храните фразу отдельно от файла и не теряйте.

**Когда делать копию:** после установки, после добавления пользователей и перед `rayctl uninstall`.

**Вернуть на той же ноде:**

```bash
rayctl restore -i /root/node-2026-11-14.rcbak
```

Команда спросит фразу и подтверждение (`yes`). Подписка восстановленной ноды сразу идёт дальше: с v0.26.0 её
`seq` продолжается от часов, и клиенты принимают первый же её ответ (раньше они десять минут отбрасывали ответы
восстановленной ноды). Прежняя база остаётся рядом, в
`/var/lib/raycontrol/rayd.db.before-restore`, пока вы её не удалите.

**Восстановление возвращает ноду целиком в состояние копии.** Заменяется вся база, а не её часть, с двумя
исключениями:

- **Отзывы устройств остаются (с v0.27.0).** Отзыв — навсегда. Устройство, которое в базе этой ноды отозвано, а в
  копии ещё нет, остаётся отозванным, и его пользователь получает новые учётные данные, как при отзыве; `restore`
  печатает такие устройства. Остальные устройства этого человека переподключатся после следующей подписки.
- **Новые учётные данные тоже остаются (с v0.27.0).** Если после копии пользователь получил новые данные
  (`rayctl user renew`, обновление до v0.27.0) или у него создали и отозвали устройство, прежние данные из копии
  не возвращаются: у обновлённых — нынешние, у второго случая — новые. `restore` называет таких пользователей.
  Обычная ротация после копии откатывается к копии, как и всё остальное.
- **Чего нода знать не может.** Журнал действий лежит в той же базе и восстанавливается вместе с ней, поэтому
  «отозвано после копии» и «данные обновлены после копии» видно только из нынешней базы. Устройства копии, о
  которых нынешняя база ничего не знает (новый сервер, или их пользователя здесь удалили), `restore` перечисляет с
  предупреждением: отзовите снова те, что должны остаться отозванными, и выполните `rayctl user renew ИМЯ` для
  пользователей, которым меняли данные после копии.
- **Если нынешнюю базу не прочитать,** `restore` отказывает и ничего не меняет. `rayctl restore -no-carry`
  восстанавливает копию как есть — тогда отозванные после неё устройства вернутся со старыми учётными данными
  пользователя, и их нужно отозвать снова.
- **Пользователи, удалённые или выключенные после копии, вернутся рабочими.** Сразу после восстановления пройдите
  по `rayctl user list` и повторите удаления.
- **Адреса администратора, порт SSH и аварийное устройство — из копии.** Не закрывая сессию, проверьте
  `rayctl admin`: ваш нынешний адрес должен быть в списке. Нет — впишите его (§7), иначе следующая SSH-сессия
  не пройдёт.
- Всё, что вы добавили после копии, пропадает: пользователи, устройства, сервисы.

**Переезд на новый сервер или смена адреса.** Порядок важен: две ноды с одной базой делят одну зону Cloudflare
и стирают записи друг друга (§1).

1. **Старый сервер: копия и остановка `rayd`.** Сделайте копию, заберите файл, затем остановите `rayd`, чтобы
   он перестал раз в час править записи DNS:

   ```bash
   systemctl disable --now rayd
   ```

   Уже подключённые клиенты ещё работают, но подписку обновить не могут.
2. **Новый сервер: установка.** Пройдите §2–§5 с новым адресом: `restore` работает только поверх установленной
   ноды. sshd на новом сервере должен слушать на том же порту, что и на старом: порт SSH периметр возьмёт из
   копии.
3. **Новый сервер: восстановление.**

   ```bash
   rayctl restore -i node.rcbak -host 203.0.113.99
   ```

   Команда сама обновляет записи в Cloudflare и в конце печатает состояние ноды.
4. **Не закрывая сессию, проверьте доступ.**

   ```bash
   rayctl admin
   ```

   В списке — адреса со старой ноды. Вашего нынешнего нет — впишите: `rayctl admin 198.51.100.50`. Откройте
   вторую SSH-сессию и убедитесь, что она проходит.
5. **Аварийный пакет устройства, который напечатала установка на новом сервере, больше не действует:** его
   устройство было в базе, которую заменила копия. Действует аварийное устройство старой ноды. В его пакете
   старый адрес, поэтому стучитесь с явным адресом: `./rayctl knock -addr 203.0.113.99 @emergency.bundle`. Или
   выпустите новый пакет (§7).
6. **Повторите отзывы и удаления,** сделанные после копии: новый сервер о них не знает, `restore` перечислил
   устройства копии в предупреждении (выше).
7. **Проверьте записи DNS:**

   ```bash
   rayctl dns sync
   ```

   ```bash
   rayctl dns
   ```

   Все записи должны указывать на новый адрес, строк `problem:` быть не должно.
8. **Устройствам нужны новые приглашения:** в прежних пакетах устройств старый адрес. Пользователи, их учётные
   данные и ключи сервисов остаются прежними. Имена прежних устройств заняты, пока те не отозваны (§10.2). Старое
   устройство отзывайте, когда новое у человека уже работает: отзыв меняет его учётные данные (§10.6), и новое
   устройство переподключится с ними само.
9. **Старый сервер снимайте так, чтобы он не удалил записи,** которые уже указывают на новый:

   ```bash
   rayctl uninstall -keep-dns
   ```

Не включайте `rayd` на старом сервере, пока не сняли с него ноду.

### 12.3. Обновление ноды

Обновление с v0.25.1 на v0.26.0 по шагам, вместе с relay и машинами администраторов, — §12.5.

**Какая версия стоит:**

```bash
rayctl version
```

```
rayctl     vX.Y.Z
installed  vX.Y.Z (rayd on this host)
```

Первая строка — версия самого `rayctl`, вторая — установленная на этом хосте, ноде или relay. Root и работающий
`rayd` не нужны. На своей машине (§7) `rayctl version` печатает только первую строку, а с `-remote ФАЙЛ` — ещё
строку `node` с версией ноды. Эту команду знает `rayctl` после v0.26.0; в v0.26.0 и раньше версию ноды показывает
первая строка `rayctl status`, версию relay — `rayctl update status` на его хосте.

**Есть ли новый релиз:**

```bash
rayctl update -check
```

```
installed v0.25.1, release v0.26.0 available: rayctl update
```

или, если обновлять нечего: `raycontrol v0.26.0 is installed, the newest release`.

**Обновить:**

```bash
rayctl update
```

Что происходит:

1. `rayctl` скачивает релиз и проверяет его так же, как установщик (§3.3): подпись, версию, контрольную сумму. Пока
   проверка не прошла, из архива ничего не запускается.
2. Печатает `release v0.26.0 verified: its own rayctl updates the node` и передаёт обновление `rayctl` из самого
   релиза.
3. Тот печатает состав релиза и спрашивает:

   ```
   Update raycontrol v0.25.1 to v0.26.0? rayd, rayspa and the data plane restart; clients reconnect and send SPA again. Type yes to go on:
   ```

   Введите `yes`.
4. Прежние бинарники и копия базы уходят в `/var/lib/raycontrol-install/previous/`; ставятся новые; `rayd`,
   `rayspa` и сервисы перезапускаются.
5. Проверяется, что `rayd` отвечает новой версией, периметр на месте и каждый сервис, работавший до обновления,
   работает снова.

Успех:

```
raycontrol v0.26.0 is running; the previous binaries are kept for rayctl update -rollback
```

- **Клиенты** переподключаются сами; перерыв — около минуты.
- **Обновление до v0.27.0** один раз даёт новые учётные данные каждому пользователю, у которого есть отозванное
  устройство (§10.6). Тогда в конце есть строка `N users have new credentials: each had a device revoked before
  v0.27.0 …`: устройства этих людей переподключатся сами через 15–30 с. Если строки нет, никому данные не меняли.
- **Если что-то не поднялось,** обновление откатывается само: возвращаются прежние бинарники и база, и команда
  заканчивается строкой `update failed, the previous version runs again: <причина>`. Нода при этом работает на
  прежней версии.
- **Откатить вручную** уже удавшееся обновление:

  ```bash
  rayctl update -rollback
  ```

  Если обновление меняло схему базы, команда предупредит, что сделанное после обновления будет потеряно, и
  спросит подтверждение. Отнятое после обновления остаётся отнятым (отозванные устройства, выключенные
  пользователи и сервисы), а учётные данные пользователей остаются нынешними, с v0.27.0 — все: и новые после
  обновления до v0.27.0 или `rayctl user renew`, и сменённые ротацией. Данные, которые знают отозванные раньше
  устройства, откат не возвращает. Переподключаются только устройства тех, у кого после обновления отозвали
  устройство: их данные при откате меняются ещё раз.
- **Нет доступа к GitHub.** Скачайте три файла релиза на другой машине (§3.4), перенесите в каталог на ноде и:

  ```bash
  rayctl update -from /root/rc-release
  ```

  Подпись проверяется так же.
- **Конкретная версия:** `rayctl update -version v0.26.0`. На более старую версию нода сама не уходит: её надо
  назвать явно.
- **Только одно обновление, откат или `apply` за раз.** Второе сразу откажет: `another … is running`.
- **Со старых версий.** С v0.15.0 и новее — просто `rayctl update`. С v0.10–v0.14 — в два шага:
  `rayctl update -version v0.15.0`, затем `rayctl update` ([RELEASE.md](RELEASE.md), «Со старых версий: ступени»).

**Автообновление** (по умолчанию выключено):

```bash
rayctl update auto patch -window 03:00-05:00
```

```
rayd checks GitHub for releases every ~6 h and updates to a newer patch release of this minor version in the window 03:00-05:00, node time (rayctl update status)
```

- Ставятся только **патч-версии** той же минорной: v0.26.0 → v0.26.2, но не v0.27.0. Минорные обновления — руками.
- **Самая новая патч-версия вашей минорной** — с v0.27.0. Нода спрашивает у GitHub последний релиз. Если это
  патч вашей минорной, она его и ставит. Если последний релиз — уже новая минорная (v0.27.0), нода по очереди
  спрашивает следующие номера своей: v0.26.1, v0.26.2 и так далее, пока не встретит два пропущенных номера подряд,
  и ставит самый старший найденный. Один пропущенный номер (релиз сняли, а следом вышел исправленный) она
  переступает. За одну проверку — не больше 8 номеров, то есть не больше 18 запросов к GitHub. Без новой
  минорной запросов 2, как раньше; с новой минорной и без патчей — 4. Каждый найденный релиз проверяется подписью, как при обновлении: версия берётся из подписи
  и должна совпасть с номером.
- Новую минорную нода не ставит, но говорит о ней: в строке `auto-update` в `rayctl status` после `ok … ago:` —

  ```
  patch, window 03:00-05:00: v0.27.0 is out, a new minor version, which it leaves: this node runs v0.26.0; rayctl update takes it (or an admin's phone, with remote updates on)
  ```

  и в `rayctl update status`, вместе с найденным патчем, если он есть:

  ```
  latest     v0.27.0
  patch      v0.26.2, the newest patch release of v0.26.0: the auto update takes it in its window
  newer      v0.27.0 is a new minor version: the auto update takes patch releases only; rayctl update takes it
  ```

  Строку `auto-update` о новой минорной ноды пишут после v0.26.0. Нода на v0.26.x патчи своей минорной после
  выхода v0.27.0 сама не найдёт: её обновляет `rayctl update -version v0.26.N` или `rayctl update`.
- `rayctl update -check` при новой минорной называет и самый новый патч вашей (с v0.27.0):

  ```
  installed v0.26.0, release v0.27.0 available: rayctl update
  release v0.26.2, the newest patch release of v0.26.0, available: rayctl update -version v0.26.2
  ```
- Окно — по часам сервера, не короче 30 минут; без `-window` — 03:00–05:00.
- Ставятся только подписанные релизы и никогда не старее установленного.
- Версию, обновление на которую откатилось, нода больше сама не ставит.
- Выключить: `rayctl update auto off`.

**Обновление с телефона администратора** (по умолчанию выключено):

```bash
rayctl update remote on
```

После этого admin-устройство может запустить обновление на подписанный релиз новее установленного. Выключить:
`rayctl update remote off`.

**Состояние обновлений:**

```bash
rayctl update status
```

```
installed  v0.26.0
latest     v0.26.0
remote     off
auto       patch (window 03:00-05:00, CET +01:00)
last       none
```

- `latest` — то, что видела последняя проверка самой ноды. Сам `rayctl update status` к GitHub не ходит: запрос
  показывает GitHub адрес ноды, а решает это root (`rayctl update -check`). Нода проверяет, только если включено
  автообновление или `rayd -update-check`. Иначе строка такая:

  ```
  latest     not checked: rayd asks GitHub only with rayctl update auto patch or rayd -update-check; rayctl update -check asks now
  ```

  Сразу после включения автообновления, до первой проверки, — `latest     not known yet: …`. Так с v0.27.0;
  раньше строки `latest` в этих случаях не было вовсе.

Журнал обновлений, запущенных нодой или с телефона, — `journalctl -u raycontrol-update`.

### 12.4. Relay: установка и обновление

> **Не проверено на настоящем хосте.** Ни `bootstrap.sh -relay` на хосте с systemd, ни `rayctl update` на relay
> (v0.26.0) в CI не запускаются и на настоящем relay ни разу не запускались. Пересылка, стук и точка замера
> проверены в сетевых пространствах имён, шаги установки и обновления — модульными тестами. Держите доступ к
> консоли провайдера relay, пока обновляете.

**Relay** — второй сервер перед нодой. Клиент стучится к нему, а ядро relay пересылает соединения к ноде. Ключей
сервисов и расшифрованного трафика на relay нет. Нужен, когда прямой путь к ноде в сети клиента режется.

**Что нужно:** отдельный сервер с публичным IPv4 (нода и relay на одном хосте не живут) и сервис `api` на ноде.
DNS-туннели и Yggdrasil через relay не ходят.

**Установка.** На ноде, от root:

```bash
rayctl relay add msk 198.51.100.20
```

```bash
rayctl relay bundle -o /root/msk.bundle msk
```

Вторая команда печатает, с каких адресов будет открыт SSH хоста relay и какой порт замера нужно открыть у его
провайдера.

- **Адреса SSH хоста relay.** Без `-admin` это адрес SSH-сессии, из которой вы запустили команду на ноде. Из
  tmux, screen или с консоли адреса нет, и команда откажет: `the relay host's SSH needs admin addresses (-admin)`.
  Тогда задайте их сами: `rayctl relay bundle -admin 198.51.100.50 -o /root/msk.bundle msk`. Впишите адрес, с
  которого будете заходить на хост relay.
- **В пакете relay — его закрытый ключ.** Скопируйте файл **только** на хост relay и удалите его на ноде:

  ```bash
  shred -u /root/msk.bundle
  ```

- **Файрвол провайдера relay.** Команды, которая печатает полный список портов relay, нет: печатается только
  порт замера. Нужны ещё его SSH, порты, которые он пересылает (TCP и UDP 443, порт подписки и порт API ноды), и
  его собственный диапазон SPA. Проще всего открыть у провайдера relay весь входящий трафик.

На хосте relay, от root, из обычной SSH-сессии:

```bash
curl -fsSL https://raw.githubusercontent.com/arngory/raycontrol/v0.26.0/install/bootstrap.sh -o bootstrap.sh
```

```bash
bash bootstrap.sh -relay /root/msk.bundle
```

Скрипт — тот же, что в §3.1: сверьте его так же. Файл `/root/msk.bundle` на хосте relay после установки удалите:
установка сохранила свою копию в `/etc/raycontrol/relay.bundle`.

Успех:

```
relay msk up: knocks with K_relay open the exit's services through here (exit 203.0.113.7).
This host's SSH (port 22) is reachable from 198.51.100.50, the relay's own admin addresses (rayctl relay set on the exit).
```

- Установка relay закрывает на его хосте всё, кроме пересылки и SSH с адресов администратора relay. Если проверка не
  проходит — например, ваш адрес не входит в список, — установка сама снимает периметр и оставляет хост открытым.
- **Аварийного входа на хост relay нет.** У него нет аварийного пакета устройства, и `rayctl knock` к relay не
  стучится. Если ваш адрес сменился, путь один — на ноде заменить список адресов SSH relay, без нового пакета:
  `rayctl relay set -admin 198.51.100.50 msk`. Relay берёт новый список в пределах минуты. Нет доступа и к ноде —
  остаётся консоль провайдера relay.
- Убрать relay — на ноде: `rayctl relay remove msk`. Только это отнимает у его адреса доступ к портам сервисов.
- Снять установку с хоста relay — на нём: `rayctl uninstall`. Команда возвращает всё, что меняла установка
  relay, и хост снова открыт.

**Обновление relay с v0.26.0: `rayctl update` на хосте relay.** От root, из обычной SSH-сессии с адреса
администратора relay:

```bash
rayctl update -check
```

```bash
rayctl update
```

- Релиз берётся и проверяется так же, как на ноде (§12.3): подпись, версия из подписи, назад — только с
  `-version` или `-force`, `-from DIR` для хоста без доступа к GitHub. Релиз новее установленного ставит `rayctl`
  самого релиза.
- Дальше — то же, что повторная установка с сохранённым пакетом (ниже): новые `rayspa`, `rayd` и `rayctl`, затем
  `rayctl install -relay /etc/raycontrol/relay.bundle` новой версии. Новый пакет с ноды не нужен.
- До любых изменений `rayctl update` проверяет пакет relay и вашу SSH-сессию: sshd на одном порту, сессия на нём,
  её адрес в списке администратора relay. Если адреса нет в списке, обновление отказывает и подсказывает команду для
  ноды: `rayctl relay set -admin <список>,<ваш адрес> msk`, затем `rayctl update` снова. Из tmux или с консоли
  адрес неизвестен: будет только предупреждение.
- Пока идёт `bootstrap.sh -relay`, обновление не начинается: `another rayctl install -relay is running`.
- После установки проверяется, что работает новый `rayspa` и его таблица применила периметр (адреса администратора,
  пересылка сервисов к ноде), пересылка включена, SSH открыт с адресов администратора, точка замера работает, если
  работала до обновления. Не прошло — relay возвращается к прежней версии с прежними юнитами и снимком периметра:

  ```
  rayctl: update failed, the previous version runs again: …
  ```

  Если не поднимается и прежняя, `rayctl` снимает периметр и оставляет хост открытым, без пересылки, и так и пишет:
  запереть вас relay не может. Тогда — повторная установка (ниже).
- `rayctl update -rollback` — вернуть версию до последнего обновления вручную.
- **Обновление оборвалось** (kill -9, пропало питание): следующий `rayctl update` отказывает и пишет
  `an update of this relay from … to … was interrupted: rayctl update -rollback puts … back`. Так и сделайте:
  `rayctl update -rollback` возвращает прежнюю версию, даже если хост остался открытым. Ctrl-C и обрыв SSH
  обновление не обрывают: оно само доводит откат до конца. Подробно, по шагам, —
  [spec/node-update-v1.md](spec/node-update-v1.md) §5.
- **Не перезагружайте и не выключайте хост relay, пока идёт обновление.** systemd остановит всё, откат не сможет
  снова запустить службы, и после загрузки relay может оказаться открытым и без пересылки. Тогда после загрузки
  выполните `rayctl update -rollback` (или повторную установку с пакетом, ниже); прервано ли обновление, говорит
  `rayctl update status`.
- `rayctl update status` на relay: установленная версия, сохранённая для отката, прерванное обновление, если было.
  Автообновления и обновления с телефона у relay нет: `rayctl update remote` и `auto` на нём отказывают — у relay
  нет API rayd для устройств.
- Пересылка прерывается на время обновления: обычно меньше минуты, а если нода не отвечает и обновление
  откатывается — до 5 минут. Клиенты переподключаются.
- **Что проверено.** Модульные тесты, весь путь обновления и отката — на временных каталогах. На настоящем хосте relay
  с systemd `rayctl update` **ни разу не запускался**, в CI его нет (см. в начале раздела).

**Relay до v0.26.0 и запасной путь.** `rayctl` relay старше v0.26.0 отказывает:

```
rayctl: this host is a relay: install/bootstrap.sh -relay with its bundle takes a new release
```

Такой relay, а также relay, который `rayctl update` оставил открытым, получает новый релиз повторной установкой
поверх — теми же двумя командами на хосте relay:

```bash
curl -fsSL https://raw.githubusercontent.com/arngory/raycontrol/v0.26.0/install/bootstrap.sh -o bootstrap.sh
```

```bash
bash bootstrap.sh -relay /etc/raycontrol/relay.bundle
```

Скрипт ставит последний опубликованный релиз; тег в адресе — версия самого скрипта (§3.1). После такого запуска
relay на v0.26.0 или новее, и дальше его обновляет `rayctl update`. Переход relay с v0.25.1 — шаг 6 в §12.5.

- `/etc/raycontrol/relay.bundle` — копия пакета relay, которую установка оставила на его хосте. Новый пакет relay
  с ноды для обновления не нужен. Если на ноде с тех пор выполняли `rayctl relay bundle`, прежний уже не действует:
  перенесите новый и укажите его.
- Запускайте из SSH-сессии с адреса администратора relay: установка проверяет, что после неё вы сможете зайти
  снова.
- На время установки пересылка прерывается, клиенты переподключаются.
- Разумно обновлять relay вместе с нодой. Пример зависимости: предел новых соединений на адрес действует на relay,
  только когда на нём стоит v0.24.0 или новее.
- **Что проверено.** В CI relay проверяется в сетевых пространствах имён (пересылка, стук, точка замера) и
  модульными тестами шагов установки, в том числе повторной поверх прежней. Целиком `bootstrap.sh -relay` на хосте
  с systemd в CI не запускается — ни первая установка, ни повторная. Запуск с путём
  `/etc/raycontrol/relay.bundle` следует из кода: установка читает пакет relay до любых изменений и не переписывает
  файл с тем же содержимым.

### 12.5. Обновление с v0.25.1 на v0.26.0

Для ноды, которая сейчас работает на v0.25.1. Раздел можно пройти, не читая остальные: ссылки на них — только за
подробностями. Что меняется в v0.26.0, коротко:

- в ссылках naive, `hy2-masq` и DoH появляется пин ключа сертификата сайта (§8, «Сертификат сайта и пины»);
- naive отвечает клиенту после соединения с адресатом и называет причину отказа (§8, «naive»);
- relay обновляется командой `rayctl update` на своём хосте (§12.4);
- `rayctl` есть для macOS и FreeBSD (§7), а `-remote` не читает файл устройства, открытый другим.

**Что произойдёт само и что нет.**

- **Автообновление v0.26.0 не поставит.** `rayctl update auto patch` ставит только патчи вашей минорной версии, а
  v0.26.0 — новая минорная. Нода на v0.25.1 об этом не скажет: строка `auto-update` в `rayctl status` говорит
  `up to date`. Что v0.26.0 вышла, видно в `rayctl update status` (`latest  v0.26.0`) и в `rayctl update -check`
  (шаг 1). Ноды новее v0.26.0 о новой минорной версии говорят сами (§12.3).
- **Обновить можно двумя способами:** `rayctl update` на ноде (шаги 1–2) или с телефона администратора, если на
  ноде включено `rayctl update remote on` (§12.3). Шаги 3–7 нужны в обоих случаях.
- **Клиентам ничего делать не надо.** Пины и новые ссылки они получат с подпиской.
- **Relay сам не обновится,** и его `rayctl` v0.25.1 обновлять relay не умеет: шаг 6.
- **Машины администраторов:** шаг 7.

**Шаг 1. Убедиться, что релиз есть.** На ноде, от root:

```bash
rayctl update -check
```

Что вы должны увидеть:

```
installed v0.25.1, release v0.26.0 available: rayctl update
```

Если вместо v0.26.0 назван более новый релиз — шаги те же, но вывод может отличаться. Если ответ
`raycontrol v0.25.1 is installed, the newest release` — v0.26.0 ещё не опубликован.

Перед обновлением сделайте резервную копию и заберите её с сервера (§12.2):

```bash
rayctl backup -o /root/node-before-v0.26.0.rcbak
```

**Шаг 2. Обновить.**

```bash
rayctl update
```

Что вы должны увидеть, по порядку:

1. `release v0.26.0 verified: its own rayctl updates the node` — подпись и сумма сошлись, дальше работает `rayctl`
   из нового релиза.
2. `rayctl v0.26.0 updates the node, handed over by the rayctl of v0.25.1`.
3. Вопрос:

   ```
   Update raycontrol v0.25.1 to v0.26.0? rayd, rayspa and the data plane restart; clients reconnect and send SPA again. Type yes to go on:
   ```

   Введите `yes`.
4. Строки `installed /usr/local/…` — по одной на бинарник, и в конце:

   ```
   raycontrol v0.26.0 is running; the previous binaries are kept for rayctl update -rollback
   ```

Что перезапускается: `rayd`, `rayspa` и data plane, как при любом обновлении. Xray — новый форк; фронт — у него
меняется конфигурация; naive — в его юните появляется `-reset-key`; бэкенды niko-server. Клиенты переподключаются
сами, перерыв — около минуты.

Если обновление не поднялось, оно откатывается само и заканчивается строкой
`update failed, the previous version runs again: <причина>`. Нода тогда работает на v0.25.1; причина — в строке.

**Шаг 3. Проверить ноду.**

```bash
rayctl status
```

В первой строке, `version`, — `v0.26.0`; строк `FAILED` нет. Если в строке `apply` стоит `FAILED` с текстом
`… failed, its process runs with the files of before` — см. таблицу в конце раздела.

```bash
rayctl update status
```

Первая строка — `installed  v0.26.0`; `remote` и `auto` — как были до обновления.

```bash
systemctl --no-pager list-units --all 'niko-*' rayd.service rayspa.service
```

У каждой службы `active` и `running`.

**Через десять минут после обновления** посмотрите ключ сайта:

```bash
rayctl service list
```

В строке `site`, в столбце `KEYS`, должно быть `key since ДАТА, next key pinned since ДАТА`. Первая дата — начало
срока нынешнего сертификата, вторая — примерно десять минут после обновления. С этого момента пины идут в подписки.

- **В `KEYS` пусто** — следующего ключа ещё нет: подождите несколько минут и посмотрите снова. Пока пусто, пинов в
  подписках нет.
- **`certificate of your own: no pins`** — на сайте свой сертификат, импортированный уже на v0.26.0. Шаг 4 сделан.
- **`key since …` при своём сертификате, импортированном до v0.26.0,** — шаг 4 обязателен.

**Шаг 4. Только если у вас свой сертификат.** Это нужно, если вы когда-либо ставили сертификат командой
`rayctl service cert` (в этом руководстве она нигде не требуется) и на ноде включён ACME, как ставит установка.
Такую ноду v0.26.0 считает выпустившей сертификат сама и через десять минут после обновления начинает отдавать пины
ключа вашего сертификата. Тогда следующий импорт с другим ключом (certbot по умолчанию делает новый ключ при каждом
продлении) без `-force` будет отклонён.

Сразу после обновления, от root на ноде, поставьте ещё раз тот сертификат, что стоит сейчас, — те же файлы цепочки и
ключа, без `-force`:

```bash
rayctl service cert site -chain /root/site-chain.pem -key /root/site-key.pem
```

Пути подставьте свои. Что вы должны увидеть:

```
certificate on site until … for …
with a certificate of your own the links of naive, hy2-masq and DoH under it carry no niko-pin:
clients check its chain only, as before pins
```

После этого в `rayctl service list` у `site` — `certificate of your own: no pins`, и ссылки идут без пина, как
раньше. Не помните, ставили ли свой сертификат, — посмотрите журнал действий: `rayctl audit -n 1000 | grep
service.cert`. Пустой ответ ничего не доказывает, если импорт был давно и запись уже ушла из журнала.

**Шаг 5. Подписки и приложение.**

- **Пины** появляются в подписках через десять минут после обновления. Клиенты берут их при очередном запросе
  подписки; подписка живёт 72 часа.
- **Что проверяет пин.** Niko 1.46.0 и новее: в naive — пин и цепочку, в `hy2-masq` и DoH — пин вместо цепочки.
  Niko 1.45.0 проверяет пин только в `hy2-masq`; в naive и DoH более ранние версии его не читают. Сертификат ноды не
  меняется, поэтому ни одна версия Niko после обновления не перестаёт подключаться.
- **Честный connect** naive: Niko 1.46.0 показывает причину отказа (`refused`, `unreachable`, `denied`, молчание
  адресата), только когда в нём включён эксперимент «Честный connect»; по умолчанию он выключен. Без него всё как
  раньше.
- **Что замечают люди:** один перерыв около минуты во время обновления.

**Если нужно вернуться на v0.25.1:**

```bash
rayctl update -rollback
```

Команда печатает `rolling back to v0.25.1 (asked for)` и перезапускает ноду на прежних бинарниках. Схему базы v0.26.0
не меняет, поэтому база остаётся как есть и подтверждения команда не спрашивает. Не добавляйте `-check`:
`rayctl update -check -rollback` — ошибка использования.

Цена отката для клиентов:

- **Откат в первые десять минут** после обновления ничего не стоит: пинов клиенты ещё не получили.
- **Откат позже.** v0.25.1 пинов не отдаёт, и клиенты, которые обновят подписку, их снимут. Но клиент, который уже
  взял пины и не обновлял подписку, держит их. Ключ сертификата при этом прежний, и пока всё работает. При следующем
  продлении v0.25.1 сделает новый ключ, и такие клиенты не пройдут naive, `hy2-masq` и DoH, пока не обновят
  подписку. Клиент, у которого один из этих профилей рабочий, перезапрашивает её сам, не раньше чем через 15–30
  секунд; остальные — при очередном запросе.

**Шаг 6. Relay.** Делается на каждом хосте relay, один раз.

> **Не проверено на настоящем хосте.** Ни `bootstrap.sh -relay` на хосте с systemd, ни `rayctl update` на relay не
> запускались в CI и ни разу не запускались на настоящем relay: обновление relay проверено только модульными
> тестами. Держите доступ к консоли провайдера relay, пока обновляете.

`rayctl` v0.25.1 на relay обновлять его не умеет и отвечает
`rayctl: this host is a relay: install/bootstrap.sh -relay with its bundle takes a new release`. Поэтому последний
раз relay обновляется повторной установкой с его пакетом. На хосте relay, от root, из SSH-сессии с адреса
администратора relay:

```bash
curl -fsSL https://raw.githubusercontent.com/arngory/raycontrol/v0.26.0/install/bootstrap.sh -o bootstrap.sh
```

```bash
sha256sum bootstrap.sh
```

Сумма должна быть `627dede2e62fce85ab576b0ab5ce903388be53597a2f74fe0dd19b2bbe7dadce`, как в §3.1. Другая — не
запускайте.

```bash
bash bootstrap.sh -relay /etc/raycontrol/relay.bundle
```

Успех — те же две строки, что при установке relay (§12.4):

```
relay msk up: knocks with K_relay open the exit's services through here (exit 203.0.113.7).
This host's SSH (port 22) is reachable from 198.51.100.50, the relay's own admin addresses (rayctl relay set on the exit).
```

- `/etc/raycontrol/relay.bundle` — копия пакета relay, которую оставила установка. Если на ноде с тех пор выполняли
  `rayctl relay bundle`, этот пакет уже не действует: перенесите новый и укажите его.
- Пересылка на время установки прерывается, клиенты переподключаются.
- Не перезагружайте и не выключайте хост relay во время установки и во время `rayctl update`. Если это случилось
  при `rayctl update`, после загрузки relay может быть открытым и без пересылки: выполните `rayctl update -rollback`
  (или `bash bootstrap.sh -relay /etc/raycontrol/relay.bundle`); `rayctl update status` говорит, прервано ли
  обновление.

Проверить версию relay:

```bash
rayctl update status
```

Первые строки — `host       relay` и `installed  v0.26.0 (rayctl)`.

Дальше relay обновляется на своём хосте командами `rayctl update -check` и `rayctl update` (§12.4). Автообновления и
обновления с телефона у relay нет.

**Шаг 7. Машины администраторов.**

- **Файлы устройств.** `rayctl` v0.26.0 не читает файл устройства (`.rcdev`), который может читать или менять группа
  или остальные, — и на Linux тоже. На каждой машине, где вы пользуетесь `-remote`:

  ```bash
  chmod 600 laptop.rcdev
  ```

  Файл должен принадлежать тому, кто запускает `rayctl`; чужой файл может взять только root. Старый `rayctl` права
  не проверял, так что до замены `rayctl` на своей машине ничего не ломается.
- **Новый `rayctl` на своей машине.** Linux — `rayctl` из архива ноды v0.26.0 (§7). macOS и FreeBSD — новые архивы
  `rayctl-darwin-arm64.tar.gz`, `rayctl-darwin-amd64.tar.gz` и `rayctl-freebsd-amd64.tar.gz`, если они вам нужны.
  Проверяются они тем же `SHA256SUMS` с подписью тем же ключом minisign
  (`RWQBergjLoDHqeme5vyIuIRXJLjTj1EF3jR1nlWBVJO3rWxgy9SZj4bD`), командами из §7.
- **Автоматика,** которая ставила сертификат командой `rayctl service cert` от члена группы `raycontrol`, теперь
  получает `permission_denied`: переведите её на root.

**Если что-то пошло не так.**

| Что вы видите | Причина | Что делать |
|---|---|---|
| `rayctl: device file laptop.rcdev is mode -rw-r--r--: it holds a private key, make it 0600: …` | `-remote` не читает файл, открытый группе или остальным | `chmod 600 laptop.rcdev`; на файловой системе без прав (FAT, SMB) — скопировать файл в домашний каталог и сделать `chmod 600` копии |
| `rayctl: device file … belongs to uid …, not to you (uid …): …` | файл другого пользователя | своя копия файла с `chmod 600`, или запуск от root |
| `rayctl: permission_denied: a site's certificate: root on the node only` | `rayctl service cert` не от root | от root на ноде |
| `rayctl: failed_precondition: not now: the links of naive, hy2-masq and DoH under site carry the pins of the node's keys, and this certificate has another key: …` | шаг 4 не сделан, а пины уже ушли клиентам; сертификат с другим ключом | поставить сертификат с ключом, который сейчас в работе, без `-force`; или с `-force`, если клиенты могут подождать новой подписки |
| на relay: `rayctl: this host is a relay: install/bootstrap.sh -relay with its bundle takes a new release` | на relay ещё v0.25.1 | шаг 6 |
| на relay: `rayctl: an update of this relay from … to … was interrupted: rayctl update -rollback puts … back` | прошлое `rayctl update` на relay оборвалось | `rayctl update -rollback`, затем снова `rayctl update` (§12.4) |
| после отката на v0.25.1 клиенты не проходят naive, `hy2-masq` или DoH | v0.25.1 продлил сертификат на новый ключ, а у клиентов пины ключа v0.26.0 | на ноде ничего: клиенты снимут пины с новой подпиской (выше, «Если нужно вернуться») |
| `rayctl status`: `apply FAILED …: service …: … of niko-….service failed, its process runs with the files of before …` | перезапуск службы после смены её файлов не удался; он остаётся в долгу и повторяется при каждом `apply` | `journalctl -u niko-ИМЯ -n 50` — почему юнит не стартует; исправить, затем `rayctl apply` |
| `update failed, the previous version runs again: …` | v0.26.0 не поднялась, откат выполнен | нода на v0.25.1; причина — в строке; приложите `rayctl report` к обращению |

### 12.6. Перезагрузка

Перезагружать сервер можно обычным `reboot`.

- **Службы поднимаются сами:** `rayd`, `rayspa` и все `niko-*` включены в автозапуск.
- **Периметр** ставит `rayspa` до подъёма сети (с v0.27.0), после системных файрволов, из сохранённого снимка: SSH с
  адресов администратора и SPA работают, даже пока `rayd` не поднялся. Если что-то снесёт таблицу
  (`systemctl restart nftables`, `nft flush ruleset`), `rayspa` вернёт её за секунды.
- **Если таблицы нет** (`rayspa` не поднялся, снимок не прочитан), хост открыт: так нода не запирает администратора.
  Это видно: `rayctl status` от root — `perimeter table FAILED perimeter down: the host is open`, `rayctl check` —
  `warn  perimeter`, в журнале `rayspa` — строка уровня error.
- **Конфиги, сертификаты и база лежат на диске,** поэтому сервисы стартуют сразу.
- **Открытые по SPA доступы пропадают.** Клиенты повторяют SPA сами. Адреса администратора хранятся на диске: SSH с
  них работает сразу после загрузки.
- **Часы.** После загрузки они должны синхронизироваться — обычно за секунды. До этого SPA может не проходить.
- **После перезагрузки** проверьте `rayctl status`, а снаружи — `rayctl probe`.

Новое ядро начинает работать только после перезагрузки. О неперезагруженном ядре напоминает `rayctl check`.

### 12.7. Смена ключей и сертификатов

Что меняется само и что — по команде:

| Что | Как меняется сейчас | Команда досрочной смены |
|---|---|---|
| учётные данные пользователей (UUID, пароли) | сами, раз в 30 дней, с перекрытием (§10.7) | нет: чтобы отнять доступ, отзовите устройство или отключите пользователя |
| ключи REALITY и имя его сервера | сами, раз в 90 дней | `rayctl service rotate reality` — через 3 дня, с публикацией заранее; `-now` — сразу |
| ключ печати dnstt | только по команде | `rayctl service rotate dns` |
| ключ сервиса masterdns | только по команде | `rayctl service rotate mdns` |
| ключ slipstream | не меняется: клиенты его закрепляют | нет |
| сертификат сайта (Let's Encrypt) | продлевается сам, когда осталась треть срока; ключ при этом прежний | свой сертификат: `rayctl service cert site -chain F -key F [-force]`, только root |
| ключ сертификата сайта (пин в ссылках naive, `hy2-masq`, DoH) | сам, при первом продлении после 180 дней, если следующий ключ пробыл в подписках 14 дней | `rayctl service rotate site` — после этих 14 дней; `-force` — сразу; `-fresh` — на новый ключ (§8, «Сертификат сайта и пины») |
| сертификаты подписки, API и hy2-obfs | самоподписанные, закреплены клиентами; не меняются | нет |
| ключи подписи ноды | не меняются | нет |
| ключ устройства | не меняется | отозвать устройство и выдать приглашение заново |
| клиентский ключ admin-устройства | по команде с него | `rayctl -remote ФАЙЛ remote rotate` |
| ключи relay | при каждом новом пакете relay | `rayctl relay bundle` |

- **Плавная смена** dnstt и masterdns: новый ключ сразу попадает в подписки, прежний принимается ещё 2 дня. Вторая
  такая смена в пределах этих двух дней отклоняется — `rayctl: failed_precondition: …`: прежний ключ ещё нужен
  клиентам. `-force` меняет всё равно и снимает его сразу.
- **Смена с `-now`** — когда ключ утёк: прежний перестаёт приниматься сразу, клиенты без свежей подписки теряют
  профиль, пока её не обновят.
- **Продление сертификата сайта** с v0.26.0 не перезапускает naive, сайт и DoH: они сами берут новую цепочку, и
  соединения не рвутся. `hy2-masq` и Yggdrasil при продлении перезапускаются, как раньше: их клиенты
  переподключаются.
- **Смена ключа сайта** (сама или по `rayctl service rotate site`) перезапускает naive, сайт, `hy2-masq` и Yggdrasil
  один раз. Что стоит каждый флаг — §8, «Сертификат сайта и пины».
- **Утёк пакет устройства или потеряно устройство** — ключи сервисов менять не нужно: отзыв устройства с v0.27.0
  сам меняет учётные данные его пользователя (§10.6).
- **Сменить токен Cloudflare:** `rayctl dns cloudflare` с новым токеном; старый отзовите в панели Cloudflare.

Когда были смены и когда следующая, показывает столбец `KEYS` в `rayctl service list`.

### 12.8. Удаление

Сначала резервная копия, если ноду может понадобиться вернуть (§12.2). Затем:

```bash
rayctl uninstall
```

Команда спросит подтверждение (`yes`) и вернёт всё, что меняли `install` и `apply`:

- останавливает и убирает службы и периметр — **сервер после этого открыт**, как до установки;
- удаляет записи raycontrol в Cloudflare;
- возвращает системные настройки и файлы к значениям до установки, убирает системных пользователей;
- удаляет бинарники и `/var/lib/raycontrol` со всеми ключами и пользователями.

В конце: `raycontrol is removed.`

| Флаг | Что меняет |
|---|---|
| `-yes` | не спрашивать подтверждение |
| `-keep-state` | оставить `/var/lib/raycontrol` (пользователи, ключи, сертификаты) для следующей установки; записи DNS тогда тоже остаются |
| `-keep-dns` | оставить записи в Cloudflare (при переезде) |
| `-purge-packages` | удалить и системные пакеты, которые ставил установщик (nftables, polkitd и другие) |

После удаления:

- **Отзовите токен Cloudflare:** удалите его в панели Cloudflare, там же, где создавали. Он был в базе ноды и
  остаётся во всех её резервных копиях.
- Удалите или уберите в надёжное место резервные копии: в них все ключи ноды.
- С `-keep-dns` записи с комментарием `raycontrol` остались в зоне: когда они не нужны, удалите их руками.

В CI удаление проверяется сравнением системы со снимком до установки.

## 13. Если что-то не работает

Сначала — три команды: `rayctl status`, `rayctl check` и `journalctl -u rayd -u rayspa -u 'niko-*' -p warning --since
-1h`. Затем найдите свой признак.

### Установка

| Признак | Причина | Что делать |
|---|---|---|
| `FAIL  port udp 53: … is taken by …` | на UDP 53 слушает другой DNS-сервер: bind9, dnsmasq, unbound или systemd-resolved, настроенный слушать не только на 127.0.0.53 и 127.0.0.54 | остановите его: `systemctl disable --now ИМЯ`. Обычный systemd-resolved с заглушкой на 127.0.0.53 не мешает и выключать его не нужно. После установки то же показывает строка `port53 FAILED` в `rayctl status`: `ss -lunp 'sport = :53'` |
| `FAIL  port tcp 443: … is taken by …` | в образе провайдера стоит nginx или apache | `systemctl disable --now nginx`, повторить |
| `cloudflare: HTTP 401: 1000 Invalid API Token` | вставлен ID токена вместо значения, лишние символы при вставке или токен отозван | создать токен заново (§1), затем `rayctl dns cloudflare` |
| `cloudflare: no zone for … that this token can see` | токену не дана зона домена или нет права Zone · Zone · Read | исправить права токена (§1), затем `rayctl dns cloudflare` |
| `Failed at step EXEC … Permission denied` у `niko-*` в журнале | каталоги или бинарники закрыты для служб: они созданы руками под umask 077 или установкой версии до v0.11.0 | `umask 022`, затем `rayctl apply`: он открывает каталоги и бинарники заново |
| `warn  updates: … asks for a reboot` или `kernel … is installed but … is running` | обновление поставило ядро, а сервер не перезагружен | `reboot`, затем `rayctl check` |
| `no admin address: pass -admin …` | установка запущена из tmux, screen или с консоли | добавить `-admin` со своим адресом |
| после установки не пускает по SSH | адрес администратора не ваш: вы заходили через VPN или сменился адрес | `rayctl knock @emergency.bundle` (§7); с консоли провайдера — `rayctl admin <адрес>` |
| после смены `Port` в `sshd_config` и перезапуска sshd не пускает по SSH; `rayctl check`: `warn  ssh port: sshd is configured for …, which the perimeter does not admit` | периметр пускает SSH только на порты сервисов `ssh`, а их порт установка прочитала один раз | с консоли провайдера вернуть прежний `Port` и перезапустить sshd; затем по шагам §7, «Сменить порт sshd на установленной ноде» |

### Сертификат не выпускается

Признак: нет строки `certificate stored`, в `rayctl status` — `acme site FAILED …`.

```bash
journalctl -u rayd --since -1h | grep -i certif
```

| Что в ошибке | Причина | Что делать |
|---|---|---|
| `lookup … on [::1]:53: … connection refused` или `127.0.0.1:53` | службы не могут прочитать `/etc/resolv.conf` или в нём нет `nameserver`; в `rayctl status` — `resolver FAILED` | `ls -lL /etc/resolv.conf` — нужно 0644 и строка `nameserver` (§2.5); `rayctl apply` ставит права сам |
| `does not resolve`, ошибки Cloudflare | записи DNS не на месте или токен не тот | `rayctl dns`; исправить; `rayctl dns sync` |
| без Cloudflare: таймаут проверки | TCP 80 закрыт у провайдера или нет записей A | открыть TCP 80 (§6.1), завести записи из `rayctl dns` |
| `urn:ietf:params:acme:error:…` | отказал сам Let's Encrypt, часто из-за лимита попыток | прочитать ошибку; не перезапускать `rayd` по кругу: лимит — 5 неудач в час на имя |
| `x509: certificate signed by unknown authority … (the node trusts its embedded root list: rayctl roots)`; в `rayctl status` — `tls-roots FAILED` | исходящий HTTPS идёт через прокси, который вскрывает TLS, или `-acme-directory` — частный УЦ: их корней нет во встроенном списке, а хранилищу системы нода не верит (§6.4) | `rayctl roots file ROOT.pem` с корнем прокси или УЦ; проверить — `rayctl roots`; повтор — `systemctl restart rayd` или подождать |

**Повтор.** Неудачу нода повторяет сама: через час, потом через 2, 4 и так до суток. Если причина была на вашей
стороне и вы её исправили, не ждите — `rayctl dns sync` или `rayctl dns cloudflare` запускают новую попытку сразу,
но не чаще раза в 15 минут на сайт. `systemctl restart rayd` тоже запускает попытку сразу.

### Клиенты не подключаются

| Признак | Причина | Что делать |
|---|---|---|
| `rayctl probe`: `node not reachable` | SPA не доходит или порты закрыты у провайдера | файрвол провайдера (§6.1); часы на обеих машинах; `systemctl is-active rayspa` |
| проба проходит с одного места и не проходит с другого | сеть клиента режет UDP | `rayctl probe -carrier tls @probe.bundle`; клиент сам переходит на SPA по TCP |
| SPA перестал проходить у всех сразу | часы ноды ушли больше чем на 30 секунд | `timedatectl`; `systemctl restart systemd-timesyncd` |
| у одного человека не проходит ничего | часы на его телефоне неверны | включить на телефоне время из сети |
| подписка есть, UDP-профили (Hysteria2) не работают | провайдер или сеть клиента режет UDP; у провайдера закрыты диапазоны меняющихся портов | `rayctl probe -channel`: потери в `channel udp`; открыть диапазоны (§6.1) |
| один профиль работает, только пока недавно работал другой | старый клиент не стучал SPA перед этим профилем: порт был открыт стуком соседнего. Так было с naive до Niko 1.32.1 и с Yggdrasil до v0.19.1 ноды | обновить Niko и ноду |
| «подключилось и через минуту отвалилось» на Yggdrasil с двух телефонов | нода до v0.20.1: один ключ на все устройства пользователя | `rayctl update` |
| naive: в журнале Niko `unexpected response status: 429` | пользователь упёрся в предел соединений | `rayctl conn-limit` покажет, кто и где; обычно это торрент-клиент или сканер |
| Hysteria2: `too many connections` | то же | то же |
| «трафик исчерпан», профилей нет | пользователь перешёл лимит | `rayctl user usage`; поднять лимит или `rayctl user reset-usage ИМЯ` |
| профиля нет в подписке | сервиса нет у пользователя или он выключен | `rayctl user list`, `rayctl service list` |
| свежее приглашение отклонено | истёк срок, неверный PIN пять раз или им уже воспользовались | `rayctl device list`; отозвать лишнее, выдать новое с другим именем устройства |
| `device "…" of …: the name is taken` при выдаче приглашения | у пользователя есть неотозванное устройство с таким именем (на ноде старше v0.27.0 — и отозванное) | другое имя или сначала отозвать прежнее устройство |
| отозванное устройство продолжает работать | нода старше v0.27.0: отзыв не менял учётные данные; или процесс не принял изменение | `rayctl status` (ошибка применения); на старой ноде — §10.6, последний абзац |
| после смены вашего адреса сервер не пускает по SSH | адрес администратора — один точный адрес | `./rayctl knock @emergency.bundle` со своей машины (§7); с консоли провайдера — `rayctl admin`; впредь — сеть провайдера в списке |
| после `rayctl restore` не пускает по SSH или отозванные снова работают | восстановление вернуло адреса администратора из копии; устройства, отозванные после копии, возвращаются, только если база этой ноды о них не знает (новый сервер) или был `-no-carry` | §12.2: `rayctl admin`; устройства из предупреждения `restore` — отозвать снова |
| naive, `hy2-masq` и DoH перестали проходить у клиентов, остальные профили работают | пин не сошёлся: ключ сайта сменён `rayctl service rotate site -force` или `-fresh`, поставлен свой сертификат с `-force` или нода откатилась ниже v0.26.0 и продлила сертификат на новый ключ | ничего на ноде: клиент с этим рабочим профилем сам перезапросит подписку через 15–30 с, остальные — при очередном запросе (§8, «Сертификат сайта и пины») |
| `niko-*` перезапускается по кругу | конфиг не принят или занят порт | `journalctl -u niko-ИМЯ -n 50`; `ss -ltnup 'sport = :443'` |
| сервис в локальной сети ноды недоступен через прокси (`10.x`, `192.168.x`, `127.0.0.1` ноды, адрес метаданных провайдера); naive отвечает `denied` | так задумано: data plane не ходит в собственные и локальные сети ноды — ни процессы (naive, Xray, Hysteria2, `IPAddressDeny`), ни периметр (часть `local` политики выхода, с v0.27.0); иначе любой пользователь достал бы службы ноды, API метаданных и соседей в частной сети VPS | не открывать. `rayctl egress allow local` снимает только правило периметра, проверки процессов остаются; к своим сервисам ходите по SSH или поднимите их на публичном адресе. Подробно — [egress-policy-v1](spec/egress-policy-v1.md) §10 |
| ничего не открывается после `nft flush ruleset` или перезапуска firewalld | снесена таблица периметра | `rayspa` возвращает её за секунды сам; если нет — `systemctl restart rayspa` |
| `rayctl status`: `perimeter table FAILED perimeter down: the host is open` | таблицы периметра нет: `rayspa` не поднялся после загрузки или его таблицу не берёт ядро; хост открыт, SSH пускает без стука | `journalctl -u rayspa -b -p warning` — почему; исправить, `systemctl restart rayspa` |
| `rayctl status`: `perimeter FAILED … rayspa has not followed the perimeter …` | `rayspa` не связан с `rayd` дольше 90 с: остановлен или перезапускается по кругу | `systemctl status rayspa`; строка `perimeter table` от root скажет, открыт ли хост |

### DNS-туннели

| Признак | Причина | Что делать |
|---|---|---|
| `dns-zone … FAILED`, шаг `parent` не `ok` | делегирования нет или оно ведёт не на ноду: записи не созданы, сменился адрес | `rayctl dns`; `rayctl dns sync`; без Cloudflare — завести записи у регистратора |
| делегирование верное, но ни один резолвер не довёл пробу | входящий UDP 53 закрыт у провайдера | открыть UDP 53; спросить поддержку провайдера |
| с ноды всё проходит, у клиента туннель не работает | резолвер клиента не доходит до ноды или режет ответы | `rayctl probe -dns` из сети клиента; сменить резолвер в клиенте |
| `port53 FAILED` | рядом с фронтом на UDP 53 встал другой DNS-сервер | `ss -lunp 'sport = :53'`; остановить его |
| `dns-zone … FAILED: … no answer in 5s (last ok never)` у всех туннелей на ноде v0.13.0–v0.18.0 | ошибка самой проверки, клиентам не мешает | `rayctl update` |

### Ping и скорость

| Признак | Причина | Что делать |
|---|---|---|
| ping через VPN показывает 1–20 мс до любого адреса и один хоп | отвечает сам телефон: на этом профиле ping через ноду не идёт | это не поломка; §11. Проверка: `ping 203.0.113.77` |
| ping через VPN показывает 100 % потерь, а сайты открываются | в Niko включена настройка «Не отвечать на ping с телефона», а профиль ping не несёт | так и задумано; §11. Настоящий ping — только naive с ping через ноду |
| ping через VPN «не работает» после включения настройки в Niko | на ноде не выполнен `rayctl apply` после `icmp=on`, или профиль не naive | §9; `rayctl service set naive icmp=on`, `rayctl apply` |
| traceroute не показывает путь до ноды | так задумано: путь до ноды внутри туннеля | — |
| нода не отвечает на ping снаружи | так задумано | проверять `rayctl probe` |
| низкая скорость на DNS-туннеле | природа канала: 0,1–3 Мбит/с | использовать как аварийный |
| рывки в звонках на REALITY или naive | UDP идёт поверх TCP | для звонков — Hysteria2 |

### Обновление

| Признак | Причина | Что делать |
|---|---|---|
| `update failed, the previous version runs again: …` | новая версия не поднялась; откат выполнен | нода работает на прежней версии; причина — в строке; приложите `rayctl report` к обращению |
| `this host is a relay: install/bootstrap.sh -relay …` | `rayctl update` relay старше v0.26.0 | повторная установка с пакетом, §12.4 |
| `this host is a relay: remote and automatic updates do not apply …` | `rayctl update remote` или `auto` на хосте relay | relay обновляется только `rayctl update` на его хосте, §12.4 |
| `… not from the relay's admin addresses …, then rayctl update again` | SSH-сессия не с адреса администратора relay | на ноде `rayctl relay set -admin …`, затем `rayctl update` на relay, §12.4 |
| `an update of this relay … was interrupted: rayctl update -rollback …` | прошлое обновление relay оборвалось | `rayctl update -rollback` на relay, §12.4 |
| `the last update or rollback of this relay did not bring it back (open and not forwarding, unless its rayspa still runs) …` | прежняя версия не поднялась, хост открыт без пересылки, если `rayspa` удалось остановить | `rayctl update -rollback` или повторная установка с пакетом, §12.4 |
| `permission_denied: a site's certificate: root on the node only` | `rayctl service cert` не от root: с v0.26.0 импорт — только root на ноде | от root на ноде; автоматику, которая импортирует от группы `raycontrol`, перевести на root |
| `device file … is mode …: it holds a private key, make it 0600: …` | `rayctl` v0.26.0 не читает файл устройства, открытый группе или остальным | `chmod 600 ФАЙЛ` (§10.4) |
| `rayctl status`: `apply FAILED …: service …: … of niko-….service failed, its process runs with the files of before …` | перезапуск после смены файлов не удался; он остаётся в долгу и повторяется при каждом `apply` | `journalctl -u niko-ИМЯ -n 50` — почему юнит не стартует; исправить, затем `rayctl apply` |
| `unexpected "slipstream-server" in the archive` | на ноде `rayctl` старше v0.15.0 | `rayctl update -version v0.15.0`, затем `rayctl update` |
| `rayd does not give the deployment's inputs (GetDeployInputs)` | бинарник `rayctl` новее работающего `rayd` | `systemctl restart rayd`, затем `rayctl apply` |
| `another … is running` | идёт другое обновление или `apply` | дождаться |
| `warning: github.com: x509: …; trying again with the system's certificate store` | цепочка GitHub или зеркала ведёт к корню не из встроенного списка: список старше смены корня у хоста или исходящий HTTPS идёт через прокси, который вскрывает TLS | ничего: подпись релиза проверяется всё равно, новый релиз приносит новый список; за таким прокси — `rayctl roots file ROOT.pem` (§6.4) |
| `downloading SHA256SUMS: … x509: certificate signed by unknown authority …` | корня нет ни во встроенном списке, ни в хранилище системы: прокси, который вскрывает TLS | `rayctl roots file ROOT.pem` с корнем прокси, затем `rayctl update`; без сети к GitHub — `rayctl update -from DIR` (§12.3) |

## 14. Чек-лист перед выдачей подписки людям

Пройдите по порядку. Каждый пункт — команда и то, что должно получиться.

**Сервер**

- [ ] `rayctl check` заканчивается строкой `This host can run a node`; среди `warn` нет `updates` и `clock`.
- [ ] `timedatectl` показывает `System clock synchronized: yes`.
- [ ] Автообновления системы включены (§2.1); вход по SSH — только по ключам (§2.6).
- [ ] Аварийный пакет устройства сохранён вне сервера, и `./rayctl knock @emergency.bundle` с вашей машины
      открывает SSH.
- [ ] `rayctl admin` показывает ваши нынешние адреса. Если ваш адрес меняется — в списке сеть провайдера, либо
      вход через `knock` проверен (§0, §7).
- [ ] У вас есть доступ к консоли провайдера на случай, если SSH закроется.
- [ ] В группе `raycontrol` и среди admin-устройств — только те, кому вы доверяете ноду целиком (§6.6).
- [ ] В зоне Cloudflare одна нода (§1).

**Нода**

- [ ] `rayctl status`: версия последняя (`rayctl update -check`), нет строк `FAILED`, `acme site ok`.
- [ ] `rayctl dns`: провайдер подключён, строк `problem:` нет.
- [ ] `systemctl --no-pager list-units --all 'niko-*' rayd.service rayspa.service`: все `active running`.
- [ ] С DNS-туннелями: `rayctl dns check -now` — у каждой зоны нет `FAILED`.
- [ ] У провайдера открыты порты из строки `must let in` и диапазоны меняющихся UDP-портов — либо весь входящий
      трафик (§6.1).
- [ ] Сервер перезагружен после установки хотя бы раз, и после перезагрузки `rayctl status` снова без `FAILED`.

**Снаружи**

- [ ] `rayctl probe -channel @probe.bundle` с другой машины: `both signatures valid`, все нужные профили в списке,
      в `channel udp` нет потерь.
- [ ] То же из сети, похожей на сеть ваших людей: мобильный интернет нужного оператора.
- [ ] Свой телефон с Niko добавлен по приглашению; каждый профиль по очереди подключается и открывает сайт.
- [ ] Тестовое устройство для пробы отозвано, файл пакета устройства удалён.

**Правила и запас**

- [ ] Вы решили про торренты и SMTP (`rayctl egress`), лимиты трафика и сроки пользователей (§9).
- [ ] `rayctl node name` и, если нужно, `rayctl node note` заданы: люди видят их в приложении.
- [ ] Резервная копия сделана, лежит вне сервера, фраза записана отдельно (§12.2).
- [ ] Вы знаете, как обновлять ноду (§12.3), и решили, включать ли автообновление.
- [ ] Люди предупреждены: ping через VPN ничего не показывает (§11); приглашение одноразовое; PIN придёт отдельно.

**Каждому человеку**

- [ ] Свой пользователь (`rayctl user add`) и своё приглашение на каждое устройство — с коротким сроком и PIN.
- [ ] После регистрации в `rayctl device list` у устройства стоит `registered`.

## 15. Что готовится

Этого в v0.26.0 **нет**; команд для этого не существует. Перечислено, чтобы вы не искали:

- обновление relay по просьбе ноды, чтобы обновление с телефона администратора обновляло и relay (вторая волна; на
  relay будет выключено по умолчанию). Сейчас relay обновляется только `rayctl update` на его хосте (§12.4);
- собственная сборка сетевой библиотеки для naive в клиенте;
- ping через Hysteria2: сейчас он есть только у naive.

На стороне клиента ждёт выпуска настройка «Не отвечать на ping с телефона»: её нет в Niko 1.45.0, она появится в
следующем выпуске и будет выключена по умолчанию (§11).

Планы и история — в [04-roadmap.md](04-roadmap.md) и [handoff/SYNC.md](handoff/SYNC.md).
